# 12장 개발 계획 — 태그 목록과 사용 빈도

작성일: 2026-10-28

목표는 엔진의 `list_tags` / `list-tags` 응답을 손실 없이 받아 태그 표기 선택에 사용할 수 있게 하는 것이다. 12장은 색인에서 읽기 층 메인 노트의 태그를 집계하는 **읽기 명령**이다. 앱이 파일이나 DB를 직접 훑어 결과를 재계산하지 않는다.

근거: [12장 명세](./spec-chapter-12-list-tags.md), [5장 인자](./spec-chapter-05-arguments.md), [6장 출력과 오류](./spec-chapter-06-output-and-errors.md), [8장 색인 신선도](./spec-chapter-08-index-and-freshness.md).

## 1. 현재 상태와 선행 관계

- 공통 `Transport`, `decodeResponse`, 오류 분류, mock과 회고 읽기 클라이언트가 있다. 12장 전용 DTO·클라이언트는 없다. `DocRoute.tsx`의 태그 표시는 현재 정적 화면이며 엔진 연동의 근거가 아니다.
- 실제 네이티브 전송·파일 감시와 태그 선택 UI는 아직 별도 작업이다. 12-1은 mock 기반 계약만으로 독립 개발할 수 있다.
- 8-2의 오래된 예약 콜백 문제는 해결됐으나, 성공 응답의 중첩 추가 필드, 실패 원인 및 구독자 간 변경 가능한 바이트 격리는 [재검토](./review-chapter-08-task-02-followup.md)에서 보완 대상으로 남았다. 12-2에서 코디네이터 상태를 실제 화면에 연결하기 전에 해결 및 재검증한다.
- 7-1 쓰기 결과의 미분류 실패·미정의 종료/WL 조합 처리도 별도 보완 대상이다. 태그를 저장하는 흐름에 연결하기 전에 해결한다. 12-1의 읽기 계약에 두 작업을 섞지 않는다.

## 2. 명세에서 유지할 의미

| 구분 | 엔진 계약과 앱의 처리 |
|---|---|
| 데이터 범위 | 어느 표면이든 `reading` 층 메인 노트만 센다. 하위 노트, 기록 층, 휴지통, 색인되지 않은 충돌 사본 등은 포함되지 않는다. 전체 vault의 모든 태그라고 표시하지 않는다. |
| 개수 | 노트 하나에 같은 태그는 한 번만 센다. count는 노트 수이며 같은 태그의 입력 횟수가 아니다. |
| 검색 | 엔진이 query 앞뒤 공백을 5.3 규칙으로 제거하고 빈 값은 필터 없음으로 취급한다. 부분 일치이며 ASCII에만 대소문자 무시가 적용된다. `%`, `_`, `\\`는 리터럴이다. 앱에서 일반적인 Unicode 대소문자 접기나 정규화를 적용하지 않는다. |
| 순서 | count 내림차순, 동률은 태그 UTF-8 바이트 오름차순. limit은 정렬 후 앞에서 자른다. 앱은 localeCompare나 UTF-16 정렬로 다시 섞지 않는다. 서로 다른 대소문자 및 NFC/NFD 표기는 별개다. |
| limit | 생략 또는 빈 명령 옵션은 전체다. 0은 전체가 아니라 오류이며 최대 허용 32비트 정수는 2,147,483,647이다. 도구 표면은 null·문자열 숫자·소수 등을 타입 오류로 거절한다. |
| 신선도 | 파일을 열거나 색인을 갱신하지 않고 마지막 색인 상태를 읽는다. 성공 또는 빈 배열만으로 최신 색인·태그 없음·vault 전체 건강을 확정하지 않는다. |
| 긴 query | 이스케이프 후 앞뒤 `%`를 포함한 LIKE 패턴이 UTF-8 50,000바이트를 넘으면 비교할 reading 메인 노트 태그 행이 있을 때 예상 밖 실패가 날 수 있다. 행이 없으면 `[]`일 수 있으므로 앱에서 길이만으로 엔진 결과나 WL-400을 단정하지 않는다. |

## 3. 12-1 — 응답 계약과 명령 클라이언트

첫 구현 단위는 순수 타입 검사, 두 표면의 호출과 fixture다. 권장 파일은 `src/engine/commands/listTags.ts`, `src/engine/__fixtures__/chapter12/`, 관련 테스트 및 `src/engine/index.ts`, README다. 프로젝트 구조에 맞는 동등한 파일 분리는 허용한다.

### 3.1 응답과 검증

- 성공 응답은 배열이며 원소는 `tag: string`, `count: number`다. count는 집계 결과이므로 1 이상의 정수로 검사한다. 빈 배열은 정상이다. 누락 키, null, 문자열 숫자, 0, 음수, 소수, 잘못된 뒤쪽 원소를 거절한다.
- `ResponseValidator<T>` 타입 가드와 `decodeResponse`를 재사용한다. 스키마 불일치는 `contract_violation/schema_mismatch`이고 엔진 오류 코드로 바꾸지 않는다. 성공 시 stderr 진단, 실패의 원본과 기존 분류를 보존한다.
- 객체의 추가 키는 버리지 않는다. 배열·문자·태그 표기와 원소 순서를 변경하지 않는다. 중복 제거, 빈 목록 채우기, 정렬·검색·limit 재적용은 하지 않는다. 입력 인자와 실제 결과의 의미적 일치 여부를 로컬에서 추측해 거절하지 않는다.
- JSON 숫자는 JavaScript number로 표현된다. 엔진이 보장하지 않은 임의의 더 작은 count 상한을 설정하지 않는다. 직렬화 숫자의 정밀도 한계가 실제로 중요한 환경에서는 원본 바이트를 보존하고 별도 계약으로 다룬다.

### 3.2 호출 표면

두 표면을 이름과 인자에서 명시적으로 구분한다. API 이름은 구현 시 조정할 수 있다.

```typescript
createListTagsClient(transport).listTagsTool({ query: '랭', limit: 10 })
// execute({ command: 'list_tags', args: ['{"query":"랭","limit":10}'] })

createListTagsClient(transport).listTagsCommand({ query: 'a=b', limit: 10 })
// execute({ command: 'list-tags', args: ['query=a=b', 'limit=10'] })
```

- 도구 표면은 JSON 객체 한 칸이고 기본 호출도 `['{}']`다. 명령 표면은 `query=<원문>`과 `limit=<값>`의 이름 인자이며 기본 호출은 `[]`다. 한 칸의 값에 `=`나 `--`가 있어도 `query=` 뒤에 그대로 둔다. shell 명령 문자열을 만들지 않는다.
- 저수준 API는 query의 공백·특수문자·NFC/NFD를 보정하지 않는다. 지정하지 않은 옵션은 생략하고 `query: ''`는 명시적으로 전달한다. 타입으로 표현할 수 있는 범위의 엔진 실패를 가로채 임의 WL 오류나 빈 결과로 만들지 않는다.
- 도구와 명령의 타입·빈 값 규칙이 다르므로 한쪽 입력을 다른 쪽으로 조용히 바꾸지 않는다. 잘못된 JSON, null, 모르는 키, 반복 옵션 등 전체 원시 문법의 시험은 기존 `Transport.execute`에 맡긴다. `JSON.stringify`가 NaN/Infinity를 null로 바꾸는 점을 고려해 공개 숫자 API가 이 값을 조용히 다른 요청으로 바꾸지 않도록 명시적인 로컬 입력 오류 또는 명확히 제한된 타입/검증 정책을 정하고 테스트한다. 이 로컬 오류에 WL 코드를 붙이지 않는다.
- `query`와 `limit` 이외의 layer 옵션은 추가하지 않는다. 필터나 긴 query의 실제 SQLite 동작은 엔진의 책임이며 앱이 재구현하지 않는다.

### 3.3 픽스처와 검증

- 12.6의 `랭킹`, `실험` 두 항목 및 끝 LF 1개를 명세 fixture로 기록하고 UTF-8 바이트·키 순서·들여쓰기를 확인한다. `[]`, count 차이·동률·보충 평면 문자·NFC/NFD·대소문자 분리·추가 필드·오류는 합성 fixture임을 표시한다. 실제 응답 검증은 키 순서나 들여쓰기와 분리한다.
- 도구/명령의 기본 호출, 한 옵션과 양 옵션, `query=a=b`, 공백, `%`, `_`, `\\`, 빈 query, 한글, 대소문자와 NFC/NFD를 원문 argv로 검증한다. 0·음수 등 엔진이 거절하는 값은 명세에 맞는 실패 응답 mock을 주입해 공통 분류가 보존됨을 확인한다.
- 성공·빈 배열·모든 원소 검사·추가 키 및 응답 순서 보존, malformed JSON·빈 stdout·스키마 위반, 성공 stderr, WL-400, 예상 밖 실패와 로컬 전송 실패를 검증한다. 모의 응답은 엔진의 실제 검색·정렬 동작 검증이 아님을 밝힌다.
- 완료 기준: 기존 테스트와 신규 테스트, `npm test`, `npm run build` 통과. 공식 12장 8건 수용 묶음을 실행할 수 없다면 실행했다고 주장하지 않는다.

## 4. 12-2 — 태그 선택 화면과 신선도 연결

선행 조건은 실제 엔진 Transport, 8-2 잔여 격리 결함 해결, 색인 갱신 연결 및 저장 흐름의 7-1 보완이다. 이 조건이 충족되기 전에는 UI 목업과 실제 결과를 혼동하지 않는다.

1. vault와 query별로 응답·읽는 중·오류·마지막 성공을 구분한다. 요청 완료 순서가 뒤바뀌거나 vault가 전환돼도 오래된 결과가 현재 선택지를 덮지 않게 한다. 실패를 빈 배열로 바꾸지 않고 이전 결과가 있다면 신선도 상태와 함께 유지한다.
2. 8장의 재조정 성공 후 영향을 받는 태그 목록을 다시 읽는다. 갱신 실패 또는 보류 중에는 기존 결과를 최신으로 단정하지 않는다. 재조정 자체와 `list_tags` 호출을 하나의 원자적 스냅숏으로 가정하지 않는다.
3. 받은 순서와 표기를 그대로 보여 주고 count가 읽기 층 메인 노트 수임을 분명히 한다. 읽기 층 이외의 태그나 하위 노트 전용 태그도 반드시 검색된다고 안내하지 않는다.
4. limit을 사용해 응답이 limit개인 경우 목록의 완전성을 추측하지 않는다. 사용자 입력과 서버 query가 달라지기 전 이전 결과를 현재 검색 결과로 오인하지 않게 표시한다. 자동 재시도·정렬 변경·클라이언트 로컬 부분 검색으로 엔진 동작을 바꾸지 않는다.
5. 태그 선택은 원문을 유지하되 저장 동작은 별도의 쓰기 계약과 초안 정책을 따른다. 목록에 없는 태그라는 사실만으로 태그를 자동 생성·삭제하거나 원본을 변경하지 않는다.

완료 기준: 지연 mock으로 검색·vault 전환 경합 및 실패 상태를 검증하고, 실제 전송/감시가 준비되면 격리 vault에서 reindex 전후 변경과 선택 흐름을 따로 확인한다. 실제 엔진 검증과 mock 검증을 구분해 기록한다.

## 5. 실제 엔진 계약 검증 — 별도 통합 단계

공식 묶음의 8건은 도구 표면의 전체 1건, 빈 결과 query 4건, limit 1·10·1000 세 건이다. 여기에 엔진을 이용한 별도 경계 검증을 추가한다. 이 단계는 12-1 mock 통과와 별개다.

- reading/기록 층 메인 노트, 하위 노트, 휴지통, 한 노트의 중복 태그로 집계 범위와 count 확인. count가 다른 태그 및 동률에서 UTF-8 순서와 limit 절단 확인(보충 평면 문자 포함).
- ASCII 대소문자, `É`/`é`, `%`·`_`·`\\`, NFC/NFD, 빈 query, 명령·도구 표면, 0·소수·null·문자열·32비트 경계 및 오류 분류 확인. 오류 문구와 우선순위를 재현할 경우 12.4와 5장 기준으로 비교한다.
- 패턴 50,000바이트 경계에서 태그 행이 있는 vault와 없는 vault를 각각 확인한다. query 길이 자체가 아니라 이스케이프와 양쪽 `%`를 포함한 UTF-8 바이트 수이며, 특별히 49,998 ASCII, 16,666 한글, 24,999개의 `%`와 그 다음 경계를 구분한다.
- 색인 후 파일을 바꾸고 재조정 전후를 비교한다. 실행 환경·엔진 버전·fixture·수용 묶음 여부를 결과와 함께 남긴다. 앱이 SQLite를 직접 조회하거나 실제 파일을 모조 구현해 엔진 검증을 대신하지 않는다.

## 6. 다음 개발 요청 범위

**12-1의 타입·validator·두 호출 표면·fixture·테스트·사용 예시만 구현한다.** 12-2 UI·감시·네이티브 전송, 8-2와 7-1 결함 수정, 엔진 재구현은 별도 작업이다. 이번 문서는 계획이며 앱 소스나 기존 개발 현황의 완료 상태를 바꾸지 않는다.
