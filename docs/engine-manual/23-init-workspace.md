# withlog > 1부 vault 엔진 설명서 > 23장 명령 init-workspace

최종 수정: 목요일 10/22 · 22:57

새 vault에 골격을 갖추고 빌트인 템플릿을 심어 쓸 수 있는 워크스페이스로 만든다. 이미 워크스페이스인 vault에서 부르면 빠진 폴더와 빠진 템플릿만 채우고 조용히 끝난다.

- 단발 모드로 엔진을 띄워 vault를 새로 만들거나 다시 열 때 앱이 가장 먼저 부르는 명령이다(3.1).
- `.withlog/workspace.json` 표식 파일이 생겨야 그 vault가 워크스페이스가 되고(1.1), 이후의 쓰기 명령이 표식 확인을 통과한다(7.1).
- 앱이 넘겨준 빌트인 템플릿을 `.withlog/templates/` 아래에 쓴다(2.4).
- 멱등(idempotent)이다. 이미 있는 파일과 폴더는 덮지 않고, 표식 파일이 이미 있으면 `created: false`로 알린다.

## 23.1 한눈에

| 명령 | 하는 일 | 쓰기 깃발 | 읽는 자리 | 바꾸는 자리 |
|---|---|---|---|---|
| `init-workspace` | 골격 폴더를 만들고 템플릿과 표식 파일을 심는다 | 씀 | 없음(파일의 있음만 본다) | `.withlog/agendas/`, `.withlog/templates/doc/`, `.withlog/templates/ritual/`, `notes/`, `.withlog/templates/` 아래 파일들, `.withlog/workspace.json` |

엔진 안의 실제 차례는 이렇다.

1. 인자를 가르고 검증한다(23.3).
2. 색인을 맞춘다(8장).
3. vault가 git 저장소면 앞쪽 자동 커밋 처리를 한다(31장).
4. 골격 폴더 4곳을 차례로 만든다(23.5).
5. 문서 템플릿을 차례로 심는다(23.5).
6. 리추얼 템플릿을 차례로 심는다(23.5).
7. 표식 파일이 없으면 쓴다(23.5).
8. vault가 git 저장소면 뒤쪽 자동 커밋 처리를 한다(31장).
9. stdout으로 결과를 알린다(23.6).

## 23.2 부르는 법

| 표면 | 꼴 | 쓰는 쪽 |
|---|---|---|
| 명령 | `init-workspace [name=<워크스페이스 이름>] [templates=<빌트인 템플릿 JSON 배열>]` | 앱 |
| 도구 | 없음. `init_workspace`는 모르는 명령이다 | 없음 |

단발 모드에서는 이렇게 부른다(예시 값).

```bash
java -jar wl-sidecar.jar init-workspace name=새-vault 'templates=[]' --withlog.vault=/Users/me/새-vault --withlog.db.home=/Users/me/.wl/db
```

셸에 따라 `[]`가 파일 이름 패턴으로 풀릴 수 있어서 `templates=` 칸은 따옴표로 감싼다. 엔진이 받는 칸은 따옴표를 뗀 `templates=[]`다.

`wl-cli init-workspace ...`를 부르면 같은 argv가 소켓으로 serve 모드 엔진에 간다(3.3). 앱이 보내는 argv는 `["init-workspace", "name=<이름>", "templates=<JSON 배열 글>"]`이고, 2026-09-10에 빌트인 템플릿을 모두 뺀 뒤로 배열이 `[]`다. 템플릿 본문의 정본이 앱이라 엔진 안에는 빌트인 본문이 없고, 그래서 본문을 인자로 받는다.

vault 뿌리는 인자로 안 받는다. 엔진이 이미 `WITHLOG_VAULT`나 `--withlog.vault=`로 vault 1개에 묶여 있어서, 인자로 또 받으면 오타 난 경로가 새 vault 만들기로 조용히 성공하기 때문이다. 뿌리 폴더를 만들지도 못한다. 폴더가 없으면 엔진이 뜨지 못하므로(1.1, 3.1), 이 명령이 도착했다는 것이 폴더가 있다는 뜻이다. 뿌리 폴더는 2부 호스트가 먼저 만든다.

## 23.3 인자와 검증

**칸 가르기.** 인자는 5.2의 명령 표면 규칙으로 가른다. `--`로 시작하는 칸은 설정이라 뺀다. 첫 `=`가 맨 앞이 아닌 칸이 옵션이고, 옵션 이름은 첫 `=` 앞을 다듬은 글이고, 값은 첫 `=` 뒤의 글을 다듬지 않은 그대로다. 그 밖의 칸(`=`가 없거나 맨 앞에 있는 칸)은 자리 인자다. 칸을 앞에서부터 보다가 `name`과 `templates` 밖의 옵션을 만나면 그 자리에서 서고, 다 본 뒤 자리 인자가 1칸 이상이면 선다. 그래서 자리 인자와 모르는 옵션이 함께 있으면 자리와 상관없이 모르는 옵션으로 선다. 같은 옵션을 2번 주면 뒤엣것이 이긴다. 자리 인자를 1칸도 안 받는 것은, 남는 자리 인자를 조용히 버리면 문법을 틀린 사람이 그 사실을 모르기 때문이다.

`name`. 없어도 된다. 주면 다듬지 않고 그대로 쓰고, 공백뿐이면(`name=` 포함) 거절한다. 안 준 것은 「알아서 정하라」이고 빈 글은 「이름 없는 워크스페이스」라서 뜻이 다르다. 안 주면 vault 폴더 이름을 쓴다. 그 이름은 엔진이 뜰 때 정리한 vault 경로의 마지막 조각이다. vault 경로는 받은 값을 다듬고, 상대 경로면 그 경로를 정한 프로세스의 작업 폴더에 대고 절대 경로로 바꾸고, `.`과 `..`을 글자로 지우고, 끝의 `/`를 뗀 글이다. 단발 모드는 엔진 프로세스의 작업 폴더에 대고 풀고, `wl-cli`를 거치면 `wl-cli`가 자기 작업 폴더에 대고 푼 절대 경로를 LaunchAgent plist에 적어 serve 모드 엔진에 넘긴다(3.4). 심볼릭 링크는 안 풀고, 뿌리가 `/`면 빈 글이다. 기본 이름은 빈 글이어도 거절하지 않는다. `name`은 표식 파일을 이번에 쓸 때만 쓰이고, 이미 워크스페이스면 무시된다. 다만 공백뿐인 `name` 검사는 그때도 돈다.

`templates`. 없어도 되고, 빈 배열이 정상이다. 주면 그 값 전체가 JSON 배열 1개여야 하고, `templates=`처럼 빈 글도 배열이 아니라서 거절한다. 읽개는 kotlinx.serialization 1.6.3의 JSON 읽개를 기본 설정(`isLenient` 끔)으로 쓰고, 동작은 이렇다(코드 읽기로 확인. 라이브러리는 읽기 구조가 같은 1.5.1 소스와 Kotlin 1.9.25 표준 라이브러리 소스로 확인했다).

- 키는 큰따옴표여야 하고, 끝에 남는 쉼표와 배열 뒤의 다른 글은 문법 오류다.
- 따옴표 없는 값은 문법 오류가 아니라 문자열이 아닌 리터럴로 받는다. 그래서 `"category": doc`은 「문자열이 아니다」로 거절된다.
- 항목 1개 안에 같은 키가 2번 나오면 뒤엣것이 이긴다. 거절하지 않는다.
- `builtin`은 따옴표 없는 `true`나 `false` 글자만 불리언으로 받는다. `True`, `TRUE`, `"true"`는 「boolean이 아니다」로 거절한다.

항목은 64개까지이고, 명령 표면에는 도구 표면의 항목 수 검사가 없어서 여기 따로 둔다. 항목마다 `category`가 갈래를 정하고, 갈래마다 받는 키가 다르다.

| 키 | `doc` | `ritual` | JSON 타입 |
|---|---|---|---|
| `category` | 필수 | 필수 | 문자열. `doc`이나 `ritual` |
| `id` | 필수 | 필수 | 문자열 |
| `name` | 필수 | 필수 | 문자열 |
| `format` | 필수 | 필수 | 문자열 |
| `desc` | 필수 | 필수 | 문자열. 빈 글도 된다 |
| `body` | 필수 | 필수 | 문자열. 빈 글도 된다 |
| `type` | 필수 | 받지 않음 | 문자열 |
| `builtin` | 필수 | 받지 않음 | 불리언 리터럴 `true`나 `false` |
| `rev` | 받지 않음 | 필수 | 문자열 |
| `icon` | 받지 않음 | 필수 | 문자열 |

모르는 키를 거절하는 이유는, 버려진 키가 곧 파일에 안 담긴 값이기 때문이다. 이 명령이 만드는 것은 사용자가 앞으로 계속 쓸 템플릿이다.

**값 검사.** 모양을 지난 항목은 골격 폴더를 만든 뒤에 값을 검사한다. 문서 항목 모두를 먼저, 리추얼 항목 모두를 나중에 보고, 템플릿을 1개라도 쓰기 전에 모든 항목의 값 검사가 끝난다. 예외는 문서 항목의 경로 안전 검사 1가지이고, 그 항목을 쓰는 차례에 그 자리가 차 있는지 보기 전에 한다(23.4, 23.9의 1번).

| 칸 | 값 검사 |
|---|---|
| `id` | 공백뿐이 아니고 다듬기 없이 `^[A-Za-z0-9._-]{1,128}$`에 맞아야 한다. 문서 항목은 쓸 때 경로로도 안전해야 한다(100자 이하, `..` 없음, `.`으로 시작하지 않음). 리추얼 항목은 경로 안전 검사를 안 받는다(23.9의 8번) |
| `name` | 공백뿐이면 안 된다. 다듬지 않고 쓴다 |
| `format` | `markdown`, `html`, `json` 가운데 어느 것과 똑같아야 한다 |
| `type` | `plan`, `build`, `report`, `research`, `meeting`, `free` 가운데 어느 것과 똑같아야 한다 |
| `rev` | `morning`, `evening`, `weekly` 가운데 어느 것과 똑같아야 한다 |
| `icon` | `^[A-Za-z][A-Za-z0-9]{0,63}$`에 맞아야 한다 |
| `desc`, `body` | 검사 없음 |

디스크를 읽을 때(2.4)는 모르는 `type`과 `rev`를 기본값으로 접지만 여기서는 거절한다. 디스크의 값은 거절할 상대가 없지만 여기는 방금 값을 보낸 쪽이 있고, 리추얼 파일 이름이 곧 `rev`라서 오타가 `morning`으로 접히면 엉뚱한 본문이 `morning.md`로 심기기 때문이다.

**검사 사이에 끼는 일.** 칸 가르기만 vault와 색인을 건드리기 전에 끝난다. 모양 검사(`templates`, `name`)는 23.1의 2번 색인 맞추기와 3번 vault git 처리 뒤에 돈다. 그래서 「아무것도 쓰기 전에」라는 말은 이 명령이 vault 파일을 쓰기 전이라는 뜻이다. 모양이 틀린 호출도 색인을 그 vault에 맞추고, serve 모드면 다른 쓴 쪽의 커밋을 만들 수 있다. 쓰기 명령 공통의 차례(7.1)를 따른 결과이고, 다시 짓는 구현도 지금 엔진과 같게 둔다(23.9의 6번).

6번부터는 23.1의 2번 색인 맞추기와 3번 vault git 처리가 이미 돈 뒤라서, 「vault 파일은 그대로」여도 vault 밖의 색인과 serve 모드의 vault `.git`은 바뀌었을 수 있다. 5번에서 서면 색인은 그 앞까지 맞춰졌을 수 있다.

8번의 칸 차례는 문서 항목이 `id`, `name`, `format`, `desc`, `body`, `type`, `builtin`이고, 리추얼 항목이 `id`, `name`, `format`, `desc`, `body`, `rev`, `icon`이다. 11번도 같은 칸 차례로 본다. 12번은 그 항목을 쓰는 차례에, 자리가 차 있는지 보기 전에 본다. 그래서 `..a`처럼 바른 글자로만 된 id는 그 자리가 이미 차 있어도 `skipped`에 들지 않고 `WL-400`으로 선다.

```text
WL-500 파일을 쓰지 못했다: <절대 경로>
```

2번째 줄의 `<경로>`와 5번째 줄 끝 사용법의 꺾쇠는 자리표가 아니라 글자 그대로다. `모르는 명령이다` 뒤에는 이름 목록 줄이 더 붙고, 그 목록은 계약이 아니다. 색인 맞추기가 서는 길은 여럿이고 그 문구는 8장이 적는다. 위 블록에는 그 가운데 `아젠다 폴더를 읽지 못했다`만 적었다. `폴더를 만들지 못했다`의 경로는 만들려던 골격 폴더의 절대 경로이고, 막은 자리의 경로가 아니다. 13번은 임시 파일 이름을 3번 고르고도 실패하면 「임시 파일 이름을 3번 골랐는데 다 이미 있었다: <폴더>」로 서는 등 문구가 몇 가지 더 있다(7.4). `<JSON 값>` 자리는 그 값을 공백 없이 압축한 JSON 글로 적고, 키가 없으면 `null`이다. 문자열이면 큰따옴표째 적히고 따옴표 없는 리터럴이면 글 그대로다. 모르는 키 목록의 「쓸 수 있는 것」은 문서 항목이면 `[body, builtin, category, desc, format, id, name, type]`, 리추얼 항목이면 `[body, category, desc, format, icon, id, name, rev]`다.

9번까지에서 서면 vault 파일은 그대로다. 10번부터에서 서면 골격 폴더가 남지만 표식 파일은 없어서, 그 폴더는 아직 워크스페이스가 아니다. 고쳐서 다시 부르면 남은 것을 덮지 않고 마저 끝난다.

## 23.5 읽고 쓰는 자리

이 명령이 「있다」고 보는 기준은 「자리가 차 있다」(0.3)다. 쓸 자리에 파일이든 폴더든 무엇이 있으면 있는 것이고, 내용은 안 본다. 그 판정은 파일 시스템의 이름 찾기를 따라서, 대소문자나 정규화만 다른 이름도 macOS 기본 APFS에서는 차 있는 자리다(0.3). 템플릿과 표식 파일 자리에 가리키는 곳이 없는 심볼릭 링크가 있으면 빈자리로 쳐서 쓰고, 그때 원자적 이름 바꾸기가 링크 자체를 새 파일로 바꾼다. 권한 때문에 판정이 실패한 자리도 빈자리로 쳐서 쓰려다 `WL-500`으로 선다. 골격 폴더 자리에 가리키는 곳이 없는 링크나 일반 파일이 있으면 폴더를 못 만들어 `WL-500`으로 선다(코드 읽기로 확인).

| 걸음 | 자리 | 있으면 | 없으면 |
|---|---|---|---|
| 골격 | `.withlog/agendas`, `.withlog/templates/doc`, `.withlog/templates/ritual`, `notes` 차례 | 그대로 둔다. 폴더가 아닌 파일이면 `WL-500` | 중간 폴더까지 만든다 |
| 문서 템플릿 | `.withlog/templates/doc/<id>.<확장자>`. 확장자는 `format`이 `markdown`이면 `md`, `html`이면 `html`, `json`이면 `json` | `skipped`에 적는다 | 2.4의 바이트로 쓰고 `seeded`에 적는다 |
| 리추얼 템플릿 | `.withlog/templates/ritual/<rev>.md` | `skipped`에 적는다 | 2.4의 바이트로 쓰고 `seeded`에 적는다 |
| 표식 | `.withlog/workspace.json` | 그대로 둔다. `created`가 거짓 | 1.1의 바이트로 쓴다. `created`가 참 |

골격 폴더는 표의 차례로 만들고, 1개를 못 만들면 그 자리에서 서서 그 앞의 폴더만 남는다. 새 폴더의 권한은 0.2를 따른다.

템플릿은 문서 항목을 먼저, 리추얼 항목을 나중에 심고, 같은 갈래 안에서는 받은 차례를 지킨다. 그래서 부르는 쪽이 섞어 보내도 응답의 차례가 흔들리지 않는다. 「있다」는 그 파일 자리만 보고, 같은 id의 템플릿이 다른 확장자나 다른 이름으로 있는지는 안 본다. 스캔으로 보면 손편집으로 id를 바꾼 파일 때문에 차 있는 자리를 비었다고 보고 덮게 되기 때문이다. 같은 자리를 가리키는 항목이 2개면 앞 항목이 쓰고 뒤 항목은 `skipped`에 든다.

템플릿 파일은 2.4의 쓰기 바이트로 쓴다. 울타리는 `format`이 html이나 json이어도 `---`이고, 문서 템플릿의 `builtin`은 받은 값을 적는다. 표식 파일은 1.1의 바이트다. `name`은 받은 값이나 폴더 이름이고, `createdAt`은 쓰는 순간을 밀리초 아래에서 자른 UTC 밀리초 시각이다. 노트의 `created`가 로컬 벽시계에 `+09:00`을 붙이는 것과 규칙이 다른데, 옛 구현이 이 값만 `toISOString()`으로 찍어서 그 바이트를 따랐다. 파일 쓰기는 모두 원자적이다(7.4).

23.1의 2번 색인 맞추기는 아직 워크스페이스가 아닌 폴더에서도 돈다. notes나 `.withlog/agendas`가 없으면 노트와 아젠다 0개로 보고 그냥 지나간다. 색인 DB는 엔진이 뜰 때 vault 밖 `<db.home>/<VaultKey>/meta.db`에 이미 생기고(8.2), 이 걸음은 그 DB를 vault에 맞춘다. vault가 git 저장소면 다른 쓰기 명령처럼 앞뒤로 자동 커밋 처리를 받고, 쓴 쪽은 명령 표면이라 `app`이다(31장).

## 23.6 응답

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `created` | 불리언 | 늘. 이번 호출이 표식 파일을 썼으면 `true` |
| 2 | `seeded` | 문자열 배열 | 늘. 이번에 쓴 템플릿 파일의 vault 상대 경로. 비면 `[]` |
| 3 | `skipped` | 문자열 배열 | 늘. 자리가 차 있어 건너뛴 템플릿 파일의 vault 상대 경로. 비면 `[]` |

`created`는 표식 파일을 이번에 썼는가만 보고 정한다. 골격 폴더는 노트나 아젠다를 쓰는 다른 명령도 만들어서, 폴더로 재면 빈 폴더에 노트 1개를 쓴 vault가 워크스페이스로 세어지기 때문이다. 만든 폴더 목록은 안 싣는다. 부르는 쪽이 가를 것은 「새로 만들었나」뿐이기 때문이다. `skipped`가 차 있는 것이 정상이다. 있는 vault를 다시 열 때마다 모든 템플릿이 여기 들고, 그 목록이 아무것도 안 덮었다는 증거다. 경로는 받은 `id`와 `rev` 글자로 지어서 디스크의 이름 정규화와 상관없이 받은 글자 그대로다.

바이트는 6.1의 stdout 규칙이고, 끝에 줄바꿈 1개가 붙는다. 빈 폴더에 앱이 보내는 argv(`templates=[]`)를 부르면 종료 코드 0과 아래 바이트가 나온다(예시 값, 코드 읽기로 확인).

```json
{
  "created": true,
  "seeded": [],
  "skipped": []
}
```

같은 호출을 다시 부르면 `created`만 `false`가 된다. 템플릿을 실어 보내는 예는 이렇다. `templates=` 뒤에 아래 JSON을 1칸으로 붙이고, 보기 좋게 줄을 나눴을 뿐 실제로는 1줄이어도 같다(예시 값).

```json
[
  {
    "category": "doc",
    "id": "m-plan",
    "name": "기본 플래닝 템플릿 (markdown)",
    "type": "plan",
    "format": "markdown",
    "desc": "설계 전에 씁니다",
    "builtin": true,
    "body": "# [제목] 설계 플랜\n\n이 작업을 한 줄로 요약합니다.\n"
  },
  {
    "category": "ritual",
    "id": "t-morning",
    "rev": "morning",
    "name": "기본 모닝 데일리 템플릿",
    "icon": "sunrise",
    "format": "markdown",
    "desc": "아침에 씁니다",
    "body": "# 모닝 리포트 - [날짜]\n"
  }
]
```

빈 폴더에서 부르면 응답은 이렇고, 심긴 파일 2개는 픽스처의 `m-plan.md`, `morning.md`와 같은 바이트로 쓰이는 것으로 읽힌다(2.4).

```json
{
  "created": true,
  "seeded": [
    ".withlog/templates/doc/m-plan.md",
    ".withlog/templates/ritual/morning.md"
  ],
  "skipped": []
}
```

같은 인자로 픽스처 vault에서 부르면 템플릿 자리 2곳과 표식 파일이 이미 차 있어서 아무것도 안 쓴다.

```json
{
  "created": false,
  "seeded": [],
  "skipped": [
    ".withlog/templates/doc/m-plan.md",
    ".withlog/templates/ritual/morning.md"
  ]
}
```

빈 폴더에서 `name=새-vault`로 불렀다면 표식 파일은 이렇게 쓰이고 끝에 줄바꿈 1개가 붙는다(예시 값). `createdAt`은 부른 순간이다.

```json
{
  "schemaVersion": 1,
  "name": "새-vault",
  "createdAt": "2026-10-22T05:12:33.481Z"
}
```

## 23.7 모양이 다른 대상

| 대상 | 동작 |
|---|---|
| 이미 워크스페이스인 vault | 빠진 골격 폴더와 빠진 템플릿만 채우고 `created`가 `false`다. `name`은 무시된다 |
| 골격 폴더만 있고 표식이 없는 폴더 | 이어서 갖추고 `created`가 `true`다. 중간에 멈춘 앞 호출이 이 모양을 남긴다 |
| 노트는 있는데 표식이 없는 옛 vault | 노트를 안 건드리고 표식을 써서 워크스페이스로 만든다 |
| 표식 자리가 폴더 | 차 있는 것으로 보아 안 쓰고 `created`가 `false`다. 그 폴더는 쓰기 명령의 표식 확인도 통과한다 |
| 골격 자리가 일반 파일 | `WL-500`으로 선다. 그 앞 골격 폴더는 남는다 |
| 같은 id의 옛 html 문서 템플릿이 있고 markdown 항목을 심음 | `<id>.md` 자리가 비어 있어 심는다. 그 뒤 같은 id가 2벌이고 1건 읽기는 html 쪽을 고른다(2.4) |
| 같은 자리를 가리키는 항목 2개 | 앞 항목이 `seeded`, 뒤 항목이 `skipped`에 든다 |
| 리추얼 항목의 `format`이 `json` | `format: json`으로 쓰이고, 읽을 때는 html로 읽힌다(2.4) |
| 리추얼 항목의 `id`가 `.x`, `a..b`, 101자부터 128자 | 거절 없이 심기지만, 다음 읽기에서 경로 안전 검사에 걸려 건너뛰는 템플릿이 된다(23.9의 8번) |
| 템플릿 항목의 `name`에 앞뒤 공백 | 공백째 쓰이고(1.9가 따옴표로 감싼다), 읽을 때는 다듬어 공백 없이 읽힌다 |
| `name`에 앞뒤 공백 | 공백째 표식 파일에 적힌다 |
| vault 뿌리가 `/`이고 `name`을 안 줌 | `name`이 빈 글인 표식을 쓴다 |
| vault 뿌리가 심볼릭 링크 | 링크를 안 풀어서, 기본 이름은 링크의 이름이다 |

## 23.9 받아들임 묶음과 얼어 있는 특이점

묶음의 읽기 레인은 이 명령을 부르지 않고, 쓰기 축에도 이 명령의 케이스가 없다. 픽스처 vault는 이 명령을 거치지 않고 파일을 직접 만들었다. 그래서 이 장의 규칙은 모두 코드 읽기로 확인했고, 받아들임 검사가 덮는 것은 없다. 34장의 쓰기 레인이 생기면 빈 폴더, 이미 워크스페이스인 vault, 값 검사 실패의 남는 모양을 먼저 덮을 자리로 둔다.

지금 엔진의 특이점이고, 지킬지 고칠지는 부록 D에서 정한다. 정하기 전에는 지금 엔진과 같게 판다(0.5). 검사가 안 덮어 어느 쪽으로 파도 검사로는 안 가려지지만, 다음 쓰기 레인의 기대값을 지금 엔진으로 뜨기 때문이다.

1. 「모든 항목을 검사한 뒤에 쓴다」가 경로 안전 검사에서 깨진다. `id`가 `^[A-Za-z0-9._-]{1,128}$`에는 맞지만 `..`을 품었거나, `.`으로 시작하거나, 101자 이상 128자 이하인 문서 항목은 쓰는 차례가 되어서야 `WL-400`으로 선다. 그 앞 항목들은 이미 심겨 있고 표식 파일은 안 쓰인다.
2. 값 검사가 골격 폴더를 만든 뒤에 돌아서, 값이 틀린 호출도 골격 폴더 4개를 남긴다. 표식이 없어 워크스페이스는 아니다.
3. 템플릿 자리 판정이 파일 자리 1곳만 봐서, 옛 html 문서 템플릿 옆에 같은 id의 markdown 파일을 심어 같은 id 2벌을 만든다.
4. 리추얼 항목에 `format: json`을 받아 쓰지만, 읽는 쪽은 그 템플릿을 html로 읽는다.
5. `name`을 다듬지 않아서 앞뒤 공백이 표식 파일에 남는다. 공백뿐인 이름만 거절한다.
6. 색인 맞추기와 vault git 쓰기 앞 처리가 `templates`와 `name` 검사보다 먼저 돈다. 그래서 모양이 틀린 호출도 색인을 바꾸고, serve 모드면 다른 쓴 쪽의 커밋을 만들 수 있다. 아젠다 slug 충돌(2.9의 2번)이나 목록을 못 읽는 아젠다 폴더처럼 색인 맞추기를 세우는 상태에서는, 골격을 갖추는 일까지 함께 막힌다.
7. 표식 판정이 「자리가 차 있다」라서, 그 자리에 있는 폴더나 망가진 파일도 표식으로 친다. 내용을 아무도 안 읽기 때문에, 이름과 생성 시각이 틀린 표식도 티가 안 난다.
8. 리추얼 항목의 `id`는 경로 안전 검사를 안 받아서, `.x`, `a..b`, 101자부터 128자인 id도 `<rev>.md`의 `id:` 줄로 심긴다. 읽는 쪽(2.4의 7번)은 그 id를 경로로 안전하지 않다고 보아 「템플릿 id 가 안전한 경로 세그먼트가 아니다: <id>」로 건너뛴다. 그래서 방금 `seeded`에 든 리추얼 템플릿이 다음 목록에서 사라지고 `incomplete`로만 세어진다.
9. 템플릿 항목의 `name`도 다듬지 않고 쓰지만 읽을 때는 다듬어서, 앞뒤 공백이 든 이름은 심은 값과 읽은 값이 다르다.

정할 것은 1번과 2번과 6번의 차례를 고칠지(모든 검사를 첫 쓰기 앞으로 모을지), 3번에서 같은 id의 다른 확장자를 차 있는 자리로 볼지, 8번에서 리추얼 id에도 경로 안전 검사를 걸지다.
