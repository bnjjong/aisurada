# withlog > 1부 vault 엔진 설명서 > 31장 vault git: 자동 커밋과 명령 history, commit-vault

최종 수정: 목요일 10/22 · 22:56

vault가 git 저장소면 엔진은 vault 자신의 저장소 `main` 브랜치에 스스로 커밋하고, 노트 1건의 판을 그 저장소에서 모아 보여 준다. 이 장은 언제, 무엇을, 어떤 바이트로 커밋하는지와 명령 `history`, `commit-vault`의 계약을 정한다.

- 커밋은 serve 모드에서 저절로 일어난다. 때는 마지막 쓰기 뒤 5분, 쉬지 않고 쓸 때 15분, 쓴 쪽이 바뀌기 직전, 내려갈 때, 뜰 때다. 단발 모드는 `commit-vault` 말고는 커밋하지 않는다.
- 10분 안의 `.git/index.lock`이 있거나, 병합이나 리베이스가 진행 중이거나, HEAD가 `main`이 아니면 건너뛰고 30초 뒤 다시 해 본다. 10분 넘은 잠금은 지운다. git이 실패하면 30초부터 8분까지 2배씩 미룬다. 어느 갈래도 쓰기를 실패시키지 않는다.
- 커밋은 `*.tmp`를 뺀 vault 전체를 담고, 훅과 서명을 끄고, 저자와 커미터를 `withlog-auto <noreply@withlog.local>`로 못박고, 꼬리 줄 `Withlog-*`를 단다.
- `history`는 자동 커밋, 손 커밋, 옛 스냅숏을 목록 1개로 합쳐 판을 내고, `commit-vault`는 지금 커밋을 시도해 결과를 글자로 낸다. 이 2개 명령은 명령 표면에만 있고, git이 실패해도 종료 코드 0으로 답한다.
- 근거: 픽스처 vault는 git 저장소가 아니라 받아들임 묶음이 이 장을 1건도 안 잰다. 모두 코드 읽기로 확인했고, git 명령의 동작은 git의 규약으로 적었다.

## 31.1 커밋하는 때 5가지

엔진 프로세스는 메모리에 「커밋 안 한 쓰기」의 대기 기록을 1개 든다. 대기 기록에는 쓴 쪽 목록, 세션 목록, 「쓴 쪽과 세션」 짝의 목록, 첫 쓰기 시각, 마지막 쓰기 시각이 든다. 목록 3개는 모두 겹친 값을 빼고 처음 들어온 차례를 지킨다. 쓰기 깃발 명령이 7.1의 4번에 닿으면, 그 일이 성공하든 실패하든 끝날 때 이 대기 기록에 더한다(7.1의 6번). 7.1의 1번, 2번, 3번에서 선 호출은 안 더한다. 세션은 도구 표면의 표식 값을 검사 없이 그대로 넣어서, 빈 글이 와도 목록에 든다(`wl-cli`는 빈 값이면 표식을 안 붙여서 보통은 안 생긴다, 3.3). 대기 기록은 커밋이 되거나 「바뀐 것 없음」이나 「꺼짐」으로 끝나면 비운다. 대기 기록은 git을 안 부르고 메모리에만 있어서, 쓰기마다 드는 값이 없다.

| 때 | 조건 | 꼬리 줄의 까닭 | 모드 |
|---|---|---|---|
| 유휴 | 정비 걸음(5초마다)에서 대기 기록이 있고, 다시 해 볼 시각이 지났고, 마지막 쓰기 뒤 쉬는 시간이 찼다 | `idle` | serve |
| 오래 기다림 | 위와 같은데 쉬는 시간은 못 채웠고, 첫 쓰기 뒤 15분이 지났다 | `overdue` | serve |
| 쓴 쪽이 바뀔 때 | 쓰기 깃발 명령이 일하기 직전(7.1의 4번)에 대기 기록이 있고, 대기 기록의 짝 목록이 이번 쓰기의 짝 1개만 든 목록이 아니고, 다시 해 볼 시각이 지났다 | `writer` | 단발 모드와 serve 모드 모두. 단발 모드는 대기 기록이 늘 비어 있어 실제로는 안 일어난다 |
| 내려갈 때 | 받기를 멈추고 처리 중인 연결을 최대 5초 기다린 뒤, 실행 잠금을 놓기 전 | `shutdown` | serve |
| 뜰 때 | 실행 잠금을 잡은 뒤, 소켓을 열기 전 | `startup` | serve |

쉬는 시간은 설정 `withlog.vault.autocommit.idle.seconds`(환경변수 `WITHLOG_VAULT_AUTOCOMMIT_IDLE_SECONDS`)이고 기본값은 300초다. 값은 64비트 정수 초이고, 정수로 안 읽히거나 빈 글이면 엔진이 종료 코드 1로 못 뜬다(33.1의 값 읽기). 0이나 음수면 쓰기 뒤 첫 정비 걸음(5초 안)에서 곧바로 커밋한다. 15분은 설정이 없다. 쉬는 시간만 있으면 5분 안쪽으로 쉬며 2시간을 쓸 때 판이 끝에 1개만 생겨서, 90분째에 지운 문단을 이력에서 못 되찾기 때문이다. 15분은 쉬는 시간의 3배라 쉬지 않고 2시간을 쓰면 판이 8개쯤 생긴다.

짝은 쓴 쪽과 세션을 `:`로 이은 글자다. 명령 표면은 늘 `app:`이고, 도구 표면은 `tool:<세션 id>`이며 세션 표식이 없으면 `tool:`이다. 「짝 목록이 이번 쓰기의 짝 1개만 든 목록이 아니다」는 대기 기록에 다른 짝이 1개라도 섞였다는 뜻이다. 쓴 쪽이 바뀌기 직전에 커밋하는 이유는 노트 쓰기가 본문을 통째로 갈아 끼우기 때문이다. 앱에서 고친 글을 Claude 세션의 쓰기가 덮으면 그 글이 사라지는데, 덮기 직전에 커밋해 두면 덮이기 전의 글이 늘 이력에 남는다. Claude 세션 2개도 서로의 글을 덮을 수 있어서 세션까지 짝에 넣는다. 같은 짝이 연달아 쓰면 git을 안 부른다. 앱의 자동저장이 쓰기마다 이 자리를 지나서 그 값이 0이어야 하기 때문이다. 이 커밋이 건너뛰어지거나 실패하면 대기 기록이 안 비어서, 그 뒤 커밋 1개에 짝 여럿이 섞인다. 쓰기 2개가 동시에 오면 2개 모두 커밋 전에 지나가 커밋 1개에 섞일 수도 있다. 엔진이 쓰기를 줄 세우지 않기 때문이다(7.1).

뜰 때 커밋은 엔진이 꺼져 있던 사이에 바뀐 것을 담는다. 손편집, 강제로 죽어 못 담은 쓰기, 단발 모드의 쓰기가 여기 든다. 새 프로세스의 대기 기록은 늘 비어 있어서 이 커밋의 쓴 쪽은 `outside`다. 소켓을 열기 전에 해서 그 변경이 뒤에 오는 앱이나 Claude 세션의 커밋에 안 섞이고, 잠금을 잡은 뒤에 해서 다른 엔진 프로세스의 커밋과 안 겹친다. 다른 프로세스가 잠금을 쥐고 있으면 serve는 커밋 없이 종료 코드 0으로 끝난다(3.2).

내려갈 때 커밋은 처리 중이던 쓰기가 다 끝난 뒤, 잠금을 놓기 전에 한다. 잠금을 놓은 뒤에 하면 새로 뜬 엔진의 뜰 때 커밋과 겹친다. launchd의 `ExitTimeout`이 25초(3.4)이고 앞의 기다림이 최대 5초라 이 커밋은 20초 안에 끝나야 한다. 유휴 종료(기본 10분)도 같은 길을 지난다. 자동 커밋의 쉬는 시간이 그보다 짧아서 보통은 그 전에 이미 커밋된다.

단발 모드는 정비 걸음과 뜰 때, 내려갈 때 커밋이 없다. 그 프로세스의 대기 기록은 프로세스와 함께 사라지고, 그 쓰기는 다음 serve의 뜰 때 커밋에 `outside`로 담기거나 `commit-vault`가 담는다(31.7의 1번).

자동 커밋은 쓰기의 조건이 아니라 안전망이다. git이 건너뛰거나 실패해도 쓰기는 그대로 성공하고, 어떤 갈래도 실패를 밖으로 내지 않는다. 내려갈 때 실패를 내면 유휴 종료의 종료 코드 0 규칙이 깨지기 때문이다. 다만 커밋 작업은 1번에 1개씩 돌고, 대기 기록에 더하기와 쓴 쪽 검사도 같은 잠금을 쥔다. 커밋 1번은 git 걸음을 최대 5개 부르고 걸음 1개는 최대 63초까지 걸려서(31.2, 31.3), 그동안 쓰기는 7.1의 4번과 6번 자리에서 기다린다.

설정 `withlog.vault.autocommit.enabled`(환경변수 `WITHLOG_VAULT_AUTOCOMMIT_ENABLED`, 명령줄 `--withlog.vault.autocommit.enabled=<값>`, 기본 `true`)를 거짓으로 두면 대기 기록에 아무것도 안 더하고, 뜰 때와 내려갈 때와 `commit-vault`는 `disabled`로 끝난다. 받는 글자는 33.1의 불리언 규칙이다. 앞뒤의 U+0020 이하 글자를 떼고 대소문자를 안 가려 `true`, `on`, `yes`, `1`이 참, `false`, `off`, `no`, `0`이 거짓이고, 빈 글을 포함해 그 밖이면 엔진이 종료 코드 1로 못 뜬다. 다시 배포하지 않고 끄는 자리다.

## 31.2 건너뛰기와 재시도

**git을 띄우는 꼴.** 자동 커밋과 `history`의 git은 늘 같은 꼴로 띄운다. 31.6의 스냅숏 걸음과 `history`의 스냅숏 목록 읽기만 예외다.

| 항목 | 규칙 |
|---|---|
| 실행 파일 | `git`을 엔진 프로세스의 `PATH`에서 찾는다. launchd가 띄운 엔진은 launchd의 최소 `PATH`를 받는다(33.1). 못 띄우면 그 걸음의 실패다 |
| 작업 폴더 | vault 뿌리(1.1의 글자) |
| 환경 | `GIT_INDEX_FILE`을 지우고 `GIT_DIR=<vault>/.git`과 `GIT_WORK_TREE=<vault>`를 못박는다. 나머지(`HOME`, `TZ`, `LANG`, `GIT_CONFIG_*` 등)는 엔진에서 물려받는다 |
| 앞 옵션 | 모든 git 명령 앞에 `-c core.hookspath=/dev/null -c commit.gpgsign=false -c core.quotepath=false`를 붙인다 |
| 출력 | 표준 출력과 표준 오류를 합쳐서 따로 도는 읽기가 끝까지 읽는다. 글로 쓸 때는 UTF-8로 풀고 깨진 바이트는 U+FFFD가 된다 |
| 시간 제한 | 걸음 1개가 60초를 넘기면 SIGTERM을 보내고, 3초 안에 안 끝나면 SIGKILL로 끝낸다. 그 걸음은 실패다 |

환경을 못박는 이유는, 엔진을 띄운 셸이 다른 저장소를 가리키는 `GIT_DIR`이나 `GIT_WORK_TREE`를 내보내도 그 저장소에 커밋하면 안 되기 때문이다. 출력을 따로 읽는 이유는 다 끝난 뒤에 읽으면 64KB 파이프가 차서 git이 쓰다 막히기 때문이다. SIGTERM을 먼저 보내는 이유는 git이 SIGTERM에서는 `index.lock`을 치우고 끝나지만, 곧바로 SIGKILL하면 그 잠금이 남아 다음 커밋과 사람의 git이 모두 막히기 때문이다.

**막힌 까닭.** 커밋을 시도하면 무엇이든 담기 전에 아래 차례로 막힌 까닭을 본다. 처음 걸린 까닭 1개만 쓴다.

| 차례 | 까닭 글자 | 조건 | 영구 |
|---|---|---|---|
| 1 | `off` | 자동 커밋을 껐다 | 예 |
| 2 | `not-repo` | `<vault>/.git`이 폴더가 아니다. 링크는 따라가서, 폴더를 가리키는 링크는 저장소로 본다. `.git`이 파일인 작업 트리와 서브모듈은 여기 든다 | 예 |
| 3 | `index-lock` | `.git/index.lock`이 있고 수정 시각이 10분 안이다 | 아니오 |
| 4 | `in-progress` | `.git` 아래 `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` 가운데 1개라도 있다(링크는 따라간다) | 아니오 |
| 5 | `not-main` | `git symbolic-ref -q HEAD`의 합친 출력을 5.3의 다듬기로 다듬은 글이 정확히 `refs/heads/main`이 아니다. 종료 코드는 안 본다. git을 못 띄웠거나 시간을 넘긴 경우도 여기 든다 | 아니오 |

1번부터 4번은 파일 조회라 git을 안 부른다. 3번은 잠금 파일의 수정 시각을 엔진의 지금 시각과 견준다. 파일이 없으면 안 쥔 것이고, 수정 시각을 다른 이유로 못 읽으면 쥔 것이고, 시각이 미래면 10분 안으로 친다. 10분보다 오래됐으면 끝나지 못한 git이 남긴 것으로 보고 경고 로그를 남기고 지운 뒤 4번으로 간다. 지우기가 실패하면 쥔 것으로 본다. 10분인 이유는 잠금을 정당하게 오래 쥐는 쪽이 2가지이기 때문이다. 엔진의 git 걸음 1개가 최대 63초를 쥐고, 사람이 편집기를 여는 `git commit`은 메시지를 쓰는 동안 몇 분을 쥔다. 사람이나 다른 세션이 다른 브랜치에서 일하는 동안 그 브랜치에 자동 커밋을 섞지 않으려고 5번을 둔다.

**결과.**

| 결과 | 언제 | 대기 기록 | 다시 해 볼 시각과 실패 횟수 |
|---|---|---|---|
| `committed` | 커밋을 1개 만들었다 | 비운다 | 시각은 그대로, 실패 횟수는 0으로 |
| `nothing` | 담아 보니 바뀐 것이 없다 | 비운다 | 같다 |
| `disabled` | 영구 까닭(`off`, `not-repo`)에 걸렸다 | 버린다. 다시 해 봐도 안 바뀌어서 정비 걸음이 영영 들여다보지 않게 한다 | 시각과 횟수 모두 그대로 |
| `skipped` | 영구가 아닌 까닭에 걸렸다 | 둔다 | 시각은 지금부터 30초 뒤, 실패 횟수는 그대로 |
| `failed` | git이 실패했다. `git add`, 바뀐 목록 읽기, `git commit` 가운데 1개가 0이 아닌 종료 코드로 끝났거나, 시간을 넘겼거나, 못 띄웠다 | 둔다 | 실패 횟수를 1 올리고, 시각은 그 횟수 n에 따라 지금부터 30초 × 2^(n-1) 뒤, 최대 8분 |

연달아 실패하면 미루는 시간이 30초, 1분, 2분, 4분, 8분이고 5번째부터는 8분에 머문다. 늘리는 이유는 실패 까닭이 `git add`의 시간 초과(손으로 넣은 수 GB 파일)일 때 시도마다 60초 동안 커밋 작업을 붙들어, 그동안 모든 쓰기가 기다리기 때문이다. 이 결과 처리는 커밋을 부른 쪽과 상관없이 같아서, `commit-vault`의 `skipped`와 `failed`도 다시 해 볼 시각과 실패 횟수를 똑같이 고친다(31.5).

「다시 해 볼 시각」은 유휴, 오래 기다림, 쓴 쪽이 바뀔 때만 지킨다. 그 전에는 git을 아예 안 부른다. 지키지 않으면 쓴 쪽이 2개 쌓인 뒤로 쓰기마다 커밋을 다시 해서, `git add`가 시간을 넘기는 vault에서 쓰기마다 1분씩 섰기 때문이다. 뜰 때, 내려갈 때, `commit-vault`는 이 시각을 안 보고 바로 시도한다.

## 31.3 커밋 바이트

막힌 까닭이 없으면 이 차례로 커밋한다. 걸음마다 31.2의 꼴로 띄운다.

1. `git add -A -- . :(exclude)*.tmp`. 셸을 안 거쳐서 마지막 칸 `:(exclude)*.tmp`가 그대로 argv 1칸으로 간다. `.gitignore`가 빼지 않은 vault 전체를 담되 모든 깊이의 `*.tmp`를 뺀다. 앱이 직접 쓰는 그림과 손으로 복사한 첨부는 엔진을 안 지나서 vault 전체를 담는다. `*.tmp`를 빼는 이유는 커밋이 쓰기와 다른 스레드에서 돌아서 반쯤 쓴 임시 파일(7.4)을 담을 수 있고, 담기면 다음 커밋이 그것을 지운 것으로 또 적기 때문이다. vault의 `.gitignore`를 고치지 않고 여기서 빼는 이유는 그 파일이 사용자의 파일이기 때문이다.
2. `git diff --cached --no-renames --name-status -z`로 바뀐 경로와 상태 글자를 읽는다. 출력은 NUL로 나뉜 「상태」와 「경로」의 짝이 이어진 것이고, 상태 칸의 첫 글자를 상태로 쓴다. 바뀐 것이 없으면 `nothing`이고 커밋을 안 만든다.
3. 노트 id를 모은다. 2번 출력의 차례대로, 경로의 마지막 조각이 정확히 `note.md`인 것만 본다. 상태가 `D`(지움)면 HEAD 쪽 글을 읽는다. 지운 경로를 모두 모아 `git cat-file --batch` 1번에 `HEAD:<경로>`를 줄마다 주고, 그 판의 글 전체를 UTF-8로 푼다(깨진 바이트는 U+FFFD). 그 걸음이 실패하면 지운 파일의 id만 빠지고 커밋은 그대로 한다. `D`가 아닌 나머지 상태(`A`, `M`, `T`, `U` 등)는 vault의 그 파일을 링크를 따라가 열어 앞 4,096바이트만 UTF-8로 푼다. 4,096바이트 끝에서 잘린 여러 바이트 글자는 U+FFFD가 되는데, 머리가 그 안에서 닫히면 id는 그 앞에 있어서 영향이 없다. 읽지 못한 파일은 건너뛴다. 1.14의 규칙으로 id를 뽑고, 겹친 id는 처음 나온 것만 남긴다. 그래서 지운 파일과 나머지 파일의 id가 2번의 차례대로 섞여 든다. 노트 폴더는 제목이나 아젠다를 고치면 옮겨져서 경로만으로는 노트 1건의 이력이 끊기는데, 꼬리 줄의 id가 그것을 잇는다(31.4).
4. `git commit -q --no-verify -F -`로 메시지를 표준 입력에 실어 커밋한다. 환경에 `GIT_AUTHOR_NAME`과 `GIT_COMMITTER_NAME`을 `withlog-auto`로, `GIT_AUTHOR_EMAIL`과 `GIT_COMMITTER_EMAIL`을 `noreply@withlog.local`로 더한다. 시각은 git이 정한다.

메시지는 이 꼴이고, 줄마다 LF로 끝난다. 제목의 쓴 쪽들은 쉼표 1글자(`,`)로 공백 없이 잇고, 꼬리 줄의 값들은 공백 1글자로 잇는다. 그래서 앱과 도구가 섞인 커밋의 제목은 `wl(app,tool): ...`이고 `wl(app, tool)`이 아니다.

```text
wl(<쓴 쪽들을 쉼표로 이은 것>): 노트 <id 수>개, 파일 <바뀐 경로 수>개

Withlog-Writer: <쓴 쪽들을 공백으로 이은 것>
Withlog-Reason: <까닭>
Withlog-Session: <세션들을 공백으로 이은 것>
Withlog-Notes: <노트 id 앞 200개를 공백으로 이은 것>
```

| 조각 | 값 |
|---|---|
| 쓴 쪽 | `app`, `tool`, `outside`. 대기 기록에 처음 들어온 차례이고, 대기 기록이 비었을 때만 `outside` 1개다 |
| `<id 수>` | 3번에서 모은 id의 수. 200개로 자르지 않는다 |
| `<바뀐 경로 수>` | 2번의 짝 수. 이름 바꾸기를 안 읽어서 옮긴 파일은 지운 것 1개와 더한 것 1개로 2개다 |
| 까닭 | `idle`, `overdue`, `writer`, `shutdown`, `startup`, `restore`(31.5) |
| `Withlog-Session` 줄 | 세션이 1개라도 있을 때만. 받은 세션 값을 검사 없이 처음 들어온 차례로 싣는다 |
| `Withlog-Notes` 줄 | id가 1개라도 있을 때만. 커밋 1개에 200개까지 싣는데, 밀린 것을 1번에 담는 첫 커밋에서만 닿는다 |

git은 `-F`로 받은 메시지를 편집기 없이 쓰므로 기본 정리 규칙 가운데 공백 정리(줄 끝 공백, 앞뒤 빈 줄, 이어진 빈 줄)만 거친다. 엔진은 `commit.cleanup` 같은 사용자의 git 설정을 따로 막지 않는다. 엔진이 짓는 메시지에는 정리될 글자가 없어서 기본 설정에서는 위 바이트 그대로 남는다. 세션 값에 줄 끝 공백이나 줄바꿈이 든 경우는 31.7의 8번이다.

픽스처 0001을 앱에서 고치고 5분이 지나면 이런 커밋이 생긴다(예시 값).

```text
wl(app): 노트 1개, 파일 1개

Withlog-Writer: app
Withlog-Reason: idle
Withlog-Notes: ndfixture-00000001
```

Claude 세션이 새 노트 1개를 만든 뒤 앱이 쓰기를 보내면, 앱의 쓰기 직전에 이런 커밋이 생긴다(예시 값). 파일 2개는 이를테면 새 `note.md`와, 그 쓰기가 새로 만든 아젠다 파일이다.

```text
wl(tool): 노트 1개, 파일 2개

Withlog-Writer: tool
Withlog-Reason: writer
Withlog-Session: 3f2a9c1e-5b7d-4e8f-9a01-2b3c4d5e6f70
Withlog-Notes: ndmvhnelpc-0c1d2e3f
```

제목 머리 `wl(`은 사람 커밋과 가르는 표시다. 사람 커밋은 `git log --invert-grep --grep='^wl('`로 따로 본다. 저자와 커미터를 함께 못박는 이유는 `--author`만 주면 커미터에 사람 이름이 남아 `git log --author`로 가르는 목적이 반쪽이 되기 때문이다. 훅을 `core.hookspath=/dev/null`로 통째로 끄는 이유는 `--no-verify`가 `pre-commit`과 `commit-msg`만 건너뛰고 `post-commit`은 돌리기 때문이다. vault에 사내 위키 수집 `pre-push` 훅이 깔린 적이 있어서 커밋 훅이 더 깔리는 날을 막는다. 서명을 끄는 이유는 서명이 pinentry를 띄우면 엔진이 멈추기 때문이다.

커밋한 뒤 `wl-cli doctor`의 `vault git` 줄이 마지막 자동 커밋과 커밋 밖 경로 수를 적는다(3.6).

## 31.4 명령 history

`history`는 노트 1건의 판 목록을 내고, 판 1개를 고르면 그 판의 글까지 낸다. 명령 표면에만 있고 도구 이름은 없다. 도구 표면에 열면 기록 층 노트(1.7)의 옛 본문이 도구 표면으로 새는 뒷문이 되기 때문이다. 쓰기 깃발이 없어서 표식 확인, 색인 맞추기, 쓴 쪽 남기기가 없고, 색인도 안 보고 노트가 지금 있는지도 안 묻는다. 되찾으려는 노트는 이미 사라졌거나 통째로 바뀐 노트이기 때문이다.

`history <노트 id> [번호] [commit=<커밋>] [query=<글자>]`

인자는 이 차례로 검사한다. 1번과 2번은 5.2의 인자 문법이고, 3번부터는 그 뒤에 이 명령이 본다. 실패는 모두 `WL-400`과 종료 코드 3이다.

| 차례 | 조건 | 문구 |
|---|---|---|
| 1 | `commit`, `query` 밖의 옵션 이름. argv 차례로 처음 걸린 칸에서 바로 선다 | `history 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [commit, query] 뿐이다.` |
| 2 | 자리 인자 3칸 이상 | `history 이 받는 자리 인자는 2 개인데 <n> 개를 받았다: history <노트 id> [번호] [commit=<커밋>] [query=<글자>]` |
| 3 | 2번째 자리 인자가 있는데 1 이상의 정수가 아니다 | `판 번호는 1 이상의 정수여야 한다: <받은 값>` |
| 4 | `commit` 값이 있는데 커밋 모양이 아니다 | `커밋은 40 자리 16 진수여야 한다: <다듬은 값>` |
| 5 | 번호와 `commit`을 함께 썼다 | `판 번호와 커밋을 함께 줄 수 없다. 하나만 준다` |
| 6 | 노트 id가 없거나 공백뿐이다 | `인자가 하나 필요하다: history <노트 id> [번호] [commit=<커밋>] [query=<글자>]` |

**번호(3번).** 2번째 자리 인자를 다듬지 않고 정수로 읽는다. 맨 앞에 `+`나 `-` 1개를 받고, 나머지 글자는 모두 유니코드 10진 숫자(Java `Character.isDigit`가 0부터 9를 주는 글자)여야 하고, 32비트 부호 있는 정수 범위 안이어야 한다. 앞뒤 공백, 빈 글, 범위 밖 값은 정수가 아니다. 그래서 `+2`, `002`, `۲`(아랍 숫자 2)는 모두 2로 읽히고(31.7의 11번), `2147483648`과 `-2`는 3번에서 선다. 3번 문구의 `<받은 값>`은 받은 글자 그대로다.

**커밋(4번).** `commit=` 값을 5.3의 다듬기로 다듬고, 다듬어서 비면 안 준 것으로 본다. 그다음 UTF-16 코드 단위로 정확히 40개이고, 단위마다 `a`부터 `f`이거나 Java `Character.isDigit`가 참인 글자여야 한다. 대문자 16진수는 안 받는다. 유니코드 숫자도 받아서 그런 글자가 든 40자는 4번을 지나 판 고르기에서 선다(31.7의 11번). 기본 다국어 평면 밖의 숫자는 서로게이트 2단위라 어느 쪽도 숫자가 아니어서 4번에서 선다. 문구의 `<다듬은 값>`은 다듬은 글자다. 짧은 해시를 안 받는 이유는 판 목록이 늘 40자로 실리고, 짧으면 커밋 2개를 가리킬 수 있기 때문이다. 번호와 커밋을 함께 막는 이유는 번호와 커밋이 서로 다른 판을 가리킬 수 있기 때문이다.

**나머지 칸.** `query`는 5.3의 다듬기로 다듬고, 비면 안 준 것으로 본다(31.7의 3번). `commit`과 `query`는 함께 줄 수 있다. 노트 id는 다듬지 않고 모양도 안 본다. 하위 노트는 자기 하위 id(`sn_`)를 그대로 준다. 응답의 `id`는 받은 글자 그대로다.

**판을 모으는 길.** 노트 id가 ASCII 영문자, 숫자, `-`, `_`로 된 1자 이상 128자 이하가 아니거나, `<vault>/.git`이 폴더가 아니면(링크는 따라간다) git을 안 부르고 판은 0개다. 아니면 3곳에서 모은다.

| 출처 | `source` | 찾는 법 |
|---|---|---|
| 경로 따라가기 | 저자 이름(`%an`)을 다듬은 글이 정확히 `withlog-auto`면 `auto`, 아니면 `manual` | 아래 1번과 2번 |
| 꼬리 줄 | 같다 | 아래 3번과 4번 |
| 옛 스냅숏 | `snapshot` | 아래 5번 |

1. 지금 경로 찾기: `git grep -l -z -F -e <노트 id> -- *note.md`. `.git`이 추적하는 파일의 작업 트리 내용에서, 대소문자를 가리는 고정 글자로 찾는다. pathspec의 `*`는 `/`도 넘어서, 경로가 `note.md`로 끝나는 파일이면 어느 깊이든 든다(`keynote.md`도 든다). 종료 코드가 0이 아니면(못 찾은 1과 오류 모두) 지금 경로는 0개다. 찾은 경로 가운데 안전한 경로만 남긴다. 안전한 경로는 1자 이상 1,024자 이하이고, `/`나 `-`로 시작하지 않고, NUL과 LF가 없고, `..` 조각이 없는 경로다. 그다음 vault의 그 파일 앞 4,096바이트를 읽어 1.14의 머리 id가 정확히 그 노트 id인 경로만 남긴다.
2. 경로마다 `git log main --follow --format=%x1e%H%x1f%ct%x1f%an --name-only -- <경로>`를 부른다. 출력을 U+001E로 나눠 기록 1개씩 보고, 기록마다 빈 줄을 뺀 1번째 줄을 U+001F로 나눠 커밋, committer 시각(유닉스 초), 저자 이름을 얻는다. 2번째 줄을 다듬은 글이 그 판의 경로다. 2번째 줄이 없는 기록(파일 목록이 안 나오는 병합 커밋 등)과 커밋이 40자 커밋 모양이 아닌 기록과 시각이 정수가 아닌 기록은 버린다. 종료 코드가 0이 아니면(`main`이 없을 때 포함) 그 경로의 판은 0개다.
3. 꼬리 줄 커밋 찾기: `git log main --format=%x1e%H%x1f%ct%x1f%an%x1f%B -F --grep=<노트 id>`. 기록마다 U+001F로 최대 4조각으로 나누고 4번째 조각(메시지 전체)의 줄 가운데, `Withlog-Notes:`로 시작하고 그 머리를 뗀 뒤 다듬어 공백 1글자로 나눈 조각에 그 노트 id가 정확히 든 줄이 있는 커밋만 남긴다. 1번과 2번에서 이미 찾은 커밋은 경로와 상관없이 뺀다.
4. 남은 커밋마다 `git diff-tree -r --root --no-commit-id --name-only -z <커밋>`으로 그 커밋이 첫 부모와 견줘 바꾼 경로를 얻는다. 이름 바꾸기 판정은 안 하고, 병합 커밋은 아무 경로도 안 나와서 버려진다. 마지막 조각이 정확히 `note.md`인 경로를 git 출력 차례로 후보로 삼고, `git cat-file --batch` 1번으로 그 커밋의 그 경로 글 전체를 읽는다. 머리 id(1.14, 글 전체에서 본다)가 그 노트 id인 첫 후보의 경로를 붙이고, 없으면 그 커밋을 버린다. 그 커밋에서 지워진 `note.md`도 후보에는 들지만, 그 커밋에 글이 없어서 고를 수 없다.
5. 옛 스냅숏: 31.6의 꼴로 `git log`에 argv 2칸 `--format=%H %ct`와 `refs/withlog/snapshots/<노트 id>`를 주어 부른다. 종료 코드가 0이 아니면(참조가 없을 때 포함) 스냅숏은 0개다. 줄마다 다듬어 공백 1글자로 나눈 조각이 정확히 2개이고, 앞이 40자 커밋 모양이고 뒤가 정수인 줄만 판(커밋, committer 시각)으로 삼는다. 판마다 `git ls-tree -l <커밋>`을 따로 1번씩 부르고, 그 출력의 빈 줄이 아닌 첫 줄을 첫 탭에서 나눠 뒤를 다듬은 글을 경로(파일 이름)로, 앞을 공백으로 나눈 마지막 칸을 크기로 읽는다. 크기가 정수가 아니거나 그 걸음이 실패하면 경로가 빈 글이 되어 아래 6번에서 버려진다.

1번과 2번에서 찾은 판 뒤에 4번에서 찾은 판을 잇고, 커밋과 경로가 같은 판은 처음 것 1개로 친다. 그 뒤에 5번의 판을 잇는다. 꼬리 줄로 따로 찾는 이유는 폴더가 옮겨지며 글도 크게 바뀌면 git의 이름 바꿈 판정이 놓치기 때문이다. 지금 경로를 git이 추적하는 파일에서만 찾으므로, 아직 커밋 안 된 새 노트는 경로 따라가기로는 판이 0개다.

모든 판은 이렇게 다듬는다.
1. `git cat-file --batch-check` 1번에 판마다 `<커밋>:<경로>`를 줄로 준다. 응답의 빈 줄이 아닌 줄을 입력 차례대로 맞대고, `<blob> blob <크기>` 꼴이 아닌 판(그 커밋에 그 파일이 없거나 폴더인 판)은 버린다. git이 실패하면 모든 판을 버린다.
2. committer 시각(초)이 늦은 것부터 늘어놓는다. 같은 시각이면 모은 차례를 지킨다.
3. 바로 뒤에 남긴 판과 blob이 같은 판은 뺀다. 스냅숏과 자동 커밋이 같은 글을 들 수 있기 때문이다. 이웃끼리만 견줘서 떨어진 자리의 같은 글은 남는다(31.7의 10번).
4. `git cat-file --batch` 1번으로 판마다 글을 읽는다. 글은 바이트 크기대로 잘라 UTF-8로 풀고 깨진 바이트는 U+FFFD가 된다. 1.8의 규칙으로 도장을 뽑는다.

「못 읽은 판」은 9번에서 글을 못 얻은 판이다. 커밋이 40자 커밋 모양이 아니거나 경로가 1번의 안전한 경로가 아니거나, git이 실패하거나 시간을 넘기거나, 그 항목이 blob이 아니거나 크기가 32비트 정수 범위를 넘는 경우다. 크기 상한은 따로 없고, UTF-8이 아닌 글은 U+FFFD를 넣어 읽은 판이다. 못 읽은 판도 `versions`에 남고, 도장 키가 없고, `matches`에는 안 든다.

이 명령은 git이 실패해도 서지 않는다. 걸음 1개가 실패하거나 시간을 넘기면 그 걸음이 찾은 판이 없는 것으로 보고 나머지를 이어 간다. 그래서 「판이 없다」와 「git이 실패했다」와 「`main`이 없다」가 응답에서 같다(31.7의 14번). 걸음마다 31.2의 시간 제한이 걸리고, 5번의 스냅숏 걸음은 31.6의 5초 제한이다.

**판 고르기.** `commit`을 주면 목록에서 그 커밋을 가진 첫 판이고, 없으면 `WL-409 그 커밋은 이 노트의 판 목록에 없다: <다듬은 커밋>`이다. 번호를 주면 목록의 그 차례(1부터)이고, 목록이 비었으면 `WL-409 그 노트에는 판이 아직 없다: <노트 id>`, 범위를 넘으면 `WL-409 판 번호가 범위 밖이다(1 부터 <판 수> 까지 있다): <번호>`다. `<번호>`는 읽어 낸 수를 ASCII 10진으로 적은 것이라, `+2`를 받으면 `2`로 적힌다. 종료 코드는 3이다. 조용히 빈 답을 내면 「그 판이 없다」와 「판이 아예 없다」가 화면에서 갈라지기 때문이다. 고른 판의 글은 9번과 같은 방법으로 1번 더 읽는다. 못 읽으면 실패하지 않고 `body`와 `noteBody` 없이 답한다.

응답은 객체 1개이고 키 차례가 계약이다. 성공은 늘 종료 코드 0이다.

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `id` | 문자열 | 늘. 받은 노트 id 글자 그대로 |
| 2 | `count` | 정수 | 늘. 판 수 |
| 3 | `body` | 문자열 | 판을 골랐고 그 글을 읽었을 때. 파일 전체(머리 포함) |
| 4 | `noteBody` | 문자열 | `body`와 함께. 1.6의 규칙으로 머리를 뺀 본문이고, 프론트매터가 없다고 판정되면(1.6의 7번 포함) 파일 전체 |
| 5 | `matches` | 문자열 배열 | `query`를 줬을 때. 비어도 싣는다 |
| 6 | `versions` | 배열 | 늘. 비면 `[]` |

`matches`는 목록 차례대로, 판의 본문(`noteBody`와 같은 규칙)에 `query` 글자가 들어 있는 판의 커밋을 싣는다. 본문의 시작 자리마다 `query`와 같은 길이의 구간을 글자 1개씩 견준다. 글자 2개가 같거나, 각자를 대문자로 바꾼 글자가 같거나, 대문자로 바꾼 글자를 다시 소문자로 바꾼 글자가 같으면 같은 글자로 본다. 글자 1개는 UTF-16 코드 단위 1개이고, 견주는 자리 2곳이 모두 서로게이트 짝이면 그 짝을 코드 포인트 1개로 본다(JDK 21의 `String.regionMatches(true, …)`). 바꾸기는 로캘 없이 글자 1개 단위로 하는 Java `Character.toUpperCase`와 `Character.toLowerCase`라서, `ß`와 `SS`처럼 길이가 바뀌는 짝은 다른 글자다. 이 판정에 쓰는 글은 9번과 같은 방법으로 모든 판을 1번 더 읽어 얻는다. 같은 커밋을 든 판이 2개면 그 커밋이 2번 실린다. 목록은 줄이지 않는데, 줄이면 판 번호가 검색어에 따라 바뀌기 때문이다. 머리를 엔진이 떼는 이유는 머리 읽는 규칙이 엔진에 1벌 있어서, 부르는 쪽이 2벌째를 두면 비교에 머리 조각이 섞이기 때문이다.

`versions`의 항목은 이 차례다.

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `index` | 정수 | 늘. 1부터 |
| 2 | `takenAt` | 문자열 | 늘. committer 시각을 `+09:00`으로 옮긴 `yyyy-MM-ddTHH:mm:ss+09:00`. 3곳 모두 committer 시각이다 |
| 3 | `source` | 문자열 | 늘. `auto`, `manual`, `snapshot` |
| 4 | `commit` | 문자열 | 늘. 40자 |
| 5 | `path` | 문자열 | 늘. 그 커밋 안의 vault 상대 경로. 스냅숏은 트리 뿌리의 파일 이름 |
| 6 | `bytes` | 정수 | 늘. blob의 바이트 수 |
| 7 | `editedBy` | 문자열 | 그 판의 글에 도장이 있을 때(`editedBy`와 `editedAt`을 다 들어 모두 비지 않음). 다듬은 글 그대로 |
| 8 | `editedSessionId` | 문자열 | 그 판의 도장에 세션이 있을 때. `editedBy`가 `app`이어도 싣는다(31.7의 4번) |

`editedBy`가 없으면 「모른다」이지 「AI가 썼다」가 아니다. 편집 도장은 2026-09-03에 들어왔고 그 앞의 글에는 없다. 부르는 쪽이 빈칸을 `tool`로 떨어뜨리면 되살릴 사람이 찾던 판을 지나친다. 화면은 번호가 아니라 `commit`으로 판을 고른다. 번호는 목록을 본 뒤 새 판이 생기면 밀리기 때문이다.

판 2개가 있는 노트의 목록 응답은 이런 모양이다(예시 값).

```json
{
  "id": "ndfixture-00000001",
  "count": 2,
  "versions": [
    {
      "index": 1,
      "takenAt": "2026-10-21T14:10:42+09:00",
      "source": "auto",
      "commit": "8c1f0e7d2b4a69f3e5d1c0b9a8f7e6d5c4b3a291",
      "path": "notes/serving/2026-06-16-1000-픽스처-노트-0001/note.md",
      "bytes": 236,
      "editedBy": "tool",
      "editedSessionId": "3f2a9c1e-5b7d-4e8f-9a01-2b3c4d5e6f70"
    },
    {
      "index": 2,
      "takenAt": "2026-10-20T09:00:00+09:00",
      "source": "manual",
      "commit": "0d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4",
      "path": "notes/serving/2026-06-16-1000-픽스처-노트-0001/note.md",
      "bytes": 198
    }
  ]
}
```

같은 노트에 `commit=0d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4`를 주면 `count` 뒤에 `body`(옛 `note.md` 전체)와 `noteBody`(`# 픽스처 노트\n\n`)가 들어가고 `versions`는 그대로다. `query=픽스처`를 함께 주면 `noteBody` 뒤에 `matches`가 들어간다.

앱의 이력 화면은 `history <id>` 뒤에 `commit=<커밋>`과 `query=<글자>`를 붙이거나 함께 붙여 부르고, 번호는 안 쓴다(코드 읽기로 확인).

## 31.5 명령 commit-vault

`commit-vault`는 vault의 커밋 안 한 변경을 지금 커밋하고 결과를 글자로 낸다. 이력 화면의 「이 판으로 되돌리기」가 되돌리기 직전과 직후에 부른다. 명령 표면에만 있고 인자도 옵션도 없다. 인자는 5.2의 차례로 본다. `이름=값` 칸이 1개라도 있으면 그 칸에서 바로 `WL-400 commit-vault 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [] 뿐이다.`로 서고, 이것이 자리 인자 수보다 먼저다. 이름 칸 없이 자리 인자만 있으면 `WL-400 commit-vault 이 받는 자리 인자는 0 개인데 <n> 개를 받았다: commit-vault`다. 실패 2가지 모두 종료 코드 3이다.

쓰기 깃발이 없어서 표식 확인, 색인 맞추기, 쓴 쪽 검사와 남기기가 모두 없다. 쓰기로 선언하면 쓰기 앞뒤 걸음이 이 명령 자체를 「앱의 쓰기」로 남기기 때문이다. 하는 일은 31.2와 31.3의 시도 1번이고, 「다시 해 볼 시각」을 안 본다. 까닭은 늘 `restore`이고, 쓴 쪽은 그 프로세스의 대기 기록에서 오며 대기 기록이 비었으면 `outside`다. 단발 모드로 부르면 새 프로세스라 대기 기록이 비어 있어서 늘 `outside`다.

결과는 31.2의 결과 처리를 그대로 지난다. `committed`와 `nothing`은 대기 기록을 비우고 실패 횟수를 0으로 돌리고, `disabled`는 대기 기록을 버리고, `skipped`는 다시 해 볼 시각을 30초 뒤로 미루고, `failed`는 실패 횟수를 올려 시각을 미룬다. serve 모드에서는 그 값이 뒤의 자동 커밋에도 그대로 걸린다.

직전에 커밋하는 이유가 이 명령의 존재 이유다. 앱에서 쓰던 글은 같은 쪽의 쓰기가 이어지는 동안 커밋되지 않는다(31.1). 그 글을 커밋 전에 옛 판으로 덮으면 이력 어디에도 안 남아서, 되돌리기를 되돌릴 수 없다. 직후 커밋은 되돌린 판이 목록 맨 위에 곧바로 서게 한다.

응답은 늘 종료 코드 0이고, 키는 `outcome`과 필요할 때의 `blocked` 차례다. stdout 바이트는 6.1의 규칙이다.

| `outcome` | 뜻 | `blocked` |
|---|---|---|
| `committed` | 커밋을 1개 만들었다 | 없음 |
| `nothing` | 바뀐 것이 없다 | 없음 |
| `skipped` | 지금은 커밋하면 안 되는 상태다 | `index-lock`, `in-progress`, `not-main` |
| `disabled` | 자동 커밋이 꺼졌거나 git 저장소가 아니다 | `off`, `not-repo` |
| `failed` | git이 실패했다 | 없음 |

```json
{
  "outcome": "skipped",
  "blocked": "index-lock"
}
```

앞의 2가지면 지금 vault의 글이 이력에 있다. 나머지 3가지면 없고, 앱은 그때 되돌리기를 안 한다. 덮으면 지금 글을 잃기 때문이다. 앱은 모르는 `outcome`을 `failed`로 읽고 모르는 `blocked`는 버린다(코드 읽기로 확인). `blocked`를 싣는 이유는 「다른 git 작업이 돌고 있어요」 1문장으로는 남은 잠금과 진행 중인 병합과 다른 브랜치를 사람이 가를 수 없었기 때문이다. 위 5가지 밖의 글자는 이 명령에서 나오지 않는다.

## 31.6 옛 스냅숏

스냅숏은 노트 본문 파일을 덮기 직전에 지금 그 파일의 바이트를 vault git의 별도 참조에 남기던 장치다. 2026-09-14부터 2026-10-15까지 기본으로 켜져 있었고, 자동 커밋이 쓴 쪽이 바뀌기 직전에 커밋하게 된 뒤로 기본이 꺼졌다. 쓰기만 꺼지고 `history`는 옛 스냅숏을 계속 읽는다.

스위치는 설정 `withlog.vault.snapshot.enabled`(환경변수 `WITHLOG_VAULT_SNAPSHOT_ENABLED`)이고 기본값은 거짓이다. 받는 글자는 31.1의 불리언 규칙과 같다. 켜면 노트와 하위 노트의 본문 파일을 쓰는 모든 쓰기(만들기, 고치기, 메타 쓰기, 파생 쓰기, 폴더 옮긴 뒤의 쓰기)가 이 걸음을 지난다. 자리는 크기 상한을 지난 뒤, 원자적 쓰기(7.4) 바로 앞이다(7.2의 「판정 뒤의 걸음」). 그래서 폴더를 옮기는 쓰기는 옮긴 뒤 새 자리의 파일(옛 바이트)을 남긴다. `restore_doc`의 `agenda` 바꾸기만 안 지난다(7.3).

1. id가 ASCII 영문자, 숫자, `-`, `_`로 된 1자 이상 128자 이하가 아니면 아무것도 안 한다. 루트 노트는 노트 id, 하위 노트는 하위 id(`sn_`)를 쓴다.
2. `<vault>/.git`에 아무것도 없거나(파일이든 폴더든 있으면 된다, 링크는 따라간다) 덮을 자리에 파일이 없으면 아무것도 안 한다. 진짜 새 파일이라 잃을 바이트가 없기 때문이다.
3. `git hash-object -w -- <파일 절대 경로>`로 지금 바이트를 blob으로 넣는다.
4. `git mktree`의 표준 입력에 `100644 blob <blob>\t<파일 이름>\n` 1줄을 준다. 파일 이름은 덮을 파일의 실제 이름이라 폴더 노트면 `note.md`나 `note.json`이고 단일 파일 노트면 그 파일 이름이다. blob이 40자 커밋 모양이 아니거나, 이름이 비었거나 255자를 넘거나 `/`나 `..`이 들면 멈춘다. 이름을 `note.md`로 못박으면 json 노트의 스냅숏이 거짓 이름을 달기 때문이다.
5. `git rev-parse --verify -q refs/withlog/snapshots/<id>`로 앞 스냅숏을 찾는다. 종료 코드가 0이고 출력이 있으면 그것이 부모이고, 아니면 부모 없이 간다.
6. `git commit-tree <트리> [-p <앞 스냅숏>] -m 'withlog-auto: <id> — <vault 상대 경로>'`로 커밋을 만든다. 가운데 줄표는 U+2014이고 앞뒤에 공백이 1개씩 있다. `<vault 상대 경로>`는 덮을 파일의 자리이고, 상대 경로로 못 바꾸면 절대 경로다. 저자와 커미터는 31.3과 같다.
7. `git update-ref refs/withlog/snapshots/<id> <커밋>`으로 참조를 옮긴다. 이 걸음의 결과는 안 본다.

이 걸음의 git은 31.2와 다른 꼴로 띄운다. `PATH`에서 찾은 `git`을 vault 뿌리에서 띄우는 것은 같지만, `GIT_DIR`과 `GIT_WORK_TREE`를 못박지 않고 엔진의 환경을 그대로 물려주며, `-c` 앞 옵션도 안 붙인다. 표준 출력과 표준 오류는 합쳐서 그 걸음이 끝난 뒤에 읽고, 걸음마다 5초를 넘기면 SIGKILL로 끝낸다(31.7의 15번). 3번, 4번, 6번이 실패하면(0이 아닌 종료 코드, 빈 출력, 시간 초과, 못 띄움) 조용히 멈추고 다시 해 보지 않는다. 이 걸음이 쓰기 앞에 서 있어서, 안전망이 본업을 막으면 안 되기 때문이다. 5번의 실패는 「앞 스냅숏 없음」으로 읽혀서 31.7의 12번이 생긴다.

`main`이 아니라 노트마다 따로 둔 참조에 쌓아서 `git log`와 `git status`의 출력은 전혀 안 바뀐다. 노트 쓰기가 하루 수십에서 수백 건이라 `main`에 쌓으면 사람 이력이 묻히기 때문이다. `commit-tree`는 훅을 안 돌리고 `-S` 없이는 서명도 안 하고 인덱스도 안 건드려서, 이 걸음에는 31.2의 앞 옵션이 없다.

`history`는 스위치와 상관없이 같은 꼴(5초, SIGKILL, 환경 그대로)로 스냅숏을 읽는다. 읽는 법은 31.4의 5번이다.

## 31.7 얼어 있는 특이점

다시 지을 때 지킬지 고칠지는 부록 D에서 정하고, 정하기 전에는 지금 엔진과 같게 판다(0.5). 묶음이 이 장을 안 덮어서 어느 쪽으로 짜도 검사로는 안 가려지지만, 다음 레인의 기대값을 지금 엔진으로 뜨기 때문이다. 모두 코드 읽기로 확인했고 실행해 보지는 않았다.

1. 단발 모드의 쓰기는 쓴 쪽 정보를 잃는다. 그 프로세스의 대기 기록이 사라져서, 다음 serve가 뜰 때 커밋에 `outside`로 담긴다.
2. 거절되거나 실패한 쓰기도 쓴 쪽으로 남는다(7.6의 10번). 그동안 바깥에서 바뀐 것이 있으면 그 커밋이 그 쓴 쪽 이름을 단다.
3. `history`의 `query`는 앞뒤를 뗀 뒤 비면 「안 줌」으로 본다. 그래서 `찾을 글자가 비었다` 문구는 나올 일이 없고, `query=`는 `matches` 없이 성공한다. 앞뒤에 공백을 붙인 검색어도 공백 없이 찾는다.
4. `history`의 `editedSessionId`는 `editedBy`가 `app`인 판에서도 실린다. `get_doc`은 그 경우를 빼서(11.6) `history`와 `get_doc`이 같은 도장을 다르게 낸다.
5. 기본 브랜치가 `main`이 아닌 vault는 자동 커밋이 영영 안 되고, 대기 기록이 있는 동안 30초마다 git을 다시 부른다. git을 못 띄우는 기기도 `not-main`으로 같은 길을 간다. `symbolic-ref`의 표준 오류도 합쳐 읽어서, git이 경고를 1줄이라도 내면 `main` 위에서도 `not-main`이 된다.
6. `history`는 지금 경로를 경로 글자가 `note.md`로 끝나는 파일에서만 찾는다. 그래서 json 노트(`note.json`), html 노트(`note.html`), 대부분의 단일 파일 노트는 git 판이 0개이고 옛 스냅숏만 나온다. 이름이 우연히 `note.md`로 끝나는 단일 파일 노트(예시 값 `.-keynote.md`)는 머리 id가 맞으면 찾힌다. 자동 커밋의 `Withlog-Notes` 줄과 꼬리 줄로 찾은 판의 경로는 마지막 조각이 정확히 `note.md`인 파일만 본다.
7. 스냅숏의 git 걸음은 31.2의 환경 못박기를 안 해서, 엔진의 환경에 `GIT_DIR`이 있으면 vault가 아닌 저장소에 쓰고 읽는다. `.git`도 있는지만 봐서 `.git`이 파일인 작업 트리에서도 돈다.
8. 꼬리 줄의 세션 값은 검사 없이 실린다. 줄바꿈이 든 세션 값은 꼬리 줄을 여러 줄로 쪼개고, 빈 세션 값은 `Withlog-Session:` 줄에 빈 조각으로 실린다. 세션 값 끝의 공백은 git의 공백 정리가 떼어서, 대기 기록의 값과 커밋에 남은 글자가 다를 수 있다.
9. 내려갈 때 커밋이 launchd의 남은 시간(약 20초)을 넘기면 SIGKILL을 맞아 `index.lock`이 남을 수 있다. 그 잠금이 생긴 뒤 10분이 지날 때까지 자동 커밋과 `commit-vault`가 `index-lock`으로 건너뛴다.
10. 판 접기는 이웃한 판끼리만 견줘서, 글을 되돌렸다 다시 고친 이력은 같은 글의 판이 떨어진 자리에 여러 번 남는다.
11. `history`의 번호와 `commit` 검사는 ASCII 숫자만 받지 않는다. 번호는 부호와 유니코드 숫자를 받아서 `+2`, `002`, `۲`(아랍 숫자 2)를 모두 2로 읽는다. `commit`은 「숫자」 자리에 기본 다국어 평면의 유니코드 숫자도 받아서, 그런 글자가 든 40자는 `WL-400`이 아니라 판 고르기까지 가서 `WL-409 그 커밋은 이 노트의 판 목록에 없다`로 끝난다. 다시 짜는 구현이 ASCII만 받으면 이 2가지에서 답이 갈린다.
12. 스냅숏의 5번 걸음이 시간을 넘기거나 실패하면, 앞 스냅숏이 있어도 부모 없는 커밋을 만들고 7번이 참조를 그리로 옮긴다. 그러면 그 노트의 옛 스냅숏 사슬이 참조에서 끊겨 `history`에 다시 안 나온다. git 객체는 정리될 때까지 남는다.
13. 하위 id는 루트 노트 안에서만 유일한데(1.4), `history`와 스냅숏 참조는 하위 id 1개로 찾는다. 다른 루트에 같은 하위 id가 있으면(손으로 복사한 폴더 등) 그 하위 노트 2개의 판이 목록 1개와 스냅숏 사슬 1개에 섞인다.
14. `history`는 git이 실패하거나 시간을 넘겨도 서지 않고 그 걸음의 판을 빼고 답한다. 그래서 git을 못 띄우는 기기와 `main`이 없는 저장소에서도 `count` 0과 종료 코드 0이 나오고, 「판이 없다」와 「판을 못 읽었다」를 응답으로 가를 수 없다.
15. 스냅숏 목록 읽기(31.4의 5번)는 `git log`가 끝난 뒤에야 출력을 읽는다. 출력이 파이프 용량(코드에 남은 기록으로는 이 기기에서 64KB)을 넘으면 git이 쓰다가 막혀 5초 제한에 걸리고, 그 노트의 옛 스냅숏이 목록에서 통째로 빠진다. 줄 1개가 52바이트라 스냅숏이 1,200개쯤을 넘는 노트에서 생긴다. 스냅숏이 켜져 있던 동안에는 본문 파일을 덮는 쓰기마다 스냅숏이 1개 생겨서, 그때 자주 고친 노트는 이 수에 닿을 수 있다. 코드 읽기로 확인했고 실행해 보지 않았다.
