DEVELOPER GUIDE

aisurada 개발자 사용 가이드

이 문서는 저장소를 처음 받은 개발자가 빌드하고, 돌려 보고, 시험하고, 고치는 데 필요한 것을 모았다. 2026-11-04 판(main 브랜치)을 기준으로 쓰고, 명령과 수치는 이 판에서 직접 확인한 것만 적었다. 읽어서만 확인한 것은 「확인 방법」을 함께 적었다.

docs/ 아래 기록은 이름을 바꾸기 전에 쓴 것이라 옛 이름이 그대로 적혀 있다. 읽다가 낯선 이름이 나오면 §10의 대응표로 바꿔 읽는다.

엔진은 색인 파일이 없다. 명령을 받을 때마다 vault 폴더를 훑는다. 화면은 엔진을 직접 부르지 않고 호스트의 sidecar_call로 ais-cli.jar를 실행하며, ais-cli가 소켓으로 엔진에 붙는다.

#3. 처음 시작하기

bash
# 1. 엔진과 클라이언트를 짓는다 (dist/에 jar 4개가 생긴다)
./build.sh

# 2. 가장 작은 vault를 만든다 (임시 폴더에서 해 보자)
export VAULT_DIR=$(mktemp -d)/vault && mkdir -p "$VAULT_DIR"
java -jar dist/ais-engine.jar init-workspace name=시험 'templates=[]' --aisurada.vault="$VAULT_DIR"

# 3. 읽기와 쓰기 (아젠다 이름이 slug가 된다. 한글 이름이면 slug도 한글이다)
java -jar dist/ais-engine.jar create-agenda 'title=demo' --aisurada.vault="$VAULT_DIR"
java -jar dist/ais-engine.jar create-doc agenda=demo type=free title=제목 body=본문 --aisurada.vault="$VAULT_DIR"
java -jar dist/ais-engine.jar list-docs --aisurada.vault="$VAULT_DIR"

# 4. 엔진을 띄워 두고 클라이언트로 부른다 (터미널 둘). 변수는 export하지 말고 명령 앞에 붙인다
AISURADA_VAULT="$VAULT_DIR" AISURADA_SIDECAR_SOCKET="$HOME/aisurada-dev.sock" java -jar dist/ais-engine.jar serve            # 터미널 1
AISURADA_VAULT="$VAULT_DIR" AISURADA_SIDECAR_SOCKET="$HOME/aisurada-dev.sock" java -jar dist/ais-cli.jar list-docs limit=5  # 터미널 2 (VAULT_DIR을 같은 값으로 다시 준다)

4번의 AISURADA_* 값을 export하면 같은 터미널에서 띄우는 앱도 그 값을 물려받는다. 소켓 경로가 vault 하나에 고정돼서 앱이 여는 다른 vault와 어긋나고, 그 소켓에 엔진이 없으면 §7의 AIS-400 오류가 난다.

create-doc은 agenda=, type=, title=, body=가 필요하다(type=을 빼면 AIS-400). 응답에는 id, path, 쓰기 전 토큰 precondition(f1:…)이 들어 있다.

ais-cli는 떠 있는 엔진이 없으면 launchd로 엔진을 띄우려고 한다. 이걸 피하려면 4번처럼 엔진을 먼저 직접 띄운다(§6). 끝나면 터미널 1에서 Ctrl-C로 엔진을 내리고 rm "$HOME/aisurada-dev.sock"로 소켓을 지운다.

#Rust 엔진 이전 (engine-rs/)

엔진(Java)을 Rust로 옮기는 작업 공간이다. 같은 기능을 하는 것을 기준으로 옮기며(바이트 단위 호환이 아니다), 읽기 명령 16개는 앱이 이미 이것으로 읽는다: 새로고침 길의 6개(list_docs, list_agendas, list_projects, list_templates, list_trash, reindex), 노트 하나를 여는 길의 6개(get_doc, list_sub_notes, get_sub_note, list_comments, list_attachments, get_agenda_facts), 그리고 검색·태그·템플릿 하나·판 목록의 4개(search_docs, list_tags, get_template, history). 쓰기 명령과 4부·태스크·자원 명령, ais-cli와 MCP는 아직 Java 엔진이다. 결정과 단계는 개발자의 vault 노트 「Rust 엔진 이전 — 결정 3: 코드 구조와 클라우드 대비」와 1단계 기록, 2단계 새로고침 길 기록, 2단계 노트 여는 길 기록, 2단계 검색·판 목록 기록에 있다.

자리내용
engine-rs/crates/ais-core/vault 규칙 라이브러리: frontmatter(노트 머리 YAML 읽기·쓰기), vault(아젠다·노트·후속 노트·프로젝트·템플릿·휴지통·코멘트·사실층 읽기와 훑기, 본문 글자 뽑기 plain_text, git 실행 git과 노트의 판 목록 history), commands(명령 실행기), model(응답 모양), engine(진입점 Engine::call)
engine-rs/crates/ais-core/examples/compat_check(Java 엔진과 읽기 응답 맞대기), ais_call(명령 하나를 불러 응답 보기), yaml_check·yaml_fuzz_cases(머리 읽기·쓰기 맞대기)
engine-rs/crates/ais-core/tests/합성 vault로 읽기 동작을 확인하는 통합 시험(Java 없이 돈다)
engine-rs/tools/compat/합성 vault 생성기 make-fixture.sh, 검색 시험 노트를 덧붙이는 add-search-notes.sh, git 저장소와 판 이력을 만드는 add-git-history.sh
engine-rs/tools/yaml-spike/머리 읽기·쓰기를 Java 기준값과 맞대는 도구(YamlGroundTruth.java, run.sh, cases.txt)

앱의 호출 길. 화면은 workspace/engine.ts의 engineCall 한 곳으로 엔진을 부른다. 문자열 목록(argv)은 늘 Java 엔진(sidecar_call → ais-cli)으로 간다. 호출 객체(Call, data/commands.ts의 read.docs() 따위)는 호스트의 engine_commands가 알린 명령이면 Rust 엔진(engine_call, src-tauri/src/engine.rs)으로, 아니면 toArgv로 풀어 Java 엔진으로 간다. Rust 응답은 engine.ts의 어댑터가 기존 화면 모양으로 바꾼다. 되돌리는 스위치: 앱을 AISURADA_ENGINE=java로 띄우면 engine_commands가 빈 목록을 돌려줘서 모든 명령이 Java 엔진으로 간다. 시험과 브라우저의 가짜 호스트에는 engineCommands가 없어서 늘 Java 경로다.

bash
(cd engine-rs && cargo test -p ais-core)                                              # Java 없이 도는 단위·통합 시험
pnpm --dir native-host exec node --import tsx --test scripts/engine-route.test.mjs    # 화면의 라우팅과 어댑터
cargo test --manifest-path native-host/src-tauri/Cargo.toml --locked engine::         # 호스트 engine_call (실제 Tauri 호출 경로)

Java 엔진과 읽기 응답을 맞대려면 ./build.sh로 dist/ais-engine.jar를 만든 뒤 아래를 돌린다. compat_check는 vault를 읽기만 하고, 응답을 새 모양으로 바꿔 견주며, 어긋남이 0이어야 한다.

bash
engine-rs/tools/compat/make-fixture.sh <빈 폴더>        # 합성 vault(진짜 vault 내용 없음)
engine-rs/tools/compat/add-search-notes.sh <그 폴더>    # 검색 순위·서식·동점 시험 노트를 덧붙인다
engine-rs/tools/compat/add-git-history.sh <그 폴더>     # git 저장소와 판 이력(`history` 시험용). 작업 트리는 그대로 돌아온다
(cd engine-rs && cargo run -q -p ais-core --example compat_check -- ../dist/ais-engine.jar <합성 vault> [다른 vault...])

노트 머리 읽기·쓰기를 Java와 맞대려면 기준값은 노트 머리가 들어가므로 저장소 밖 폴더에 뽑는다.

bash
engine-rs/tools/yaml-spike/run.sh <저장소 밖 폴더> --vault <vault 폴더>     # Java 기준값. vault는 읽기만 한다
(cd engine-rs && cargo run -q -p ais-core --example yaml_check -- <저장소 밖 폴더>/ground-truth.jsonl)

퍼징 사례는 cargo run -q -p ais-core --example yaml_fuzz_cases -- <ground-truth.jsonl> <건수> <시드> > 사례.txt로 만들고, run.sh <다른 폴더> --cases 사례.txt로 기준값을 다시 뽑아 같은 yaml_check에 넣는다. yaml_check의 「실패」 열이 0이어야 하고, 「경고」는 Rust가 Java보다 너그럽게 읽은 입력이다.

#5. 엔진 쓰는 법

#세션 에이전트(Codex·Gemini) 확장

노트에 적는 세션 id는 원래 Claude Code 것만 있었다. 이 확장은 Codex와 Gemini CLI의 세션도 같은 자리에 적고, 노트 칩에서 터미널로 이어 열고, 두 CLI의 대화 기록을 세션 화면에서 읽게 한다. 외부 설명서에 없는 확장이다. 설명서의 4.4(세션 표식), 1.7·1.10(머리말 키와 도장), 7장(read-session, session-titles)과 어긋나는 곳은 아래 표가 전부다. 이 표 밖에서는 설명서대로 동작해야 한다.

곳설명서확장

#프로젝트의 저장소와 아젠다의 projectRepo

프로젝트가 저장소(로컬 폴더, GitHub 저장소, 또는 둘 다)를 여러 개 가지고, 아젠다가 그중 하나를 이름으로 가리킨다. 나중에 GitHub App 연동과 앱 안의 개발 기능이 이 위에 올라간다. 외부 설명서에 없는 확장이다. 설명서 21.5는 프로젝트 파일의 키를 4개로 못 박아 두었고(조건부 키 없음), 20.5는 아젠다의 키를 6개로 정했다.

  • 프로젝트 파일. 저장소가 있으면 hue 다음에 repos: 한 줄이 붙는다. 값은 한 줄짜리 JSON 배열이다: repos: [{"name":"app","path":"/Users/me/app","github":"me/app","githubId":123}]. 항목은 name(필수, 프로젝트 안에서 유일, 50자까지, 빗금 없음), path(절대 경로), github(owner/name), githubId(양의 정수, github와 함께)이고 path나 github 가운데 하나는 있어야 한다. 최대 20개. 저장소가 없으면 파일은 설명서의 4줄 그대로다.
  • 왜 한 줄인가. 프로젝트와 아젠다 파일은 설명서 2.1의 줄 읽개로 읽는다. 이 읽개는 줄 맨 앞의 키: 값만 보고 들여쓴 줄은 건너뛰므로, 들여쓴 YAML 목록은 읽개에 안 보인다(repos:가 빈 값으로 읽힌다). JSON은 YAML이기도 해서 일반 YAML 도구도 읽는다.
  • 아젠다 파일. project 바로 뒤에 projectRepo: <저장소 이름>이 붙는다. 프로젝트가 없는 아젠다는 늘 없는 것으로 읽는다. 기존 repo(로컬 경로, 자유 텍스트)는 그대로이고 프로젝트가 없는 아젠다는 지금처럼 이것만 쓴다.
  • 명령. create-project와 update-project의 repos=<JSON 배열>(update는 통째로 바꾸고 빈 값이나 []는 지움, 안 주면 그대로), create-agenda와 update-agenda의 projectRepo=<이름>. 틀린 값은 파일을 쓰기 전에 AIS-400으로 거절한다. projectRepo는 project가 있고 그 프로젝트의 repos에 그 이름이 있어야 한다. update-agenda로 프로젝트를 바꾸거나 미분류로 보내면 낡은 가리킴을 같이 지우고, 안 건드리면 그대로 둔다.
  • 읽을 때는 너그럽다. 손으로 고친 repos:에서 못 읽는 항목과 겹친 이름은 건너뛰고, 줄 전체가 JSON 배열이 아니면 없는 것이다. 프로젝트가 저장소를 지워도 아젠다 파일은 건드리지 않아 낡은 이름이 남을 수 있고, 그 판단은 쓰는 쪽(화면)이 한다.
  • 응답. list-projects와 create/update-project는 저장소가 있을 때만 repos 배열을, list-agendas와 create/update-agenda는 가리킬 때만 projectRepo를 싣는다. 없으면 설명서의 모양 그대로다.
  • 로컬 폴더가 없는 GitHub 항목. path가 없으면 앱이 정한 폴더(~/Library/Application Support/aisurada/repos/<소유자>/<이름>)에 받아 쓴다. 엔진은 이 폴더를 알지 못한다. 받는 일과 GitHub 연결은 호스트(아래 「GitHub App 연결」)가 하고, 폴더를 풀어 쓰는 일은 화면(repoLinks.ts)이 한다.
  • 화면. 프로젝트 폼(Forms.tsx의 EntityForm)에 저장소 목록 편집기(RepoListEditor.tsx)가 있다. 항목마다 이름, 폴더(「폴더 고르기」 대화상자), GitHub owner/name(연결했으면 「내 저장소에서 고르기」)을 적는다. 저장하기 전에 validateRepos가 엔진과 같은 규칙으로 막고, 바뀐 것만 repos=로 보낸다(reposField: 항목을 모두 지우면 빈 값을 보내 줄을 지운다). 아젠다 폼은 고른 프로젝트에 저장소가 있으면 「프로젝트 저장소」 선택을 보이고, 고르면 옛 「저장소」 글 칸은 숨긴다(옛 repo 값은 그대로 둔다). 프로젝트를 바꾸면 선택은 비워진다. 프로젝트가 없는 아젠다와 저장소가 없는 프로젝트의 아젠다는 옛 「저장소」 글 칸만 쓴다.
  • 안내 팝업. 편집기의 「왜 필요해요?」가 RepoGuide.tsx를 연다. 글이 아니라 그림 3장을 한 장씩 넘겨 보는 팝업이고(제목과 설명은 장마다 한 줄, 시험이 글자 수 상한을 지킨다), 그림은 인라인 SVG다. 1장은 프로젝트의 저장소 목록에서 아젠다가 하나를 고르면 아젠다 화면에 그 저장소가 표시되는 흐름과 점선의 「앞으로: 앱 안 개발」, 2장은 이 컴퓨터의 폴더(그대로 사용, 복사 안 함)와 GitHub 저장소(앱이 앱 전용 폴더에 받음, 연결 필요)의 두 방식과 지금 연결 상태·받는 폴더, 3장은 개인 키는 키체인에만, 읽기와 받기만 함, 빼도 폴더는 그대로, 목록은 프로젝트 파일에 저장이다. 색은 모두 앱의 색 변수(.rg-* 클래스)에서 와서 화면 모양과 어두운 모드를 따른다. 그림에 적힌 말은 이 문서의 동작 설명을 그대로 옮긴 것이라, 저장 위치나 받는 규칙이나 GitHub에 하는 일이 바뀌면 그림과 시험의 글(repo-links.test.mjs의 GUIDE_WORDS)을 같이 고친다. 팝업은 Modal(포털)이라 서버 렌더 시험으로 열 수 없어, 시험은 그림 3장의 글과 설명, 글자 수 상한, 편집기의 단추만 본다. 모양은 앱 CSS를 입혀 따로 렌더해서 눈으로 확인한다.

#프로젝트 자원: 스킬과 에이전트 정의 (resource/)

프로젝트에서 AI에게 작업을 시키기 위한 바탕으로, 스킬(SKILL.md가 든 폴더. AI에게 일하는 법을 알려 주는 지침)과 에이전트 정의(이름, 설명, 지침, 쓸 스킬, 권한을 적은 글 하나)를 vault에 보관하고 관리한다. 외부 설명서에 없는 확장이다. 지금은 엔진의 명령줄 표면, MCP 도구, 화면(글로벌 페이지와 프로젝트 페이지)이 있고 작업 실행기는 아직 없다. 진행 계획은 이슈 #53(AI가 쓴 변경의 승인 워크플로우)과 같이 본다.

  • 규칙 4개(사용자가 확정). ① 스킬과 에이전트는 특정 AI 도구에 종속되지 않는다(중립한 형식이고, 도구별 차이는 선택 칸 tools에만 둔다). ② 자원은 글로벌과 프로젝트 두 범위로 관리한다. ③ 프로젝트는 글로벌 자원을 ID로 참조하고, 참조한 것만 그 프로젝트에서 쓸 수 있다. ④ 참조하지 않은 것은 쓰지 않는다.
  • 위치. .aisurada/resources/ 아래다. 설명서가 정한 notes/와 .aisurada/projects/ 등을 건드리지 않는 새 영역이고, 노트를 훑는 쓰기 명령과 기존 명령이 이 영역을 보지 않는다(시험으로 확인). global/{skills/<slug>/SKILL.md, agents/<slug>.md}(글로벌), projects/<프로젝트 slug>/{skills/…, agents/…, refs.md}(프로젝트 자원과 참조 목록), .trash/<id>/(지운 자원), .history/<id>/(고치기 전의 판). 범위는 파일 위치로 정해진다. 프로젝트 slug는 만든 뒤 바뀌지 않아서(update-project에 slug 인자가 없다) 프로젝트별 폴더가 어긋나지 않는다.
  • ID. 노트·아젠다와 같은 형식(머리 + 36진수 시각 + - + 16진수 8자리)이고 머리가 종류를 알려 준다: 스킬 sk…, 에이전트 정의 ap…. ID는 머리말 안에 있어서 이름을 바꿔도 참조가 안 끊긴다(바꾸면 폴더·파일이 옮겨진다). 참조는 이름이 아니라 ID로 건다.
  • 파일 모양. --- 머리말(YAML)과 지침 본문이다. 공통은 id, name, description, 에이전트만 permission(read, edit, publish 3단계, 모르는 값은 가장 약한 read로 읽는다), skills(스킬 ID 목록), repo(프로젝트 에이전트가 쓸 저장소 이름), 선택 칸 tools, 기록 칸 editedAt, editedSession, editedAgent다. 본문은 파일에서 끝에 줄바꿈 하나가 붙은 채 적히고 읽을 때 그 하나를 뗀다. 같은 값이면 늘 같은 바이트다.
  • 도구별 선택 칸 tools. tools: {claude: {...}, codex: {...}}처럼 소문자 도구 이름 아래에 둔다. 정의가 도구에 물들지 않게 안전장치 셋을 둔다. ① 중립 항목만으로 정의가 완전하다 ② 도구 칸은 없어도, 몰라도 무시된다 ③ 모르는 도구 칸도 읽고 다시 쓸 때 지우지 않고 보존한다(시험으로 고정). tools={}는 칸을 비운다.
  • 이름과 범위. 이름은 60자까지, /와 \와 제어 문자가 없고 slug(50자까지)를 만들 수 있어야 한다. 한 범위·한 종류 안에서는 slug가 하나뿐이다. 범위가 다르면 같은 이름이 공존한다(ID로 구분하고 화면은 「글로벌 · 이름」, 「프로젝트 · 이름」으로 보인다). 스킬과 에이전트는 이름이 같아도 된다.
  • 참조(refs.md). 프로젝트 폴더의 refs.md에 줄마다 <ID> # <이름 힌트>를 적는다. 엔진은 ID만 읽고 힌트는 읽는 사람을 위한 것이다(참조를 켜고 끌 때마다 지금 이름으로 새로 적는다). 프로젝트 파일이 아니라 따로 두는 까닭은, 설명서가 프로젝트 파일의 줄을 정해 두었고 그 파일을 모르는 옛 빌드가 다시 쓸 때 모르는 줄을 버리기 때문이다. 글로벌 자원만 참조한다(프로젝트 자원은 참조하지 않아도 쓸 수 있다). 참조한 글로벌 자원을 지우면(휴지통) 「깨진 참조」로 알리고, 되살리면 이어진다.
  • 쓸 수 있는 자원을 계산하는 곳은 하나다. ResourceResolver.resolve가 프로젝트 자원 + 참조한 글로벌 자원을 낸다(출처 own/ref). 깨진 참조(broken)와, 쓸 수 있는 에이전트가 필요로 하지만 쓸 수 없는 스킬(missingSkills, 글로벌 스킬이면 canReference: true라 참조해서 채울 수 있다)도 같이 낸다. 화면의 선택 목록, AI가 보는 목록, 실행 입력은 모두 이 결과만 써야 규칙 ④가 새지 않는다. 빠진 스킬은 스스로 쓸 수 있게 되지 않는다(자동으로 참조하지 않는다). set-resource-ref의 with-skills=true가 에이전트를 참조할 때 그 에이전트의 글로벌 스킬도 함께 참조하게 해 준다.
  • 에이전트 검사. skills는 존재하는 스킬이어야 하고, 글로벌 에이전트는 글로벌 스킬만, 프로젝트 에이전트는 글로벌 스킬과 자기 프로젝트의 스킬을 쓴다. repo는 프로젝트 에이전트만 줄 수 있고 그 프로젝트의 저장소 이름이어야 한다(글로벌 에이전트에는 저장소 칸이 없다).
  • 명령 15개(명령줄과 MCP 도구 모두. 도구 이름은 밑줄 이름이고 with-skills는 withSkills다. 틀린 값은 쓰기 전에 AIS-400, 없는 것은 AIS-404). 앞의 8개는 자원을 다루고, 뒤의 7개는 승인 워크플로(아래)다. MCP에서는 읽기 6개(list_resources, get_resource, usable_resources, list_resource_versions, list_resource_changes, get_resource_change)가 기본 모드에도 보이고, 쓰기 4개(save_resource, delete_resource, restore_resource, set_resource_ref)는 노트와 같이 --write일 때만 보인다(설정의 「노트를 만들고 고치는 것도 허용」). 승인·거절·정책 변경(approve-resource-change 따위)은 MCP 도구가 아니다. 도구는 같은 ResourceCommands로 가고, 인자 해석(ArgsParser의 RESOURCE_TOOLS)이 JSON 인자를 명령줄과 같은 옵션 맵으로 바꾼다.

#승인 워크플로(이슈 #53)

AI가 고친 스킬·에이전트 정의가 곧바로 쓰이지 않고, 사람이 승인한 판만 쓰이게 한다. 에이전트의 권한(read/edit/publish)과 참조가 AI 스스로에 의해 풀리지 않게 하려는 것이다. 엔진(이 절)과 화면, 알림 세 조각이다. 러너 연결은 4단계의 첫 작업이다.

  • AI의 통로 판별. 세션 표식이 달린 요청이나 MCP 도구 이름(밑줄)으로 부른 요청은 AI다. 앱 화면은 명령 이름(하이픈)으로 세션 표식 없이 부르므로 사람이다. 사람이 낸 변경은 정책과 상관없이 바로 적용한다.

  • 정책(set-resource-policy, 사람만). 칸 4개가 각각 auto(AI가 써도 바로 적용)나 approve(승인 필요)다. 기본은 project=auto(프로젝트 자원의 내용), global=approve(글로벌 자원 변경), refs=approve(참조 끄기), permission=approve(권한 내림). 권한 올림, 도구 칸(tools) 변경, 참조 켜기는 정책과 상관없이 늘 승인이 필요하다(Approvals.Category의 fixed). tools는 도구별 허용 도구 목록 같은 권한성 값이 들어갈 수 있어서 같이 묶었다. 되살리기는 예전 판이 없는 만들기로 본다.

  • 대기 변경. 승인이 필요하면 적용하지 않고 .aisurada/pending/<pc…>.json에 올린다(vault 안이라 이력에 남고 vault를 옮겨도 따라온다). 응답은 오류가 아니라 queued: true, changeId, 까닭(reasons), 안내 글이다. 같은 변경을 되풀이하면 새로 쌓지 않고 같은 changeId에 duplicate: true를 준다. 대기 중에는 list-resources, get-resource, usable-resources, MCP 조회 모두에 이전 판이 그대로 보인다.

  • 승인·거절. approve-resource-change <id>는 같은 명령 경로를 한 번 더 지나 적용하고(승인 때의 검사와 평소 검사가 갈라지지 않는다) 쓴 이는 올린 AI의 세션으로 남긴다. 만들기는 대기에 올릴 때 보인 ID로 만든다. 승인 전에 대상이 바뀌었으면(f1이 어긋났거나 이름이 겹침) 적용하지 않고 stale로 남기고 AIS-412/409를 낸다. reject-resource-change <id> [reason=]는 이유를 남긴다. 결정이 난 변경은 최근 200건까지 남는다. AI가 승인·거절·정책 변경·직접 수정 처리를 부르면 AIS-403이다(MCP 도구도 아니고, 세션 표식이 달린 ais-cli도 거절한다).

  • 승인한 판의 지문(P2). 승인할 때 파일 바이트의 SHA-256(f1:…)과 사본을 앱 폴더(~/Library/Application Support/aisurada/approvals/<vault 해시>/의 ledger.json, copies/)에 적는다. 읽는 쪽(ResourceStore.scanServed, ResourceRefs.readApproved, ResourceResolver)은 지금 파일의 지문이 기록과 맞을 때만 그 파일을 쓴다. 파일을 직접 고쳐 어긋나면(dirty) 승인해 둔 사본을 대신 쓰고 화면 목록에는 approval: dirty가 붙는다. 기록 없이 생긴 새 파일(new)은 아예 쓰지 않고 조회도 404다. 이런 것은 list-resource-changes의 unapproved에 이전·지금 판과 함께 나온다. 사람이 save-resource로 고치면 승인한 판 위에 얹어 쓰고 직접 고친 내용은 이어받지 않는다(AI가 사소한 변경으로 직접 고친 내용을 세탁하지 못하게 한다). resolve-resource-edit <id|refs:<프로젝트>> action=approve|revert가 직접 고친 것을 받아들이거나 승인한 판으로 되돌린다(새 파일이면 휴지통으로).

  • 기준선과 깨진 기록장. 기록장이 없는 vault는 처음 읽을 때 있는 자원과 참조 목록을 모두 승인한 것으로 받아들인다(이 기능 전에 만든 자원이 못 쓰이게 되지 않게). 기록장이 깨졌으면 비어 있는 것으로 보지 않고 AIS-500으로 멈춘다(모든 파일이 다시 승인된 것이 되지 않게).

  • 명령. list-resource-changes [decided=<건수>](대기·승인 안 된 직접 수정·결정 난 것, counts.pending/counts.unapproved는 화면 배지용. list-resources도 approvals 칸에 같은 수를 낸다), get-resource-change <id>(이전 판 before, 새 판 after, 바뀐 칸 changedFields), approve-resource-change, reject-resource-change, resolve-resource-edit, get-resource-policy, set-resource-policy. 앞의 둘만 MCP 읽기 도구다. 새 명령 7개는 AisCliMain.ENGINE_COMMANDS_APPROVALS에도 있어야 앱이 ais-cli로 부를 수 있고, TasksTest가 레지스트리와 대조한다.

#태스크 (task/)

사람이 일을 티켓으로 적어 두면 나중에 러너가 집어 에이전트에게 맡기는 단위다. 외부 설명서에 없는 확장이다. 지금은 1단계(태스크 저장, 명령, 상태 전이, 화면) 까지이고 러너와 태스크 안 채팅은 아직 없다. 알림은 2단계로 따로 있다(아래 「알림」). 계획은 「태스크 시스템 구현 계획」 문서(5단계, 결정 12개)를 따른다.

  • 위치. .aisurada/tasks/ 아래다. 노트를 훑는 명령과 기존 명령이 이 영역을 보지 않는다(시험으로 확인). TSK-14.md(태스크), TSK-14/activity.jsonl(활동, 한 줄에 사건 하나, 최근 500줄까지), .trash/<id>/(지운 태스크). 실행 기록(러너가 만드는 로그)은 vault가 아니라 앱 폴더에 둔다(결정 3).
  • 키와 ID. 키 TSK-<번호>는 엔진이 매기고 만든 뒤 바뀌지 않는다. 지운 번호(휴지통에 있는 것 포함)를 다시 쓰지 않는다. ID는 tk…(노트 nd…, 스킬 sk…와 같은 형식)이고 파일 안에 있다. 접두 TSK는 엔진 오류 코드(AIS-…)와 겹치지 않게 골랐다.
  • 파일 모양. --- 머리말(YAML)과 설명 본문이다. 머리말은 스킬·에이전트 자원처럼 SnakeYAML로 읽고 쓰므로 criteria, links, refs를 들여쓴 목록으로 적는다(줄 읽개로 읽는 프로젝트·아젠다 파일과 다르다). 모르는 머리말 칸은 지우지 않고 보존한다(시험으로 고정). key, id, title, type, priority, status, repo, project, baseBranch, labels, criteria, links, refs, createdAt, editedAt, editedSession, editedAgent 순서로 쓴다. 유형은 feature·bug·chore, 우선순위는 high·medium·low다.
  • 완료 기준은 필수다. create-task는 criteria가 비면 AIS-400으로 거절한다. 일이 끝났는지 이 기준으로 확인하기 때문이다(사용자 결정, 2026-11-13). repo(owner/name)와 title도 필수다.
  • 명령 9개. MCP에는 읽기 도구 list_tasks, get_task만 열린다. 상태를 바꾸는 일은 사람과 러너만 한다.

  • 연결. 종류는 blocks(건 쪽이 받는 쪽을 막는다), relates(관련, 한 번이면 양쪽에 보인다), duplicates(건 쪽이 받는 쪽의 중복)다. 연결은 건 쪽 파일에만 적고 반대쪽(blocked-by, duplicated-by)은 읽을 때 계산한다. 두 파일이 어긋날 일이 없다. 자기 자신에게 못 걸고, 서로 막는 순환(blocks의 맞은편)은 거절한다. blocks로 막힌 태스크는 막은 태스크가 Done이 되기 전에는 Ready For Develop → In Progress로 못 간다(Failed·Cancelled는 풀지 않는다). 지운 태스크는 막지 않고, 되살리면 다시 막는다(결정 4).
  • 기록. 만들기, 상태 바뀜(from, to), 고침(바뀐 칸 이름), 연결, 댓글이 activity.jsonl에 시간순으로 남는다. 고치면 editedAt이 남고, 세션 표식이 오면 editedSession(과 Claude가 아닐 때 editedAgent)이 남는다. 완료 기준을 확인하면 확인한 시각과 쪽(human, runner)이 항목에 남고, 확인이 풀리면 기록이 지워진다.
  • 쓰기 비용. 쓰기 명령은 vault 전체 쓰기 잠금과 노트 색인 맞추기(NoteIndex.reconciled)를 거치므로 태스크를 쓸 때마다 노트 폴더를 훑는다. 호출 한 번은 노트 17개짜리 vault에서 0.1초 안팎이었다(JVM을 띄우는 시간 포함). 노트가 아주 많은 vault의 값은 재지 않았다.
  • 화면. 레일의 「태스크」(/tasks)가 보드와 목록이고(ui/TasksPage.tsx), 태스크를 열면 /task/<키>가 상세다(ui/TaskDetailPage.tsx). 만들기와 편집은 한 양식이다(ui/TaskFormModal.tsx). 엔진을 부르는 얇은 층과 순수 계산(폼 값 → 인자, 거르기, 상태별 묶기, 한 줄 풀이)은 ui/tasksClient.ts에 모았고, 화면은 엔진을 controller.callEngine으로 부른다(호스트 커맨드를 더하지 않았다). 스타일은 src/tasks.css(모든 화면 모양의 토큰을 따르고, 토큰이 없으면 대체값으로 물러난다)다.
    • 보드. 열 5개(Draft, Ready For Develop, In Progress, Waiting Answer, In Review)와 접어 둔 끝난 상태(Done, Failed, Cancelled)다. Draft 열 아래의 한 줄 입력은 Enter를 누르면 요약이 채워진 만들기 양식을 연다(완료 기준이 필수라서 바로 만들지 않는다). 거르기(검색, 저장소, 유형, 라벨, 막힌 것만)는 한 번에 받은 목록을 화면에서 거른다. 보드와 목록 가운데 고른 것은 localStorage의 aisurada.tasks.view에 둔다.
    • 상세. Jira 이슈 화면 구조다. 가운데는 설명, 완료 기준(체크하면 update-task로 저장하고 확인한 시각과 쪽이 남는다), 연결된 태스크, 연결한 자원, 활동(전체·댓글·이력)이고, 오른쪽은 세부 정보와 Ready For Develop 조건이다. 상태 메뉴는 엔진이 알려 준 transitions를 그대로 보인다. 사람이 바꿀 수 있는 곳만 나오고, 조건이 모자라거나 막혀 있으면 까닭과 함께 막혀 보인다. 화면은 이 규칙을 다시 만들지 않는다. 상태를 바꿀 때 지금 상태를 from으로 넘겨서, 그 사이에 다른 곳이 먼저 바꿨으면 엔진이 거절한다.
    • 새로 불러오기. 창이 다시 눈에 띄면 다시 읽는다(러너나 다른 창이 바꾼 것을 따라간다).
    • 시험용 preset. 두 페이지는 엔진 없이 처음 모양을 정하는 preset 속성을 받는다(앱은 주지 않는다). 서버 렌더 시험이 데이터가 든 보드와 상세를 그려 보는 데 쓴다.
  • 시험. TasksTest(만들기와 필수 값, 거절 문구, 고치기 보호와 모르는 칸 보존, 완료 기준 확인 기록, 번호, 휴지통, 상태 전이 전부, 연결과 막힘, 활동, 목록 거르기, 손으로 망가뜨린 파일, MCP 읽기 도구와 쓰기 도구 없음, 기존 명령과의 공존)와 McpServerTest의 도구 개수, 화면은 tasks-ui.test.mjs(순수 함수, 가짜 엔진으로 본 호출 인자, 서버 렌더로 본 보드·목록·상세·상태 메뉴와 레일)다. 서버 렌더에는 document가 없어서 설명(마크다운) 영역은 그리지 않는다. 데이터가 든 보드와 상세는 진짜 엔진으로 만든 임시 vault의 응답을 서버 렌더하고 Edge headless로 그려서 모양을 눈으로 확인했다(밝은 모양과 어두운 모양). 실제 앱 창(WKWebView)에서 눌러 본 확인은 없다.
  • ais-cli가 넘겨 주는 이름. 앱은 엔진을 ais-cli를 거쳐 부르는데, ais-cli는 AisCliMain의 목록(ENGINE_COMMANDS_61, 태스크 9개는 ENGINE_COMMANDS_TASKS, 승인 명령 7개는 ENGINE_COMMANDS_APPROVALS)에 든 이름만 엔진으로 넘긴다. 태스크 명령이 이 목록에 빠져 있어서 실제 앱에서는 모두 「알 수 없는 이름」(종료 코드 2)으로 거절되던 결함을 러너를 만들면서 찾아 고쳤다(5b38c33). 엔진 시험과 화면 시험은 ais-cli를 거치지 않아 잡지 못했다. 이제 TasksTest가 엔진 명령 이름이 모두 ais-cli를 통과하는지 대조한다.
  • 아직 없는 것. 코드를 고치고 PR을 올리는 러너(4단계), 태스크 안 채팅(정의 에이전트, 3b), 질문을 위 단계 에이전트가 먼저 푸는 계층(5단계). 승인 워크플로우(이슈 #53)는 러너가 코드를 고치기 전에 필요하다. 읽기 전용 러너는 아래 「러너」에 있다.

#알림 (notifications.rs)

태스크 시스템 2단계다. 알림 목록 저장, 채널 설정, macOS 배너를 호스트의 이 모듈 한 곳에서 맡는다. 외부 설명서에 없는 확장이다. 러너(3단계)도 화면도 같은 push를 거치므로 「어디로 보낼지」가 한 곳에서만 정해진다. 알림을 만드는 쪽은 러너(질문, 보고, 실패), 승인 알림(approvals.rs, 아래 「승인 워크플로」의 「알림」)과 **설정의 「시험 알림 보내기」**다.

  • 저장. 목록은 vault마다 ~/Library/Application Support/aisurada/notifications/items-<vault 경로의 SHA-256 앞 8바이트>.json에(최근 200개, 새것이 앞), 설정은 모든 vault가 같이 쓰는 …/notifications/settings.json에 둔다. vault 안에 두지 않는 까닭은 이 컴퓨터에서만 뜻이 있는 기록이고 vault의 git 이력을 부풀리지 않으려는 것이다. 파일이 없거나 망가졌으면 빈 목록, 기본 설정으로 읽는다(알림은 지워져도 큰일이 아니고 앱이 죽으면 안 된다). 쓸 때는 임시 파일에 쓰고 이름을 바꾼다.
  • 알림 하나. id, kind(question·pr·failed·done·approval·test), title(120자), body(400자), taskKey(TSK-14, 없을 수 있다), at(밀리초), read. id를 주면 같은 id가 이미 있을 때 새로 만들지 않는다(같은 일을 두 번 알리지 않으려는 것이다. 러너는 run-<실행 id>-done 같은 id를 준다).
  • 설정과 보내는 곳. 채널 스위치 2개(앱 안, macOS)와 소식 5개(질문, 리뷰할 일, 실패·막힘, Done, 스킬·에이전트 변경의 승인 대기)별 채널 스위치다. 기본은 모두 켜고 Done만 macOS를 끈다(조용히 알려도 된다). 승인 대기는 늦으면 AI의 일이 막혀서 둘 다 켠다. 옛 설정 파일에 승인 소식 칸이 없으면 켠 것으로 읽는다. 알림은 설정과 무관하게 목록(알림 센터)에는 늘 쌓인다. 설정은 토스트와 배너만 정한다: 토스트는 앱 안 채널 && 그 소식의 앱 안, 배너는 macOS 채널 && 그 소식의 macOS다. test는 채널 스위치만 따른다(route).
  • 명령 5개. notifications_list, notifications_push, notifications_mark_read, notifications_settings_get, notifications_settings_set. push는 쌓고, 설정에 따라 배너를 보내고, 화면에 사건(ais://notifications: {unread, pushed, toast})을 알린 뒤 {item, toast, banner, unread}를 돌려준다. banner는 off, sent, sent-fallback, failed: …다. 열린 vault가 없으면 push는 거절하고 list는 빈 목록을 낸다.
  • macOS 배너. tauri-plugin-notification(2.4.0. tauri 2.11.2와 맞는 가장 새 판. 2.5 이상은 tauri 2.12가 필요하다)으로 보내고, 그것이 실패하면 osascript(display notification)로 한 번 더 시도한다(이때 배너는 Script Editor 이름으로 뜬다). 배너를 누르면 앱이 앞으로 올 뿐 그 태스크로 가지는 않는다(플러그인이 macOS에서 누름 소식을 주지 않는다). 태스크로 가는 단추는 알림 센터와 토스트에 있다.
  • 집중 모드는 macOS가 처리한다(사용자 결정). 집중 모드에서 aisurada를 허용하지 않으면 macOS가 배너를 막고 알림 센터에 쌓는다. 앱이 집중 모드 상태를 읽어 토스트까지 숨기지는 않는다. 읽는 방법과 권한은 확인하지 못했다.
  • 화면. 레일 맨 위의 종 단추(안 읽은 수 배지)가 알림 센터를 연다(ui/NotificationCenter.tsx: 안 읽음·전체 탭, 모두 읽음, 질문은 「답하기」, 승인은 「승인하러 가기」, 그 밖에는 「태스크 보기」). 토스트는 메인 창 오른쪽 아래에 3개까지 뜨고 8초 뒤에 사라진다. 설정 화면의 「알림」(ui/NotificationSettings.tsx)이 채널(Telegram은 자리만), 소식별 스위치, 집중 모드 안내, 시험 알림을 보인다. 화면의 상태는 ui/notificationsStore.ts(GitHub 연결처럼 모듈 하나의 저장소)가 들고, 앱이 켜질 때 한 번 읽고 호스트의 사건을 받아 갱신한다. 노트 창은 목록만 따라가고 토스트는 안 띄운다. 스위치는 .set-switch(설정 화면 시험이 세는 이름)가 아니라 .ntf-switch이고, 모든 화면 모양에서 같게 보이도록 :root[data-skin]으로 덮었다.
  • 시험. 호스트는 notifications::tests(기본 설정, 가는 곳 계산, 설정 파일 읽기·쓰기와 모자란 칸 채우기, 알림 검사와 자르기, 쌓기·같은 id·200개 상한, 읽음, vault별 파일, AppleScript 글 탈출, JSON 이름) 10건이고, 실제 macOS 알림을 한 번 보내는 real_banner_smoke는 cargo test -- --ignored real_banner_smoke로만 돈다(이 컴퓨터에서 sent를 확인했다). 화면은 notifications-ui.test.mjs(저장소의 읽기·사건 반영·되돌림, 서버 렌더로 본 센터·토스트·설정·레일의 종)다. 알림 센터, 토스트, 설정 화면은 진짜 컴포넌트를 서버 렌더하고 Edge headless로 다섯 화면 모양(밝은 모양과 어두운 모양)에서 그려서 모양을 눈으로 확인했다.
  • 확인하지 못한 것. 실제 앱 창(WKWebView)에서 종·토스트·설정을 눌러 본 것, 번들한 앱에서 macOS 배너가 aisurada 이름과 아이콘으로 뜨는지(개발 실행은 터미널 이름으로 뜬다), 시스템 설정의 알림 허용 상태가 어떻게 보이는지. 설정의 「시험 알림 보내기」로 직접 확인할 수 있다.

#러너 (runner/)

태스크 시스템 3단계(읽기 전용)다. 외부 설명서에 없는 확장이다. Ready For Develop인 태스크를 호스트가 집어서 claude에게 저장소와 노트를 읽게만 하고, 조사 결과([보고])를 댓글로 남겨 In Review로 보내거나, 사람만 답할 수 있는 질문([질문])을 남겨 Waiting Answer로 보낸다. 코드를 고치고 PR을 올리는 일은 4단계다. 앱이 켜져 있는 동안에만 돈다.

파일맡은 일
runner/mod.rs언제 누구를 돌릴지: 15초마다 훑기, 동시 실행 수, 「지금 실행」·중지·답하기, 앱을 껐다 켰을 때 이어 가기, 앱을 닫을 때 멈추기, 화면 명령 6개

runner/protocol.rs태스크를 프롬프트로, claude의 마지막 답을 [보고]와 [질문]으로, claude를 읽기 전용으로 띄우는 인자, MCP 설정
runner/store.rs설정과 실행 기록 파일
runner/host.rs엔진(ais-cli)·claude·GitHub 저장소 사본·알림을 감싼 trait Host(시험은 가짜를 끼운다)와 읽기 전용 작업 폴더

정리끝났으면 작업 폴더를 git worktree remove로 지운다. 질문으로 멈춘 동안에는 남겨 둔다

읽기 전용을 지키는 법. claude에는 다음 인자를 준다(protocol::claude_args). 모두 실제 claude 2.1.322로 확인했다.

  • --permission-mode dontAsk --permission-prompts none: 미리 허용한 도구만 쓰고 나머지는 묻지 않고 거절한다.
  • --allowedTools "Read(<작업 폴더>/**)" mcp__aisurada: 파일 읽기와 노트 읽기만 허용한다. Read 규칙에 경로를 주지 않으면 /etc/hosts까지 읽혔다. 경로를 준 규칙 하나가 Read·Grep·Glob을 모두 그 폴더로 가둔다(/etc, ~/.ssh 거절을 확인했다). 노트는 vault 전체를 읽을 수 있다(사용자 결정 2-나: 질문하기 전에 노트에서 먼저 찾는다).
  • --disallowedTools Bash Edit Write NotebookEdit WebFetch WebSearch Agent Task: 셸, 쓰기, 웹, 하위 에이전트를 막는다.
  • --strict-mcp-config --mcp-config <JSON>: 이 호출이 준 MCP 서버만 쓴다. 서버는 ais-cli mcp(--write 없음)라서 읽기 도구만 있고, AISURADA_VAULT로 이 실행의 vault에 못 박는다. 쓰기 모드 설정이 오면 거절한다.
  • --output-format json: 결과 글, 세션 id, 토큰, 비용(total_cost_usd)을 한 번에 받는다. 모델은 설정(기본 sonnet)에서 정한다.

상태와 사람이 할 일. 상태 전이는 모두 엔진의 transition-task를 거친다(규칙은 한 곳).

#GitHub App 연결 (github.rs)

프로젝트의 GitHub 저장소(앞의 「프로젝트의 저장소와 아젠다의 projectRepo」)를 앱이 읽고 받아 오는 호스트 쪽 바탕이다. 사용자가 GitHub에서 직접 만든 GitHub App의 App ID와 개인 키(PEM) 로 설치 토큰을 받는 방식이고, 사용자 로그인(디바이스 플로우)은 쓰지 않는다. 활동은 앱(봇) 이름으로 남는다.

  • GitHub와 말하는 곳은 이 모듈뿐이다. 화면의 CSP(connect-src 'self' ipc:)는 그대로고, 엔진과 에이전트(MCP)는 토큰을 볼 수 없다. HTTP는 ureq(rustls), RS256 서명은 ring, 키체인은 security-framework다. JWT는 base64url 세 조각이라 직접 만든다(iat는 60초 앞당기고 10분 안에 만료).
  • 보관. 개인 키(PEM)는 키체인(서비스 co.kcd.aisurada.github-app, 계정 private-key)에만 둔다. App ID, 앱 이름과 slug는 ~/Library/Application Support/aisurada/github-app.json에 둔다. 설치 토큰은 설치 id별로 메모리에만 두고 만료 5분 전부터는 새로 받는다.
  • 명령(invoke). github_status(네트워크 없이 연결 여부), github_connect(appId, pemPath)(키는 파일 경로로만 받아 호스트 안에서 읽고 화면으로 돌려보내지 않는다. 키로 GET /app을 불러 App ID가 맞을 때만 저장한다), github_disconnect, github_repositories(설치된 모든 계정의 저장소. 설치 하나가 실패해도 나머지는 주고 실패는 errors에 적는다), github_clone(fullName).
  • clone. ~/Library/Application Support/aisurada/repos/<소유자>/<이름>에 받는다. 폴더에 .git이 있으면 GitHub를 부르지 않고 그대로 쓴다. 이름은 폴더로 쓰기 전에 owner/name 모양(.., 빗금, 앞의 - 거절)을 검사한다. 토큰은 명령줄(ps에 보임)이 아니라 환경변수(GIT_CONFIG_*로 http.extraheader)로만 싣고, 키체인 자격 증명 도우미가 토큰을 저장하지 못하게 credential.helper를 비운다. 실패하거나 시간(10분)이 넘으면 반쯤 받은 폴더를 지운다. 이미 있는 로컬 폴더를 쓰려면 프로젝트 저장소 항목의 path를 쓴다. 화면은 path가 있는 항목은 받지 않는다(entriesToClone).
  • 화면. 모든 호출은 githubStore.ts가 한다. 이 모듈은 연결 상태(github_status가 주는 connected, 앱 이름, cloneRoot)와 저장소별 받기 상태(cloning·done·error)를 한 곳에 두고 설정, 프로젝트 폼, 아젠다 화면이 같이 본다. 같은 저장소를 받는 중에 다시 부르면 그 결과를 같이 기다린다. 앱이 켜질 때(App.tsx) 한 번 상태를 읽어 와서, 폴더 없는 GitHub 항목의 폴더를 처음부터 풀 수 있다.
    • 설정의 「GitHub 연결」(GithubConnect.tsx). App ID를 적고 개인 키 파일(.pem)을 고르면 github_connect를 부른다. 키 내용은 화면에 오지 않고 경로만 넘어간다. 연결되면 입력을 비우고 키체인에 들어갔으니 파일을 지워도 된다고 알린다. 연결을 끊으면 키체인의 키와 앱 정보가 지워지고, 이미 받은 저장소 폴더는 그대로다.
    • 받기. 프로젝트를 저장하고 나서 폴더 없는 새 GitHub 항목을 백그라운드로 받고, 끝나면 알림으로 결과(받음, 이미 있음, 실패 이유)를 알린다. 편집기의 각 항목에는 상태 글과 「지금 받기」가 있다. 연결이 없으면 호스트를 부르지 않고 설정에서 연결하라는 글을 보인다.
    • 시험. scripts/repo-links.test.mjs(순수 함수, 가짜 호스트로 본 상태 흐름, 서버 렌더로 본 글과 단추). 실제 창에서 눌러 본 확인은 없다.
  • 시험. 기본 시험 9개는 가짜 GitHub 서버(로컬 TCP)와 로컬 git 저장소로 JWT 서명 검증, App ID 검사, 설치별 토큰 재사용과 만료 교체, 쪽 나누기 없는 목록, clone과 토큰 흔적 없음을 잰다. 개인 키는 시험 전용 일회용 키다. #[ignore] 시험 두 개는 실제 키체인(keychain_round_trip)과 실제 GitHub(real_github_smoke, 환경변수 AISURADA_REAL_APP_ID, AISURADA_REAL_PEM_FILE, AISURADA_REAL_REPO)를 쓰고 cargo test -- --ignored로만 돈다.
  • 확인한 것과 못 한 것. 실제 키체인의 저장·읽기·덮어쓰기·삭제와, 실제 GitHub의 연결·목록·clone을 확인했다. 확인한 저장소(bnjjong/aisurada)가 공개 저장소라서 비공개 저장소를 토큰으로 받는 길은 실제로 증명하지 못했다. 쓰기(push, PR)는 이 모듈에 없다. 설치 하나에 저장소가 100개를 넘는 쪽 나누기와 20쪽 상한, 호출 한도는 실제로 겪어 보지 못했다.

#앱이 연 vault (current-vault.json)

에이전트의 MCP 서버를 등록할 때 AISURADA_VAULT 경로를 박아 넣으면, 손 확인이나 옛 설정의 vault가 그대로 남아 노트가 앱과 다른 vault에 쓰인다. 그래서 등록에는 vault를 박지 않고, 앱이 연 vault를 파일에 적어 둔다.

  • 쓰는 쪽. 호스트(workspace.rs의 allow_workspace)가 워크스페이스를 열 때마다 ~/Library/Application Support/aisurada/current-vault.json에 {"vault":"<경로>","updatedAt":<ms>}를 적는다(임시 파일에 쓰고 이름을 바꾼다). 못 적어도 vault 열기는 막지 않는다. 호스트 시험은 진짜 HOME의 파일을 덮어쓰지 않게 이 쓰기를 건너뛴다(cfg!(test)).
  • 읽는 쪽. VaultPointer.resolve가 ais-cli(AisCliMain, DoctorCommand, SweepCommand)와 MCP 서버에서 호출마다 읽는다. 환경변수가 비지 않았으면 그것이 이기고, 없으면 파일이다. 둘 다 없으면 AIS-400 vault를 정하지 못했다…다. 파일이 망가졌거나 절대 경로가 아니면 없는 것으로 본다.
  • 엔진은 그대로다. 엔진(serve)은 여전히 AISURADA_VAULT가 필수이고 launchd 항목의 환경에 vault를 싣는다. 바뀐 것은 클라이언트가 vault를 정하는 길뿐이다.
  • 격리. 파일은 HOME 아래라서 가짜 HOME으로 띄운 앱(손 확인, 받아들임 점검, 번들 검증)은 자기 HOME에 적고 진짜 파일을 안 건드린다.
  • 한계. 앱을 한 번도 안 열었으면 파일이 없다. 앱을 끄고 다른 vault로 AISURADA_VAULT를 준 ais-cli를 돌려도 파일은 그대로다(앱이 마지막으로 연 vault).

#두 가지 모양

  • 단발 모드: java -jar dist/ais-engine.jar <명령> [인자...] 명령 1개를 처리하고 끝난다.
  • serve 모드: java -jar dist/ais-engine.jar serve vault 1개를 맡아 유닉스 소켓에서 요청을 받는다. 요청마다 vault를 다시 훑는다. 요청이 없으면 10분 뒤 스스로 내려간다.

#쓰기 규칙 (고칠 때 지킬 것)

  • 쓰기는 같은 폴더의 임시 파일에 쓴 뒤 원자적 이름 바꾸기로 둔다. 실패하면 다른 길로 다시 하지 않고 AIS-500으로 선다.
  • update_doc, 메타 쓰기 3개, update_sub_note는 직전에 읽은 토큰 f1이 지금 파일 바이트와 맞아야 쓴다. 안 왔거나 어긋나면 AIS-412, 종료 코드 5.
  • 편집 도장(editedBy, editedAt)은 파일 글이 실제로 달라질 때만 새로 찍는다.
  • 쓰기 명령은 일하기 전에 vault를 훑고, 노트로 못 읽는 파일이 있으면 아무것도 안 쓰고 종료 코드 1로 선다.
  • serve는 시작·종료·유휴·15분 경과·작성자 전환 때 vault를 자동 커밋한다. .git이 있는 main 브랜치에서만 돈다. 단발 모드는 자동 커밋하지 않는다.

#명령을 새로 넣는 길

  1. src/aisurada/cmd/에 실행기를 만든다. 쓰기 공통 부품은 write/에 있다.
  2. CommandRegistry의 COMMAND_NAMES(도구 표면도 있으면 TOOL_NAMES), 쓰기면 WRITE_COMMANDS, 그리고 USAGE_LINES에 이름과 사용법을 넣는다.
  3. 시험을 test/aisurada/에 두고 test.sh에 한 줄 넣는다(§8).
  4. 설명서 장이 있으면 그 장의 바이트 예시와 맞는지 대조하고, 받아들임 묶음에 케이스를 더할 수 있으면 더한다(§8).

#MCP 서버 (ais-cli mcp)

Claude 같은 MCP 클라이언트가 노트를 도구로 쓰게 하는 모드다. 표준 입출력으로 한 줄에 JSON-RPC 메시지 하나씩 주고받고(initialize, ping, tools/list, tools/call), 입력이 닫히면 끝난다. 프로토콜은 src/aisurada/cli/McpServer.java, 도구 정의는 McpTools.java에 있다. 이것은 설명서 밖의 확장이다. 외부 설명서에는 MCP가 없고, 예전 Node MCP 서버는 C119에서 지웠다.

연결하는 법, 도구 28개의 인자, 안전장치, 응답과 오류 예시는 mcp-guide.md에 따로 정리했다. 이 절은 만드는 쪽 이야기만 적는다.

  • 도구. 이름은 엔진 도구 38개와 같다. 기본은 읽기 19개만 내놓고 --write를 주면 37개를 내놓는다. purge_doc(영구 삭제)는 어느 쪽에도 없다. 모델이 되돌릴 수 없는 삭제를 하지 못하게 하려는 것이다. 읽기와 쓰기의 구분은 CommandRegistry.WRITE_COMMANDS에서 나오므로 두 곳이 어긋나지 않는다.
  • 호출 길. 도구 호출은 단발 ais-cli와 같은 길(runEnginePipeline: 소켓 찾기, 엔진 띄우기, 요청 왕복)을 JVM 하나에서 되풀이한다. 이 길은 곳곳에서 System.exit을 부르는데, AisCliMain의 종료 호출은 모두 exit() 하나를 거친다. mcp 모드에서만 exit()이 프로세스를 끝내는 대신 CliExit을 던지고, 그 호출만 isError로 답한다. 이 길이 표준 출력·오류에 쓰는 글은 호출마다 모아서 돌려주므로 프로토콜 출력에 섞이지 않는다.
  • vault. 도구를 부를 때마다 정한다. AISURADA_VAULT가 있으면 그것, 없으면 앱이 지금 연 vault(아래 「앱이 연 vault」)다. 서버 하나는 한 번에 vault 하나를 맡지만 호출마다 바뀔 수 있다.
  • 스키마를 고칠 때. McpTools의 입력 스키마 키는 ArgsParser가 받는 키와 같아야 한다. McpServerTest가 엔진의 「모르는 키다 … 쓸 수 있는 것은 […] 뿐이다」 문구와 도구 38개를 모두 대조하고, 필수 키도 하나씩 빼 보며 잰다. 도구의 인자를 바꾸면 McpTools도 고친다. 안 고치면 이 시험이 선다.
  • Claude에 연결. ais-cli claude-mcp status|add [--write]|remove|config(ClaudeMcpCommand)가 Claude Code에 서버를 등록한다. Codex와 Antigravity·Gemini CLI는 codex-mcp, gemini-mcp(AgentMcpCommand)가 같은 방식으로 한다. 셋 다 등록에 vault를 박지 않는다(McpRegistration). CLI마다 -- 자리가 달라서(codex와 agy는 이름 바로 뒤, gemini는 java 경로 뒤) 인자 모양은 AgentMcpCommandTest가 가짜 CLI로 못 박고, 진짜 CLI로는 임시 HOME에서 확인했다. Claude의 설정 파일을 직접 고치지 않고 claude mcp add-json --scope user만 부른다. 등록하는 Java와 jar는 이 명령을 돌린 것이라, 앱에서 부르면 앱에 든 것이 등록된다. config는 등록하지 않고 Claude Desktop 설정에 붙여 넣을 mcpServers 조각만 출력한다. 설정 화면의 「Claude 연결」(src/plugs/claude/connect.tsx)은 sidecar_call로 이 명령을 부르기만 하므로 호스트 커맨드를 더하지 않았다(4부 9개 그대로). 4부를 끈 판에는 이 화면이 없다(plugs/empty/connect.tsx). 연결은 지금 연 워크스페이스 하나에 묶이고, 다른 워크스페이스에서 다시 연결하면 바뀐다.

시험은 bash test.sh에 들어 있다. McpServerTest는 스키마 대조, 노출 규칙, 가짜 호출기로 프로토콜, 진짜 엔진과 진짜 mcp 프로세스의 왕복(읽기·쓰기·낡은 f1 거절·휴지통·영구 삭제 거절·vault 없는 환경에서도 서버가 사는지)을 잰다. ClaudeMcpCommandTest는 등록 상태를 파일에 두는 가짜 claude로 status·add·remove·config를 잰다.

#6. ais-cli와 launchd — 건드리기 전에

ais-cli는 떠 있는 엔진이 없으면 ~/Library/LaunchAgents/co.kcd.aisurada.sidecar.<키>.plist를 쓰고 launchctl을 부른다. 엔진이 동시 상한(3개)을 넘으면 가장 오래 조용한 엔진을 내리고, 하루 한 번 24시간 넘게 조용한 엔진도 내린다. 이 저장소의 시험은 모두 임시 HOME과 가짜 launchctl로 돌아서 진짜 launchd는 쓴 적이 없다.

안전하게 돌리는 법:

  • 엔진을 먼저 직접 띄운다(AISURADA_SIDECAR_SOCKET을 짧은 경로로 주고 serve). 그러면 ais-cli가 launchd를 부르지 않고 그 소켓에 붙는다.
  • java -Duser.home=<격리 HOME>으로 띄운다. 안 그러면 4부 명령이 진짜 ~/.claude/projects를 읽는다. ($HOME 환경 변수는 JVM의 user.home을 바꾸지 못한다.)
  • 이미 있는 등록을 덮어쓰고 싶지 않으면 AISURADA_SIDECAR_KEEP_REGISTRATION=1을 준다. 엔진이 없을 때 plist가 있고 그 jar가 남아 있으면 plist를 다시 쓰지 않고 그대로 띄운다. 개발 실행과 빌드 폴더 번들은 호스트가 알아서 켠다(§7).
  • ais-cli doctor로 키, 레이블, 소켓, plist를 진단한다. 등록한 엔진을 지우려면 launchctl bootout gui/$(id -u)/<레이블> 뒤에 그 plist를 지운다.

앱을 격리해서 띄우는 전체 순서는 beta-hand-check.md의 §1에 있다.

개발 실행은 엔진 jar를 자동으로 넘기지 않는다. 번들 판은 자원 폴더의 ais-sidecar.jar를 ais-cli에 넘기지만, tauri dev와 target/…/bundle 아래 번들은 낡은 사본을 쓰지 않으려고 넘기지 않는다(sidecar.rs의 execute). 대신 jar를 직접 지정하지 않은 개발 실행과 빌드 폴더 번들은 AISURADA_SIDECAR_KEEP_REGISTRATION=1을 ais-cli에 넘긴다(호스트 execute, 앱 스크립트 ais-cli). 엔진이 없을 때 이 스위치가 켜져 있고 ~/Library/LaunchAgents/…plist가 이미 있으며 그 plist의 jar도 남아 있으면, ais-cli는 plist를 다시 쓰지 않고 있는 등록 그대로 엔진을 띄운다(PlistGenerator.keepsExistingRegistration). 그래서 빌드 폴더의 앱을 진짜 vault로 띄워도 정식 앱이 해 둔 엔진 등록이 설치본 jar로 바뀌지 않는다. 이런 앱은 이미 등록된 엔진을 쓰므로 그 엔진이 앱보다 낡았으면 화면이 「모르는 명령이다」를 띄울 수 있다(§12). 등록이 아예 없으면(처음 쓰는 HOME 등) 예전처럼 설치본 jar로 등록하고, 설치본도 없으면 AIS-400 AISURADA_SIDECAR_JAR 가 없고 …로 선다. 이 규칙은 PlistGeneratorTest(스위치 판정), sidecar.rs의 sidecar_export_obeys_dev_build_bundle_and_explicit_override, ais-cli-script.test.mjs가 잰다. 진짜 launchd와 앱 창에서는 확인하지 못했다. 앱으로 워크스페이스를 만들거나 열어 보려면 앱을 띄우는 터미널에서 먼저 이렇게 한다.

bash
unset AISURADA_VAULT AISURADA_SIDECAR_SOCKET              # §3 예시의 값이 남아 있으면 지운다
export AISURADA_SIDECAR_JAR="$PWD/dist/ais-sidecar.jar"   # 반드시 절대 경로다(plist에 그대로 실린다)

대신 한 번 java -jar dist/ais-cli.jar install --cli dist/ais-cli.jar --sidecar dist/ais-sidecar.jar로 ~/Library/Application Support/aisurada/bin/에 깔아도 된다. 깐 사본은 빌드할 때마다 다시 깔아야 한다.

이 길은 진짜 launchd를 쓴다. vault마다 ~/Library/LaunchAgents/co.kcd.aisurada.sidecar.<키>.plist가 생기고 launchctl에 올라간다. 이 저장소의 시험은 모두 가짜 launchctl이라 이 길을 자동으로 잰 적이 없다. 끝나면 java -jar dist/ais-cli.jar doctor로 레이블과 plist를 보고, launchctl bootout gui/$(id -u)/<레이블> 뒤에 그 plist를 지운다. launchd를 건드리지 않고 앱을 보려면 beta-hand-check.md의 격리 실행법을 쓴다. 이때는 엔진 하나가 vault 하나만 맡으므로 그 vault만 열 수 있다.

#앱에 든 ais-cli

native-host/src-tauri/resources/ais-cli(셸 스크립트)가 번들의 Contents/Resources/bin/ais-cli로 들어간다(tauri.conf.json의 resources).

  • 같은 앱의 Java(Resources/runtime/bin/java)로 같은 앱의 ais-cli.jar를 돈다. 번들 Java는 릴리스 설정(tauri.release.conf.json)으로 지은 번들에만 있고, 없으면 PATH의 java를 쓴다. 심볼릭 링크로 불러도 앱 안의 자리를 찾는다. 엔진 jar는 AISURADA_SIDECAR_JAR로 앱의 ais-sidecar.jar를 넘긴다. 단 target/…/bundle 아래의 개발용 빌드는 낡은 사본을 쓰지 않으려고 넘기지 않고, 대신 이미 있는 엔진 등록을 덮어쓰지 않게 AISURADA_SIDECAR_KEEP_REGISTRATION=1을 켠다(호스트 sidecar.rs의 규칙과 같다. 사용자가 jar를 정해 두었으면 그 jar를 따르고 스위치는 켜지 않는다).
  • 셸 내장 기능만 쓴다. Finder나 launchd가 띄운 환경은 PATH가 비어 있다. 실제 번들 검증에서 dirname 때문에 서던 것을 고쳤다. 외부 명령은 절대 경로로 부르는 readlink 하나뿐이다.
  • 호스트는 앱이 뜰 때 이 폴더를 ask.rs의 set_tools_dir로 알려 두고, claude -p를 띄울 때 PATH 맨 앞에 얹는다. 그래서 앱 안에서 묻는 Claude는 사용자가 래퍼를 만들거나 Java를 깔지 않아도 ais-cli를 부를 수 있다. 앱 안 터미널(pty_start_session)의 PATH는 바꾸지 않았다. 사용자의 로그인 셸 환경을 따른다.
  • 터미널에서 쓰려면 연동 가이드 2단계의 링크 한 줄이면 된다. 예전 가이드로 만든 ~/.local/bin/ais-cli(시스템 java)가 있어도 앱이 띄우는 Claude에게는 번들 것이 먼저 잡힌다.
  • 시험은 스크립트 test:cli-script(가짜 앱 폴더에서 진짜 셸 스크립트를 돌린다. PATH가 비었을 때, 링크로 불렀을 때, 개발용 빌드일 때 포함), PATH 얹기 ask.rs의 bundled_tools_dir_comes_first_only_when_it_exists, 실제 번들 scripts/verify-release.mjs(PATH 없이 스크립트로 노트를 읽고, MCP 등록 명령이 번들 Java를 가리키는지)다.
  • 못 한 것. Java가 없는 Mac에서는 돌려 보지 않았다. 이 기계에는 JDK가 있다. 스크립트가 번들 Java를 절대 경로로 고르는 것(sh -x)과 PATH를 비운 채 도는 것까지만 확인했다.

#화면 모양 (skin)

설정 → 「화면 모양」에서 물성(기본값), 격자, 유리, 모던, 기본(이전 모양) 중에서 고른다. 밝게·어둡게(data-theme, 레일의 ◐)와는 따로 고르므로 모든 모양에 밝게와 어둡게가 있다.

무엇어디
저장aisurada.prefs.v1의 state.skin('tactile'·'grid'·'glass'·'modern'·'classic'). 16장의 설정 21개에 들어가지 않는 확장 값이라, 고르기 전에는 readPreferences 결과에 나타나지 않는다. readSkin이 읽고, 없거나 모르는 값(없앤 'page' 포함)이면 물성이다
적용<html data-skin>. main.tsx가 첫 그리기 전에 걸고, App.tsx가 state.skin을 따라간다. 다른 창은 storage 이벤트와 포커스에서 refreshTheme으로 따라온다. 노트 창은 설정을 쓰지 않는다
기본 모양src/styles.css. 설정의 모양 고르기 카드(.set-skin*, .skin-preview)도 여기에 둔다. 카드의 미리보기 그림은 지금 켠 모양과 상관없이 각자의 모양을 그린다
물성src/skin-tactile.css. 눌리는 것은 떠 있고 쓰는 것은 파인 둥근 모양. 모든 규칙이 :root[data-skin="tactile"] 아래에 있어서 다른 모양에는 영향이 없다. 파일 맨 위에 다섯 규칙(깊이가 역할, 반경은 높이의 절반, 선 대신 면, 위에서 한 방향의 빛, 회색에도 색)과 토큰이 있다
격자src/skin-grid.css. 반경 2px, 그림자 없음, 네이비 먹선 상자. 켜짐·선택은 네이비로 채우고 빨강은 포커스·현재 위치·눌림에만 쓴다. 「모든 요소 반경 2px·그림자 없음」을 한 줄(:root[data-skin="grid"] *)로 덮고 원이 필요한 몇 곳만 되돌린다
유리src/skin-glass.css. 반투명 흰 면(--surface)에 흐림(backdrop-filter)을 건 패널, 배경에는 블루·시안·레드의 빛번짐(:root의 radial-gradient). 컨트롤 반경 12px, 패널 24px, 강조는 블루 유리구슬. 글자 색은 불투명하게 둬서 대비를 지킨다. --surface가 반투명이라 이 값을 불투명한 바탕으로 쓰는 새 요소는 --glass-solid를 쓴다
모던src/skin-modern.css. 1px 옅은 선, 곡률 8px(떠 있는 것은 12~14px), 검정에 가까운 네이비와 회색, 블루 하나는 포커스·선택에만. 그림자는 평소 1px과 떠 있는 것 두 가지뿐이고 탭은 아래 줄로 현재 위치를 말한다

지킬 것.

  • 전역 규칙(button, input …)은 :where()로 특이도를 낮춰 썼다. 그래야 styles.css의 개별 클래스(border: 0, background: transparent)를 덮어쓰지 않는다.
  • styles.css에서 background: transparent나 border: 0으로 맨살로 만든 버튼을 새로 더하면 네 스킨 파일(skin-tactile.css·skin-grid.css·skin-glass.css·skin-modern.css)의 「맨살 버튼」 선택자 목록에 모두 넣는다. 빠뜨리면 그 스킨에서 그 버튼만 상자나 알약, 유리 조각으로 보인다.
  • 물성은 토큰(--bg, --soft, --surface, --sunken, --accent …)을 바꿔서 기본 모양의 규칙까지 같이 물든다. 기본 모양의 색을 #rrggbb로 박은 곳은 물성에서도 그 색이다.
  • 설정 화면 인수 시험이 .set-switch를 3개로 센다. 모양 고르기 카드는 그래서 다른 클래스(.set-skin-option)를 쓴다.
  • 격자는 모든 요소의 반경과 그림자를 한 줄로 덮는다. 설정 카드의 미리보기 그림은 그 규칙에 흔들리지 않도록 styles.css에서 반경·그림자에만 !important를 쓴다.
  • 유리는 backdrop-filter를 큰 패널에만 건다. 버튼마다 걸면 느려진다. 맨살 버튼과 일반 버튼은 반투명 배경만 쓴다.

새 모양을 더하려면 types.ts의 Skin, storage.ts의 SKINS, Settings.tsx의 SKIN_OPTIONS, src/skin-<이름>.css와 main.tsx의 import, 미리보기 그림 규칙(styles.css)을 함께 고친다. 시험은 scripts/chapters14-17.test.mjs의 「화면 모양」과 scripts/views-checks.js의 설정 점검(다섯 모양을 차례로 눌러 data-skin과 저장 값을 잰다)이다.

#글꼴과 화면 크기 (typography)

설정 → 「글꼴과 크기」에서 화면 크기(90·100·110·125·150·175%), 앱 글꼴, 터미널 글꼴을 고른다. 글꼴은 설치된 글꼴 이름 하나나 쉼표로 이은 CSS 글꼴 목록이고, 비우면(「기본값」) 기본 글꼴이다. 화면 크기는 ⌘ + / ⌘ - / ⌘ 0(Ctrl도 됨)으로도 바꾼다.

무엇어디
저장aisurada.prefs.v1의 state.uiScale(위 여섯 값만), state.uiFont, state.terminalFont. 화면 모양(skin)처럼 16장의 설정 21개 밖 확장 값이라 고르기 전에는 readPreferences 결과에 나타나지 않는다. workspace/typography.ts의 readTypography가 읽고, 이상한 값은 항목별로 기본이다. 글꼴 글은 ; { } < > \와 주석 표시, 200자 초과를 받지 않는다
앱 글꼴styles.css의 --font-ui-base(기본 목록)와 --font-ui(:root의 font-family가 읽는다). 고르면 <html>에 --font-ui: "고른 글꼴", var(--font-ui-base)를 덧씌우고, 비우면 지운다(applyTypographyVars). 쉼표·따옴표가 없는 이름은 한 글꼴로 보고 따옴표로 감싸고(Source Han 2처럼 공백·숫자가 있어도 되게), 끝에 기본 목록이 붙어서 고른 글꼴에 없는 글자(한글 등)는 기본 글꼴이 채운다. main.tsx가 첫 그리기 전에 걸고 App.tsx가 상태를 따라간다
터미널 글꼴--font-terminal(기본은 var(--font-mono)). TerminalHost.tsx가 이 변수를 읽는다(전에는 --font-mono). 바꾸면 ais:typography window 이벤트로 열려 있는 터미널이 options.fontFamily를 바꾸고 칸 수를 다시 잰다. 터미널이 쥔 글꼴은 .term-screen의 data-font-family에도 적는다(WebGL로 그리면 글꼴이 DOM에 안 드러나서 실제 창 점검이 이것을 읽는다). 노트의 코드 블록은 이 설정을 따르지 않는다(--font-mono와 고정 목록 그대로)
화면 크기웹뷰 확대다. services.setZoom → Tauri getCurrentWebview().setZoom(배율 / 100)(macOS는 WKWebView의 pageZoom). core:webview:allow-set-webview-zoom 권한이 capabilities/main.json과 note.json에 있다(contracts.test.mjs가 두 목록이 같은지 잰다). CSS zoom은 쓰지 않았다. 앱이 아닌 환경(브라우저, 시험)에서는 setZoom이 없어 글꼴만 바뀐다
단축키interaction/shortcuts.ts의 zoomShortcutFor(Cmd/Ctrl과 +·-·0, 키 이름과 물리 키 이름을 모두 본다). controller.handleKey가 탭 단축키보다 먼저, 어느 화면에서나 듣는다. 한 단계는 stepScale(맨 끝에서 멈춤, 0은 100%)
창마다메인 창은 바꾼 값을 저장소에 쓴다. 노트 창은 설정을 공유 저장소에 쓰지 않는 규칙(15.14) 때문에 단축키로 바꾼 배율이 그 창에만 남고(controller의 localScale), 글꼴은 저장소(storage 이벤트, 포커스)를 따라간다. 설정 화면은 메인 창에만 있다
화면ui/TypographySettings.tsx. 글꼴 입력은 500ms 멈췄을 때, 칸을 떠날 때, Enter에서 저장한다(글자마다 저장하면 입력 중간의 이름이 그대로 적용된다). 쓸 수 없는 글이면 오류 문구를 보이고 직전 값을 지킨다. 배율 단추는 일반 button에 aria-pressed라 스킨의 단추 모양을 따르고, 고른 단추의 색만 :root:root로 덮는다. 설정 인수 시험이 .set-switch를 3개로 세므로 그 클래스는 쓰지 않는다

#좌측 메뉴(레일)의 두 탭: 노트와 에이전트

레일(Rail.tsx) 맨 위에 탭 둘이 있다. 노트 탭은 노트 일(전체 노트, 캘린더, 즐겨찾기, 연결, 템플릿, 휴지통)과 프로젝트·아젠다 목록이고, 에이전트 탭은 에이전트 일(태스크, 스킬·에이전트, 러너 한 줄, 프로젝트 자원)이다. 연동 가이드는 두 탭이 같이 쓰므로 탭 메뉴가 아니라 아래 줄의 「?」 단추다. 시안은 디자인 캔버스의 「02 물성 · 사이드바 탭 (노트 / 에이전트)」 보드다.

  • 어느 탭이 켜질지는 화면 주소가 정한다(navigation/railTabs.ts의 railTabOf). 노트 탭은 /notes /agenda/… /calendar /favorites /connections /templates /trash /review, 에이전트 탭은 /tasks /task/… /resources /project/…다. 연동 가이드·세션·터미널처럼 어느 쪽도 아닌 화면에서는 직전에 켜 둔 탭을 그대로 둔다. 그래서 알림의 「승인하러 가기」처럼 주소로 들어와도 맞는 탭이 켜지고 탭과 본문이 어긋나지 않는다.
  • 탭을 누르면 그 탭에서 마지막으로 보던 화면으로 간다. 처음 누르면 각 탭의 첫 화면(/notes, /tasks)이다. 이미 그 탭의 화면이면 아무것도 하지 않는다. 기억은 모듈 변수에 두므로 앱을 켜 둔 동안만 가고 저장하지 않는다(rememberRailTab, railTabTarget).
  • 에이전트 탭 이름 옆 배지는 「내 차례」의 합이다: 러너가 답을 기다리는 태스크 수(runnerStore의 waiting)와 승인이 필요한 변경 수(approvalsStore)를 더한다. 노트 탭을 보고 있어도 보인다. 태스크 메뉴에는 답 대기 수, 스킬·에이전트 메뉴에는 승인 수가 따로 붙는다.
  • 러너 한 줄(「러너 · 쉬는 중」 따위)은 에이전트 탭에만 있고 누르면 태스크 화면으로 간다. 러너가 없는 빌드(supported false)에서는 숨긴다. 색 단계는 태스크 화면의 러너 막대와 같은 runnerTone을 쓴다.
  • 프로젝트 자원 줄은 프로젝트마다 하나이고 누르면 프로젝트 페이지(/project/<slug>)다. 예전에 노트 탭 프로젝트 머리에 있던 「프로젝트 페이지」 단추는 여기로 옮겼다. 줄은 아젠다 줄(.rail-agenda)을 그대로 써서 모든 모양(skin)에서 같은 활성 표시를 갖는다. 프로젝트별 자원 개수는 아직 안 보인다(시안에는 있다).
  • 탭 줄의 색은 레일 바탕(스킨마다 밤하늘 위에 --ink가 다시 정의된다)에서 읽히도록 --ink를 섞어 만들었다(color-mix). 그래서 시안의 물성 알약과 모양이 조금 다르다. 선택자를 .workspace-rail .rail-tabs …부터 걸어 스킨의 일반 버튼 규칙보다 앞서게 했다.
  • 시험은 scripts/rail-tabs.test.mjs 7건(주소→탭 표, 기억과 누름 규칙, 노트·에이전트 탭의 메뉴와 줄, 연동 가이드, 배지 합)이고 tasks-ui, resources-ui가 새 위치를 본다. views-checks.js의 메뉴 순서는 노트 탭 여섯 개로 고쳤지만 실제 창에서 돌려 보지는 않았다. 실제 앱 창에서 탭을 눌러 본 확인은 없다.

#후속 노트 탭

메인 창에서는 후속 노트(노트 폴더 아래 sub/에 든 하위 노트)가 노트 위에 뜨는 창이 아니라 탭 바의 탭 하나로 열린다. 상위 노트와 후속 노트를 탭으로 오가며 볼 수 있고, 앱을 껐다 켜도 남는다. 탭 바가 없는 노트 창(새 창으로 옮긴 노트)만 예전의 후속 노트 창(interaction/Overlays.tsx의 SubNotePages)을 그대로 쓴다.

  • 주소와 탭 식별자. 후속 노트는 (최상위 노트 id, 후속 id 사슬)로만 정해지므로 주소가 사슬 전체다: /sub/<최상위 노트 id>/<후속 id>/<그 아래 후속 id>…(routes.ts의 subAddress, parseRoute의 kind: 'sub'). 탭 식별자는 sub:<최상위 노트 id>/<후속 id>/…(subTabId, parseSubTab)다. isNoteTab은 최상위 노트 탭만 가리키고(후속 탭은 아니다), 저장할 탭은 isStoredTab, 탭이 기대는 최상위 노트는 tabRootId가 돌려준다.
  • 여는 길은 controller.openSubNotes(root, ids) 하나다. 후속 노트 목록의 행, 노트 안의 후속 노트 카드(#sub:), 「추가」, ⌘K 미리보기 안의 카드, 링크의 사슬(receiveURLs로 온 .md 파일 링크), 노트 창이 메인 창에 보낸 show_in_main의 sub가 모두 여기를 지난다. 메인 창에서는 /sub/…로 이동하는 것이 전부이고, 노트 창에서만 state.subNotes로 창을 연다. 최상위 노트가 새 창으로 옮겨져 있으면 탭을 열지 않고 그 창을 앞으로 가져온다.
  • 탭 모델(navigation/tabs.ts). 후속 탭은 같은 최상위 노트의 탭 무리(상위 노트 탭과 이미 열린 후속 탭들) 바로 뒤에 놓인다(withTab). 무리가 없으면 상위 노트 탭을 앞에 함께 연다. 최상위 노트가 볼트에서 사라지면 후속 탭도 함께 걸러진다(available). 저장 형식은 그대로 openIds 문자열 배열(버전 1)이고 후속 탭 식별자가 섞여 들어간다. 사슬 중간의 노트가 지워졌어도 탭은 남고, 열면 「이 후속 노트를 찾을 수 없어요」와 「탭 닫기」가 보인다.
  • 화면. navigation/SubNoteScreen.tsx가 holdSubChain(navigation/subNotes.ts)으로 최상위 노트부터 사슬의 목록을 한 단계씩 읽은 뒤 일반 노트 화면(NoteScreen)을 parent·root와 함께 그린다. 그래서 본문 폭 조절, 세션 레일, 이력, 삭제가 최상위 노트와 같다. 후속 노트 화면의 정보줄 아래에는 「↰ 상위 노트 제목」 칩이 조상마다 하나씩 있어 누르면 그 탭으로 간다(옛 창의 이동 경로 자리). 레일(왼쪽 메뉴)은 노트 화면처럼 숨는다.
  • 탭 이름. 탭 바(TabBar.tsx)는 후속 탭에 「↳」 표시를 붙이고 제목만 보인다. 마우스를 올리면 「최상위 제목 › … › 이 제목」이 나온다. 이름을 알려면 목록을 읽어야 하므로 탭 바가 열린 후속 탭의 사슬을 미리 읽어 둔다(앱을 다시 켠 직후에도 이름이 보인다). 아직 못 읽었으면 「↳ 후속 노트」다.
  • 닫기와 지우기. 탭의 ×와 ⌘W는 일반 탭과 같다. 후속 노트를 지우면(controller.popSubNote) 그 탭과 그 아래 후속 탭들이 닫히고 상위 탭으로 돌아간다. 상위 탭이 닫혀 있으면 이웃 탭이다. Esc는 후속 탭을 닫지 않는다(노트 창의 후속 노트 창만 Esc로 한 단계씩 닫힌다). 노트를 새 창으로 옮기면 그 노트의 후속 탭도 메인 창에서 닫힌다.
  • 시험. interaction.test.mjs(열기·자리·저장·지우기·새 창 이동·링크 사슬, 노트 창의 후속 노트 창), navigation.test.mjs(주소 왕복, 탭 모델의 저장·걸러냄·자리), sub-tabs-ui.test.mjs(탭 이름·↳·설명 글, 최상위 노트가 없는 탭). 실제 창 점검 interaction-checks.js, views-checks.js, editor-checks.js, part4-checks.js의 후속 노트 사례를 창 대신 탭을 보도록 고쳤지만 실제 앱 창(WKWebView)에서 돌려 보지는 않았다.

#코드 블록 문법 색 (editor/codeSyntax.ts)

코드 블록의 언어별 색을 입히는 곳은 한 모듈이다. 문법을 토큰(키워드, 문자열, 주석 같은 조각)으로 나누는 일은 Prism이 하고, 편집기와 읽기 화면이 같은 모듈과 같은 CSS를 쓴다.

화면칠하는 방법
편집기(Editor.tsx의 CodeSyntaxPlugin)Lexical의 registerCodeHighlighting이 코드 노드를 입력할 때마다 다시 나눠 토큰 노드로 바꾼다. 색은 화면에만 있고 저장되는 Markdown은 그대로다
읽기 화면(ReadMarkdown.tsx), 외부 문서, 코멘트정화가 끝난 DOM의 pre > code.language-<이름>을 highlightCodeBlocks가 칠한다
Claude 응답 글(plugs/claude/modelProse.tsx)같은 highlightCodeBlocks를 쓴다
  • 문법. Lexical에 든 Prism에는 Kotlin, Bash, YAML, JSON, Groovy, Dockerfile, properties가 없어서 편집기의 언어 선택 목록(tools.tsx의 languages)에 있어도 색이 없었다. codeSyntax.ts가 이들과 TOML, JSX, TSX를 더 불러오고, 펜스에 흔히 쓰는 이름(gradle, zsh, jsonc, c++)을 별칭으로 잇는다. prismjs는 이 때문에 직접 의존성이다(1.30.0, Lexical이 쓰는 버전과 같다). 문법을 더하면 codeSyntax.ts에 prism-<이름>.js를 불러오되, 기대는 문법(Kotlin·Groovy는 clike, JSX는 markup·javascript, TSX는 JSX·typescript)을 먼저 불러온다.
  • 언어를 적지 않은 블록은 칠하지 않는다. Lexical은 기본값으로 이런 블록의 언어를 javascript로 바꾸는데, 그러면 저장할 때 펜스가 ```에서 ```javascript로 바뀐다. 그래서 토크나이저의 defaultLanguage를 null로 둔다. 모르는 언어(mermaid 포함)도 그대로 둔다.
  • 색은 CSS 클래스 token <종류>로 정한다. Lexical의 theme.codeHighlight가 토큰 종류를 그대로 클래스로 바꾸고, Prism이 만드는 HTML도 같은 클래스를 단다. 색 값은 styles.css의 --tok-* 변수이고 밝기마다(라이트, OS 다크, data-theme="dark") 값만 다르다. light-dark()는 macOS 13의 WebKit에 없어서 쓰지 않는다.
  • 별칭 문제. Prism은 토큰에 별칭을 달아(assign-left는 variable) HTML에 둘 다 클래스로 쓰지만, Lexical은 종류 이름 하나만 쓴다. 별칭으로 색이 정해지는 이름(function-name, scalar, decorator 등)도 styles.css에 규칙이 있어야 두 화면이 같게 칠해진다. 새 문법을 더했을 때 빠뜨리지 않도록 code-syntax.test.mjs가 문법에서 이름을 읽어 CSS와 맞대어 본다.
  • 함께 켜지는 것. registerCodeHighlighting은 색 입히기와 함께 Lexical의 코드 안 편집 기능(들여쓰기, 줄 이동 따위)도 등록한다. Tab은 tools.tsx의 기존 처리(우선순위 높음)가 먼저 받아 \t을 넣는다. 다른 키 동작은 앱 창에서 손으로 확인하지 않았다.
  • 한계. 펜스 이름이 대문자(Kotlin)이면 읽기 화면은 칠하는데 편집기는 칠하지 않는다(Lexical이 이름을 그대로 비교한다). 문자열 안의 ${…}처럼 토큰 안에 든 토큰은 읽기 화면에서는 바깥 색을 물려받고 편집기에서는 안쪽 토큰 색을 쓴다. Swift의 directive처럼 별칭이 둘로 갈리는 몇몇 토큰은 두 화면의 색이 다를 수 있다.
  • 시험. scripts/code-syntax.test.mjs(test-native.sh가 부른다)가 문법 쪽(Kotlin 토큰, 선택 목록의 모든 언어에 문법이 있는지, 모르는 이름과 이스케이프, 별칭 규칙)과 헤드리스 편집기(색이 입혀지는지, 입력해도 색이 따라가는지, 색 때문에 저장되는 Markdown이 달라지지 않는지, 언어 없는 블록이 그대로인지)를 잰다. 실제 번들 조건(Vite, safari15)에서 편집기와 읽기 화면을 Edge headless로 그려 라이트·다크 모두 색이 나오는 것을 확인했다. 앱 창(WKWebView)과 Claude 응답 글에서는 확인하지 않았다.

try (ChapterTestSupport t = new ChapterTestSupport("chapter99")) {

#13. 지금 상태와 한계

  • 엔진 시험, 화면·호스트 시험, 34장 받아들임, 4부를 뺀 실제 창 점검 8종은 통과한다. 수치는 README.md와 각 완료 기록에 있다.
  • 사람이 앱을 직접 조작해 본 확인은 아직 없다. 점검표는 §9의 문서에 있다.
  • MCP 서버(ais-cli mcp)는 진짜 엔진과 진짜 프로세스로 표준 입출력 왕복을 잰다. 진짜 Claude Code 2.1.318로는 격리 HOME에서 등록, 쓰기 모드로 바꿔 끼우기, 연결 확인(✔ Connected), 끊기까지 확인했다. 못 한 것: 모델이 실제로 도구를 부르는 흐름, Claude Desktop, MCP 규격 공식 문서와의 대조(받는 개정은 2024-11-05, 2025-03-26, 2025-06-18이고 규격은 다른 자료로 짰다).
  • 설정 화면의 「Claude 연결」 단추는 4부 실제 창 점검에서 가짜 claude로 눌러 보았다. 진짜 claude로 화면의 단추를 눌러 본 적은 없다(손 확인 4-4).
  • 설정의 「글꼴과 크기」는 브라우저(개발 서버, 샘플 vault)에서 다섯 모양 모두 눈으로 보았다. 실제 WKWebView 점검(test:views:acceptance 28건, test:navigation:acceptance 13건, 둘 다 4부를 뺀 판)에서 웹뷰 확대가 되는 것(innerWidth가 배율만큼 변함), ⌘ 단축키, 앱 글꼴 적용·오류·기본값, 열려 있는 터미널의 글꼴 변경, 150% 확대 중 터미널 화면이 칸 안에 드는 것까지 확인했다. 못 본 것: 터미널과 편집기가 확대된 채로 눈에 어떻게 보이는지(글자가 또렷한지, 편집기 팝오버 위치)는 화면을 직접 보지 못했다(점검은 DOM 값과 크기만 잰다). 노트 창(note-*)에서 같은 권한으로 확대되는지는 점검이 없고(권한 목록이 메인과 같다는 것만 계약 시험이 잰다), 4부를 켠 판은 안 돌렸다.
  • 앱에 든 Java로 도는 ais-cli는 릴리스 설정의 디버그 번들에서 실제로 확인했다(verify-release.mjs 10건). Java가 없는 Mac에서 설치해 본 확인, 서명·공증, 공개 배포용 최적화 빌드로 다시 지은 확인은 없다.
  • 4부를 켠 판의 실제 창 점검은 있지만 얕다(묻기 왕복, 세션 화면, 설정의 Claude 연결 8건). 레일 대화, 세션 입력창, 굳히기는 안 잰다. 진짜 launchctl로 돌려 본 확인, 서명·공증·업데이트, 원본 아이콘은 없다.
  • 물성 모양은 캘린더(일·주·월), 노트 읽기·편집, 설정, 빠른 검색, 시작 화면, 연결, 템플릿을 브라우저에서 눈으로 확인했다. 격자는 캘린더(일), 노트 편집, 설정을 밝게·어둡게로, 유리와 모던은 캘린더(일)를 밝게·어둡게로, 설정과 노트 편집을 밝게로 확인했다. 4부 화면(묻기 카드, 세션 화면, 레일 대화)과 이력 비교, 리포트, 휴지통은 물성 말고는 눈으로 확인하지 못했다.
  • 외부 설명서와 달라진 곳: Codex·Gemini 세션을 노트에 적고 읽는 확장이 있다(§5 「세션 에이전트 확장」). mins 필드를 지웠다(위 「vault의 모양」). 데일리 리포트 명령(list-reports, get-report, save-report)도 엔진에서 뺐다. 이 저장소의 받아들임 묶음은 mins를 뺀 기대값으로 고쳐 두었고, 리포트 사례 2건(list_reports/all, get_report/missing)을 덜어 27건이다. 진짜 묶음(읽기 레인 460건)을 구해 돌리면 응답에 mins가 없는 만큼, 그리고 리포트 사례만큼 어긋난다.
  • 설명서 원문이 제공되지 않은 부분(3부 18장, 4부 ais-agent 데몬, 진짜 받아들임 묶음)은 추측해서 채우지 않았다. 각 완료 기록의 「못 한 것」을 먼저 본다.
