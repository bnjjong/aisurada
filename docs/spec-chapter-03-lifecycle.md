# withlog 1부 vault 엔진 설명서 > 3장 실행 형태와 프로세스 수명

이 장은 엔진 프로세스를 띄우는 꼴 2가지와, 그 사이를 잇는 `wl-cli`가 언제 엔진을 띄우고 내리며 기기 위에 무엇을 남기는지를 정한다. 소켓 위의 바이트는 4장이 정하고, 설정 키와 기기 위 파일의 자리는 33장이 정한다.

- 단발 모드는 argv 첫 칸의 명령 1개를 처리하고 끝난다. 받아들임 묶음 460건이 모두 이 꼴로 엔진을 부르고, 바이트 계약은 stdout과 종료 코드와 stderr의 첫 `WL-` 번호 3가지뿐이다.
- serve 모드는 vault마다 잠금 1개를 쥐고 소켓 1개를 연다. 연결 없이 10분이 지나면 종료 코드 0으로 스스로 내려간다.
- `wl-cli`는 첫 칸으로 갈래를 정한다. 엔진 명령이면 소켓에 붙고, 못 붙으면 LaunchAgent로 엔진을 띄운 뒤 30초까지 기다리며, 엔진에 못 닿으면 종료 코드 4로 끝난다.
- launchd는 인스턴스를 1개로 지키기만 하고, 띄우고 내리는 결정은 `wl-cli`와 엔진이 한다. 그래서 plist에 `KeepAlive`가 없고 `RunAtLoad`가 거짓이다.
- 근거: 단발 모드의 명령과 인자 꼴, stdout 바이트, 종료 코드 0과 3은 묶음이 잰다. serve 모드, `wl-cli`, launchd 동작은 코드 읽기로만 확인했고 시간 값도 실행해 재지 않았다. 지금 엔진이 JDK 21과 Spring Framework 6.2.8과 Spring Boot 3.5.3에서 물려받은 동작은 그 라이브러리 소스로 확인했고, 자리마다 그렇게 밝혔다.

## 3.1 단발 모드

단발 모드는 엔진 실행 파일을 명령 1개와 함께 부르는 꼴이다. 지금 엔진에서는 이렇게 부른다.

```text
java [JVM 인자...] -jar wl-sidecar.jar <명령> [인자...] [--<설정 키>=<값>...]
```

묶음의 케이스는 argv 가운데 `<명령> [인자...]`만 정하고, 앞뒤 조각은 구현마다 어댑터가 붙인다(34.5). 지금 엔진의 어댑터로 부르면 케이스 `list_tags/limit=1`의 argv는 아래와 같다. `⟦…⟧`은 실행기가 회차마다 채우는 자리이고, argv 칸 사이는 공백 1개로 적었으며 `{"limit":1}`이 칸 1개다.

```text
⟦java⟧ -XX:TieredStopAtLevel=1 -Xmx512m -XX:-UsePerfData -Duser.home=⟦HOME⟧ -Djava.io.tmpdir=⟦TMPDIR⟧ -jar ⟦wl-sidecar.jar⟧ list_tags {"limit":1} --withlog.vault=⟦vault⟧ --withlog.db.home=⟦WLX_STATE_DIR⟧/db
```

종료 코드는 0이고, stdout은 아래 바이트 뒤에 줄바꿈 1개가 붙는다(「묶음이 잰다」).

```json
[
  {
    "tag": "랭킹",
    "count": 1
  }
]
```

**묶음이 주는 환경.** 실행기는 구현의 환경을 처음부터 새로 짓고 아래 표의 변수만 준다(「묶음이 잰다」). 부모 셸이 실vault를 가리키는 `WITHLOG_VAULT`를 내보내도 구현에게 닿지 않게 하려는 규칙이다. 이 설명서에서 「묶음의 환경」은 늘 이 표를 뜻한다.

| 변수 | 값 |
|---|---|
| `WITHLOG_VAULT` | 입력 vault를 펼친 절대 경로. `realpath`를 지난 값이다 |
| `HOME` | 입력 HOME을 펼친 절대 경로. 레인에 HOME이 없으면 빈 폴더다 |
| `TMPDIR` | 빈 임시 폴더 |
| `WLX_STATE_DIR` | 구현이 색인 같은 제 상태를 두는 빈 폴더 |
| `TZ` | `Asia/Seoul` |
| `LANG`, `LC_ALL` | `en_US.UTF-8` |
| `PATH` | 부모 셸의 값. 없으면 `/usr/bin:/bin` |
| 이름이 `WLX_IMPL_`로 시작하는 변수 | 부모 셸의 값 그대로. 어댑터 설정의 몫이다 |

어댑터의 `${이름}`은 이 환경에서 채운다. 그래서 지금 어댑터의 `--withlog.vault=${WITHLOG_VAULT}`는 늘 환경변수 `WITHLOG_VAULT`와 같은 글자다. 뒤 조각의 `--withlog.vault=`와 `--withlog.db.home=`은 지금 엔진의 어댑터와 1부 실행 스크립트가 고른 꼴이라, 다시 짓는 구현의 어댑터는 다른 꼴을 써도 된다.

**실행 1번의 차례.** 단발 모드는 아래 차례로 걷고, 앞 걸음에서 서면 뒤 걸음은 안 돈다(코드 읽기로 확인).

1. vault 문턱. 환경변수 `WITHLOG_VAULT`가 공백뿐이 아니거나, argv의 어느 칸이든 글자 그대로 `--withlog.vault=`로 시작하면 지나간다. 이 걸음은 칸의 자리와 혼자 선 `--`를 안 본다. 아니면 엔진 로그 없이 아래 2줄을 stderr에 쓰고 종료 코드 2로 끝난다.
2. 설정 칸 읽기. `--`로 시작하는 칸을 설정으로 가른다(아래 「설정 칸」). 이름이 빈 칸(`--=x`)이 있으면 엔진이 못 뜬다.
3. 엔진 조립. 설정 값을 타입에 맞춰 읽고(33.1), vault를 해석하고, 색인 폴더를 만들어 DB를 열고 스키마를 올리고, 스키마 판을 읽는다(4.5). 어느 것이든 실패하면 엔진이 못 뜬다. 이 걸음 안의 차례는 엔진 조립 차례를 따라서 이 설명서는 정하지 않는다. 다만 색인 자리가 vault 키에서 나와서 vault 해석이 색인 열기보다 먼저다.
4. 첫 칸이 정확히 `serve`면 serve 모드로 간다(3.2).
5. 세션 표식을 뗀다(4.4). 단발 모드로는 표식이 올 수 없어서 실제로는 아무것도 안 뗀다.
6. 명령 찾기. 첫 칸을 도구 이름에서 먼저, 명령 이름에서 다음에 찾고 대소문자를 가린다(5.1). argv가 비었거나 못 찾으면 종료 코드 2다.
7. 인자를 해석해 명령을 처리하고, 결과를 stdout과 stderr에 쓰고 끝난다.

```text
WITHLOG_VAULT 환경변수가 없다. vault 폴더의 절대 경로를 넣고 다시 실행한다.
설정으로 주려면 --withlog.vault=<경로> 를 붙인다.
```

위가 1번의 2줄이다. 가장 흔한 실수를 수십 줄의 스택 트레이스 대신 2줄로 알리려는 문턱이다.

「엔진이 못 뜬다」는 2번과 3번의 실패를 말한다. 종료 코드 1로 끝나고 WL 줄이 없다. 3번의 실패는 stderr에 엔진 로그 줄과 실패 기록(지금 엔진은 대개 「Application run failed」와 스택 트레이스)을 남긴다. 2번의 실패는 엔진 로그가 아직 안 선 때라서, 지금 엔진에서는 그 실패 기록이 stdout으로 나간다고 Spring Boot 3.5.3과 logback 1.5.18의 소스로 읽혔다(3.8의 29번, 실행해 보지 않았다). 다시 짓는 구현은 어느 실패든 stdout을 0바이트로 둔다. 2번과 3번의 실패가 모두 1이라서 3번 안의 차례는 종료 코드를 안 바꾼다. 아래 표는 이 차례로 결과가 갈리는 경우다.

| 경우 | 결과 |
|---|---|
| vault 폴더가 없고 명령도 모름 | 3번에서 서서 종료 코드 1 |
| `--=x`와 모르는 명령이 함께 옴 | 2번에서 서서 종료 코드 1. 지금 엔진은 실패 기록을 stdout에 쓴다(3.8의 29번) |
| vault는 맞고 명령만 모름 | 6번에서 종료 코드 2. 그 전에 3번이 `<db.home>/<VaultKey>/meta.db`를 만들고 스키마를 올린다 |
| argv가 `--withlog.vault=/v` 1칸뿐 | 1번을 지나고 2번이 그 칸을 설정으로 읽는다. `/v`가 폴더면 6번에서 `모르는 명령이다: --withlog.vault=/v`와 종료 코드 2, 아니면 3번에서 종료 코드 1 |
| `list_tags -- --withlog.vault=/v`이고 환경변수 `WITHLOG_VAULT`가 없음 | 1번은 지나지만 `--` 뒤의 칸은 설정이 아니라서 vault 값이 없다. 3번에서 종료 코드 1 |
| argv가 비었고 환경변수 `WITHLOG_VAULT`가 맞음 | 6번에서 `모르는 명령이다: (없음)`과 종료 코드 2 |

**설정 칸.** `--`로 시작하는 칸은 자리와 상관없이 엔진 프로세스의 설정이다. 첫 칸도 설정으로 읽히지만, 그 칸은 6번에서 명령 이름으로도 찾아져 모르는 명령이 된다. 그래서 설정 칸은 명령 이름 뒤에 둔다. 칸을 이름과 값으로 가르는 규칙은 Spring Framework 6.2.8의 명령줄 해석이고, 그 소스로 확인했다.

| 칸 | 설정으로 읽는 법 |
|---|---|
| `--<이름>=<값>` | 이름은 `--` 바로 뒤부터 처음 `=` 앞까지이고, 값은 그 뒤 전부다. `--a=b=c`는 이름 `a`와 값 `b=c`다 |
| `---x=y` | `--` 뒤의 `-x`가 이름이다 |
| `--<이름>` | `=`가 없으면 값이 빈 글이다 |
| 같은 이름을 여러 번 | 모든 값을 argv 차례대로 `,`로 이은 글자 1개가 값이다. 이름의 글자가 같을 때만 잇는다. `=`가 없는 칸은 값을 보태지 않고, `--<이름>=`은 빈 값 1개를 보탠다. 그래서 `--a --a=x`는 `x`이고 `--a=x --a=`는 `x,`다 |
| 혼자 선 `--` | 설정이 여기서 끝난다. 그 뒤의 칸은 `--`로 시작해도 설정이 아니다 |
| `--=<값>` | 이름이 비어 엔진이 못 뜬다. 혼자 선 `--` 뒤에 오면 설정이 아니라서 괜찮다 |
| 모르는 이름 | 조용히 버린다 |

설정의 이름과 값의 타입은 33.1이 정한다. 명령 인자에서 빼는 일은 이 표와 따로 돈다. 명령의 인자를 해석하는 단계가 `--`로 시작하는 칸을 혼자 선 `--`와 그 뒤의 칸까지 모두 빼서(5.2, 5.4), 명령은 그 칸을 못 본다. 부르는 쪽이 vault와 색인 자리를 같은 argv에 실어 보내서, 안 빼면 도구 표면이 그 칸까지 인자로 세어 인자 수 초과로 거절하기 때문이다.

**공백.** 이 장과 33장에서 「다듬는다」와 「공백뿐」은 0.3의 뜻이고, 「유니코드 공백」은 0.3의 다듬기 모음 28글자다. 지금 엔진과 `wl-cli`가 쓰는 코틀린 표준 라이브러리의 공백 판정이 이 글자들이다. 불리언과 정수 설정은 Spring의 규칙을 따라 떼는 글자가 다르고, 자리마다의 규칙은 33.2 끝의 표에 모았다.

**vault 지정.** vault는 설정 `withlog.vault`다. 1번 문턱을 지나면 33.1의 우선순위로 값을 고른다. 명령줄이 환경변수를 이겨서, 묶음처럼 환경변수와 명령줄 칸을 함께 주면 명령줄 값이 vault다. 고른 값을 다듬어 비면 엔진이 못 뜬다. 그다음 글자를 아래 차례로 정리한다. JDK 21의 경로 규칙이고 그 소스로 확인했다.

1. NUL 글자가 있으면 엔진이 못 뜬다.
2. 이어진 `/`를 1개로 줄이고 끝의 `/`를 뗀다. 뿌리 `/`는 그대로 둔다.
3. 상대 경로면 프로세스 작업 폴더를 앞에 붙여 절대 경로로 바꾼다.
4. `.` 조각을 지운다.
5. `<이름>/..` 짝을 더 지울 것이 없을 때까지 지운다. 절대 경로 맨 앞의 `..`은 뿌리 위로 갈 수 없어서 그냥 지운다.
6. 심볼릭 링크는 안 풀고, 유니코드 정규화(NFC, NFD)도 안 한다.

| 받은 값(「예시 값」) | 정리한 글자 |
|---|---|
| `/Users/me/vault/` | `/Users/me/vault` |
| `/Users/me//vault` | `/Users/me/vault` |
| `/Users/me/x/../vault` | `/Users/me/vault` |
| `/../Users/me/vault` | `/Users/me/vault` |

정리한 자리가 폴더가 아니면 엔진이 못 뜬다. 이 판정은 심볼릭 링크를 따라가서 폴더를 가리키는 링크도 받지만, vault 글자는 링크 경로 그대로다. 정리한 글자가 딥링크의 `ws=` 값이 되고(11.6), vault 키(33.3)의 재료가 된다. node의 `path.resolve`도 위 4가지 예에서 같은 글자를 낸다.

**stdout과 stderr.** stdout에는 결과 바이트만 나간다. 성공하면 6.1의 JSON과 줄바꿈 1개이고, 실패하면 0바이트다(「묶음이 잰다」). 지금 엔진은 결과를 JVM 표준출력 글 흐름으로 써서 그 인코딩을 JVM이 로캘에서 고르고, 묶음은 늘 `en_US.UTF-8`로 돌린다. 다시 짓는 구현은 로캘과 상관없이 늘 UTF-8로 쓴다. 묶음과 앱이 UTF-8만 받고, serve 모드는 이미 로캘과 상관없이 UTF-8 바이트를 싣기 때문이다. 지금 엔진의 로캘 의존은 3.8의 특이점이다.

stderr에는 엔진 로그 줄이 먼저 나오고, 명령의 진단 줄과 WL 실패 줄이 뒤에 나온다(6.4). 지금 엔진의 로그 줄은 Spring Boot 기본 꼴의 INFO 줄이고 UTF-8로 쓴다. stdout에 로그를 안 섞는 까닭은 부르는 쪽이 stdout을 곧바로 JSON으로 읽기 때문이다.

출력 가운데 계약은 아래 표의 3가지뿐이다.

| 출력 | 계약인가 |
|---|---|
| stdout 바이트 | 계약이다. 성공이면 6.1의 JSON과 LF 1개, 실패면 0바이트다 |
| 종료 코드 | 계약이다 |
| stderr의 첫 `WL-` 번호 | 계약이다. stderr 전체에서 정규식 `\bWL-\d{3}\b`가 처음 맞는 글자이고, 줄 머리일 필요가 없다. 묶음의 `wl` 칸이 이 규칙으로 읽는다. 지금 읽기 레인은 이 칸을 아직 안 쓴다 |
| stderr의 나머지 | 계약이 아니다. 문턱 2줄, 모르는 명령 안내, 진단 줄, WL 줄의 문구, 엔진 로그, 스택 트레이스가 여기 든다 |

엔진이 쓰는 고정 글은 줄마다 LF 1개로 끝나고 마지막 줄도 LF로 끝난다. 계약이 위 표뿐이라 다시 짓는 구현은 문구를 바꿔도 된다. 지킬 것은 1가지다. 실패 줄의 `WL-` 번호보다 앞에 `WL-`와 숫자 3자리 꼴의 글자를 쓰지 않는다. 앞에 쓰면 그 글자가 「처음 나오는 번호」로 읽힌다. 지금 엔진은 단발 모드에서 vault 경로가 든 로그 줄을 먼저 써서, 경로에 그 꼴이 든 vault에서는 이 규칙을 어긴다(3.8의 8번).

**모르는 명령.** argv가 비었거나 첫 칸을 못 찾으면 stdout을 비우고, 아래 글을 stderr에 쓰고, 종료 코드 2로 끝난다.

```text
모르는 명령이다: <첫 칸. argv가 비었으면 (없음)>
도구 이름으로 부르려면 이렇게 한다: <도구> '<json>'
  list_docs, search_docs, list_tags, get_doc, list_trash, list_reports, get_report, list_templates, get_template, list_sub_notes, get_sub_note, list_attachments
사이드카 고유 명령은 이렇다.
  reindex
  reindex-paths <vault 상대 경로> [경로...]
  (사용법 줄 59줄이 더 온다)
```

2번째 줄의 `<도구> '<json>'`은 꺾쇠까지 글자 그대로다. 사용법 줄은 명령 61개에 1줄씩 61줄이고, 위의 `reindex`와 `reindex-paths`가 그 처음 2줄이다. 줄마다 앞에 공백 2칸이 붙고, 줄마다 LF 1개로 끝나며 마지막 줄 뒤에도 LF가 1개 있다. 명령의 차례는 부록 A의 차례이고 3.3의 명령 이름 목록과도 같다. 사용법 줄의 글자는 부록 A.3에 바이트까지 있다. 사람이 읽는 안내라 계약은 아니고, 다시 짓는 구현이 문구를 맞추고 싶을 때 쓴다.

**종료 코드.**

| 종료 코드 | 언제 | stdout | 근거 |
|---|---|---|---|
| 0 | 명령 성공 | 결과 바이트 | 묶음이 잰다 |
| 2 | vault 문턱에서 섬, 모르는 명령, 빈 argv | 0바이트 | 코드 읽기로 확인 |
| 3 | `WL-400`, `WL-404`, `WL-409`, `WL-500` | 0바이트 | 종료 코드와 빈 stdout만 묶음이 잰다 |
| 5 | `WL-412` | 0바이트 | 코드 읽기로 확인 |
| 1 | 엔진이 못 뜸, 명령 처리 중 예상 밖 예외 | 0바이트. 지금 엔진은 2번 걸음의 실패에서 실패 기록을 stdout에 쓴다(3.8의 29번) | 코드 읽기로 확인, 실행 안 함 |

종료 코드 1이면 WL 줄이 없다. 3번 걸음의 실패와 명령 처리 중 예상 밖 예외는 stderr에 엔진 로그의 실패 기록과 스택 트레이스를 남긴다. 단발 모드에는 종료 코드 4가 없고, 4는 `wl-cli`가 엔진에 못 닿았을 때만 낸다(3.3). 묶음의 실패 케이스 `get_doc/missing`(`{"id":"nd없는노트"}`)은 종료 코드 3과 0바이트 stdout으로 맞는다.

**실행 1번이 남기는 것.** 3번의 색인 DB `<db.home>/<VaultKey>/meta.db`는 명령이 무엇이든, 모르는 명령이어도 열고 스키마를 올린다(8.2). serve 모드의 잠금, 실행 상태 파일, 소켓은 안 건드린다. vault git에는 `commit-vault`(31.5)만 커밋하고, 쓰기 명령이 남기는 쓴 쪽 기록은 프로세스와 함께 사라진다(3.7). stdin은 안 읽는다. 지금 엔진은 SQLite 드라이버의 네이티브 라이브러리를 JVM 임시 폴더(`java.io.tmpdir`)에 풀 수 있는데, 이것은 JVM 구현만의 일이다.

세션 표식(4.4)은 단발 모드로 올 수 없다. 표식이 NUL 글자로 시작하는데 운영체제의 argv가 NUL을 못 싣기 때문이다. 그래서 단발 모드의 도구 표면 쓰기에는 세션 id가 없다.

같은 vault와 같은 색인에 단발 모드 프로세스 여럿이 동시에 떠도 읽기는 맞아야 한다. 묶음이 케이스를 나란히 부르고(기본은 CPU 수에서 2를 뺀 값을 2부터 8 사이로 묶은 수이고, `--jobs`로 바꾼다), 이 성질이 깨지면 묶음이 어긋나기 때문이다(「묶음이 잰다」). 묶음은 펼친 vault마다 케이스보다 먼저 `reindex`를 1번 부르고, 그 걸음은 종료 코드 0만 본다. 그래서 새 색인의 스키마를 여러 프로세스가 동시에 처음 올리는 일은 묶음에서 안 생기고, 그때 어떻게 되는지는 재지 않았다.

## 3.2 serve 모드

serve 모드는 vault 1개를 맡아 유닉스 도메인 소켓으로 명령을 받는 상주 프로세스다. 부르는 꼴은 첫 칸이 정확히 `serve`인 argv다.

```text
java -jar wl-sidecar.jar serve
```

launchd가 plist(3.4)로 이렇게 띄우고, 사람이 손으로 띄워도 된다. `serve` 뒤의 칸은 3.1의 설정 칸으로만 쓰이고 나머지는 버린다. 통로가 TCP 포트가 아니라 소켓인 까닭은, TCP 포트에는 같은 기기의 어느 프로세스나 붙지만 소켓은 파일 권한으로 다른 사용자를 막을 수 있기 때문이다. 같은 사용자의 프로세스는 소켓에도 붙는다.

**뜨는 차례.** 아래는 코드 읽기로 확인한 차례다.

1. 3.1의 1번부터 3번까지(vault 문턱, 설정 칸, 엔진 조립)를 똑같이 지나고, 실패도 같은 종료 코드다.
2. 소켓 자리를 정한다. 환경변수 `WITHLOG_SIDECAR_SOCKET`이 공백뿐이 아니면 그 값을 다듬은 글자이고, 아니면 `~/Library/Caches/withlog/wl-<해시 16자>.sock`이다(33.3). 이 글자를 3.1의 vault 경로와 같은 규칙으로 정리하고, 상대 경로의 기준은 엔진 프로세스의 작업 폴더다. 정리한 글자의 UTF-8이 102바이트를 넘으면 엔진이 못 뜨고, 스택 트레이스에 `소켓 경로가 102 바이트를 넘는다(<n> 바이트): <경로>. WITHLOG_SIDECAR_SOCKET 로 더 짧은 자리를 지정한다.`가 든다.
3. 시작 시각을 벽시계에서 읽는다. 이 값이 실행 상태 파일의 `startedAt`이다. 프로세스가 뜬 시각이 아니라 이 걸음의 시각이라서, JVM을 띄우고 색인을 맞춘 시간만큼 프로세스 시작보다 늦다.
4. `~/Library/Application Support/withlog/run/` 폴더를 만들고 `<VaultKey>.lock`을 연다(없으면 만든다). 만들거나 열지 못하면 엔진이 못 뜬다. 그다음 잠금을 기다리지 않고 1번 시도한다. 못 잡으면 경고 로그 1줄을 남기고 종료 코드 0으로 끝나며, 실행 상태 파일과 소켓은 안 건드린다.
5. vault git에 `startup` 커밋을 한다(31.1). 실패해도 계속 간다.
6. 활동 시각을 지금으로 맞춘다. 연결이 1번도 안 오면 유휴 10분을 이 순간부터 센다.
7. 실행 상태 파일 `run/<VaultKey>.json`을 처음 쓴다. 못 쓰면 아래 「내려가는 차례」를 돌고 종료 코드 1로 끝난다.
8. 소켓의 부모 폴더를 만들고, 소켓 자리에 있는 것을 지운다. 남은 소켓 파일과 일반 파일과 빈 폴더와 심볼릭 링크(링크 자신)는 묻지 않고 지운다. 안이 찬 폴더라서, 또는 권한 때문에 못 지우면 아래 「내려가는 차례」를 돌고 종료 코드 1이다. 그다음 bind 한다. bind가 실패하면 그 자리의 소켓 파일을 지우고 내려가는 차례를 돌고 종료 코드 1이다. bind 하면 로그 「소켓을 열었다」를 남기고, 정비 스레드를 띄우고, 연결을 받는다.

2번에서 미리 재는 까닭은 소켓 경로가 너무 길면 그 vault에서만 이유를 모른 채 안 뜨기 때문이다. macOS의 소켓 경로 칸은 104바이트이고 끝 1바이트가 NUL 몫인데, JDK 21은 102바이트까지만 소켓을 연다(2026-10-28 실측). 그래서 상한은 102다. 103으로 재면 정확히 103바이트인 경로가 이 검사를 지나 `bind`에서 `Unix domain path too long`으로 종료 코드 1이 되고, `wl-cli`는 길이 문구 대신 jar가 없다거나 엔진이 준비되지 않았다는 엉뚱한 문구를 낸다. 4번이 실패가 아니라 종료 코드 0인 까닭은 다른 프로세스가 이미 그 vault를 맡았으면 할 일이 없기 때문이다. 코드는 실패로 끝내면 누가 plist에 `KeepAlive`를 켜는 날 10초 간격의 무한 재기동이 된다고 적는다. 이 까닭은 `KeepAlive`를 `{SuccessfulExit: false}`(실패로 끝날 때만 되살림)로 켠 경우를 가정한다. `KeepAlive`를 그냥 참으로 켜면 0으로 끝나도 되살려서(3.4), 지금 설계는 어느 쪽이든 `KeepAlive`를 안 둔다.

8번에서 엔진이 남은 파일을 지우는 까닭은 남은 소켓 파일 위에 bind 하면 실패하기 때문이고, 클라이언트가 지우면 살아 있는 엔진의 소켓을 뺏을 수 있어서 엔진이 지운다. 7번이 8번보다 앞인 차례도 지킨다. `wl-cli`의 다시 띄우기(3.3)가 새 pid를 그 파일에서 먼저 확인하기 때문이다.

**잠금.** 잠금은 vault 키마다 1개이고 프로세스가 사는 동안 쥔다. 지금 엔진은 POSIX 레코드 잠금을 쓴다. `fcntl`의 `F_SETLK`로 기다리지 않고, 쓰기 잠금 `F_WRLCK`을 0바이트부터 파일 끝 너머까지(길이 0) 건다. 0부터 끝까지의 배타 잠금이라는 것은 JDK 21의 자바 쪽 소스로 확인했고, 그것이 `fcntl` 잠금이라는 것은 OpenJDK의 macOS 구현에 기댄 것이라 이 저장소에서 재지 않았다. 다시 짓는 구현이 지금 엔진과 같은 기기에서 함께 돌 수 있으면 같은 잠금을 써야 서로를 막는다. POSIX 레코드 잠금은 그 프로세스가 그 파일의 어느 서술자를 닫아도 풀려서, 잠금 파일을 다른 길로 열었다 닫지 않는다. 프로세스가 죽으면 운영체제가 풀어 준다. 잠금 파일은 크기 0이고 아무도 안 지운다. 지우면 그 파일을 연 다른 프로세스와 서로 다른 inode를 잠가 양쪽 모두 잠금을 잡기 때문이다.

**권한 비트.** 엔진과 `wl-cli`는 폴더와 파일과 소켓 파일의 권한 비트를 따로 정하지 않고, 모두 프로세스의 umask를 따른다(코드 읽기로 확인). 소켓, `~/Library/Caches/withlog/`, `run/`, 실행 상태 파일, 잠금 파일, 색인 폴더가 모두 그렇다. 유닉스 도메인 소켓에 붙으려면 소켓 파일에 쓰기 권한이 있어야 해서, 흔한 umask 022에서는 주인만 붙는다. 다른 사용자를 막는 실제 담장은 이 권한과 홈 아래 폴더들의 권한이다.

**실행 상태 파일.** 사람이 유령 프로세스를 찾는 단서이고, `wl-cli`가 동시 상한과 청소와 다시 띄우기를 정할 때 읽는 자리다. 바이트는 이런 꼴이고 끝에 줄바꿈 1개가 붙는다(「예시 값」).

```json
{
  "pid": 4242,
  "vault": "/Users/me/vault",
  "socket": "/Users/me/Library/Caches/withlog/wl-17dc9196931802ce.sock",
  "startedAt": "2026-10-21T05:05:00.123456Z",
  "lastActiveAt": "2026-10-21T05:09:41.207Z",
  "openConnections": 0,
  "builtCommit": "0123456789abcdef0123456789abcdef01234567"
}
```

| 차례 | 키 | 타입 | 값 | 읽는 쪽 |
|---|---|---|---|---|
| 1 | `pid` | 정수 | 엔진 프로세스 id | 상한, 청소, 다시 띄우기, `doctor` |
| 2 | `vault` | 문자열 | 정리한 vault 절대 경로 | `doctor`, `sweep` 출력 |
| 3 | `socket` | 문자열 | 정리한 소켓 절대 경로 | 사람 |
| 4 | `startedAt` | 문자열 | 뜨는 차례 3번의 순간. UTC이고 초 아래는 0, 3, 6, 9자리 중 필요한 만큼 | 다시 띄우기, `doctor` |
| 5 | `lastActiveAt` | 문자열 | 마지막 활동 순간. 밀리초로 잘라 UTC로 적고, 초 아래는 0자리나 3자리 | 상한, 청소, `doctor` |
| 6 | `openConnections` | 정수 | 그 순간 열린 연결 수 | 상한, 청소, 다시 띄우기, `doctor` |
| 7 | `builtCommit` | 문자열이나 `null` | 엔진을 지은 git 커밋 40자. 모르면 `null` | `doctor` 커밋 줄 |

처음 쓸 때의 `lastActiveAt`은 뜨는 차례 6번의 순간이다. 문자열 값은 6.1과 같은 규칙으로 탈출한다. `"`는 `\"`, `\`는 `\\`, 제어 글자는 `\b`, `\t`, `\n`, `\f`, `\r`과 소문자 `\u00xx`이고, 한글을 비롯한 나머지 글자는 UTF-8 그대로다. 들여쓰기는 2칸이고 줄마다 키 1개다.

`wl-cli`는 JSON 파서 없이 이 파일을 줄로 훑는다. 그래서 지키는 꼴은 「줄 1개에 키 1개, 키와 값이 같은 줄」이다. 키 차례와 들여쓰기 칸 수에는 안 기대지만, 지금 엔진은 위 차례와 2칸으로 쓴다. 읽는 규칙은 이렇다(코드 읽기로 확인).

| 읽는 일 | 규칙 |
|---|---|
| 줄 찾기 | 앞의 유니코드 공백을 뗀 줄 머리가 `"<키>"`인 첫 줄 |
| 값 글자 | 그 줄의 첫 `:` 뒤를 다듬고, 끝의 `,` 1개를 떼고, 다시 다듬은 글자 |
| 문자열 칸 | 값 글자가 `"`로 시작하고 끝나야 한다. 안쪽의 `\"`를 `"`로, 그다음 `\\`를 `\`로 되돌린다. 그 밖의 탈출(`\n`, `\u00xx`)은 글자 그대로 남는다 |
| 정수 칸 | 값 글자가 `"`로 시작하지 않아야 한다. `pid`는 64비트, `openConnections`는 32비트 10진수로 읽고 부호를 받는다 |
| `null` | 문자열 칸이면 따옴표가 없어서, 정수 칸이면 숫자가 아니어서 「모름」이다. 그래서 `builtCommit`의 `null`은 「모름」이다 |
| 시각 칸 | ISO 순간으로 읽는다 |
| 못 읽음 | 파일을 못 읽거나 UTF-8이 아니면 모든 칸이 「모름」이고, 칸마다 못 읽으면 그 칸이 「모름」이다 |

엔진은 이 파일을 같은 폴더의 `<VaultKey>.json.tmp`에 쓴 뒤 이름을 바꿔 덮는다. 반쯤 쓴 JSON을 읽는 쪽이 생기면 진단 장치가 그 파일 때문에 못 돌기 때문이다. 쓸 글자가 지난번과 같으면 안 쓴다. 조용한 엔진이 5초마다 디스크를 건드리지 않게 하려는 규칙이고, 대가로 밖에서 지운 파일은 값이 바뀔 때까지 안 돌아온다.

**연결과 활동 시각.** 연결은 받는 순간 1을 세고 처리가 끝나면 1을 뺀다. 받는 순간에 세는 까닭은 처리 스레드가 뜨기 전에 유휴 판정이 돌면 열린 연결을 0으로 볼 수 있기 때문이다. 활동 시각은 연결 처리가 끝날 때마다 지금으로 바뀌고, 정비 때 열린 연결이 있어도 바뀐다. 아무 바이트도 안 보낸 생존 확인 연결(4.3)과 프레임이 어긋난 연결도 활동으로 친다.

**정비 5초.** 정비 스레드는 일을 마친 뒤 5,000밀리초를 쉬고 다시 깬다. 고정 주기가 아니라서, 3번의 커밋이 오래 걸리면 다음 정비와 유휴 판정도 그만큼 밀린다. 첫 정비는 소켓을 연 지 5초 뒤다.

1. 열린 연결이 있으면 활동 시각을 지금으로 바꾼다. 응답이 큰 요청 1개가 정비 시각과 겹칠 때 그 요청을 유휴로 오판하지 않으려는 규칙이다.
2. 실행 상태 파일을 쓴다(바뀌었을 때만).
3. vault git 자동 커밋이 밀렸으면 커밋한다(31.1).
4. 유휴 종료가 켜져 있고 유휴면 받기를 멈춘다.

2번과 3번은 묶여서 차례로 돌고, 2번이 실패하면 그 회차의 3번은 건너뛴다. 실패는 경고 로그만 남기고 정비 스레드는 산다. 그 스레드가 죽으면 유휴 종료도 함께 사라져서, 흔적을 남기려다 유령을 만드는 셈이 되기 때문이다.

**유휴 10분.** 유휴는 열린 연결이 0이고, 마지막 활동 뒤로 설정 `withlog.idle.timeout.minutes`(기본 10, 33.1)분 이상이 지난 상태다. 지난 시간은 단조 시계로 재서 벽시계를 바꿔도 안 흔들리고, 실행 상태 파일의 `lastActiveAt`은 같은 순간을 벽시계로 적는다. 판정은 정비 때만 해서, 실제로 내려가는 때는 문턱을 넘은 뒤의 다음 정비다. 값이 0 이하면 유휴 종료를 끄고 정비는 그대로 돈다. 정비를 계속 돌리는 까닭은 끈 엔진의 실행 상태 파일이 처음 값으로 굳으면, 상한을 지키는 쪽이 멀쩡히 도는 엔진을 가장 오래 조용한 것으로 고르기 때문이다. 10분인 까닭은 작업 1개를 하는 동안의 명령은 몇 분 간격으로 이어지고, 그 밖의 시간에 JVM을 띄워 놓을 까닭이 없기 때문이다.

**내려가는 차례.** 받기를 멈추는 길은 3가지다. 유휴면 정비 스레드가 멈추고, 신호(SIGTERM, SIGINT, SIGHUP)면 JVM 종료 훅이 멈추고, 받기(accept)가 입출력 오류로 실패해도 멈춘 것으로 친다. 어느 길이든 받던 스레드가 소켓 파일을 지우고 로그 「소켓을 닫았다」를 남긴다. 그 뒤 아래 차례는 프로세스마다 1번만 돈다.

1. 새 연결을 안 받는다.
2. 열린 연결이 0이 되거나 5초가 지날 때까지 50밀리초 간격으로 기다린다. 5초를 넘겨도 오류로 안 친다.
3. vault git에 `shutdown` 커밋을 한다(31.1).
4. 실행 상태 파일을 지운다.
5. 잠금을 놓고 잠금 파일을 닫는다. 잠금 파일은 안 지운다.

2번이 있는 까닭은 처리 스레드가 프로세스 종료를 안 붙잡아서, 안 기다리면 응답을 쓰던 연결이 반쯤 잘리기 때문이다. 코드에 남은 실측 기록으로는 39MB 응답이 5MB 남짓에서 끊겼다. 3번이 4번과 5번보다 앞인 까닭은 잠금을 놓은 뒤에 커밋하면 새로 뜬 엔진의 `startup` 커밋과 겹치기 때문이다. 4번이 5번보다 앞인 까닭은 잠금을 쥔 동안만 그 실행 상태 파일이 자기 것으로 보장되기 때문이다. 순서를 뒤집으면 그 사이에 새로 뜬 엔진의 파일을 지울 수 있다. 2번과 3번은 launchd의 `ExitTimeOut` 25초(3.4) 안에 끝나야 하고, 기다림이 최대 5초라서 커밋에 20초가 남는다. 내려갈 때 `<VaultKey>.json.tmp`는 따로 안 지운다. 그 파일은 실행 상태 파일을 쓰는 순간에만 있어서 보통은 남지 않는다.

유휴나 받기 실패로 내려가면 종료 코드 0이다. 유휴 종료를 실패로 끝내면 `KeepAlive`를 켜는 날 무한 재기동이 되기 때문이다. 신호로 내려가면 지금 엔진은 128에 신호 번호를 더한 값으로 끝난다. SIGHUP은 129, SIGINT는 130, SIGTERM은 143이다. JDK 21의 신호 처리 소스로 확인했고 실행해 재지는 않았다. 이 값을 읽는 쪽은 없다. plist에 `KeepAlive`가 없어서 launchd도 종료 코드로 되살리지 않기 때문이다. 다시 짓는 구현은 같은 관례를 따르기를 권한다.

SIGKILL을 맞으면 위 차례가 안 돌아서 소켓 파일과 실행 상태 파일이 남는다. 잠금은 운영체제가 푼다. 남은 소켓 파일에는 연결이 안 되므로 `wl-cli`가 엔진을 새로 띄우고, 새 엔진이 뜨는 차례의 8번에서 그 파일을 지운다. 남은 실행 상태 파일은 새 엔진이 덮거나, 문턱 넘게 조용했으면 하루 청소가 지운다(3.5).

**serve 모드 엔진에 온 `serve`.** 요청 argv의 첫 칸이 `serve`면 모르는 명령이다. 상태 2와 오류 코드 0으로 답한다. `serve`는 프로세스를 띄울 때만 읽는 이름이라 명령 목록에 없기 때문이다. serve 모드는 뜰 때 vault를 훑지 않고, 색인을 맞추는 때는 8.3이 정한다.

## 3.3 `wl-cli`

`wl-cli`는 사람과 Claude와 앱이 엔진을 부르는 얇은 클라이언트다. 지금은 `java -jar wl-cli.jar <첫 칸> [나머지...]`로 돈다. 앱은 호출마다 `wl-cli`를 새 프로세스로 띄우고 환경변수 `WITHLOG_VAULT`를 열린 vault로 덮어 넘긴다(33.2). `wl-cli`는 응답 JSON을 해석하지 않고 응답 바이트를 그대로 흘린다. 옛 구현의 호출 1번이 0.13초였고 JVM 콜드 스타트가 0.07초를 먹어서, 남은 60밀리초 안에 JSON 파서나 SQLite 드라이버를 싣지 않으려는 설계다.

**갈래 표.** 첫 칸 1개로만 가르고 나머지 칸은 안 본다. 맞추기는 대소문자를 가리는 정확한 맞추기이고, 위 줄부터 처음 맞는 갈래로 간다(코드 읽기로 확인).

| 첫 칸 | 갈 곳 | 종료 코드 |
|---|---|---|
| `doctor`, `sweep`, `report`, `schedule`, `install` | `wl-cli`가 직접 한다. `report`와 `schedule`은 버릴 기능이라 이 설명서가 안 다룬다(0.1) | 3.5, 3.6 |
| 없음, `--help`, `-h` | 사용법과 목록을 stdout에 쓴다 | 0 |
| `--list`, `-l` | 목록만 stdout에 쓴다 | 0 |
| 도구 이름 29개, 명령 이름 61개 | 엔진(아래 차례) | 응답의 상태 칸 |
| 그 밖 | 아래 5줄을 stderr에 쓴다 | 2 |

도구 29개는 도구 표면 전체이고 명령 61개는 엔진의 명령 표면 전체다. 목록과 안내에 나오는 차례는 아래와 같다. 명령 61개의 차례는 부록 A와 같고, 도구 29개의 차례는 부록 B와 다르다. 차례는 계약이 아니다.

```text
직접 하는 명령 5개
doctor, sweep, report, schedule, install

명령 61개
reindex, reindex-paths, list-docs, search-docs, get-doc, list-sub-notes, get-sub-note, list-attachments, list-comments, list-tags, list-trash, list-reports, get-report, list-templates, get-template, list-agendas, list-projects, create-project, update-project, delete-project, save-report, save-template, set-favorite, evaluate-doc, link-docs, write-attachment, delete-doc, restore-doc, purge-doc, create-sub-note, update-sub-note, delete-sub-note, export-markdown, create-doc, update-doc, empty-trash, create-agenda, update-agenda, delete-agenda, save-ritual-template, delete-doc-template, init-workspace, create-comment, update-comment, delete-comment, shard-notes, verify-shard, plan-day, check-notes, history, commit-vault, get-agenda-facts, get-ask, append-ask-turn, list-chats, append-chat-turn, update-agenda-facts, facts-brief, read-session, session-titles, recent-sessions
```

`serve`는 어느 목록에도 없어서 모르는 이름이다. 4부 명령 7개도 명령 61개 안에 있어서 엔진으로 가고, 4부가 빠진 엔진은 `WL-409`로 답한다(32.2). 모르는 이름이면 아래 5줄을 stderr에 쓴다. 이름은 위 차례로 `, `로 잇는다.

```text
알 수 없는 이름: <첫 칸>
도구: <도구 29개>
명령: doctor, sweep, report, schedule, install
사이드카 고유 명령: <명령 61개>
전체 설명은 wl-cli --list 로 본다.
```

`wl-cli`가 쓰는 글은 이 절과 3.5, 3.6의 것 모두 줄마다 LF 1개로 끝나고, 여러 줄 글의 마지막 줄 뒤에도 LF가 1개 있다. 글 안의 줄바꿈도 LF 1개다. 문장은 모두 사람용이라 계약이 아니다. `WL-400`으로 시작하는 줄 3가지는 0.2대로 종료 코드 2와 그 `WL-400` 번호만 계약이다.

목록은 도구마다 `<이름> — <설명>` 1줄(들여쓰기 없음), 빈 줄, 직접 하는 명령 5개의 같은 꼴, 빈 줄, `사이드카 고유 명령: <명령 61개>`, 안내 1줄 `  앱이 쓰는 배선입니다. 이름이 하이픈인 것이 표시이고, 도구 이름(밑줄)과 다른 표면입니다.`이다. 사용법은 그 앞에 아래 3줄과 빈 줄 1개를 붙인다. 모든 줄은 LF 1개로 끝나고, 설명 문장은 계약이 아니다.

```text
사용법: wl-cli <도구 또는 명령> [인자...]
  도구는 JSON 한 덩이를 받습니다: wl-cli get_doc '{"id":"..."}'
  명령은 이름과 값을 받습니다: wl-cli list-docs limit=0
```

**`report`와 `schedule`을 다시 지을 때.** 다시 짓는 `wl-cli`는 이 이름 2개를 모르는 이름처럼 다뤄 종료 코드 2로 끝내도 된다. 앱은 리포트 화면에서 `schedule status --json`을 부르는데, 실패하면 배너를 안 그리고 개발자 콘솔에 경고 1번을 남길 뿐이다(코드 읽기로 확인). 설치된 리포트 잡이 남은 기기에서는 그 잡이 실패한다.

**엔진 갈래의 차례.** 아래는 코드 읽기로 확인한 차례다.

1. `WITHLOG_VAULT`를 읽는다. 없거나 공백뿐이면 `WL-400 WITHLOG_VAULT 환경변수가 없다. vault 폴더의 절대 경로를 넣고 다시 실행한다.`를 stderr에 쓰고 종료 코드 2다. 값은 다듬고 폴더가 있는지는 안 본다. 그 판정은 엔진이 하고, 2곳에서 하면 어느 쪽만 고치는 날 결과가 갈리기 때문이다.
2. 소켓 자리를 3.2 뜨는 차례의 2번 규칙으로 정한다. vault 키와 상대 경로의 기준은 `wl-cli`의 작업 폴더다. 102바이트를 넘으면 `WL-400 소켓 경로가 102 바이트를 넘는다(<n> 바이트): <경로>. WITHLOG_SIDECAR_SOCKET 로 더 짧은 자리를 지정한다.`이고 종료 코드 2다.
3. 붙어 본다. 소켓 파일이 있고 연결이 되면 곧바로 닫는다(생존 확인 연결, 4.3). 되면 4번으로, 안 되면 5번으로 간다.
4. 다시 띄우기 판정(아래)을 한다. 다시 띄울 필요가 없으면 곧바로 6번으로 가고, 다시 띄웠으면 그 절의 기다림이 끝난 뒤 6번으로 간다.
5. 띄우고(아래) 30초 기다림(아래)을 한다.
6. 소켓에 새로 연결한다. 3번이나 5번에서 붙었어도 그사이 엔진이 내려가면 여기서 실패하고, 다시 시도하지 않고 종료 코드 4로 끝난다(실패 표). 붙으면 요청 프레임(4.1)을 짓는다. argv는 받은 그대로이고 `--` 칸도 안 뺀다. `CLAUDE_CODE_SESSION_ID`를 다듬은 값이 비지 않으면 세션 표식(4.4)을 끝에 붙인다. 이때 칸 수와 칸 크기를 잰다. 명령 이름과 표식 2칸까지 센 칸이 64칸을 넘거나, 칸 1개의 UTF-8 바이트가 1,048,576을 넘으면 1바이트도 안 쓰고 예외로 죽어 종료 코드 1이다. 이 검사가 5번 뒤라서, 이 실패는 plist를 쓰고 엔진을 띄운 뒤에도 날 수 있다.
7. 프레임을 다 쓰고 쓰기 쪽을 닫는다.
8. 응답 머리(4.2)를 읽고, stdout 길이만큼 표준출력으로, stderr 길이만큼 표준오류로 바이트를 그대로 옮긴다.
9. 하루 청소가 밀렸으면 돈다(3.5). 6번부터 8번이 실패한 호출에서는 안 돈다.
10. 응답 머리의 상태 칸을 종료 코드로 삼아 끝난다. 운영체제가 종료 코드의 아래 8비트만 넘겨서, 255를 넘는 상태는 256으로 나눈 나머지가 된다.

그래서 성공한 호출의 stdout은 엔진 stdout과 바이트까지 같다. `wl-cli`는 운영체제가 준 argv 바이트를 그대로 싣지 않는다. JVM이 argv를 UTF-8로 풀어 글자로 받고, `wl-cli`가 그 글자를 다시 UTF-8로 쓴다. UTF-8로 올바른 argv는 바이트가 같고, UTF-8이 아닌 바이트는 JVM이 U+FFFD로 바꿀 것으로 보이나 재지 않았다.

**알림 줄.** `wl-cli`가 성공하는 길에서 stderr에 쓰는 줄은 아래가 전부이고, 모두 계약이 아니다. 엔진 stderr 앞뒤에 붙을 수 있다. 보통의 띄우기가 성공하면 아무 줄도 안 쓴다. launchctl의 출력은 삼키기 때문이다.

| 줄 | 언제 |
|---|---|
| `사이드카를 다시 띄운다 — jar 가 뜬 뒤에 바뀌었다: <jar>` | 다시 띄우기 직전 |
| `사이드카 재시작 대상이 없다 …`로 시작하는 2줄 | 다시 띄우기가 113을 받음 |
| `사이드카가 아직 뜨는 중이다. <상한>초까지 기다린다: <소켓>` | 기다린 지 10초가 지남 |
| `사이드카 동시 상한 …`으로 시작하는 줄 | 띄우기 전에 다른 엔진을 내림(3.5) |
| 하루 청소의 줄 | 하루 청소가 돎(3.5) |

**띄우기.** 3번에서 못 붙었을 때만 탄다. 흔한 경우인 「이미 떠 있다」에 launchctl 비용을 안 붙이려는 차례다.

1. plist 본문을 짓는다(3.4). 엔진 실행 파일 자리를 못 정하면 아래 1줄과 종료 코드 2다. 그때까지 디스크에는 아무것도 안 썼다. `<설치 자리>`는 `~`를 푼 절대 경로 `<user.home>/Library/Application Support/withlog/bin/wl-sidecar.jar`다.

```text
WL-400 WITHLOG_SIDECAR_JAR 가 없고 설치된 wl-sidecar.jar 도 없다(<설치 자리>). `install` 을 돌리거나 jar 의 절대 경로를 WITHLOG_SIDECAR_JAR 에 넣는다. 이 값이 plist 에 그대로 실리므로 상대 경로를 쓰면 launchd 가 못 찾는다.
```

2. 디스크의 plist와 글자가 다르면 덮어쓰고 `launchctl bootout gui/<uid>/<레이블>`을 부른다. 파일이 없으면 다른 것으로 치고, `~/Library/LaunchAgents/`가 없으면 만든다. 파일은 있는데 못 읽거나(UTF-8이 아님 포함) 못 쓰면 예외로 죽어 종료 코드 1이다. bootout의 종료 코드는 안 본다. 글자가 같으면 아무것도 안 한다. 안 내리면 launchd가 옛 정의를 그대로 쓰기 때문이다.
3. 동시 상한을 지킨다(3.5).
4. `launchctl kickstart gui/<uid>/<레이블>`을 부른다.
5. 결과가 113(그런 서비스가 없다)이면 `launchctl bootstrap gui/<uid> <plist 경로>`를 부르고(종료 코드는 안 본다) 4번을 다시 한다.
6. 아직 113이고 레이블이 꺼져 있으면, `launchctl enable gui/<uid>/<레이블>`, 5번의 bootstrap, 4번을 차례로 다시 한다. `launchctl print-disabled gui/<uid>`의 출력에서 레이블을 부분 글자로 품은 줄 가운데, `=>` 뒤를 다듬은 글이 `true`로 시작하는 줄이 1개라도 있으면 꺼진 것으로 본다. 2026-10-22에 이 저장소의 기기(macOS 26)에서 출력 꼴만 세어 보니 `=> disabled`와 `=> enabled`만 있고 `=> true`는 없었다. 그래서 그 기기의 launchctl에서는 이 갈래가 안 탄다(3.8의 17번).
7. 마지막 kickstart의 종료 코드가 0이 아니면 아래 글을 stderr에 쓰고 종료 코드 4다. 마지막 줄은 그 kickstart의 출력을 다듬은 글이고, 비면 빈 줄이다.

```text
사이드카를 못 띄웠다. launchctl kickstart 가 <코드> 를 줬다: <레이블>
plist=<plist 경로>
로그=<로그 경로>
<마지막 kickstart의 출력을 다듬은 글>
```

6번이 따로 있는 까닭은 bootstrap이 「이미 올라옴」과 「꺼짐」 모두에 5를 줘서 그 값으로는 못 가리기 때문이다.

**launchctl 부르기.** launchctl은 `/bin/launchctl`을 쓰고 stdout과 stderr를 합쳐 받는다. 1번에 10초를 넘기면 그 프로세스를 끝내고, 출력은 프로세스가 끝난 뒤에 읽는다. 돌리지 못했거나 10초를 넘기면 아래 글 가운데 1줄을 stderr에 쓰고 종료 코드 4로 끝난다. 이 규칙은 띄우기, 다시 띄우기, 30초 기다림의 진단, `doctor --prune`에 걸린다. 동시 상한과 하루 청소와 `sweep`은 그 실패를 글로 적고 계속 간다(3.5).

```text
<프로그램> 가 10 초 안에 안 끝났다: [<argv를 ", "로 이은 글>]
<프로그램> 를 못 돌렸다: <운영체제 문구>
<프로그램> 를 기다리다 끊겼다
uid 를 못 읽었다. 홈 폴더 속성도 `id -u` 도 답을 안 줬다.
```

`<프로그램>`은 `/bin/launchctl`이고, uid를 읽을 때만 `id`다. 예를 들어 kickstart가 10초를 넘기면 `/bin/launchctl 가 10 초 안에 안 끝났다: [/bin/launchctl, kickstart, gui/501/co.kcd.withlog.sidecar.17dc9196931802ce-vault]`다(「예시 값」).

uid는 `~` 폴더 주인의 uid이고, 심볼릭 링크를 따라가 읽는다. 지금 구현의 `~`는 JVM의 `user.home`이다(33.3). 못 읽으면 `PATH`에서 찾은 `id -u`의 출력을 다듬은 글이고, 그것도 비면 위의 uid 글로 종료 코드 4다. uid는 launchctl을 부를 때마다 다시 읽고, launchctl을 안 부르는 호출은 uid를 안 읽는다. 프로세스를 1개 더 띄우지 않으려고 파일 속성을 먼저 본다. 이 값이 틀리면 남의 도메인에 잡을 올리려 드는 셈이라 기본값으로 물러서지 않는다.

**30초 기다림.** 띄운 뒤에는 붙어 보기를 되풀이한다. 시계는 띄우기의 마지막 kickstart가 돌아온 뒤에 재기 시작한다. 붙어 보고, 안 되면 100밀리초를 쉬고, 다시 붙어 본다. kickstart는 엔진의 준비를 안 기다리고 곧바로 돌아오고, 프로세스가 살아 있는 것과 요청을 받을 준비가 된 것은 다르기 때문이다. 상한은 환경변수 `WITHLOG_READY_TIMEOUT_SECONDS`의 양의 정수 초이고(읽는 규칙은 33.2), 없거나 틀리면 30초다. 기다린 지 10초가 지나도 못 붙으면 stderr에 아래 1줄을 1번 쓴다. 상한이 10초 이하이면 그 전에 기다림이 끝나서 이 줄이 사실상 안 나온다.

```text
사이드카가 아직 뜨는 중이다. <상한>초까지 기다린다: <소켓>
```

상한이 지나면 `launchctl print gui/<uid>/<레이블>`을 1번 부르고, 아래 글을 쓰고 종료 코드 4로 끝난다. 마지막 줄은 그 출력을 다듬은 글의 앞 1,200 UTF-16 단위이고, 잘라도 표시를 안 붙인다. print가 0이 아닌 종료 코드를 줘도 그 출력을 그대로 싣는다. print를 돌리지 못했거나 10초를 넘기면 아래 글 대신 launchctl 글 1줄로 종료 코드 4다.

```text
사이드카가 <상한> 초 안에 준비되지 않았다: <소켓>
WITHLOG_READY_TIMEOUT_SECONDS 로 더 기다리게 할 수 있다.
<launchctl print 출력을 다듬은 글의 앞 1,200자>
```

30초인 까닭은 기기가 바쁠 때 JVM 시작부터 소켓이 열리기까지 16초에서 20초가 걸린 기록이 있기 때문이다. 이 기다림은 요청을 보내기 전이라 길게 기다려도 같은 쓰기가 2번 가지 않는다.

**다시 띄우기.** 이미 붙는 엔진이라도 그 실행 파일이 뜬 뒤에 바뀌었으면 다시 띄운다. 빌드가 엔진 jar를 제자리에서 덮으면 도는 JVM이 아직 안 읽은 클래스부터 깨지고, 그 고장이 「사이드카와 말이 안 통한다」로만 보이기 때문이다. 아래 4가지가 모두 맞아야 한다.

- 실행 상태 파일이 있다.
- 디스크의 plist에서 jar 경로를 읽었다. 파일을 UTF-8로 읽어 줄마다 다듬고, 다듬은 줄이 통째로 `<string>…</string>`인 줄의 값을 차례로 모으고, `&lt;`, `&gt;`, `&amp;`를 이 차례로 되돌린 뒤, 처음 나오는 `-jar` 다음 값을 쓴다. 지금 환경으로 새로 지은 plist 글이 아니라 디스크의 파일을 읽는다.
- 그 jar 파일의 수정 시각과 실행 상태 파일의 `startedAt`을 모두 읽었고, 수정 시각이 `startedAt`보다 뒤다. 그 2개를 순간 그대로 나노초까지 맞대고, 같으면 안 띄운다. 수정 시각은 심볼릭 링크를 따라간 파일에서 읽는다.
- `openConnections`가 정확히 0이다. 모르면 안 띄운다. 남의 호출을 도중에 끊는 것이 고치려는 고장보다 나쁘기 때문이다.

1가지라도 못 읽으면 조용히 안 띄우고 6번으로 간다. 다시 띄우기는 붙는 데 성공한 위에 얹은 자가 치유라서, 그 판정이 실패해도 호출은 실패하면 안 되기 때문이다. 맞으면 stderr에 `사이드카를 다시 띄운다 — jar 가 뜬 뒤에 바뀌었다: <jar>`를 쓰고 `launchctl kickstart -k gui/<uid>/<레이블>`을 부른다.

| `kickstart -k` 결과 | 다음 |
|---|---|
| 0, 37 | 실행 상태 파일의 `pid`가 옛 값과 달라질 때까지 100밀리초마다 본다. 상한은 30초 기다림과 같고, 넘으면 조용히 다음으로 간다. 그다음 30초 기다림을 한다 |
| 113 | stderr에 아래 2줄을 쓰고 30초 기다림으로 간다 |
| 그 밖 | `사이드카 재시작이 실패했다. launchctl kickstart -k 가 <코드> 를 줬다: <레이블>`과, 그 출력을 다듬은 글을 다음 줄에 쓰고 종료 코드 4 |

```text
사이드카 재시작 대상이 없다 — 그 라벨이 launchd 에 없다(113): <레이블>
낡은 jar 로 계속 돈다. wl-cli install 로 그 라벨을 다시 등록해야 한다.
```

옛 `pid`는 판정 때 읽은 실행 상태 파일의 값이다. 그 값을 몰랐으면 pid를 안 지켜보고 곧바로 30초 기다림으로 간다. 지켜보는 동안 파일이 없거나 `pid`를 못 읽으면 「아직 안 바뀜」으로 친다. 옛 엔진이 파일을 지우고 새 엔진이 아직 안 쓴 틈을 새 엔진으로 잘못 읽지 않으려는 규칙이다. pid 지켜보기는 알림 줄을 안 쓰고, 뒤의 30초 기다림은 10초 알림 줄을 쓴다. 기다림 2개가 상한을 따로 써서 이 길의 기다림은 최대 상한의 2배다.

37은 실패가 아니라 「다른 호출이 이미 다시 띄우는 중」이다. 앱이 뜰 때 호출 여럿이 한꺼번에 와서 모두 같은 판정을 내리면 launchd가 1개만 통과시키기 때문이다. 진 쪽이 곧바로 붙으면 방금 깨졌다고 본 옛 프로세스에 붙어서, 진 쪽도 이긴 쪽과 같은 새 프로세스를 기다린다. 소켓이 아니라 pid를 보는 까닭은 옛 프로세스가 내려가는 동안에도 옛 소켓이 듣고 있어서, 소켓만으로는 옛것과 새것을 못 가리기 때문이다.

**실패 표.** 엔진이 응답을 보냈으면 종료 코드는 응답의 상태 칸이다. 그 밖의 실패는 아래와 같다. 글은 줄마다 LF 1개로 끝나고 여러 줄 글은 줄마다 LF로 끝난다. 계약은 종료 코드와 `WL-` 번호뿐이고 문구는 계약이 아니다.

| 조건 | 종료 | stderr |
|---|---|---|
| `WITHLOG_VAULT` 없음 | 2 | `WL-400 WITHLOG_VAULT 환경변수가 없다. …` |
| 소켓 경로가 102바이트 초과 | 2 | `WL-400 소켓 경로가 102 바이트를 넘는다…` |
| 띄워야 하는데 엔진 실행 파일 자리가 없음 | 2 | `WL-400 WITHLOG_SIDECAR_JAR 가 없고 …` |
| kickstart 실패 | 4 | `사이드카를 못 띄웠다. …` 4줄 |
| 상한 안에 못 붙음 | 4 | `사이드카가 <상한> 초 안에 준비되지 않았다: …` 3줄 |
| 다시 띄우기 실패 | 4 | `사이드카 재시작이 실패했다. …` 2줄 |
| launchctl을 못 돌림, 10초 초과, uid를 못 읽음 | 4 | 위 launchctl 글 1줄 |
| 6번 연결 때 소켓 파일이 없음 | 4 | `사이드카가 안 떠 있다. 소켓 파일이 없다: <소켓>` |
| 6번 연결 때 파일은 있는데 연결 실패 | 4 | `소켓 파일은 있는데 못 붙는다: <소켓>. 사이드카가 죽었거나 아직 뜨는 중이다. 이유=<운영체제 문구>` |
| 응답 머리가 어긋나거나 응답이 끝까지 안 옴 | 4 | `사이드카와 말이 안 통한다: <문구>`(4.2) |
| 인자가 64칸 초과, 칸 1개가 1 MiB 초과 | 1 | 스택 트레이스 |
| 요청을 쓰거나 응답을 읽는 중의 입출력 오류(끊긴 파이프, 연결 재설정) | 1 | 스택 트레이스 |
| plist를 못 읽거나 못 씀, `run/` 폴더 목록을 못 읽음 | 1 | 스택 트레이스 |

`이유=` 뒤는 JDK가 옮긴 운영체제 문구(`Connection refused` 같은 것)라 더욱 계약이 아니다. 응답이 중간에 끊긴 것을 읽는 쪽이 끝(EOF)으로 받으면 4이고, 연결 재설정 같은 입출력 오류로 받으면 1이다.

4는 「엔진에 못 닿았다」이고 3은 「엔진이 명령을 돌렸는데 실패했다」다. 앞은 다시 해 보거나 사람을 부를 일이고 뒤는 사용자에게 알릴 결과라서 같은 값으로 두지 않는다. 앱은 5를 1글자도 안 쓴 실패로 읽고, 종료 코드로 다시 할지를 가르는 자리(레일 대화 저장)에서는 4와 앱 다리의 시간 초과(음수 상태)와 다리 실패만 다시 해도 되는 실패로 본다(코드 읽기로 확인). 그래서 다시 짓는 `wl-cli`도 4와 5를 그대로 지킨다. 그 자리는 1을 다시 해도 같은 실패로 보아서, 엔진에 못 닿은 일이 1로 끝나면 다시 시도하지 않는다(3.8의 19번). 본문 자동저장은 종료 코드를 안 보고 실패하면 4초마다 다시 쓴다.

**시간 상한이 없는 자리.** `wl-cli`는 소켓 연결과 요청 쓰기와 응답 읽기에 시간 상한을 안 둔다. 생존 확인 연결도 같다. 엔진이 요청을 받고 매달리면 `wl-cli`도 그대로 기다리고, 그 호출을 끊는 것은 부르는 쪽의 상한뿐이다. 앱은 `wl-cli` 1번을 120초까지 기다린다(4.3).

**JVM 밖의 `~`와 uid.** 지금 `wl-cli`의 `~`는 JVM 속성 `user.home`이고, JVM은 그 값을 `HOME`이 아니라 운영체제 계정에서 얻는다(33.3). JVM이 아닌 `wl-cli`도 운영체제 계정의 홈 폴더를 `~`로 쓴다(32.4와 같다). launchd가 띄운 지금 엔진이 실행 상태 파일과 잠금 파일을 그 자리에 두어서, 같은 자리를 봐야 동시 상한과 다시 띄우기가 맞게 돈다. 계정 홈은 보통 `HOME`과 같아서 차이는 `HOME`을 바꿔 부른 때만 난다. uid는 `~` 폴더 주인의 uid를 먼저 쓰고, 못 읽으면 자기 프로세스의 uid를 쓴다. 지금 `id -u`가 내는 값이 그 값이다. uid는 launchctl을 부를 때마다 다시 읽는다.

## 3.4 LaunchAgent plist

`wl-cli`는 vault마다 LaunchAgent 1개를 둔다. launchd를 쓰는 까닭은 4가지다. 레이블이 인스턴스를 1개로 지키고, 엔진이 `wl-cli`나 앱의 자식이 아니라서 부모가 죽어도 고아가 안 생기고, 앱이 꺼져 있어도 엔진을 세울 수 있고, 종료 유예와 로그 받기를 launchd가 해 준다.

| 값 | 꼴 |
|---|---|
| 레이블 | `co.kcd.withlog.sidecar.<VaultKey>` |
| plist 자리 | `~/Library/LaunchAgents/<레이블>.plist` |
| launchd 도메인 | `gui/<uid>` |
| 로그 자리 | `~/Library/Application Support/withlog/logs/sidecar-<VaultKey>.log` |

레이블 머리 `co.kcd.withlog.sidecar.`는 정리하는 쪽이 거르는 계약이다. 같은 폴더에 리포트 잡(`co.kcd.withlog.morning` 같은 이름)이 살아서, 머리를 덜 보면 그것까지 건드리기 때문이다.

plist 바이트는 아래 꼴이다. 줄마다 LF로 끝나고 파일 끝에도 LF 1개가 있다. vault는 `/Users/me/vault`이고 홈은 `/Users/me`이며 나머지 경로도 「예시 값」이다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>co.kcd.withlog.sidecar.17dc9196931802ce-vault</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home/bin/java</string>
    <string>-jar</string>
    <string>/Users/me/Library/Application Support/withlog/bin/wl-sidecar.jar</string>
    <string>serve</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>WITHLOG_VAULT</key>
    <string>/Users/me/vault</string>
    <key>WITHLOG_SIDECAR_SOCKET</key>
    <string>/Users/me/Library/Caches/withlog/wl-17dc9196931802ce.sock</string>
  </dict>
  <key>RunAtLoad</key>
  <false/>
  <key>ExitTimeOut</key>
  <integer>25</integer>
  <key>StandardOutPath</key>
  <string>/Users/me/Library/Application Support/withlog/logs/sidecar-17dc9196931802ce-vault.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/me/Library/Application Support/withlog/logs/sidecar-17dc9196931802ce-vault.log</string>
</dict>
</plist>
```

| 자리 | 값 | 까닭 |
|---|---|---|
| `ProgramArguments` 1번째 | `WITHLOG_SIDECAR_JAVA`를 다듬은 값. 공백뿐이거나 없으면 `wl-cli`를 돌리는 JVM의 `<java.home>/bin/java` | launchd가 주는 `PATH`가 최소라서 `java`만 적으면 못 찾는다 |
| `ProgramArguments` 3번째 | `WITHLOG_SIDECAR_JAR`를 다듬은 값. 공백뿐이거나 없으면 설치본 `~/Library/Application Support/withlog/bin/wl-sidecar.jar`(일반 파일일 때만) | 빌드 산출물 자리는 빌드나 worktree 정리에 사라진다(3.5) |
| `ProgramArguments` 4번째 | `serve` | 엔진이 이 글자를 바꾸면 이미 설치된 plist가 단발 모드로 떠서 소켓을 안 열고, 아무도 못 붙는다 |
| `WITHLOG_VAULT` | vault를 `wl-cli`의 작업 폴더 기준 절대 경로로 바꾸고 정리한 글자 | launchd는 로그인 셸 환경을 안 물려준다 |
| `WITHLOG_SIDECAR_SOCKET` | 3.3 엔진 갈래의 2번에서 정한 소켓 경로 | 안 실으면 엔진이 제 규칙으로 자리를 정해서, 클라이언트가 덮은 자리와 갈리면 엔진은 떠 있는데 아무도 못 붙는다 |
| `RunAtLoad` | `false` | 켜도 첫 로그인 1번만 이득이고, 유휴 종료 뒤에는 어차피 필요할 때 띄운다 |
| `KeepAlive` | 키 없음 | 그냥 켜면 0으로 끝난 엔진도 launchd가 10초 간격으로 끝없이 되살린다. `{SuccessfulExit: false}`로 좁히면 0의 되살림은 막지만, 실패 종료의 되살림에 상한이 없다. 3.2의 「0으로 끝낸다」는 이 좁힌 설정을 가정한 까닭이다 |
| `ExitTimeOut` | `25` | 코드에 남은 기록으로는 안 주면 SIGTERM에서 SIGKILL까지 약 5초였고, 엔진이 연결을 기다리고 커밋하고 흔적을 지울 시간이 모자란다 |
| `StandardOutPath`, `StandardErrorPath` | 같은 로그 파일 | serve 모드는 stdout에 아무것도 안 쓰고 엔진 로그는 stderr로 간다 |

글자는 `&`, `<`, `>`만 이 차례로 `&amp;`, `&lt;`, `&gt;`로 바꾸고, 따옴표와 그 밖의 글자는 그대로 쓴다. 폴더 이름의 `&` 1개가 plist 전체를 깨면 bootstrap이 어느 글자 때문인지 안 알려 주고 실패하기 때문이다. 줄바꿈과 탭도 그대로 들어간다. XML 1.0에 넣을 수 없는 제어 글자(U+0001 같은 것)가 든 경로는 launchctl이 plist를 못 읽을 것으로 보이나 재지 않았다. `WITHLOG_SIDECAR_JAVA`와 `WITHLOG_SIDECAR_JAR`는 다듬은 글자를 상대 경로든 없는 파일이든 확인 없이 그대로 싣는다. 설치본을 쓰는 판정은 그 자리가 일반 파일인지이고, 심볼릭 링크를 따라간다.

파일은 UTF-8로 쓰고 원자적 쓰기가 아니다. `wl-cli`는 이 파일을 엔진을 띄워야 할 때만 쓰고, 디스크의 글자와 다를 때만 쓴다(3.3 띄우기의 2번). 매번 쓰면 수정 시각으로 설치 시점을 못 보고, 쓸 때마다 bootout이 따라와 붙어 있던 엔진을 내리기 때문이다. `doctor --plist`는 지금 환경으로 지을 본문을 쓰지 않고 보여 준다(3.6).

로그 폴더 `logs/`는 `wl-cli`가 만들지 않는다. 폴더가 없을 때 launchd가 어떻게 하는지는 재지 않았다. 로그 줄의 꼴은 계약이 아니다.

**JVM이 아닌 구현.** 지금 `wl-cli`가 쓰는 plist는 엔진을 `<자바> -jar <jar> serve` 4칸으로 띄우고, vault와 소켓 자리를 환경변수 2개로만 준다. 그래서 무엇을 다시 짓느냐에 따라 지킬 것이 다르다.

| 다시 짓는 것 | 지킬 것 |
|---|---|
| 엔진만. 지금 `wl-cli`와 짝지음 | 엔진이 argv `<자바 자리> -jar <jar 자리> serve`로 serve 모드가 떠야 한다. JVM이 아니면 `WITHLOG_SIDECAR_JAVA`에 엔진 실행 파일이나 감싸는 스크립트를 주고, 그것이 앞 2칸(`-jar`와 jar 자리)을 건너뛰고 `serve`를 받게 짓는다. `WITHLOG_SIDECAR_JAR`에는 아무 경로나 줘도 되지만, 그 파일이 있으면 수정 시각이 다시 띄우기 판정(3.3)에 쓰인다 |
| `wl-cli`도 | `ProgramArguments`는 다시 지은 엔진을 serve 모드로 띄우는 argv면 되고 `-jar` 꼴은 계약이 아니다. 자바 기본값과 「지금 도는 `wl-cli` jar」 같은 원본 후보(3.5)도 JVM 구현만의 규칙이다. 다만 같은 기기에서 지금 구현과 섞여 돌 수 있어서, 레이블, plist 자리, 환경변수 2개, `RunAtLoad` 거짓, `KeepAlive` 없음, `ExitTimeOut` 25, 로그 자리, `doctor --prune`이 읽는 `<key>WITHLOG_VAULT</key>` 다음 줄 꼴(3.6)은 지키는 편이 안전하다 |

## 3.5 상한, 청소, 설치

엔진은 다른 vault의 엔진을 모른다. 그래서 엔진 개수와 유령을 다루는 일은 `wl-cli`가 실행 상태 파일(3.2)을 읽어서 한다(코드 읽기로 확인).

**살아 있는지.** 실행 상태 파일의 `pid`를 못 읽었으면 살아 있지 않다. 읽었으면 JDK의 프로세스 조회로 그 pid가 운영체제 프로세스 표에 있는지 본다. JDK의 macOS 구현은 이 조회를 sysctl로 한다고 알려져 있고, 이 저장소에서 재지 않았다. 그래서 권한과 상관없이 다른 사용자의 프로세스도 산 것으로 보고, 좀비도 표에 남은 동안은 산 것으로 보일 수 있다. 그 pid가 엔진이라는 보장은 없어서 단서로만 쓰고, 내릴 때는 늘 레이블로 내린다. 동시 상한, 하루 청소, `sweep`, `doctor`가 모두 이 판정을 쓴다.

**동시 상한 3.** 엔진을 새로 띄우기 직전(3.3 띄우기의 3번)에만 돈다. 이미 붙는 vault를 부를 때는 이 비용이 안 붙는다.

1. `run/` 폴더에서 이름이 `.json`으로 끝나는 파일을 이름 차례로 읽는다. 이름 차례는 UTF-16 단위의 차례이고, vault 키가 ASCII라서 바이트 차례와 같다. 폴더가 없으면 아무것도 안 한다. 폴더 목록을 못 읽으면 예외로 죽어 종료 코드 1이다.
2. 지금 띄우려는 vault의 키와 이름이 같은 것을 뺀다.
3. 살아 있지 않은 것을 뺀다. `pid`를 못 읽은 파일도 여기서 빠진다.
4. 남은 수가 「상한에서 1을 뺀 수」보다 많으면 그 차이가 내릴 수 n이다. 아니면 아무것도 안 한다.
5. `openConnections`가 1 이상인 것을 뺀다. 모르면 0으로 본다.
6. `lastActiveAt`이 오래된 차례로 늘어놓고(모르면 맨 뒤, 같으면 1번의 이름 차례) 앞의 n개를 고른다.
7. 고른 것마다 `launchctl bootout gui/<uid>/<그 레이블>`을 부르고 stderr에 아래 1줄을 쓴다. launchctl이 돌았으면 1번째 꼴이고, 못 돌았거나 10초를 넘겼으면 2번째 꼴이다. 실패해도 계속 간다.

```text
사이드카 동시 상한 <상한>개를 지키려고 가장 오래 조용했던 것을 내린다: <레이블> (마지막 활동 <얼마 전>, bootout rc=<launchctl의 종료 코드>)
사이드카 동시 상한 <상한>개를 지키려고 가장 오래 조용했던 것을 내린다: <레이블> (마지막 활동 <얼마 전>, bootout 실패: <launchctl 글>)
```

레이블은 실행 상태 파일 이름에서 짓는다. 경로에서 키를 다시 지으면 정규화 규칙이 1번이라도 바뀌는 날 남의 레이블을 내리기 때문이다. 상한은 환경변수 `WITHLOG_SIDECAR_LIMIT`의 양의 정수이고, 없거나 틀리면 3이다. 0을 「끈다」로 안 읽는 까닭은, 「1개도 못 띄운다」로 읽히면 호출마다 남의 엔진을 내리기 때문이다. 모두 연결이 열려 있어서 못 내리면 상한을 넘겨서라도 띄운다. 자리를 못 비운 것이 사용자의 호출을 막을 까닭은 아니라고 본 규칙이다. 손으로 띄운 엔진은 레이블이 없어 bootout이 실패하고 그대로 돈다.

**「얼마 전」 글.** 상한, 청소, `doctor`가 함께 쓰는 글이다. 못 읽은 것과 방금을 사람이 가를 수 있게 0초로 메우지 않는다.

| 값 | 글 |
|---|---|
| 모름 | `(모름)` |
| 지금보다 뒤의 시각(미래). 1나노초라도 뒤면 해당한다 | `(시각이 미래다: <그 순간>)`. `<그 순간>`은 읽은 시각을 UTC ISO 꼴로 다시 적은 글이고, 초 아래는 필요한 만큼 0, 3, 6, 9자리다 |
| 1분 미만 | `<초>초 전` |
| 1시간 미만 | `<분>분 전` |
| 1일 미만 | `<시간>시간 전` |
| 그 밖 | `<일>일 전` |

수는 모두 내림이다. 59.9초 전은 `59초 전`이다.

**하루 청소.** 오래 조용한 엔진을 내리는 마지막 그물이다. 사람이 정리 명령을 안 불러도 돌게 하려고 엔진 갈래의 호출 끝에 붙였다.

| 판정 | 규칙 |
|---|---|
| 도는 때 | 엔진 갈래가 응답을 다 흘린 뒤, 마지막 청소 뒤로 24시간 이상이 지났을 때. 시각 파일이 없거나 못 읽으면 지난 것으로 본다. 시각 파일이 미래면 그 시각이 지나 24시간이 될 때까지 안 돈다 |
| 시각 파일 | `~/Library/Caches/withlog/last-sweep`. UTC ISO 순간(초 아래는 필요한 만큼 0, 3, 6, 9자리)과 LF 1개. 읽을 때는 다듬고 ISO 순간으로 읽어서 LF나 앞뒤 공백이 없어도 받는다. 폴더가 없으면 쓸 때 만든다 |
| 대상 | 지금 vault가 아니고, `openConnections`가 0이고(모르면 0), `lastActiveAt`을 읽었고, 그 뒤로 조용한 시간이 문턱 이상인 것. 살았는지는 안 본다 |
| 문턱 | `WITHLOG_SWEEP_QUIET_HOURS`의 양의 정수 시간. 없거나 틀리면 24시간 |
| 하는 일 | `launchctl bootout`. 내리기 직전에 살아 있지 않았으면 실행 상태 파일도 지운다 |

자동 청소는 시각 파일을 먼저 쓰고 일한다. 거꾸로 하면 청소가 어딘가에서 걸릴 때 호출마다 다시 시도하고, launchctl 1번이 최대 10초라서 `wl-cli` 전체가 느려지기 때문이다. 자동 청소는 아래 글을 stderr에만 쓰고 종료 코드를 안 바꾼다. 대상이 없으면 아무것도 안 쓴다.

```text
<문턱>시간 넘게 조용한 사이드카 <n>개를 내린다.
  내렸다: <레이블> (bootout rc=<코드>)
    죽은 흔적을 지웠다: <파일 이름>
```

2번째 줄은 대상마다 서고, launchctl이 못 돌았으면 `(bootout 실패: <launchctl 글>)` 꼴이다. 3번째 줄은 살아 있지 않았던 대상의 파일을 실제로 지웠을 때만 선다. 시각 파일을 못 쓰면 `청소 시각을 못 남겼다: <경로> (<문구>)`를 쓰고, 그 밖의 실패는 `하루 한 번 청소가 실패했다: <문구>` 1줄로 삼킨다. 엔진 갈래가 6번부터 8번에서 실패해 종료 코드 4나 1로 끝난 호출에서는 자동 청소가 안 돈다.

마지막 활동을 모르는 것을 안 건드리는 까닭은 청소에는 자리를 비울 의무가 없고, 안 내려서 생기는 손해는 엔진 1개가 더 도는 것뿐이기 때문이다. 살아 있는 엔진의 실행 상태 파일은 안 지운다. 그 엔진이 bootout의 종료 신호를 받고 스스로 지우는데, 함께 지우면 서로 경합하기 때문이다.

**`wl-cli sweep`.** `wl-cli sweep [--dry-run]`은 같은 판정을 손으로 부른다. `--dry-run` 글자가 argv에 있는지만 보고, 다른 칸은 무시한다. `WITHLOG_VAULT`가 없거나 공백뿐이어도 돌고, 그때는 뺄 vault가 없다. stdout에 아래 꼴을 쓴다.

```text
<문턱>시간 넘게 조용한 사이드카 <n>개
  <레이블>
    vault=<vault 또는 (못 읽음)>  마지막 활동 <얼마 전>  (<그 pid 가 돈다 또는 그 pid 로 도는 것이 없다>)
```

2번째와 3번째 줄은 대상마다 선다. `--dry-run`이면 stdout에 `  아직 안 내렸다. 진짜 내리려면 --dry-run 를 뺀다.`를 더 쓰고 아무것도 안 바꾼다. 아니면 대상마다 내리고 stderr에 자동 청소와 같은 2번째와 3번째 줄을 쓴 뒤 시각 파일을 쓴다. 손으로 돌린 것도 시각을 찍어서 바로 다음 호출이 같은 일을 또 하지 않는다. 종료 코드는 보통 0이다. 부르는 쪽이 스케줄 잡이라서, 청소 실패로 그 잡이 실패하면 진짜 할 일이 막히기 때문이다. 다만 `run/` 폴더 목록을 못 읽는 입출력 오류와 넘치는 문턱 값(3.8의 22번)은 잡지 않아 종료 코드 1이다.

**설치.** `wl-cli install [--dry-run] [--cli <경로>] [--sidecar <경로>]`는 jar 2개를 `~/Library/Application Support/withlog/bin/`에 둔다. plist가 jar의 절대 경로를 글자로 들고 있어서, 빌드 산출물 자리를 박으면 `clean`이나 worktree 정리 뒤에 그 레이블이 조용히 안 뜨기 때문이다. 코드에 남은 기록으로는 실제로 지운 worktree를 가리키는 plist가 있었다. `WITHLOG_VAULT`는 안 본다.

깃발은 argv의 어디에 와도 되고 차례를 안 본다. 같은 깃발을 여러 번 주면 처음 것이 이긴다. 모르는 깃발과 남는 칸은 무시한다. `--cli`와 `--sidecar` 다음 칸은 다듬어서 비었거나 `--`로 시작하면 「경로가 없다」로 선다.

| 원본 | 고르는 차례 |
|---|---|
| `wl-cli.jar` | `--cli` 다음 칸, 다듬은 `WITHLOG_CLI_JAR`(공백뿐이면 없음), 지금 도는 `wl-cli` jar의 경로가 `<뿌리>/wl-cli/build/libs/<이름>.jar` 모양이면 그것, `<작업 폴더>/withlog-backend/wl-cli/build/libs/wl-cli.jar`와 `<작업 폴더의 부모>/withlog-backend/wl-cli/build/libs/wl-cli.jar` 중 일반 파일인 첫 것 |
| `wl-sidecar.jar` | `--sidecar` 다음 칸, 다듬은 `WITHLOG_SIDECAR_JAR`(공백뿐이면 없음), `wl-cli.jar` 원본이 `<뿌리>/wl-cli/build/libs/<이름>.jar` 모양이면 `<뿌리>/wl-sidecar/build/libs/wl-sidecar.jar` |

앞의 후보가 정해지면 그것이 파일이 아니어도 다음 후보로 안 넘어간다. 그래서 `--cli`에 없는 파일을 주면 아래 3번에서 선다.

1. 깃발 다음 칸이 없으면 `<깃발> 뒤에 경로가 없다.`이고 종료 코드 2다.
2. 원본을 못 정하면 아래 글 가운데 1가지와 종료 코드 2다. `wl-cli.jar`를 먼저 정하고 `wl-sidecar.jar`를 다음에 정한다.
3. 원본 2개가 모두 일반 파일인지 `wl-cli.jar`부터 본다. 아니면 처음 걸린 원본의 절대 경로로 `원본 jar 가 없다: <경로>. 먼저 빌드한다(`pnpm backend:jars`).`이고 종료 코드 2다. 1개만 바뀐 채 성공처럼 끝나면 jar 2개의 프레임 규약이 갈려도 밖에서 모르기 때문이다.
4. `--dry-run`이면 무엇을 복사할지 stdout에 쓰고 종료 코드 0이다.
5. 폴더를 만들고 `wl-cli.jar`, `wl-sidecar.jar` 차례로 깐다. 원본을 같은 폴더의 `wl-cli.jar.installing`(또는 `wl-sidecar.jar.installing`)에 복사한 뒤, 원자적 이름 바꾸기로 대상을 덮고, 임시 파일은 끝에 지운다. 복사나 이름 바꾸기가 실패하면 예외로 죽어 종료 코드 1이고, 그때는 먼저 깐 jar만 바뀌었을 수 있다.
6. 설치한 자리와 크기를 stdout에 쓰고 종료 코드 0이다.

```text
원본 wl-cli.jar 을 못 찾았다. 저장소에서 `pnpm backend:jars` 를 돌린 뒤 그 자리에서 부르거나, --cli 로 절대 경로를 준다.
  지금 도는 jar: <경로 또는 (모름)>
  작업 폴더: <작업 폴더>
--sidecar 를 줘야 한다. <wl-cli.jar 원본의 절대 경로> 가 빌드 산출물 모양이 아니라 짝을 못 찾는다. 빌드 산출물 모양은 `<뿌리>/wl-cli/build/libs/*.jar` 다.
```

위는 2번의 글이다. 앞의 3줄이 `wl-cli.jar`를 못 정했을 때이고, 마지막 1줄이 `wl-sidecar.jar`를 못 정했을 때다. 아래는 4번과 6번의 stdout이다. `<크기>`는 쉼표 없는 10진 바이트 수이고, 4번은 원본의 크기를, 6번은 깐 파일의 크기를 적는다.

```text
# (dry-run) 아무것도 안 바꿈 — 복사될 것 미리보기
# 자리: <폴더>
  wl-cli.jar  <크기> 바이트  ← <원본>
  wl-sidecar.jar  <크기> 바이트  ← <원본>
```

```text
✓ jar 둘을 설치함
  자리: <폴더>
  wl-cli.jar  <크기> 바이트  ← <원본>
  wl-sidecar.jar  <크기> 바이트  ← <원본>
  래퍼와 plist 가 이 자리를 박게 하려면 `schedule on` 을 한 번 돌린다.
```

모든 글은 줄마다 LF로 끝나고, 사람용이라 계약이 아니다. 이름 바꾸기로 덮는 까닭은 도는 엔진이 옛 파일을 연 채로 살아 있게 하려는 데 있다. 제자리 덮어쓰기는 도는 JVM을 깨뜨린다. 설치 뒤 첫 엔진 갈래 호출은 jar의 수정 시각이 바뀐 것을 보고 엔진을 다시 띄운다(3.3). 원자적 교체를 재는 검사는 엔진 저장소에도 없어서 이 규칙은 코드 읽기로만 확인했다. 「지금 도는 `wl-cli` jar」와 빌드 산출물 자리 같은 원본 후보는 JVM 구현만의 규칙이고, 다시 짓는 `wl-cli`는 제 산출물에 맞는 후보를 정해도 된다.

## 3.6 `doctor`

`wl-cli doctor [--plist] [--prune [--dry-run]]`는 이 vault의 엔진 상태를 사람이 읽게 stdout에 쓴다. `--prune`이 아니면 아무것도 안 바꾼다. plist, 소켓, 실행 상태, 로그가 `~/Library` 아래 4곳에 흩어져 있어서, 사람이 손으로 대조하면 반드시 빠뜨리는 곳이 생기기 때문이다.

**깃발.** 깃발은 argv에 그 글자가 있는지만 보고 차례를 안 본다. 모르는 칸은 무시한다. `--dry-run`은 `--prune`과 함께일 때만 뜻이 있고, 혼자면 아무 일도 안 한다. `--plist`와 `--prune`을 함께 주면 진단 뒤에 plist 본문을 먼저 쓰고 그다음 정리를 한다.

**종료 코드.** 진단에 나쁜 소식이 담겨도 0이다. 이 명령을 부르는 때가 이미 무언가 잘못된 때라서, 0이 아닌 값을 주면 부르는 스크립트가 진단을 못 읽고 먼저 서기 때문이다. 예외는 아래와 같다.

| 조건 | 종료와 stderr | stdout |
|---|---|---|
| `WITHLOG_VAULT`가 없거나 공백뿐 | 2와 3.3의 `WL-400` 줄 | 아무것도 안 나간다 |
| 소켓 경로가 102바이트를 넘음 | 2와 3.3의 `WL-400` 줄 | 아무것도 안 나간다 |
| `--plist`인데 엔진 실행 파일 자리를 못 정함 | 2와 3.3 띄우기 1번의 `WL-400` 줄 | 진단 줄은 모두 이미 나갔다 |
| `--prune`의 bootout에서 launchctl을 못 돌리거나 10초를 넘김 | 4와 launchctl 글 1줄 | 그 대상의 `  <레이블>  vault=<vault>` 줄까지는 이미 나갔다. 그 대상의 plist와 남은 대상은 손대지 않는다 |
| uid를 못 읽음 | 4와 3.3의 uid 글(`id`를 못 돌렸으면 `id 를 못 돌렸다: …`) | 커밋 줄 앞까지의 줄 |
| 그 밖의 입출력 오류 | 1과 스택 트레이스 | 그 앞까지의 줄 |

uid는 커밋 줄에 실을 다시 띄우는 명령을 지으려고 늘 읽는다. 출력 글은 사람용이라 계약이 아니고, 다른 부품이 이 출력을 기계로 읽지 않는다(코드 읽기로 확인). 이 절은 줄의 차례와 뜻을 정한다.

**vault git 줄.** vault 바로 아래에 `.git` 폴더가 없으면 `git 저장소가 아니다. 자동 커밋이 안 돈다`다. 있으면 `마지막 자동 커밋 <얼마 전> (<짧은 커밋> <제목>)  커밋 밖 <n>개`이다. 마지막 자동 커밋은 vault의 HEAD에서 거슬러 올라가며 저자 칸에 `withlog-auto`가 드는 첫 커밋이고(git의 `--author` 맞추기), 시각은 그 커밋을 만든 시각(committer 시각)이다. 커밋 밖 수는 `git status --porcelain --untracked-files=all`에서 `*.tmp`를 뺀 줄 수라서, 추적 안 하는 폴더 안의 파일을 1개씩 센다. 이 절의 git은 `PATH`의 `git`을 vault에서 `--no-optional-locks`를 붙여 5초 상한으로 돌린다. 읽기만 하는 진단이 `index.lock`을 남겨 자동 커밋을 막으면 안 되기 때문이다. git이 없거나 실패하거나 5초를 넘기면 앞 값은 `자동 커밋이 아직 없다`, 뒤 값은 `커밋 밖 (못 쟀다)`가 된다.

`vault git` 아랫줄은 아래 차례에서 처음 맞는 1줄이다. 엔진의 자동 커밋이 건너뛰는 갈래(31.2)와 같은 차례로 본다. HEAD를 못 읽으면 3번째와 4번째 줄은 안 선다.

```text
⚠ .git/index.lock 이 있다(<얼마 전>에 생겼다). 자동 커밋과 되돌리기가 이것에 막힌다. 오래된 잠금은 사이드카가 다음 커밋 때 지운다
⚠ vault 에서 병합이나 리베이스가 진행 중이다. 끝날 때까지 자동 커밋을 건너뛴다
⚠ vault 의 HEAD 가 브랜치가 아니다(detached). main 으로 돌아올 때까지 자동 커밋을 건너뛴다
⚠ vault 의 HEAD 가 main 이 아니다(<브랜치>). 돌아올 때까지 자동 커밋을 건너뛴다
```

2번째 줄은 `.git` 아래에 `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` 중 1개라도 있을 때다. `<브랜치>`는 HEAD가 가리키는 이름에서 `refs/heads/`를 뗀 글자다.

**`plist 사이드카` 아랫줄.** 파일이 없으면 `⚠ 그 파일이 지금 없다. 다음에 뜰 때 실패한다`다. 엔진이 살아 있고 파일 수정 시각이 `startedAt`보다 뒤면 inode로 3가지를 가른다. 지금 경로의 inode와 그 pid가 연 파일의 inode가 같으면 「제자리에서 덮어써졌다」(⚠, 도는 JVM이 깨진다)이다. 다르면 「새 파일로 바뀌었다」(⚠ 없음, 안 깨지지만 도는 코드가 낡았다)이고, 못 읽으면 「바뀌었다」(⚠)다. 연 파일의 inode는 `/usr/sbin/lsof -p <pid> -Fni` 출력에서 경로가 글자 그대로나 실제 경로로 같은 줄의 inode다. 이 lsof는 출력을 끝까지 읽은 뒤에야 5초 상한을 걸어서, 출력을 안 닫고 매달린 lsof 앞에서는 `doctor`도 함께 기다린다(3.8의 30번). 3가지 모두 다시 띄우는 명령 `launchctl kickstart -k gui/<uid>/<레이블>`을 함께 적는다. inode로 가르는 까닭은 `install`의 원자적 교체는 안전한데 수정 시각만 보면 경고가 떠서, 거짓 경고가 진짜 경고를 안 읽게 만들기 때문이다. `사이드카 jar` 줄과 `plist 사이드카` 줄이 다른 파일을 가리키면 그 사실을 짚는 2줄이 더 선다.

**커밋 줄.** 주체는 4개이고 이 차례로 선다.

| 주체 | 빌드 커밋을 읽는 자리 |
|---|---|
| `이 사이드카` | 엔진이 살아 있으면 실행 상태 파일의 `builtCommit`, 아니면 plist가 띄울 jar 안의 도장 |
| `도는 wl-cli` | 지금 도는 `wl-cli` jar 안의 도장 |
| `설치본 wl-cli` | `bin/wl-cli.jar` 안의 도장 |
| `설치본 사이드카` | `bin/wl-sidecar.jar` 안의 도장 |

도장은 jar 안의 `META-INF/wl-build-commit.txt`(빌드한 HEAD 40자)와 `META-INF/wl-watched-paths.txt`(그 jar에 오르는 소스 폴더 목록, 줄마다 1개)다. HEAD는 `doctor`를 부른 작업 폴더에서 `git rev-parse HEAD`로 읽는다.

| 판정 | 조건(위에서부터 처음 맞는 것) | 줄 |
|---|---|---|
| 저장소 없음 | HEAD를 못 읽었다 | `<주체> 커밋   (못 쟀다 — 이 명령을 git 저장소 밖에서 돌렸다: <작업 폴더>)` |
| 빌드 모름 | 빌드 커밋이 없다 | `<주체> 커밋   (모른다 — 빌드 커밋 정보가 없다. 구버전이거나 그 jar 를 못 찾았다)` |
| 최신 | 빌드 커밋과 HEAD가 같다 | `<주체> 커밋   <HEAD 앞 7자>  (최신 — 지금 HEAD 로 빌드됐다)` |
| 다른 저장소 | 그 저장소가 빌드 커밋을 모른다(`git cat-file -e <커밋>^{commit}` 실패) | `<주체> 커밋   (못 쟀다 — <작업 폴더> 는 이 jar 를 빌드한 저장소가 아니다)`와 안내 1줄 |
| 문서만 | jar에 감시 폴더 목록이 있고, 그 가운데 1개 이상이 HEAD에 폴더로 있고, 커밋 2개 사이에 감시 폴더의 차이가 없다(`git diff --quiet`. 각 폴더의 `src/test`, `src/testFixtures`는 뺀다) | `<주체> 커밋   <빌드 앞 7자>  (HEAD 는 <HEAD 앞 7자> 이지만 이 jar 에 오르는 파일은 지금 HEAD 와 같다 — 재빌드 안 해도 된다)` |
| 낡음 | 그 밖. 못 잰 것도 여기 든다 | `⚠ <주체> 는 커밋 <빌드 앞 7자> 로 빌드됐는데, 지금 저장소 HEAD 는 <HEAD 앞 7자> 이다.`와 2줄, 엔진 주체면 다시 띄우는 명령 1줄 |

**4부 조각.** 4부가 든 판에서만 `vault git` 줄과 `사이드카 jar` 줄 사이에 2줄이 선다. `wl-agent 소켓  <경로>  (<소켓 상태>)`와 `wl-agent 로그  <경로>  (<있음 또는 없음>)`이다. 소켓은 `WITHLOG_AGENT_SOCKET`이 공백뿐이 아니면 그 값을 다듬어 정리한 절대 경로이고, 아니면 `~/Library/Caches/withlog/wl-agent-<해시 16자>.sock`이다. 로그는 그 소켓 이름 끝의 `.sock`을 떼고 `.log`를 붙인, 같은 폴더의 파일이다. 지금 `wl-cli`는 4부 모듈이 실행 파일에 들어 있을 때만 이 2줄을 찾아서, 1부만으로 지은 판에서는 아무 줄도 안 나온다(32.4).

**`--plist`.** 진단 줄 뒤에 빈 줄, `이 값으로 plist 를 쓴다 (아직 안 썼다)`, 지금 환경으로 지은 plist 본문(3.4), 빈 줄 1개를 쓴다. 본문이 LF로 끝나는데 줄로 한 번 더 써서 빈 줄이 생긴다. 파일은 안 쓴다.

**`--prune`.** vault 폴더가 사라진 LaunchAgent를 내리고 plist를 지운다. 기준은 그 1가지이고, 「사라졌다」는 plist에서 읽은 vault 자리가 폴더가 아니라는 뜻이다. 그 자리에 일반 파일이 있어도 대상이다. 지금 vault의 레이블은 늘 빼고, plist에서 vault를 못 읽은 것도 대상이 아니다. 설계 초안의 기준이던 「최근 워크스페이스 목록에 없는 것」을 안 쓰는 까닭은 그 목록이 앱 화면의 브라우저 저장소에 살아서 `wl-cli`가 못 읽기 때문이다.

출력은 빈 줄 1개로 시작한다. 대상이 없으면 `정리할 것이 없다. vault 폴더가 사라진 에이전트가 0개다.`를 쓰고 끝난다. 있으면 `정리 <n>개`(`--dry-run`이면 `정리 대상 <n>개 (아직 안 지웠다)`)와 대상마다 `  <레이블>  vault=<vault>`를 쓴다. `--dry-run`이 아니면 대상마다 bootout을 부르고 `    bootout rc=<코드>`와 `    plist 지웠다: <경로>`(또는 `못 지웠다`)를 쓴다. plist를 못 지워도 종료 코드는 그대로다. `--dry-run`이면 `  진짜 지우려면 --dry-run 를 뺀다.`를 쓰고, 끝에 늘 `  잠금 파일(.lock)은 안 지운다. 크기 0 이라 해가 없고, 지우면 잠금이 갈린다.`를 쓴다.

plist에서 vault는 `<key>WITHLOG_VAULT</key>`를 품은 첫 줄 다음의, 공백뿐이 아닌 첫 줄을 다듬은 글이 통째로 `<string>…</string>`일 때 그 안의 글자이고, `&lt;`, `&gt;`, `&amp;`를 이 차례로 되돌린다. 다른 모양이면 못 읽은 것으로 본다. XML 파서를 안 싣는 대신 모양이 다르면 답을 안 내서, 추측으로 남의 plist를 지우지 않으려는 규칙이다.

**다시 짓는 `doctor`가 낼 것.** 지킬 것은 종료 코드 규칙과 `--prune`이 지우는 대상의 규칙 2가지다. 줄의 꼴과 차례는 따르기를 권하는 정도이고 계약이 아니다. 커밋 줄 4개, `plist 사이드카` 아랫줄의 inode 판정, jar 줄 2개를 짚는 2줄은 엔진을 jar로 짓는 지금 저장소에 매인 진단이다. 그래서 다시 지은 산출물에 맞는 진단으로 바꾸거나 빼도 된다. 다른 부품이 기대는 것은 실행 상태 파일의 `builtCommit` 칸뿐이고, 지금 `doctor`가 그 칸으로 도는 엔진의 커밋을 적는다.

## 3.7 모드 경합

단발 모드는 serve 모드의 잠금을 안 본다. 그래서 같은 vault에 serve 모드 엔진 1개와 단발 모드 엔진 여럿이 함께 돌 수 있다. 단발 모드가 잠금을 안 잡는 까닭은 코드에 적혀 있지 않다.

| 자리 | 함께 돌 때 일어나는 일 | 근거 |
|---|---|---|
| vault 파일 | 프로세스 사이에 쓰기 잠금이 없다. 선결 조건 토큰(7.2)이 노트 파일의 덮어쓰기를 잡지만, 대조와 쓰기 사이는 원자적이지 않다 | 코드 읽기로 확인 |
| 색인 DB | `db.home`이 같으면 같은 파일을 WAL 모드와 잠금 대기 5초로 함께 연다. 동시 읽기는 맞아야 한다 | 동시 읽기는 묶음이 잰다. 쓰기끼리의 경합은 재지 않았다 |
| `db.home`이 다름 | 색인이 2벌로 갈라져 서로의 쓰기를 모른다. 쓰기 명령은 일하기 전에 제 색인을 디스크에 맞추고(8.3) 읽기는 안 맞춘다 | 코드 읽기로 확인 |
| 스키마 올리기 | 프로세스마다 뜰 때 돈다. 이미 최신이면 맞대기만 한다. 새 색인을 여러 프로세스가 동시에 처음 올릴 때는 재지 않았다 | 코드 읽기로 확인 |
| vault git | 단발 모드의 쓰기는 serve 모드 엔진의 쓴 쪽 기록에 없다. 다음 serve 커밋이 `git add -A`로 그 변경까지 담고, 꼬리 줄의 쓴 쪽은 serve 모드 엔진이 기억한 쪽이나 `outside`가 된다(31.3) | 코드 읽기로 확인 |
| 실행 상태, 잠금, 소켓 | 단발 모드는 안 건드린다 | 코드 읽기로 확인 |

launchd가 띄운 엔진은 plist에 적힌 `WITHLOG_*` 2개만 받는다. 그래서 셸에서 단발 모드에 준 `--withlog.db.home`이나 `WITHLOG_DB_HOME`이 serve 모드 엔진에는 없고, 묶음과 1부 실행 스크립트처럼 색인 자리를 따로 주는 단발 실행은 앱이 쓰는 색인을 안 건드린다.

serve 모드 엔진끼리는 잠금이 막는다. 잠금 자리는 vault 키에만 매여서, 소켓 자리가 달라도 같은 vault면 2번째 엔진은 종료 코드 0으로 내려간다. 그 결과 아래 2가지에서 아무도 소켓을 안 여는 때가 생긴다. 2가지 모두 코드에서 읽은 길이고 재지 않았다.

- 손으로 띄운 엔진이 다른 소켓 자리로 잠금을 쥔 동안 `wl-cli`가 기본 자리로 엔진을 띄우면, 새 엔진이 곧바로 내려가고 `wl-cli`는 30초를 기다린 뒤 종료 코드 4로 끝난다.
- 엔진이 내려가는 동안(3.2 내려가는 차례의 1번부터 5번까지)에는 소켓 파일이 이미 없다. 그때 온 `wl-cli`가 kickstart를 부르면, launchd는 아직 도는 옛 프로세스를 보고 새 프로세스를 안 띄울 수 있다. 그러면 `wl-cli`는 30초를 기다리다 종료 코드 4로 끝난다. bootout으로 내려가는 동안 새 프로세스가 뜨면 그 프로세스는 잠금을 못 잡고 곧바로 내려가서 결과가 같다.

같은 폴더라도 경로 글자가 다르면 vault 키가 달라져서 잠금, 소켓, 색인, 레이블이 모두 2벌이 되고 잠금이 서로를 못 막는다(33.4).

## 3.8 얼어 있는 특이점

다시 지을 때 지킬지 고칠지는 부록 D에서 정한다.

1. vault 문턱은 글자 그대로의 `--withlog.vault=`만 보는데 값 고르기는 느슨한 이름을 받는다(33.1). 그래서 `--WITHLOG.VAULT=/v`만 주면 「환경변수가 없다」로 종료 코드 2이고, `WITHLOG_VAULT`와 함께 주면 그 값이 환경변수를 이긴다.
2. 모르는 명령의 안내는 도구를 읽기 도구 12개만 적는다. `list_comments`, 쓰기 도구 15개, `plan_day`는 있는 도구인데 목록에 없다(갈래는 부록 B).
3. 명령 처리 중 예상 밖 예외는 단발 모드에서 WL 줄 없는 종료 코드 1이고, serve 모드에서는 상태 3과 오류 코드 0이며 stderr가 1줄뿐이다(4.3). 엔진이 못 뜨는 실패는 모드 2가지 모두 종료 코드 1이다. serve 모드에서 그렇게 되면 소켓이 안 열려서, `wl-cli`는 30초를 기다린 뒤 종료 코드 4로 끝난다. 종료 코드 1은 실행해 재지 않았다.
4. 혼자 선 `--` 뒤의 설정 칸은 설정으로도 인자로도 안 쓰이고 조용히 사라진다.
5. 같은 설정을 2번 주면 쉼표로 이어져서, `--withlog.vault=`를 2번 주면 쉼표가 든 경로를 찾다 그런 폴더가 없으면 엔진이 못 뜬다.
6. 빈 `--withlog.vault=`는 문턱을 지나고 환경변수까지 이긴 뒤 빈 값이라 엔진이 못 뜬다.
7. 단발 모드 stdout의 인코딩이 로캘을 탄다. UTF-8이 아닌 로캘에서 한글이 깨지는지는 재지 않았고, 다시 짓는 구현은 늘 UTF-8로 쓴다(3.1).
8. 단발 모드는 vault 경로가 든 로그 줄을 WL 줄보다 먼저 써서, 경로에 `WL-`와 숫자 3자리 꼴이 든 vault에서는 「처음 나오는 `WL-` 번호」가 엉뚱한 글자가 된다.
9. 실행 상태 파일을 밖에서 지우면 값이 바뀔 때까지 안 돌아온다.
10. `startup` 커밋은 소켓을 열기 전이라서, 그 시간이 `wl-cli`의 30초 기다림을 깎아 먹는다. 밀린 변경이 많은 vault의 첫 호출은 그만큼 종료 코드 4에 가까워진다.
11. `startedAt`이 프로세스 시작보다 늦다. JVM이 jar를 연 뒤 이 시각을 읽기 전에 jar가 바뀌면, 다시 띄우기 판정이 그 변경을 못 본다.
12. 받기(accept)가 어떤 입출력 오류로든 실패하면 엔진은 정상 종료 길을 타고 종료 코드 0으로 내려간다.
13. 유휴 분 값이 153,722,868 이상이면 그 시간을 나노초로 바꾸다 넘쳐서, 연결이 0인 첫 정비에서 정비 스레드가 죽는다. 그 뒤로는 실행 상태 파일이 굳고 유휴 종료도 자동 커밋 정비도 없다. 분 값이 153,722,867,280,912,931 이상이면 잠금과 `startup` 커밋 뒤에 엔진이 못 뜬다. 코드로 읽은 길이고 실행해 보지 않았다.
14. `wl-cli`는 vault 폴더가 있는지 안 본다. 오타 난 vault는 launchd가 띄운 엔진이 못 뜨고, `wl-cli`는 30초를 기다린 뒤 「준비되지 않았다」와 종료 코드 4로 끝난다. 까닭은 엔진 로그 파일에만 남는다.
15. 부르는 쪽마다 환경(`WITHLOG_SIDECAR_JAR`, `WITHLOG_SIDECAR_JAVA`, `WITHLOG_SIDECAR_SOCKET`)이 다르면, 엔진을 새로 띄울 때마다 plist가 번갈아 다시 쓰이고 bootout이 따른다.
16. 다시 띄우기 판정은 jar의 수정 시각만 봐서, 내용이 같아도 수정 시각만 바뀌면 다시 띄운다.
17. `print-disabled` 판정은 `=>` 뒤가 `true`로 시작하는 줄만 꺼짐으로 읽는다. 2026-10-22에 이 저장소의 기기(macOS 26)에서 출력 꼴만 세어 보니 `=> disabled`와 `=> enabled`만 있고 `=> true`는 없었다. 그래서 그 기기에서는 꺼진 레이블을 켜고 다시 올리는 갈래가 안 타고, 꺼진 레이블은 「사이드카를 못 띄웠다」와 종료 코드 4로 끝난다고 코드로 읽힌다. 실제로 꺼진 레이블로 재 보지는 않았다.
18. `wl-cli`는 상태 칸을 그대로 종료 코드로 넘겨서, 255를 넘는 상태는 256으로 나눈 나머지가 된다. 상태 256이면 종료 코드 0이다.
19. 엔진에 붙은 뒤 요청을 쓰거나 응답을 읽다 난 입출력 오류(EOF가 아닌 것)는 종료 코드 4가 아니라 1이다. 앱에서 종료 코드로 다시 할지를 가르는 자리는 1을 다시 해도 같은 실패로 보아서 다시 시도하지 않는다(3.3).
20. 64칸과 1 MiB 검사가 띄우기 뒤라서, 너무 큰 호출도 plist를 쓰고 엔진을 띄운 뒤에야 종료 코드 1로 선다.
21. `WITHLOG_READY_TIMEOUT_SECONDS`가 9,223,372,037 이상이면 초를 나노초로 바꾸는 곱이 64비트를 넘쳐 감긴다. 9,223,372,037부터 18,446,744,073까지는 곱이 음수가 되어, 기다리지 않고 곧바로 「준비되지 않았다」로 끝나고 pid 지켜보기도 건너뛴다. 그보다 큰 값은 감긴 곱을 나노초로 쓰는 엉뚱한 상한이 된다. 코드로 읽은 길이고 실행해 보지 않았다.
22. `WITHLOG_SWEEP_QUIET_HOURS`가 2,562,047,788,015,216 이상이면 시간 값이 넘쳐서, 자동 청소는 「하루 한 번 청소가 실패했다」를 쓰고 `sweep`은 종료 코드 1로 끝난다.
23. 실행 상태 파일을 읽는 쪽은 `\"`와 `\\`만 되돌려서, 제어 글자가 든 경로는 `\n` 같은 글자가 남은 채로 읽힌다.
24. 하루 청소의 시각 파일이 미래면 그 시각 뒤 24시간까지 자동 청소가 안 돈다.
25. `install`은 jar 2개를 차례로 깔아서, 2번째 jar에서 실패하면 1번째만 바뀐 채 종료 코드 1로 끝난다.
26. 하루 청소는 엔진 갈래가 응답을 받은 호출 끝에서만 돈다. 엔진에 못 닿은 호출과 `wl-cli`가 직접 하는 명령 뒤에는 안 돈다.
27. 3.7의 「아무도 소켓을 안 여는 때」 2가지는 코드에서 읽은 길이고 재지 않았다.
28. 로그 폴더 `logs/`를 만드는 쪽이 1부에 없다.
29. 단발 모드에서 설정 칸 읽기(3.1의 2번)가 실패하면 실패 기록이 stdout으로 나간다고 읽힌다. `--=x`가 그 예다. 엔진 로그 설정(stderr로 보내는 설정)이 서기 전이라서, 로그 라이브러리의 기본 설정이 표준출력으로 쓰기 때문이다. 이때 stderr는 비고 종료 코드는 1이다. Spring Boot 3.5.3과 logback 1.5.18의 소스로 읽은 길이고 실행해 보지 않았다. 다시 짓는 구현은 stdout을 0바이트로 둔다.
30. `doctor`가 쓰는 lsof는 출력을 끝까지 읽은 뒤에야 5초 상한을 건다. 그래서 출력을 안 닫고 매달린 lsof 앞에서는 `doctor`가 상한 없이 기다린다(3.6). launchctl은 반대로 끝나기를 먼저 기다리고, git은 따로 도는 읽기로 5초 상한을 지킨다.
