withlog 1부 「다시 짜기 시험」 2차의 결과물이 왔다. 설명서(`withlog 1부 vault 엔진 설명서.md`)와 회신, 지시문만 받은 다른 기기의 세션이 1차 위에 이어서 지었다. 받아들임 묶음 448건으로 돌려서 결과를 정리해 줘.

## 받은 것

| 자리 | 무엇 |
|---|---|
| 이 저장소 (구현은 커밋 `4a8acb8` 기준) | 소스 43개 파일, `build.sh`, `README.md` |
| 첨부 `spec-gaps-2차.md` | 설명서가 모호하거나 빠진 자리와 고른 짐작 8개. 이 시험의 핵심 산출물이다. 설명서 문장이 들어 있어서 저장소에는 올리지 않았다 |
| 아래 어댑터 본문 | 저장소에 `my-engine.json`이 없다. 경로가 지은 기기 기준이라 뺐다 |

저장소 소스의 패키지 이름은 `withlog`이고 jar는 `dist/wl-engine.jar`다. 저장소 이름만 `aisurada`다.

짓는 쪽의 사정은 이렇다.

- 짓는 쪽은 설명서와 회신 밖 withlog 자료(소스, 저장소, `fixtures/expect`, 웹 검색)를 안 열었다. 묶음은 한 번도 못 봤다.
- 지은 범위는 읽기 명령 12개(1차의 `get_doc`, `get_sub_note`에 이번 10개)와 준비 걸음 `reindex`다. 1차 구현의 고칠 곳 3곳도 고쳤다.
  - A: `reindex`의 `skipped`에 템플릿, 회고, 휴지통 갈래를 싣는다.
  - B: 훑다 처음 서는 자리 앞까지만 노트로 본다.
  - C: 짓지 않은 명령과 `serve`는 종료 코드 3과 `WL-409 이 판에는 <명령>이 없다`로 답한다.
- 색인은 안 두고 부를 때마다 디스크를 훑는다(8.6). 색인 낡음에 기대는 동작은 지금 엔진과 다르고, 묶음은 그 갈래를 안 잰다.
- 호출 1번이 이 기기에서 약 0.15초다. 가장 무거운 `search_docs`와 `list-docs bodies=true limit=0`도 같았다.

검증은 두 갈래로 했다. 둘 다 설명서로 지은 vault로만 했고, 묶음은 못 봤다.

| 검증 | 결과 |
|---|---|
| 짓는 쪽의 자가 시험 | 297건 통과. 설명서에 바이트까지 적힌 토큰 5건이 바이트까지 같았다 |
| 따로 연 세션이 설명서만 보고 지은 검증 스크립트 6개 | 1차 회귀 207건(11 + 146 + 50), 설명서 예시 63건, 2차 경계 180건이 모두 맞았다 |

따로 연 세션의 검증은 처음에 결함 3곳을 찾았다. 모두 설명서가 분명히 적은 규칙을 구현이 놓친 것이라, 설명서의 빈 곳이 아니다. 고친 뒤 다시 돌려 통과했다.

| 결함 | 절 | 묶음에 닿을 수 있는지 |
|---|---|---|
| `search_docs` 평문 7걸음 정규식에서 느낌표 위치가 틀렸다. `> [!NOTE] 글`에서 `[!NOTE]`가 평문에 남았다 | 10.5 | 닿을 수 있다 (콜아웃 본문이 있는 노트 + `search_docs`) |
| `mins: .nan`과 `evaluation.score: .nan`이 훑기를 세우지 않았다 | 1.8, 1.15의 6번 | 안 닿는다 |
| 태그가 1개도 없는 vault에서 긴 `query`가 종료 코드 1이 됐다 | 12.9의 6번 | 안 닿는다 (설명서가 「묶음 밖」이라 적은 자리) |

그 가운데 첫째는 `spec-gaps-2차.md` 4번이 「설명서 그대로 지었다」고 적은 자리다. 처음 지은 코드는 달랐고 지금은 글과 같다. 짓는 쪽의 자기 보고가 틀렸을 수 있다는 예라서, 항목 검토 때 참고해 줘.

짓는 쪽 자가 시험 vault의 한계도 있다. 설명서가 본문을 안 적은 노트 4개(`ndfixture-00000007`, `ndbulk-00000110`, `…200`, `…201`)는 설명서 예시의 `precondition` 토큰을 못 맞췄다. 엔진은 파일 바이트의 해시를 계산하니 맞을 것으로 보지만, 묶음에서 처음 확인되는 자리다. 이 4개 노트의 `precondition`이 어긋나면 알려 줘.

## 돌리는 법

1. 저장소를 묶음 폴더 밖에서 받는다. 묶음 폴더 안에 두면 무결성 검사가 선다(34.5의 9번).
2. 이 기기의 JDK 21 자리(`/usr/libexec/java_home -v 21`)를 `JAVA_HOME`으로 주고 짓는다. 처음에는 SnakeYAML 2.4를 Maven Central에서 내려받아 체크섬을 확인하니 인터넷이 필요하다.

```bash
git clone https://github.com/bnjjong/aisurada.git
cd aisurada
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./build.sh
```

3. 어댑터 `my-engine.json`을 묶음 폴더 밖에 만든다. `prefix`의 두 칸을 이 기기의 절대 경로로 바꾼다.
   - 첫 칸(java): `<JDK 21 자리>/bin/java`. `/usr/bin/java`는 쓰지 않는다. 실행기가 HOME을 바꿔서 그 스텁이 사용자 폴더의 JDK를 못 찾을 수 있다.
   - `-jar` 다음 칸: `<받은 자리>/aisurada/dist/wl-engine.jar`

```json
{
  "format": "wlx-adapter",
  "version": 1,
  "surface": "engine",
  "name": "withlog-rebuild-p1",
  "prefix": [
    "<JDK 21 자리>/bin/java",
    "-XX:TieredStopAtLevel=1",
    "-Xmx512m",
    "-XX:-UsePerfData",
    "-Duser.home=${HOME}",
    "-Djava.io.tmpdir=${TMPDIR}",
    "-jar",
    "<받은 자리>/aisurada/dist/wl-engine.jar"
  ],
  "suffix": [
    "--withlog.vault=${WITHLOG_VAULT}"
  ]
}
```

4. 저장소 뿌리에서 부른다. `--out`은 없거나 빈 폴더여야 하고, 다시 돌릴 때는 새 이름을 쓴다. 준비 걸음 `reindex`는 실행기가 먼저 1번 부른다.

```bash
node fixtures/expect/run.mjs --engine <어댑터 경로> --out /tmp/wlx-aisurada-1 --parts 1
```

`--only`를 안 붙이면 1부 읽기 케이스 448건(1차 115건 + 이번 333건)이 다 돈다. 이번 목표가 448건이다.

## 결과 읽기

| 실행기 종료 코드 | 뜻 |
|---|---|
| 0 | 448건이 모두 맞았다 |
| 1 | 어긋난 케이스가 있다. `<out>/report.json`의 `failures`를 본다 |

`report.json`의 `warnings`에 vault나 HOME이 바뀌었다는 줄이 있으면 그것도 적는다. 구현은 vault와 HOME에 아무것도 안 쓰게 지었다.

## 결과를 정리할 때 지킬 것

이 시험은 「설명서만으로 엔진을 지을 수 있는가」를 잰다. 그래서 묶음의 기대값을 짓는 쪽에 그대로 건네지 않는다. `report.json`의 `detail`에는 기대 줄이 들어 있어서, 그대로 넘기면 다음 회차가 설명서가 아니라 기대값을 보고 고치게 된다.

어긋난 케이스마다 이렇게 정리한다(설명서 머리의 「다음 할 일」 2번).

1. 케이스 id와 어긋난 검사 이름(`code`, `stdout`, `format` 같은 것)
2. 원인이 설명서의 어느 절에 있는지. 설명서가 빠뜨렸는지, 틀리게 적었는지, 설명서는 맞는데 구현이 잘못 읽었는지
3. 설명서를 고쳤다면 고친 절

짓는 쪽에는 고친 설명서와 1번(케이스 id와 검사 이름)만 다시 준다.

## `spec-gaps-2차.md` 검토

코드를 볼 수 있는 이쪽에서 항목마다 지금 엔진과 맞대 본다.

- 항목은 8개다. 묶음에 닿을 수 있다고 적은 것은 4번(`search_docs` 평문 추출) 하나이고, 나머지 7개는 경계 케이스나 정상 픽스처 밖이라 안 닿는다고 적었다. 그 판단이 맞는지도 본다.

- 항목마다 짐작이 지금 엔진과 같은지 보고, 다르면 설명서를 고친다.
- 1차 `spec-gaps.md`에 적었고 회신이 답한 항목은 다시 안 적었다.
