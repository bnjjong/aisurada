# withlog 1부 vault 엔진 설명서 > 10장 명령 search_docs

`search_docs`는 검색어 1개로 노트의 id, 제목, 아젠다 제목과 태그, 본문 평문을 함께 보고, 걸린 자리로 순위를 매겨 위에서부터 낸다. vault는 안 바꾼다.

- 필터는 9장의 8가지와 같고, 필터와 층을 지난 노트를 모두 후보로 삼아 검색어로 거른다.
- 걸린 자리(`matchedIn`)는 `id`, `title`, `meta`, `body` 차례로 보아 먼저 걸린 1곳이고, 순위도 이 차례다. 같은 자리끼리는 최신순이다.
- 본문에서 걸리면 그 주변 대목(`snippet`)을 싣고, 결과가 잘리면 `truncated`와 `hint`를 싣는다.
- 본문 평문은 마크업을 걷은 글이고, 메인 노트의 HTML 첨부 글을 그 뒤에 붙여 함께 찾는다.
- 근거: 봉투 모양, `title`과 `meta` 갈래, 같은 자리끼리의 최신순은 묶음 37건이 잰다. 갈래 사이의 순위, `id`와 `body` 갈래, `snippet`, 잘림, HTML 첨부 글은 묶음이 안 덮는다. 판정 규칙은 골든 `fixtures/golden/note-search.json`과 `fixtures/golden/body-plain-text.json`이 잰다(34.4). 나머지는 코드 읽기로 확인했다.

## 10.1 한눈에

도구 이름은 `search_docs`, 명령 이름은 `search-docs`이다. 쓰기 깃발이 없어서 워크스페이스 표식을 안 보고 색인도 안 맞춘다. 후보는 색인이 고르고, 후보마다 본문 파일과 HTML 첨부를 그때 읽는다.

「예전에 그 얘기를 어디에 적었지」를 찾는 자리라서 `list_docs`와 달리 본문까지 본다. 그리고 목록과 달리 쪽을 이어 붙이지 않는다. 순위가 붙은 결과라 「위에서 몇 건」이 곧 답이고, 잘렸다는 사실만 알려 부르는 쪽이 필터를 좁힐지 `limit`을 올릴지 정하게 한다.

후보는 메인 노트뿐이다. 하위 노트, 휴지통 노트, json 노트의 본문은 검색되지 않는다(10.7).

## 10.2 부르는 법

| 표면 | 꼴 | 쓰는 쪽 |
|---|---|---|
| 도구 | `search_docs '{"query":"랭킹","agenda":"serving"}'` | Claude와 스킬 |
| 명령 | `search-docs 랭킹 agenda=serving` 또는 `search-docs query=랭킹 agenda=serving` | 앱과 사람 |

도구 표면의 키는 `query`(필수), `limit`, 그리고 9.3의 필터 키 8개다. 명령 표면의 옵션은 `query`, `limit`, 그리고 9.3의 필터 옵션 8개(`from`, `to` 이름)다. `bodies`는 어느 표면에도 없다. 명령 표면의 자리 인자는 1개까지 받는다. 자리 인자와 `query=`를 함께 주면, 공백뿐이 아닌 자리 인자가 이기고 `query=`는 말없이 버려진다(코드 읽기로 확인).

```text
java -jar wl-sidecar.jar search_docs '{"query":"10"}' --withlog.vault=/Users/me/vault --withlog.db.home=/Users/me/.wl/db
```

표면이 바꾸는 것은 3가지다(코드 읽기로 확인). 도구 표면은 `reading` 층만 후보로 삼고, 명령 표면은 `record` 층도 후보로 삼는다. 도구 표면은 검색어를 `query` 키에서 다듬어 읽고, 명령 표면은 자리 인자로 준 검색어를 받은 그대로 쓴다. 도구 표면의 `limit`은 필터보다 먼저 JSON 타입 검사를 1번 더 지난다(10.3).

## 10.3 인자와 검증

도구 표면은 JSON 객체 1개를 읽고 키를 이 차례로 본다. 모르는 키는 9.3과 같은 이유로 거절한다. 키가 없는데 필수면 그 자리에서 서고, 키가 있으면 JSON `null`이어도 타입을 본다(5.4).

| 차례 | 키 | JSON 타입 | 필수 |
|---|---|---|---|
| 1 | `query` | 문자열 | 예 |
| 2 | `limit` | 1 이상의 정수인 숫자 | 아니오 |
| 3부터 10 | 9.3의 필터 8개 | 9.3과 같다 | 아니오 |

`limit`의 타입 검사는 따옴표 없는 리터럴(5.4)을 Java `Double.parseDouble`로 읽은 실수 x로 한다. x를 64비트 정수로 바꾸고(소수는 버리고, 범위를 넘으면 가까운 끝값으로) 그 정수를 다시 실수로 바꾼 값이 x와 같고 1 이상이면 통과한다. 통과하면 그 64비트 정수의 10진 글자가 다음 걸음으로 간다. 그래서 `1.0`, `1e2`, `01`, `+5`, `5d`는 1, 100, 1, 5, 5로 받고, `1.0000000000000001`은 실수로 읽으면 1이라 1이다. `1.5`, `0`, `-3`, `"5"`, `true`, `null`, `1e300`, `NaN`은 거절한다. JavaScript가 정수와 실수를 안 가려서 옛 CLI가 `1.0`을 1로 받았기 때문에 실수로 먼저 읽는다. 타입 검사를 지난 값도 뒤의 정수 읽개(5.3)를 다시 지난다. 그래서 `2147483648`처럼 32비트 범위를 넘는 값은 필터 검사 뒤에 `limit 은 숫자여야 한다`로 선다(코드 읽기로 확인).

명령 표면은 5.2의 문법이다. `이름=값` 꼴의 칸은 옵션으로 읽혀서 `search-docs a=b`는 「모르는 옵션 `a`」로 실패한다. 등호가 든 검색어는 `search-docs query=a=b`로 주고, 첫 `=`에서만 가르므로 값의 `a=b`가 남는다. `--`로 시작하는 칸은 설정으로 빠지므로(3.1) `--x` 같은 검색어도 `query=--x`로 준다.

검색어는 이렇게 정한다(코드 읽기로 확인).

1. 첫 자리 인자가 있고 공백뿐이 아니면 그 값을 받은 그대로 쓴다. 공백뿐인지는 5.3의 다듬기 집합으로 본다.
2. 아니면 `query` 값을 5.3으로 다듬어 쓴다. 도구 표면의 `query`가 이 자리로 간다.
3. 자리 인자와 `query`가 모두 없거나 비면 `WL-400 검색어가 필요하다: <사용법>`이다. 도구 표면에서 공백뿐인 `query`를 줘도 이 문구에 명령 표면의 사용법이 실린다.

그래서 U+3000 1글자를 자리 인자로 주면 공백뿐이라 없는 것과 같고, `query=`도 없으면 `WL-400`이다. U+FEFF는 5.3의 집합에 없어서 U+FEFF 1글자는 검색어가 된다. 그 검색어는 10.6에서 다듬으면 비어서 아무 노트에도 안 걸리고 `total` 0을 낸다.

응답의 `query`는 여기서 정한 검색어다. 그래서 같은 `"  랭킹  "`이 도구 표면과 `query=`에서는 `랭킹`으로, 명령 표면의 자리 인자로는 공백까지 실린다. 찾기는 그 검색어를 10.6의 「검색 다듬기」로 1번 더 다듬어서 결과가 같다.

검색어 다음에 9.3의 필터 1번부터 6번을 같은 규칙과 같은 차례로 본다. 마지막에 `limit`을 본다. 정수 읽개(5.3)로 읽어 정수가 아니면 `WL-400`이고, 안 주거나 빈 값이면 20이고, 1 이상 200 이하가 아니면 `WL-400`이다. 범위 검사가 필터 검사보다 뒤라서 `search-docs x agenda=없음 limit=500`은 아젠다의 `WL-404`로 실패한다. 도구 표면도 같은 차례이고, 다만 `limit`의 JSON 타입 검사가 맨 앞에 1번 더 있다. 그래서 `{"query":"x","agenda":"없음","limit":0}`은 타입 검사의 `WL-400`이고, `limit`이 500이면 타입 검사를 지나 아젠다의 `WL-404`다. 기본값 20과 상한 200은 모두 옛 CLI 값이다. 엔진 주석은 상한 200의 까닭을 「검색 1번이 vault 전체를 메모리에 올리지 않게」로 적지만, 지금 엔진은 `limit`과 상관없이 후보 전부의 본문 파일을 읽어 판정하고 응답만 자른다(10.5). 그래서 상한은 응답 크기만 막는다.

## 10.5 읽는 자리와 찾는 글

후보는 색인에서 필터와 층을 지난 노트 전부이고, 쪽으로 자르지 않는다. 순위가 「어디서 걸렸나」로 정해져서, 미리 자르면 그 안에서만 줄을 세워 제목이 맞는 노트가 빠지기 때문이다. 후보마다 견주는 글은 이렇다.

| 견주는 글 | 출처 | 시점 |
|---|---|---|
| 노트 id, 제목, 태그 | 색인의 노트 표. 제목은 응답의 `title`과 같은 값이다 | 마지막 색인 |
| 아젠다 제목 | 색인의 아젠다 표(제목 규칙은 11.6) | 마지막 색인 |
| 본문 평문 | 9.5의 규칙으로 고른 본문 파일을 1.6으로 자른 본문을 아래 규칙으로 걷은 글 | 부를 때 |
| 첨부 글 | 메인 노트 `attach/`의 HTML 첨부를 아래 규칙으로 걷은 글 | 부를 때 |

`body` 갈래가 견주는 글은 본문 평문이고, 첨부 글이 있으면 그 뒤에 공백 1개와 첨부 글을 붙인다. 본문 평문이 빈 글이어도 첨부 글이 있으면 공백 1개가 앞에 붙고, 이 공백도 대목의 자리를 셀 때 1자다. 본문 파일을 못 읽은 노트(9.5)는 본문 평문이 빈 글이고, 프론트매터를 못 읽게 된 노트는 파일 전체를 본문으로 보고 걷는다. 응답의 나머지 값과 신선도는 9.5와 같다.

본문 평문은 포맷마다 다르다(코드 읽기로 확인, 골든 `body-plain-text.json` 22건이 잰다). 본문이 빈 글이면 평문도 빈 글이다. json 포맷은 늘 빈 글이다. Lexical JSON을 걷는 규칙을 아직 안 만들었고, json 노트는 밖에서만 들어오는 옛 모양(1.13)이라 알고 남긴 차이다.

markdown 포맷은 아래 13걸음을 차례로 하고, 마지막에 앞뒤 공백을 뗀다. `(m)`은 `^`와 `$`가 줄마다 맞는 다중 줄 모드이고, `(i)`는 대소문자 무시다. 「공백」은 U+0020 1개다.

````text
차례  정규식                                              맞은 자리를 바꿀 글
1     <!--[\s\S]*?-->                                     공백
2     ```[\s\S]*?```                                      공백
3     `([^`]*)`                                           괄호 1이 잡은 글
4     !\[[^\]]*\]\([^)]*\)                                공백
5     \[([^\]]*)\]\([^)]*\)                               괄호 1이 잡은 글
6     (m) ^\s{0,3}#{1,6}\s+                               빈 글
7     (m)(i) ^\s*>\s?(\[![a-z]+\])?\s*                    빈 글
8     (m) ^\s*(?:[-*+]|\d+\.)\s+(?:\[[ x/-]\]\s*)?        빈 글
9     (m) ^\s*\|[\s:|-]*\|\s*$                            공백
10    (m) ^\s*\|.*\|\s*$                                  맞은 글의 | 를 모두 공백으로 바꾼 글
11    (m) ^\s*[-*_]{3,}\s*$                               공백
12    \*\*([^*]+)\*\*|\*([^*]+)\*|__([^_]+)__|~~([^~]+)~~   괄호 1, 2, 3, 4가 잡은 글을 이은 글
13    \s+                                                 공백
````

html 포맷은 아래 4걸음 뒤에 앞뒤 공백을 뗀다.

1. `(i)`로 `<(script|style)[\s\S]*?</\1>`에 맞는 자리를 공백으로 바꾼다.
2. `<[^>]+>`에 맞는 자리를 공백으로 바꾼다.
3. 엔티티를 푼다. 글자 그대로, 대소문자를 가려 이 차례로 바꾼다. `&amp;`를 `&`로, `&lt;`를 `<`로, `&gt;`를 `>`로, `&quot;`를 `"`로 바꾼다. 다음에 `&#`와 0 여러 개(없어도 된다)와 `39;`로 된 글과 `&apos;`를 `'`로 바꾸고, 마지막에 `&nbsp;`를 U+0020으로 바꾼다.
4. `\s+`에 맞는 자리를 공백으로 바꾼다.

3걸음은 엔티티마다 글 전체를 왼쪽부터 1번 훑고, 앞 엔티티를 바꾼 결과를 뒤 엔티티가 다시 본다. 그래서 `&amp;lt;`, `&amp;#39;`, `&amp;nbsp;`는 `<`, `'`, 공백이 되고, `&amp;amp;`는 `&amp;`로 남는다. `&AMP;`, `&NBSP;`, `&#x27;`, `&copy;` 같은 다른 엔티티는 그대로 남는다. `&nbsp;`를 바꾼 U+0020은 4걸음에서 이웃 공백과 합쳐진다.

정규식은 Java 방언이고, 다른 언어로 옮길 때 아래가 갈린다(코드 읽기로 확인).

- `\s`는 ASCII 공백 6자(U+0009부터 U+000D까지와 U+0020)만이고, `\S`는 그 나머지 전부다. JavaScript와 Python의 `\s`는 U+00A0과 U+3000 같은 글자도 받아서, markdown 13걸음과 html 4걸음의 결과가 달라진다.
- `\d`는 ASCII 숫자 10개만이다. Python 3의 `\d`는 유니코드 10진 숫자도 받는다.
- `(i)`는 Java의 대소문자 무시와 유니코드 대소문자를 함께 켠 모드다. 글자는 대문자로 바꾼 뒤 다시 소문자로 바꾼 값끼리 견준다. 그래서 7걸음의 `[a-z]`는 ASCII 대문자 26개와 U+0130, U+0131, U+017F, U+212A에도 맞는다. html 1걸음의 `script`와 `style`은 `s` 자리에 U+017F를, `i` 자리에 U+0130과 U+0131을 받는다. 닫는 태그의 `\1`도 같은 규칙으로 견줘서 `<script>`를 `</SCRIPT>`가 닫는다.
- `(m)`의 `^`와 `$`는 LF, CR, CRLF, U+0085, U+2028, U+2029를 줄 끝으로 본다. `^`와 `$` 모두 CRLF의 CR과 LF 사이에서는 맞지 않고, `^`는 글 맨 끝에서는 맞지 않는다. `.`은 이 줄 끝 글자들을 안 받는다. JavaScript의 `m`은 U+0085를 줄 끝으로 안 본다.
- 글자 집합 첫머리의 `]`는 글자로 읽는다. 위 표는 `]`를 탈출해 적었다.
- 바꿀 글의 `$1` 같은 괄호 번호는 그 괄호가 안 맞았으면 빈 글이다.
- 걸음마다 왼쪽부터 겹치지 않게 맞는 자리를 모두 바꾸고, 바꾼 결과를 그 걸음 안에서 다시 훑지 않는다.

맨 끝에 떼는 앞뒤 공백은 5.3의 다듬기 집합이다. 이 집합은 10.6 「검색 다듬기」에서 U+FEFF만 뺀 것이고, markdown 13걸음 뒤에도 html 4걸음 뒤에도 똑같이 건다. 그래서 본문이 U+FEFF로 시작하면 평문 머리에 그 글자가 남는다. 대목이 글 머리부터 잘리면 그 글자는 「검색 다듬기」에서 떨어진다.

첨부 글은 이렇게 짓는다(코드 읽기로 확인).

1. 색인의 첨부 목록에서 그 노트 폴더 바로 아래 `attach/`의 첨부만 고른다. 하위 노트의 첨부는 안 고른다. 이름은 1자 이상 뒤에 `.htm`이나 `.html`로 끝나야 하고, 확장자의 대소문자는 안 가린다. 첨부는 ASCII 확장자로 끝나는 이름만 될 수 있어서(1.12) 이 대소문자 무시는 ASCII만 접는 것과 같다. 점 앞에 U+0085, U+2028, U+2029가 든 이름은 안 고른다. 색인 뒤 새로 생긴 HTML 첨부는 다음 색인 전까지 안 읽힌다.
2. 이름을 UTF-16 차례로 늘어놓고 `<노트 폴더>/attach/<이름>`을 차례로 연다. 노트 폴더는 색인의 `path`이고, 심볼릭 링크는 따라간다. 따라간 끝이 일반 파일이 아니거나(색인 뒤 지워진 것 포함) 4,194,304바이트(4 MiB)를 넘으면 그 첨부를 건너뛴다. 크기를 못 읽으면 0바이트로 보고 읽기를 시도한다. 읽다 입출력 오류가 나면 건너뛰지 않고 명령 전체가 예상 밖 실패로 끝난다(10.9).
3. 바이트를 UTF-8로 읽는다. 깨진 바이트는 U+FFFD로 바꾸고 실패하지 않는다. 바꾸는 단위는 JDK 21의 `new String(bytes, UTF_8)`과 같다. 대부분 WHATWG 인코딩 표준의 「최대 부분」 규칙과 같은 수의 U+FFFD를 내지만, 서로게이트 자리를 인코딩한 조각(`ED` 다음 바이트가 `A0`부터 `BF`)은 다르다. `ED A0 80`은 U+FFFD 3개가 아니라 1개가 되고, 글 끝의 `ED A0`도 1개가 된다. 맨 앞 BOM(`EF BB BF`)은 떼지 않고 U+FEFF 글자로 남는다. 그다음 위의 html 규칙으로 평문을 뽑는다.
4. 빈 평문은 버리고 남은 것을 공백 1개로 잇는다. 남은 것이 0개면 첨부 글이 없다.
5. 이은 글을 앞 60,000 UTF-16 코드 단위에서 자른다. 서로게이트 쌍 가운데서 잘릴 수 있다(10.9). 60,000은 실제 vault에서 노트 1개의 첨부 글이 많아야 23,000자쯤인 것을 넉넉히 덮는 값이다.

엔진은 파일마다 (수정 시각의 밀리초, 크기)가 앞서 읽은 때와 같으면 앞서 뽑은 평문을 다시 쓴다. 이 기억은 프로세스가 사는 동안만 있어서 serve 모드에서만 효과가 난다. serve 모드 엔진이 목록마다 수 MB의 첨부를 다시 읽지 않게 하는 장치다. 첨부 글을 찾는 까닭은 노트가 HTML 문서를 첨부로 넣어 앱 안에서 그리고(2026-10-04부터), 그 문서의 글도 찾혀야 하기 때문이다. 크기 상한은 실제로 가장 큰 다이어그램 첨부(815 KB)를 넉넉히 덮는 값이다.

## 10.6 응답

먼저 검색어와 제목을 「검색 다듬기」로 다듬는다. 앞뒤에서 아래 글자를 모두 뗀다(코드 읽기로 확인, 골든 `note-search.json`의 `trim` 15건이 잰다).

| 떼는 글자 |
|---|
| U+0009부터 U+000D까지, U+001C부터 U+001F까지, U+0020 |
| U+00A0, U+1680, U+2000부터 U+200A까지 |
| U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF |

U+0085와 U+200B는 안 뗀다. 이 집합은 5.3의 다듬기 집합에 U+FEFF를 더한 것이고, Kotlin과 JavaScript의 기본 다듬기의 합집합이다. 어느 언어 쪽에 맞추든 그 반대 언어에서 되던 검색이 안 되게 바뀌어, 오늘 되던 검색을 아무도 잃지 않는 선택이 합집합뿐이었다.

다듬은 검색어를 「바늘」이라 한다. 바늘이 비면 어느 노트도 안 걸린다. 제목을 「검색 다듬기」로 다듬은 글이 빈 노트도 안 걸린다. 이 2가지 검사가 아래 갈래보다 먼저라서, 그런 노트는 `id` 갈래와 `body` 갈래로도 안 걸린다. 여기서 제목은 색인의 제목, 곧 응답의 `title`과 같은 값이다. 5.3의 공백뿐인 제목은 파일을 읽을 때 이미 노트 id로 바뀌어서(1.7) 이 규칙에 안 걸린다. 그래서 이 규칙에 걸리는 것은 U+FEFF와 5.3의 공백 글자로만 된 제목(U+FEFF가 1개 이상)뿐이다(10.9). 걸리는지는 아래 차례로 보고 먼저 걸린 자리에서 멈춘다.

| 차례 | `matchedIn` | 걸리는 조건 |
|---|---|---|
| 1 | `id` | 바늘을 로캘 없는 소문자로 바꾸고, 맨 앞의 `#doc:` 1개를 떼고, 첫 `/` 앞까지만 남긴 글이 노트 id를 같은 방법으로 소문자로 바꾼 글과 똑같다 |
| 2 | `title` | 제목에 바늘이 든다 |
| 3 | `meta` | 아젠다 제목이나 태그 1개에 바늘이 든다 |
| 4 | `body` | 10.5의 `body` 글에 바늘이 든다 |

`id` 갈래의 소문자는 Java `String.toLowerCase(Locale.ROOT)`, 곧 유니코드 15.0의 전체 소문자 대응이다. ASCII만 바꾸는 소문자가 아니다. 그래서 `#DOC:`도 벗겨지고, `ndbul`과 U+212A(켈빈 기호)와 `-00000110`을 이은 바늘도 U+212A가 `k`로 바뀌어 `ndbulk-00000110`에 걸린다. 노트 id는 1.4의 모양 검사로 ASCII 소문자와 숫자와 `-`만 든 글이라서, 대문자가 든 노트 id는 색인에 없다. 그래서 노트 쪽을 소문자로 바꾸는 걸음은 지금 결과를 안 바꾼다.

「든다」는 대소문자 무시 부분 일치다. 글의 왼쪽부터 자리를 1칸씩 옮기며, 그 자리에서 바늘 길이만큼을 바늘과 견준다. 견주기는 Java `String.regionMatches`의 대소문자 무시와 같다. UTF-16 코드 단위마다(서로게이트 쌍은 코드 포인트로) 같거나, 대문자로 바꿔 같거나, 대문자로 바꾼 것을 다시 소문자로 바꿔 같으면 같은 글자로 본다. 9.3의 `equalsIgnoreCase`와 같은 글자 규칙이고, 길이를 맞대는 대신 자리를 옮기며 찾는 것만 다르다. 대소문자 표는 9.3과 같이 유니코드 15.0이다. 문자열 전체를 소문자로 바꿔 견주는 방식과는 U+017F와 U+0131 같은 글자에서 갈린다. 이 방식에서는 `ſ`가 `s`에, `ı`가 `i`에 걸리지만, 소문자로 바꿔 견주면 안 걸린다.

id를 정확히 같을 때만 보는 이유는 부분 일치로 열면 `nd` 2글자에 모든 노트가 걸려 진짜 결과를 덮기 때문이다. 껍데기 `#doc:`과 `<노트 id>/<하위 id>`를 벗기는 이유는 사람이 id를 검색창에 넣는 경우가 본문 링크나 하위 노트 참조를 복사해 붙이는 것이기 때문이다. `#sub:`는 벗겨도 하위 id가 나와 메인 노트에는 영영 안 걸려서 안 벗긴다. 이 갈래들은 골든 `match` 41건이 잰다.

순위는 이렇다(코드 읽기로 확인, 골든 `rank` 8건과 묶음 `search_docs/title-word/10`이 잰다).

1. `matchedIn`이 위 표에서 앞인 쪽이 먼저다.
2. 같으면 `created`의 순간이 늦은 쪽이 먼저다. 순간이 같으면 적힌 벽시계 시각이 늦은 쪽이 먼저다. 이 `created`는 색인에 적힌 글자(1.9의 꼴, 초 아래 없음)를 읽은 값이라, 초 아래만 다른 노트 2개는 같은 시각이다.
3. 그래도 같으면 노트 id 글자의 내림차순이다.

id로 마지막을 가르는 이유는 같은 시각 노트가 호출마다 자리를 바꾸면, 상한에 걸려 잘리는 자리에서 결과가 흔들리기 때문이다. 늘어놓은 앞에서 `limit`건을 낸다.

`snippet`은 `body`에서 걸렸을 때만 싣는다. 다른 자리에서 걸리면 그 값이 이미 줄에 보여서 대목을 따로 보일 이유가 없다. 자리는 UTF-16 코드 단위로 센다.

1. `at`은 `body` 글에서 바늘이 처음 걸린 자리다.
2. 시작은 `at`에서 24를 뺀 값과 0 가운데 큰 값이다. 끝은 `at`에 바늘 길이와 76을 더한 값과 글 길이 가운데 작은 값이다.
3. 시작부터 끝 앞까지 잘라 「검색 다듬기」로 다듬는다.
4. 시작이 0보다 크면 앞에, 끝이 글 길이보다 작으면 뒤에 `…`(U+2026)를 붙인다. `…`와 대목 사이에 공백을 안 넣는다.

대목을 자르는 글은 10.5의 `body` 글이라서, 바늘이 본문 평문에 없고 첨부 글에만 있으면 대목도 첨부 글에서 나온다. 그때 대목이 본문 평문의 끝과 첨부 글의 앞을 함께 담을 수 있다. 바늘 길이는 다듬은 바늘의 UTF-16 코드 단위 수이고, 대소문자 무시로 맞은 자리도 바늘과 같은 길이다.

응답은 늘 객체이고 키 차례는 아래와 같다. `list_docs`와 달리 봉투를 씌우는 이유는 「얼마나 걸렸고 얼마나 돌려줬나」를 함께 말해야, 찾던 노트가 상한 밖에 있을 때 부르는 쪽이 없다고 결론 내지 않기 때문이다.

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `query` | 문자열 | 늘. 10.3에서 정한 검색어 |
| 2 | `total` | 정수 | 늘. 걸린 노트 전부의 수 |
| 3 | `returned` | 정수 | 늘. `docs`의 길이 |
| 4 | `truncated` | `true` | `total`이 `returned`보다 클 때만 |
| 5 | `hint` | 문자열 | 4번과 함께만 |
| 6 | `docs` | 배열 | 늘. 비면 `[]` |

`hint`는 늘 아래 글이다. 사람이 아니라 AI에게 하는 말이라 좁힐 수 있는 필터 이름을 적었다. 글 안의 가운뎃점 3개는 U+00B7(바이트 `C2 B7`)이고, 글 전체는 UTF-8로 68바이트다.

```text
agenda·type·tag·dateFrom으로 좁히거나 limit을 올리세요
```

```json
      "format": "markdown",
      "precondition": "f1:e1b8ea5a3160587399b3d247da8b36876cd2751fb8f086c0c116b9ab58564736",
      "links": [],
      "path": "notes/bulk/2026-07-01-1039-대량-노트-100-0200",
      "matchedIn": "title"
    }
  ]
}
```

본문에서 걸리는 예는 묶음에 없어서 규칙으로 계산했다(예시 값). 픽스처 0001의 본문 평문은 63자이고 아래와 같다.

```text
픽스처 노트 메타가 아직 아무것도 없는 노트다. 본문 한 줄 후속 메모 들여쓴 카드 문장 안의 링크다. 다른 하위
```

`search_docs '{"query":"링크다"}'`는 id와 제목과 아젠다 제목과 태그에 안 걸리고 평문의 53번 자리에서 걸린다. 시작이 29라서 앞에 `…`가 붙고, 끝이 글 길이라서 뒤에는 안 붙는다.

## 10.7 모양이 다른 노트

| 노트 | 검색에서 | 근거 |
|---|---|---|
| json 노트 | 본문 평문이 빈 글이라 본문으로는 안 걸린다. HTML 첨부 글로는 걸린다 | 본문은 묶음이 잰다(`마크다운`이 0007만 내고, 0008 본문의 「마크다운으로」는 안 걸린다). 첨부는 코드 읽기로 확인 |
| 단일 파일 `.html` | 10.5의 html 규칙으로 평문을 뽑는다. 첨부가 없다 | 코드 읽기로 확인 |
| 단일 파일 `.md` | markdown 규칙이고 첨부가 없다 | 코드 읽기로 확인(0007이 제목으로 걸리는 것은 묶음이 잰다) |
| 하위 노트 | 후보가 아니다 | 묶음이 잰다(`랭킹`이 0003만 내고, 같은 태그를 단 하위 노트 `snfixture-00000001`은 안 나온다) |
| 기록 층 노트 | 도구 표면의 후보가 아니다. 명령 표면에서는 줄에 `tier`가 붙는다 | 코드 읽기로 확인 |
| 색인 뒤 본문 파일이 사라진 노트 | 본문 평문이 빈 글이 된다. HTML 첨부가 남아 있으면 첨부 글로 `body` 갈래에 걸리고, 없으면 id, 제목, 메타로만 걸린다 | 코드 읽기로 확인 |
| 색인 뒤 프론트매터가 깨진 노트 | 파일 전체를 본문으로 보고 걷는다. 그래서 프론트매터 글도 `body` 갈래에 걸린다 | 코드 읽기로 확인 |
| 제목이 U+FEFF와 공백으로만 된 노트 | 어떤 검색어로도, id로도 안 걸린다(10.6) | 골든 `match`가 판정 규칙을 잰다. 엔진의 이 경로는 코드 읽기로 확인 |

## 10.9 받아들임 묶음과 얼어 있는 특이점

이 장에는 같은 장에서 다룰 짝 명령이 없어서 공통 절의 10.8은 두지 않는다.

묶음이 덮는 것은 도구 표면 37건이다. 아무것도 안 걸리는 검색어 18건(없는 말, `%`, `_`, 역슬래시, 따옴표, 괄호, 정규식 글자, 1글자, 띄어쓰기, 대문자, 이모지, 줄바꿈, 등호, `-` 머리, 긴 글), 태그로 걸리는 `meta` 2건, 제목 12건, `limit` 1과 200의 2건, 필터를 단 3건이다. 걸린 수가 `limit`을 넘는 케이스가 없어서 `truncated`와 `hint`는 안 덮는다. 갈래 사이의 순위, `id`와 `body` 갈래, `snippet`, 평문 뽑기, HTML 첨부 글, 명령 표면, 기록 층, 실패, 오프셋이 섞인 순위, ASCII 밖 대소문자도 안 덮는다. 판정 규칙의 일부는 골든 `note-search.json`과 `body-plain-text.json`이 잰다. 앱의 빠른 검색이 같은 규칙을 따로 구현하고 있어서, 엔진과 앱이 이 골든 파일을 함께 읽는다(34.4).

아래는 지금 엔진의 특이점이고, 표시의 뜻은 9.9와 같다. 지킬지 고칠지는 부록 D에서 정한다.

1. json 노트의 본문은 검색되지 않는다. 같은 노트의 HTML 첨부 글은 검색된다. 본문 쪽은 묶음이 잰다(`search_docs/title-word/마크다운`).
2. 하위 노트는 검색되지 않는다. 하위 노트에만 쓴 말은 이 명령으로 못 찾는다. 묶음이 잰다(`search_docs/tag-word/랭킹`).
3. 순위의 시각 비교는 순간이고 `list_docs`의 차례는 적힌 글자라서, 오프셋이 다른 노트 사이에서 검색과 목록의 차례가 갈린다. 묶음 밖.
4. 응답의 `query`가 도구 표면과 `query=`에서는 다듬은 글이고 명령 표면의 자리 인자에서는 받은 그대로다. 묶음 밖.
5. 공백뿐인 검색어를 도구 표면에 줘도 실패 문구가 명령 표면의 사용법을 싣는다. 묶음 밖이고, 문구는 원래 계약이 아니다.
6. 검색어가 U+FEFF뿐이면 검색어 검사를 지나지만 다듬으면 비어서, 오류 없이 `total` 0을 낸다. 묶음 밖.
7. 대목을 UTF-16 코드 단위로 잘라서 시작과 끝 모두 서로게이트 쌍 가운데에 떨어질 수 있다. 시작이 쌍 가운데면 대목이 짝 없는 낮은 서로게이트로 시작하고, 끝이 쌍 가운데면 짝 없는 높은 서로게이트로 끝난다. 「검색 다듬기」는 이 글자를 안 뗀다. 엔진은 짝 없는 서로게이트를 JSON 탈출(`\ud83d` 꼴)로 적지 않고, UTF-8로 바꿀 때 `?`(0x3F) 1바이트로 내보낸다(6.1). 그래서 stdout에는 앞 `…` 바로 뒤나 뒤 `…` 바로 앞에 `?`가 선다. 단발 모드와 serve 모드가 같다. 골든도 이 경우를 일부러 안 넣었다. 코드 읽기로 확인했고 실행해 보지는 않았다. 묶음 밖.
8. 첨부 글은 메인 노트의 것만 찾는다. 4 MiB를 넘는 첨부는 말없이 빠지고, 60,000자 뒤는 안 찾는다. 이 3가지는 묶음 밖이다. serve 모드에서 수정 시각의 밀리초와 크기를 안 바꾸고 고친 첨부를 앞 글로 찾는 것은 캐시의 성질이라 계약 아님이다.
9. 태그는 여기서 유니코드 대소문자를 안 가리고 `list_tags`의 `query`는 ASCII만 안 가려서(12.3), 같은 말이 검색과 태그 목록에서 다르게 걸린다. 묶음 밖.
10. 첨부를 읽다 입출력 오류가 나면 9.9의 11번처럼 명령 전체가 예상 밖 실패로 끝난다. 실행해 보지는 않았다. 묶음 밖.
11. 제목이 U+FEFF와 5.3의 공백 글자로만 된 노트는 어떤 검색어로도, 그 노트의 id로도 안 걸린다. 제목 검사가 다른 갈래보다 먼저 「안 걸림」을 정하기 때문이다. 묶음 밖.
12. 필터와 층을 지난 후보 가운데 본문 파일의 프론트매터에 1.8의 안 잡히는 표기(`mins: !!int abc` 같은 것)가 든 노트가 1개라도 있으면, 검색어와 상관없이 명령 전체가 예상 밖 실패로 끝난다. 후보마다 본문 파일을 읽어 프론트매터를 YAML로 읽기 때문이다. 9.9의 14번과 같은 뿌리다. 코드 읽기로만 확인했다. 묶음 밖.
