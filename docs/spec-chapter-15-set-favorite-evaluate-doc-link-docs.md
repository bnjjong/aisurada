# withlog 1부 vault 엔진 설명서 > 15장 명령 set_favorite, evaluate_doc, link_docs

명령 3개는 노트의 프론트매터만 고치고 본문 바이트와 저장 자리는 그대로 둔다. 이 장을 지키면 즐겨찾기, 평가, 연결을 지금 엔진과 같은 바이트로 고친다.

- 3개 모두 쓰기 깃발이 있고 선결 조건 토큰 `f1`을 받는다(7.2).
- `set_favorite`과 `link_docs`는 결과가 지금 값과 같으면 파일을 안 열고 `changed: false`로 답한다. `evaluate_doc`은 시각을 새기므로 늘 쓴다.
- 쓸 때는 색인의 값으로 프론트매터를 다시 짓고, 파일에서 읽은 본문 바이트를 그대로 붙여 같은 자리에 쓴다.
- 응답 모양이 3개 모두 다르고, 파일을 쓴 호출만 `path`와 `precondition`을 싣는다.
- 근거: 이 장의 규칙은 모두 「코드 읽기로 확인」이다. 받아들임 묶음은 명령 3개를 부르지 않고(34.3), 예시 바이트는 1.9의 규칙으로 지었고 토큰은 그 바이트의 SHA-256을 직접 계산했다.

명령 3개를 같은 절에서 나란히 다뤄서 이 장에는 15.8이 없다.

## 15.1 한눈에

| 명령 | 도구 이름 | 명령 이름 | 고치는 키 |
|---|---|---|---|
| 즐겨찾기 | `set_favorite` | `set-favorite` | `favorite`, `favoriteCategory` |
| 평가 | `evaluate_doc` | `evaluate-doc` | `evaluation` |
| 연결 | `link_docs` | `link-docs` | `links` |

읽는 자리는 노트 색인과 그 노트의 본문 파일이다. `link_docs`는 이은 뒤 대상 노트가 색인에 있는지도 본다. 쓰는 자리는 그 노트의 본문 파일 1개이고, 폴더 이름이 규약과 어긋나 있어도 안 옮긴다. 명령 3개가 날짜, 시각, 제목처럼 폴더 이름에 매달린 값을 안 바꾸기 때문이다. 여기서 옮기면 이번 변경과 무관하게 옛 이름을 뒤늦게 고치는 일이 되고, html 단일 파일에서는 같은 id 파일이 2개 남는다.

## 15.2 부르는 법

| 표면 | 꼴 |
|---|---|
| 도구 | `set_favorite '{"id":"<노트 id>","favorite":true,"category":"<라벨>","f1":"<토큰>"}'` |
| 명령 | `set-favorite <노트 id> [favorite=<true 또는 false>] [category=<라벨>] [f1=<토큰>]` |
| 도구 | `evaluate_doc '{"id":"<노트 id>","score":80,"note":"<메모>","f1":"<토큰>"}'` |
| 명령 | `evaluate-doc <노트 id> [score=<점수>] [note=<메모>] [clear=true] [f1=<토큰>]` |
| 도구 | `link_docs '{"from":"<출발 id>","to":"<대상 id>","kind":"direct","f1":"<토큰>"}'` |
| 명령 | `link-docs <출발 id> <대상 id> [kind=<종류>] [remove=true] [f1=<토큰>]` |

명령 표면의 자리 인자는 노트 id이고, `link-docs`만 출발과 대상 2칸이다. id에는 `=`도 줄바꿈도 없어서 자리로 받아도 안전하다. 메모처럼 여러 줄일 수 있는 값은 이름 인자로 받는데, 자리로 받으면 값 안의 `=`를 이름 인자 문법으로 읽기 때문이다. 앱이 보내는 argv의 실측은 이렇다(`fixtures/golden/sidecar-argv.json`, 토큰은 `a` 64자로 채운 자리 값).

```json
["set-favorite","ndm1abcd-00000001","favorite=true","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
["set-favorite","ndm1abcd-00000001","category=매뉴얼","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
["evaluate-doc","ndm1abcd-00000001","score=80","note=틀을 잘 따랐다","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
["evaluate-doc","ndm1abcd-00000001","clear=true","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
["link-docs","ndm1abcd-00000001","ndm1abcd-00000002","kind=direct","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
["link-docs","ndm1abcd-00000001","ndm1abcd-00000002","kind=attach","remove=true","f1=f1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"]
```

부르는 꼴과 `wl-cli`는 13.2와 같다. 명령 3개 모두 칸 목록이 표면 2개에서 같고, 도구 표면의 `id`, `from`, `to`가 명령 표면의 자리 인자로 간다. 표면 2개의 차이는 3가지다. 도장 글자(`tool`과 `app`)와 `editedSessionId`가 14.2처럼 다르다. 불리언 칸(`favorite`, `clear`, `remove`)은 도구 표면에서 따옴표 없는 JSON `true`나 `false`여야 하고, 명령 표면에서는 글 `true`나 `false`다. `score`는 도구 표면에서 따옴표 없는 JSON 값이고 명령 표면에서는 글이다.

## 15.3 인자와 검증

다듬기와 공백 글자, 대소문자를 안 가리는 비교는 13.3과 같다. 노트 id(`id`, `from`, `to`)는 다듬지 않는다. 그래서 앞뒤에 공백이 붙은 id는 인자가 없다는 실패가 아니라 `노트 id 모양이 아니다`로 서고, 공백뿐인 id는 `인자가 하나 필요하다`(`link_docs`의 `to`는 `대상 노트 id 가 필요하다`)로 선다.

명령 표면의 불리언 칸 3개(`favorite`, `clear`, `remove`)는 같은 규칙이다. 값을 다듬고, 다듬은 글이 비면 안 준 것으로 보고, 그 밖에는 글자까지 정확히 `true`나 `false`여야 한다. 대소문자를 가려서 `True`와 `yes`와 `1`은 `<이름> 은 true 나 false 여야 한다: <다듬은 값>`으로 선다.

**`set_favorite`**

| 칸 | 도구 표면 | 명령 표면 | 값 | 안 주면 |
|---|---|---|---|---|
| `id` | 필수 문자열 | 자리 인자 1칸 | 노트 id 모양 | 실패 |
| `favorite` | JSON 불리언 | 불리언 글 | 위 불리언 규칙 | 아래 규칙 |
| `category` | 문자열 | 문자열 | 받은 글자. 공백뿐(빈 글 포함)이면 「지운다」, 아니면 다듬은 값 | 지금 라벨을 그대로 |
| `f1` | 문자열 | 문자열 | 14.3과 같다 | 안 온 것 |

새 즐겨찾기 값은 이렇게 정한다. `favorite`을 주면 그 값이다. 안 주고 `category`도 안 주면 지금 값을 뒤집는다. 안 주고 `category`만 주면 지금 값을 지킨다. 라벨만 고치려는 호출이 별을 함께 끄면 안 되기 때문이다. 그래서 이 명령의 `favorite=false`와 안 준 것은 뜻이 다르고, 목록 필터의 같은 이름(9장)과 반대다. 뒤집기는 엔진이 지금 색인의 값을 보고 정해서, 부르는 쪽이 화면의 값을 확실히 남기려면 `favorite`을 직접 싣는다.

`category`에서 빈 글과 안 준 것을 가르는 이유는, 라벨을 지우는 방법이 빈 글을 주는 것뿐이기 때문이다. 다듬는 이유는, 그 값이 글이 아니라 폴더 라벨이라 `매뉴얼 `과 `매뉴얼`이 갈라지면 즐겨찾기 화면에 같은 이름이 2줄 생기기 때문이다. 길이 상한은 없다(15.9의 2번). 별을 끄면서 라벨을 남길 수 있고, 그때 파일에는 `favorite` 줄 없이 `favoriteCategory` 줄만 남는다.

**`evaluate_doc`**

| 칸 | 도구 표면 | 명령 표면 | 값 | 안 주면 |
|---|---|---|---|---|
| `id` | 필수 문자열 | 자리 인자 1칸 | 노트 id 모양 | 실패 |
| `score` | JSON 숫자 | 실수 글 | 아래 실수 문법. 0 이상 100 이하. 소수도 된다 | `clear`가 참이 아니면 실패 |
| `note` | 문자열 | 문자열 | 받은 글자. 저장할 때 다듬고 앞 1,000자(UTF-16 단위)만 남긴다 | 빈 글 |
| `clear` | JSON 불리언 | 불리언 글 | 참이면 평가를 지운다 | 거짓 |
| `f1` | 문자열 | 문자열 | 14.3과 같다 | 안 온 것 |

`clear`가 참이면 지우기이고 `score`와 `note`의 값은 안 본다. 옛 CLI가 `clear`를 먼저 봐서 `clear`와 `score`를 함께 주면 지우기가 이긴다. 다만 도구 표면의 칸 타입 검사(5.4)는 그보다 먼저라서, 도구 표면에서 `score`가 문자열이면 지우기여도 실패한다(15.9의 3번). 거짓이면 `score`가 필수다.

점수는 범위를 먼저 보고 반올림을 나중에 한다. 반올림을 먼저 하면 `100.4`가 100이 되어 통과하는데, 옛 도구 스키마는 그 값을 거절했기 때문이다. 범위 밖 값을 100으로 조이지 않고 실패시키는 이유는, `150`은 손편집된 파일이 아니라 사람이 방금 친 오타라서 조용히 100점으로 바꾸면 사용자는 자기가 150을 준 줄 알기 때문이다. 범위 검사는 0 이상이고 100 이하인지라서 `-0.0`은 통과한다. 반올림은 가장 가까운 정수이고 딱 절반이면 큰 쪽이라 `33.6`은 34, `99.5`는 100, `0.5`는 1이다.

**실수 문법.** 명령 표면은 `score`를 다듬고, 다듬은 글이 비면 안 준 것으로 본다. 그다음 Java `Double.valueOf`가 받는 글만 받는다. 꼴은 이렇다.

- 앞뒤에 U+0000부터 U+0020까지의 글자가 0개 이상 붙어도 된다.
- 부호 `+`나 `-`가 0개나 1개 온다.
- 그다음 `NaN`, `Infinity`, 10진 숫자 부분, 16진 숫자 부분 가운데 1가지가 온다. 10진 숫자 부분은 `80`, `80.`, `80.5`, `.5`에 지수 `e8`, `E+8`, `e-8`을 0개나 1개 붙인 글이다. 16진 숫자 부분은 `0x`나 `0X` 뒤에 16진 숫자와 소수점이 오고 반드시 `p`나 `P` 지수가 붙는 글이다(`0x1p6`은 64).
- `NaN`과 `Infinity`가 아니면 맨 끝에 접미사 `f`, `F`, `d`, `D`가 0개나 1개 붙을 수 있다.
- 숫자는 ASCII만 받는다. 크기가 너무 크면 무한대로, 아주 작으면 0으로 읽힌다.

도구 표면은 JSON 읽개가 따옴표 없는 글을 문자열이 아닌 값으로 넘겨서(5.4의 JSON 읽개), `80`과 `1e2` 같은 JSON 숫자뿐 아니라 `0x1p6`, `.5`, `+80`, `80d`, `NaN`도 같은 문법으로 읽힌다. 따옴표 친 `"80"`과 따옴표 없는 `true`는 타입 실패다. 도구 표면은 읽은 값을 실수로 1번 읽어 Java의 실수 글(`80`은 `80.0`, `1e7`은 `1.0E7`, `1e999`는 `Infinity`)로 다시 적어 넘기고, 명령 쪽 해석이 그 글을 다시 읽는다. 표면 2개 모두 `NaN`과 `Infinity`처럼 읽힌 값은 범위 검사가 거절한다. 이 문법은 지금 엔진의 언어 런타임(Kotlin 1.9.25의 `toDoubleOrNull`과 Java `Double.parseDouble`)이 정한다. 부록 D가 정하기 전에는 다시 짠 구현도 이 목록을 계약으로 보고 그대로 받는다(0.5, 15.9의 8번). 묶음은 이 문법을 안 재서 10진 숫자와 부호와 지수만 받는 구현도 통과하지만, 그런 구현은 `0x1p6` 같은 글에 지금 엔진과 다른 종료 코드를 낸다.

메모를 다듬는 이유는 그 값이 글이 아니라 1줄 라벨에 가깝기 때문이고, 옛 CLI도 다듬었다. 여러 줄도 되고, 프론트매터에 블록 스칼라(1.9)로 적혀서 안에 `---` 줄이 있어도 울타리를 안 깬다.

**`link_docs`**

| 칸 | 도구 표면 | 명령 표면 | 값 | 안 주면 |
|---|---|---|---|---|
| `from` | 필수 문자열 | 자리 인자 첫 칸 | 노트 id 모양. 고치는 노트 | 실패 |
| `to` | 필수 문자열 | 자리 인자 2번째 칸 | 노트 id 모양. 있는지는 이을 때만 알린다 | 실패 |
| `kind` | 문자열 | 문자열 | `direct`, `indirect`, `attach`. 다듬고, 다듬은 글이 비면 안 준 것으로 본다. 대소문자를 안 가린다 | `direct` |
| `remove` | JSON 불리언 | 불리언 글 | 참이면 끊는다 | 거짓 |
| `f1` | 문자열 | 문자열 | 14.3과 같다. `from` 노트의 토큰이다 | 안 온 것 |

`from`과 `to`가 같으면 실패한다. 그래프에 자기 고리가 생기고 연결 패널에 자기가 백링크로 뜨기 때문이다. 모르는 `kind`를 `direct`로 떨어뜨리지 않는 이유는, `atach` 같은 오타가 사용자가 안 만든 실선을 그래프에 1개 그리기 때문이다. 같은 이유로 `remove=yes`도 거짓이 아니라 실패다. 거짓으로 읽으면 끊으려던 연결이 오히려 1개 더 생긴다.

**검사 차례.** 명령 3개가 같은 뼈대를 지난다.

1. 세션 표식을 떼고 이름을 찾는다.
2. 표면의 인자를 읽는다(5.2, 5.4). 도구 표면의 칸 차례는 위 표의 차례다.
3. 워크스페이스 표식을 본다.
4. vault 전체의 색인을 맞춘다.
5. 자동 커밋의 앞 걸음을 지난다. 13.3의 6번처럼 실패하지 않는다.
6. 값을 읽는다. `set_favorite`은 `id`가 있는지, `id` 모양, `favorite` 차례다. `evaluate_doc`은 `id`가 있는지, `id` 모양, `clear`이고, `clear`가 참이 아니면 `score`가 있는지, 숫자인지, 범위 차례다. `link_docs`는 `from`이 있는지, `to`가 있는지, `from` 모양, `to` 모양, `kind`, `remove` 차례이고, 그다음 자기 연결인지다.
7. 색인에서 노트를 찾는다. 없으면 `WL-404`다.
8. `set_favorite`과 `link_docs`는 결과가 지금 값과 같으면 여기서 끝낸다(15.5).
9. 15.5의 메타 쓰기를 한다.

그래서 `id`가 맞는 `link-docs <id> <id> kind=x remove=yes`는 `kind`가 `remove`보다 앞이라 「모르는 관계 종류」로 선다.

| 18 | 본문 파일을 못 읽음 | 3개 모두 | 3 | `WL-500` |
| 19 | 토큰 거절 3가지 | 3개 모두 | 5 | `WL-412` |
| 20 | 프론트매터가 없음 | 3개 모두 | 3 | `WL-500` |

도구 표면에서 불리언 칸이나 `score`의 타입이 틀리면 8번, 9번, 11번, 14번까지 안 가고 1번에서 선다. 값이 그대로인 `set_favorite`과 `link_docs`는 16번 뒤에서 성공으로 끝나서 17번부터는 안 지난다. 17번부터는 아무것도 안 쓰는 실패다. 지금 문구는 이렇다. 19번의 3줄 문구는 14.4와 같고, `<본문 파일>`은 고치는 노트(`link_docs`면 `from`)의 본문 파일이다.

```text

WL-400 인자 검증 실패(set_favorite): favorite 는 true 나 false 여야 한다: <JSON 값>
WL-400 인자 검증 실패(evaluate_doc): score 는 숫자 여야 한다: <JSON 값>
WL-400 set-favorite 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [category, f1, favorite] 뿐이다.
WL-400 evaluate-doc 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [clear, f1, note, score] 뿐이다.
WL-400 link-docs 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [f1, kind, remove] 뿐이다.
WL-400 <명령 이름> 이 받는 자리 인자는 <상한> 개인데 <n> 개를 받았다: <사용법>
WL-400 인자가 하나 필요하다: <사용법>
WL-400 대상 노트 id 가 필요하다: <사용법>
WL-400 노트 id 모양이 아니다: <받은 값>
WL-400 <이름> 은 true 나 false 여야 한다: <다듬은 값>
```

명령 표면의 사용법 글 3개는 이렇다.

```text
set-favorite <노트 id> [favorite=true|false. 안 주면 지금 값을 뒤집는다] [category=<라벨. 빈 값이면 지운다>] [f1=<직전에 읽은 토큰>]
evaluate-doc <노트 id> [score=<0~100>] [note=<평가 메모>] [clear=true] [f1=<직전에 읽은 토큰>]
link-docs <출발 노트 id> <대상 노트 id> [kind=direct|indirect|attach] [remove=true] [f1=<직전에 읽은 토큰>]
```

점수 범위 문구의 값은 Java의 실수 글이라, `150`을 주면 `평가 점수는 0 에서 100 사이여야 한다: 150.0`이고 `1e7`이면 `1.0E7`, `NaN`이면 `NaN`이다. 도구 표면의 숫자도 실수로 1번 읽어 다시 적은 뒤 넘어와서, 이 문구에서 표면 2개의 글자가 같다. 대상이 없다는 문구는 2번째 자리 인자가 없거나 공백뿐일 때 난다. 도구 표면은 `to`를 빼면 그 전에 `인자 검증 실패(link_docs): to 가 필요하다.`로 서고, 공백뿐인 `to`를 주면 이 문구가 난다. 쓰기 입출력 실패는 7.4의 문구이고 파일 시스템의 절대 경로를 싣는다.

## 15.5 읽고 쓰는 자리와 신선도

**값이 그대로인 호출.** `set_favorite`은 새 즐겨찾기 값과 새 라벨이 색인의 지금 값과 모두 같으면 파일을 안 연다. 라벨은 미분류끼리도 같다. `link_docs`는 이을 때 같은 `to`와 `kind`의 연결이 이미 있거나, 끊을 때 같은 `to`와 `kind`의 연결이 없으면 파일을 안 연다. 이 갈래는 토큰을 안 맞대고, 응답에 `path`와 `precondition`이 없다. 같은 값을 다시 쓰면 수정 시각이 바뀌어 vault 동기화와 색인 훑기가 그 노트를 매번 다시 읽어서 쓰지 않는다. 토큰을 안 싣는 이유는, 파일이 안 바뀌었으니 부르는 쪽이 이미 든 토큰이 여전히 맞기 때문이다. 지금 값을 다시 읽어 실으면 「이 쓰기가 이 바이트를 만들었다」는 거짓말이 된다.

`evaluate_doc`은 이 갈래가 없다. 평가에는 시각이 붙어서 같은 점수를 다시 줘도 내용이 달라지고, 평가가 없던 노트를 지워도 옛 CLI처럼 파일을 다시 쓴다.

**새 값.** `set_favorite`은 즐겨찾기와 라벨만 갈아 낀다. `evaluate_doc`은 평가를 갈아 끼우거나 지운다. 새 평가는 점수를 반올림해 0에서 100으로 조이고, 메모를 다듬어 앞 1,000자만 남기고, `at`에 엔진 시계의 지금 순간을 UTC 밀리초까지 남긴다. `link_docs`는 이을 때 연결을 목록 맨 뒤에 붙이고, 끊을 때 그 항목만 뺀다. 대상 id 차례로 다시 늘어놓지 않는 이유는, 그러면 노트 1개를 이을 때마다 연결 목록 전체가 뒤집혀 파일이 통째로 다시 쓰이기 때문이다.

**메타 쓰기.** 명령 3개가 같은 차례로 쓴다.

1. 색인 행에서 저장 자리와 포맷을 얻는다. 자리가 없으면 `WL-409`이고, 지금 vault에서는 닿지 않는다.
2. 본문 파일을 읽는다. 14.5의 4번과 같다.
3. 토큰을 맞댄다. 14.5의 토큰 대조와 같고, json 노트만 토큰 없이 지나간다.
4. 프론트매터를 읽는다. 없으면 `WL-500`이다.
5. 프론트매터를 다시 짓는다. 값은 색인의 노트 값에 위 새 값을 얹은 것이고, `agenda`는 14.5의 7번처럼 파일에 적힌 글자(빈 글이거나 문자열이 아니면 `path`의 2번째 조각), `sessionId`는 파일에 적힌 값(다듬어 앞 128자)이다. `created`는 14.3처럼 색인의 값을 다시 찍는다. 도장은 1.10으로 정한다.
6. 본문은 4번에서 프론트매터를 떼고 남은 파일 바이트 그대로다. 색인의 본문을 안 쓰는 이유는, json 노트에서 그 값이 빈 글이라 즐겨찾기 1개를 켠 대가로 본문이 사라지기 때문이다.
7. 울타리는 포맷이 정하고(1.6), 파일 전체의 UTF-16 길이가 1,000,000을 넘는지 보고, 7.4의 원자적 쓰기로 같은 자리에 쓴다. 31.6의 스냅숏 갈고리를 지난다.
8. 그 노트를 다시 읽어 색인한다. 다시 읽을 때 아젠다는 폴더 이름의 slug로만 찾는다(15.9의 5번).

값은 고치기 직전에 맞춘 색인에서 온다. 색인을 안 맞추고 쓰던 시절에는, 앱이 파일에서 태그를 늘린 뒤 `set_favorite`을 부르면 색인의 옛 태그가 파일에 되돌려 써져 그 태그가 사라졌다. 같은 까닭으로 1.8이 읽으며 고친 값이 이 쓰기에서 파일에도 반영된다(14.5와 같다).

`link_docs`는 이은 뒤 대상 id가 노트 색인에 있는지 보고, 없으면 경고를 싣는다. 층은 안 가리고, 하위 노트는 대상이 될 수 없다(`to`가 노트 id 모양이어야 한다). 끊을 때는 안 본다. 사라진 대상을 가리키는 연결을 치우는 것이 끊기의 주된 쓸모라, 대상이 없는 것이 이상하지 않기 때문이다. 이을 때도 막지 않고 알리기만 한다. 앞으로 만들 노트를 미리 가리키는 것이 정상 흐름이기 때문이다.

**자동 커밋.** 끝나면 쓴 쪽을 남긴다. 파일을 안 쓴 호출과 실패한 호출도 남긴다(7.1, 31.1). 13.5와 같이 serve 모드 엔진에서만 커밋으로 이어진다.

## 15.6 응답

**`set_favorite`**

| 차례 | 키 | 타입 | 있는 조건 | 값 |
|---|---|---|---|---|
| 1 | `id` | 문자열 | 늘 | 노트 id |
| 2 | `favorite` | 불리언 | 늘 | 결과 즐겨찾기 값 |
| 3 | `category` | 문자열 | 결과 라벨이 있을 때 | 결과 라벨 |
| 4 | `changed` | 불리언 | 늘 | 파일을 썼으면 `true` |
| 5 | `path` | 문자열 | 파일을 썼을 때 | 노트의 저장 자리 |
| 6 | `precondition` | 문자열 | 파일을 썼을 때 | 방금 쓴 바이트의 토큰 |

라벨이 `favorite`과 `changed` 사이에 끼는 것이 실측한 옛 CLI의 차례다. 값이 같아도 차례가 다르면 stdout 바이트가 갈린다. 결과 라벨은 파일을 썼으면 이번에 정한 값(길이를 안 자른 값)이고, 안 썼으면 색인의 값이다.

**`evaluate_doc`**

| 차례 | 키 | 타입 | 있는 조건 | 값 |
|---|---|---|---|---|
| 1 | `id` | 문자열 | 늘 | 노트 id |
| 2 | `path` | 문자열 | 늘 | 노트의 저장 자리 |
| 3 | `precondition` | 문자열 | 늘 | 방금 쓴 바이트의 토큰 |
| 4 | `evaluation` | 객체나 `null` | 늘 | 평가. 지웠으면 `null` |

`evaluation`만은 지웠을 때 키를 빼지 않고 `null`을 싣는다. 옛 CLI가 그렇게 명시했고, 이 자리에서만 `null`이 「지웠다」를 뜻한다. 객체의 키는 `score`(정수), `note`(문자열), `at`(UTC `yyyy-MM-ddTHH:mm:ss.SSSZ`) 차례로 11.6의 평가와 같다. 밀리초가 0이어도 `.000`을 적는다.

**`link_docs`**

값이 그대로였으면 키 3개다.

| 차례 | 키 | 타입 | 값 |
|---|---|---|---|
| 1 | `id` | 문자열 | `from` 노트 id |
| 2 | `changed` | 불리언 | `false` |
| 3 | `note` | 문자열 | 이을 때 `이미 있는 연결이에요.`, 끊을 때 `제거할 연결이 없어요.` |

바꿨으면 이렇다.

| 차례 | 키 | 타입 | 있는 조건 | 값 |
|---|---|---|---|---|
| 1 | `id` | 문자열 | 늘 | `from` 노트 id |
| 2 | `to` | 문자열 | 늘 | 대상 id |
| 3 | `kind` | 문자열 | 늘 | 종류의 정식 소문자 |
| 4 | `removed` | 불리언 | 늘 | 끊었으면 `true` |
| 5 | `changed` | 불리언 | 늘 | `true` |
| 6 | `path` | 문자열 | 늘 | `from` 노트의 저장 자리 |
| 7 | `precondition` | 문자열 | 늘 | 방금 쓴 바이트의 토큰 |
| 8 | `warning` | 문자열 | 이었고 대상이 색인에 없을 때 | 아래 문구 |

안 바뀐 갈래에 `to`와 `kind`를 안 싣는 것이 옛 CLI의 모양이다. 채워 넣으면 「이 연결을 만들었다」로 읽힌다. 마침표까지 들어간 `note`의 문장 2개와 아래 경고는 옛 CLI 글자 그대로라서 계약이다.

```text
대상 문서 id를 vault에서 찾지 못했어요(<대상 id>) — 연결은 저장되지만 대상이 생길 때까지 그래프엔 안 보일 수 있어요.
```

## 15.7 모양이 다른 대상

| 노트 | 동작 | 픽스처 |
|---|---|---|
| 폴더의 `note.json` | 토큰 없이도 쓴다. 본문의 JSON 바이트를 그대로 두고 `---` 울타리로 쓴다. 응답에 토큰이 실린다 | 0005, 0008 |

## 15.9 받아들임 묶음과 얼어 있는 특이점

받아들임 묶음은 명령 3개를 부르지 않는다(34.3). 저장소의 옛 차등 검증 쓰기 축이 `set_favorite` 15건, `evaluate_doc` 15건, `link_docs` 14건을 파일 지문으로 얼려 두었지만 묶음 밖이다.

지금 엔진의 특이점이다. 지킬지 고칠지는 부록 D에서 정하고, 모두 코드 읽기로 찾았다.

1. 값이 그대로인 `set_favorite`과 `link_docs`는 토큰을 안 맞대서, 토큰이 없거나 낡아도 종료 코드 0으로 성공한다. 「토큰이 없으면 거절한다」는 7.2의 규칙은 파일을 쓰는 갈래에만 걸린다.
2. 즐겨찾기 라벨에 길이 상한이 없다. 100자를 넘는 라벨은 통째로 적히고 읽을 때 앞 100자만 남아서, 같은 라벨로 다시 불러도 늘 「바뀌었다」로 파일을 다시 쓴다. 응답의 `category`는 긴 글 그대로이고 읽기 명령은 100자를 낸다.
3. `clear`가 참이면 `score`를 안 읽는다. 그래서 명령 표면의 `score=abc clear=true`가 성공하고, `score`가 150인 지우기도 표면 2개 모두에서 성공한다. 도구 표면에서 `score`가 문자열이면 칸 타입 검사가 먼저라 실패한다.
4. 메모의 1,000자 자르기가 UTF-16 단위라서 이모지 같은 서로게이트 쌍을 가를 수 있다. 남은 반쪽 글자는 프론트매터에 1.9의 큰따옴표 탈출로 `note: "…\uD83D"`처럼 적히고, 다시 읽으면 반쪽 글자 그대로 돌아온다. 응답 JSON에서는 그 반쪽 글자가 stdout에 `?`(0x3F)로 나간다. 실행해 보지는 않았다.
5. 쓴 뒤의 색인 맞추기가, 파일의 `agenda`가 폴더 이름의 아젠다와 다른 노트에서 조용히 실패한다. 다시 읽을 때 폴더의 slug만 아는 표를 넘기기 때문이다. 그래서 다음 쓰기 명령이나 `reindex`가 오기 전까지 읽기 명령은 옛 값을 낸다.
6. 도구 표면이 기록 층 노트를 막지 않는다. 값이 그대로인 `set_favorite`과 `link_docs`는 토큰 없이 성공해서, `get_doc`이 `WL-409`로 감추는 노트의 즐겨찾기 상태와 연결이 응답으로 드러난다.
7. 평가가 없던 노트에 지우기를 보내도 파일을 다시 쓴다. 노트가 이미 정규형이면 바이트가 같고 수정 시각만 바뀐다.
8. 점수 문법이 15.3처럼 Java의 실수 글을 통째로 받아서 `0x1p6`, `80d`, `.5`, `+80`, 앞뒤 제어 문자가 통과한다. 도구 표면에서도 따옴표 없는 같은 글이 JSON 숫자가 아닌데도 통과한다.
9. 즐겨찾기 라벨이 아주 길어 프론트매터 조각이 16,000 UTF-16 단위를 넘으면, 파일은 써지고 성공으로 답하지만 쓴 뒤의 다시 읽기가 「프론트매터가 없다」로 노트를 못 세운다(13.9의 17번). 색인은 옛 행을 지켜서 읽기 명령은 옛 즐겨찾기 값을 내고, `get_doc`의 `body`는 파일 전체가 된다(8.3). 그 뒤 파일을 여는 쓰기는 이 장의 명령 3개와 `update_doc` 모두 「프론트매터가 없어」 `WL-500`으로 선다. `link_docs`로 연결을 약 350건 쌓아도 같은 일이 난다. 연결 1건이 프론트매터에서 약 45자를 차지하고, 연결 수에 상한이 없기 때문이다. 실행해 보지는 않았다.
