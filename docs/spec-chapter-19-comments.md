# 19장 list_comments와 코멘트 쓰기 3개 — 구현 계약

사용자가 제공한 19장 설명서의 구현용 요약이다. 이 저장소는 TypeScript 앱/엔진 응답 소비 계층이며, vault 파일을 다루는 Java 엔진 소스와 `fixtures/golden/comment-parse.json`, `comment-anchors.json`은 포함하지 않는다. 아래에서 파일 처리 규칙은 연결된 엔진의 계약이고, 여기서 구현한 범위는 호출·응답 검증·호스트 전송이다.

## 표면과 인자 (19.1–19.4)

| 명령 | 표면 | 인자 |
|---|---|---|
| `list_comments` | 도구 | JSON 객체 한 칸, 필수 문자열 `parent`만 |
| `list-comments` | 명령 | `<노트 id> [하위 노트 id]` |
| `create-comment` | 명령만 | 같은 자리 두 칸, 필수 `body`, 선택 `anchor_quote`, `comment_id` |
| `update-comment` | 명령만 | 같은 자리 두 칸, 필수 `comment_id`, `body` |
| `delete-comment` | 명령만 | 같은 자리 두 칸, 필수 `comment_id` |

명령 자리 두 칸은 루트 id와 그 루트 안의 하위 id다. 손자도 그 루트와 손자 id 두 칸으로 찾는다. 명령 첫 칸에 `<루트>/<하위>`를 넣거나 세 칸을 보내지 않는다. 도구 `parent`는 `/`로 나눈 뒤 공백뿐인 조각을 버리되 남은 조각을 다듬지 않고, 1–2조각만 허용한다. 도구 목록에는 record 층을 막는 게이트가 없다.

엔진은 자리 인자를 다듬지 않는다. 공백뿐인 두 번째 칸은 없는 것으로 본다. `comment_id` 옵션만 5.3 공백 집합으로 다듬고, 본문과 인용문은 날것으로 읽는다. 쓰기 세 개 모두 `f1`을 받지 않는다.

클라이언트는 문자열을 그대로 보내며 엔진의 WL 검증 순서를 복제하지 않는다. 일반/null prototype 객체와 알려진 옵션 타입만 받는다. 모르는 키는 값이 undefined여도 TypeError다. 명령 자리 인자가 `--`로 시작하거나 첫 `=`가 첫 글자 뒤에 있으면 설정/옵션 충돌을 전송 전에 거절한다. `=abc`, 빈 문자열, 공백, 슬래시가 있는 잘못된 참조의 WL 판단은 엔진에 맡긴다.

## 파일 자리와 읽기 (19.5–19.7)

| 대상 | 코멘트 파일 | 마커가 사는 본문 |
|---|---|---|
| 노트 | 색인의 노트 경로 + `/comments.json` | 그 노트의 본문 |
| 하위 노트 | 직계 컨테이너 경로 + `/sub-comments/<하위 id>.json` | 그 하위 노트 자신의 본문 |

컨테이너는 바로 위 루트 노트 또는 부모 하위 노트다. 목록은 색인에서 경로만 찾고 코멘트 파일은 호출 시 읽는다. 코멘트 색인 표를 목록의 정본으로 쓰지 않는다. 본문 파일은 목록 읽기에서 열지 않는다.

일반 파일이 없으면 absent다. 200,000바이트 초과, I/O 실패, JSON 구문 오류는 종료 0의 unreadable 봉투다. 깊은 배열로 인한 스택 넘침은 예상 밖 실패다. UTF-8은 JDK의 대체 해독 규칙을 따르고 앞 BOM을 떼지 않는다. JSON은 kotlinx.serialization-json 1.6.3 기본 읽개로 파일을 다듬지 않고 읽는다. JavaScript JSON.parse로 파일 읽기를 재현하지 않는다.

최상위 배열 또는 객체의 comments 배열에서 객체 후보를 취한다. 그 밖의 읽힌 값은 loaded 빈 배열이다. 후보 규칙은 다음과 같다.

- id: `^cm[a-z0-9]+-[a-z0-9]{1,8}$`, 모양 검사만 대소문자 무시. 처음 차지한 id는 그 후보가 뒤에서 버려져도 유지된다. 중복 검사와 쓰기의 id 비교는 글자 그대로다.
- createdAt: 빈 글이 아닌 문자열. 시각 파싱을 하지 않는다.
- body: 문자열, 앞 20,000 UTF-16 코드 단위. 빈 글도 받는다.
- editedAt: 빈 글이 아닌 문자열일 때만 둔다.
- anchor: 객체의 quote가 빈 글이 아닌 문자열이면 앞 2,000 코드 단위를 `{quote: ...}`로 둔다. 앵커가 잘못되어도 코멘트는 남는다.
- 나머지 키는 파일 읽기에서 버린다. 항목은 createdAt, id의 UTF-16 코드 단위 차례로 정렬한다.

응답은 아래 세 형태를 구별한다. `unreadable`을 빈 배열로 대체하지 않는다.

```ts
type CommentsEnvelope =
  | { state: 'absent' }
  | { state: 'loaded'; comments: readonly CommentItem[] }
  | { state: 'unreadable'; reason: string };
```

absent에는 comments/reason이 없고, loaded에는 reason이 없으며, unreadable에는 comments가 없다. 응답 구조 검증은 이 조건과 항목 타입을 검사하며 추가 키·순서·날짜 문자열·대소문자를 보존한다. 파일의 후보를 버리는 규칙을 클라이언트가 다시 적용하지 않는다.

reason은 다음 셋 중 하나다. 경로는 코멘트 파일의 vault 상대 경로다.

```text
파일이 너무 크다(<n>바이트). 상한은 200000바이트다.
파일을 못 읽었다: <경로>
내용이 JSON이 아니다: <경로>
```

파일 직렬화는 짝 없는 서로게이트를 소문자 `\u` 탈출로 남기지만, 엔진 stdout의 UTF-8 변환은 해당 코드 단위마다 `?`를 낸다. 클라이언트는 받은 바이트와 문자열을 보존한다.

## 쓰기와 삭제 (19.8)

엔진은 문법 검사, 워크스페이스 확인, 색인 맞추기, 필요한 git 커밋, 대상/옵션 검사, 파일 읽기, 변경/재작성 순으로 처리하고 성공/실패와 무관하게 쓴 쪽을 기록한다. unreadable 파일에는 쓰지 않고 `WL-409`로 선다. absent는 빈 목록으로 본다.

쓰기 파일은 읽기에서 남긴 항목에 변경을 얹어 다시 정렬한 `{ "v": 1, "comments": [...] }`의 2칸 들여쓰기 JSON과 끝 LF 하나다. 남은 항목이 없으면 파일을 지우고 빈 sub-comments 폴더는 남긴다. 키 순서는 id, createdAt, 선택 editedAt, 선택 anchor, body다.

| 작업 | 검증과 변경 | 성공 응답 |
|---|---|---|
| create | body 필수·공백뿐 거절·20,000 코드 단위 이하, anchor_quote 2,000 이하. 다듬은 선택 id가 없으면 발급, 모양은 검사하지 않음. 같은 id 있으면 WL-409. 현재 createdAt, 날것 body, 공백뿐이 아닌 인용문으로 생성. 본문에 마커는 심지 않음 | id, path, total |
| update | comment_id 필수, body 필수·공백뿐 거절·20,000 이하. 없는 id는 WL-409. body와 editedAt만 변경. createdAt과 현재 시각이 모두 25자이고 현재가 앞서면 editedAt을 createdAt으로 당김 | id, path, total |
| delete | comment_id 필수. 항목 존재 확인 뒤 본문 마커를 걷고 코멘트 항목을 삭제 | id, path, remaining, markerStripped, 조건부 bodyBefore/bodyAfter |

삭제 대상 본문이 markdown이 아니면 마커가 없어도 WL-409다. 프론트매터를 뗀 본문에서 `<!--(/?)wlc:(cm[a-z0-9]+-[a-z0-9]{1,8})-->`를 대소문자 무시로 찾고, 잡힌 id가 comment_id와 글자 그대로 같은 조각만 지운다. 짝·코드 펜스를 가리지 않고 구간의 글은 남긴다.

마커가 없어 본문이 그대로면 본문을 쓰지 않는다. 바뀌면 f1 검사·새 도장 없이 파생 쓰기하며 루트 프론트매터를 다시 짓고 하위 노트는 이동할 수 있다. 본문 쓰기 후 색인 재삽입 등이 실패하면 코멘트 파일은 남고 본문만 바뀔 수 있다. 실패를 vault 전체 무변경으로 해석하지 않는다.

markerStripped가 true이면 bodyBefore/bodyAfter가 모두 문자열이고, false이면 둘 다 없어야 한다. 토큰은 **코멘트가 달린 본문**의 것이며 코멘트 파일이나 직계 컨테이너 본문의 것이 아니다. 보유 토큰이 before와 같을 때만 after를 승계하고, 승계하더라도 본문을 다시 읽기 전 전체 본문 저장을 보류한다. 마커가 없었던 삭제 성공도 코멘트 파일을 바꾸므로 명령 전체의 no-op이 아니다.

## 호환 동작과 근거 (19.9)

아래 동작의 수정은 부록 D 결정이 없으므로 이 클라이언트에서 바꾸지 않는다.

1. 읽기에서 탈락/절단된 항목은 다음 파일 쓰기에서 사라지거나 잘린 채 저장된다.
2. create가 모양에 맞지 않는 comment_id도 받아 다음 읽기에서 안 보일 수 있다.
3. 코멘트 색인 id는 vault 전체에서 유일하여 다른 파일의 같은 id가 쓰기를 막을 수 있다.
4. 파일 쓰기에는 200,000바이트 상한이 없어 성공 직후 unreadable이 될 수 있다.

단일 파일 노트의 create, JSON/HTML 삭제 거절, 하위 노트 이동, 프론트매터의 모르는 키 소실 등도 엔진이 판정한다. 클라이언트에서 예상 경로를 조립해 파일을 직접 고치지 않는다.

원문 19.8 마커 표에는 대문자 id 마커를 소문자 comment_id로 제거하는 행이 있지만, 같은 절의 알고리즘과 19.5/19.9.13은 id를 글자 그대로 견준다고 한다. 테스트는 반복해서 명시된 글자 그대로 비교를 기준으로 한다. 첫 마커 예시의 공백 추가 역시 ‘조각만 지우고 글은 그대로 둔다’는 규칙과 충돌한다. 실제 golden 파일과 JAR을 확보해 이 예시의 차이를 확인해야 한다.

명세는 list_comments/쓰기 세 개를 직접 부르는 수용 케이스가 없다고 보고한다. 읽기의 loaded/absent 예시는 get_doc/get_sub_note의 comments를 통한 간접 근거다. 쓰기 응답과 예시 토큰은 코드 읽기 예시다. 추가한 mock/가짜 프로세스 시험을 원본 수용 묶음이나 파일 엔진 검증으로 세지 않는다.
