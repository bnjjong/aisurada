# withlog 1부 vault 엔진 설명서 > 12장 명령 list_tags

`list_tags`는 읽기 층 메인 노트에 달린 태그마다 그 태그를 단 노트 수를 세어 많은 차례로 낸다. vault는 안 바꾼다.

- 어느 표면이든 `reading` 층 노트만 센다. 명령 표면도 기록 층의 태그를 못 본다.
- 하위 노트의 태그는 안 센다. 노트 1개에 같은 태그는 1번만 센다.
- `query`는 태그 이름의 부분 일치이고, 대소문자 무시는 ASCII 글자에만 걸린다.
- 차례는 개수의 내림차순이고, 같으면 태그 글자의 바이트 차례다. `limit`은 그 차례의 앞에서 자른다.
- 근거: 개수, 차례, 하위 노트 제외, `limit`의 자르기는 묶음 8건이 잰다. 대소문자, 와일드카드 글자, 명령 표면, 실패는 코드 읽기로 확인했다.

---

## 12.1 한눈에

도구 이름은 `list_tags`, 명령 이름은 `list-tags`이다. 쓰기 깃발이 없어서 워크스페이스 표식을 안 보고 색인도 안 맞춘다. 파일은 1개도 안 열고 색인만 읽는다.

쓰임은 노트에 태그를 달기 전에 이미 있는 표기를 보는 1가지다. 뜻이 맞는 태그를 다시 쓸지 새로 만들지 정해서 표기 흔들림을 막는다. 그래서 많이 쓰인 차례로 낸다. 많이 쓰인 태그가 그 뜻의 표준 표기일 가능성이 높기 때문이다.

---

## 12.2 부르는 법

| 표면 | 꼴 | 쓰는 쪽 |
|---|---|---|
| 도구 | `list_tags '{"query":"랭","limit":10}'` | Claude와 스킬 |
| 명령 | `list-tags query=랭 limit=10` | 앱과 사람 |

```text
java -jar wl-sidecar.jar list_tags '{}' --withlog.vault=/Users/me/vault --withlog.db.home=/Users/me/.wl/db
```

도구 키와 명령 옵션은 모두 `query`와 `limit` 2개이고 이름이 같다. 명령 표면은 자리 인자를 0개만 받는다. 표면이 바꾸는 것은 인자를 읽는 법뿐이고, 볼 층은 어느 표면이든 `reading`으로 못박혀 있다(코드 읽기로 확인). 층을 고르는 인자를 열면 기록 층 태그가 새는 길이 생기기 때문이다.

---

## 12.3 인자와 검증

도구 표면은 JSON 객체 1개를 읽고 키를 `query`, `limit` 차례로 본다. `query`는 JSON 문자열, `limit`은 1 이상의 정수인 숫자여야 하고, 어느 키든 JSON `null`이면 타입 오류다. `limit`의 타입 검사는 10.3과 같은 규칙이다. 그래서 `1e2`는 100이고 `0`, `1.5`, `"5"`, `1e300`은 거절한다. 그 밖의 키는 거절한다.

명령 표면은 5.2의 문법이다. 옵션 이름은 `query`와 `limit`뿐이다.

`query`는 5.3으로 앞뒤 공백을 떼고, 비면 거르지 않는다. 남은 글이 태그 이름 어디에든 들면 그 태그를 남긴다. `%`, `_`, `\`는 와일드카드가 아니라 그 글자 그대로 찾는다. 대소문자 무시는 SQLite `LIKE`의 기본 동작과 같아서 ASCII의 `A`부터 `Z`와 `a`부터 `z`에만 걸린다. `Backend`는 `backend`를 찾지만 `É`는 `é`를 못 찾는다. 엔진이 싣는 sqlite-jdbc 3.50.3.0의 SQLite 3.50.3은 ICU 없이 지은 판이고(그 라이브러리에 든 컴파일 옵션 목록으로 확인), 엔진은 `case_sensitive_like`도 안 켜서 이 기본 동작 그대로다. 견주는 글은 태그 글자 그대로이고 유니코드 정규화를 안 한다.

`query`에는 글자 수 상한이 없고, 값의 뜻에도 실패가 없다. 도구 표면에서 `query`가 문자열이 아니면 12.4의 차례 3에서 서는데, 이것은 JSON 타입 검사의 실패다. 다만 엔진은 `query`를 SQLite `LIKE`의 패턴(`%`, `\`와 `%`와 `_` 앞에 `\`를 붙인 `query`, `%`)으로 넘기고, SQLite가 50,000바이트를 넘는 패턴을 거절한다. 그래서 그 패턴이 UTF-8로 50,000바이트를 넘으면 12.9의 6번처럼 예상 밖 실패가 된다.

`limit`은 5.3의 정수 읽개로 읽고, 어느 표면이든 1 이상이어야 한다. 0을 「전부」로 읽는 `list-docs`와 다르게 0은 실패다. 안 주거나 빈 값이면 전부다. `query`를 먼저 읽고, `limit`은 정수 읽기 다음에 범위를 본다. 도구 표면은 타입 검사가 이미 1 이상을 보장하지만, 2,147,483,647을 넘는 정수는 타입 검사를 지난 뒤 정수 읽기에서 `limit 은 숫자여야 한다`로 선다. 상한은 따로 없어서 2,147,483,647은 받는다.

## 12.4 실패

| 차례 | 조건 | 표면 | 종료 | 코드 |
|---|---|---|---|---|
| 1 | vault 없음, 모르는 이름 | 공통 | 2 | 없음 |
| 2 | 인자 2칸 이상, JSON이 아님, 객체가 아님, 모르는 키 | 도구 | 3 | `WL-400` |
| 3 | 키의 JSON 타입이 틀림(`null`, 1 미만이거나 정수가 아닌 `limit` 포함) | 도구 | 3 | `WL-400` |
| 4 | 모르는 옵션, 자리 인자가 있음 | 명령 | 3 | `WL-400` |
| 5 | `limit`이 32비트 정수가 아님. 도구 표면은 2,147,483,647을 넘는 정수일 때만 | 공통 | 3 | `WL-400` |
| 6 | `limit`이 1 미만 | 명령 | 3 | `WL-400` |

모두 코드 읽기로 확인했고, 묶음에는 실패 케이스가 없다. 2번의 문구는 9.4의 꼴에서 도구 이름만 `list_tags`로 바뀌고, 쓸 수 있는 키 목록은 `[query, limit]`이다. 나머지 문구는 이렇다.

```text
WL-400 인자 검증 실패(list_tags): query 는 문자열 여야 한다: <JSON 값>
WL-400 인자 검증 실패(list_tags): limit 는 1 이상의 정수 여야 한다: <JSON 값>
WL-400 list-tags 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [limit, query] 뿐이다.
WL-400 list-tags 이 받는 자리 인자는 0 개인데 <n> 개를 받았다: list-tags [query=<태그 이름의 일부>] [limit=<받을 태그 수. 1 이상>]
WL-400 limit 은 숫자여야 한다: <다듬은 값>
WL-400 태그 개수 상한은 1 이상이다: <n>
```

이 표 밖의 실패가 1가지 있다. `LIKE` 패턴이 50,000바이트를 넘는 긴 `query`는 WL 코드가 없는 예상 밖 실패(6.6)이고, 12.9의 6번에 적었다.

## 12.5 읽는 자리와 신선도

색인의 메인 노트 태그 표를 노트 표와 이어 읽고, 노트의 층이 `reading`인 행만 센다. 태그는 프론트매터를 1.8로 읽은 값이라, 다듬어지고 노트 안에서 겹친 것이 빠지고 노트마다 50개까지다. 그래서 「그 태그를 단 노트 수」가 곧 행 수다.

하위 노트의 태그는 색인의 다른 표에 있고 이 명령은 그 표를 안 본다. 픽스처의 하위 노트 `snfixture-00000001`은 태그 `후속`과 `랭킹`을 달았는데, `후속`은 목록에 없고 `랭킹`의 개수는 메인 노트 0003의 1이다(묶음이 잰다).

값은 마지막 색인 시점의 값이다(8.3). 파일을 안 열어서 색인 뒤 디스크의 변화는 아무것도 안 보인다. 묶음은 이 낡음을 못 재고, 부를 때마다 vault를 훑는 구현도 통과한다.

## 12.6 응답

맨 위는 배열이고 원소는 `tag`, `count` 차례의 객체다. 바이트 규칙은 6.1과 같고, 맞는 태그가 없으면 `[]`다.

| 차례 | 키 | 타입 | 뜻 |
|---|---|---|---|
| 1 | `tag` | 문자열 | 태그 글자 그대로 |
| 2 | `count` | 정수 | 그 태그를 단 `reading` 층 메인 노트 수 |

차례는 `count`의 내림차순이고, 같으면 `tag` 글자의 UTF-8 바이트 차례(9.5)다. 태그는 글자가 똑같아야 같은 원소다. 대소문자만 다른 태그는 다른 원소이고, 유니코드 정규화를 안 해서 NFC와 NFD로 적힌 같은 낱말도 다른 원소다. `limit`은 이 차례로 늘어놓은 앞에서 자른다. 그래서 개수가 같은 태그 사이의 자르기도 늘 같은 자리다.

픽스처 vault에서 `list_tags '{}'`는 이 바이트를 낸다(묶음이 잰다). `랭킹`(U+B7AD로 시작)이 `실험`(U+C2E4로 시작)보다 앞이다.

```json
[
  {
    "tag": "랭킹",
    "count": 1
  },
  {
    "tag": "실험",
    "count": 1
  }
]
```

`list_tags '{"limit":1}'`은 앞의 `랭킹` 1개를 낸다. `limit` 10과 1000은 2개를 그대로 낸다. `query`가 `노트`, `a`, `설계`, `zzzz`이면 `[]`다(모두 묶음이 잰다).

## 12.7 모양이 다른 노트

| 노트 | 세는지 | 근거 |
|---|---|---|
| 폴더의 `note.json`, 단일 파일 `.md`와 `.html` | 센다. 태그는 프론트매터에서 온다 | 코드 읽기로 확인(픽스처의 이 노트들에는 태그가 없다) |
| 하위 노트 | 안 센다 | 묶음이 잰다 |
| 같은 id에서 진 쪽, 충돌 사본, 노트가 못 된 파일 | 색인에 없어 안 센다 | 코드 읽기로 확인 |
| 휴지통 노트 | 안 센다. 픽스처의 휴지통 노트가 단 `복구`가 목록에 없다 | 묶음이 잰다 |
| 기록 층 노트 | 어느 표면이든 안 센다 | 코드 읽기로 확인 |

## 12.9 받아들임 묶음과 얼어 있는 특이점

이 장에는 같은 장에서 다룰 짝 명령이 없어서 공통 절의 12.8은 두지 않는다.

묶음이 덮는 것은 도구 표면 8건이다. 전체 1건, `query` 4건(모두 빈 결과), `limit` 1, 10, 1000의 3건이다. `query`가 걸리는 경우, 대소문자, 와일드카드 글자, 명령 표면, 실패, 개수가 2 이상인 태그의 차례는 안 덮는다.

아래는 지금 엔진의 특이점이고, 표시의 뜻은 9.9와 같다. 지킬지 고칠지는 부록 D에서 정한다.

1. 하위 노트에만 쓴 태그 표기는 안 보인다. 표기 흔들림을 막는다는 쓰임과 어긋난다. 묶음이 잰다(`후속`이 `list_tags/all`에 없다).
2. `query`의 대소문자 무시가 ASCII 글자에만 걸린다. `search_docs`는 같은 태그를 유니코드 대소문자 없이 찾는다(10.9). 묶음 밖.
3. `limit=0`이 `list-docs`에서는 전부이고 여기서는 실패다. 묶음 밖.
4. 같은 수끼리의 차례가 UTF-8 바이트 차례다. `랭킹`이 `실험`보다 앞인 것은 묶음이 잰다. UTF-16 차례로 늘어놓는 구현과 갈리는 U+10000 이상 글자의 자리는 묶음 밖이다.
5. 명령 표면도 기록 층 태그를 못 본다. 앱이 기록 노트를 목록에서 볼 수 있는 것(9.2)과 다르다. 묶음 밖.
6. `query`로 지은 `LIKE` 패턴이 UTF-8로 50,000바이트를 넘으면, SQLite가 그 패턴으로 태그를 견줄 때 `LIKE or GLOB pattern too complex` 오류를 내고 명령 전체가 예상 밖 실패로 끝난다(6.6). 패턴은 `query`에 앞뒤 `%` 2바이트와 탈출용 `\`를 더한 길이라서, 한글만 쓴 `query`는 16,666자까지 받고 16,667자부터 이 실패다. 색인에 태그가 1개도 없으면 SQLite가 패턴을 쓸 일이 없어서 `[]`가 나온다. 기록 층 노트에만 태그가 있을 때 오류가 나는지는 SQLite가 조건을 견주는 차례에 달려서 정하지 못했다. 50,000은 엔진이 싣는 SQLite 라이브러리의 패턴 길이 상한이다. 코드 읽기와 그 라이브러리의 컴파일 옵션 목록으로 확인했고 실행해 보지는 않았다. 묶음 밖.
