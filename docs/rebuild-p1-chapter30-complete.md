# 30장 완료 — 답 없는 코멘트 점검

작성일: 2026-10-29

기준은 제공된 PDF 78~86쪽이다. 도구 표면 없이 `check-notes`를 `cmd/CheckNotes.java`에 연결했다. 읽기 결과만 내지만 쓰기 깃발을 따라 표식 검사와 공통 쓰기 전 준비를 거친다.

## 구현

읽기 층 루트 노트 전체에서 markdown/html 본문 파일의 도장을 다시 읽고 가장 이른 도장 순간 E를 정한다. JSON 노트의 도장은 읽지 않는다. 코멘트는 기존 `CommentsReader`의 걸러진 항목을 사용하고, 마지막 createdAt C를 오프셋 있는 날짜시각으로 고른다. 못 읽는 코멘트 파일과 시각은 판정에서 빼며, 시각이 잘못된 유효 항목도 comments 수에는 남긴다.

마지막 변경 L은 도장, 또는 E보다 앞에 만들지 않은 노트의 created다. E가 없으면 모든 노트의 created를 쓴다. C의 자기 오프셋 날짜가 기준일 14일 전 이상이며, 각자의 분 아래를 버린 순간에서 C가 L보다 뒤인 항목만 낸다. 창의 위쪽 끝은 없다. C 선택과 결과 정렬은 순간 다음 지역 날짜시각을 비교하므로 같은 순간에는 동쪽 오프셋이 늦은 값이다.

응답은 date, windowDays, count, section, items 순서다. count와 section은 items보다 앞의 개별 JSON 줄이며, section은 도장 유무에 따른 두 문장을 구별한다. 날짜시각은 `OffsetDateTime.toString()`의 초·소수 생략과 원래 오프셋을 보존한다.

## 검증

`test/withlog/Chapter30Test.java` 65개 검증: 정확한 section 글, 키 순서, 14일 경계와 미래 코멘트, 자기 오프셋 날짜, 같은 순간의 서로 다른 오프셋, 같은 분 판정, 첫 도장 이전·같은 순간의 무도장 노트, 기록 층 도장 제외, JSON 도장 생략, 단일 HTML 노트의 E 기여, 잘못된 도장·코멘트 파일, 나노초·오프셋 초, 날짜와 표면 실패를 확인했다. 실제 wl-cli에서도 점검 결과를 왕복했다.

## 유지한 경계

30.9를 유지한다. 첫 도장 하나가 생기면 그 이전 무도장 노트가 판정에서 빠지고, JSON 노트는 도장을 읽지 못한다. 미래 코멘트도 세며 section의 시각은 값마다 다른 오프셋의 벽시계다. 제목의 따옴표와 줄바꿈을 section에서 탈출하지 않는다. 읽지 못한 코멘트 파일은 이 점검의 오류로 승격하지 않는다. 영속 색인의 낡음은 기존 8.6 차이대로 재현하지 않는다.
