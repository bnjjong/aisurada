## 8번 — wl-cli와 serve 모드의 작은 결함

`wl-cli` 세부 분기는 임시 `HOME` 디렉토리를 격리 구성하여 검증했다(`cli8.sh`). 새 구현체는 JVM 시스템 속성인 `withlog.launchctl.cmd`를 통해 모의(Mock) `launchctl`을 주입받아 동작한다. 지금 엔진은 `/bin/launchctl` 바이너리를 임의로 대체할 수 없으므로, `launchctl` 프로세스 실행만을 정밀 차단하는 macOS 샌드박스(`sandbox-exec`) 격리 환경에서 구동했다. 따라서 시스템 실제 `launchd` 서비스는 전혀 호출되지 않았다.

| 검증 분기 | 지금 엔진 | 옛 판 | 새 판 |
|---|---|---|---|
| `sweep --dry-run`, `WITHLOG_VAULT`를 끝 슬래시(`/`), 상대 경로, `./`로 전달 | 현재 vault 대상 제외 (대상 1개) | 현재 vault도 대상에 포함 (대상 2개) | 현재 vault 대상 제외 (대상 1개) |
| UTF-8이 아닌 비정상 plist 존재 및 사이드카 미기동 | 종료 코드 1 반환, plist 보존 | plist 강제 덮어쓰기 후 기동, 종료 코드 0 | 종료 코드 1 반환, plist 보존 |
| UID 판독 실패 상황에서 사이드카 프로세스 정상 기동 중 | 정상 종료 (종료 코드 0) | 비정상 종료 (종료 코드 4) | 정상 종료 (종료 코드 0) |
| 첫 번째 `bootout` 명령 실행 실패 | 예외 발생 후 종료 코드 4 반환 | 실패 무시 후 기동 진행, 종료 코드 0 | 예외 발생 후 종료 코드 4 반환 |
| `--list` 옵션 출력 형식 | 상세 긴 설명 출력 | `create_doc — create_doc 도구` 형태의 단순 자리표 | 각 도구별 1줄 요약 설명 |

첫 번째 `bootout` 검증의 경우, 양측이 동일한 조건의 실패 환경을 완벽히 모사하지는 못했다. 새 구현체는 10초 타임아웃을 유발시켰고, 지금 엔진은 프로세스 실행 자체를 차단하여 기동 실패를 유도했다. 다만 지금 엔진 소스 코드 분석 결과, 기동 실패와 10초 타임아웃 모두 동일한 예외 클래스(`LaunchControlException`)를 발생시켜 최종적으로 종료 코드 4로 매핑됨을 검증했다(지금 엔진 wl-cli 소스의 `LaunchControl.kt` 내 `runProgram` 및 `WlCli.kt` 내 `run`). `--list`의 세부 설명 문구는 설명서 3.3 규약상 엄격한 명세 계약 대상이 아니므로 결함 판정에서 제외했다.

serve 모드가 파일 락을 획득하고 실행 상태 파일(pid/state)을 기록한 뒤 유닉스 소켓을 바인딩하기 직전에 SIGTERM 신호를 수신하는 경계 상황은, 실행 상태 파일이 디스크에 생성되는 즉시 프로세스에 SIGSTOP 신호를 전달하여 동기화했다(`serve-signal.mjs`). 5회 반복 시험 모두 소켓이 열리기 직전에 정밀하게 중단되었다.

| 점검 항목 | 지금 엔진 | 옛 판 | 새 판 |
|---|---|---|---|
| 프로세스 종료 코드 | 143 | 143 | 143 |
| 실행 상태 파일 (state) | 5회 모두 자동 삭제 | 5회 모두 디스크 잔류 | 5회 모두 자동 삭제 |
| 유닉스 소켓 파일 | 5회 모두 잔류 | 생성되지 않음 | 생성되지 않음 |

설명서 3.2의 「내려가는 차례」 규약에 따르면 외부 신호(Signal)로 종료될 때도 실행 상태 파일은 반드시 정리되어야 한다. 옛 판은 셧다운 훅(Shutdown Hook) 등록을 소켓 생성 이후에 수행했기 때문에 그 이전 단계에서 수신한 신호에 대해서는 정리 로직이 동작하지 못했다. 한편 지금 엔진에 소켓 파일이 잔류하는 이유는 신호가 도달하는 찰나의 순간에도 내부 비동기 bind 작업이 완결되어 파일이 생성되었기 때문이며, 다음 엔진 인스턴스가 bind 수행 직전 기존 소켓을 선제 삭제하므로 문제가 없다(지금 엔진의 소켓 서버 `SidecarSocketServer.kt` 내 `bindAddress`).

참조 비교 처리는 색인 과정을 거친 분류 및 평가 메모에 한해 `?` 식별자를 덧붙이는 로직이다(설명서 11.6 및 15.9의 4번 항목). 옛 판은 「인자 객체와 색인 값 객체의 동일성(`===`)」 여부로 분기 처리했으나, 새 판은 호출부에서 직접 처리하도록 리팩토링되었다. 해당 필드에 짝이 맞지 않는 고립 서로게이트(Unpaired Surrogate) 문자를 주입한 노트를 대상으로 15장 쓰기 명령 3종과 `update_doc`을 실행했다(`sc-surr.mjs`). 색인 값은 `라벨?끝`, 인자 값은 `새?라벨` 형태로 디스크에 기록되었으며, 옛 판과 새 판 모두 바이트 단위까지 지금 엔진과 완벽히 일치했다.

## 그대로 남은 것

- `withlog 1부 다시 짜기 18장 판 확인 — 새 쓰기 4개는 지금 엔진과 같고, 공용 쓰기 도우미에 설명서와 다른 곳 2곳`에서 식별된 공용 파일 쓰기 도우미 `AtomicWriter` 관련 차이점 2곳이 여전히 유지된다. 비어 있는 디렉토리 위치에 첨부 파일을 저장할 경우 새 구현체는 디렉토리를 삭제한 뒤 파일을 작성하며, `attach` 경로에 이미 일반 파일이 존재하는 경우 실패 에러 메시지 형식이 상이하다. 14종의 파일 시스템 레이아웃 환경에서 재시험을 진행해도 동일하게 2가지 차이가 확인되었다.
- 8번 항목 중 테스트 전용 JVM 시스템 속성 3종이 제품 코드 내에 여전히 포함되어 있다. 테스트용 시각 및 난수 시드를 제어하는 `TestApparatus`의 `withlog.test.now`, `withlog.test.random`과 명령어 실행기 `EngineExecutor.java:53`의 `withlog.test.session.id`가 해당되며, 마지막 속성이 활성화될 경우 세션 ID가 누락된 Claude 쓰기 호출 시에도 세션 ID를 임의로 날인한다.
- E21w 동작 차이가 그대로 남아 있다. 이미 색인된 vault 환경에서 코멘트 파일 1개가 손상될 경우 지금 엔진은 정상적으로 쓰기를 수행하지만, 새 구현체는 모든 쓰기 호출을 종료 코드 1로 전면 거절한다. 이번 6번 수정으로 인해 동일 vault 내 읽기 작업 시에도 해당 손상 노드가 조회 결과에서 누락된다.
- 설명서 수정 요구사항 5곳이 확정되지 않은 상태로 유지되고 있으며, 문서 개정은 아직 반영되지 않았다. 4번 항목(설명서 8.6 마지막 줄에 쓰기 거절 동작을 명문화하는 부분)이 향후 E21w의 공식 스펙을 결정지을 기준점이다.
