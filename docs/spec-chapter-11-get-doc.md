# withlog 1부 vault 엔진 설명서 > 11장 명령 get_doc

`get_doc`은 노트 1건을 본문과 코멘트까지 읽고, vault는 안 바꾼다. 이 장은 부르는 꼴, 검사 차례, 실패, 응답 바이트를 정하고, 변형 명령 `get_sub_note`도 함께 정한다.

- 노트가 있는지와 메타는 마지막 색인 시점의 값이고, 본문과 토큰과 도장과 `sessionId`와 코멘트와 사실층은 부를 때 파일에서 읽는다.
- WL 실패는 모두 stdout이 비고 종료 코드 3이며, `WL-400`, `WL-404`, `WL-409`가 이유를 가른다. vault나 명령 이름을 못 정한 실패는 코드 없이 2이고, 부팅 실패와 예상 밖 예외는 단발 모드에서 1이다(코드 읽기).
- 성공 응답은 `JSON.stringify(값, null, 2)`에 줄바꿈 1개를 붙인 바이트이고, 키 차례가 계약이다. `JSON.stringify`와 갈리는 자리는 짝 없는 서로게이트 1가지다.
- 근거: 묶음 115건(`get_doc` 111건, `get_sub_note` 4건)이 이 장을 덮는다. 그 가운데 성공 113건은 응답 바이트를 재고, 실패 2건은 종료 코드와 빈 stdout만 잰다. WL 번호, 명령 표면, 기록 층, 사실층, 도장, 색인 낡음은 코드 읽기로만 확인했다.

## 11.1 한눈에

도구 이름은 `get_doc`, 명령 이름은 `get-doc`이다. 쓰기 깃발이 없어서 워크스페이스 표식을 안 보고 색인도 안 맞춘다. 읽는 자리는 6곳이다.

| 자리 | 무엇을 읽나 | 언제 |
|---|---|---|
| 색인 | 노트가 있는지, 메타, 경로, 포맷, 아젠다 id | 늘 |
| 본문 파일 | 본문, 토큰, 도장, `sessionId` | 늘. json 노트는 안 연다 |
| 코멘트 파일 | `comments` | 층 검사를 지난 뒤 |
| 아젠다 색인 | `agenda`, `agendaTitle` | 늘 |
| 사실층 파일 | `agendaFacts` | 도구 표면에서 층 검사를 지난 뒤 |
| 메인 노트의 HTML 첨부 | 응답에 안 쓰는 검색 평문 | 색인에 `.htm`, `.html` 첨부가 있을 때(11.5) |

본문 파일과 HTML 첨부는 노트를 색인에서 꺼내는 걸음에서 읽혀서, 도구 표면이 기록 층 노트를 거절하기(11.3) 전에 이미 읽힌다.

이 명령은 노트를 고치기 직전에 부르는 자리라서, 사용자가 남긴 코멘트를 놓치지 않게 함께 싣는다. 토큰과 코멘트를 본문 앞에 두는 이유도 같다. Claude는 응답을 출력 상한이 있는 셸 출력으로 받아서, 긴 본문의 뒤가 잘려도 토큰과 코멘트는 닿아야 한다.

근거: 읽는 자리와 차례는 코드 읽기로 확인했다.

## 11.2 부르는 법

| 표면 | 꼴 | 쓰는 쪽 |
|---|---|---|
| 도구 | `get_doc '{"id":"<노트 id>"}'` | Claude와 스킬 |
| 명령 | `get-doc <노트 id>` | 앱과 사람 |

꼴 2가지는 같은 처리로 간다. 응답이 다른 자리는 도구 표면만 `agendaFacts`를 싣고 층이 `record`인 노트를 거절하는 것뿐이다. 첫 칸은 도구 이름에서 먼저, 명령 이름에서 다음에 찾고 대소문자를 가린다. 스킬이 부르는 도구 이름이 계약이라, 이름이 겹쳐도 그쪽이 이기게 하려는 차례다.

단발 모드(명령 1개를 처리하고 끝나는 실행, 3.1)에서 묶음의 어댑터는 아래 argv로 엔진을 부른다. 실행기는 셸 없이 칸을 그대로 넘기고, 아래는 읽기 쉽게 칸을 빈칸으로 이어 적었다.

```text
${WLX_IMPL_JAVA} -XX:TieredStopAtLevel=1 -Xmx512m -XX:-UsePerfData -Duser.home=${HOME} -Djava.io.tmpdir=${TMPDIR} -jar ${WLX_IMPL_JAR} get_doc {"id":"ndfixture-00000002"} --withlog.vault=${WITHLOG_VAULT} --withlog.db.home=${WLX_STATE_DIR}/db
```

`-jar ${WLX_IMPL_JAR}`까지가 어댑터의 앞 조각이고, 명령 이름과 JSON 1칸이 케이스의 argv이고, 뒤 2칸이 어댑터의 뒤 조각이다. 환경은 실행기가 처음부터 지어서 아래 변수만 있다.

| 변수 | 값 |
|---|---|
| `PATH`, `WLX_IMPL_`로 시작하는 변수 | 실행기를 부른 셸의 값 |
| `WITHLOG_VAULT` | 입력 vault를 펼친 절대 경로 |
| `HOME` | 입력 HOME을 펼친 절대 경로 |
| `TMPDIR` | 빈 임시 폴더 |
| `WLX_STATE_DIR` | 구현이 상태를 두는 빈 폴더 |
| `TZ` | `Asia/Seoul` |
| `LANG`, `LC_ALL` | `en_US.UTF-8` |

경로는 모두 `realpath`를 지난 값이다. 작업 폴더는 실행기를 부른 자리를 물려받고, 호출 1번을 120초까지 기다린다. stdin은 README가 「닫혀 있다」고 적는 자리이고, 실행기는 그 자리를 `/dev/null`에 이어 준다. 구현이 읽으면 곧바로 끝을 만난다. `-Duser.home=${HOME}`이 붙는 까닭은 JVM이 `user.home`을 `HOME`이 아니라 운영체제 계정에서 얻기 때문이다(묶음 README가 적는다). 다시 짠 구현은 같은 argv와 환경을 받는 자기 어댑터를 적고, JVM 칸은 안 따라도 된다.

지금 엔진이 `user.home`을 쓰는 자리는 3곳이다. 1부 명령의 단발 모드에서는 `withlog.db.home`의 기본값 1곳뿐이다. serve 모드는 실행 상태 파일과, `WITHLOG_SIDECAR_SOCKET`이 없을 때의 소켓 자리에도 쓰고(3.2), 4부의 세션 명령은 그 아래 `.claude/projects`를 읽는다(32장). 기기 위 파일의 목록은 33.3에 있다. `get_doc`과 `get_sub_note`에는 `withlog.db.home` 기본값만 걸린다. `user.dir`은 프로세스의 작업 폴더다.

argv는 이 차례로 다룬다.

1. 끝 2칸이 세션 표식이면 먼저 뗀다. 표식의 모양은 1.10에 있다. 운영체제 argv에는 U+0000을 실을 수 없어서, 단발 모드에는 표식이 올 수 없고 소켓 요청에만 온다. 읽기에는 영향이 없다.
2. 첫 칸이 명령 이름이다. `--`로 시작해도 명령 이름으로 본다. 그래서 설정을 명령보다 앞에 두면 `모르는 명령이다: --withlog.vault=…`와 종료 코드 2로 선다.
3. argv가 비면 `모르는 명령이다: (없음)`과 종료 코드 2다. vault 검사(1.1)를 먼저 지나야 이 줄에 온다.
4. 나머지 칸 가운데 자리와 상관없이 `--`로 시작하는 칸은 인자 해석에서 뺀다. `--`만 든 칸도 뺀다. 그 칸들은 스프링이 설정으로 읽는다(1.1).

`wl-cli`를 거치면 같은 argv가 소켓으로 serve 모드 엔진에 가고 결과 바이트는 같다. 단발 모드의 stderr에만 엔진 로그 줄이 섞인다.

엔진이 받는 설정은 아래 7개다. 이름 맞추기와 우선순위는 1.1과 같다(명령줄, JVM 속성, 환경변수 차례). 환경변수 이름은 점을 `_`로 바꾸고 대문자로 올린 이름이다.

| 설정 이름 | 환경변수 | 기본값 | 뜻 | 장 |
|---|---|---|---|---|
| `withlog.vault` | `WITHLOG_VAULT` | 없음. 필수 | vault 뿌리 | 1.1 |
| `withlog.db.home` | `WITHLOG_DB_HOME` | `<user.home>/Library/Application Support/withlog/db` | 색인 폴더들의 부모 폴더 | 8.2 |
| `withlog.notes.shard.by.month` | `WITHLOG_NOTES_SHARD_BY_MONTH` | 없음. 디스크로 정한다 | 샤드 판정 덮기 | 1.3 |
| `withlog.vault.snapshot.enabled` | `WITHLOG_VAULT_SNAPSHOT_ENABLED` | `false` | 덮기 직전 스냅숏 | 31.6 |
| `withlog.vault.autocommit.enabled` | `WITHLOG_VAULT_AUTOCOMMIT_ENABLED` | `true` | 자동 커밋 | 31.1 |
| `withlog.vault.autocommit.idle.seconds` | `WITHLOG_VAULT_AUTOCOMMIT_IDLE_SECONDS` | `300` | 유휴 커밋까지의 초 | 31.1 |
| `withlog.idle.timeout.minutes` | `WITHLOG_IDLE_TIMEOUT_MINUTES` | `10` | serve 모드 유휴 종료까지의 분 | 3.2 |

값은 설정마다 이렇게 바꾼다. 바꾸지 못하면 부팅이 실패하고(11.4), 그 실패는 단발 모드의 `get_doc`에서도 난다. 엔진이 모든 설정을 부팅 때 한꺼번에 바꾸기 때문이다.

| 설정 | 받는 값 | 빈 값, 공백뿐, `=` 없는 칸 | 그 밖의 값 |
|---|---|---|---|
| `withlog.notes.shard.by.month` | 앞뒤의 U+0020 이하 글자를 떼고 대소문자를 안 가려 `true`, `on`, `yes`, `1`, `false`, `off`, `no`, `0` | 설정이 없는 것과 같다 | 부팅 실패 |
| `withlog.vault.snapshot.enabled`, `withlog.vault.autocommit.enabled` | 같다 | 부팅 실패 | 부팅 실패 |
| `withlog.vault.autocommit.idle.seconds`, `withlog.idle.timeout.minutes` | 글 안의 공백 글자를 모두 지운 뒤 읽은 64비트 정수. 맨 앞 `-` 1개를 건너 `0x`, `0X`, `#`로 시작하면 16진이고, 아니면 앞에 `+`나 `-`가 붙어도 되는 10진이다. `010`은 10, `3 00`은 300, `-0x10`은 -16이고, `+0x10`은 실패다. 숫자 글자는 전각 `３` 같은 유니코드 10진 숫자도 받는다. 0과 음수도 받는다 | 부팅 실패 | 부팅 실패(수 아님, 소수, 64비트 밖) |
| `withlog.db.home` | 글 그대로의 경로. 다듬지 않고, 상대 경로면 작업 폴더에 붙인다 | 기본값 | 없음 |

0과 음수의 뜻은 serve 모드에만 걸린다. 유휴 종료 시간이 0 이하면 유휴 종료를 안 하고(3.2), 유휴 커밋 시간이 0 이하면 쓰기 뒤 다음 정비 때 커밋한다(31.1). 「공백뿐」은 설정마다 다르다. 불리언은 U+0020 이하 글자만 공백으로 본다. 수는 1장의 다듬기 글자에서 U+00A0, U+2007, U+202F 3개를 뺀 글자를 공백으로 보고 글 안에서 모두 지우며, 그 3개가 남으면 수가 아니라서 부팅 실패다. `withlog.db.home`은 1장의 다듬기로 본다.

- 엔진이 모르는 이름은 조용히 무시한다. 다만 `spring.`이나 `logging.`으로 시작하는 이름은 지금 엔진의 틀(스프링 부트 3.5.3)이 읽어서 동작이 바뀐다. 예를 들어 `--spring.main.banner-mode=console`을 주면 스프링 배너가 stdout에 찍혀 응답 JSON 앞에 붙고, `--logging.config=<파일>`은 로그를 stdout으로 돌릴 수 있다. 환경변수 `SPRING_APPLICATION_JSON`도 설정을 줄 수 있다. 이 이름들은 계약이 아니고 묶음도 안 준다. 다시 짠 구현은 모두 무시해도 된다.
- `--=x`처럼 이름이 빈 칸은 스프링이 거절해 부팅이 실패한다. `--`만 든 칸이 있으면 스프링은 그 뒤 칸을 설정으로 안 읽는다.
- `withlog.db.home`의 색인 파일은 그 폴더의 `<VaultKey>/meta.db`이고, 이 배치는 지금 엔진의 것이지 계약이 아니다(11.5).

엔진이 설정을 거치지 않고 직접 보는 환경변수는 `WITHLOG_VAULT`(1.1의 사전 검사)와 `WITHLOG_SIDECAR_SOCKET`(serve 모드의 소켓 자리, 3.2) 2개다. `WLX_STATE_DIR`은 안 본다. `TZ`와 `LANG` 같은 변수는 JVM이 읽어 시간대와 출력 부호화에 쓴다(11.6).

근거: 설정 표, 값 바꾸기, argv 차례는 코드 읽기와 스프링 6.2.8, 스프링 부트 3.5.3 소스로 확인했다. 어댑터의 argv와 환경은 `fixtures/expect`의 README와 어댑터 파일에서 옮겼다. 묶음이 쓰는 꼴(명령 이름, JSON 1칸, 뒤에 붙인 `--` 설정 2칸)만 묶음이 잰다.

## 11.3 인자와 검증

도구 표면은 이 차례로 본다.

1. `--`로 시작하는 칸을 뺀 인자가 0칸이나 1칸이어야 한다. 2칸 이상은 셸 따옴표를 빠뜨린 경우라 조용히 버리지 않고 거절한다.
2. 1칸이면 다듬는다. 없거나 비면 `{}`다. BOM은 다듬기 대상이 아니라 남고, 아래 3번에서 파싱 실패가 된다.
3. JSON으로 읽는다. 읽개 규칙은 아래 표에 있다. 따옴표 없는 값을 문자열 아닌 리터럴로 받아서, `get_doc ndfixture-00000001`은 파싱 실패가 아니라 「인자는 JSON 객체여야 한다」로 가고, `{"id": ndfixture-00000001}`은 「id 는 문자열 여야 한다」로 간다.
4. 최상위가 객체여야 한다.
5. 키는 `id`만 받는다. 오타 키가 조용히 무시되면 안 되기 때문이다.
6. `id` 키가 있어야 한다. JSON `null`은 키가 있는 것이라 7번으로 간다.
7. `id`가 JSON 문자열이어야 한다. 수, 불리언, `null`, 따옴표 없는 리터럴, 배열, 객체는 거절한다.

`id` 값은 다듬지 않는다. 길이 상한은 없고, serve 모드에서 프레임 상한(4.1)만 걸린다.

JSON 읽개는 kotlinx.serialization 1.6.3의 기본 설정이다. 코멘트 파일(1.12)도 같은 읽개로 읽는다. 다른 언어로 옮길 때 맞출 규칙은 이렇다.

| 입력 | 결과 |
|---|---|
| 토큰 사이 공백 | U+0020, 탭, LF, CR 4자뿐이다. 다른 공백 글자는 리터럴의 일부가 되거나 오류다 |
| 따옴표 없는 리터럴 | 값 자리에서 받는다. 위 공백 4자, `,` `:` `{` `}` `[` `]` `"` `\`, U+0000부터 U+001F를 만날 때까지가 리터럴 1개다. 내용은 검사하지 않아서 `hello`, `NaN`, `01`, `1.50`, `'x'`가 모두 문자열 아닌 값이다. 리터럴이 정확히 `null`이면 JSON `null`이다 |
| `hello world`, `a:b`(따옴표 없이) | 리터럴 뒤에 글이 남아 파싱 실패 |
| `{"id": 'x'}` | 홑따옴표까지 든 리터럴 `'x'`라서 「문자열 여야 한다」 |
| 키 | 늘 큰따옴표 문자열이어야 한다. 따옴표 없는 키와 홑따옴표 키는 파싱 실패 |
| 문자열 안의 날 제어 글자 | 탭과 줄바꿈까지 그대로 받는다 |
| 탈출 | `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`와 16진 4자리 `\uXXXX`만 받는다. `\x` 같은 것은 파싱 실패다. `\ud800`은 짝 없는 서로게이트가 된다 |
| 값 뒤에 남은 글 | `{} x`, `{}{}`는 파싱 실패 |
| 앞 쉼표, 끝 쉼표 | 파싱 실패 |
| 같은 키 | 마지막 값이 이기고, 자리는 처음 나온 자리다 |
| 깊은 중첩 | 상한이 없다. 객체는 200겹부터 스택을 안 쓰는 읽기로 바꾸지만 배열은 늘 재귀로 읽어서, 아주 깊은 배열은 스택이 넘쳐 예상 밖 실패가 날 수 있다(11.9) |

명령 표면은 `--`로 시작하는 칸을 빼고 나머지를 앞에서부터 본다. 첫 `=`가 맨 앞이 아닌 칸은 옵션이고, `=` 앞 글자를 다듬은 것이 옵션 이름이다. `get-doc`은 옵션이 없어서 그런 칸을 만나는 즉시 거절한다. `=x`처럼 `=`가 맨 앞인 칸은 자리 인자다. 모든 칸을 본 뒤 자리 인자가 2칸 이상이면 거절한다.

표면 2가지 모두 그다음 이 차례로 본다.

1. id가 없거나 공백뿐이면 거절한다. 빈 셸 변수를 모양 오류로 오해하지 않게 하려는 검사다. 문구는 도구 표면에서도 명령 표면의 사용법을 적는다.
2. id가 `^nd[0-9a-z]+-[0-9a-f]{8}$`이어야 한다. 공백이 붙거나 대문자가 있거나 `sn…`이면 틀린 모양이다.
3. 색인에 그 id의 노트가 있어야 한다.
4. 도구 표면이면 그 노트의 층이 `reading`이어야 한다.

근거: 틀린 모양 1건(`get_doc/missing`)의 종료 코드만 묶음이 잰다. 차례와 JSON 읽개의 세부는 코드 읽기로 확인했고, 읽개는 같은 계열인 kotlinx.serialization 1.5.1 소스를 읽고 1.6.3 jar의 오류 문구와 맞대 보았다.

## 11.4 실패

| 차례 | 조건 | 표면 | 종료 | 코드 |
|---|---|---|---|---|
| 1 | vault 값 없음(1.1의 사전 검사) | 공통 | 2 | 없음 |
| 2 | 부팅 실패(vault 값이 없거나 비었거나 폴더가 아님, 색인 폴더를 못 만듦, 설정 값 변환 실패) | 공통 | 1(코드 읽기) | 없음 |
| 3 | 모르는 이름이나 빈 argv | 공통 | 2 | 없음 |
| 4 | 인자 2칸 이상 | 도구 | 3 | `WL-400` |
| 5 | JSON이 아님 | 도구 | 3 | `WL-400` |
| 6 | 객체가 아님 | 도구 | 3 | `WL-400` |
| 7 | `id` 밖의 키 | 도구 | 3 | `WL-400` |
| 8 | `id` 없음 | 도구 | 3 | `WL-400` |
| 9 | `id`가 문자열이 아님 | 도구 | 3 | `WL-400` |
| 10 | `이름=값` 칸 | 명령 | 3 | `WL-400` |
| 11 | 자리 인자 2칸 이상 | 명령 | 3 | `WL-400` |
| 12 | id가 비었음 | 공통 | 3 | `WL-400` |
| 13 | id 모양이 틀림 | 공통 | 3 | `WL-400` |
| 14 | 색인에 없음 | 공통 | 3 | `WL-404` |
| 15 | 층이 `record` | 도구 | 3 | `WL-409` |
| 16 | 노트 경로의 폴더 이름 1개가 공백 글자로만 됨(코멘트 파일 경로를 못 지음) | 공통 | 3 | `WL-400` |
| 17 | 예상 밖 예외 | 공통 | 단발 모드는 1(코드 읽기), serve 모드는 3 | 없음 |

실패하면 stdout은 늘 0바이트다. WL 실패의 stderr는 진단 줄(이 명령에는 없다) 뒤 `WL-<번호> <문구>`와 줄바꿈 1개로 끝나고, 단발 모드에서는 그 앞에 엔진 로그 줄이 섞인다. 지금 문구는 표 차례대로 이렇다. `<원문>`은 다듬은 인자 글이다.

```text
WITHLOG_VAULT 환경변수가 없다. vault 폴더의 절대 경로를 넣고 다시 실행한다.
설정으로 주려면 --withlog.vault=<경로> 를 붙인다.
모르는 명령이다: <이름>
WL-400 get_doc 이 받는 인자는 JSON 한 덩어리인데 <n> 개를 받았다. 셸에서 따옴표로 감쌌는지 본다: get_doc '{"키":"값"}'
WL-400 인자 JSON 파싱 실패(get_doc): <원문>
WL-400 인자 검증 실패(get_doc): 인자는 JSON 객체여야 한다: <원문>
WL-400 인자 검증 실패(get_doc): 모르는 키다: [<정렬한 키들>]. 쓸 수 있는 것은 [id] 뿐이다.
WL-400 인자 검증 실패(get_doc): id 가 필요하다.
WL-400 인자 검증 실패(get_doc): id 는 문자열 여야 한다: <압축한 JSON 값>
WL-400 get-doc 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [] 뿐이다.
WL-400 get-doc 이 받는 자리 인자는 1 개인데 <n> 개를 받았다: get-doc <노트 id>
WL-400 인자가 하나 필요하다: get-doc <노트 id>
WL-400 노트 id 모양이 아니다: <받은 값>
WL-404 Note not found: <노트 id>
WL-409 도구 표면이 읽을 수 없는 노트다(층=record): <노트 id>. 기계가 남긴 기록 노트는 앱에서만 열립니다.
WL-400 빈 경로 조각은 결합할 수 없다: 기준=<공백뿐인 폴더 바로 위 폴더의 절대 경로>
```

계약은 stderr에서 처음 나오는 `WL-` 번호 1개다. 묶음의 `wl` 칸이 이것만 맞대고, 지금 읽기 레인에는 그 칸이 아직 없다. `WL-` 뒤의 문구, 줄 끝 줄바꿈, 앞에 오는 로그 줄은 지금 엔진의 모양이라 계약이 아니다. 다시 짠 구현은 진단 줄과 로그 없이 `WL-` 줄 1줄만 내도 된다. 문구 안의 자리표도 모양만 적어 둔다. `<정렬한 키들>`은 모르는 키를 UTF-16 코드 단위 차례로 늘어놓아 `, `로 이은 글이다. `<압축한 JSON 값>`은 받은 값을 빈칸 없이 다시 적은 글이다. 문자열은 큰따옴표로 감싸 다시 탈출하고, 따옴표 없는 리터럴과 수는 받은 글자 그대로 둔다. 1.10의 `frontmatter 에 쓸 수 없는 값이다: <타입> (<값>)`처럼 `<값>`이 시간대나 실행마다 달라지는 문구도 있다.

vault 값이 없으면 첫 2줄이 stderr 전부이고, 엔진이 뜨기 전이라 번호가 없다. `모르는 명령이다` 뒤에는 도구 이름 목록과 명령 사용법이 여러 줄 붙는데, 그 줄들은 계약이 아니다. 기록 층을 404가 아닌 409로 거절하는 이유는, 없다고 답하면 부르는 쪽이 노트가 사라진 줄 알고 같은 노트를 다시 만들기 때문이다.

16번은 훑기가 세운 노트인데도 응답을 못 짓는 갈래다. 엔진은 코멘트 파일 경로를 노트 경로의 `/` 조각마다 이어 짓고, 1장의 다듬기 글자로만 된 조각을 거절한다. 그래서 `notes/serving/ /note.md`처럼 폴더 이름이 U+0020 1자인 노트는 색인에 있어도 `get_doc`이 이 문구로 선다. 기준 경로는 그 조각 바로 위 폴더의 절대 경로이고, 위 예에서는 `<vault>/notes/serving`이다. 층 검사 뒤에 코멘트를 읽어서, 도구 표면의 기록 층 노트는 `WL-409`가 먼저다. `get_sub_note`도 직계 컨테이너 경로에 그런 조각이 있으면 같다.

부팅 실패는 스프링이 뜨는 도중의 실패라 WL 줄이 없다. stderr에 스프링의 실패 로그가 나오고 그 안에 원인 문구(1.1)가 든다. 색인 폴더와 스키마도 부팅 때 만들어서, `withlog.db.home`에 못 쓰는 경우도 여기 든다. 엔진은 이 갈래의 종료 코드를 정하지 않고, 예외가 `main` 밖으로 나가 JDK 실행기가 1로 끝낸다. 실행해 보지는 않았다. 다시 짠 구현은 6.6의 시작 실패 규칙대로 종료 코드 1과 0바이트 stdout으로 끝낸다(1.1).

예상 밖 예외는 엔진이 잡지 않는다. 버그의 스택 트레이스를 남기려고 그렇게 둔다. `get_doc`에서 생길 수 있는 자리는 4곳이다. 색인 DB 오류, HTML 첨부를 읽다 난 입출력 오류(11.5), 색인 뒤에 바뀐 본문 파일의 프론트매터에 든 1.8의 안 잡히는 표기, 아주 깊게 겹친 배열이 든 코멘트 파일(11.3)이다. 단발 모드는 stdout 0바이트에 스프링 실패 로그와 스택 트레이스를 남기고 종료 코드 1로 끝난다(부팅 실패와 같은 규칙, 실행해 보지 않았다). serve 모드는 상태 3, 오류 코드 칸 0, stderr 1줄로 답하고, 그 앞에 쌓인 진단 줄은 버린다.

```text
사이드카 안에서 실패했다: <예외 문구, 없으면 예외 종류 이름>. 자세한 것은 사이드카 로그에 있다.
```

`wl-cli`가 serve 모드 엔진에 닿지 못하면 `wl-cli`가 종료 코드 4를 낸다(3.3). 엔진 자신은 이 명령에서 4, 5, `WL-412`, `WL-500`을 안 낸다. 코멘트 파일을 못 읽는 것은 실패가 아니라 `unreadable` 봉투로 답한다(11.6). 묶음의 `get_doc/missing`(`nd없는노트`)은 모양 검사의 `WL-400`이지만, 묶음이 아직 번호를 안 맞대서 종료 코드 3과 빈 stdout만 본다.

근거: 실패 1건의 종료 코드와 빈 stdout만 묶음이 잰다. 번호, 문구, 부팅 실패, 예상 밖 예외의 갈래는 코드 읽기로 확인했다.

## 11.5 읽고 쓰는 자리

노트는 색인에서 찾는다. 색인은 `reindex`, `reindex-paths`, 쓰기 명령만 맞추고 엔진은 뜰 때도 안 훑어서, 색인을 안 지은 vault의 `get_doc`은 모두 `WL-404`다. 읽기 앞에서 안 맞추는 이유는 손해의 크기가 다르기 때문이다. 낡은 읽기는 다음 훑기가 고치지만 낡은 쓰기는 사용자 글을 지우고, 읽기마다 맞추면 부를 때마다 vault 전체를 훑게 된다. 이 명령은 아무것도 안 쓴다.

| 값 | 출처 | 시점 |
|---|---|---|
| 노트가 있는지, `type`, `title`, `created`, `date`, `time`, `mins`, `tier`, `format`, `path`, `tags`, `links`, `favorite`, `favoriteCategory`, `template`, `evaluation`, 아젠다 id | 노트 색인 | 마지막 색인 |
| `agenda`, `agendaTitle` | 아젠다 색인 | 마지막 색인 |
| `body`, `precondition`, 도장, `sessionId` | 본문 파일. 1번 읽고 1번 해석한다 | 부를 때 |
| `comments`, `agendaFacts` | 그 파일 | 부를 때 |

「있는 노트」는 마지막 색인에서 1.2의 훑기가 세운 노트다. 그래서 같은 id 2벌은 이긴 쪽을 내고 충돌 사본은 `WL-404`다. 본문 파일은 색인의 경로와 포맷으로 정한다. 폴더 노트면 `<path>/note.md`, `<path>/note.json`, `<path>/note.html` 가운데 색인 포맷의 것이고, `path`의 마지막 조각이 정확히 `.md`, `.html`, `.json`으로 끝나면 그 경로 자체다. json 노트는 본문 파일을 안 연다(json 노트를 읽는 규칙은 1.13의 표에 모았다).

부를 때 본문 파일을 읽으면 1.6과 1.8대로 YAML 조각 전체를 짓지만, 쓰는 값은 본문과 도장 3개와 `sessionId`뿐이다. `id`, `created`, `mins`, `evaluation`, `tags`는 안 본다. 그래서 색인 뒤에 파일에서 `id`가 사라지거나, `created`가 깨지거나, `mins: .nan`이나 `evaluation.score: .nan`이 생겨도 `get_doc`은 성공하고 그 메타는 색인의 옛 값이다. 다만 YAML을 짓는 단계의 실패는 그대로 따른다. 문법 오류처럼 잡히는 실패면 프론트매터가 없는 파일로 보고, 1.8의 안 잡히는 4갈래면 예상 밖 실패다.

색인 뒤에 파일이 바뀌면 메타는 색인 값 그대로이고 본문 쪽만 새로 읽힌다.

| 색인 뒤에 바뀐 것 | 응답 |
|---|---|
| 본문 파일이 사라짐, 1,000,000바이트 초과, UTF-8이 아님, 입출력 오류 | 종료 코드 0. `body`는 빈 글이고 `precondition`, 도장, `sessionId`가 없다 |
| 프론트매터를 못 읽게 됨(울타리 없음, YAML 문법 오류처럼 잡히는 실패, 맵 아님, 16,000단위 초과) | `body`는 파일 글 전체다. BOM을 포함하고 줄바꿈 떼기도 안 한다. `precondition`은 그 파일의 토큰이고, 도장과 `sessionId`가 없다 |
| 파일의 `id`나 메타 값이 바뀜, 메타에 `.nan`이 생김 | 메타는 색인 값 그대로이고, `body`, 토큰, 도장, `sessionId`는 새 파일의 값이다. 다른 노트의 도장이 섞여 나올 수 있다 |
| `note.md`가 지워지고 `note.html`이 생김 | 색인 포맷(`markdown`)대로 `note.md`를 찾다가 첫 줄과 같이 답한다. `format`은 `markdown`이다 |
| 노트 폴더가 옮겨짐 | 색인 경로에 본문 파일이 없어 첫 줄과 같다. 코멘트는 옛 경로를 봐서 `absent`다 |
| 프론트매터에 1.8의 안 잡히는 표기가 생김 | 예상 밖 예외(11.4) |

묶음은 펼친 vault마다 케이스 앞에 준비 걸음 `reindex`를 1번 부르고, 그 걸음은 종료 코드 0이면 된다. README는 색인이 없는 구현이 이 걸음에서 아무것도 안 하고 0으로 끝나도 된다고 적는다. 케이스는 나란히 돌고 vault, HOME, `WLX_STATE_DIR`, `TMPDIR`을 같이 쓴다. 그래서 구현은 같은 vault를 동시에 읽는 호출을 견뎌야 하고, 준비 걸음이 지은 색인을 케이스가 지우면 안 된다. 읽기 레인은 준비 걸음을 포함해 vault와 HOME을 바꾸면 안 된다. 묶음은 준비 걸음 뒤로 vault를 안 바꾸므로, 색인을 지어 두는 구현도 부를 때마다 디스크를 훑는 구현도 묶음을 통과한다. 2가지 구현이 갈리는 것은 묶음 밖의 일이다. `reindex`를 1번도 안 부른 vault에서 지금 엔진은 모든 id에 `WL-404`를 내고 훑는 구현은 노트를 낸다. 색인 뒤에 파일이 바뀐 vault에서 지금 엔진은 위 표처럼 옛 메타를 내고 훑는 구현은 새 메타를 낸다. 이 차이를 계약으로 둘지는 부록 D가 정하고(8.6), 그 전에 지금 엔진과 같은 바이트를 내려면 색인을 지어 두어야 한다.

색인을 둔다면 단발 실행 사이에도 남아야 하고, 놓을 자리는 구현이 정한다. 묶음은 구현의 상태를 `WLX_STATE_DIR` 아래에 두라고만 하고 그 안을 안 본다(8.6). `--withlog.db.home=${WLX_STATE_DIR}/db`는 지금 엔진의 어댑터가 그 규칙을 지키려고 붙인 칸이다. 그래서 다시 짠 구현의 어댑터는 자기 방식으로 `WLX_STATE_DIR`을 넘기면 되고, `withlog.db.home`을 받을 필요가 없다. `--withlog.db.home=`과 `WLX_STATE_DIR`이 함께 오면 지금 엔진은 `withlog.db.home`만 쓴다. 색인 폴더를 못 만들면 부팅이 실패하는 동작은 지금 엔진의 내부 배치에서 생기는 실패라 계약이 아니고, 묶음도 안 잰다. 색인 파일 자리, 스키마 판 5, VaultKey를 색인 폴더 이름에 쓰는 일도 같은 까닭으로 계약이 아니다. 다만 VaultKey 공식 자체는 `wl-cli`의 소켓과 실행 상태 파일 이름에 쓰여서 계약이다(8.2).

지금 엔진은 응답에 안 싣는 HTML 첨부 평문도 읽는다. 노트 1건을 응답 객체로 옮기는 길이 `list_docs`의 본문 싣기와 같아서 생기는 읽기다. 고르는 첨부는 색인의 첨부 가운데 메인 노트의 것(하위 노트의 것은 빼고)이면서 이름 전체가 `.+\.html?`에 대소문자 무시로 맞는 것이고, 이름의 UTF-16 코드 단위 차례로 본다. 첨부마다 이렇게 한다.

1. 일반 파일(링크를 따라감)이 아니면 건너뛴다. 폴더로 바뀐 첨부, 끊긴 링크, 사라진 파일이 여기 든다.
2. 파일 정보(수정 시각과 크기)를 읽는다. 못 읽으면 시각과 크기를 모두 0으로 친다.
3. serve 모드에서 앞서 같은 파일 정보로 평문을 뽑았으면 그 값을 다시 쓰고 파일을 안 연다.
4. 크기가 4,194,304바이트를 넘으면 건너뛴다. 딱 4,194,304바이트는 읽는다.
5. 파일을 통째로 읽는다. 여기서 나는 입출력 오류(읽기 권한 없음, 그 사이에 사라진 파일, 장치 오류)는 아무도 안 잡아서 `get_doc` 전체가 예상 밖 예외로 실패한다(11.9의 6번).

다시 짠 구현은 이 읽기를 안 해도 같은 성공 응답을 낸다. 5번의 실패까지 따라 할지는 부록 D가 정하고, 묶음은 이 갈래를 안 잰다.

근거: 색인 뒤에 안 바뀐 vault의 응답만 묶음이 잰다. 출처 표, 다시 해석하는 범위, 낡은 갈래, HTML 첨부 읽기, 상태 자리는 코드 읽기와 묶음 README로 확인했고 실행해 보지 않았다.

## 11.6 응답

바이트는 UTF-8이고 2칸 들여쓰기, `": "`, 빈 배열 `[]`, 빈 객체 `{}`, 정수만, BOM 없음, 끝 줄바꿈 1개다. 탈출은 `\"`, `\\`, `\b`, `\t`, `\n`, `\f`, `\r`과, 나머지 U+001F 이하를 적는 소문자 `\u00xx`다. 한글, U+007F, U+2028, `/`는 그대로다. 조건부 키는 `null`로 싣지 않고 키째 뺀다. 옛 구현이 그렇게 냈고 앱과 묶음이 이 모양에 맞춰져 있기 때문이다.

짝 없는 서로게이트는 탈출하지 않고, UTF-8 바이트로 바꾸는 단계에서 `?`(0x3F) 1바이트가 된다. 실패도 U+FFFD도 아니다. `JSON.stringify`라면 `\ud800`을 쓰는 자리라서, `JSON.stringify` 바이트와 갈리는 자리는 이것 1가지다. 서로게이트가 생기는 자리는 2갈래이고 결과는 모두 `?`다.

- 파일에서 바로 읽는 칸. 코멘트 파일에 `\ud800`으로 적힌 글, UTF-16 단위로 자른 코멘트 본문(20,000자)과 인용(2,000자), 2,001단위로 읽은 사실층(아래 `agendaFacts`)이 그렇다. stdout으로 내보낼 때 `?`가 된다.
- 색인을 거치는 칸. YAML 큰따옴표 `"\uD800"`으로 적은 제목, 태그, 즐겨찾기 분류, 평가 메모, 그리고 1.8의 자르기로 끝이 갈린 즐겨찾기 분류와 평가 메모가 그렇다. 색인(SQLite)에 넣을 때 UTF-8로 바꾸면서 이미 `?`가 되어 저장된다.

다른 언어로 다시 짤 때는 길이를 UTF-16 단위로 세고 자른 뒤, 짝 없는 서로게이트가 나올 자리에 `?`를 내면 같은 바이트가 된다.

단발 모드 stdout은 JVM 표준 출력의 문자 집합으로 바꿔 나가고, 엔진은 그것을 UTF-8로 못박지 않는다. 묶음은 `LANG`과 `LC_ALL`을 `en_US.UTF-8`로 주고, 그때 UTF-8이다. 다른 로캘에서 지금 엔진이 내는 바이트는 재지 않았다. serve 모드는 로캘과 상관없이 UTF-8로 바꿔 보낸다. 다시 짠 구현은 로캘과 상관없이 늘 UTF-8을 내고 짝 없는 서로게이트만 `?`로 바꾸면 계약을 지킨다.

`agenda`와 `agendaTitle`은 노트의 아젠다 id로 아젠다 색인을 찾은 slug와 제목이다. 노트 프론트매터의 `agenda` 글자가 아니다. 아젠다 색인은 마지막 `reindex`가 아젠다 파일에서 지은 값이다. `reindex`는 아젠다 행을 더하거나 고치기만 하고 지우지 않아서, 아젠다 파일이 사라져도 옛 slug와 제목이 남는다. 행을 못 찾으면 `agenda`와 `agendaTitle`을 빈 글로 싣고 `agendaFacts`를 빼는 갈래가 코드에 있지만, 색인이 노트 행에서 아젠다 행을 외래 키로 붙잡아 두어서 정상 색인에서는 생기지 않는다.

`agendaTitle`은 이렇게 정한다(아젠다 파일의 형식은 2.1).

1. 아젠다 파일 프론트매터의 `title`을 다듬은 값이다. 아젠다 파일은 YAML이 아니라 줄 단위 `키: 값` 읽개로 읽어서 모든 값이 글이다. `title: 2026`도 `2026`이고, `title: |`는 `|`다.
2. `title`이 없거나 공백뿐이면 본문으로 간다. 아젠다 파일의 본문은 닫는 `---` 바로 뒤의 글 전체이고, 1.6의 6번 같은 줄바꿈 떼기는 없지만 통째로 다듬은 뒤에 쓴다. 다듬은 본문을 `\r\n`, `\n`, `\r`에서 가른 첫 줄, 곧 처음 비지 않은 줄을 쓴다. 그 줄 맨 앞의 `#`들과 바로 뒤따르는 ASCII 공백(U+0020, 탭, U+000B, U+000C)을 떼고 다시 다듬는다. `# 서빙`과 `#서빙`은 `서빙`이다. `#`가 줄 맨 앞이 아니면 아무것도 안 뗀다.
3. 2번의 결과가 비면(줄이 `#`뿐이면) 다음 줄로 안 가고 slug를 쓴다.

아젠다 파일은 `---` 울타리만 받는다. 여는 줄과 닫는 자리를 찾는 법, BOM 떼기, 프론트매터 조각 16,000자 상한, 파일 1,000,000바이트 상한, 엄격한 UTF-8은 1.6과 같다. 이 값은 `reindex` 때 읽혀 색인에 든다.

`agendaFacts`는 도구 표면에서만 싣는다. 앱은 안 쓰는 값이라 노트마다 싣는 것은 낭비다. 이렇게 정한다.

1. 아젠다 색인의 slug(응답의 `agenda`)가 안전한 경로 조각이 아니면 키를 뺀다. 안전한 경로 조각은 1자 이상 100 UTF-16 단위 이하이고, `/`, `\`, `..`, U+0020 미만 글자가 없고, `.`으로 시작하지 않는 글이다. 아젠다 색인의 slug는 이미 이 검사를 지난 값이라 실제로는 걸리지 않는다. 그 파일 자리가 휴지통 기록 같은 엔진 파일이 함께 사는 `.withlog/` 아래라서 1번 더 본다.
2. `.withlog/facts/<slug>.md`가 일반 파일(링크를 따라감)이 아니면 키를 뺀다.
3. 파일을 UTF-8 해독기로 열어 UTF-16 단위 2,001개가 찰 때까지, 또는 파일 끝까지 읽는다. 읽기 1번이 덜 돌려주면 다시 읽는다. 2,001번째 단위가 상위 서로게이트여도 짝은 더 안 읽는다. 해독기는 깨진 UTF-8(1.6의 엄격한 기준)이나 입출력 오류를 만나면 실패하고, 그러면 키를 뺀다.
4. 프론트매터를 안 떼고, BOM과 CRLF도 그대로 둔다. BOM은 다듬기 대상이 아니라 글에 남는다.
5. 다듬는다. 비면 키를 뺀다.
6. 다듬은 글이 2,000단위를 넘으면 아래 고정 문장을, 아니면 그 글을 싣는다.

```text
이 아젠다의 사실층이 상한(2000 자)을 넘어 안 싣는다. .withlog/facts/ 아래 파일을 상한 아래로 줄이면 다시 실린다.
```

3번의 해독기는 지금 엔진에서 2,001단위보다 앞서 더 많은 바이트를 풀어 둔다. JDK 21의 버퍼 읽기가 부를 때마다 8,192글자를 채우려 하고, 그 아래 해독기가 8,192바이트씩 읽기 때문이다. 그래서 앞 2,001단위 너머의 깨진 바이트로도 키가 빠질 수 있고, 파일 끝에서 잘린 글자는 담은 글이 2,001단위에 못 미칠 때만 깨진 것으로 본다. 깨진 바이트를 보는 정확한 범위는 22.5가 정하고, 다시 짠 구현은 0.5의 기본값대로 그 걸음을 따른다. 그 범위를 「앞 2,001단위를 이루는 바이트」로 좁힐지는 부록 D에서 정한다(22.9의 11번과 14번). 픽스처에는 사실층 파일이 없다.

`type`, `title`, `mins`, `tags`, `links`, `favorite`, `favoriteCategory`, `template`은 1.7과 1.8로 읽은 값이다. `favorite`는 참일 때만 `true`로 싣는다. `links`와 `tags`는 비어도 `[]`로 싣는데, 1건을 통째로 읽는 자리라 「없다」와 「안 봤다」를 가를 수 있어야 하기 때문이다. `links`의 항목은 `to`, `kind` 차례의 객체이고 `kind`는 소문자다.

`created`는 1.9의 꼴(초는 늘, 초 아래와 오프셋의 초는 버림, 오프셋 0은 `Z`, 초를 버려 0이 되는 `+00:00:30`도 `Z`)이고, `date`는 그 오프셋의 날짜 `yyyy-MM-dd`, `time`은 시와 분을 2자리씩 콜론으로 이은 `HH:mm`이다. 프론트매터 `'2026-06-16T10:00:59.9+09:00'`은 `2026-06-16T10:00:59+09:00`, `2026-06-16`, `10:00`이 되고, `'2026-06-16'`은 `2026-06-16T00:00:00+09:00`, `00:00`이 된다.

`sessionId`는 본문 파일에서 1.8대로 읽어(다듬고 앞 128자) `created` 바로 뒤에 둔다. `tier`는 명령 표면에서 `record`일 때만 `"record"`이고, 도구 표면은 그 노트를 거절해서 원리상 안 나온다.

도장은 `editedBy`와 `editedAt`을 다듬은 글자 그대로다. 어느 것이라도 비었거나 문자열이 아니면 3개 모두 빼고, `editedSessionId`만 있어도 뺀다. `editedSessionId`는 값이 있고 다듬은 `editedBy`가 정확히 `app`이 아닐 때만 싣는다. 대소문자를 가려서 `App`이면 싣는다. 앱 표면 도장의 세션은 옛 결함으로 무관한 값이 적혔던 자리라 뺀다.

`format`은 색인의 포맷이고 프론트매터 `format`은 안 본다. 색인의 포맷은 훑기가 본문 파일 이름으로 정한 값이다. `precondition`은 1.14의 토큰이다. 토큰은 「본 것이 최신이다」만 보증하고 「본 것이 전부다」는 보증하지 않는다. 그래서 잘린 본문에 토큰이 붙어 쓰이는 위험은 부르는 쪽 규약이 막는다. `body`는 1.6으로 프론트매터를 뗀 나머지다. json 노트는 `body`가 빈 글이고 토큰과 `sessionId`와 도장이 없다.

`evaluation`은 `score`, `note`, `at` 차례의 객체다. `note`는 빈 글이어도 `"note": ""`로 싣고, `at`은 UTC 밀리초 3자리이며 밀리초 아래는 버린다. 프론트매터에 `at`이 없으면 `created`의 순간이라, 0003이면 `2026-06-18T03:30:00.000Z`가 된다.

`path`는 색인의 vault 상대 경로다. 구분자는 `/`이고 앞에 `/`가 없으며, 폴더 노트는 폴더까지, 단일 파일은 확장자까지, 디스크 이름 그대로다.

`deepLink`는 `withlog://doc/<enc(노트 id)>?ws=<enc(vault 경로)>`이고 맨 끝 키다. vault 경로는 1.1의 정리한 글자다. `enc`는 `encodeURIComponent`와 같아서, UTF-8 바이트 가운데 영문자, 숫자, `-_.!~*'()`만 두고 나머지를 대문자 `%XX`로 바꾼다. `/Users/df/with-ai/내 vault (copy)!`는 `%2FUsers%2Fdf%2Fwith-ai%2F%EB%82%B4%20vault%20(copy)!`가 된다.

`comments`는 `state`로 시작하는 봉투다. 파일을 읽는 차례와 항목 규칙은 1.12에 있다.

| `state` | 다른 키 | 언제 |
|---|---|---|
| `absent` | 없음 | 그 경로가 일반 파일이 아니다. 단일 파일 노트는 `<path>/comments.json`이 생길 수 없어 늘 이 값이다 |
| `loaded` | `comments` 배열. 비어도 싣는다 | 읽었다 |
| `unreadable` | `reason` | 200,000바이트 초과, 입출력 오류, JSON이 아님 |

```text
파일이 너무 크다(<n>바이트). 상한은 200000바이트다.
파일을 못 읽었다: <코멘트 파일의 vault 상대 경로>
```

## 11.8 변형 명령 get_sub_note

하위 id는 루트 안에서만 유일해서 부모 참조를 함께 받는다. 도구 표면은 `get_sub_note '{"parent":"<부모 참조>","id":"<하위 id>"}'`이고, 받는 키는 `parent`와 `id`이며 2개 모두 필수 JSON 문자열이다. 도구 표면의 검사 차례와 JSON 읽개는 11.3과 같다. 모르는 키를 먼저 보고, 칸 검사는 `parent`의 있음과 타입을 본 뒤 `id`로 넘어간다. 명령 표면은 `get-sub-note <부모 참조> <하위 id>`이고, 옵션이 없고 자리 인자를 2칸까지 받는다. 부모 참조는 `<노트 id>/<하위 id>/…`처럼 루트에서 컨테이너까지 이은 경로이고, 겹 수에 상한이 없다.

그다음 이 차례로 본다.

1. 1번째 자리 인자(`parent`)가 없거나 공백뿐이면 `인자가 하나 필요하다`, 2번째(`id`)가 없거나 공백뿐이면 `인자가 둘 필요하다`로 거절한다.
2. `parent`를 `/`로 자르고, 조각마다 다듬고, 빈 조각을 버린다. 남은 조각이 없으면(`/`나 ` / `) `WL-400 부모 노트 참조가 비었다: <원문>`이다. `<원문>`은 받은 `parent` 글 그대로이고 다듬지 않았다. 첫 조각이 비어 버려지면 다음 조각이 루트가 된다.
3. 첫 조각이 노트 id 모양이어야 한다(`WL-400`). 루트 노트가 색인에 있는지는 여기서 안 본다.
4. 뒤 조각을 앞에서부터 1개씩 끝까지 보고 나서 다음 조각으로 간다. 조각마다 하위 id 모양인지(`WL-400`), 그 루트의 색인에 있는지(`WL-404`), 직계 부모가 앞 조각인지(`WL-404`)를 이 차례로 본다. 첫 하위 조각의 직계 부모는 루트다. 그래서 2번째 조각의 모양이 틀려도 1번째 조각이 색인에 없으면 `WL-404`가 먼저 선다.
5. `id`도 마지막 조각(없으면 루트)을 컨테이너로 삼아 4번 검사를 받는다. `id`는 다듬지 않는다.
6. 도구 표면이면 루트 노트를 색인에서 찾는다. 없으면 `WL-404 Note not found: <루트>`이고, 층이 `record`면 `WL-409`다.

하위 노트는 루트의 색인에 함께 들어서, 루트가 없으면 4번이나 5번이 먼저 `SubNote not found`로 선다. 색인은 하위 노트 행을 루트 행에 외래 키로 붙잡아 두어서 6번의 `Note not found`는 정상 색인에서는 안 나온다. 4번과 6번 사이에 다른 프로세스가 그 노트를 색인에서 지우는 경합에서만 나올 수 있다. 기록 층 루트 아래의 없는 하위 id도 6번보다 5번이 먼저라 `WL-404`다.

검사가 읽는 파일도 있다. 4번과 5번은 색인에서 하위 노트를 꺼낼 때마다 그 본문 파일을 읽고(json 하위 노트는 안 연다) 프론트매터를 1.8대로 짓는다. 그래서 경로 위의 하위 노트와 대상 하위 노트의 본문 파일을 모두 읽고, 대상은 응답을 지을 때 1번 더 읽는다. 6번은 루트 노트를 `get_doc`과 같은 길로 꺼내서, 루트의 본문 파일과 HTML 첨부(11.5)까지 읽는다. 명령 표면은 6번이 없어서 루트를 안 읽는다. 이 읽기에서 나는 실패는 `get_doc`과 같다. 1.8의 안 잡히는 표기가 그 파일들 어디에 있어도, 루트의 HTML 첨부를 읽다 입출력 오류가 나도 예상 밖 실패로 선다(11.9). 다시 짠 구현은 응답에 쓰는 대상의 본문만 읽어도 성공 응답이 같다.

```text
WL-400 인자가 하나 필요하다: get-sub-note <부모 노트 id> <하위 노트 id>
WL-400 인자가 둘 필요하다: get-sub-note <부모 노트 id> <하위 노트 id>
WL-400 인자 검증 실패(get_sub_note): 모르는 키다: [<정렬한 키들>]. 쓸 수 있는 것은 [parent, id] 뿐이다.
WL-400 인자 검증 실패(get_sub_note): <parent 나 id> 가 필요하다.
WL-400 인자 검증 실패(get_sub_note): <parent 나 id> 는 문자열 여야 한다: <압축한 JSON 값>
WL-400 get-sub-note 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [] 뿐이다.
WL-400 get-sub-note 이 받는 자리 인자는 2 개인데 <n> 개를 받았다: get-sub-note <부모 노트 id> <하위 노트 id>
WL-400 부모 노트 참조가 비었다: <원문>
WL-400 노트 id 모양이 아니다: <첫 조각>
WL-400 하위 노트 id 모양이 아니다: <값>
WL-404 SubNote not found: <노트 id>/<하위 id>
WL-404 SubNote not found: <하위 id>
WL-404 Note not found: <노트 id>
WL-409 도구 표면이 읽을 수 없는 노트다(층=record): <루트 노트 id>. 기계가 남긴 기록 노트는 앱에서만 열립니다.
```

`<노트 id>/<하위 id>` 꼴은 색인에 없을 때이고, `<하위 id>`만 적힌 꼴은 직계 관계가 어긋날 때다. 직계를 보는 이유는, 같은 루트 아래라는 것만 보면 손자를 다른 자식 아래인 것처럼 가리켜 엉뚱한 자리를 읽거나 쓰기 때문이다. 루트 층을 보는 이유는 하위 노트에 층이 없고 루트로만 닿아서, 루트가 막히면 하위 노트도 막혀야 하기 때문이다.

응답 키는 `id`(하위 id만), `parent`(다듬은 조각을 `/`로 이은 참조), `type`, `title`(공백뿐이면 하위 id), `created`, `date`, `time`, `mins`, 도장 3개, `format`, `precondition`, `comments`, `body`, `links`, `tags`, `path` 차례다. `links`와 `tags`는 `get_doc`처럼 비어도 늘 `[]`로 싣는다. 메타는 하위 노트 색인의 값이고, 본문과 토큰과 도장은 부를 때 그 본문 파일에서 읽는다. `comments`는 직계 컨테이너의 `sub-comments/<하위 id>.json`을 부를 때 읽고, 옛 `.md` 하위 노트도 같다. 값 규칙은 `get_doc`과 같고, `agenda`, `agendaTitle`, `agendaFacts`, `sessionId`, `tier`, `favorite`, `favoriteCategory`, `template`, `evaluation`, `deepLink`는 없다.

## 11.9 받아들임 묶음과 얼어 있는 특이점

묶음이 덮는 것은 `get_doc` 111건(픽스처에서 노트로 서는 110건과 틀린 id 1건)과 `get_sub_note` 4건(성공 3건, 틀린 하위 id 1건)이다. 모두 도구 표면이다. 성공 113건은 응답 바이트를 재고, 실패 2건은 종료 코드 3과 빈 stdout만 맞댄다. 명령 표면, WL 번호, 기록 층, `agendaFacts`, `sessionId`, 도장, `unreadable` 봉투, 평가 시각 대체, 색인 낡음, 설정과 argv 갈래, 부팅 실패, 예상 밖 예외는 안 덮는다.

얼어 있는 특이점은 지금 엔진의 동작이고, 지킬지 고칠지는 부록 D에서 정한다. 표시가 없으면 코드 읽기로 확인했고 실행해 보지 않았다.

1. json 노트는 `sessionId`와 도장까지 잃는다. 본문 파일을 안 여는 갈래가 그 값도 건너뛰기 때문이다.
2. `wl-cli` 도움말은 json 노트를 마크다운으로 바꿔 준다고 적지만 `body`는 빈 글이고, 묶음이 빈 글을 얼렸다.
3. 사실층은 2,001자를 먼저 읽고 다듬어서, 앞 공백이 많은 긴 파일은 잘린 글이 실린다. 그 자르기가 서로게이트 쌍을 가르면 끝이 `?`로 나간다. 앞 2,001자 너머의 깨진 바이트로도 키가 빠질 수 있다.
4. 코멘트 id는 첫 항목이 차지해서, 그 항목이 버려지면 같은 id의 뒤 항목도 못 산다.
5. `get_doc`은 id를 안 다듬고 `get_sub_note`는 부모 조각을 다듬는다. `get_sub_note`의 `id`는 다듬지 않는다.
6. HTML 첨부를 읽다 입출력 오류가 나면 예외를 안 잡아 `get_doc` 전체가 실패한다. 응답에 안 쓰는 읽기라서 생기는 실패다.
7. 메타는 낡고 본문만 새로운 응답이 나올 수 있고, 다른 노트의 도장이 섞일 수도 있다(11.5). 색인이 없는 vault는 모든 id가 `WL-404`다.
8. 짝 없는 서로게이트는 `?`로 나가서 `JSON.stringify`의 `\ud800`과 다르다. 색인을 거치는 값은 색인에 넣을 때 이미 `?`가 된다.
9. 이름이 정확히 `.md`, `.html`, `.json`으로 끝나는 폴더 노트는 본문 파일을 못 찾아 `body`가 빈 글이다(1.13).
10. 아젠다 파일이 사라져도 `agendaTitle`은 아젠다 색인의 옛 제목이다.
11. `get_sub_note`는 루트 층 검사를 하위 노트 찾기 뒤에 해서, 기록 층 루트 아래의 없는 하위 id에 `WL-409`가 아니라 `WL-404`를 낸다.
12. 색인 뒤에 본문 파일의 프론트매터에 1.8의 안 잡히는 표기(`!!int abc` 같은 것)가 생기면 `get_doc`이 예상 밖 예외로 실패한다(1.15의 6번과 같은 뿌리). `mins: .nan`은 `get_doc`을 안 세운다.
13. 도구 표면에서 기록 층 노트를 거절하기 전에 본문 파일과 HTML 첨부를 먼저 읽어서, 그 읽기의 입출력 오류가 `WL-409`보다 먼저 선다.
14. 코멘트 파일이나 도구 인자의 JSON에 배열이 아주 깊게 겹쳐 있으면 읽개가 재귀로 내려가다 스택이 넘쳐 예상 밖 실패가 날 수 있다. 코멘트 파일은 200,000바이트라서 10만 겹까지 겹칠 수 있다. 2026-10-24에 단발 모드로 재니 4,000겹은 받고 5,000겹에서 종료 코드 1로 섰다. 이 경계는 JVM 스택 크기에 달려서 계약이 아니다.
15. `--spring.main.banner-mode=console` 같은 스프링 설정 이름이 stdout 바이트를 바꿀 수 있다(11.2).
16. 폴더 이름 1개가 공백 글자로만 된 노트는 훑기가 세워 색인에 들지만, `get_doc`이 코멘트 파일 경로를 못 지어 `WL-400 빈 경로 조각은 결합할 수 없다: 기준=…`로 선다(11.4의 16번).
17. `get_sub_note`는 도구 표면에서 루트 노트의 층만 보면 되는데 루트의 본문 파일과 HTML 첨부까지 읽고, 경로 위 하위 노트의 본문 파일도 모두 읽는다(11.8). 그래서 응답과 상관없는 파일의 1.8 표기나 입출력 오류로 예상 밖 실패가 날 수 있다.

확인하지 못한 것도 있다. 단발 모드 stdout이 `en_US.UTF-8` 밖의 로캘에서 어떤 바이트를 내는지, 부팅 실패와 예상 밖 예외의 단발 모드 종료 코드가 정말 1인지는 실행해서 재지 않았다. 코드 읽기로는 1이다. BOM으로 시작하는 `comments.json`이 `unreadable`인 것과, 색인을 거친 짝 없는 서로게이트가 `?`가 되는 것은 코드 읽기로 확인했다(1.12, 11.6).
