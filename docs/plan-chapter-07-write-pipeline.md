# 7장 기반 개발 계획 — 쓰기 계약과 상태 확인

작성일: 2026-10-26

다음 개발 목표는 **엔진이 발급한 토큰을 정확한 대상에 이어 붙이고, 충돌·부분 반영·응답 유실에서 초안을 보존할 수 있는 쓰기 계약을 준비하는 것**이다. 현재 저장소에는 실제 엔진과 파일 쓰기 실행부가 없으므로 앱에서 소비하는 계약부터 구현한다. 파일 시스템과 색인·git 파이프라인까지 구현했다고 주장하지 않는다.

근거: [7장 쓰기 파이프라인](./spec-chapter-07-write-pipeline.md), [6장 출력과 실패](./spec-chapter-06-output-and-errors.md), [5장 인자](./spec-chapter-05-arguments.md), 기존 `src/engine` 구현.

## 1. 선행 작업 2 검토 결과

직접 실행한 결과 `npm test`는 6개 파일·88개 테스트가 통과했고, `npm run build`도 통과했다. 불완전 목록·검색 봉투·warning·회고 읽기 클라이언트의 주요 구현은 계획과 일치한다. 실제 엔진과 공식 448건 검증 묶음은 실행하지 않았다.

문서·타입 사용 예시의 보완 1건을 별도로 남긴다.

- `ListResponse`의 배열 가지는 `readonly T[]`인데 README는 `Array.isArray`만으로 분기한다. 현재 TypeScript에서 else 가지에 readonly 배열이 남아 `.reports`, `.incomplete` 접근이 타입 오류다. 기존 테스트는 타입 단언으로 접근해 이 사례를 검증하지 않는다.
- 같은 예시에서 MockTransport에 응답을 등록하지 않아 그대로 실행하면 전송 실패가 반환된다.
- 보완: 읽기 전용 배열도 좁힐 수 있는 명시적 타입 가드 또는 안전한 분기 API를 제공하고, 응답을 등록한 예시를 타입 검사 대상 파일로 검증한다. 원본 배열을 변경하거나 `as any`로 우회하지 않는다.

이는 주요 봉투 처리의 런타임 실패는 아니므로 7장 계획은 진행한다. 다음 개발의 시작에서 이 예시 보완을 작은 독립 변경으로 먼저 완료한다.

기존 6장 작업 3인 `/review` 화면 연결은 별도 후속 작업으로 유지한다. 이번 요청에 따라 7장 계약 준비를 먼저 진행하며, 회고 UI 구현은 이 범위에 섞지 않는다.

## 3. 7장에서 고정해야 하는 계약

### 토큰은 대상에 묶인 불투명 문자열

- 응답 키는 `precondition`, 요청 키는 `f1`이다. 다른 키로 바꿔 전달하지 않는다.
- 앱은 SHA-256을 계산하거나 `f1:` 접두사·64자리 해시를 생성하지 않는다. 받은 값의 trim·대소문자 변환·정규화도 하지 않는다.
- 루트 노트와 하위 노트, 서로 다른 vault의 같은 id를 구분해 토큰을 보관한다. 저장소 식별자와 대상 식별자를 호출자가 제공하도록 하며 경로 문자열을 임의로 추측하지 않는다.
- `link_docs`는 대상(to)이 아니라 출발 노트(from)의 토큰을 사용한다.
- 토큰이 없는 것과 잘못된 타입인 null은 다르다. 없음은 키 생략이며 문자열을 보내면 원문을 보낸다. 도구 표면의 null은 WL-400이고, 없는 토큰의 허용 여부는 엔진이 판정한다.
- `set_favorite`, `link_docs`의 no-op 및 JSON 메타 쓰기 면제 때문에 토큰 없는 모든 호출을 앱에서 거절하지 않는다.
- 성공 쓰기가 돌려준 새 토큰은 해당 대상의 다음 쓰기에 사용할 수 있다. 다만 기존 본문·초안과 어떤 판을 가리키는지 함께 관리해야 한다.

### 실패는 명령 전체의 롤백을 뜻하지 않는다

- WL-412는 해당 토큰으로 보호하는 본문 쓰기가 거절됐다는 뜻이다. 그 전에 색인 맞추기·자동 커밋·쓴 쪽 기록이 일어날 수 있어 vault 전체 무변경이라고 표시하지 않는다.
- WL-500에는 폴더 이동 후 크기 상한 거절처럼 일부 반영된 실패가 있다. 자동 재시도하거나 이전 경로가 여전히 맞다고 가정하지 않는다.
- 예상 밖 실패, 응답 중단, 신호 종료는 완료 여부가 불확실하다. 초안을 남기고 재조회한다.
- 명령 전체는 트랜잭션이 아니다. 파일 1개가 원자적으로 저장됐다는 사실과 여러 파일의 일괄 성공을 구분한다.
- stderr 문구로 MISSING/MALFORMED/STALE를 자동 판별하거나 현재 토큰을 추출하지 않는다. WL-412 공통 복구 경로만 사용한다.

### 파생 쓰기 토큰은 조건부로 이어받는다

| 응답 | 영향받은 대상 | 토큰 쌍 |
|---|---|---|
| delete_sub_note | 삭제한 자식의 직계 컨테이너 | containerBefore / containerAfter |
| delete_comment | 코멘트가 달린 루트 또는 하위 노트 | bodyBefore / bodyAfter |

- 두 키는 모두 없거나 모두 문자열이어야 한다. 한쪽만 있거나 null이면 계약 오류다.
- 보유한 토큰이 before와 정확히 같을 때만 after로 연결할 수 있다. 다르거나 보유 토큰이 없으면 해당 대상 재조회가 필요하다.
- 쌍이 없으면 컨테이너 본문을 다시 쓰지 않았다는 뜻이다. 삭제 명령 전체에 변화가 없었다는 뜻은 아니다.
- before가 같아도 기존 캐시 본문에는 삭제된 카드/마커가 남을 수 있다. 토큰만 갱신해 그 본문을 다시 저장하지 않는다. 본문을 재조회하거나 정확한 변경을 적용하기 전에는 전체 본문 저장을 보류한다.
- 편집 중인 초안은 파생 결과로 덮어쓰지 않는다. 서버 본문 갱신과 초안 재적용을 별도 상태로 관리한다.

## 4. 개발 단계

### 7-1 — 토큰 전달과 쓰기 결과 해석 (바로 다음 개발 단위)

권장 파일:

- `src/engine/write/preconditions.ts`: 토큰 필드 검사·요청 결합.
- `src/engine/write/derivedTokens.ts`: before/after 쌍 validator와 이어받기 판단.
- `src/engine/write/outcomes.ts`: 기존 DecodedResponse와 검증된 쓰기 부가정보를 사용하는 결과 정책.
- `src/engine/write/types.ts`: 대상 식별·토큰 변경·재조회 판단 타입.
- 관련 테스트, 공개 export, README 및 타입 검사되는 예시.

구현 순서:

1. 1절의 작업 2 사용 예시·타입 분기 문제를 먼저 수정한다.
2. 선택적 precondition과 두 종류 토큰 쌍의 순수 validator를 만든다. 기존 ResponseValidator 및 base validator 조합을 사용하고 원본 객체를 변경하지 않는다.
3. 알려진 도구 요청 인자 객체에 f1을 결합하는 순수 함수를 만든다. 토큰을 별도 인자로 받되 입력 객체에도 f1이 있으면 중복 소유권이 생기지 않도록 타입/API에서 막거나 명확히 거절한다. precondition 키를 요청으로 복사하지 않는다.
4. 토큰 쌍 비교 결과를 `unchanged`·`advance_and_refresh_body`·`reload_required` 등 앱 내부 판단으로 돌려준다. 이는 엔진 응답에 추가하는 필드가 아니다.
5. 성공·WL-412·기타 명령 실패·전송 실패·계약 오류에 따른 본문 보호와 재조회 필요성을 판단한다. 문구·모든 명령 상세 응답을 추측하지 말고 이미 검증한 부가정보만 사용한다.
6. 합성 응답과 mock으로 위 정책을 검증하고 전체 테스트·빌드를 실행한다.

범위 제한:

- 아직 `update_doc` 등 전체 쓰기 클라이언트를 만들지 않는다. 13~15·17·19장의 요청/응답 스키마가 없으므로 필요한 부분만 알려진 토큰 계약으로 검증한다.
- write flag는 토큰 유무와 별개다. 이 단계에서 35개 쓰기 명령·61개 명령 레지스트리나 밑줄 이름 자동 변환기를 추가하지 않는다.
- 토큰의 문자열 유효성을 엔진의 f1 문법으로 제한하거나 클라이언트에서 WL-412를 만들어내지 않는다.
- 자동 재조회·재시도·쓰기·원격 변경 적용은 실행하지 않는다. 필요한 행동을 데이터로 제공한다.

완료 기준: 원본 토큰과 키 누락이 보존되고, before 불일치나 부분 반영 가능성에서 잘못된 새 토큰으로 재저장하지 않도록 판단 정보가 남는다. 기존 88개 사례와 새 경계 사례, 예시 타입 검사, 빌드가 통과한다.

### 7-2 — 초안과 저장 상태 전이

7-1 뒤에 독립 개발한다. 실제 에디터 없이 순수 상태 전이와 주입 가능한 저장/재조회 함수로 검증한다.

- 상태는 최소한 읽은 기준 판, 현재 초안, 요청에 보낸 초안 판, 저장 중 여부, 충돌/재조회 필요 여부를 구분한다.
- 같은 대상의 앱 저장은 한 번에 하나만 보낸다. 이는 앱 내부 요청 정책이며 엔진에 전역 잠금이 생겼다고 설명하지 않는다.
- 저장 중 새 입력이 생기면 성공 응답이 그 새 입력까지 저장 완료로 만들지 않는다. 방금 보낸 판만 확인하고 최신 초안은 남긴다.
- 늦게 도착한 응답은 요청 id·대상·판을 대조해 반영한다. 다른 vault나 다른 문서에 토큰이 섞이지 않게 한다.
- WL-412이면 초안을 유지한 채 최신 본문을 별도로 읽는다. 새 토큰만 교체해 같은 옛 본문을 재전송하지 않는다.
- 재적용은 최신 기준 본문 위에서 명시적으로 수행한다. 충돌·완료 불확실 상태를 무시하는 자동 재전송 경로를 두지 않는다.
- 본문과 토큰이 일치하는 기준 판으로 확인되기 전에는 전체 본문 저장을 허용하지 않는다.

완료 기준: 저장 중 추가 편집, 응답 순서 역전, 외부 변경, 파생 쓰기, 응답 유실에서 초안이 유지된다. 실제 파일 쓰기 없이 deferred mock으로 경합을 검증한다.

### 7-3 — 명령별 쓰기와 실제 연결

선행 자료: 9~11·13~15·17·19장, 부록 B·C·D, 실행 가능한 엔진과 테스트 vault, Tauri 전송 계층.

- 읽기에서 받은 토큰을 해당 쓰기로 전달하고 명령별 응답 validator를 연결한다.
- JSON 메타 쓰기 면제와 set_favorite/link_docs no-op을 엔진 결과로 확인한다. 쓰기 성공인데 precondition이 없다고 모두 계약 위반으로 처리하지 않는다.
- 저장 후 새 토큰, 파생 토큰, 경고, 부분 반영 결과를 7-1·7-2에 연결한다.
- 격리 vault에서 WL-412 세 갈래, 파일 이동 후 실패, 파일 쓰기 후 응답 유실을 검증한다.
- 에디터와 안전 종료의 settleWrites 연결은 초안·실패가 저장 완료로 오인되지 않게 한다.

완료 기준: 실제 대상 바이트와 앱의 저장 판이 일치하며, 응답이 불확실하면 재조회 후 명시적 재적용으로 진행한다. 이 단계 전에는 실제 저장 기능 완료라고 보고하지 않는다.

## 5. 7-1 검증 행렬

| 대상 | 필수 사례 |
|---|---|
| 선택적 토큰 | 없음, 문자열, 공백 포함 문자열 원문 보존, null/숫자 거절, 임의 접두사 재작성 없음 |
| 요청 결합 | f1 키만 사용, 미지정 시 생략, 중복 f1 소유 방지, 본문·추가 인자·입력 객체 무변경 |
| 대상 분리 | 서로 다른 vault, 루트/하위 노트, link_docs 출발 노트 토큰의 문맥 명시 |
| 파생 쌍 | 둘 다 없음, 둘 다 문자열, 한쪽 누락, 잘못된 타입, container/body 이름 혼용 방지 |
| 토큰 연결 | before 일치·불일치·보유 토큰 없음, 일치해도 본문 갱신 필요 정보 |
| 성공 | 새 토큰 있음, 알려진 no-op, 부가정보 없는 성공을 전체 무변경으로 단정하지 않음 |
| WL-412 | 대상 본문 쓰기 거절, 초안 유지 지침, 최신 토큰만 바꾸는 자동 재전송 없음 |
| 부분 반영 | WL-500·예상 밖 실패에서 파일/폴더 상태 재조회 판단 |
| 전송 | pre_dispatch와 in_flight/unknown, signal, 응답 스키마 오류에서 완료 불확실성 |
| 회귀 | 종료/WL 분류, 성공 stderr/warning, 원본 바이트, 목록·검색·회고 기존 사례 |
| 타입·예시 | readonly 목록 분기 타입 검사, mock 등록 후 실제 success 결과, 공개 API 사용 예시 |

합성 토큰은 앱이 만드는 토큰 발급기가 아니라 테스트 자료다. 이 테스트는 실제 SHA-256·fsync·파일 잠금·DB·git을 검증하지 않는다.

## 6. 엔진 구현 시 후속 검증 항목

현재 앱 작업과 별도인 엔진 개발에 다음 목록을 전달한다. 특히 7.6의 특이점은 부록 D 결정 전 임의로 개선하지 않는다.

| 절 | 구현·검증할 것 |
|---|---|
| 7.1 | 문법 → 표식(init 예외) → 전체 색인 → 쓴 쪽 검사 → 명령 → finally 쓴 쪽 기록 → 응답 순서, 35/26개 깃발, 깃발과 실제 변경의 차이 |
| 7.2 | 전체 파일 바이트(BOM 포함) 해시, 쓰기 직전 엄격 UTF-8 읽기, JSON 본문 거절 우선순위, MISSING/MALFORMED/STALE, JSON 토큰 없음 면제, no-op 판정 우선 |
| 7.3 | 카드/마커 걷기 후 삭제, 변화 없으면 재쓰기 없음, 도장 유지, 토큰 쌍의 생성, 삭제 실패 전 부분 반영 |
| 7.4 쓰기 | 부모 mkdir → 같은 폴더에 배타 생성(임시 이름 3회) → 바이트 쓰기·파일 fsync·닫기 → atomic rename, 오류 시 임시 파일 정리, 폴더 fsync 없음 |
| 7.4 이동 | 대상 존재 검사, 부모 mkdir, 원자적 이동, 토큰 대조 → 이동 → 크기 상한 → 쓰기 순서, 원래 자리도 찬 후보로 계산 |
| 7.4 경계 | 심볼릭 링크·끊긴 링크, umask와 권한, 1,000,000 UTF-16 코드 단위 저장 상한과 별도 바이트 읽기 상한, 경로 조각 검사, 폴더 삭제 열거 실패 |
| 7.5 | 프로세스 벽시계와 +09:00 표기, 순간 변환과 UTC 표기를 명령별로 구분, 기존 오프셋 유지, 주입 가능한 시계로 테스트 |
| 7.6 | 토큰 대조~쓰기 잠금 없음, 실패 호출 쓴 쪽 기록, 폴더 이름 왕복·대소문자/NFD·NFC, 이동만 반영된 실패 |

이 단계의 원자성·동시성은 실제 파일 시스템의 격리 임시 폴더, 고장 주입, 프로세스 중단을 사용해 검증해야 한다. mock 통과만으로 보장하지 않는다.

## 7. 다음 개발 요청의 범위

**7-1과 작업 2 사용 예시 보완을 한 개발 단위로 진행한다.** 이후 7-2를 별도 검토하고, 전체 명령 스키마와 실제 실행 환경이 준비되면 7-3으로 연결한다. 이번 문서는 계획이며 애플리케이션 소스는 변경하지 않았다.
