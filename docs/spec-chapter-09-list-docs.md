# withlog 1부 vault 엔진 설명서 > 9장 명령 list_docs

`list_docs` 는 조건에 맞는 노트의 메타 목록을 만든 시각 차례로 내고, vault는 안 바꾼다.

- 필터는 8가지(아젠다, 유형, 태그, 즐겨찾기, 즐겨찾기 카테고리, 날짜, 날짜 하한, 날짜 상한)이고 모두 AND로 묶는다.
- 차례는 색인에 적힌 `created` 글자의 오름차순이고, 같으면 경로에서 `/`를 `U+0001`로 바꾼 글자의 차례다.
- 도구 표면은 늘 전부를 내고 기록 층 노트를 뺀다. 명령 표면은 `limit` 을 안 주면 100건에서 말없이 자르고 기록 층도 낸다.
- 응답은 봉투 없는 배열이다. 줄 1개는 `get_doc` 응답(11.6)에서 `agendaFacts`, `comments`, `body`, `deepLink` 를 뺀 모양이고, `tags` 만 비면 키째 빠진다.
- **근거**: 도구 표면의 필터, 차례, 줄 모양은 묶음 38건이 잰다. 명령 표면, 100건 자르기, `bodies=true`, 기록 층, 같은 시각끼리의 차례, WL 번호는 코드 읽기로만 확인했다.

---

## 9.1 한눈에

도구 이름은 `list_docs`, 명령 이름은 `list-docs` 이다. 쓰기 깃발이 없어서 워크스페이스 표식을 안 보고 색인도 안 맞춘다(7.1, 8.3). 노트를 고르고 늘어놓는 일은 색인이 하고, 줄마다 본문 파일과 HTML 첨부를 그때 읽어 토큰과 도장과 `sessionId` 를 붙인다.

스킬이 「그날 쓴 노트」와 「그 아젠다의 노트」를 모으는 자리다. 날짜 하루를 거르는 `date` 가 `from`, `to` 와 따로 있는 것은 옛 호출자가 그 이름으로 하루를 거르기 때문이다. 도구 표면은 건수 상한 없이 전부를 낸다. 말없이 잘린 목록은 「그런 노트가 없다」와 구별되지 않기 때문이다.

하위 노트는 이 목록에 안 나오고 `list_sub_notes` (16장)로 본다. 휴지통의 노트도 안 나오고 `list_trash` (26장)로 본다.

## 9.2 부르는 법

| 표면 | 꼴 | 쓰는 쪽 |
|---|---|---|
| 도구 | `list_docs '{"agenda":"serving", "type":"research"}'` | Claude와 스킬 |
| 명령 | `list-docs agenda=serving type=research limit=0` | 앱과 사람 |

단발 모드(3.1)에서는 이렇게 부른다. `wl-cli` 를 거쳐도 같은 argv가 serve 모드 엔진에 가고 stdout 바이트는 같다.

```bash
java -jar wl-sidecar.jar list_docs '{"type":"research"}' --withlog.vault=/Users/me/vault --withlog.db.home=/Users/me/.wl/db
```

표면 2개는 같은 처리로 가고, 갈리는 자리는 4곳이다(코드 읽기로 확인).

| 무엇 | 도구 표면 | 명령 표면 | 이유 |
|---|---|---|---|
| 날짜 구간 이름 | `dateFrom`, `dateTo` | `from`, `to` | 도구 키는 옛 CLI 이름이 계약이고, 스킬 문서와 래퍼가 그 이름으로 부른다 |
| 건수 | 늘 전부다. `limit` 키가 없다 | `limit=<n>`. 안 주면 100이고 0 이하면 전부다 | 옛 CLI에 상한이 없었고, 명령 표면은 손으로 1번 찍어 보는 쓰임이 흔하다 |
| 본문 | 못 싣는다. `bodies` 키가 없다 | `bodies=true` 면 `body` 와 `attachText` 를 싣는다 | 앱이 부팅할 때 목록 1번으로 노트를 통째로 세우려고 연 옵션이다 |
| 층 | `reading` 만 | `reading` 과 `record` | 기록 노트는 사람이 아니라 AI에게만 감추는 층이다(1.7, 5.5) |

## 9.3 인자와 검증

도구 표면은 5.4의 규칙으로 JSON 객체 1개를 읽는다. 받는 키는 아래 표의 8개이고, 그 밖의 키는 거절한다. 오타 난 키를 버리면 「필터를 걸었는데 다 나온 목록」이 「맞는 노트가 없다」와 구별되지 않기 때문이다.

| 차례 | 도구 키 | 명령 옵션 | 도구 표면의 JSON 타입 |
|---|---|---|---|
| 1 | `agenda` | `agenda` | 문자열 |
| 2 | `date` | `date` | 문자열 |
| 3 | `dateFrom` | `from` | 문자열 |
| 4 | `dateTo` | `to` | 문자열 |
| 5 | `type` | `type` | 문자열 |
| 6 | `tag` | `tag` | 문자열 |
| 7 | `favorite` | `favorite` | 불리언 |
| 8 | `favoriteCategory` | `favoriteCategory` | 문자열 |
| 없음 | 없음 | `limit` | 명령 표면만 |
| 없음 | 없음 | `bodies` | 명령 표면만 |

도구 표면은 타입을 표 차례로 본다. 문자열 자리는 JSON 문자열만 받고, 불리언 자리는 따옴표 없는 `true` 와 `false` 만 받는다. 그래서 `2026`, `"true"`, `TRUE` 는 거절한다. 같은 호출이 읽기에 따라 다른 필터가 되는 것을 막는 검사다. 값이 JSON `null` 인 키도 「안 준 것」이 아니라 타입 오류다(5.4). 그래서 `{"agenda": null}` 은 전부를 내지 않고 `WL-400 인자 검증 실패(list_docs): agenda 는 문자열 여야 한다: null` 로 선다(코드 읽기로 확인).

명령 표면은 5.2의 문법이고 자리 인자를 0개만 받는다. `list-docs 3` 을 친 사람이 3건을 기대하는데 조용히 100건이 나오면 문법을 틀린 줄 모르기 때문이다. 같은 옵션을 2번 주면 뒤엣것이 이긴다. 이것은 명령 표면 전체의 규칙(5.2)이라 10장, 12장, 16장에도 그대로 걸린다. 도구 표면에서 같은 키가 2번 오면 역시 마지막 값이 이긴다(5.4).

필터 값, `limit`, `bodies` 는 모두 5.3의 다듬기 집합으로 앞뒤를 떼고 읽는다. 떼고 나서 빈 값은 그 칸을 안 준 것과 같다. 그래서 `{"agenda": ""}` 와 `list-docs agenda=` 는 아젠다를 안 거르고, `limit=` 은 기본값 100이고, `bodies=` 는 거짓이다. U+FEFF는 다듬기 집합에 없어서 U+FEFF 1글자는 빈 값이 아니다(코드 읽기로 확인).

이 장과 10장의 대소문자 무시 견주기는 모두 Java의 글자 대응을 쓰고, 12장의 `query` 만 SQLite의 ASCII 규칙을 쓴다. 표는 엔진이 도는 JDK의 유니코드 판이다. 엔진은 JDK 21로 지어 JDK 21 이상에서 돌고, JDK 21의 표는 유니코드 15.0이다. 그래서 다시 짓는 구현은 유니코드 15.0의 대소문자 대응을 쓰면 JDK 21에서 도는 지금 엔진과 같다. 다른 판을 고를지는 5.3의 숫자 판처럼 부록 D에서 정한다. 받아들임 묶음은 ASCII 밖 대소문자를 재지 않는다.

필터의 뜻과 검사 차례는 이렇다. 처음 걸린 검사에서 멈추고, 차례는 9.4의 실패 차례와 같다.

1. `agenda` 는 걸음 2개로 아젠다 1개를 정한다.
   - 1번째 걸음은 값과 slug가 글자까지 똑같은 아젠다를 색인에서 찾는다. 이 비교는 대소문자를 가린다. 값이 slug가 될 수 없는 모양이면 이 걸음을 건너뛴다. slug가 될 수 없는 모양은 UTF-16 코드 단위로 100개를 넘거나, `/` 나 `\` 가 들었거나, 어느 자리든 `..` 이 들었거나, `.` 로 시작하거나, U+0020 미만 글자가 든 값이다. 색인에는 이 모양의 slug가 못 들어와서(2.1), 이 건너뛰기는 밖에서 안 보이고 구현이 생략해도 결과가 같다. 건너뛰든 안 건너뛰든 2번째 걸음으로 가기 때문이다.
   - 2번째 걸음은 아젠다 제목과 견준다. 견주는 제목은 응답의 `agendaTitle` 과 같은 값이다(11.6). 곧 아젠다 파일의 `title` 이고, 없으면 본문 첫 줄에서 머리 `#` 들을 뗀 글이고, 그것도 없으면 slug다. 그래서 제목과 본문이 없는 아젠다 `serving` 은 `agenda=SERVING` 으로도 고른다. 1번째 걸음은 대소문자를 가려서 못 찾지만, 2번째 걸음이 물러선 제목 `serving` 과 대소문자 없이 맞대기 때문이다. 저장된 제목은 아젠다를 세울 때 이미 앞뒤 공백을 뗀 값이라, 견줄 때 다시 다듬지 않는다.
   - 제목 견주기는 Java `String.equalsIgnoreCase` 와 같다. UTF-16 길이가 같고, 코드 단위마다(서로게이트 쌍은 코드 포인트로) 같거나, 대문자로 바꿔 같거나, 대문자로 바꾼 것을 다시 소문자로 바꿔 같아야 한다. 대문자로 바꿔 견주는 걸음이 있어서 「양쪽을 소문자로 바꿔 견주기」보다 넓다. 예를 들어 U+017F(ſ)는 소문자로 바꿔도 그대로이지만 대문자로 바꾸면 S 라서 `s` 와 같은 글자다.
   - 맞는 아젠다가 여럿이면 slug의 UTF-16 차례로 맨 앞의 아젠다를 쓴다. 값을 slug 꼴로 바꿔 다시 찾는 걸음은 없다. 옛 구현에는 그 걸음이 있었지만, 두면 이름 규칙이 2벌이 되고 slug도 제목도 아닌 값은 이미 오타에 가깝기 때문이다.
   - slug로도 제목으로도 못 찾으면 `WL-404` 이다. 빈 목록으로 답하지 않는 이유는 오타가 흔하고, 빈 목록이 「그 아젠다에 노트가 없다」와 구별되지 않기 때문이다. 제목을 받는 이유는 스킬 문서가 「slug나 이름으로」 지정하라고 안내하기 때문이다. 묶음 케이스 `list_docs/agenda-title=서빙` 이 인자 `{"agenda":"서빙"}` 으로 이 갈래를 잰다.
2. `type` 은 `plan`, `build`, `report`, `research`, `meeting`, `free` 가운데 1개와 1번의 `equalsIgnoreCase` 규칙으로 견준다. 그래서 `BUILD` 뿐 아니라 U+0131이 든 `buıld` 와 U+017F가 든 `reſearch` 도 받는다. ASCII만 접는 구현과는 이런 글자에서만 갈린다. 그 밖의 값은 `WL-400` 이다. 파일을 읽을 때처럼 `build` 로 물러서지 않는다. 사람이 친 오타가 조용히 다른 필터가 되면 「필터가 안 먹는다」로 보이기 때문이다. 거르는 대상은 색인의 유형이라, 파일에 모르는 유형이 적혀 `build` 로 물러선 노트(1.7)도 `type=build` 에 걸린다.
3. `tag` 는 값을 `,` 로 나누고, 조각마다 5.3의 다듬기로 앞뒤를 떼고, 빈 조각을 버리고, 글자까지 같은 조각을 1개로 합친다. 남은 태그를 모두 가진 노트만 남는다. 비교는 색인에 든 태그(1.8로 읽은 값)와 글자까지 같아야 하고, 대소문자도 유니코드 정규화도 맞추지 않는다. 줄바꿈 검사는 조각을 다듬은 뒤에 한다. 다듬은 조각 안에 CR이나 LF가 남으면 `WL-400` 이다. 그래서 `{"tag":"랭킹\n,실험"}` 은 조각이 `랭킹` 과 `실험` 이 되어 통과하고, `{"tag":"랭\n킹"}` 은 선다. 조각 가운데 든 U+0085, U+2028, U+2029는 거절하지 않는다. 도구 표면도 같은 글자를 받아 쉼표로 나누므로, 쉼표가 든 태그로는 거를 수 없다(9.9).
4. `favorite` 는 도구 표면이 JSON 불리언을 받는다. 명령 표면은 다듬은 값을 로캘 없는 소문자(Java `toLowerCase(Locale.ROOT)`)로 바꿔 `true` 나 `false` 와 정확히 맞댄다. `true` 와 `false` 의 글자로 바뀌는 ASCII 밖 글자가 없어서, 결과는 ASCII 대소문자만 접는 것과 같다. 그 밖의 값은 `WL-400` 이고, 문구에는 소문자로 바꾼 값이 적힌다. `true` 만 거르고 `false` 는 필터를 안 건 것과 같다. 묶음 케이스 `list_docs/favorite=false` 가 인자 `{"favorite": false}` 로 110건을 잰다. 옛 CLI가 참일 때만 걸러서, 거짓을 「즐겨찾기 아닌 것만」으로 읽으면 옛 CLI와 이 엔진이 같은 인자에 다른 답을 내기 때문이다.
5. `favoriteCategory` 는 노트의 `favoriteCategory` (1.7)와 글자까지 똑같은 노트만 남긴다. 실패는 없다. 노트의 `favorite` 값은 안 본다. 부분 일치가 아닌 이유는 이 값이 화면에서 골라 넣는 폴더 라벨이고, 부분 일치면 「회사」가 「회사-보안」까지 끌어오기 때문이다. 저장된 값은 1.7대로 UTF-16 코드 단위 100개까지라서, 그보다 긴 필터 값은 아무것도 안 고른다.
6. `date`, `from`, `to` 는 이 차례로 각각 날짜로 읽는다. 날짜 문법은 Java `LocalDate.parse` (ISO 날짜, 엄격한 해석)와 같고 아래가 전부다.
   - 연도는 ASCII 숫자다. 부호가 없으면 정확히 4자리다. `+` 가 붙으면 5자리 이상, `-` 가 붙으면 4자리 이상이고 모두 0이면 안 된다. 부호가 붙으면 10자리까지 읽지만 연도는 -999,999,999부터 999,999,999까지만 받는다.
   - 연도 뒤에 `-`, 2자리 월, `-`, 2자리 일이 오고 그 뒤에는 아무 글자도 없다.
   - 달력에 있는 날이어야 한다. 연도 0과 음수 연도도 달력으로 받는다.

   그래서 `2026-6-1`, `2026-02-31`, `2026-06-16T10:00`, `+2026-06-16`, `12026-06-16`, `-0000-01-01` 은 `WL-400` 이고, `0000-01-01`, `-0001-01-01`, `+12026-01-01` 은 통과한다. 다음에 구간을 짓고 양 끝을 포함한다. `date` 만 있으면 그날 하루다. `date` 와 `from` 이나 `to` 가 함께 오면 하한은 `date` 와 `from` 가운데 늦은 날이고, 상한은 `date` 와 `to` 가운데 이른 날이다. 옛 CLI가 조건 3개를 따로 AND로 걸었고, 이 겹친 구간은 그 결과와 같다. 하한이 상한보다 뒤면 `WL-400` 이고, `date` 가 구간 밖이라 겹친 자리가 없을 때도 같다. 하한과 상한의 앞뒤는 달력으로 견준다. 노트 쪽 날짜는 `created` 를 그 오프셋 그대로 둔 달력 날짜, 곧 응답의 `date` 다. 노트를 고르는 견주기는 날짜를 `yyyy-MM-dd` 글자로 바꿔 UTF-8 바이트 차례로 한다. 4자리 연도끼리는 달력 차례와 같지만, 9999를 넘는 연도는 글자가 `+` 로 시작해서 어긋난다(9.9).
7. `limit` (명령 표면)은 5.3의 정수 읽개로 읽고, 정수가 아니면 `WL-400` 이다. 32비트 범위를 넘는 3000000000 도 정수가 아니다. 숫자가 아닌 값을 0으로 물러서 읽지 않는 이유는, 0이 「전부」라서 오타가 vault 전체를 내면 안 되기 때문이다. 안 주거나 빈 값이면 100이고, 0 이하면 전부다.
8. `bodies` (명령 표면)는 다듬은 값이 정확히 `true` 나 `false` 여야 한다. `favorite` 와 달리 대소문자를 가린다. 안 주거나 빈 값이면 거짓이다. 이 검사는 목록을 다 읽은 뒤에 해서, 다른 인자의 실패와 첨부 읽기의 예상 밖 실패(9.9)가 먼저 나온다. 걸려도 stdout은 비고 종료 코드 3이다.

볼 층은 인자가 아니라 표면이 정한다. 도구 표면은 `reading` 만, 명령 표면은 `reading` 과 `record` 를 본다(코드 읽기로 확인). 기록 노트에 마스킹이 못 가린 자격증명이 섞일 수 있어서 AI가 쓰는 표면에서만 감춘다(5.5).

실패하면 stdout은 늘 0바이트이고, stderr는 진단 줄 뒤 `WL-<번호> <문구>` 로 끝난다(6.4). 차례 1과 2의 문구는 11.4와 같다. 나머지의 지금 문구는 표 차례대로 이렇다.

```text
WL-400 list_docs 이 받는 인자는 JSON 한 덩어리인데 <n> 개를 받았다. 셸에서 따옴표로 감쌌는지 본다: list_docs '{"키":"값"}'
WL-400 인자 JSON 파싱 실패(list_docs): <다듬은 원문>
WL-400 인자 검증 실패(list_docs): 인자는 JSON 객체여야 한다: <다듬은 원문>
WL-400 인자 검증 실패(list_docs): 모르는 키다: [<정렬한 키들>]. 쓸 수 있는 것은 [agenda, date, dateFrom, dateTo, type, tag, favorite, favoriteCategory] 뿐이다.
WL-400 인자 검증 실패(list_docs): <키> 는 문자열 여야 한다: <JSON 값>
WL-400 list-docs 이 모르는 옵션이다: <이름>. 쓸 수 있는 것은 [agenda, bodies, date, favorite, favoriteCategory, from, limit, tag, to, type] 뿐이다.
WL-400 list-docs 이 받는 자리 인자는 0 개인데 <n> 개를 받았다: <사용법>
WL-404 아젠다 not found: <다듬은 값>
WL-400 모르는 유형 이다: <다듬은 값>. 쓸 수 있는 것은 [plan, build, report, research, meeting, free] 뿐이다.
WL-400 태그에 줄바꿈이 있다: '<다듬은 조각>'
WL-400 모르는 즐겨찾기 값 이다: <소문자로 바꾼 값>. 쓸 수 있는 것은 [true, false] 뿐이다.
WL-400 <date 또는 from 또는 to> 은 YYYY-MM-DD 모양이어야 한다: <다듬은 값>
WL-400 날짜 구간이 뒤집혔다: <하한> ~ <상한>
WL-400 limit 은 숫자여야 한다: <다듬은 값>
WL-400 bodies 은 true 나 false 여야 한다: <다듬은 값>
```

도구 표면의 불리언 자리는 `<키> 는 true 나 false 여야 한다: <JSON 값>` 이다. `<JSON 값>` 은 받은 값을 공백 없는 JSON 글로 다시 적은 것이라, 문자열이면 따옴표가 붙고 `null` 은 `null` 이다. 날짜 문구는 도구 표면에서도 `dateFrom` 이 아니라 `from` 을 쓴다. `<하한>` 과 `<상한>` 은 날짜를 ISO로 다시 적은 글이라, 9999를 넘는 연도는 `+12026-01-01` 처럼 적힌다. 태그 문구의 조각에 든 줄바꿈은 그대로 실려서 문구가 여러 줄이 된다. `<사용법>` 은 아래 글이다.

```
list-docs [agenda=<slug 또는 이름>] [type=<유형>] [tag=<태그,태그>] [favorite=true] [favoriteCategory=<라벨>] [date=<YYYY-MM-DD>] [from=<YYYY-MM-DD>] [to=<YYYY-MM-DD>] [limit=<건수. 0 이면 전부>] [bodies=true. 본문까지 싣는다. 기본은 메타만]
```

계약은 처음 나오는 `WL-` 번호와 종료 코드이고, 문구는 계약이 아니다(0.2).

## 9.5 읽는 자리와 신선도

| 값 | 출처 | 시점 |
|---|---|---|
| 어떤 노트가 있는지, 필터가 보는 값, 차례, `type`, `title`, `created`, `date`, `time`, `mins`, `tier`, `format`, `path`, `tags`, `links`, `favorite`, `favoriteCategory`, `template`, `evaluation` | 색인의 노트 표 | 마지막 색인 |
| 아젠다 찾기, `agenda`, `agendaTitle` | 색인의 아젠다 표 | 마지막 색인 |
| `precondition`, 도장, `sessionId`, `body` | 줄마다 본문 파일. 1번 읽고 1번 해석한다 | 부를 때 |
| `attachText`, 그리고 싣지 않을 때도 읽는 HTML 첨부 | 줄마다 메인 노트 `attach/` 의 HTML 첨부(10.5) | 부를 때. 어느 첨부를 읽을지는 색인이 정한다 |

읽기는 색인을 안 맞춰서(8.3), 목록은 마지막 `reindex`, `reindex-paths`, 쓰기 명령 뒤의 상태다. 그 뒤 디스크에 생긴 노트는 안 나오고, 사라진 노트는 메타로 그대로 나온다.

본문 파일은 색인의 경로와 색인의 포맷으로 정한다. 폴더 노트면 `<path>/note.md` 나 `<path>/note.html` 이고, 단일 파일 노트면 `<path>` 그 파일이다. json 노트는 본문 파일을 아예 안 연다(11.5와 같다). 색인 뒤 그 파일이 사라졌거나, 1,000,000바이트를 넘거나(1.6), 엄격한 UTF-8이 아니거나, 읽다 입출력 오류가 나면 줄은 색인의 메타로 나온다. 그때 `precondition`, 도장, `sessionId` 가 없고 `bodies=true` 면 `"body": ""` 다. 크기는 1,000,000바이트까지 받고 1바이트라도 넘으면 이 갈래다. 이 갈래들이 실패가 아닌 이유는, 파일 1개가 목록 전체를 세우면 안 되기 때문이다.

엔진은 그 파일 안의 `id` 를 색인과 맞대지 않는다. 그래서 색인 뒤 같은 경로에 다른 노트의 파일이 들어서면, 그 파일의 본문과 토큰과 도장과 `sessionId` 가 색인의 메타와 줄 1개에 섞여 나온다(9.9). 포맷이 바뀐 경우도 색인 포맷의 파일만 찾는다. 폴더의 `note.md` 가 지워지고 `note.json` 이 생겼으면, 다음 색인 전까지는 본문 파일이 사라진 `markdown` 노트로 다룬다. 묶음은 vault를 안 바꿔서 이 낡음을 못 재고, 부를 때마다 vault를 훑는 구현도 통과한다(8.6).

차례는 이렇게 정한다(코드 읽기로 확인).

1. 색인에 적힌 `created` 글자의 오름차순이다. 이 글자는 1.9의 꼴(초까지 적고 초 아래는 없고, 오프셋 0은 `Z`)이고 노트에 적힌 오프셋을 그대로 둔다. 견주기는 글자의 바이트 차례라서, 오프셋이 섞이면 순간이 아니라 적힌 벽시계 글자로 늘어선다(9.9).
2. 같으면 vault 상대 경로에서 `/`를 모두 `U+0001`로 바꾼 글자의 바이트 차례다. 그래야 `notes/serving/` 아래 노트가 `notes/serving-latency/` 아래 노트보다 앞에 서서(`U+0001`이 `-` 보다 작다), 폴더마다 이름 차례로 깊이 우선 훑은 차례(1.2)와 대체로 같아진다. 1.2의 이름 차례는 UTF-16 차례라서 아래 문단의 글자에서만 갈린다. 경로를 그대로 견주면 `/` (0x2F)가 `-` (0x2D)보다 커서 차례가 뒤집힌다. 같은 분에 만든 노트가 실제로 많고, 마지막 키가 유일하지 않으면 같은 질의가 회차마다 다른 차례를 낸다.

바이트 차례는 UTF-8 바이트를 앞에서부터 견주고, 앞이 같으면 짧은 쪽이 먼저인 차례다. 코드 포인트 차례와 같다. JavaScript의 기본 글자 비교는 UTF-16 코드 단위 차례라서, `U+10000` 이상 글자와 `U+E000` 부터 `U+FFFF` 까지 글자가 만나는 자리에서 갈린다.

건수는 이 차례로 늘어놓은 앞에서 자른다. 엔진은 안에서 쪽을 나눠(`limit` 이 1부터 99면 `limit` 건, 아니면 100건씩) 읽어 잇고, 모은 줄이 `limit` 에 닿거나 전체 건수에 닿거나 빈 쪽이 나오면 멈춘다. 바깥에서는 「정렬한 전체의 앞 `limit` 건」과 같고 다른 쓰기가 끼지 않으면 차이가 없다(9.9의 13번). 다만 마지막 쪽은 통째로 읽어서, 응답에 안 나갈 줄의 본문 파일과 첨부도 읽는다(9.9의 11번과 14번). 픽스처 vault에서 도구 표면 `list_docs '{}'` 는 110건을 낸다(묶음이 잰다). 명령 표면 `list-docs` 는 앞 100건(`ndfixture-00000001` 부터 `ndbulk-00000191` 까지)을 내고, `ndbulk-00000192` 부터 `ndbulk-00000201` 까지 10건을 아무 표시 없이 뺀다(예시 값, 코드 읽기로 계산).

HTML 첨부는 줄마다 읽고 `bodies=true` 가 아니면 버린다. 읽는 규칙은 10.5와 같다. 응답에 안 싣는데도 읽는 까닭은 목록과 검색과 `get_doc` 이 같은 읽기 길을 쓰기 때문이고, 그래서 첨부 읽기의 실패가 이 명령에도 닿는다(9.9).

serve 모드는 stdout이 64 MiB(67,108,864바이트)를 넘으면 응답 프레임을 1바이트도 안 쓰고 연결을 닫는다(4.2). 그래서 노트가 아주 많은 vault의 `bodies=true` 를 `wl-cli` 로 부르면, 사이드카에 못 붙은 것과 같은 종료 코드 4로 끝나는 것으로 읽힌다(3.3). 단발 모드에는 이 상한이 없다. 코드 읽기로 확인했고 실행해 보지는 않았다.

키마다의 값 규칙은 11.6과 같다. `agendaFacts`, `comments`, `deepLink` 는 목록에 없다. 사실층은 노트 수백 건이 같은 아젠다를 가리키는 응답에 실으면 같은 글이 수백 벌 실려서 뺀다. 코멘트는 노트를 고치기 직전에 사용자가 손댄 자리를 알리려고 1건 읽기(`get_doc`)에만 싣는 값이라, 목록에는 그 쓰임이 없다. `deepLink` 는 옛 CLI의 목록 줄에 없던 키이고(옛 모양은 `fixtures/cli-contract/cli-output-shape.json`), 앱이 받은 노트를 프론트매터로 다시 쓸 때 필요한 칸도 아니라서 목록에 더하지 않았다(코드 읽기로 확인).

상세와 값 규칙이 다른 키는 `tags` 1개뿐이다. 상세는 비어도 `[]` 를 싣지만 목록은 비면 키째 뺀다. 옛 CLI가 그렇게 냈고 묶음이 그 모양을 얼렸다. 반대로 `links` 는 비어도 늘 싣는다. 앱이 받은 노트를 그대로 프론트매터로 다시 쓰는데, 메모리에 없는 칸은 다음 저장에서 파일에서 사라지기 때문이다. `created`, `mins`, `format`, `path`, 평가의 `at` 이 목록에 있는 이유도 같다.

`body` 는 1.6으로 프론트매터를 뗀 나머지이고, 프론트매터를 못 읽게 됐으면 파일 전체다. `json` 노트는 `""` 다. `attachText` 는 10.5의 첨부 글이고, 그 글이 없으면 키가 빠진다. `body` 와 `attachText` 는 `precondition` 뒤, `links` 앞에 선다. 그 자리라야 `bodies=true` 의 줄이 상세(11.6)와 키 차례로 맞물린다. 그때 남는 차이는 상세에만 있는 `agendaFacts`, `comments`, `deepLink` 와, 비면 빠지는 `tags` 와, 목록에만 있는 `attachText` 다.

픽스처 vault를 펼쳐 `reindex` 를 부른 뒤 `list_docs '{"type": "research"}'` 를 부르면 종료 코드 0과 아래 바이트에 줄바꿈 1개가 나온다(묶음이 잰다). 토큰은 픽스처 파일로 계산한 실제 값이다. 묶음은 토큰 자리를 `⟦token:<파일 경로>⟧` 자리표로 맞대서, 토큰의 값이 아니라 빈칸과 따옴표와 역슬래시가 없는 글자인지와 같은 파일이 같은 회차에서 늘 같은 값인지만 잰다. 토큰 값의 정의는 1.14이고 코드 읽기로 확인했다. 이 장과 10장, 16장의 다른 예시에 적은 토큰도 픽스처 파일로 계산한 값이고, 묶음이 재는 범위는 같다.

## 9.9 받아들임 묶음과 얼어 있는 특이점

이 장에는 같은 장에서 다룰 짝 명령이 없어서 공통 절의 9.8은 두지 않는다. 빠진 내용이 아니라 장 틀이 「있을 때만 둔다」고 정한 자리다.

묶음이 덮는 것은 도구 표면 38건이다. 전체 1건, 아젠다 4건(slug 2, 제목 2), 유형 6건, 태그 2건, 날짜 15건, 즐겨찾기와 카테고리 4건, 필터를 섞은 4건, 실패 2건(없는 아젠다, 뒤집힌 구간)이다. 실패 2건은 종료 코드 3과 빈 stdout만 맞대고 WL 번호는 안 본다. 명령 표면(`limit`, `bodies`, 기록 층의 `tier`), 도장과 `sessionId` 키, 토큰 값, 같은 `created` 끼리의 차례, 오프셋이 섞인 차례, 색인 낡음, HTML 첨부, ASCII 밖 대소문자, 날짜 문법의 경계는 안 덮는다.

이 장이 `list_docs/favorite=false` 처럼 적은 것은 묶음 케이스의 이름표이고, 명령 표면 호출이 아니다. 묶음의 1부 케이스는 모두 도구 표면으로 부르고, 이름표 옆에 그 케이스의 JSON 인자를 함께 적었다.

아래는 지금 엔진의 특이점이다. 지킬지 고칠지는 부록 D에서 정하고, 항목 끝의 표시가 지금의 구현 범위를 정한다. 10.9, 12.9, 16.9도 같은 표시를 쓴다.

| 표시 | 뜻 | 다시 짓는 구현이 할 일 |
|---|---|---|
| 「묶음이 잰다」 | 받아들임 묶음이 그 동작을 맞댄다 | 지금 엔진과 같게 낸다. 다르게 내면 받아들임 검사가 실패하고, 고치려면 부록 D에서 정한 뒤 묶음의 기대값을 다시 떠야 한다 |
| 「묶음 밖」 | 묶음이 안 잰다 | 0.5의 기본값대로 지금 엔진과 같게 낸다. 다르게 내도 받아들임 검사는 지난다. 그래도 같게 내는 이유는 다음 쓰기 레인이 지금 엔진으로 기대값을 뜨고, 앱이 지금 동작에 기댈 수 있기 때문이다. 부록 D가 고치기로 정한 것만 다르게 낸다 |
| 「계약 아님」 | 결과가 요청이 겹친 시각이나 serve 모드 프로세스가 산 시간에 달려, 같은 입력에 같은 바이트를 정할 수 없다 | 재현하지 않아도 된다. 쪽을 나누지 않고 일관되게 읽거나 늘 파일을 새로 읽는 구현도 맞는 구현으로 본다. 같은 밀리초 안의 바깥 편집을 디스크대로 보는 구현을 8.6이 허용한 것과 같은 판단이고, 부록 D가 달리 정하면 그 결정을 따른다 |

1. 차례가 순간이 아니라 적힌 `created` 글자다. 오프셋이 다른 노트가 섞이면 시간 순서와 어긋나고, 초 아래 차이는 색인에서 버려져 경로 차례로 간다. 검색(10.6)은 순간으로 견줘서 이 명령과 검색의 차례가 갈린다. 묶음 밖.
2. 쉼표가 든 태그로는 못 거른다. 도구 표면의 `tag` 도 쉼표로 나눈다. 묶음 밖.
3. `favorite: false` 는 필터가 아니다. 묶음이 잰다(`list_docs/favorite=false`).
4. 빈 문자열 필터는 필터가 아니라서 `{"type": ""}` 도 전부를 낸다. 묶음 밖.
5. 날짜 실패 문구가 도구 표면에서도 `dateFrom`, `dateTo` 가 아니라 `from`, `to` 를 쓴다. 묶음 밖이고, 문구는 원래 계약이 아니다.
6. 명령 표면의 기본 100건 자르기에는 아무 표시가 없다. 응답이 봉투 없는 배열이라 잘렸는지 알 길이 없다. 묶음 밖.
7. `bodies` 는 대소문자를 가리고 `favorite` 는 안 가린다. 묶음 밖.
8. `type` 의 대소문자 무시가 유니코드 대응이라 `buıld` 가 `build` 로 통한다. 묶음 밖.
9. 노트를 고르는 날짜 견주기가 `yyyy-MM-dd` 글자의 바이트 차례라서, 9999를 넘는 연도가 어긋난다. `+12026-01-01` 처럼 `+` (0x2B)로 시작하는 글자는 모든 4자리 연도 글자보다 앞선다. 그래서 하한으로 주면 모든 노트가 걸리고, 상한으로 주면 아무 노트도 안 걸린다. `from=+12026-01-01` 만 주면 전부를 내고, `to=+12026-01-01` 이나 `date=+12026-01-01` 을 주면 `[]` 를 낸다. 하한과 상한을 함께 주면 달력으로 견주는 뒤집힘 검사를 먼저 하고, 안 뒤집혔으면 그 뒤에 위 글자 견주기를 그대로 한다. 음수 연도는 `-` (0x2D)도 숫자보다 앞서지만, 노트의 연도는 늘 0 이상이라 달력과 같은 답이 나온다. 코드 읽기로만 확인했다. 묶음 밖.
10. 색인 뒤 같은 경로에 다른 노트의 파일이 들어서면, 그 파일의 본문, 토큰, 도장, `sessionId` 가 색인의 메타와 줄 1개에 섞인다(9.5). 다음 색인이 고친다. 다만 색인 없는 구현은 이 자리가 8.6의 「바깥 편집 뒤 다음 맞추기 전의 읽기」 갈래라서 디스크대로 내도 된다. 묶음 밖.
11. 줄마다 메인 노트의 HTML 첨부를 읽고, 읽다 입출력 오류가 나면 예외를 안 잡아 명령 전체가 예상 밖 실패로 끝난다(6.6). 권한이 없는 첨부나, 확인과 읽기 사이에 지워진 첨부에서 생긴다. 엔진이 쪽으로 읽은 줄은 `limit` 보다 많을 수 있어서(`limit=150` 이면 쪽 크기가 100이라 줄을 200개까지 읽고 150개만 낸다), 응답에 안 나갈 줄의 첨부도 이 실패를 낸다. 단발 모드는 stdout 0바이트, stderr에 Spring Boot의 실패 로그와 스택 트레이스를 남기고 종료 코드 1로 끝나는 것으로 읽힌다. 1은 엔진이 정한 값이 아니라 JVM이 정한 값이고, 6.6이 다시 짓는 구현에도 1을 요구한다. serve 모드는 상태 3과 오류 코드 칸 0과 `사이드카 안에서 실패했다: <예외 문구>. 자세한 것은 사이드카 로그에 있다.` 1줄을 낸다. 실행해 보지는 않았다. 묶음 밖.
12. `attachText` 는 60,000 UTF-16 코드 단위에서 잘려 서로게이트 쌍이 갈릴 수 있다. 그때 끝에 남은 짝 없는 서로게이트는 JSON 탈출(`\ud83d` 꼴)로 적히지 않고 stdout에 `?` (0x3F) 1바이트로 나간다(6.1). 규칙은 10.9의 7번과 같다. 묶음 밖.
13. 안쪽 쪽 나누기가 쪽마다 색인을 따로 읽고 따로 세어서, 쪽 사이에 다른 연결이나 다른 프로세스의 쓰기가 끼면 겹친 줄이나 빠진 줄이 나올 수 있다. 맞는 노트가 100건을 넘고 `limit` 이 0 이하이거나 100보다 커서 쪽을 2개 이상 읽을 때만 생긴다. 코드 읽기로만 확인했다. 계약 아님.
14. 엔진이 읽는 줄 가운데 본문 파일의 프론트매터에 1.8의 안 잡히는 표기(`mins: !!int abc` 같은 명시 태그)가 든 노트가 1개라도 있으면, 명령 전체가 예상 밖 실패로 끝난다(6.6). 줄마다 토큰과 도장을 얻으려고 프론트매터를 YAML로 읽는데, 그 읽개가 이 표기에서 YAML 오류가 아닌 예외를 내고 아무도 안 잡기 때문이다. 그런 파일은 `reindex` 도 세워서(1.15의 6번) 색인에는 그 전의 행이 남는다. `mins: .nan` 은 이 읽기에서 안 터진다. 11.9의 12번과 같은 뿌리이고, 11번처럼 응답에 안 나갈 줄도 해당한다. 코드 읽기로만 확인했다. 묶음 밖.
