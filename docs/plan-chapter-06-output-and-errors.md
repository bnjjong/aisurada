# 6장 기반 다음 개발 계획

작성일: 2026-10-26

다음 개발 목표는 **엔진 응답을 손실 없이 받아, 성공·부분 결과·실패를 구분하는 앱 공통 계층을 만드는 것**이다. 첫 작업은 실행 환경에 의존하지 않는 TypeScript 계약과 mock 검증으로 끝내고, 회고 화면을 첫 연동 대상으로 삼는다.

## 1. 현재 상태와 적용 범위

확인한 근거:

- [6장 출력 규약과 실패](./spec-chapter-06-output-and-errors.md): 출력 바이트, 응답 모양, 진단, 종료 코드, 예상 밖 실패.
- [4장 소켓 규약](./spec-chapter-04-socket-protocol.md): 응답 프레임의 상태와 오류 코드가 서로 다른 칸이다.
- [3장 수명](./spec-chapter-03-lifecycle.md), [5장 인자](./spec-chapter-05-arguments.md): 실행 모드와 호출 표면의 차이.
- `package.json`: React/Vite/TypeScript 앱이며 테스트 스크립트가 없다.
- `src/views/MainViews.tsx`, `src/views/DocRoute.tsx`: 화면은 샘플 또는 자리 표시자다.
- `src/store/useTabsStore.ts`, `src/store/useAgendaStore.ts`: 데이터는 초기 샘플과 메모리 상태를 사용한다.
- `step1-blueprint.html`: Tauri Rust와 사이드카 연동을 후속 단계로 제시한다. 현재 파일 목록에는 Tauri 실행부, 엔진 소스, jar, CLI가 없다.

이 계획은 현재 앱이 기존 엔진을 소비하는 범위를 기본으로 한다. 엔진을 새로 구현하는 경우의 출력 생성 작업은 7절에 별도로 둔다. 엔진 전체 재구현이나 전체 명령 연동을 이번 작업의 완료 조건으로 잡지 않는다.

문서에 언급된 성공 439건·실패 9건의 검증 묶음은 현재 저장소에 없다. 새로 작성하는 테스트는 이 묶음의 통과를 대신하지 않는다. `boundary-decisions.md`에 등장하는 Java 코드와 자가 시험 파일도 현재 파일 목록에는 없으므로 구현 완료의 근거로 삼지 않는다.

## 2. 먼저 고정할 설계

### 원본 응답과 화면 모델

호출 흐름은 다음과 같다.

```text
화면 → 명령별 클라이언트 → 공통 응답 해석 → Transport
                                             ├─ MockTransport
                                             └─ TauriTransport → wl-cli 또는 소켓
```

Transport는 실행 방식, 종료 코드, stdout/stderr 원본 바이트를 전달한다. 소켓이면 프레임의 오류 코드와 `pid`, `dbSchema`도 전달한다. 요청별로 응답을 모으며 화면이나 다른 요청과 진단 버퍼를 공유하지 않는다.

- 원본 응답의 `exitCode`는 숫자로 보존한다. 알려진 값 0~5를 분류하되 알 수 없는 값을 다른 코드로 덮어쓰지 않는다.
- 소켓의 오류 코드 0은 코드 없음이다. CLI에서 구조화된 코드가 제공되지 않는 상태와 출처를 구분한다.
- 소켓에서는 프레임의 오류 코드가 기준이다. stderr에 `WL-999`가 있어도 구조화된 400을 바꾸지 않는다.
- CLI에서는 문서의 `/\bWL-\d{3}\b/` 첫 일치를 호환 정보로 추출하되, 출처를 `stderr`로 표시한다. 이 추출값의 한계는 유지하고 자동 생성·재시도의 근거로 단독 사용하지 않는다.
- 연결 실패나 프레임 손상은 명령의 도메인 실패와 구분한다. 직접 소켓 연결에서 난 로컬 실패를 엔진이 반환한 코드라고 기록하지 않는다.
- JSON 해석·응답 스키마 오류는 앱의 계약 오류로 분류한다. 엔진의 `WL-500`으로 바꾸지 않는다.
- UI용 날짜·라벨 변환은 명시적인 매핑에서 한다. 원본 응답을 다듬거나 키를 채우지 않는다.

`NoteDoc`는 현재 탭 표시용 타입이며 `planning`, `code` 같은 UI 분류를 사용한다. 이를 엔진 DTO로 재사용하지 않고, 엔진의 실제 열거값과 응답 모양을 확인한 뒤 매핑한다.

### 응답 처리 규칙

| 관측값 | 앱 처리 |
|---|---|
| 종료 0, JSON 정상 | 성공. stderr가 있어도 실패로 바꾸지 않는다 |
| 종료 0, `incomplete` 있음 | 읽은 목록과 불완전 안내를 함께 보여 준다 |
| 종료 0, `warning` 있음 | 성공 결과와 경고를 함께 보여 준다 |
| 종료 0, `ok: false`·`failed`·`stoppedAt` 있음 | 해당 명령의 응답 규칙으로 일부 실패를 표시한다 |
| 종료 2 | 호출·설정 문제로 안내한다. `WL-400`이 있어도 종료 3으로 바꾸지 않는다 |
| 종료 3, WL 400/404/409/500 | 각각 입력·대상 없음·상태 거절·파일 처리 실패로 구분한다 |
| 종료 3, 소켓 오류 코드 0 | 예상 밖 엔진 실패로 안내하고 진단·로그 확인 경로를 제공한다 |
| 종료 4 또는 로컬 연결 실패 | 사이드카 연결 문제로 안내한다. 대상 없음으로 처리하지 않는다 |
| 종료 5, WL 412 | 충돌로 처리한다. 편집 내용을 보존하고 다시 읽기·재적용 경로를 제공한다 |
| 종료 1, 신호 종료, 미지의 코드 | 분류되지 않은 실행 실패로 보존하고 원문 진단을 제공한다 |
| 종료 0인데 JSON 없음·손상, 또는 실패인데 stdout 있음 | 계약 위반으로 기록하고 성공 데이터로 반영하지 않는다 |

`WL-404`만 대상 없음으로 해석할 수 있지만 자동 생성까지 실행하지 않는다. `WL-500`에는 영구적으로 거절되는 경우도 있으므로 일괄 자동 재시도하지 않는다. 쓰기 후 예상 밖 실패나 연결 끊김은 이미 반영된 쓰기가 있을 수 있어 재조회 후 상태를 확인한다. 같은 요청을 곧바로 다시 쓰지 않는다.

### 응답 모양과 알림

- 목록 3종은 `T[] | { reports/templates/trash: T[]; incomplete: ... }` 형태를 각각 검사한다. 빈 정상 배열과 읽지 못해서 빈 목록을 구분한다.
- 검색은 늘 봉투다. `query → total → returned → truncated? → hint? → docs` 순서를 계약 자료에 기록하고, `truncated`와 `hint`의 동반 여부를 검증한다.
- 코멘트는 `absent | loaded | unreadable` 상태를 보존한다. 상세 스키마는 11·19장 확보 후 정의한다.
- 키 누락, 빈 배열, `false`, `null`을 구분한다. 특히 회고의 `body`·`memo`, 평가 삭제의 `evaluation`은 명시적인 nullable 필드다.
- 경고는 엔진이 준 LF와 순서를 유지한다. stderr 원문도 보존하며, 사람이 읽는 문구를 파싱해 도메인 오류를 결정하지 않는다.
- 성공 결과의 경고·불완전 안내는 화면에 남기는 안내 영역으로 표시하고, stderr 원문은 상세 보기로 제공한다. 실패 안내와 읽은 결과를 동시에 표시할 수 있어야 한다.

## 3. 개발 순서와 완료 기준

### 작업 1 — 공통 응답 계약과 실패 분류 (다음 개발의 첫 단위)

예상 파일: `src/engine/types.ts`, `transport.ts`, `decodeResponse.ts`, `classifyFailure.ts`, `testing/MockTransport.ts` 및 테스트.

1. 실행 출처, 원본 바이트, 종료 코드, 구조화된 WL 코드의 타입을 정의한다.
2. 성공일 때만 JSON을 해석하고, 명령별 validator를 받는 공통 함수를 만든다. 타입 단언만으로 응답을 통과시키지 않는다.
3. 종료 코드와 WL 코드를 함께 분류한다. 원본·파생 분류·사용자 행동을 구분한다.
4. mock으로 성공, 진단 있는 성공, 코드별 실패, 응답 손상, 연결 실패를 주입한다.
5. 테스트 실행기를 선정하고 `test` 스크립트를 추가한다. 선택 시 현재 TypeScript/Vite 구성과 호환되는 버전을 확인한다.

완료 기준: 5절의 공통 계약 사례가 자동 검증되고 `npm run build`가 통과한다. React 화면이나 Tauri 없이 검증 가능해야 한다.

### 작업 2 — 봉투와 명령별 응답 검사

세부 범위·API·검증 기준은 [작업 2 개발 계획](./plan-chapter-06-task-02.md)을 따른다. 작업 1과 보완 개발은 코드 확인 및 테스트 31개·빌드 통과로 검토했다.

예상 파일: `src/engine/envelopes.ts`, `commands/reports.ts`, `__fixtures__/` 및 테스트.

1. 정상 배열과 incomplete 봉투의 분기를 구현한다.
2. 검색 봉투와 warning 전달 규칙을 구현한다. 개별 검색 행의 전체 DTO는 10장 확보 후 완성한다.
3. 6장에 실제 예시가 있는 회고 목록·단건 응답을 우선 검증한다. 본문 없는 회고의 null과 목록의 `hasMemo: false`를 구분한다.
4. 고정 문구와 키 순서의 기대 바이트를 fixture로 관리한다. 직접 만든 경계 예시에는 합성 fixture임을 표시한다.

완료 기준: 정상 빈 목록, 불완전 빈 목록, nullable 회고, 잘린 검색을 구분하며 원본 데이터를 변경하지 않는다. 미확보한 명령 스키마를 임의로 완성하지 않는다.

### 작업 3 — 회고 화면에서 한 경로 완성

예상 변경: `src/views/ReviewView.tsx`, `src/routes.tsx`, 공통 결과 안내 컴포넌트.

1. `/review`의 `GenericView`를 회고 목록·단건 읽기 화면으로 교체한다.
2. 로딩·빈 목록·정상 목록·일부 누락·실패 상태를 표시한다.
3. 같은 클라이언트에 mock을 주입해 성공 stderr와 WL 실패를 실제 화면에서 확인한다.
4. 늦게 도착한 이전 요청이 현재 선택의 결과를 덮지 않도록 요청 식별 또는 취소 처리를 한다.

완료 기준: mock 시나리오 전환으로 상태를 재현할 수 있고, 목록을 일부 읽었을 때 결과와 안내가 함께 남는다. 브라우저 mock 단계임을 명확히 표시한다.

회고를 먼저 고르는 이유: 6장에 목록·단건의 구체적인 예시가 있고, null 예외와 incomplete 봉투를 한 흐름에서 검증할 수 있다. 노트 편집과 충돌 복구는 읽기 경로 검증 뒤에 연결한다.

### 작업 4 — Tauri와 실제 엔진 연결

착수 전 필요한 입력: 실행 가능한 엔진/CLI와 테스트 vault, 회고 명령 상세 및 관련 부록. 현재 확보한 6장만으로 옵션 전체를 추정하지 않는다.

1. 기존 청사진의 Tauri 방향으로 네이티브 호스트를 구성하고 `TauriTransport`를 구현한다.
2. 첫 실연결은 기존 `wl-cli`를 argv 배열로 호출하는 방식을 우선 검토한다. 셸 문자열을 조립하지 않고 stdout/stderr·종료 코드를 수집한다.
3. 구조화된 오류 코드가 필요한 직접 소켓 방식은 3·4장의 프로세스 수명, 잠금, 프레임 검증을 포함하는 별도 작업으로 평가한다. CLI 경로와 이 경로를 동시에 구현하지 않는다.
4. 격리한 테스트 vault에서 읽기 명령을 실행하고 mock과 동일한 화면 경로를 통과시킨다.

완료 기준: 실제 성공·진단·대상 없음·설정 실패·사이드카 연결 실패를 구분한다. mock으로의 조용한 대체가 없어야 한다. 실제 엔진이 제공되기 전에는 이 단계의 통과를 보고하지 않는다.

### 작업 5 — 쓰기 경고와 충돌 복구

7장, 13~15장, 부록 C·D를 확보하고 노트 읽기·편집 기능이 준비된 뒤 착수한다.

- 쓰기 성공의 warning을 유지하고, 실패 시 편집 초안을 보존한다.
- WL-412이면 최신 본문과 토큰을 읽고 사용자가 수정 내용을 재적용할 경로를 만든다.
- 쓰기 응답을 못 받았을 때는 재조회 후 반영 여부를 확인한다.
- 닫기 가드의 `settleWrites()`와 연결한다. 충돌·실패가 있는 초안을 저장 완료로 처리하지 않는다.

완료 기준: 충돌·예상 밖 실패·연결 끊김에서 초안이 남고 중복 쓰기가 발생하지 않는다.

## 4. 작업 의존 관계

`작업 1 → 작업 2 → 작업 3 → 작업 4` 순서로 진행한다. 작업 5는 작업 4 및 편집·토큰 규약 확보 뒤에 진행한다.

첫 개발 요청의 범위는 **작업 1**로 고정하는 것을 권장한다. 이 단위가 끝나면 엔진 없이도 오류 분류의 정확성을 확인할 수 있고, 후속 UI와 실행부가 같은 계약을 사용한다.

| 구분 | 필수 사례 | 확인할 결과 |
|---|---|---|
| 원본 보존 | 한글, 따옴표, 역슬래시, 제어문자, U+2028/U+2029 | 원본 바이트를 그대로 보존하고 JSON 값이 올바르게 해석됨 |

| 불완전 목록 | 정상 [], reports/templates/trash 각각의 봉투 | 빈 결과와 미독 항목을 구분 |
| 조건부 키 | 키 없음, false, [], null | 서로 다른 값으로 유지 |
| 검색 | 0건, 잘림, truncated/hint 한쪽만 있음 | 정상 봉투 처리 및 잘못된 조합 감지 |
| 일부 성공 | ok:false, failed, stoppedAt | 명령별 정책 적용, 종료 0 유지 |
| 경고 | 여러 줄 warning + stderr | 각 원문과 줄 순서 유지 |
| 미지의 값 | 알려지지 않은 종료/WL 코드 | 원본 유지, 성공·404 등으로 추측하지 않음 |

공통 사례는 작업 1, 봉투·명령 사례는 작업 2, 화면·요청 경합은 작업 3에서 검증한다. 작업 4부터 실제 프로세스와 임시 vault를 사용하는 통합 검증을 더한다. 실제 쓰기 검증은 작업 5의 격리 vault에서 수행한다.

## 7. 엔진 재구현으로 범위가 확장되는 경우

앱 소비 계층과 별도로 다음 작업이 필요하다.

1. 명령별 응답 builder로 키 순서·조건부 키·null 예외를 명시한다. 전역의 falsy 제거·null 채우기를 금지한다.
2. 결과를 완전히 직렬화한 뒤 출력한다. 실패 시 stdout 0바이트를 보장하고 단발/serve에서 같은 바이트를 사용한다.
3. UTF-8을 로캘과 무관하게 고정하고 JSON escape와 마지막 LF를 바이트 비교한다.
4. 알려진 오류의 진단→WL 줄 순서와 종료 코드, 예상 밖 실패의 모드별 경계를 구현한다. serve는 요청 실패 후 다음 요청을 받고 스택을 별도 로그에 남긴다.
5. 짝 없는 서로게이트의 `?` 치환은 JSON 직렬화와 UTF-8 변환 양쪽의 차이를 시험한다. JavaScript 기본 `JSON.stringify`나 `TextEncoder`만으로 같다고 가정하지 않는다. 구현 정책은 부록 D 확인 후 고정한다.
6. 4부 실수 `2.0` 및 특수 시각 문자열은 별도 계약으로 검증한다. 1부 정수 직렬화만 통과하고 전체 호환을 선언하지 않는다.
7. 공식 448건과 새 경계 사례를 함께 실행한다. stderr 자유 문구 전체를 무조건 고정하지 않고, 계약인 코드·고정 봉투 문구·순서·선결 조건 안내의 뜻을 검증한다.

이번 계획 작성에서 애플리케이션 코드는 변경하지 않았다. 구현과 테스트 실행은 후속 개발 작업이다.
