# Rust 엔진 이전 1단계 — 노트 머리(YAML) 읽기·쓰기

## 요약

**결론:** 노트 머리(맨 위 YAML)의 읽기와 쓰기를 Rust(`engine-rs/crates/ais-core`의 `frontmatter`)로 옮겼고, Java 엔진과 같은 결과를 내는 것을 확인했다. 진짜 노트 머리 71건은 모두, 손으로 만든 사례 96건은 순환 구조 1건(알려진 차이)만 빼고 모두 읽은 값과 다시 쓴 글이 Java와 같고, 무작위로 망가뜨린 입력 22,000건에서는 값이 어긋나거나 Java가 읽는 입력을 못 읽은 경우가 9건(0.04%)이었다. 그 9건은 모두 흔치 않은 문법이다. YAML 파서는 `libyaml-safer`로 정했다.

이 기록은 개발자의 vault 노트 「Rust 엔진 이전 — 결정 3: 코드 구조와 클라우드 대비」의 6절 「앞으로의 단계」 가운데 1단계의 결과다. 요구사항은 같은 기능을 하는 것을 기준으로 옮기는 것이었고(바이트 단위 호환이 아님), 완료 기준은 Rust 구현이 Java 엔진과 같은 읽기·쓰기 결과를 내는지 재어 보고 YAML 라이브러리를 정하는 것이었다.

## 1. 무엇을 했나

그림 설명: 같은 입력을 Java 엔진과 Rust 구현에 넣고, Java가 낸 결과(기준값)와 Rust 결과를 사례마다 맞댄다. 용어는 이렇다. **기준값**은 지금 엔진이 실제로 낸 결과다. **퍼징**은 진짜 노트와 사례를 무작위로 망가뜨려(글자 지우기, 줄 바꾸기, 이상한 글 끼워 넣기) 두 구현이 같은 반응을 하는지 보는 시험이다. **SnakeYAML**은 Java 엔진이 노트 머리를 읽는 데 쓰는 YAML 라이브러리다.

## 2. 알게 된 것

- **Java 엔진은 노트 머리를 쓸 때 YAML 라이브러리를 쓰지 않는다.** 825줄짜리 직접 만든 작성기(`FrontmatterWriter`)가 키 차례, 따옴표 규칙, 긴 글 접기를 정한다. SnakeYAML은 읽기에만 쓰인다. 그래서 Rust에서도 쓰기에는 라이브러리가 필요 없고, 읽기에만 파서가 필요하다.
- **읽기 규칙은 YAML 1.1이다.** SnakeYAML은 `yes`·`no`·`on`·`off`를 불리언으로, `010`을 8진수 8로, `1:30`을 60진수 90으로 읽고, 시각(`2026-11-14T…`)은 일부러 문자열로 둔다. `y`와 `n`은 불리언이 아니다. Rust 파서는 문법만 읽고 형은 정하지 않으므로, 형을 정하는 정규식은 SnakeYAML 2.4에서 직접 꺼내(`Resolver.INT` 등) 그대로 옮겼다. 기억으로 쓴 정규식은 몇 군데 틀려서, 실제 값을 확인하고 쓴 것이 중요했다.
- **같은 키가 겹칠 때의 순서가 규칙이다.** 같은 키가 여러 번 나오면 앞의 것을 지우고 마지막 자리에 둔다. 병합 키(`<<`)는 먼저 나온 원본이 이기고, 맵이 직접 적은 값만 제자리에서 덮어쓴다. 이 순서를 맞추느라 처음 구현을 두 번 고쳤다.
- **외부에서 오는 입력이라 읽기 코드가 죽으면 안 된다.** 퍼징이 `base: &base { <<: *base }`처럼 자기 자신을 병합하는 입력에서 읽기 코드가 끝없이 재귀해 스택 오버플로로 죽는 것을 잡았다. 병합 중인 맵을 다시 병합하는 경우를 감지하도록 고쳤다.

## 3. 결과

| 입력 | 건수 | 읽기 일치 | 쓰기 일치 | 비고 |
| --- | ---: | ---: | ---: | --- |
| 진짜 vault 노트 머리(43)와 손 확인용 vault 노트 머리(28) | 71 | 71 | 71 | 전부 일치 |
| 손으로 만든 사례(`cases.txt`)와 깊이 시험 | 96 | 95 | 70/70 | 나머지 1건은 알려진 차이(순환 구조) |
| 퍼징, 시드 1 | 4,000 | 3,970 | 모두 일치 | 실패 0, 알려진 차이 5, 경고 25 |
| 퍼징, 시드 2~4 | 18,000 | 17,860 | 모두 일치 | 실패 9, 알려진 차이 19, 경고 112 |

- 퍼징 행은 손으로 만든 사례 96건을 뺀 숫자다(실행마다 그 사례가 함께 들어가서 뺐다). 퍼징 입력에서 쓰기를 맞댄 것은 읽은 값이 같았던 경우 모두이고(약 12,700건), 어긋난 것이 없다.
- 읽기 일치에는 Java도 못 읽은 입력(머리 없음)을 Rust도 못 읽은 경우가 포함된다.
- 퍼징 사례의 씨앗은 진짜 노트 머리와 손으로 만든 사례이고, 시드를 고정해서 같은 사례를 다시 만들 수 있다.

### 알려진 차이와 경고

| 구분 | 내용 | 규모 | 판단 |
| --- | --- | --- | --- |
| 알려진 차이 | 자기 자신을 가리키는 구조(`a: &x [*x]`): Java는 순환 구조를 만들고 Rust는 머리 없음으로 본다 | 손으로 만든 사례 1건 | 노트 머리에 쓸 일이 없어서 그대로 둔다. |
| 알려진 차이 | Java가 `NumberFormatException`으로 명령 자체가 실패하는 입력(`a: ._` 같은 이상한 실수 글) | 시드당 4~8건 | Rust는 머리 없음으로 본다. |
| 알려진 차이 | 60진수 정수가 32비트를 넘는 입력(`1234567890123456789:0`): Java는 값이 넘쳐서 틀어진다(`-2101722900`). Rust는 맞는 값(`74074073407407407340`)을 낸다 | 22,000건 중 2건 | JVM 특이점이라 재현하지 않는다(결정 1-나). |
| 경고 | Java는 거부하는데 Rust는 읽는다. 대부분 값이 탭 하나뿐인 입력(`editedAt:\t`)과 내용이 잘못된 `!!timestamp`·`!!binary`·`!!set` 태그다 | 시드당 25~38건 | 노트가 사라지는 쪽이 아니라서 실패로 세지 않는다. |

### 남은 실패 9건

| 종류 | 예 | 건수 |
| --- | --- | ---: |
| 흐름 컬렉션(`{}`, `[]`) 안에서 콜론 뒤에 공백 없이 값이 붙은 형태 | `y:[2, 3]`, `<<:{k: 1}`, `[1:, 2]`, `{a 1, b:[2]}` | 6 |
| 앵커 이름에 특수문자가 든 형태 | `&!!bool "true"`, `&? k`, `&amp'` | 3 |

두 가지 모두 Java(SnakeYAML 2.x)는 읽고 Rust 파서(libyaml 계통)는 거부한다. 이 형태는 엔진이 쓴 노트에는 나오지 않는다. 엔진은 흐름 컬렉션을 쓰지 않고(프로젝트 파일의 `repos:`만 따옴표 친 키의 한 줄 JSON), `&`로 시작하는 글은 따옴표로 감싼다. 사람이 손으로 이런 머리를 썼다면 그 노트는 Rust에서 머리 없음으로 보여 목록에서 건너뛰어진다.

## 4. 파서 선택: `libyaml-safer`

같은 퍼징 4,096건(시드 1, 손으로 만든 사례 포함)을 두 파서로 돌려 맞댔다.

| | `saphyr-parser` 0.3.4 | `libyaml-safer` 0.3.0 |
| --- | --- | --- |
| 성격 | YAML 1.2 규격을 엄격히 따르는 파서 | libyaml(C)을 한 줄씩 옮긴 안전한 Rust 파서. "libyaml과 동작이 다르면 버그"가 방침 |
| 어긋난 사례 | 80건. Java가 읽는 입력을 거부하는 경우가 섞여 있었다(따옴표 문자열을 줄바꿈으로 이어 쓴 형태, 흐름 컬렉션의 줄 이음 등) | 30건. Java가 읽는 입력을 거부하는 경우가 없었다 |
| 최근 갱신 | 2026-11-11, 최근 다운로드 약 850만 | 2025-12-22(0.3.0), 최근 다운로드 약 4.8만 |
| 라이선스 | MIT 또는 Apache-2.0 | MIT |

SnakeYAML이 PyYAML/libyaml 계통이라, 같은 계통의 파서가 문법을 받아들이는 폭이 거의 같았다. 갱신이 뜸한 것은 걱정이지만, 이식 대상인 libyaml이 안정된 라이브러리이고 이 크레이트가 같은 동작을 목표로 하기 때문에 크게 보지 않는다. 파서는 [`events.rs`](../engine-rs/crates/ais-core/src/frontmatter/events.rs)의 얇은 경계(이벤트 → `Raw`) 뒤에 있어서, 나중에 바꿔도 값 해석 규칙(`read.rs`)은 그대로 둘 수 있다.

## 5. 아직 하지 않은 것

- **파일 가르기:** 본문 파일에서 머리와 본문을 가르는 규칙(`---` 울타리, HTML 노트의 `<!--aisurada` 울타리, BOM 처리)은 아직 옮기지 않았다. Java의 `MetaWriter.split`이다. 2단계(읽기 명령 이전)에서 한다.
- **새 노트의 머리 만들기:** 키 차례가 고정된 `buildFullNoteFrontmatter`와 아젠다·프로젝트 머리는 옮기지 않았다. 3단계(쓰기 경로)에서 한다. 이번에 옮긴 `dump_string`과 `dump_key`가 그 바탕이다.
- **태스크와 자원 파일:** `TaskFormat`, `ResourceFormat`은 직접 만든 작성기가 아니라 SnakeYAML의 쓰기(`Yaml.dump`, 블록 스타일)를 쓴다. 이 글의 모양을 Rust에서 똑같이 만들지, 읽기만 호환하고 새로 쓸지는 아직 정하지 않았다. 4단계 전에 정해야 한다.
- **측정하지 않은 것:** 읽기·쓰기 속도, 메모리. 기준값은 모두 이 컴퓨터(macOS, JDK 21)에서 뽑았다.
- **앱에는 연결하지 않았다.** 호스트와 `ais-cli`는 여전히 Java 엔진을 쓴다.
