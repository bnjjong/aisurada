# Rust 엔진 이전 3단계 W4b — 휴지통 쓰기(`delete_doc`, `restore_doc`, `purge_doc`, `empty_trash`)

## 요약

**결론:** 노트를 휴지통으로 보내고, 되살리고, 영구 삭제하고, 비우는 쓰기 4개를 Rust 엔진으로 옮겼다. 이것으로 **W4와 3단계(쓰기 경로)가 끝났다.** Java 엔진과 합성 vault에서 **응답과 폴더 전체 바이트가 976건 모두 같다**(앞 묶음 포함, 488단계, 이 가운데 휴지통은 32단계, 준비 단계 2개 포함). 쓰기 스위치(`AISURADA_ENGINE_WRITE=rust`)는 기본 꺼짐이라 앱의 동작은 그대로다. 실제 창 확인은 아직 못 했다([손 확인 안내](rust-engine-hand-check.md)).

[W4a 기록](rust-engine-step3-w4a.md)에 이어진다. 앱 화면이 만드는 vault 쓰기 명령은 채팅 쓰기 `append-chat-turn`을 뺀 나머지가 모두 호출 객체이고 Rust 엔진이 처리할 수 있다. 문자열 목록(Java 길)로 남은 것은 `append-chat-turn`, 채팅·세션 읽기(`list-chats`, `read-session`, `session-titles`), 일정(`schedule`)이며 이것들은 4단계(세션·묻기) 몫이다.

## 1. 하는 일

휴지통은 `.aisurada/trash/` 아래에 있다. 보관물은 `files/`에, 목록은 `trash.json`에 있고 목록 맨 앞이 가장 최근에 버린 항목이다.

| 명령 | 하는 일 |
| --- | --- |
| `delete_doc` | 노트(폴더째, 후속 노트와 첨부 포함)를 `files/<휴지통 id>`로 옮기고 목록 맨 앞에 항목을 더한다. 경로가 `.md`·`.html`·`.json`으로 끝나면 보관 이름에 확장자를 붙인다. **즐겨찾기였으면** 응답에 `wasFavorite`·`favoriteCategory`와 「이 노트는 즐겨찾기였어요」 경고가 붙는다 |
| `restore_doc` | 보관물을 원래 아젠다의 자리(월별 배치면 만든 달 폴더)로 되돌리고 목록에서 뺀다. 자리에 이미 무엇이 있으면 이름에 `-restored-<휴지통 id 꼬리 6자>`를 붙인다. **원래 아젠다가 없어졌으면** `recovered` 아젠다(없으면 만든다)로 보내고, 보관물 머리의 `agenda`를 그 slug로 바꾼다. 보관 파일이 사라졌으면 목록에서만 정리하고 400으로 알린다 |
| `purge_doc` | 보관물과 목록의 항목을 영구 삭제한다 |
| `empty_trash` | 모든 항목의 보관물을 지우고 목록을 `[]`로 비운다. 못 지운 항목은 남기고 이유를 알린다. 응답에 지운 개수, 못 읽어 건너뛴 항목 수, 목록에 없는 보관물(고아) 수가 있다. 고아는 지우지 않고 세기만 한다 |

**목록이 1,000,000바이트를 넘으면** 쓸 때 목록 맨 뒤(가장 오래된) 항목부터 보관물까지 영구 삭제해서 줄인다. 항목이 하나만 남으면 멈춘다. 지운 항목은 응답의 `autoPurged`에 담는다. 이 일은 쓸 때마다 목록을 통째로 다시 지어 견주는 방식이라 항목을 한꺼번에 많이 줄여야 하면 느리다(Java도 같은 방식이다). 한 번에 한 항목씩 늘어나는 보통의 사용에서는 한두 번이면 끝난다.

**목록을 쓸 때 못 읽은 항목은 빠진다.** 목록 파일에 모양이 틀린 항목(id가 틀림, 날짜를 못 읽음 따위)이 있으면 읽기는 건너뛰고, 쓰기는 그 항목을 빼고 다시 쓴다. 이 점도 Java와 같다.

| 부품 | 자리 | 하는 일 |
| --- | --- | --- |
| 명령 | `commands/trash_write.rs` | 네 명령 |
| 목록·보관 폴더 | `write/trash_file.rs` | 보관 파일 자리(보관 폴더 밖으로 못 나감), 목록 파일 차례대로 읽기, 목록 쓰기와 크기 줄이기 |
| 읽기 | `vault/trash.rs` | 항목에 목록 파일의 차례(`file_order`)를 더했다. 쓸 때는 읽을 때의 「버린 시각이 늦은 것부터」가 아니라 파일에 적힌 차례를 지킨다 |
| 화면 | `data/commands.ts`의 `write.deleteDoc`, `restore`, `purge`, `emptyTrash` | 호출 객체가 됐다. 되살리기와 영구 삭제의 인자 이름은 `trashId`다 |

## 3. Java와 다르게 둔 것

- Java는 보내기 직전에 첨부 글을 한 번 훑는 `AttachText.extract`를 부르는데 결과를 쓰지 않는다. 첨부 하나를 못 읽으면 예외로 보내기가 실패하는 아주 드문 경우가 있는데, Rust는 이 훑기를 하지 않는다.
- 되살릴 때 보관물 머리나 파일을 못 읽어 아젠다를 못 고치면 Java는 진단 한 줄을 내보내고 그냥 옮기는데, Rust는 진단을 내보내지 않고 그냥 옮긴다. 목록이 1MB를 넘어 자동 영구 삭제가 일어날 때의 진단 줄도 같다(응답의 `autoPurged`가 알린다).
- 휴지통 목록은 읽을 때 YAML 읽개를 쓴다. 맞대기의 목록은 Java가 쓴 JSON이라 같다.
- 스냅숏 쓰기는 안 옮겼다(스냅숏 설정이 켜지면 호스트가 쓰기를 Java로 보낸다).

## 4. 3단계를 마치며

3단계(쓰기 경로)가 옮긴 쓰기 명령은 `commit_vault`를 빼고 **26개**다: 아젠다 3, 프로젝트 3, 템플릿 3, 사실층 1, `init_workspace`, 노트 머리 3(`set_favorite`, `evaluate_doc`, `link_docs`), 노트 `create_doc`·`update_doc`, 후속 노트 3, 코멘트 3, 휴지통 4. 맞대기는 **976건, 488단계에서 어긋남 0**이다.

앱을 `AISURADA_ENGINE_WRITE=rust`로 띄워야 이 길이 켜진다. **기본값을 바꾸는 일은 실제 앱 창에서 점검표를 다 누른 뒤에 별도 커밋으로** 한다(결정 G). 점검 결과는 이슈 [#54](https://github.com/bnjjong/aisurada/issues/54), [#61](https://github.com/bnjjong/aisurada/issues/61)에 남긴다.

## 5. 확인하지 못한 것과 남은 일

- **실제 앱 창에서 확인하지 못했다.** 손 확인 점검표에 휴지통 항목을 더했다.
- 두 프로세스가 휴지통 목록을 동시에 쓰는 경합 시험은 하지 않았다(이슈 #63).
- 다음은 4단계(세션·묻기·태스크·자원)다. Java 엔진이 아직 맡는 vault 쓰기: `write_attachment`, `export_markdown`, `shard-notes`, `plan_day`, 태스크·자원 명령, `append-chat-turn`. 앱 화면은 이 중 채팅 쪽 `append-chat-turn`만 쓴다.
