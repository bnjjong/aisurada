「새 구현」은 『withlog 1부 vault 엔진 설명서』만 보고 다른 기기에서 15장까지 지은 Java 21 구현이고, 이 저장소의 `temp/`에 있다. 「지금 엔진」은 withlog가 실제로 쓰는 Kotlin 사이드카 jar(10-20 빌드)다. 같은 픽스처 vault 2벌에 지금 엔진과 새 구현을 같은 차례로 불러 응답과 바뀐 파일을 바이트로 맞댔다. 1부 읽기 448건과 이 노트에 안 적은 쓰기 시나리오는 모두 같았다.

## 1. 깨진 노트가 있어도 15장 쓰기가 안 선다 - 높음

지금 엔진은 쓰기 전에 SQLite 색인을 디스크와 맞추고(설명서 8.3), 맞추기가 실패하면 쓰기를 거절한다(15.4의 3번). 그래서 vault에 노트로 못 읽히는 파일이 하나라도 있으면 쓰기가 모두 선다. 새 구현은 `create_doc`만 서고 15장 명령 3개(`set_favorite`, `evaluate_doc`, `link_docs`)는 그대로 간다.

reindex 뒤 깨진 노트(`mins: !!int abc`)를 넣고, 멀쩡한 노트 `ndfixture-00000002`(폴더 `2026-06-17-1100-연결-대상-노트-0002`)에 `set_favorite`을 불렀다. 노트 폴더 이름이 날짜로 시작해서 이름 차례가 곧 날짜 차례다. 쓰기에 실을 토큰(`f1`, 파일을 읽은 그대로라는 표시)은 깨진 노트를 넣기 전에 받았다.

| 넣은 것 | 지금 엔진 | 새 구현 |
|---|---|---|
| 6월 30일 폴더의 깨진 노트(대상보다 뒤) | 종료 코드 1, 안 씀 | 종료 코드 0, `favorite: true`를 씀 |
| 6월 1일 폴더의 깨진 노트(대상보다 앞) | 종료 코드 1, 안 씀 | 종료 코드 3, `WL-404 Note not found: ndfixture-00000002` |
| slug가 `serving`인 아젠다 파일 1개 더 | 종료 코드 1, 안 씀 | 종료 코드 3, 같은 `WL-404` |

지금 엔진의 예외는 깨진 노트면 `java.lang.NumberFormatException: For input string: "abc"`이고, 아젠다가 겹치면 `UNIQUE constraint failed: agendas.slug`다. `evaluate_doc`과 `link_docs`도 같은 모양으로 갈렸다.

표의 아래 2줄이 더 위험하다. 있는 노트를 「없다」고 답해서, 그 답을 믿은 Claude가 같은 노트를 새로 만들 수 있다. 새 구현은 같은 vault에서 `get_doc`도 `WL-404`라서 노트가 있는지 확인할 길도 없다. 설명서 8.6은 이 읽기 차이를 색인 없는 구현에 허용했지만 쓰기는 허용하지 않았다.

원인은 훑기 깃발 하나다. 새 구현은 색인 없이 명령마다 노트 폴더를 이름 차례로 훑고, `haltOnFatal`은 노트로 못 읽는 파일을 만났을 때 명령을 세울지 정하는 깃발이다. `create_doc`은 이 깃발을 `true`로 두고 먼저 훑는다(`CreateDoc.java:83`, `:84`). 15장 명령 3개는 읽기용 `NoteIndex.fresh`만 부르고(`SetFavorite.java:41`, `EvaluateDoc.java:44`, `LinkDocs.java:40`), 이 함수는 깃발을 `false`로 두고 깨진 파일 앞까지만 노트로 본다(`NoteIndex.java:53`, `:54`). 15장 명령도 `true`로 먼저 훑으면 고쳐진다.

## 2. create_doc이 명령줄의 샤드 설정을 안 본다 - 중간

샤드 vault는 노트를 `notes/<아젠다>/<YYYY-MM>/` 아래 달 폴더에 두는 배치다. 엔진은 vault 모양을 보고 새 노트의 자리를 정하고, 설정 `withlog.notes.shard.by.month`가 그 판정을 덮는다. 설명서 1.3과 33.1은 이 설정을 명령줄, JVM 속성, 환경변수 차례로 받게 했다.

| 단발 모드로 부른 꼴 | 지금 엔진이 만든 자리 | 새 구현이 만든 자리 |
|---|---|---|
| 평평한 vault에 `--withlog.notes.shard.by.month=true` | `notes/serving/2026-07/2026-07-01-1000-설정-참-...` | `notes/serving/2026-07-01-1000-설정-참-...` |
| 샤드 vault에 `--withlog.notes.shard.by.month=false` | `notes/serving/2026-07-01-1000-설정-거짓-...` | `notes/serving/2026-07/2026-07-01-1000-설정-거짓-...` |

새 구현은 시작할 때 명령줄과 JVM 속성과 환경변수를 모두 읽고 검증한다(`EngineConfig.java:178`). 그런데 노트 자리를 정하는 `isShardedVault`(`CreateDoc.java:710`)는 그 값을 안 쓰고 JVM 속성과 환경변수만 다시 읽는다. 앱은 이 설정 없이 serve 모드로 불러서 안 닿는다. 다만 설명서 28장은 샤드 방향을 단발 모드의 명령줄로 못박으라고 적었고, 그렇게 부른 `create_doc`은 노트를 반대쪽 배치에 만든다.

## 3. wl-cli가 WITHLOG_SIDECAR_JAR 파일이 있는지 따진다 - 중간

`wl-cli`는 엔진이 안 떠 있으면 launchd에 올리고, plist의 jar 자리를 환경변수 `WITHLOG_SIDECAR_JAR`에서 받는다. 설명서 3.4는 이 값을 상대 경로든 없는 파일이든 확인 없이 싣는다. JVM이 아닌 엔진은 자바 자리(`WITHLOG_SIDECAR_JAVA`)에 감싸는 스크립트를 주고 jar 자리에는 아무 경로나 줘도 되기 때문이다(3.4의 짝짓기 표).

새 구현은 그 파일이 없으면 값을 줬어도 아래 문구와 종료 코드 2로 끝난다(`WlCliMain.java:347`, `DoctorCommand.java:200`). 값을 줬는데 「없다」고 하니 문구가 틀렸고, 감싸는 스크립트 구성은 이 `wl-cli`로 못 띄운다. `doctor --plist`도 같은 검사에 걸린다.

```text
WL-400 WITHLOG_SIDECAR_JAR 가 없고 설치된 wl-sidecar.jar 도 없다(.../Library/Application Support/withlog/bin/wl-sidecar.jar). `install` 을 돌리거나 jar 의 절대 경로를 WITHLOG_SIDECAR_JAR 에 넣는다...
```

## 4. doctor가 커밋 밖 파일이 많으면 그 수를 못 잰다 - 중간

`wl-cli doctor`의 「커밋 밖」 줄은 vault git에 아직 안 담긴 파일 수이고, 자동 커밋이 멈춘 것을 알아채는 줄이다. 새 구현은 git이 끝나기를 5초까지 기다린 다음에 출력을 읽는다(`DoctorCommand.java:515`의 `waitFor`, `:520`의 `readAllBytes`). 출력이 파이프 버퍼를 넘으면 git이 쓰다가 막혀서 5초 상한에 걸린다. 에이전트가 재니 커밋 밖 파일 50개는 0.32초에 `커밋 밖 50개`였고, 3,000개(git 출력 218KB)는 5.09초 뒤 `커밋 밖 (못 쟀다)`였다. 설명서 3.8의 30번은 출력을 따로 도는 읽기로 받으라고 적었다.

## 5. 14장 update_doc이 없다 - 범위

13장과 15장은 지었는데 14장만 비었고, 부르면 `WL-409 이 판에는 update_doc이 없다 (종료 코드 3)`다(`EngineExecutor.java:83`). `create_doc`의 경고 5가지 중 3가지가 `update_doc`으로 고치라고 안내하는데 그 명령이 없다. 앱의 본문 자동저장이 보내는 `update-doc`도 14장 명령이라서, 이 판의 serve 모드에 앱을 붙이면 저장이 안 된다.

## 7. 쓰기마다 vault를 2번 훑는다 - 낮음

`create_doc`과 15장 명령이 쓰기 1번에 같은 훑기를 2번 한다(`CreateDoc.java:85`, `MetaWriter.java:187`). 실제 vault 크기에서 훑기 1번이 약 0.45초라서, 앱이 쓰는 serve 모드에서는 쓰기마다 그만큼을 더 쓴다. serve 모드 시간은 재지 않았다.

## 8. 그 밖의 낮음

`wl-cli`와 serve 모드의 작은 결함(`sweep`, 못 읽는 plist, `launchctl` 실패, `uid` 읽기, 종료 갈고리, `--list`)과, 시험용 속성과 규칙 사본 같은 코드 손질거리다. 6번부터 8번의 상세와 코드 자리, 이 노트의 결함을 다시 확인하는 명령은 하위 노트 「낮음 결함 상세와 다시 확인하는 법」에 있다.

## 설명서에서 고칠 곳

새 구현과 따로, 설명서에서 고칠 곳이다.

1. 3.2와 3.3의 소켓 경로 상한 「103바이트를 넘으면」이 1바이트 넘친다. 이 기기의 JDK 21은 102바이트까지만 소켓을 연다. 그래서 정확히 103바이트면 지금 엔진과 새 구현의 serve 모드가 모두 `bind`에서 `Unix domain path too long`으로 종료 코드 1이고, `wl-cli`는 길이 문구 대신 jar가 없다거나 엔진이 준비되지 않았다는 엉뚱한 문구를 낸다(`wl-cli`는 새 구현으로 재고 지금 엔진은 코드로 맞댔다). 상한을 102로 고친다.
2. 13.4의 9번과 15.4의 3번은 「색인 맞추기 실패」를 종료 코드 3으로 적었는데, 실측은 지금 엔진과 새 구현 모두 6.6의 예상 밖 실패인 1이다(위 1번). 8.7의 4번은 같은 실패를 「6.6의 예상 밖 실패 모양」이라고 적어서 설명서 안에서도 어긋난다. 13.4와 15.4의 표에 「예상 밖 실패면 1」을 더한다.
3. 8.6 「남는 차이」 표에 `create_doc` 줄이 없다. `reindex` 뒤 아젠다 파일을 손으로 지우고 그 아젠다로 노트를 만들면, 지금 엔진은 옛 색인 행을 믿고 `agendaCreated: false`로 노트만 쓴다(13.9의 4번). 색인 없는 구현은 아젠다 파일을 다시 만들고 `agendaCreated: true`다.
4. 8.6 표의 마지막 줄은 맞추기가 선 vault의 읽기 규칙인데 쓰기에도 걸리는 것처럼 읽힌다. 새 구현의 15장 쓰기가 그 규칙대로 움직여서 위 1번이 났다. 「쓰기 명령은 이 경우에도 색인 맞추기 실패로 답한다」 한 줄을 붙인다.
