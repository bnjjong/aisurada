## 수정할 문제

### 1. 성공 응답의 중첩 추가 필드 격리

`cloneReindexResponse`는 현재 루트 및 항목을 얕게 복사합니다. validator가 허용하는 JSON 추가 필드의 중첩 객체·배열이 클라이언트 원본, 코디네이터 내부 상태, 스냅숏 사이에 공유됩니다.

- 응답 루트와 `skipped`·`conflicts` 항목의 중첩 추가 필드를 빠짐없이 보존하면서 독립 복제해 주세요. 기존 필수 필드, 배열 순서와 값을 바꾸지 마세요.
- 원본 응답과 그 중첩 객체를 변경하거나 동결하지 마세요. 원본을 사후 변경해도 내부 상태가 바뀌지 않고, 스냅숏 변경 시도 역시 원본·내부 상태·다른 스냅숏에 영향을 주지 않아야 합니다.
- full 결과를 기록한 뒤 paths 결과에서 노출되는 `unverifiedPriorHealth`의 추가 필드도 격리를 검증해 주세요.

### 2. 실패 정보의 중첩 소유권 격리

`cloneRefreshFailure`는 `coordinator_error.cause`를 공유하고 다른 실패의 detail 등도 얕게 복사합니다.

- 실패를 내부에 보관할 때와 외부에 제공할 때 소유권을 분리해 원본, 내부 상태, 서로 다른 스냅숏 사이로 변경이 전파되지 않도록 해 주세요. 원래 실패의 종류·메시지·의미 있는 상세를 보존해야 합니다.
- `Error`의 name, message, stack, cause와 사용자 정의 속성, `Uint8Array`를 포함한 지원 값의 복제 정책을 명시해 주세요. JSON 직렬화로 예외와 바이트를 손실하지 마세요.
- `cause: unknown`은 임의 호스트 객체까지 무조건 복제 가능하다고 가정하지 말고, 순환 참조 및 지원하지 않는 값의 처리 정책을 정의하고 테스트해 주세요. 정보 손실이나 참조 공유를 조용히 감추지 말고, 정상적인 엔진 응답 처리에 불필요한 실패를 만들지 않도록 설계해 주세요.
- nonempty `Uint8Array`에는 `Object.freeze`를 호출하지 말고 독립 버퍼를 사용해 주세요. 엔진 종료 코드나 WL 코드를 새로 만들지 마세요.

### 3. 구독자별 스냅숏 격리

`notifySubscribers`가 한 스냅숏을 모든 리스너에게 공유해 첫 리스너가 실패 바이트를 바꾸면 다음 리스너도 변경된 값을 받습니다.

- 각 구독자의 변경 가능한 바이트와 실패 원인 등이 서로 및 내부 상태와 독립적이어야 합니다. 특정 vault 구독자와 전역 구독자를 모두 검증해 주세요.
- 리스너가 통지 도중 코디네이터를 다시 호출하더라도 같은 통지의 수신자들이 동일한 사건의 상태를 보도록 설계해 주세요. 단순히 각 리스너 직전에 변화한 내부 상태를 다시 읽는 방식은 이 조건을 확인해야 합니다.
- 구독자 예외 격리, 구독 해제, dispose 및 기존 알림 동작을 유지해 주세요.

## 회귀 검증

다음 상황을 실제 공개 API를 통해 검증해 주세요.

1. 성공 응답 루트와 항목의 중첩 객체·배열: 원본을 변경한 뒤의 내부 스냅숏, 스냅숏의 변경 시도 후 원본과 다른 스냅숏을 각각 확인.
2. full 이후 paths 응답의 이전 건강 정보도 중첩 추가 키를 보존하고 격리하는지 확인.
3. `getClient`의 중첩 객체 예외, `Error`의 상세와 원인, 계약 위반 detail, 지원 정책의 순환/특수 값이 보존되고 격리되는지 확인.
4. 첫 구독자가 `raw.stderr` 등 바이트를 수정해도 두 번째 구독자와 이후 `getSnapshot`이 원래 값을 받는지 확인. 변경 가능한 cause도 같은 방식으로 검증.
5. 통지 중 재진입, 기존 오래된 예약 콜백, 실패 후 자동 재시도 방지, 실행 중 새 요청, vault 분리 및 dispose 회귀를 확인.

기존 테스트를 약화하거나 지우지 말고 `npm test`와 `npm run build`를 실행해 주세요. mock 기반 검증과 실제 엔진 검증을 구분해 보고해 주세요.
