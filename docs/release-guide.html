Java 런타임 동봉

“Java를 설치해 주세요”를 없애는 작업

순서 01
런타임 준비 스크립트배포용 리소스 설정라이선스 파일
완료 기준: Java 없는 Mac에서 엔진이 실행됨
세부 작업 · 수정할 파일

구현할 일

  • 재배포 가능한 Java 21 ARM64 배포판을 선택하고 버전·다운로드 URL·SHA-256을 고정합니다. 라이선스와 고지 파일도 함께 보관합니다.
  • macOS 런타임의 실제 Java 홈을 runtime/ 아래로 배치합니다. 실행 권한·라이브러리를 보존합니다. 첫 배포의 런타임 축소는 필수로 잡지 않습니다.
  • 런타임은 native-host/.release/runtime/ 같은 별도 작업 폴더에 준비합니다. 루트 build.sh가 dist/를 지우므로 그 안에 미리 준비하지 않습니다.
  • 배포용 Tauri 설정에 런타임 리소스를 추가하고, 준비 → 앱 빌드 순서를 하나의 명령으로 연결합니다.
  • 앱 내부 Java → CLI → launchd 엔진의 경로를 추적합니다. 개발용 환경변수나 시스템 Java에 의존하지 않는지 확인합니다.
  • 앱이 없어진 임시 경로나 DMG 마운트 경로를 엔진 실행 경로로 남기지 않도록 Applications 설치 후 점검합니다.

예상 변경 파일 · 제안 경로

native-host/scripts/prepare-runtime.mjs
native-host/scripts/release-build.mjs
native-host/src-tauri/tauri.release.conf.json
native-host/package.json · .gitignore

필요하면 src-tauri/src/sidecar.rs와 src/aisurada/cli/PlistGenerator.java의 경로 연결을 수정합니다. 현재 앱 내부 Java 우선 탐색 로직은 활용합니다.

확인할 증거

설치된 앱의 런타임 파일 목록·버전, 실제 실행 중인 Java 경로, 시스템 Java 없는 환경에서의 노트 조회·저장 결과.

시험 배포와 일반 공개를 나누어 준비

소수 대상 첫 시험판

  • ad-hoc 서명을 적용하고, Java 실행 파일·동봉 라이브러리를 포함한 중첩 코드의 서명 결과를 확인합니다.
  • 최종 앱을 담은 DMG를 생성합니다. 런타임 포함을 끝낸 뒤 서명하고, 이후 앱 내부 파일을 변경하지 않습니다.
  • codesign 검증 결과를 기록하고, 실제 다운로드 후 보안 경고와 허용 절차를 설치 안내에 적습니다.

일반 사용자 대상 공개

  • Apple Developer 계정과 Developer ID Application 인증서를 준비합니다. 인증서 준비는 Java 동봉 작업과 독립적으로 시작할 수 있습니다.
  • Java의 실행 방식에 필요한 entitlements와 hardened runtime 구성을 실제 선택한 배포판에 맞춰 검증합니다.
  • Developer ID 서명 → Apple 공증 제출 → 성공 확인·stapling → 최종 앱·DMG 검증 순서로 연결합니다.
  • 인증서·암호·공증 자격 정보는 GitHub Secrets에서 전달하고 로그나 저장소에 남기지 않습니다.

통과 기준

시험판은 ad-hoc 서명과 첫 실행 절차를 확인합니다. 일반 공개판은 Developer ID 서명·공증·Gatekeeper 평가까지 통과해야 합니다. ad-hoc 서명은 경고 제거를 보장하지 않습니다.

테스트 환경

  • 우선 Apple Silicon Mac. JDK/JRE·소스 코드·개발용 AISURADA_* 변수가 없는 별도 Mac 또는 VM을 우선 사용합니다.
  • 다른 사용자 계정만 사용하는 경우 시스템 전체에 Java·Git이 남아 있는지 별도로 확인합니다.
  • macOS 최소 지원 버전은 Tauri와 선택한 Java 런타임 조건을 확인해 확정합니다.

실제 사용자 순서로 확인

  1. 접근 가능한 GitHub Release 초안 또는 시험판에서 DMG 다운로드
  2. DMG 열기 → Applications로 앱 복사 → DMG 추출
  3. 터미널 환경변수 없이 Finder에서 앱 실행
  4. 한글·공백 경로의 새 워크스페이스 생성, 노트 작성·수정·저장
  5. 앱·엔진 종료 후 다시 실행해 저장 내용 확인
  6. 새 버전으로 앱 교체 후 기존 워크스페이스 열기
  7. Git·Claude 미설치 상태의 기능 범위·오류 안내 확인

배포 전 정할 의존성 방침

Git이 없을 때 기본 노트 작업까지 막히는지 조사합니다. 필요한 기능에 맞춰 Git 동봉·기능 제한·설치 전제 중 방침을 정합니다. 이 점을 해결하기 전 “아무것도 추가 설치하지 않아도 모든 기능 사용 가능”으로 안내하지 않습니다.

01 · DIRECTION

첫 목표는 작고 명확하게

Apple Silicon Mac용 설치 파일 하나를 만들어, 다른 Mac에서 실행되는지 확인합니다.

권장 첫 배포 범위

Java 런타임을 포함한 macOS용 DMG를 만들고, 설치를 확인한 뒤 GitHub Releases에 시험판으로 공개합니다. 사용자가 Java를 따로 설치하는 과정은 기본 배포 흐름에서 제외합니다.

사용자에게 보여 줄 설치 과정은 다음과 같습니다.

  1. GitHub의 Releases에서 자신의 Mac에 맞는 .dmg 파일 다운로드
  2. DMG를 열고 aisurada.app을 Applications 폴더로 이동
  3. 앱 실행 → 워크스페이스 생성 또는 열기 → 노트 사용

첫 단계에서는 앱스토어 등록, Windows·Linux 동시 지원, 자동 업데이트까지 묶지 않습니다. 앱을 만들고 설치하고 확인하는 흐름을 먼저 완성합니다. Claude 기능의 별도 준비 사항과 macOS 보안 안내는 설치 설명에 함께 적습니다.

왜 macOS부터 시작하나요?

현재 Java CLI는 엔진을 띄울 때 macOS의 launchd / launchctl을 사용합니다. Tauri가 여러 운영체제를 지원하더라도, 이 앱의 실행 구조까지 자동으로 다른 운영체제에 맞춰지는 것은 아닙니다. Windows·Linux는 별도 이식·검증 작업으로 다룹니다.

배포 준비 때 확인할 주요 파일

  • native-host/src-tauri/tauri.conf.json — 앱 정보·빌드 명령·포함 리소스
  • native-host/src-tauri/src/sidecar.rs — 앱 내부 Java·JAR 경로 탐색
  • build.sh — Java 엔진 빌드
  • native-host/README.md — 개발 빌드·검증 명령

위 파일 링크는 저장소 폴더 안에서 문서를 열 때 사용할 수 있습니다. HTML만 따로 복사하면 상대 경로의 파일은 함께 제공되지 않습니다.

04 · JAVA RUNTIME

Java는 앱 안에 넣어서 배포합니다

사용자에게 Java 설치·버전 선택·환경변수 설정을 맡기지 않는 것을 기본 요건으로 잡습니다.

JAR는 Java 프로그램이고, Java 런타임은 그 프로그램을 실행하는 환경입니다. JAR를 앱에 넣는 것만으로 Java 설치 문제가 해결되지는 않습니다. 기본 개발 빌드는 시스템 Java를 사용할 수 있습니다. 0.0.1 시험 배포는 별도 배포 설정으로 내부 런타임을 포함합니다.

Java 배포 방식 비교
방식사용자 경험판단
Java 별도 설치앱 외에 Java 설치·버전·경로를 준비개발자끼리 임시 공유할 때만 고려
앱에 런타임 포함앱 설치 후 실행, 시스템 Java와 분리사용자용 배포의 기본 방향
목표 번들 구조 · macOS 예시
aisurada.app/
└── Contents/
    ├── MacOS/                 # Tauri 실행 파일
    └── Resources/
        ├── ais-cli.jar
        ├── ais-sidecar.jar
        └── runtime/           # 앱 전용 Java 실행 환경
            ├── bin/java
            └── …

재배포 가능한 Java 21 런타임 배포판을 정하고, 라이선스·고지 파일과 함께 앱에 포함합니다. 필요하면 사용하는 Java 모듈을 분석해 런타임 크기를 줄이는 작업을 후속으로 진행할 수 있습니다. 첫 배포에서는 실제 엔진이 정상 실행되는 구성이 우선입니다.

  • 런타임 준비를 매번 수작업으로 하지 않도록 버전과 다운로드 파일·체크섬을 고정합니다.
  • Apple Silicon용 앱에는 ARM64 런타임, Intel용 앱에는 x64 런타임을 포함합니다.
  • 실행 권한과 내부 라이브러리를 유지하고, Java 엔진·백그라운드 프로세스가 모두 포함된 런타임을 쓰는지 확인합니다.
  • 런타임은 최종 서명·공증 전에 넣습니다. 동봉된 Java 실행 파일과 네이티브 라이브러리까지 서명 결과를 확인합니다.
  • 새 런타임 파일만 넣는 데서 끝내지 않고, Tauri 리소스 매핑과 배포 스크립트까지 연결합니다.
Java 포함과 외부 의존성 제거는 별개입니다.

엔진의 Git 기능은 외부 git 명령을 호출하고, Claude 기능은 별도 Claude CLI와 인증 상태에 의존합니다. Git이 없는 Mac에서 어떤 기능이 가능한지 확인하고, 포함 여부·필수 조건·기능 제한 중 방침을 정해야 합니다. Claude 준비 사항은 선택 기능 안내로 구분합니다.

앱 용량이 늘고 런타임 보안 업데이트도 앱 배포에 반영해야 하지만, 사용자는 Java를 따로 관리하지 않아도 됩니다.

05 · FIRST RELEASE

첫 배포는 수동으로 한 번 완주합니다

성공한 절차를 확인한 뒤 자동화하면 문제의 위치를 파악하기 쉽습니다.

  1. 지원 대상을 정합니다.

    첫 시험판은 Apple Silicon Mac용으로 시작합니다. 지원할 최소 macOS 버전은 Tauri와 동봉 런타임의 조건을 함께 확인한 뒤 정하고, 실제 검증한 범위를 설치 안내에 적습니다.

  2. Java 런타임 포함과 외부 의존성 방침을 준비합니다.

    04절의 구성을 실제 빌드에 반영합니다. 사용자용 배포는 pnpm release:build로 배포 설정을 적용합니다.

  3. 버전과 배포할 소스를 확정하고 테스트합니다.

    검증할 변경을 커밋하고 앱 버전을 맞춥니다. 기존 엔진·호스트 검사를 실행하고, 최종 설치 파일로 주요 기능을 추가 확인합니다.

  4. 배포용 앱과 DMG를 생성합니다.

    시험 배포용 서명 또는 Developer ID 서명을 설정한 뒤 release 빌드를 사용합니다. 아래 명령은 기존 빌드 진입점입니다.

저장소 루트에서 · 기존 검사
bash test.sh
bash test-native.sh
저장소 루트에서 · macOS 빌드
cd native-host
pnpm install --frozen-lockfile
pnpm tauri build --bundles app,dmg

빌드하는 Mac에는 Rust/Cargo, Xcode 도구, Node.js 22.12 이상, pnpm 10.33.4, JDK 21 빌드 환경이 필요합니다. 일반 사용자에게 이 개발 도구를 설치시키지는 않습니다. 위 빌드 명령만으로 런타임 동봉·서명 설정이 자동 완성되지는 않습니다.

현재 beforeBuildCommand는 화면 빌드와 Java JAR 빌드를 실행합니다. 기본 출력 경로는 아래와 같으며, 명시적인 --target을 사용하면 target 이름이 경로에 추가됩니다.

기본 산출물 위치
native-host/src-tauri/target/release/bundle/
├── macos/aisurada.app
└── dmg/… .dmg
  1. 깨끗한 환경에서 실제로 설치합니다.

    다른 Mac이나 테스트 계정에서 Java·개발 소스·개발용 환경변수에 의존하지 않는지 확인합니다. 가능하면 GitHub 초안에서 DMG를 받아 Applications로 옮기고 Finder로 실행합니다. 빌드 폴더 안의 앱을 실행하는 것만으로 설치 검증을 대신하지 않습니다.

  2. 노트와 엔진이 함께 동작하는지 확인합니다.

    새 워크스페이스 생성 → 노트 작성·수정 → 앱 종료 → 재실행 → 저장 내용 확인을 수행합니다. 앱 업데이트 후 기존 워크스페이스가 열리는지, Claude가 없는 환경의 안내가 적절한지도 확인합니다.

  3. GitHub Release를 준비합니다.

    저장소 Releases에서 배포할 커밋의 태그를 선택하거나 생성합니다. 예: 태그 v0.1.0, 제목 aisurada 0.1.0 — 초기 시험판. Pre-release를 체크하고 검토 중에는 Draft로 보관합니다.

  4. 파일과 안내를 확인하고 공개합니다.

    DMG, 지원 환경, 설치 방법, 서명 상태, 변경 내용, 알려진 문제를 함께 제공합니다. 공개 후에도 실제 다운로드 링크에서 받은 파일이 같은 산출물인지 확인합니다. 비공개 저장소의 릴리스는 저장소 읽기 권한이 있는 사람만 접근할 수 있습니다.

첫 배포 완료의 기준

다른 사용자가 GitHub에서 설치 파일을 내려받아, Java를 별도로 설치하지 않고 앱을 열고 노트를 작성·저장·다시 열 수 있어야 합니다.

06 · MACOS SIGNING

서명과 공증은 언제 필요한가요?

앱을 만든 사람을 확인하고, 인터넷에서 내려받은 앱을 macOS가 검사하도록 하는 절차입니다.

시험 배포와 일반 사용자 배포
구분준비설치 경험
소수 대상 시험 배포ad-hoc 서명 + 제한 사항 명시보안 경고나 개인정보 보호 및 보안 설정에서 실행 허용이 필요할 수 있음
일반 사용자 대상 공개Apple Developer 계정, Developer ID Application 인증서, Apple 공증검증된 배포자로 제공하며 첫 실행 안내는 시스템 정책에 따름

ad-hoc 서명은 개발자 신원을 Apple이 확인한 서명이 아닙니다. Apple Silicon용 인터넷 배포에서 서명 부재로 앱이 손상된 것으로 취급되는 문제를 줄이는 데 쓰지만, 보안 경고를 없애 주지는 않습니다. Tauri에서는 bundle.macOS.signingIdentity에 "-"를 지정하는 방법을 안내합니다. 일반 배포는 Developer ID 서명과 공증을 함께 준비합니다. Tauri macOS 서명·공증 공식 가이드

앱 내부 파일을 바꾸면 서명 검증에 영향을 주므로 런타임 포함 → 서명·공증 → DMG 최종 확인 순서로 진행합니다. 인증서와 공증 자격 정보는 저장소에 커밋하지 않고, 자동화 시 GitHub Actions의 Secrets 등으로 전달합니다.

07 · AUTOMATION

수동 성공 뒤, 같은 과정을 자동화합니다

태그를 올리면 빌드하고 Release 초안까지 준비하는 정도로 시작합니다.

권장 자동화 흐름 · 구현 예정
v0.1.1 태그 push
  → 소스 checkout / 고정된 개발 도구 설치
  → 앱 버전과 태그 일치 확인
  → 테스트
  → 아키텍처에 맞는 Java 런타임 준비
  → 앱·DMG 빌드 / 서명·공증
  → GitHub Release 초안에 DMG 첨부
  → 사람이 다운로드·설치 확인
  → 시험판 공개

Tauri의 공식 tauri-action은 앱 빌드와 릴리스 파일 업로드에 사용할 수 있습니다. 이 저장소는 앱이 하위 폴더에 있어 projectPath: native-host가 필요하고, Java 빌드 도구 및 런타임 준비 단계는 추가해야 합니다. Tauri GitHub Actions 가이드

  • 워크플로 파일 위치 예: .github/workflows/release.yml
  • 초기 트리거: 수동 실행 또는 v* 버전 태그 push
  • 초기 산출물: Apple Silicon Mac용 DMG와 Release 초안
  • 빌드 프로젝트 경로: native-host
  • 런타임·pnpm·의존성 버전 고정, 체크섬 및 lockfile 사용
  • 릴리스 생성에 필요한 contents: write 권한 설정
  • 최종 공개는 설치 확인 후 수행

Intel Mac용을 추가할 때는 앱과 Java 런타임의 아키텍처를 함께 맞추고 별도로 검증합니다. Rust target을 바꾸는 것만으로 동봉 Java까지 변환되지는 않습니다.

앱 파일과 사용자 데이터는 따로 관리합니다

앱 교체가 사용자의 노트 저장소를 덮어쓰지 않도록 해야 합니다. 새 버전이 기존 워크스페이스를 열고, 저장 형식 변경이 있다면 이관 과정을 수행하는지 확인합니다. 데이터 형식이 바뀐 경우 이전 앱으로 교체하는 것만으로 복구된다고 안내하지 않습니다. 백업은 notes/뿐 아니라 숨김 폴더 .aisurada/와 첨부를 포함한 워크스페이스 전체를 대상으로 합니다.

자동 업데이트는 언제 붙이나요?

설치 파일 생성·서명·버전 관리·기존 데이터 호환성이 안정된 다음에 붙입니다. 업데이트 파일 서명은 macOS 개발자 서명과 별도의 검증 체계이므로, 초기 배포 작업과 구분해 설계합니다.

문제가 있는 버전을 공개했다면?

릴리스 설명에 알려진 문제를 표시하고 필요하면 해당 배포본을 비공개 처리합니다. 수정판은 새 버전·새 태그로 배포합니다. 이전 파일을 같은 이름으로 조용히 덮어쓰기보다, 어떤 버전에서 해결됐는지 추적할 수 있게 남깁니다. 데이터 변경이 있었다면 백업 기반의 복구 방법도 함께 안내합니다.
