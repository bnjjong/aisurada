# 14장 개발 계획 — 노트 수정과 충돌 복구

작성일: 2026-10-28

진행 갱신: 14-1 구현 후 독립 검토에서 발견한 요청 필드 누락·사용 예시·검증 공백을 보완했다. 18개 파일·348개 테스트와 빌드가 통과했다. 상세는 [검토 및 보완 기록](./review-chapter-14-task-01.md)을 따른다. 이하 14-1은 작성 당시 계획이다.

목표는 `update_doc` / `update-doc`의 요청과 응답을 정확히 전달하고, 실제 저장에서는 최신 본문·대상 토큰·사용자 초안을 안전하게 함께 관리하는 것이다. 14장은 **엔진이 기존 노트를 수정하는 명령**이다. 앱이 파일을 직접 고치거나 이동·색인·토큰 발급 로직을 재구현하지 않는다.

근거: [14장 명세](./spec-chapter-14-update-doc.md), [13장 인자와 경고](./spec-chapter-13-create-doc.md), [11장 노트 읽기](./spec-chapter-11-get-doc.md), [7장 쓰기 파이프라인](./spec-chapter-07-write-pipeline.md), [5장 인자](./spec-chapter-05-arguments.md), [6장 출력](./spec-chapter-06-output-and-errors.md), [8장 색인](./spec-chapter-08-index-and-freshness.md).

## 1. 현재 상태와 의존 관계

- 공통 `Transport`, `decodeResponse`, 실패 분류, `MockTransport`, warning 및 precondition 유틸리티와 7-1 쓰기 결과 정책은 있다. 8-2 코디네이터도 있다. 14장 전용 요청·응답 클라이언트는 없다.
- `get_doc` 전용 클라이언트·11장 전체 DTO, 7-2 초안/저장 상태 관리, 실제 앱 전송·에디터 연결은 아직 없다. 최근 앱 검증 기준은 17개 파일·290개 테스트 및 빌드 통과다.
- 형제 프로젝트의 재구현 엔진 JAR은 격리된 단발 **읽기** 세 호출만 시험했다. 앱에서 사용 가능한 실제 전송부나 14장 쓰기 호환성이 검증된 것은 아니다. [실제 전송 검토](./review-next-work-2026-10-28.md)와 구분한다.
- 14-1은 mock 기반의 요청·응답 계약으로 독립 진행할 수 있다. 실제 저장에는 11장 읽기, 7-2 초안 상태와 실제 전송 등 아래 선행 작업이 필요하다. 재구현 JAR과 기존 엔진은 별도 구현이므로 둘의 동작·색인 신선도가 같다고 가정하지 않는다.

## 2. 구현에서 지켜야 할 핵심 계약

| 항목 | 계약과 앱 처리 |
|---|---|
| 대상과 표면 | 도구 `update_doc`은 JSON 객체 한 칸이고 `id`, `body`, `title`, `tags`, `template`, `f1`만 받는다. 명령 `update-doc`은 id 한 자리 인자와 이름 옵션이며 `date`, `time`, `mins`도 받는다. 둘 모두 `links`는 받지 않는다. |
| 생략과 빈 값 | 준 칸만 바꾼다. `body: ''`는 본문 비우기, `tags: []`는 태그 전체 삭제다. 생략과 다르며 null도 생략이 아니다. `template`은 빈 값이나 잘못된 모양으로 지우지 못하고 기존 값을 유지한다. |
| 원문 | id·title·body·date·time·f1과 태그 문자열은 클라이언트에서 trim·정규화하지 않는다. 실제 엔진은 f1 등을 5.3에 따라 다듬어 읽는다. 앱은 이를 미리 흉내 내지 않고 보낸 원문과 엔진 동작을 구분한다. |
| 길이·검증 | 도구는 body 200,000 UTF-16 단위, tags 50개, template 200단위 상한이 있다. 명령 표면에는 이 도구 상한이 없다. 날짜·시각·정수·제목 등의 문법과 실패 우선순위는 엔진이 판단한다. 저수준 클라이언트가 문구나 WL 코드를 만들어내지 않는다. |
| 토큰 | 응답 `precondition`을 다음 요청 `f1`로 원문 전달한다. markdown/html은 토큰 누락·불일치 시 WL-412, json은 **토큰 없이 메타 수정 가능**하며 토큰을 줬으면 비교한다. json에 body가 있으면 빈 문자열도 WL-500이며 토큰 비교보다 먼저다. 토큰 부재를 빈 본문 저장의 근거로 삼지 않는다. |
| 수정 결과 | 성공에 `id`, `path`, `precondition`, `renamed`가 필수이고 `warning`은 선택 문자열이다. `path`는 새 자리이며 폴더 경로 또는 단일 파일 경로다. `renamed`는 경로 글자 비교 결과이지 콘텐츠 변경 여부가 아니다. |
| 쓰기와 이동 | 값이 같거나 id와 토큰만 준 호출도 쓰기와 정식 경로 이동이 일어날 수 있다. 폴더는 통째로 이동하며 옛 md/json·html 단일 파일은 각기 다른 절차를 거친다. 저장 상한이 폴더 이동 뒤에 걸릴 수 있으므로 WL-500을 전체 롤백으로 취급하지 않는다. |
| 신선도 | 응답 토큰은 방금 쓴 파일의 토큰이다. 후속 색인 실패에도 성공할 수 있으므로 목록/경로 메타가 즉시 최신이라고 보장하지 않는다. 읽기 응답의 메타는 색인, 본문·토큰은 파일에서 올 수 있어 같은 판이라고 자동 가정하지 않는다. |
| 경고 | 오래된 파일 삭제 실패, 들여쓴 블록, 제목/헤딩 불일치, U+FFFD 증가의 순서로 한 문자열에 합쳐진다. 원문과 LF를 보존한다. 성공과 경고를 함께 표시하고 문구 파싱만으로 자동 삭제·수정하지 않는다. |

## 3. 14-1 — 응답 계약과 요청 클라이언트

바로 다음 독립 개발 단위. 권장 파일은 `src/engine/commands/updateDoc.ts`, `src/engine/__fixtures__/chapter14/`, 관련 테스트, `src/engine/index.ts`, README 및 사용 예시 검증이다. 실제 파일 쓰기·UI·저장 상태 관리·네이티브 전송은 포함하지 않는다.

### 3.1 응답 DTO와 validator

```typescript
interface UpdateDocResponse {
  readonly id: string;
  readonly path: string;
  readonly precondition: string;
  readonly renamed: boolean;
  readonly warning?: string;
  readonly [extraKey: string]: unknown;
}
```

- 객체 여부와 네 필수 필드의 타입을 검사하고, warning이 **있으면** 문자열인지 검사한다. 누락, null, 잘못된 타입은 `decodeResponse`의 `schema_mismatch`다. `withOptionalWarning` 재사용을 검토하되 14장에서는 `precondition`이 필수이므로 기존 선택적 precondition validator만으로 끝내지 않는다.
- id·path·토큰 및 warning의 형식을 추측해 수정하지 않고 추가 키를 보존한다. 조건부 warning을 null/빈 글로 채우지 않는다. JSON의 키 순서와 들여쓰기는 실제 응답 validator에서 강제하지 않는다.
- `decodeResponse`와 `determineWriteOutcome`를 재사용할 수 있게 검증된 결과를 반환한다. 성공 stderr와 warning은 서로 다른 정보다. 계약 위반이어도 쓰기가 이미 반영됐을 수 있으므로 결과 정책을 통과시키고 자동 재전송하지 않는다.

### 3.2 표면별 요청

권장 API 형태(정확한 이름은 구현 시 조정 가능):

```typescript
client.updateDocTool({ id, body: '', tags: [], f1: token })
// execute({ command: 'update_doc', args: [JSON.stringify({ id, body: '', tags: [], f1: token })] })

client.updateDocCommand({ id, title: '새 제목', date: '2026-06-17', mins: '0', f1: token })
// execute({ command: 'update-doc', args: [id, 'title=새 제목', 'date=2026-06-17', 'mins=0', `f1=${token}`] })
```

- 도구와 명령의 옵션 타입을 분리하고 명령의 `tags`는 JSON 배열 문자열 한 칸 `tags=${JSON.stringify(tags)}`로 보낸다. `body=`, `tags=[]`, `mins=`, `f1=`와 미지정의 차이를 유지한다. 명령 `mins`는 5.3의 정수 문법과 빈 값을 유지하도록 문자열로 받는 것을 권장한다.
- 속성이 `undefined`이면 생략하고 빈 문자열·빈 배열은 포함한다. null 및 미지원 키를 조용히 생략·변환하지 않는다. 정적 타입을 우회한 런타임 값의 정책을 명시하고, 엔진의 잘못된 JSON·null·모르는 키 테스트는 `Transport.execute`를 직접 사용한다. 로컬 구조 오류는 엔진 WL 오류가 아니다.
- `f1`은 응답에서 요청으로 전송할 때 선택적이며 문자열 그대로 둔다. 기존 `combinePrecondition`을 재사용하는 경우 중복 `f1` 및 `precondition` 키를 조용히 덮어쓰지 않는다. 범위가 붙은 토큰은 대상 vault·노트와 대조해야 하며, 클라이언트가 vault 정보를 받지 못하는 경우 검증한 것처럼 주장하지 않는다. 실제 앱에서 대상 문맥 대조는 14-3의 책임이다.
- 명령 표면의 id는 자리 인자다. 5.2에 따라 `--`로 시작하는 값은 설정 칸이 되고 첫 글자 뒤의 `=`는 옵션으로 해석되므로, 저수준 클라이언트는 이런 id를 다른 값으로 바꾸거나 설정 인자로 실행하지 않는다. 안전한 타입의 로컬 오류로 거절하고, 잘못된 원시 argv의 엔진 동작 검증은 명시적인 `Transport.execute` 호출에서 다룬다. NUL·플랫폼 인자 제한도 실제 전송부에서 별도 처리한다.
- 필드를 몰래 다른 표면으로 보내거나 14.3의 길이 상한을 명령 표면에 확대하지 않는다. 엔진 검증 순서를 클라이언트에서 재현하려 하지 않는다.

### 3.3 fixture와 완료 기준

- 14.6의 두 성공 응답(본문 수정, 제목 수정·warning)을 명세 예시 fixture로 작성한다. 2칸 들여쓰기·키 순서·UTF-8·끝 LF를 **독립 기대 바이트**와 비교한다. 이 예시는 코드 읽기와 명세 규칙으로 만든 예시이며 공식 수용 묶음에서 측정한 출력이 아니다. 나머지 경계 응답은 합성 fixture로 표시한다.
- 양 표면에서 id만, 빈 body, tags 생략/빈 배열/쉼표·한글·따옴표 포함 배열, template, f1 공백, 명령의 date/time/mins, 등호·줄바꿈·특수문자 원문을 전달하는지 확인한다. 도구에서 date/time/mins/links가 노출되지 않고 위험한 자리 id의 로컬 처리도 검증한다.
- 필수 키 각각 누락·null·타입 오류, 선택 warning 타입과 줄바꿈, 추가 키, 손상 JSON·빈 stdout·성공 stderr, 3/400·3/404·3/409·3/500·5/412·미분류 실패·전송 실패 및 계약 위반을 검증한다. 결과 정책이 오류 원본과 초안 보존/재확인 판단을 유지하는지 확인한다.
- 기존 전체 테스트와 신규 테스트, `npm test`, `npm run build` 통과. 이 단계의 mock 호출은 실제 쓰기·경고 생성·이동·원자적 쓰기·공식 수용 묶음을 검증한 것이 아니다.

## 4. 14-2 — 11장 노트 읽기와 저장 기준 판

1. 11장에 따라 `get_doc` / `get-doc`의 요청과 전체 응답을 별도 계획·구현한다. 목록이나 특정 필드만 흉내 낸 DTO를 11장 전체 계약 완료로 표시하지 않는다. 읽기 층, 기록 층, comments·본문·format·선택 필드와 diagnostics를 검증한다.
2. vault와 노트 id, 읽은 본문·메타·format·precondition을 같은 대상의 기준 판으로 보관한다. 메타는 색인, 본문과 토큰은 파일에서 온다는 차이를 기록한다. 경로는 응답의 값을 사용하고 임의로 새 경로를 계산하지 않는다.
3. markdown/html의 읽기 응답에서 토큰이 없으면 파일 읽기 실패 등일 수 있다. 빈 본문과 토큰 부재로 빈 파일을 덮거나 새 노트를 자동 생성하지 않는다. json은 원래 읽기 토큰이 없고 메타 수정만 가능한 별도 경로로 다룬다.
4. 도구 표면의 `get_doc`은 기록 층을 거절하지만 쓰기는 막지 않는다. 기록 층의 안전한 실제 읽기·쓰기 경로는 명령 표면으로 별도 확인한다. 도구의 WL-409를 대상 부재로 바꾸지 않는다.

완료 기준: 필요한 11장 계약 테스트 및 대상·vault 분리, 읽기 실패와 json 예외를 확인한다. 실제 쓰기는 아직 연결하지 않는다.

## 5. 14-3 — 초안과 저장 상태(7-2)

- 기준 본문·토큰, 현재 초안, 실제 요청에 보낸 초안 판과 진행 중 요청 id를 구분한다. 같은 vault·대상의 앱 저장은 직렬화하되 엔진에 전역 잠금이 있다고 주장하지 않는다. 14.9에 따르면 외부 동시 쓰기 두 개는 모두 토큰 대조를 지날 가능성이 있다.
- 요청 중 추가 편집이 있으면 성공은 보낸 판만 확정하고 최신 초안을 보존한다. 다른 vault·id 또는 이전 세대의 늦은 성공/실패가 현재 화면을 덮거나 토큰을 바꾸지 못하게 한다.
- WL-412는 초안을 보존하고 최신 본문과 토큰을 다시 읽어 사용자가 변경을 재적용하도록 한다. 새 토큰만 교체해 기존 본문을 자동 재전송하지 않는다. WL-500, 미분류 실패, in-flight/unknown 전송 실패 및 응답 계약 위반은 완료·이동 여부가 불확실하므로 재조회와 파일 상태 점검을 요구한다.
- json 메타 수정의 무토큰 예외는 명세대로 유지하되, 충돌 방지가 보장되지 않는다는 사실을 상태에 표현한다. json 본문 쓰기는 UI에서 제공하지 않는다. 저수준 클라이언트는 엔진 계약 시험을 위해 빈 body도 원문 전달할 수 있다.
- 성공의 새 `path`와 `precondition`은 해당 대상에만 반영하고 warning과 stderr를 유지한다. 저장 중 사용자가 바꾼 초안까지 저장됐다고 처리하지 않는다. 성공 뒤 색인 조회가 오래되거나 실패할 수 있음을 별도로 표시한다.

완료 기준: 주입 가능한 저장·읽기 함수와 deferred mock으로 저장 중 추가 편집, 응답 역전, 서로 다른 vault/id, 재조회 실패, WL-412, 부분 이동 가능 실패, 토큰 없는 json, 응답 유실을 검증한다. 실제 에디터·파일 연결은 다음 단계다.

## 6. 14-4 — 실제 전송·에디터 및 격리 vault 통합

선행 조건: 14-1~14-3과 실제 호스트 전송, 실행 대상 엔진·vault 선택, 파일 감시/색인 정책. 실제 실행 전에 임시 vault·HOME·상태 경로를 명시적으로 분리한다. 재구현 엔진과 원본 엔진의 결과를 구분하고, 자동 설치·launchctl·실사용 vault 쓰기 없이 시험한다.

1. markdown/html 읽기→토큰 포함 수정→새 경로·토큰 확인→재읽기; 빈 본문과 태그 삭제·미지정 보존; 성공 warning과 stderr 동시 전달을 확인한다.
2. `MISSING`/`MALFORMED`/`STALE`에서 대상 본문과 초안 보존, json body 거절이 토큰보다 먼저인 점, json 메타 무토큰 예외를 검증한다. 문구만으로 충돌 세부 유형을 추측하거나 새 토큰을 추출하지 않는다.
3. 폴더 이동 시 첨부·하위 노트 동반, 옛 md/json의 폴더 승격, 옛 html의 파일 경로, 충돌 접미사, 제목 불일치와 다중 경고 순서, 부분 이동 뒤 WL-500 및 색인 실패 후 성공을 격리 fixture로 검증한다. 실패 재현을 위해 OS 오류를 주입하는 방식과 실제 파일 검사 범위를 기록한다.
4. 날짜/시각 변경 시 기존 오프셋과 초 처리, 프론트매터 정규화, macOS의 대소문자·Unicode 동등 경로와 옛 html 삭제 가능성, 같은 id 충돌 및 동시 쓰기 경합을 별도 경계로 기록한다. 위험한 재현은 오직 격리된 fixture에서만 수행한다.
5. 각각 사용한 엔진 빌드·플랫폼·fixture·검증 방법과 결과를 남긴다. 14장은 공식 수용 묶음이 호출하지 않는다. 명세가 언급한 옛 차등 쓰기 축 24건이 실제로 제공·실행된 경우에만 그 결과를 별도로 보고한다.

## 7. 다음 개발 요청의 범위

**14-1의 표면별 요청·응답 타입과 validator, 클라이언트, fixture·테스트·사용 예시만 구현한다.** 11장 전체 읽기, 7-2 상태 관리, 에디터, 실제 전송과 실제 vault 쓰기는 별도다. 이번 문서는 개발 계획이며 애플리케이션 소스는 변경하지 않았다.
