### 명령

- **`list-projects`**: 표식을 안 보고 색인도 안 맞춘다. 프로젝트 파일을 읽어 id 차례로 낸다. 없으면 `[]`이다.
- **`create-project`**: 표식 → 색인 맞추기 → `title`, `hue` 칸 → 프로젝트 행 읽기 → id 발급 → slug 비켜서기 → 자동 색 → 파일 쓰기. 50단위 자르기가 서로게이트 쌍을 가르면 `WL-400 경로로 쓸 수 없는 값이다`로 서고 아무것도 안 쓴다.
- **`update-project`**: 표식 → 색인 맞추기 → id 있음, id 모양, `hue` 칸 → id로 찾기 → 준 칸만 얹어 `<slug>.md`를 통째로 다시 쓴다. 빈 `title`은 이름을 안 바꾸고, `summary`는 다듬지 않으며 빈 글을 주면 본문을 비운다.
- **`delete-project`**: 표식 → 색인 맞추기 → id 칸 → 찾기 → 방금 맞춘 아젠다 가운데 `project`가 이 slug와 글자 그대로 같은 것의 수 → 1개 이상이면 `WL-400` → `<slug>.md`를 `.withlog/trash/projects/<slug>-<id>.md`로 이름 바꾸기 1번. 응답은 `id`, `slug`, `archivedPath`다.
- 쓰기 3개의 표식 확인, 색인 맞추기, vault git 자동 커밋은 `1~20장` 보완 때 들어온 `WritePipeline`이 맡는다.

## 색인이 없는 판의 차이(8.6)

지금 엔진은 프로젝트를 색인의 프로젝트 표에만 두고 파일을 안 읽는다(2.2, 8.7의 3번). 이 판은 색인이 없어서 8.6의 표대로 파일에서 읽고, 2.2가 「다시 짓는 구현의 출발점」으로 적은 엔진 소스의 읽기 규칙을 따랐다. 그래서 21.9의 특이점 가운데 여럿이 지금 엔진과 다르게 나온다. 설명서 21.9 끝이 「정할 것」으로 남긴 자리(프로젝트를 색인 맞추기에 넣을지)와 같은 방향이다.

| 자리 | 지금 엔진 | 이 판 |
|---|---|---|
| 손으로 둔 파일, 색인을 새로 지은 vault(21.9의 1번) | 목록에 안 나오고, 색인을 잃으면 목록이 빈다 | 파일이 있으면 늘 나온다. 고치기와 지우기도 된다 |
| 목록 차례(21.9의 2번) | 이 색인 DB에서 처음 만든 차례 | id 차례. id 앞부분이 발급 밀리초라(1.4) 엔진이 발급한 id끼리는 만든 차례와 같다. 21.6의 목록 예시가 그대로 나온다. 같은 밀리초에 만든 것과 손으로 정한 id는 다를 수 있다 |
| 손으로 고친 파일의 `update-project`(21.9의 3번) | 색인 값으로 덮는다 | 파일 값을 바탕으로 준 칸만 얹는다. 모르는 키는 사라진다 |
| 색인에 없는 같은 slug의 `create-project`(21.9의 1번) | 옛 파일을 새 id로 덮는다 | 읽히는 파일이면 `-2`로 비켜선다. 2.2로 못 읽는 파일의 자리는 덮는다 |
| serve 모드의 같은 이름 `create-project` 2개(21.9의 4번) | 2번째가 파일을 덮고 행을 넣다 예상 밖 실패 | 둘 다 성공하고 같은 파일을 차례로 쓴다. 앞쪽 응답의 id는 파일에서 사라진다(20장과 같다) |
| 파일을 손으로 지운 아젠다가 가리킬 때(21.9의 6번) | 남은 아젠다 행이 지우기를 막는다 | 아젠다도 파일에서 읽어서 안 막는다 |
| 옮길 자리가 차서 선 `delete-project`(21.9의 7번) | 행만 지워져 그 프로젝트가 목록에서 영영 사라진다 | 파일이 남아 목록에도 남는다 |
| 2.2로 못 읽는 파일(100,000바이트 초과, `pj` 모양이 아닌 id, 울타리 없음 등) | 파일을 안 읽으니 상관없다 | 목록에 안 나오고 고치기와 지우기는 `WL-404`다 |
| 1.9가 블록이나 큰따옴표로 쓰는 이름(줄바꿈, 78단위 초과, 탭 같은 글자) | 색인 값이라 그대로 | 다음 읽기부터 2.1 줄 읽개로 읽혀 `>-`, `|-`나 역슬래시 빠진 글이 된다. 아젠다의 20.9의 2번과 같은 원인이다 |
| `summary`의 앞뒤 공백 | 색인에 그대로 | 닫는 울타리 줄의 줄바꿈 1개만 떼고 그대로 읽어서 같은 글이 나온다 |

마지막 2줄은 설명서가 정하지 않은 자리라 짐작으로 정했다. 본문을 다듬지 않은 것은 지금 엔진의 목록과 `update-project`가 받은 `summary`를 바이트 그대로 지키기 때문이다.

- 옮기기 갈래: 옮길 자리가 참, 휴지통 폴더를 못 만듦, 파일 이름과 slug가 다른 파일, 심볼릭 링크, 폴더
- 2.2 읽기 규칙: 손으로 둔 파일, 빈 이름, 모르는 색, 틀린 id, 울타리 없음, 틀린 slug, BOM과 CRLF, 깨진 UTF-8, `.MD`, 하위 폴더, 100,000바이트 경계, 같은 id와 같은 slug의 파일 2개, `.withlog/projects`가 일반 파일, 아젠다 맞추기가 서는 vault

받아들임 묶음은 이 명령 4개를 부르지 않아서(21.9), 이 시험은 모두 설명서 값과 맞댄 것이다. 지금 엔진(Kotlin 사이드카)과 맞대지는 않았다.

## 그대로 둔 것과 정할 것

- 21.9의 특이점 8가지는 부록 D에서 모두 「정하지 않음」이다. 5번(`WL-400`)과 8번(서로게이트 자르기)은 지금 엔진처럼 냈고, 색인에 기대는 1, 2, 3, 4, 6, 7번은 위 표처럼 디스크를 따른다.
- 설명서 21.9 끝의 「정할 것」(프로젝트를 색인 맞추기에 넣을지)과 20.9의 「2번의 읽기를 1.8의 YAML 읽기로 바꿀지」는 의뢰자 몫이다. 이 판은 파일을 읽을 수밖에 없어서, 긴 이름이 `>-`로 읽히는 위 표의 자리가 실제로 드러난다. 프로젝트 파일만 YAML로 읽을지 정하면 그 자리가 없어진다.
- 붙여 준 글을 설명서로 바로잡을지, 설명서 21장 원문으로 `docs/engine-manual/21-projects.md`를 바꿀지는 의뢰자가 정한다.

기록은 개발 폴더의 `spec-gaps-16차.md`에 있다.
