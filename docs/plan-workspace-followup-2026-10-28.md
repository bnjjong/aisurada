# 워크스페이스 검토와 후속 개발 계획

검토일: 2026-10-28. 범위: 현재 앱 소스, 6·7·8·12장 계획 및 검토 기록. 이 문서는 전체 명세 구현의 완전한 감사가 아니라 다음 작업을 정하기 위한 현황 점검이다.

진행 갱신: 8-2 스냅숏 격리 보완과 7-1 쓰기 결과 보완을 구현했다. 최신 검증은 17개 파일·290개 테스트와 빌드 통과다. 상세는 [8-2 보완 결과](./review-chapter-08-task-02-isolation-fix.md)와 [7-1 보완 결과](./review-chapter-07-task-01-outcome-fix.md)를 따른다. 다음은 실제 실행 환경을 확인한 뒤 전송 경로를 구체화하는 작업이다. 이하 현황과 우선순위는 작성 당시 기록이다.

## 현재 확인한 상태

- `src/engine`에는 공통 전송 인터페이스와 응답 디코더, 회고 클라이언트, 쓰기 토큰과 결과 정책, reindex 클라이언트·코디네이터, 태그 목록 클라이언트가 있다. 12-1의 추가 검증도 반영됐다.
- 8-2는 예약 콜백 무효화를 고쳤지만 아래 참조 격리 문제 세 가지가 현재 코드에도 남아 있다. 상세 재현은 [8-2 재검토](./review-chapter-08-task-02-followup.md)를 따른다.
- 7-1은 결과 정책이 구현돼 있지만 미분류 실패 및 알 수 없는 종료/WL 조합을 안전하게 해석하지 않는 경로가 남아 있다.
- 라우터의 회고 화면은 `GenericView`, 노트 화면에는 고정된 표시 내용이 있다. 앱 화면에서 엔진 클라이언트를 연결한 흔적은 확인하지 못했다. `Transport`는 인터페이스와 mock이 있으며, 현재 워크스페이스에서 실제 Tauri/CLI/소켓 전송 구현과 파일 감시 구현은 확인하지 못했다. 9~11장 명세는 있으나 전용 읽기 클라이언트는 없다.
- `npm test`: 15개 파일·269개 통과. `npm run build`: TypeScript와 Vite 빌드 성공. 실제 엔진 프로세스·실제 vault·공식 수용 묶음은 이번 점검에서 실행하지 않았다.
- 현재 경로와 상위 경로에서 Git 저장소를 확인하지 못했다. 따라서 변경 이력이나 미커밋 상태에 대한 판단은 하지 않는다.

## 다음 개발 단위 A — 8-2 스냅숏 격리 보완

대상은 `src/engine/indexing/coordinator.ts`와 관련 테스트·공개 계약 문서다. 기존 일정 식별자와 stale callback 차단, 경합·실패 처리, 기존 성공/실패 타입을 유지한다. UI, 감시, DB, 7장 수정은 포함하지 않는다.

1. **성공 데이터 소유권**: `cloneReindexResponse`의 루트와 `skipped`·`conflicts` 항목 추가 키에는 중첩 JSON 객체/배열이 있을 수 있다. 전체 값을 보존하고 입력 객체를 변경하거나 동결하지 않으면서 내부에 독립 사본을 저장한다. 요청 원본 변경이 내부로, 스냅숏 변경이 원본이나 내부로 전파되지 않아야 한다. paths의 `unverifiedPriorHealth`까지 확인한다.
2. **실패 원인 격리**: `cloneRefreshFailure`의 `cause` 및 계약 위반 detail 등의 중첩 값과 바이트 배열을 분리한다. Error의 name·message·stack·cause·사용자 속성 등 의미 있는 정보는 유지한다. JSON stringify로 예외나 바이트를 소실하지 않는다. `unknown`의 모든 가능한 호스트 객체를 보편적으로 완벽 복제한다고 가정하지 말고, 지원하는 값·순환 참조 및 지원하지 않는 값의 처리 정책을 명시하고 정보 손실이나 참조 공유를 숨기지 않는다.
3. **구독자 격리**: 현재 `notifySubscribers`는 동일 스냅숏 하나를 모든 구독자에게 준다. 한 구독자가 변경 가능한 `Uint8Array`나 원인 값을 바꿔도 다른 구독자와 내부 상태에 영향이 없도록 독립 사본을 제공한다. nonempty typed array는 `Object.freeze`하지 않는다. 구독자 콜백에서 재진입하는 경우에도 같은 통지의 각 수신자가 동일한 사건의 상태를 보도록 설계한다.

회귀 테스트: 원본과 각 `getSnapshot` 및 구독자 간 양방향 변경 격리, 추가 키의 중첩 객체·배열, typed array의 바이트, Error와 중첩 cause, 지원 정책에 따른 순환/특수 값, full→paths의 이전 건강 정보. 실패 후 오래된 예약 콜백·실행 중 요청·vault 분리·dispose 등 기존 사례도 유지한다. `npm test`, `npm run build` 통과 및 README/타입 설명의 실제 보장 범위 확인을 완료 기준으로 한다.

## 개발 단위 B — 7-1 쓰기 결과 보완

대상은 `src/engine/write/outcomes.ts`, 관련 타입·테스트·사용 예시다. 자동 재시도나 실제 쓰기는 추가하지 않는다.

- `unclassified_execution_failure`는 쓰기가 없었다고 확정하지 않는다. 특히 종료 1, 알 수 없는 종료 코드 및 미정의 조합은 초안 보존, 부분 반영 가능성, 상태 재확인 필요로 표현한다.
- 충돌은 공통 분류기가 판정한 `precondition_conflict`에 근거한다. 현재 `exitCode === 5` 또는 `wlCode === 412`만으로 충돌로 분기하는 경로를 제거한다. `exit 5 + WL-500`, `exit 3 + WL-412`, `exit 1 + stderr WL-412` 등은 확정된 충돌이 아니다. 마찬가지로 `wlCode === 500`만으로 파일 처리 실패로 확정하는 분기를 검토해 공통 분류 및 코드 출처와 모순되지 않게 한다. CLI stderr 정규식은 로그에서 오탐할 수 있다.
- 알려진 no-op 성공에서 현재 `vaultState: 'unchanged'`가 대상 파일 무변경을 vault 전체 무변경으로 오해하게 하는지 점검한다. 7.1·7.2의 쓰기 전 색인/기록 등 범위와 타입 의미를 맞추고, 확정할 수 없는 외부 변경도 단정하지 않는다. 기존 호출자와 타입 변경 영향 및 테스트를 함께 살핀다.
- 실제 `decodeResponse`/`classifyFailure`를 통과한 입력으로 5/412 정상 충돌, 3/500 정상 파일 실패, 위 불일치 조합, 코드 없는 1, 미지 종료, CLI 로그 속 WL, 소켓 3/0, 전송 단계 및 계약 위반을 검증한다. 원본 바이트·분류 정보를 유지하고 초안 및 재조회 지침을 확인한다. 테스트와 빌드 통과가 완료 기준이다.

## 이후 연결 계획과 검증 경계

- 실제 전송은 엔진 실행 파일·플랫폼·vault 구성·소켓/단발 선택이 확인된 뒤 3·4·5·6장에 따라 별도 상세 계획을 세운다. 전송 실패와 엔진 실패를 구분하고 제한된 argv/프레임을 검증한다. 엔진 DB를 앱이 직접 열지 않는다.
- 회고 화면은 현재 `GenericView`이므로 UI 상태, vault별 데이터, 요청 경합과 진단/불완전 목록 표시를 실제 실행 경로와 함께 개발한다. 태그 목록은 reading 메인 노트의 마지막 색인 결과임을 표시하고 원문과 서버 순서를 보존한다.
- 7-2와 8-3은 실제 연결 외에도 늦은 응답·저장 중 편집·색인 실패·외부 변경을 다뤄야 한다. mock 테스트와 격리 vault에서의 실제 검증 결과를 별도로 기록한다.
- 6·7·8장 기존 계획 문서의 테스트 수치와 '다음 작업' 표현은 작성 당시의 기록일 수 있다. 현재 우선순위는 이 문서와 최신 검토 기록을 기준으로 한다.

이번 작업은 검토·계획과 현황 문서 갱신이며 애플리케이션 소스를 수정하지 않았다.
