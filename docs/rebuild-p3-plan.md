# 3부 화면 구현 순서

2단계에는 vault를 여는 데 필요한 최소 엔진 다리를 먼저 연결한다. 5단계에서 전체 읽기·쓰기 계약을 갖추고 다시 검증한다. 단계마다 코드, 검증 결과, 남은 범위를 함께 기록한다.

## 공통 기준

- 대상은 4부가 없는 판이다. 현재 Java 엔진과 Rust 호스트도 4부를 제공하지 않는다.
- argv, IPC 이름과 인자, 이벤트, 파일·저장 키, 주소와 딥링크, 사용자 동작 결과, markdown 왕복, 받아들임 표식은 계약으로 지킨다.
- CSS와 컴포넌트 구성은 새로 정할 수 있다. 원본 디자인 시스템 자료와 글꼴은 제공되지 않았다. 현재는 기기 기본 글꼴을 쓰고 원격 자원을 불러오지 않는다.
- 브라우저 미리보기, 실제 WKWebView 점검, 앱 번들 생성, 실제 번들 실행은 구분해서 보고한다.
- 알려진 결함은 자동으로 수정하거나 전부 재현하지 않는다. 해당 기능 구현 시 계약과 미결정 동작을 기록하고 데이터 손실 위험은 별도로 검증한다.
- 실사용 vault를 변경하지 않는다. 검증에 필요한 쓰기는 임시 vault와 격리된 홈을 사용한다.

## 제공된 자료의 한계

PDF는 13장 13.9에서 끝난다. 14~18장과 부록 A~D는 목차와 앞장의 개요만 있고 본문이 없다. 따라서 9~10단계를 설명서와 동일하게 완성했다고 판정할 수 없다. 앞선 장에서 이미 명시된 계약은 먼저 구현할 수 있다.

설명서가 언급한 `scripts/parts/screen.mjs`, `combine.mjs`, `roundtrip.mjs`, `fixtures/screen-roundtrip/`의 원본 71사례도 이 저장소에는 없다. 새로 만든 점검을 원본 검사 통과로 표현하지 않는다. 편집기를 만들 때 문서에 적힌 사례와 기대 바이트부터 독립 검증을 구성한다.

4부 꽂이 5묶음은 이름만 1장에 나와 있고 정확한 내보내기는 미제공 17장의 범위다. 빈 인터페이스를 추측해서 만들지 않고 필요한 시점에 명시된 계약부터 연결한다.

## 2단계의 완료 조건

1. 직전 vault 경로를 글자 그대로 호스트에 넘기고 `allow_workspace`를 엔진 호출보다 앞에 보낸다.
2. 초기화·이관 뒤 첫 읽기 4개와 다음 읽기 3개의 순서를 지킨다. 실패 허용 범위는 2.3을 따른다.
3. 샘플은 호스트와 엔진 없이 열리고 실제 vault의 직전 기록을 바꾸지 않는다.
4. 만들기·열기·최근 목록과 저장 키의 값 모양을 검증한다.
5. 노트 창은 main의 vault를 읽으며 workspace 변경과 main 전용 저장을 하지 않는다. 노트 창 전체 수명 구현은 15장 범위로 남긴다.

위 조건의 검증 결과와 다른 장의 연결 범위는 [2단계 기록](rebuild-p3-chapter02-complete.md)에 있다.
