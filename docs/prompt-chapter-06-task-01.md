## 이번 개발 범위

계획서의 **작업 1 — 공통 응답 계약과 실패 분류**만 구현해 줘.

목표는 React 화면이나 실제 엔진 없이도 검증 가능한 TypeScript 공통 계층을 만드는 것이야. 후속 작업에서 명령별 응답 검사, 화면, Tauri 실행부를 연결할 수 있어야 해.

예상 파일은 다음과 같고, 현재 구조에 맞게 조정해도 돼.

- src/engine/types.ts
- src/engine/transport.ts
- src/engine/decodeResponse.ts
- src/engine/classifyFailure.ts
- src/engine/testing/MockTransport.ts
- 관련 테스트 및 최소한의 사용 예시/설명

## 구현 요구사항

1. Transport 인터페이스와 원본 응답 타입을 정의해 줘.
   - 실행 출처/모드, stdout·stderr 원본 바이트, 종료 코드를 보존해 줘.
   - 소켓 프레임에서 제공되는 오류 코드, pid, dbSchema를 표현할 수 있게 해 줘.
   - 실제 프로세스 응답, 로컬 연결/프레임 실패, 신호 종료를 구분해 줘. 로컬 실패에 엔진 종료 코드를 임의로 부여하지 마.
   - 알려지지 않은 종료 코드와 WL 코드도 원본 숫자를 잃지 않게 해 줘.

2. 공통 응답 해석기를 구현해 줘.
   - 종료 0일 때만 성공 JSON을 해석하고, 명령별 런타임 validator를 받아 검증해 줘. 타입 단언만으로 검증을 대체하지 마.
   - 종료 0이어도 stderr가 있으면 성공 결과와 진단을 함께 전달해 줘.
   - 빈 성공 stdout, 손상된 JSON, 스키마 불일치, 실패인데 stdout이 존재하는 경우는 앱의 계약 오류로 구분해 줘. WL-500으로 바꾸지 마.
   - 원본 바이트와 stderr 문구·LF를 유지해 줘. 값 다듬기, 누락 키 채우기, falsy 값 제거를 하지 마.
   - 출력 생성기나 재직렬화기는 이번 범위에 넣지 마. 바이트 fixture 검증과 실제 엔진 출력 생성은 구분해 줘.

3. 종료 코드와 WL 코드를 함께 분류해 줘.
   - 3/400: 입력 오류, 3/404: 대상 없음, 3/409: 상태 거절, 3/500: 파일 처리 실패.
   - 5/412: 선결 조건 충돌. 다시 읽고 재적용해야 한다는 복구 정보를 제공해 줘.
   - 종료 2는 호출/설정 실패야. CLI stderr에 WL-400이 있어도 종료 3으로 바꾸지 마.
   - 종료 4는 사이드카 연결 문제로 구분해 줘.
   - serve의 종료 3 + 프레임 오류 코드 0은 예상 밖 엔진 실패야.
   - 단발의 종료 1, 신호 종료, 미지의 코드는 분류되지 않은 실행 실패로 보존해 줘.
   - 소켓에서는 구조화된 프레임 코드가 기준이야. 프레임 코드 0도 명시적인 '코드 없음'이므로 stderr 추출로 덮어쓰지 마.
   - CLI에서는 /\bWL-\d{3}\b/의 첫 일치를 호환 정보로 추출하되 출처를 표시해 줘. 앞선 로그나 파일명 속 WL-999를 잘못 읽을 수 있다는 한계를 테스트로 남겨 줘.
   - 미정의 코드 조합을 임의로 알려진 오류에 끼워 맞추지 마. 분류 결과와 원본 관측값을 함께 유지해 줘.

4. 복구 행동은 데이터로 제공하고 실제 부작용을 실행하지 마.
   - 자동 재시도, 대상 자동 생성, 쓰기 자동 재전송을 구현하지 마.
   - WL-500이 항상 재시도 가능한 것은 아니라는 점을 반영해 줘.
   - 쓰기 도중 예상 밖 실패나 연결 끊김은 이미 반영된 내용이 있을 수 있어. 상태 재조회가 필요하다는 정보를 제공해 줘.
   - 종료 0의 ok:false, failed, stoppedAt 등을 전역 실패 규칙으로 처리하지 마. 명령별 처리는 후속 작업이야.

5. MockTransport를 구현해 줘.
   - 성공·진단 있는 성공·코드별 실패·계약 오류·전송 실패를 주입할 수 있어야 해.
   - 요청별 원본 응답과 진단이 섞이지 않아야 하고, 여러 테스트가 상태를 공유하지 않아야 해.

## 검증과 완료 기준

현재 TypeScript/Vite 환경에 맞는 최소한의 테스트 구성을 추가하고 package.json에 단발 실행용 test 스크립트를 만들어 줘. 새 의존성을 선택하면 설치 버전의 호환성을 확인하고 lockfile도 갱신해 줘.

다음 사례를 자동 검증해 줘.

- 6.1의 회고 예시를 키 순서·2칸 들여쓰기·끝 LF까지 고정한 바이트 fixture로 읽기.
- 한글, 따옴표, 역슬래시, 제어문자, U+2028/U+2029의 원본 바이트 보존과 올바른 JSON 해석.
- 성공 JSON과 stderr 진단의 동시 전달.
- 명시한 종료/WL 조합, CLI 종료 2 + WL-400, serve 3/0, 단발 1, 신호 종료, 미지의 코드.
- 프레임 400 + stderr 앞부분 WL-999에서 프레임 우선, 프레임 0에서 stderr 추출로 덮어쓰지 않음.
- 빈/손상된 성공 JSON, validator 실패, 실패 stdout의 계약 위반.
- 로컬 연결/프레임 실패와 엔진 응답의 구분.
- 누락 키, false, 빈 배열, null 및 여러 줄 stderr의 보존.
- 요청 간 응답/진단 격리.

`npm test`와 `npm run build`를 실행하고, 이번 변경으로 생긴 실패를 해결해 줘. 실행하지 못한 검증과 이유는 명확히 남겨 줘. 저장소에 없는 공식 448건 검증 묶음을 통과했다고 보고하지 마.
