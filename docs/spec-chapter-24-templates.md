# withlog 1부 vault 엔진 설명서 > 24장 명령 템플릿 5개

이 장은 템플릿 파일을 읽는 명령 2개와 고치는 명령 3개가 받는 인자, 실패, 디스크 바이트, 응답을 정한다. 템플릿 파일의 모양은 2.4에도 있고, 여기서는 명령이 그 파일을 어떻게 고르고 읽고 쓰는지를 적는다.

- 템플릿은 `.withlog/templates/doc/` 의 문서 템플릿과 `.withlog/templates/ritual/` 의 리추얼 템플릿 2갈래이고, 갈래는 파일이 놓인 폴더가 정한다.
- 읽기 명령은 부를 때마다 폴더 2개를 통째로 훑고 색인을 안 쓴다. 못 읽은 파일이 있으면 목록을 incomplete 봉투로 감싸고, 경로와 이유는 stderr에 적는다.
- 문서 템플릿은 `<id>.md` 에, 리추얼 템플릿은 `<rev>.md` 에 원자적으로 쓴다. 옛 포맷 파일은 새 파일을 쓴 뒤에 지운다.
- 문서 템플릿 지우기는 사용자가 만든 템플릿만 지우고 휴지통을 안 지난다.
- 근거: 읽기 응답 바이트는 묶음 15건(`list_templates` 9건, `get_template` 6건)이 잰다. 쓰기 3개, 명령 표면, `bodies`, 봉투, WL 번호, 공백과 소문자와 정규식 규칙은 코드 읽기로 확인했다.

## 24.1 한눈에

| 명령 이름 | 도구 이름 | 쓰기 깃발 | 하는 일 |
|---|---|---|---|
| `list-templates` | `list_templates` | 없음 | 2갈래 템플릿의 목록. 명령 표면은 본문까지 실을 수 있다 |
| `get-template` | `get_template` | 없음 | 템플릿 1건을 본문까지 |
| `save-template` | `save_template` | 있음 | 문서 템플릿을 새로 만들거나 고친다 |
| `delete-doc-template` | 없음 | 있음 | 사용자가 만든 문서 템플릿을 지운다 |
| `save-ritual-template` | 없음 | 있음 | 리추얼 템플릿 1개를 고친다. 짝 명령이라 24.8에 따로 적는다 |

읽는 자리는 템플릿 폴더 2개뿐이고, 노트 색인도 아젠다도 안 본다. 템플릿은 사람이 손으로 고치는 파일이고 실 vault에 12개뿐이라, 색인을 두면 맞출 일만 생기고 손으로 고친 직후에 옛 값을 보여 줄 수 있기 때문이다. 같은 까닭으로 serve 모드 엔진(3.2)도 템플릿을 기억해 두지 않고 부를 때마다 파일을 다시 읽는다.

쓰는 자리는 템플릿 폴더 2개이고, 폴더가 없으면 만든다. 쓰기 깃발 명령 3개는 일을 하기 전에 워크스페이스 표식을 보고 노트 색인을 맞추며(7.1, 8.3), vault git 자동 커밋에 쓴 쪽을 남긴다(31.1). 템플릿은 색인과 무관하지만, 쓰기 깃발이 그 차례를 모든 쓰기 명령에 거는 규칙이라 그대로 따른다.

`delete-doc-template` 과 `save-ritual-template` 은 도구 표면에 없다. 도구 표면은 옛 도구 목록을 그대로 옮긴 표면인데 그 목록에 이 명령 2개의 짝이 없었고, 템플릿은 노트 평가로 키우는 자산이라 Claude 손에 지우는 길을 쥐여 주지 않으려고 뺐다(코드 읽기로 확인).

## 24.2 부르는 법

| 표면 | 꼴 |
|---|---|
| 도구 | `list_templates '{"category":"doc", "type": "plan"}'` |
| 도구 | `get_template '{"id":"m-plan"}'` |
| 도구 | `save_template '{"id":"<고칠 id>", "name":"<이름>", "type":"<유형>", "desc":"<설명>", "body":"<본문>"}'` |
| 명령 | `list-templates [category=<갈래>] [type=<유형>] [bodies=true]` |
| 명령 | `get-template <템플릿 id>` |
| 명령 | `save-template [id=<id>] [name=<이름>] [type=<유형>] [desc=<설명>] [body=<본문>]` |
| 명령 | `delete-doc-template <문서 템플릿 id>` |
| 명령 | `save-ritual-template <리추얼 템플릿 id> [name=<이름>] [desc=<설명>] [body=<본문>]` |

도구 표면의 키는 `get_template` 의 `id` 만 필수다. 표면 2가지는 같은 처리로 가고 응답 바이트도 같다. 다른 자리는 3가지뿐이다.

- `bodies` 는 명령 표면에만 있다. 도구 표면의 인자 집합을 옛 도구와 같게 지키려고 일부러 안 냈다.
- 지우기와 리추얼 고치기는 명령 표면에만 있다.
- 도구 표면의 `save_template` 은 `body` 가 200,000 UTF-16 코드 단위를 넘으면 거절한다(24.3). 명령 표면에는 길이 상한이 없다.

단발 모드(3.1)에서는 이렇게 부른다.

```bash
java -jar wl-sidecar.jar list_templates '{"category":"ritual"}' --withlog.vault=/Users/me/vault
java -jar wl-sidecar.jar save-template id=tpl-seeded 'desc=조사할 때 쓴다' --withlog.vault=/Users/me/vault
```

`wl-cli` 로 부르면 같은 argv가 serve 모드 엔진으로 가고 결과 바이트는 같다(3.3). 이 장의 이름 8개(도구 이름 3개와 명령 이름 5개)는 모두 `wl-cli` 가 엔진으로 넘기는 이름이다.

이름, 설명, 본문은 명령 표면에서도 `이름=값` 으로만 받는다. 본문에는 `=` 와 줄바꿈이 들어서, 자리 인자로 받으면 파서가 본문 안의 `-`를 옵션 문법으로 읽기 때문이다. `이름=값`은 첫 `=` 에서만 갈라서 값 안의 `=`가 그대로 남는다(5.2).

## 24.3 인자와 검증

도구 표면은 `--` 칸을 뺀 인자가 0칸이나 1칸이고, 그 1칸은 JSON 객체여야 하며, 모르는 키와 빠진 필수 키와 타입이 틀린 값을 거절한다(5.4). 차례는 인자 칸 수, JSON 문법, 객체인지, 모르는 키이고, 그 뒤에 24.2의 꼴에 적힌 키 차례대로 칸마다 「있는가, 타입이 맞는가, 길이가 맞는가」를 본다. 명령 표면은 모르는 옵션과 남는 자리 인자를 거절한다(5.2). 이 문법 검사는 워크스페이스 표식과 색인 맞추기보다 먼저다. 이 절은 그 문법을 지난 값을 무엇으로 읽는지를 명령마다 적는다.

낱말 규칙 3가지. 아래 3가지는 이 장과 25장, 29장, 30장에서 같은 뜻으로 쓴다(코드 읽기로 확인).

1. 「공백」은 아래 28개 코드 포인트다. 「앞뒤 공백을 뗀다」는 양 끝에서 이 글자들을 떼는 일이고, 「공백뿐」은 빈 글이거나 이 글자들로만 된 글이다. 인자 다듬기, 이름과 id의 빈칸 검사, 회고 본문의 내용 판정, 날짜 다듬기, 도장 다듬기가 모두 이 집합 1개를 쓴다.
   - `U+0009`, `U+000A`, `U+000B`, `U+000C`, `U+000D`
   - `U+001C`, `U+001D`, `U+001E`, `U+001F`, `U+0020`
   - `U+00A0`, `U+1680`
   - `U+2000`, `U+2001`, `U+2002`, `U+2003`, `U+2004`, `U+2005`, `U+2006`, `U+2007`, `U+2008`, `U+2009`, `U+200A`
   - `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`
   `U+0085`, `U+180E`, `U+200B`, `U+FEFF`는 공백이 아니다. 그래서 JavaScript의 `trim()` 과 2곳에서 갈린다. JavaScript는 `U+FEFF`를 떼고 `U+001C`부터 `U+001F`까지는 안 뗀다.
2. 「소문자로 바꾼다」는 로캘 규칙 없이 유니코드의 기본 소문자 대응으로 바꾼다. 그래서 U+212A(켈빈 기호)는 `k` 가 되어, `WEE` 와 U+212A와 `LY` 를 이은 글은 `weekly` 로 받는다. 기기의 로캘이 터키어여도 `EVENING` 은 `evening` 이 된다. 전각 글자 `ＷＥＥＫＬＹ` 는 전각 소문자가 되어 거절된다.
3. 「모양」을 보는 정규식은 글 전체가 맞아야 한다. 끝에 LF 1개가 붙은 값도 그 LF까지 맞아야 해서 틀린 모양이다. 그래서 `m-plan` 뒤에 LF가 붙은 id와, 블록 스칼라(`|`)로 적어 `sunrise` 뒤에 LF가 남은 아이콘은 모두 틀린 모양이다. 어떤 정규식 엔진은 `$` 가 끝의 LF 앞에서도 맞으니, 다시 지을 때는 글 전체를 맞추는 함수나 글 끝 표시를 쓴다. `[0-9]` 와 `\d` 는 ASCII 숫자 10개뿐이다. 길이는 UTF-16 코드 단위로 센다.

`list-templates` 가 받는 칸은 3개다. 자리 인자는 0칸까지 받는다.

| 칸 | 도구 키 | 명령 옵션 | 받는 값 | 안 주거나 비었을 때 |
|---|---|---|---|---|
| 갈래 | `category` | `category=` | 앞뒤 공백을 떼고 소문자로 바꾼 값이 `doc` 이나 `ritual` | 2갈래 모두 |
| 유형 | `type` | `type=` | 같은 처리 뒤 `plan`, `build`, `report`, `research`, `meeting`, `free` 가운데 1개 | 유형을 안 본다 |
| 본문 싣기 | 없음 | `bodies=` | 앞뒤 공백을 뗀 값이 정확히 `true` 나 `false`. 대소문자를 가린다 | 거짓 |

「비었을 때」는 앞뒤 공백을 뗀 값이 빈 글일 때다. 유형을 주면 리추얼 템플릿이 통째로 빠진다. 리추얼에는 유형이라는 칸이 없어서 그 조건을 만족할 길이 없기 때문이다. 그래서 `category=ritual type=plan` 은 빈 배열이다.

값을 보는 차례는 이렇다.

1. 갈래를 본다.
2. 유형을 본다.
3. 템플릿 폴더 2개를 훑고, 못 읽은 파일의 진단 줄을 stderr에 적는다(24.6).
4. `bodies` 를 본다.

`bodies` 를 훑기 뒤에 보아서, 그 값이 틀리면 3번의 진단 줄이 stderr에 먼저 찍히고 `WL-` 줄이 그 뒤에 온다. 갈래나 유형이 틀리면 훑기 전이라 진단 줄 없이 `WL-` 줄만 나온다.

`get-template` 은 id 1개를 받는다. 도구 표면은 필수 문자열 `id` 이고, 명령 표면은 자리 인자 1칸이며 옵션이 없다. 값을 다듬지 않는다. 비었거나 공백뿐이면 거절하는데, 빈 셸 변수를 모양 오류로 오해하지 않게 하려는 검사다. 그다음 id가 `^[A-Za-z0-9._-]{1,128}$` 모양이 아니면 거절하고, 모양은 맞는데 그 id의 템플릿이 없으면 `WL-404` 다. 도구 표면에 `{}` 를 주면 문법 단계의 「`id` 가 필요하다」로 서고, `{"id":""}` 를 주면 문법은 지나고 「인자가 하나 필요하다」로 선다.

`save-template` 은 id 의 있고 없음으로 만들기와 고치기를 가른다. `id` 를 안 줬거나 빈 글이면 만들기이고, 그 밖은 모두 고치기다. 공백뿐인 id 도 고치기로 가서 모양 검사에서 선다. 빈 글을 만들기로 보는 까닭은 옛 도구가 빈 id 를 「안 줬다」와 같게 다뤘기 때문이다. 만들기와 고치기를 명령 1개에 둔 까닭은 앱의 템플릿 화면이 만들 때와 고칠 때 같은 저장 단추를 쓰기 때문이다.

| 칸 | 키와 옵션 | 만들기 | 고치기 |
|---|---|---|---|
| `id` | `id` | 안 줬거나 빈 글 | 다듬지 않는다. 공백뿐이거나 `^[A-Za-z0-9._-]{1,128}$` 가 아니면 `WL-400` |
| 이름 | `name` | 필수. 앞뒤 공백을 떼고 비면 `WL-400`. 뗀 값을 저장한다 | 주면 받은 그대로 저장한다. 빈 글이거나 공백뿐이면 `WL-400`. 안 주면 지금 값 |
| 유형 | `type` | 안 주면 `plan`. 주면 다듬지 않고 소문자로 바꿔 6개 값 가운데 1개여야 하고, 빈 글도 `WL-400` | 같은 검사. 안 주면 지금 값 |
| 설명 | `desc` | 안 주면 빈 글. 주면 받은 그대로 | 주면 받은 그대로 바꾼다. 빈 글이면 설명을 지운다. 안 주면 지금 값 |
| 본문 | `body` | 필수. 안 줬거나 빈 글이거나 공백뿐이면 `WL-400`. 받은 그대로 저장한다 | 주면 받은 그대로 바꾼다. 빈 글이면 본문을 비운다. 안 주면 지금 값 |

「지금 값」은 디스크의 글자가 아니라 24.5의 규칙으로 읽은 값이다. 그래서 이름은 앞뒤 공백을 뗀 값이나 id로 물러선 값이 다시 적힌다. 고치기에서 빈 글과 안 준 것을 가르는 까닭은 설명과 본문을 지우는 길이 그것뿐이기 때문이다. 이름만 만들기에서 다듬어 저장하는 까닭은 옛 도구가 그렇게 저장했기 때문이고, 본문은 끝 줄바꿈 1개가 그 템플릿으로 만드는 노트마다 번져서 안 다듬는다.

`format` 과 `builtin` 은 안 받는다. 문서 템플릿은 언제나 마크다운으로 쓰고, `builtin` 은 제품이 심은 템플릿인지를 적은 기록이라 고치기가 바꾸면 빌트인을 사용자 템플릿으로 위장할 수 있기 때문이다. 도구 표면의 `body` 는 200,000 UTF-16 코드 단위까지 받는다. 정확히 200,000이면 받고 200,001부터 거절한다. 나머지 키와 명령 표면에는 길이 상한이 없다.

값을 보는 차례는 워크스페이스 표식과 색인 맞추기 뒤다. 만들기는 본문, 이름, 유형 차례로 보고, 고치기는 id, 이름, 유형 차례로 본 뒤 24.5의 고치기 차례로 넘어간다. 그래서 본문과 이름이 모두 빠진 만들기는 본문이 없다는 문구로 거절된다.

`delete-doc-template` 은 자리 인자 1칸을 받고 옵션이 없다. 값을 다듬지 않고, 비었거나 공백뿐이면 거절하고, 모양이 `^[A-Za-z0-9._-]{1,128}$` 가 아니면 거절한다. 이 검사 2개는 워크스페이스 표식과 색인 맞추기 뒤에 한다.

`save-ritual-template` 의 인자는 24.8에 적는다.

실패하면 stdout은 늘 0바이트이고, stderr는 진단 줄 뒤 `WL-<번호> <문구>` 로 끝난다(6.4). 리추얼과 빌트인을 지우려는 호출도 `WL-409` 가 아니라 `WL-400` 이다. 지금 문구는 이렇고, 문구는 계약이 아니다(0.2).

## 24.5 읽고 쓰는 자리

훑기. 폴더 2개를 이 차례로 본다. 먼저 `.withlog/templates/doc/` 를, 다음에 `.withlog/templates/ritual/` 을 본다. 폴더가 없거나, 폴더가 아니거나, 목록을 못 읽으면 그 폴더는 빈 것으로 보고 오류도 목록 진단 줄도 안 낸다. 템플릿을 1개도 안 만든 vault가 정상이기 때문이다. 단발 모드에서는 이때 엔진 로그 줄이 stderr에 섞일 수 있는데, 그 줄은 계약이 아니다.

폴더 바로 아래 항목 가운데 일반 파일만 본다. 심볼릭 링크는 따라가서 파일을 가리키면 그 파일을 읽고, 대상이 없거나(깨진 링크) 폴더를 가리키면 일반 파일이 아니라서 조용히 지나간다. 깨진 링크는 「못 읽은 파일」로 세지 않아서 목록이 봉투로 안 바뀐다. 하위 폴더 안은 안 본다.

파일은 이름의 UTF-16 코드 단위 차례로 늘어놓는다. 이름은 파일 시스템이 준 글자 그대로 견주고 유니코드 정규화(NFC, NFD)를 안 한다. 그래서 같은 한글 이름이라도 NFC로 지은 파일과 NFD로 지은 파일은 다른 이름이고, 그 2개가 같은 id를 들면 코드 단위가 앞인 쪽이 「처음 찾은 것」이다(코드 읽기로 확인).

| 폴더 | 후보가 되는 이름 | 포맷을 정하는 자리 |
|---|---|---|
| `doc/` | `.md`, `.html`, `.json` 으로 끝나는 이름. 대소문자를 가린다 | 확장자. `.md` 는 `markdown`, `.html` 은 `html`, `.json` 은 `json` |
| `ritual/` | `.md` 로 끝나는 이름 | 프론트매터 `format`. 정확히 `markdown` 이면 `markdown`, 그 밖과 없음은 `html` |

후보가 아닌 파일(`.DS_Store`, 쓰다 남은 `<이름>.<무작위>.tmp` 같은 것)은 조용히 지나간다. 템플릿으로 놓인 파일이 아니라서 「못 읽었다」로 세면 목록이 늘 불완전해 보이기 때문이다. 이름이 점으로 시작하는 파일도 후보다. 리추얼의 포맷을 프론트매터에서 얻는 까닭은 `format` 을 안 적은 옛 리추얼 파일의 본문이 HTML이라서, 확장자만 보면 HTML 태그가 글자로 그려지기 때문이다. 충돌 사본 이름(1.2의 정규식)은 템플릿 폴더에서 걸러지지 않는다(24.9).

후보 파일 1개 읽기. 이 차례로 읽는다. 걸리면 그 파일만 건너뛰고 이유를 남긴다.

1. 1,000,000바이트를 넘거나, 입출력 오류가 나거나, 엄격한 UTF-8이 아니면 건너뛴다. 이유는 `파일을 못 읽었거나 크기 상한을 넘었다` 다. 정확히 1,000,000바이트는 읽는다.
2. 울타리를 자르고 YAML을 읽는다. 규칙은 1.6의 읽기 2번부터 7번, 1.8의 YAML 1.1 규칙(시각 해석을 끈다)과 같다. 별칭과 겹의 상한도 노트와 같아서, 같은 YAML을 넣은 노트와 템플릿이 같은 자리에서 빠진다(2026-10-25 실측). 프론트매터가 없으면 건너뛰고 이유는 `프론트매터가 없거나 문법이 어긋난다` 다.
3. id는 프론트매터 `id` 가 길이 0이 아닌 문자열이면 그 글자 그대로다. 키가 없거나, 문자열이 아니거나(`id: 123`), 빈 글이면 파일 이름에서 `.md`, `.html`, `.json` 가운데 붙은 확장자를 뗀 값이다. 공백뿐인 글(`id: ' '`)은 길이가 0이 아니라서 그대로 id 후보가 되고 5번에서 빠진다. 리추얼의 id가 `t-morning` 인데 파일이 `morning.md` 일 수 있는 까닭이 이 규칙이다.
4. id가 경로 조각으로 안전하지 않으면 건너뛰고 이유는 `템플릿 id 가 안전한 경로 세그먼트가 아니다: <id>` 다. 안전하려면 비지 않고, 100 UTF-16 코드 단위 이하이고, `/` 와 `\` 와 `..` 이 없고, `.` 으로 시작하지 않고, U+0020 미만 글자가 없어야 한다. 이 id가 나중에 쓰기와 지우기의 파일 이름이 되므로 폴더를 벗어나는 값을 여기서 막는다.
5. id가 공백뿐이거나 `^[A-Za-z0-9._-]{1,128}$` 가 아니면 건너뛰고 이유는 `템플릿 id 모양이 어긋난다: <id>` 다. 그래서 한글 id는 템플릿이 아니다.

2번의 울타리는 확장자가 아니라 내용이 정한다. 맨 앞 U+FEFF 1개를 뗀 글이 `<!--withlog` 로 시작하면 HTML 울타리이고, `---` 로 시작하면 `---` 울타리이고, 어느 쪽도 아니면 프론트매터가 없다. 그래서 `.md` 파일이 `<!--withlog` 로 시작해도 읽히고, `.html` 파일이 `---` 로 시작해도 읽히며, `.json` 문서 템플릿도 울타리 2가지 가운데 1개를 들어야 템플릿이다. 리추얼 폴더도 같다.

울타리 안의 YAML이 비었거나(`---` 바로 다음 줄이 닫는 `---`) 주석뿐이거나 최상위가 맵이 아니면 프론트매터가 없는 것으로 건너뛴다. 빈 맵으로 보고 파일 이름을 id로 쓰지 않는다. 다만 흐름 표기의 빈 맵 `{}` 은 맵이라서, `---`, `{}`, `---` 3줄로 시작하는 파일은 모든 칸이 물러선 값인 템플릿이 된다.

본문은 닫는 울타리 3글자(`---` 나 `-->`) 바로 뒤부터다. 거기서 맨 앞이 CRLF면 그 2글자를 떼고, 그다음 맨 앞이 LF면 그 1글자를 더 뗀다. 나머지는 바이트 그대로다. 그래서 `---`, LF, LF, x 의 본문은 LF, x 이고, `---`, CRLF, LF, x 의 본문도 LF, x 다. 본문이 빈 글이면 빈 글이다.

YAML 읽기에서 1.8에 더 적을 것이 1가지 있다. 명시 태그가 붙었는데 그 타입의 값으로 못 바꾸는 글(`id: !!int abc`, `name: !!float x`, Base64가 아닌 `!!binary`)이 든 파일은 건너뛰지 않고 훑기 전체를 세운다(24.9의 16번). 문법 오류와 별칭이나 겹의 상한 초과는 그 파일만 건너뛴다.

나머지 키. 템플릿을 버리지 않고 값으로 물러선다. 오타 1개로 템플릿이 목록에서 사라지면 사용자가 그 오타를 고칠 길도 사라지기 때문이다.

| 키 | 갈래 | 읽는 법 | 없거나 틀릴 때 |
|---|---|---|---|
| `name` | 2갈래 | 문자열의 앞뒤 공백을 뗀 값 | 문자열이 아니거나 떼고 비면 `id` |
| `type` | 문서 | 6개 값 가운데 1개와 글자가 정확히 같을 때. 대소문자를 가린다 | `build` |
| `desc` | 2갈래 | 문자열 그대로. 안 다듬는다 | 빈 글 |
| `builtin` | 문서 | YAML 불리언일 때 그 값. 따옴표 없는 `yes`, `no`, `on`, `off` 도 YAML 1.1 불리언이다(1.8) | `true`. 따옴표로 감싼 `'false'` 는 문자열이라 `true` |
| `format` | 리추얼 | 위 표의 규칙 | `html` |
| `rev` | 리추얼 | `morning`, `evening`, `weekly` 와 글자가 정확히 같을 때 | `morning` |
| `icon` | 리추얼 | `^[A-Za-z][A-Za-z0-9]{0,63}$` 일 때 그 값 | 읽은 `rev` 의 기본값. `morning` 은 `sunrise`, `evening` 은 `sunset`, `weekly` 는 `calendar` |
| 그 밖 | 2갈래 | 버린다 | 다음 쓰기에서 사라진다 |

문서 템플릿의 `format` 키와 리추얼 템플릿의 `type`, `builtin` 키는 안 읽는다. `builtin` 의 기본값이 참인 까닭은 옛 구현이 그렇게 읽어서, 거짓으로 두면 빌트인이 지울 수 있는 사용자 템플릿처럼 보이기 때문이다.

같은 id. 같은 id가 여럿이면 목록에는 모두 남는다. 단건 읽기와, 이미 있는 템플릿을 찾는 쓰기 3갈래(`save-template` 고치기, `delete-doc-template`, `save-ritual-template`)는 훑기 차례에서 처음 찾은 것을 쓴다. 훑기 차례는 문서 폴더의 이름 차례, 다음 리추얼 폴더의 이름 차례라서, `tpl-halfmoved.html` 과 `tpl-halfmoved.md` 가 함께 있으면 `.html` 이 이긴다. 이 승자는 묶음의 `get_template/tpl-halfmoved` 가 잰다. 정렬로 차례를 못박지 않으면 같은 vault에서 기계마다 다른 템플릿이 나오기 때문이다. `save-template` 만들기는 새 id를 발급하므로 찾지 않고, 폴더도 안 훑는다.

문서 템플릿 쓰기 바이트. 늘 `.withlog/templates/doc/<id>.md` 에 쓴다. 바이트는 `---\n`, YAML, `---\n`, 본문을 차례로 이은 글이다. YAML의 키 차례는 `id`, `name`, `type`, `format`, `desc`, `builtin` 이고, 6개 키를 늘 적는다. `format` 은 늘 `markdown` 이고 `builtin` 은 `true` 나 `false` 다. 문자열의 따옴표와 블록과 탈출 규칙은 노트 프론트매터와 같은 1.9의 규칙이다. 본문은 받은 그대로이고 BOM은 안 쓴다. 쓰기는 1.14의 원자적 쓰기이고, 같은 이름의 파일이 있으면 덮는다.

`save_template '{"name":"리서치 노트, 정리용", "type":"research", "desc":"조사 기록용", "body":"# [제목]\n\n배경을 적는다.\n"}'` 가 id `tpl-msciohji-6b623625` 를 받았을 때의 파일이다(예시 값). 울타리와 YAML 8줄은 옛 도구가 쓰던 바이트와 같은 모양이고(코드 읽기로 확인), 이름의 쉼표가 따옴표 없이 남는다.

```markdown
---
id: tpl-msciohji-6b623625
name: 리서치 노트, 정리용
type: research
format: markdown
desc: 조사 기록용
builtin: false
---
# [제목]

배경을 적는다.
```

본문이 줄바꿈으로 끝나서 파일도 `배경을 적는다.` 뒤 줄바꿈 1개로 끝난다. 설명이 빈 글이면 그 줄은 `desc: ""` 다. 이 파일을 다시 훑으면 같은 값이 나온다.

짝 없는 서로게이트는 자리에 따라 다르게 쓰인다(코드 읽기로 확인, 실행하지는 않았다). 이름과 설명에 들면 1.9의 인쇄 가능 범위 밖이라 그 값 전체가 큰따옴표로 감싸이고, 그 글자는 대문자 `\uD83D` 꼴로 탈출한다. 그래서 다시 읽으면 같은 짝 없는 서로게이트가 돌아온다. 본문에 들면 UTF-8로 바꿀 때 `?` (0x3F) 1바이트로 바뀌어 쓰이고, 다시 읽으면 `?` 다. 어느 쪽도 저장을 거절하지 않는다. 회고(25.5)는 같은 글자를 소문자 `\ud83d` 로 탈출해 지킨다. 이 차이는 쓰는 길이 달라서 생긴 결과이고, 그렇게 고른 근거는 코드에 없다(24.9의 17번).

만들기는 이 차례다.

1. id를 `tpl-<발급 순간의 유닉스 밀리초를 소문자 36진수로>-<무작위 4바이트를 소문자 16진수 8자로>` 로 발급한다(1.4).
2. `format` 은 `markdown`, `builtin` 은 `false` 로 둔다. 도구로 만든 템플릿은 정의상 사용자 템플릿이기 때문이다.
3. `<id>.md` 를 쓴다.

고치기는 이 차례다.

1. 그 id로 처음 찾은 템플릿이 없거나 문서 템플릿이 아니면 `WL-404` 다. 리추얼 id를 주면 「없다」로 답하는데, 옛 도구가 문서 폴더만 훑어서 리추얼을 못 봤기 때문이다. 못 읽어 건너뛴 파일만 그 id를 들고 있어도 「없다」다.
2. 받은 칸은 받은 값으로, 안 받은 칸은 찾은 템플릿의 읽은 값으로 채운다. `builtin` 은 찾은 값 그대로이고 `format` 은 `markdown` 이다.
3. `<id>.md` 를 쓴다.
4. 찾은 템플릿의 포맷이 `html` 이나 `json` 이었으면 `<id>.html` 이나 `<id>.json` 1개를 지운다. 없으면 조용히 지나간다. 포맷이 `markdown` 이었으면 아무것도 안 지운다.

쓰기가 지우기보다 앞인 까닭은 그 사이에서 프로세스가 죽었을 때의 손해 때문이다. 이 차례면 같은 id의 파일 2개가 남고 같은 명령을 다시 보내면 고쳐진다. 반대 차례면 사용자 템플릿이 디스크에서 사라지고, 다시 보내도 그 id가 없어서 「없다」로 끝난다. 지우는 이름은 찾은 파일의 이름이 아니라 `<id>.<확장자>` 다.

지우기는 이 차례다.

1. 그 id로 처음 찾은 템플릿이 없으면 아무것도 안 하고 성공한다. 지우다 죽어서 다시 부르는 것이 정상 흐름이기 때문이다. 못 읽어 건너뛴 파일만 그 id를 들고 있어도 이 갈래라서, 그 파일은 남는다.
2. 찾은 것이 리추얼이면 `WL-400` 이다. 리추얼을 지우는 길은 앱에도 없다.
3. 찾은 것이 `builtin` 이 참인 문서 템플릿이면 `WL-400` 이다. `builtin` 키가 없는 파일도 참으로 읽혀 여기서 선다.
4. `<id>.md`, `<id>.html`, `<id>.json` 을 이 차례로 있으면 지우고, 실제로 지운 자리를 그 차례로 돌려준다.

확장자 3개를 다 보는 까닭은 고치기가 중간에 죽으면 같은 id의 `.html` 과 `.md` 가 남아서, 1개만 지우면 나머지가 목록에 계속 보이기 때문이다. 휴지통을 안 지나는 까닭은 휴지통 목록이 노트 단위라 템플릿을 담을 자리가 없고, 템플릿을 가리키는 외래키도 없어 복구 기능이 템플릿을 다룰 줄 모르기 때문이다.

표식과 색인. 읽기 명령 2개는 워크스페이스 표식을 안 봐서, vault가 아닌 폴더에서는 빈 배열과 `WL-404` 를 낸다(1.1). 쓰기 명령 3개는 값을 보기 전에 노트 색인을 맞추는데, 템플릿은 그 색인을 안 쓰므로 비용만 든다. 쓰기 깃발 명령이라 표식 검사를 지난 뒤의 값 검사에서 실패한 호출도 vault git의 쓴 쪽 기록을 남긴다(31.1). 템플릿 명령이 템플릿으로 읽고 쓰는 파일은 폴더 2개 안에만 있다.

## 24.6 응답

바이트 규칙은 11.6과 같다. 2칸 들여쓰기, 키 차례가 계약, 끝 줄바꿈 1개다. 템플릿 응답은 갈래에 없는 키를 `null` 로 채우지 않고 키째 뺀다. 25장의 회고 상세는 반대 규칙이라 섞지 않는다.

| 키 | 타입 | 문서 목록 차례 | 문서 상세 차례 | 리추얼 목록 차례 | 리추얼 상세 차례 |
|---|---|---|---|---|---|
| `id` | 문자열 | 1 | 1 | 1 | 1 |
| `category` | 문자열 | 2 | 2 | 2 | 2 |
| `name` | 문자열 | 3 | 3 | 3 | 3 |
| `type` | 문자열 | 4 | 4 | 없음 | 없음 |
| `rev` | 문자열 | 없음 | 없음 | 4 | 4 |
| `icon` | 문자열 | 없음 | 없음 | 5 | 5 |
| `format` | 문자열 | 5 | 5 | 6 | 6 |
| `desc` | 문자열 | 6 | 6 | 7 | 7 |
| `body` | 문자열 | 없음 | 7 | 없음 | 8 |
| `builtin` | 불리언 | 7 | 8 | 없음 | 없음 |

`category` 는 폴더가 정한 `doc` 이나 `ritual` 이다. 값들은 24.5에서 읽은 값이고, `desc` 가 없으면 `""` 다. 사용자 템플릿도 `"builtin": false` 를 싣는다. 이 키가 빠지는 것은 리추얼일 때뿐이다.

문서 상세에서 `body` 가 `builtin` 앞에 끼는 까닭은 옛 도구의 키 차례가 그랬기 때문이다. 리추얼만 보고 지으면 「목록 원소 뒤에 `body` 를 붙인다」로 오해하기 쉬운 자리이고, 묶음의 `get_template/m-plan` 이 이 차례를 잰다. 리추얼의 `icon` 은 옛 도구에 없던 키다. 앱이 리추얼 카드 3개를 같은 아이콘으로 그리지 않게 하려고 더했고, 묶음이 이 키를 잰다.

목록은 배열이고, 원소는 갈래(문서 먼저), 다음 id의 UTF-16 코드 단위 차례다. 같은 id는 훑기 차례 그대로 남는다(묶음이 잰다). 명령 표면에서 `bodies=true` 를 주면 목록 원소가 상세 응답과 같은 키, 같은 차례, 같은 값이 된다. 배열 안이라 들여쓰기만 다르다. 본문은 훑기가 어차피 다 읽어 두어서, 이 옵션은 일의 양이 아니라 실을지만 바꾼다. 이 옵션이 있는 까닭은 앱이 템플릿 본문을 늘 모두 들고 있어서, 1건씩 부르면 템플릿 수만큼 왕복이 생기기 때문이다.

못 읽은 파일이 1개라도 있으면 목록을 봉투로 감싼다. 못 읽은 파일도 갈래 조건으로 거른다. 갈래가 `doc` 이면 리추얼 폴더의 못 읽은 파일을 안 세고, 갈래가 `ritual` 이면 문서 폴더의 못 읽은 파일을 안 세고, 유형 조건이 있으면 리추얼 폴더의 못 읽은 파일을 안 센다. 문서 폴더의 못 읽은 파일은 유형으로 거르지 않는다. 아래는 문서 폴더에 프론트매터 없는 `README.md` 를 더한 픽스처에서 `list_templates '{"type": "meeting"}'` 를 부른 응답이다(예시 값).

```json
{
  "templates": [],
  "incomplete": {
    "skipped": 1,
    "conflicts": 0,
    "note": "일부 파일을 읽지 못했어요(형식 오류·크기 초과) — 목록이 불완전할 수 있어요."
  }
}
```

`templates` 는 위 배열 그대로이고 비어도 싣는다. `skipped` 는 조건으로 거른 뒤의 못 읽은 파일 수다. `conflicts` 는 늘 0이다. 옛 도구가 폴더 1개를 훑는 봉투에서 충돌 사본을 따로 세지 않았기 때문이다. `note` 는 위 글자 그대로이고, 가운뎃점은 U+00B7, 줄표는 U+2014이며 줄표 앞뒤에 공백이 1칸씩 있다.

경로와 이유는 stdout에 안 싣고 `list-templates` 만 stderr에 이렇게 적는다. 적는 파일은 `skipped` 로 센 파일과 같고 훑기 차례다. stdout에 실으면 옛 도구와 바이트가 갈리고, stdout은 계약이고 stderr는 사람 몫이라는 규칙(6.4)을 따른다. 1번째 줄은 `템플릿 <n>건을 못 읽어 목록에서 뺐다.` 이고, 2번째 줄부터는 파일마다 공백 2칸, 경로, 공백, U+2014, 공백, 이유다.

```
템플릿 1건을 못 읽어 목록에서 뺐다.
  .withlog/templates/doc/README.md — 프론트매터가 없거나 문법이 어긋난다
```

`get-template` 과, 폴더를 훑는 쓰기 갈래(`save-template` 고치기, `delete-doc-template`, `save-ritual-template`)는 이 진단 줄을 안 적는다. `reindex` 도 같은 파일을 `skipped` 배열에 `kind` 가 `docTemplate` 이나 `ritualTemplate` 인 항목으로 싣는다(8.4). 그쪽은 조건 없이 훑어서 2갈래를 모두 싣는다.

픽스처 vault를 펼치고 `list_templates '{}'` 를 부르면 종료 코드 0과 아래 바이트에 줄바꿈 1개가 나온다. 묶음의 `list_templates/all` 이다(묶음이 잰다).

```json
[
  {
    "id": "m-plan",
    "category": "doc",
    "name": "기본 플래닝 템플릿 (markdown)",
    "type": "plan",
    "format": "markdown",
    "desc": "설계 전에 씁니다",
    "builtin": true
  },
  {
    "id": "t-legacy",
    "category": "doc",
    "name": "옛 HTML 템플릿",
    "type": "report",
    "format": "html",
    "desc": "아직 HTML 인 템플릿입니다",
    "builtin": true
  },
  {
    "id": "tpl-halfmoved",
    "category": "doc",
    "name": "옮기다 만 템플릿",
    "type": "build",
    "format": "html",
    "desc": "옛 본문입니다",
    "builtin": false
  },
  {
    "id": "tpl-halfmoved",
    "category": "doc",
    "name": "옮기다 만 템플릿",
    "type": "build",
    "format": "markdown",
    "desc": "새 본문입니다",
    "builtin": false
  },
  {
    "id": "tpl-seeded",

```

`t-legacy` 는 `-` 가 `p` 보다 작아서 `tpl-` 보다 앞이다. 같은 id 2개는 파일 이름 차례(`.html` 이 `.md` 보다 앞)를 그대로 지킨다. `get_template '{"id":"t-legacy"}'` 와 `get_template '{"id":"t-morning"}'` 의 응답은 이렇다. 묶음의 `get_template/t-legacy` 와 `get_template/t-morning` 이다(묶음이 잰다).

```json
{
  "id": "t-legacy",
  "category": "doc",
  "name": "옛 HTML 템플릿",

  "desc": "아직 HTML 인 템플릿입니다",
  "body": "<h1>[제목] 완료 보고</h1>\n",

}
```

```json
{
  "id": "t-morning",
  "category": "ritual",
  "name": "기본 모닝 데일리 템플릿",
  "rev": "morning",
  "icon": "sunrise",
  "format": "markdown",
  "desc": "아침에 씁니다",
  "body": "# 모닝 리포트 - [날짜]\n"
}
```

`save-template` 의 응답은 만들기와 고치기가 같은 모양이다. 저장이 어디에 무엇으로 끝났는지만 알리고, 부르는 쪽이 방금 보낸 본문은 안 돌려준다.

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `id` | 문자열 | 늘. 만들기면 이때 발급한 값이라, 부르는 쪽이 새 템플릿을 가리킬 길이 이 키뿐이다 |
| 2 | `action` | 문자열 | 늘. `created` 나 `updated` |
| 3 | `builtin` | 불리언 | 늘. 만들기는 늘 `false`, 고치기는 찾은 값 |
| 4 | `path` | 문자열 | 늘. `.withlog/templates/doc/<id>.md` |
| 5 | `warning` | 문자열 | 받은 `body` 에 들여쓴 블록이 있을 때만 |

`warning` 은 13장의 들여쓴 블록 경고와 같은 판정과 같은 문구이고, 저장된 값이 아니라 이번에 받은 `body` 로 짓는다. 본문을 안 준 고치기가 옛 본문의 들여쓰기로 경고를 받으면, 사용자는 자기가 방금 무엇을 잘못했는지 찾다 못 찾기 때문이다. 템플릿의 들여쓰기는 그 템플릿으로 쓰는 노트마다 번져서 노트 1개보다 무겁다. 문구는 이렇게 시작한다.

```
본문에 들여쓴 블록이 1곳 있어요(1번째 줄 표) — 표·콜아웃·제목·하위 페이지 카드는 줄 맨 앞에서 시작해야 편집기가 변환합니다.
```

위 예시 값의 만들기 응답은 이렇다(예시 값).

```json
{
  "id": "tpl-msciohji-6b623625",
  "action": "created",
  "builtin": false,
  "path": ".withlog/templates/doc/tpl-msciohji-6b623625.md"
}
```

`delete-doc-template` 의 응답은 `id` (받은 값)와 `removed` (실제로 지운 vault 상대 경로의 배열) 차례다. 없는 id면 `removed` 가 `[]` 다. 참거짓이 아니라 배열인 까닭은 같은 id의 파일이 2개 남은 상태가 실재해서, 몇 개를 지웠는지가 실제 정보이기 때문이다. 픽스처 vault에서 `delete-doc-template tpl-seeded` 를 부르면 이렇다(예시 값).

```json
{
  "id": "tpl-seeded",
  "removed": [
    ".withlog/templates/doc/tpl-seeded.md"
  ]
}
```

같은 vault에서 `delete-doc-template tpl-halfmoved` 는 `.md` 와 `.html` 을 모두 지워서 `removed` 가 `.withlog/templates/doc/tpl-halfmoved.md`, `.withlog/templates/doc/tpl-halfmoved.html` 차례의 2개다(예시 값). `m-plan` 은 빌트인이라, `t-morning` 은 리추얼이라 `WL-400` 이다.

## 24.7 모양이 다른 대상

| 대상 | 읽기 | 쓰기 | 픽스처 |
|---|---|---|---|
| 옛 HTML 문서 템플릿(`.html`, `<!--withlog` 울타리) | `format` 이 `html`. 본문은 `-->` 뒤의 HTML | 고치면 `<id>.md` 를 쓰고 `<id>.html` 을 지운다. 본문을 안 주면 HTML 본문이 그대로 마크다운 파일로 옮겨진다 | `t-legacy` |
| `.json` 문서 템플릿 | `format` 이 `json`. `---` 나 `<!--withlog` 울타리를 들어야 템플릿이고, 본문은 울타리 뒤 글자 그대로 | 고치면 `<id>.md` 를 쓰고 `<id>.json` 을 지운다 | 없음 |
| 같은 id의 `.html` 과 `.md` (반쪽 이관) | 목록에 2벌이고 `html` 이 앞. 단건은 `.html` | 고치기의 바탕이 `.html` 의 값이라 `.md` 의 새 내용 위에 옛 값을 덮어쓴 뒤 `.html` 을 지운다. `builtin: false` 면 지우기는 2개 모두 지운다 | `tpl-halfmoved` |

`tpl-halfmoved` 를 `save-template id=tpl-halfmoved 'name=고친 이름'` 으로 고치면, 픽스처의 `.md` 에 있던 `새 본문입니다` 와 `# 새 본문` 이 사라지고 `.withlog/templates/doc/tpl-halfmoved.md` 가 아래 바이트에 줄바꿈 1개를 더한 글이 되고, `.html` 은 지워진다(예시 값). 응답은 `{"id": "tpl-halfmoved", "action": "updated", "builtin": false, "path": ".withlog/templates/doc/tpl-halfmoved.md"}` 모양이다.

```markdown
---
id: tpl-halfmoved
name: 고친 이름
type: build
format: markdown
desc: 옛 본문입니다
builtin: false
---
<h1>옛 본문</h1>
```

반쪽 이관 상태는 고치기가 `.md` 를 쓰고 `.html` 을 지우기 전에 죽었을 때 생긴다. 그때 같은 명령을 다시 보내면 위 규칙으로도 의도한 결과가 나온다. 바탕이 된 `.html` 의 값이 그 명령이 처음 섞으려던 값과 같기 때문이다. 다른 칸을 고치는 새 명령이면 `.md` 에만 있던 값이 사라진다.

## 24.8 변형 명령 save-ritual-template

`save-ritual-template` 은 `save-template` 의 리추얼 짝이고, 리추얼 템플릿 1개의 이름, 설명, 본문을 고친다. 명령 표면에만 있다. 만들기는 없다. 리추얼 종류가 `morning`, `evening`, `weekly` 3개로 닫혀 있어서 사용자가 4번째 종류를 만들 수 없고, 새 종류를 더하는 일은 제품의 씨앗 템플릿(23장)이 하기 때문이다.

```
save-ritual-template <리추얼 템플릿 id> [name=<이름>] [desc=<설명>] [body=<본문>]
```

- 자리 인자는 1칸이고 24.5의 규칙으로 읽은 id를 받는다. 곧 프론트매터 `id` 이고, 그 키가 없으면 파일 이름에서 `.md` 를 뗀 값이다. 파일 이름은 `<rev>.md` 라서 id와 다를 수 있다. 옵션은 `name`, `desc`, `body` 3개이고 모두 선택이다.
- 준 칸은 받은 그대로 바꾼다. 빈 `desc` 와 빈 `body` 는 지우기다.
- 준 `name` 이 빈 글이거나 공백뿐이면 `WL-400 템플릿 이름이 비었다` 다.
- 안 준 칸은 읽은 값을 다시 적는다. 이름은 앞뒤 공백을 뗀 값이나 id로 물러선 값이고, 설명은 읽은 글 그대로, 본문은 울타리 뒤에서 읽은 글이다. `save-template` 고치기와 같은 규칙이다.
- `rev`, `icon`, `format` 은 안 받는다. 그 이름으로 주면 파서가 모르는 옵션으로 세운다(`쓸 수 있는 것은 [body, desc, name] 뿐이다`). `rev` 는 파일 이름을 정해서 받으면 호출 1번이 남의 파일을 덮을 수 있고, `icon` 은 고칠 화면이 없고, `format` 은 옛 HTML 리추얼을 지켜야 하기 때문이다.

검사와 일은 이 차례다.

1. 문법을 본다(24.4의 1번부터 4번).
2. 워크스페이스 표식을 보고 노트 색인을 맞춘다.
3. 자리 인자가 비었거나 공백뿐이면 `WL-400 인자가 하나 필요하다: save-ritual-template <리추얼 템플릿 id> [name=<이름>] [desc=<언제 쓰는 양식인지>] [body=<본문>]` 이다.
4. id 모양(`^[A-Za-z0-9._-]{1,128}$`)을 보고, 다음에 이름을 본다. 모두 `WL-400` 이다.
5. 그 id로 처음 찾은 템플릿이 리추얼이 아니거나 없으면 `WL-404 Template not found: <id>` 다. 문서 템플릿 id를 줘도, 같은 id의 문서 템플릿에 가려진 리추얼을 줘도 「없다」다.
6. 폴더를 1번 더 훑어 읽은 리추얼 가운데 찾은 템플릿과 `rev` 가 같은 것을 센다. 같은 id의 문서 템플릿에 가려진 리추얼과 id가 겹친 리추얼도 세고, `rev` 는 읽을 때 기본값으로 메운 값(빠지거나 틀리면 `morning`)으로 센다. 못 읽어 건너뛴 파일은 안 센다. 센 수가 1이 아니면(찾은 템플릿 자신이 늘 들어서 곧 2 이상이면) 아무것도 안 쓰고 `WL-400` 이다. 문구는 `같은 rev 를 든 리추얼 템플릿이 <n>건이라 저장하지 않는다. 파일 이름이 rev 라서 서로를 덮는다: rev=<rev>` 다.
7. 받은 칸과 읽은 값을 섞어 `.withlog/templates/ritual/<rev>.md` 에 원자적으로 쓴다.

6번이 있는 까닭은 파일 이름이 `rev` 라서, 같은 `rev` 를 든 리추얼이 2개면 어느 쪽을 저장해도 같은 파일에 써서 나중에 쓴 쪽이 먼저 쓴 쪽을 조용히 먹기 때문이다. 템플릿에는 휴지통이 없어 먹힌 쪽을 되살릴 길이 없으니 쓰지 않고 세운다. 사용자는 파일을 열어 `rev` 를 고치면 된다.

파일 바이트는 `---\n`, YAML, `---\n`, 본문이다. YAML의 키 차례는 `id`, `rev`, `name`, `icon`, `format`, `desc` 이고 6개 키를 늘 적는다. `rev`, `icon`, `format` 은 읽은 값 그대로이고, 읽을 때 기본값으로 메운 값도 그대로 적힌다. 포맷이 `html` 이어도 울타리는 `---` 다. 옛 구현이 포맷과 상관없이 `---` 로 썼고 엔진이 그 바이트를 그대로 잇기 때문이다. 읽기는 울타리를 내용으로 고르므로(24.5) 이 파일도 읽힌다. 픽스처 vault에서 `save-ritual-template t-morning 'name=내가 고친 모닝'` 을 부르면 `.withlog/templates/ritual/morning.md` 가 아래 바이트에 줄바꿈 1개를 더한 글이 된다(예시 값).

```markdown
---
id: t-morning
rev: morning
name: 내가 고친 모닝
icon: sunrise
format: markdown
desc: 아침에 씁니다
---
# 모닝 리포트 - [날짜]
```

응답은 `save-template` 과 같은 키 4개와 선택 키 `warning` 이다. `action` 은 늘 `updated` 이고 `builtin` 은 늘 `false` 다. 앱은 리추얼 행을 빌트인처럼 다루지만 여기서 참을 내지 않는 까닭은, 리추얼을 못 지우는 진짜 이유가 빌트인이라서가 아니라 지우는 길이 없어서이고 그 2가지를 값 1개에 섞지 않으려는 데 있다. `warning` 은 받은 `body` 로 짓는 24.6의 경고와 같다.

```json
{
  "id": "t-morning",
  "action": "updated",
  "builtin": false,
  "path": ".withlog/templates/ritual/morning.md"
}
```

이 명령은 묶음이 안 덮고, 위 규칙은 코드 읽기로 확인했다.

## 24.9 받아들임 묶음과 얼어 있는 특이점

묶음이 덮는 것은 `list_templates` 9건(조건 없음, 갈래 2가지, 유형 6가지)과 `get_template` 6건(픽스처 템플릿 5개와 틀린 id 1건)이다. 모두 도구 표면이고, 틀린 id `t-없는템플릿` 은 모양 검사의 `WL-400` 인데 묶음은 종료 코드 3과 빈 stdout만 맞댄다. 명령 표면, `bodies`, 봉투와 stderr, 못 읽은 파일의 이유, 읽을 때의 기본값, 쓰기 명령 3개, WL 번호는 안 덮는다.

지금 엔진의 특이점이고, 지킬지 고칠지는 부록 D에서 정한다.

1. 템플릿 폴더는 충돌 사본 이름을 거르지 않는다. 동기화 도구가 만든 `m-plan (conflicted copy).md` 도 템플릿으로 읽혀 같은 id가 2벌 나온다. 노트(1.2)와 회고(25.5)는 거른다.
2. 문서 폴더의 아무 `.md`, `.html`, `.json` 파일이나 후보라서, 프론트매터 없는 `README.md` 1개가 목록을 늘 봉투로 바꾼다. 이름이 점으로 시작하는 파일도 후보라서 동기화 도구가 남긴 `.x.md` 같은 파일도 대개 못 읽은 파일로 센다.
3. 반쪽 이관 상태의 고치기는 `.html` 의 옛 값을 바탕으로 `.md` 를 덮는다(24.7).
4. 파일 이름이 id와 다른 템플릿은 고치면 2벌이 되고, 옛 파일의 이름이 차례에서 앞이면 단건이 계속 옛 값을 낸다. 같은 템플릿은 `builtin: false` 여도 지우기가 그 파일을 못 지운다.
5. 옛 HTML 템플릿을 본문 없이 고치면 HTML 본문이 `format: markdown` 파일에 담긴다.
6. 읽을 때 기본값으로 메운 값이 다음 쓰기에서 파일에 박힌다. 빈 이름은 id로, 모르는 `type` 은 `build` 로, 빠진 `builtin` 은 `true` 로, 모르는 `rev` 는 `morning` 으로, 틀린 `icon` 은 기본 아이콘으로, `markdown` 이 아닌 리추얼 `format` (`json` 포함)은 `html` 로 적힌다. 모르는 키는 사라진다.
7. `builtin: 'false'` 처럼 따옴표로 감싼 값은 빌트인으로 읽혀 그 템플릿을 못 지운다. 반대로 따옴표 없는 `builtin: no` 는 사용자 템플릿이다.
8. `type` 은 파일에서 읽을 때 대소문자를 가려서 `Plan` 이 `build` 가 되고, 인자로 받을 때는 안 가려서 `PLAN` 이 `plan` 이 된다.
9. 쓰기에 크기 상한이 없다. 명령 표면으로 1,000,000바이트를 넘는 본문을 쓰면 다음 훑기에서 그 템플릿이 빠진다. 도구 표면은 본문이 200,000 UTF-16 코드 단위를 넘을 때(200,001부터) 거절한다.
10. `save-ritual-template` 은 `<rev>.md` 에 써서, 손으로 만든 `custom.md` (`rev: weekly`) 같은 리추얼을 고치면 `weekly.md` 가 새로 생기고 2개 모두 남는다. 그 뒤로는 「같은 rev 2건」으로 거절된다. 같은 `rev` 의 못 읽는 `<rev>.md` 가 있으면 그 파일은 이 쓰기에 조용히 덮인다.
11. 문서 템플릿과 같은 id를 든 리추얼은 `save-ritual-template` 이 못 찾아 `WL-404` 다. 그 리추얼은 「같은 rev」를 셀 때는 들어간다.
12. 리추얼과 빌트인을 지우려는 호출이 `WL-409` 가 아니라 `WL-400` 이다.
13. 들여쓴 블록 경고 문구가 템플릿 저장에도 `update_doc` 으로 다시 저장하라고 적는다.
14. 쓰기 3개가 쓸모없는 노트 색인 맞추기를 먼저 하고, 그것이 실패하면 템플릿 저장도 실패한다.
15. 읽을 때 `name` 은 다듬고 `desc` 는 안 다듬는다. 만들기의 `name` 은 다듬어 저장하고 고치기의 `name` 은 받은 그대로 저장하므로, 고치기로 `' a '` 를 주면 파일에는 `name: " a "` 가 남고 목록과 단건에는 `a` 가 나온다. 이름 없이 다시 고치면 `name: a` 로 바뀐다.
16. 템플릿 파일 1개의 프론트매터에 그 타입의 값으로 못 바꾸는 명시 태그(`id: !!int abc`, `name: !!float x`, Base64가 아닌 `!!binary`)가 있으면, 그 파일만 건너뛰지 않고 훑기 전체가 예상 밖 실패로 선다(6.6). 그래서 `list-templates`, `get-template`, `save-template` 고치기, `delete-doc-template`, `save-ritual-template`, `reindex` 가 모두 실패하고, 폴더를 안 훑는 `save-template` 만들기만 돈다. 문법 오류나 별칭 상한 초과는 그 파일만 건너뛰는데 이 경우만 다른 것이 결함이고, 노트의 같은 결함은 1.15의 6번이다(코드 읽기로 확인, 실행하지는 않았다).
17. 짝 없는 서로게이트가 본문에서는 `?` 로 바뀌어 사라지고 이름과 설명에서는 탈출되어 지켜진다(24.5). 회고는 본문까지 지킨다(25.5).
18. 파일 이름을 유니코드 정규화 없이 견줘서, 같은 한글 이름의 NFC 파일과 NFD 파일은 다른 파일로 훑고 차례도 코드 단위가 정한다.

확인 못 한 것도 있다. 템플릿 폴더 목록을 못 읽는 경우(권한)에 빈 폴더로 보는 것은 코드로만 확인했고 실행해 보지는 않았다. 16번과 17번도 실행해 보지 않았다.
