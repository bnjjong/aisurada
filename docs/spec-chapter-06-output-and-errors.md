# withlog 1부 vault 엔진 설명서 > 6장 출력 규약과 실패

이 장은 엔진이 내는 바이트와 종료 코드를 정한다. 성공의 stdout, 조건부 키와 봉투, stderr의 구성, 종료 코드와 WL 코드, 예상 밖 실패의 답을 다룬다.

- 성공하면 stdout은 JSON 값 1개와 줄바꿈 1개이고, `JSON.stringify(값, null, 2)` 에 줄바꿈을 붙인 바이트와 같다. 실패하면 stdout은 0바이트다.
- 조건부 키는 값이 없으면 키째 빠진다. 1부에서 `null` 을 싣는 자리는 3곳뿐이다.
- 실패는 stderr의 `WL-<번호>` 줄과 종료 코드로 알린다. `WL-400`, `WL-404`, `WL-409`, `WL-500` 은 종료 코드 3이고 `WL-412` 는 5다. 이름을 못 찾거나 vault가 없으면 WL 코드 없이 2다.
- 예상 밖 실패는 serve 모드에서 종료 코드 3과 오류 코드 칸 0이고, 단발 모드에서는 JSON 없이 비정상 종료한다(코드 읽기로는 1).
- **근거**: stdout 바이트와, 실패의 종료 코드 3과 빈 stdout은 묶음이 잰다. WL 번호와 stderr 문구는 묶음이 아직 안 재서(`expect.wl` 칸이 0건이다) 코드 읽기로 확인했다.

## 6.1 stdout 바이트

성공한 명령의 stdout은 JSON 값 1개와 LF 1개다. 값은 명령마다 객체이거나 배열이다. 엔진은 값을 다 지은 뒤에 한꺼번에 내고, 실패하면 1바이트도 안 낸다. 부르는 쪽이 받은 바이트를 그대로 붓기 때문에, 반쯤 쓴 JSON이 나가면 안 된다.

| 항목 | 규칙 |
|---|---|
| 인코딩 | UTF-8, BOM 없음 |
| 들여쓰기 | 공백 2칸. 깊이마다 2칸씩 는다 |
| 줄바꿈 | LF만 쓴다. CR은 없다 |
| 키와 값 사이 | `": "` (콜론과 공백 1칸) |
| 원소 사이 | `,` 뒤에 줄바꿈 |
| 빈 배열과 빈 객체 | `[]`, `{}` 로 1줄에 쓴다 |
| 숫자 | 1부 응답의 숫자는 모두 정수이고 10진으로 쓴다. 지수와 소수점이 없다 |
| 끝 | 마지막 `}` 나 `]` 뒤에 LF 1개 |

문자열은 큰따옴표로 감싸고 아래 글자만 탈출한다. 나머지는 UTF-8 그대로 쓴다. 그래서 한글, `/`, `U+007F`, `U+2028`, `U+2029`는 탈출 없이 나간다.

| 글자 | 쓰는 꼴 |
|---|---|
| `"` | `\"` |
| `\` | `\\` |
| `U+0008` | `\b` |
| `U+0009` | `\t` |
| `U+000A` | `\n` |
| `U+000C` | `\f` |
| `U+000D` | `\r` |
| 그 밖의 `U+0000`~`U+001F` | `\u` 와 소문자 16진 4자리(`\u001f`) |

이 규칙은 JavaScript `JSON.stringify` 와 같다. 그래서 1부 응답은 `JSON.stringify(값, null, 2) + "\n"` 과 바이트까지 같고, 묶음이 이 꼴로 1부 성공 케이스 439건을 잰다. 갈리는 자리는 2가지다.

- **짝 없는 서로게이트**: 엔진은 탈출하지 않고 UTF-8로 바꾸는데, 그 변환이 짝 없는 서로게이트의 UTF-16 코드 단위 1개마다 `?` (0x3F) 1바이트를 낸다. 높은 서로게이트 바로 뒤에 낮은 서로게이트가 오면 짝이라 정상 4바이트다. `JSON.stringify` 는 `\udXXX` 로 탈출해서 바이트가 다르다(코드 읽기로 확인). 파일에 쓸 때도 같은 변환이라 `?` 가 된다(7.4). 이런 값은 도구 JSON의 `\u` 탈출로만 들어온다(5.4).
- **실수**: 엔진은 `2.0` 처럼 쓰고 JavaScript는 `2` 로 쓴다. 1부 응답에는 실수가 없고, 4부 `read-session` 의 `seconds` 만 실수라 묶음이 그 3건을 글 그대로 얼렸다(32장).

단발 모드와 serve 모드의 stdout 바이트는 같다. 엔진이 결과를 글자로 지은 뒤 모드마다 내보내기만 달리하기 때문이다. serve 모드는 그 글자를 UTF-8 바이트로 바꿔 응답 프레임에 싣고(4.2), 단발 모드는 JVM의 표준 출력 스트림으로 쓴다. 단발 모드의 그 스트림은 인코딩을 따로 못박지 않아서 로캘을 탄다. 묶음은 `LANG` 과 `LC_ALL` 을 `en_US.UTF-8` 로 주고 돌려서 UTF-8을 잰다. 다른 로캘에서의 바이트는 재지 않았다. 다시 짓는 구현은 로캘과 상관없이 UTF-8을 낸다.

픽스처 vault에서 `get_report '{"id":"rv-evening-2026-06-04"}'` 의 stdout은 아래 바이트에 LF 1개다. 묶음이 잰 값이다.

```json
{
  "id": "rv-evening-2026-06-04",
  "kind": "evening",
  "date": "2026-06-04",
  "body": "픽스처에 미리 있는 저녁 회고.",
  "memo": null
}
```

## 6.2 키 차례와 있고 없음

응답의 모양은 명령마다 정해져 있고(명령 장의 N.6), 그 모양은 아래 규칙을 함께 따른다. 응답의 키 차례가 계약이라서 같은 값이어도 차례가 다르면 다른 바이트다.

1. 응답 모양마다 키 차례가 정해져 있고 같은 키가 2번 나오지 않는다.
2. 값이 없거나 기본값인 조건부 키는 키째 뺀다. `null` 이나 빈 글로 채우지 않는다. 옛 구현이 그렇게 냈고 앱과 묶음이 그 모양에 맞춰져 있어서, 늘 실으면 모든 응답이 어긋난다. 그리고 「대목이 없다」와 「대목이 비었다」는 다른 뜻이다.
3. 출력 층은 값을 다듬거나 고치지 않는다. 저장된 값과 계산한 값을 그대로 낸다.
4. 열거값은 소문자로 쓴다(`"type": "build"`, `"format": "markdown"`, `"matchedIn": "meta"`, `"kind": "direct"`).

`null` 을 싣는 자리는 1부에 3곳이다. 이 3곳은 2번 규칙의 예외다. 4부 응답은 `null` 을 더 싣는다(32장).

| 자리 | 언제 | 이유 |
|---|---|---|
| `get_report` 의 `body`, `memo` | 그 칸이 없을 때 | 회고 1건 읽기는 칸을 늘 싣고 값이 없으면 `null` 로 둔다. 묶음이 `"memo": null` 을 잰다 |
| `list-reports bodies=true` 원소의 `body`, `memo` | 그 칸이 없을 때 | 실어 온 자료가 1건 읽기와 같아서 같은 규칙을 따른다 |
| `evaluate_doc` 의 `evaluation` | `clear` 로 평가를 지웠을 때 | 지웠다는 결과를 키로 알린다(15장) |

불리언 키는 3갈래다(코드 읽기로 확인).

| 갈래 | 키 |
|---|---|
| 늘 싣고 참이나 거짓이다 | `agendaCreated` (`create_doc`, 저장한 `plan_day`), `renamed`, `changed`, `removed` (`link_docs` 가 바꾼 응답), `saved`, `hasBody`, `hasMemo`, `builtin` (템플릿 저장 응답과 문서 템플릿 행. 리추얼 템플릿 행에는 키가 없다), `markerStripped`, `cardRemoved`, `sharded`, `applied`, `ok`, `stamped` (`check-notes` 항목), `set_favorite` 의 `favorite`, `init-workspace` 의 `created` |
| 참일 때만 싣고 거짓이면 키가 없다 | 노트 1건과 노트 목록 원소의 `favorite`, 검색 봉투의 `truncated`, `delete_doc` 의 `wasFavorite`, `get-agenda-facts` 의 `tooLargeToEdit` |
| 그 키를 싣는 응답 모양에서 늘 true 다 | 회고를 지운 `save_report` 의 `deleted`, `delete_sub_note` 의 `deleted`, `restore_doc` 의 `restored`, `purge_doc` 의 `purged` |

`init-workspace` 의 `created` 는 노트 시각 `created` (문자열)와 이름만 같은 불리언이다. 이름이 같아도 응답 모양마다 타입이 다른 키가 더 있다. `empty-trash` 의 `purged` 는 불리언이 아니라 지운 항목 수(정수)이고, `reindex` 의 `removed` 는 색인에서 뺀 노트 수(정수)이고, `delete-doc-template` 의 `removed` 는 지운 파일의 vault 상대 경로 배열이다.

배열은 1건 읽기와 목록의 원소가 다르다. 노트와 하위 노트 1건 읽기는 `links` 와 `tags` 를 비어도 `[]` 로 싣는다. 1건을 통째로 읽는 자리에서는 「없다」와 「안 봤다」를 가를 수 있어야 하기 때문이다. 노트 목록과 검색의 원소는 `links` 를 늘 싣고 `tags` 는 비면 뺀다. 하위 노트 목록의 원소는 2개 모두 늘 싣는다. 검색 봉투의 `docs` 는 비어도 `[]` 다.

시각과 날짜 글자는 거의 모든 응답에서 아래 4가지 꼴만 쓴다.

| 꼴 | 모양 | 예 | 쓰는 키 |
|---|---|---|---|
| 노트 시각 | `yyyy-MM-ddTHH:mm:ss` 와 오프셋 `±hh:mm`. 오프셋 0은 `Z`. 초는 늘 찍고 초 아래는 버린다 | `2026-06-18T12:30:00+09:00` | 노트와 하위 노트의 `created`, 휴지통의 `created`, 이력의 `takenAt` |
| 순간 | UTC `yyyy-MM-ddTHH:mm:ss.SSSZ`. 밀리초 3자리 | `2026-06-18T04:00:00.000Z` | `evaluation.at`, `trashedAt` |
| 날짜 | `yyyy-MM-dd` | `2026-06-18` | `date`, `facts-brief` 의 `from` 과 `to` |
| 시분 | `HH:MM` | `12:30` | `time` |

예외는 2가지다. 코멘트의 `createdAt` 과 `editedAt`, 도장의 `editedAt` 은 이 꼴로 다시 쓰지 않고 파일에 적힌 글자를 그대로 낸다(1.10, 1.12). `check-notes` 항목의 `lastChangeAt` 과 `lastCommentAt` 은 Java `OffsetDateTime` 의 기본 글자다(30장). 그 꼴은 초가 0이면 초를 빼고, 초 아래가 있으면 3자리, 6자리, 9자리 가운데 맞는 자릿수로 적고, 오프셋 0은 `Z` 다(코드 읽기로 확인).

같은 회고가 목록과 1건 읽기에서 다른 모양으로 나가는 것이 2번 규칙과 `null` 예외의 예다. `list_reports '{}'` 는 아래 배열을 낸다(묶음이 잰다). 1건 읽기는 6.1의 객체다.

```json
[
  {
    "id": "rv-evening-2026-06-04",
    "kind": "evening",
    "date": "2026-06-04",
    "hasBody": true,
    "hasMemo": false
  }
]
```

## 6.3 봉투

봉투는 결과 목록을 감싸는 객체다. 엔진에는 봉투가 3가지 있고, 그 밖에 결과 객체에 붙는 `warning` 키가 있다.

### incomplete 봉투

폴더 1개나 휴지통 매니페스트 1개만 읽어 목록을 내는 명령 3개가 쓴다. 못 읽은 파일이나 항목이 0개면 목록이 배열 그대로 나가고, 1개라도 있으면 그때만 객체로 감싼다. 늘 감싸면 읽는 쪽이 모두 깨지고, 늘 배열이면 못 읽은 파일이 있다는 사실을 알릴 자리가 없기 때문이다.

| 명령 | 목록 키 |
|---|---|
| `list_reports`, `list-reports` | `reports` |
| `list_templates`, `list-templates` | `templates` |
| `list_trash`, `list-trash` | `trash` |

감쌀 때의 모양은 이렇다. 아래는 회고 파일 2개를 못 읽은 「예시 값」이다.

```json
{
  "reports": [],
  "incomplete": {
    "skipped": 2,
    "conflicts": 0,
    "note": "일부 파일을 읽지 못했어요(형식 오류·크기 초과) — 목록이 불완전할 수 있어요."
  }
}
```

`skipped` 는 못 읽은 파일 수(휴지통은 못 읽은 항목 수)이고 `conflicts` 는 늘 0이다. 이 명령들은 자리 1곳만 훑어서 충돌 사본을 따로 세는 갈래가 없고, 회고 폴더의 충돌 사본은 `skipped` 에 든다. `note` 는 위 글자 그대로이고 stdout 바이트의 일부라 1글자도 바뀌면 안 된다. 어느 파일을 왜 못 읽었는지는 stdout에 안 싣고 stderr의 진단 줄로 낸다(6.4). 옛 구현의 봉투에 개수만 있었기 때문이다. 묶음의 픽스처에는 못 읽는 회고와 템플릿과 휴지통 항목이 없어서, 이 봉투는 코드 읽기로만 확인했다. 노트 목록과 검색은 이 봉투를 안 쓴다. 못 읽은 노트는 `reindex` 의 `skipped` 에 나온다(8.4).

### 검색 봉투

`search_docs` 와 `search-docs` 는 결과가 0건이어도 늘 객체를 낸다. 검색은 얼마나 찾았고 얼마나 돌려줬는지를 함께 말해야 하기 때문이다. 그 값이 없으면 부르는 쪽은 받은 것이 전부인 줄 알고, 찾던 노트가 상한 밖에 있어도 없다고 결론을 낸다.

| 차례 | 키 | 타입 | 있는 조건 |
|---|---|---|---|
| 1 | `query` | 문자열 | 늘. 실제로 찾은 검색어. 도구 표면과 `query=` 는 다듬은 값이고, 명령 표면의 자리 인자는 받은 글자 그대로다 |
| 2 | `total` | 정수 | 늘. 자르기 전의 건수 |
| 3 | `returned` | 정수 | 늘. `docs` 의 원소 수 |
| 4 | `truncated` | `true` | `total` 이 `returned` 보다 클 때만 |
| 5 | `hint` | 문자열 | `truncated` 와 함께만 |
| 6 | `docs` | 배열 | 늘 |

`hint` 의 글자는 `agenda·type·tag·dateFrom으로 좁히거나 limit을 올리세요` 이고 stdout 바이트의 일부다. 원소의 모양은 10장이다. 묶음은 이 봉투를 37건 재지만 잘린 케이스가 없어서, `truncated` 와 `hint` 는 코드 읽기로만 확인했다. 묶음의 `search_docs/equals-sign` (`{"query":"a=b"}`) 은 아래 바이트에 LF 1개를 낸다.

```json
{
  "query": "a=b",
  "total": 0,
  "returned": 0,
  "docs": []
}
```

### 코멘트 봉투

노트와 하위 노트의 코멘트는 `state` 로 시작하는 봉투에 담는다. `absent`, `loaded`, `unreadable` 3갈래이고 모양은 11.6과 19장이다.

### warning 키

쓰기 응답 몇 개는 사람이나 AI가 알아야 할 일을 `warning` 문자열 1개로 싣는다. 경고가 여럿이면 아래 차례로 LF 1개를 끼워 잇고, 1개도 없으면 키를 뺀다. 차례가 계약이다.

| 응답 | 이어 붙이는 차례 | 장 |
|---|---|---|
| `create_doc` | 같은 제목, 들여쓴 블록, 제목과 첫 헤딩 불일치, U+FFFD, 원본 요청 절 없음(도구 표면만) | 13장 |
| `update_doc` | 옛 노트 삭제 실패, 들여쓴 블록(본문을 줬고 html 노트가 아닐 때), 제목과 첫 헤딩 불일치(markdown 노트만. 본문을 안 줘도 지금 본문으로 본다), U+FFFD(본문을 줬을 때) | 14장 |
| `create_sub_note` | 들여쓴 블록, 제목과 첫 헤딩 불일치, U+FFFD | 17장 |
| `update_sub_note` | 들여쓴 블록, U+FFFD. 2개 모두 본문을 줬을 때만 | 17장 |
| `save_template`, `save-ritual-template` | 들여쓴 블록(본문을 줬을 때) | 24장 |
| `link_docs` | 대상 노트가 없음 | 15장 |
| `delete_doc` | 즐겨찾기를 잃음 | 26장 |

경고 글자는 8가지이고 부록 C.15에 모았다. `plan_day` 의 같은 제목 경고만은 응답에 안 싣고 stderr의 진단 줄로 낸다(6.4). 옛 `plan_day` 응답에 그 키가 없었기 때문이다.

## 6.4 stderr

stderr는 사람이 읽는 자리다. 실행 형태에 따라 담기는 것이 다르다.

| 실행 형태 | stderr에 나오는 차례 |
|---|---|
| 단발 모드 | 엔진이 뜨며 남기는 로그 줄, 실행 중의 로그 줄, 진단 줄, WL 줄 |
| `wl-cli` 를 거친 serve 모드 | `wl-cli` 의 안내 줄, 엔진의 진단 줄, WL 줄, `wl-cli` 의 하루 청소 줄 |

로그 줄은 Spring Boot의 기본 콘솔 꼴이고 계약이 아니다. 단발 모드의 로그 줄은 로그 설정이 UTF-8로 못박고, 진단 줄과 WL 줄은 JVM 표준 오류 스트림의 인코딩을 탄다. serve 모드의 로그는 응답에 안 실리고 사이드카 로그 파일로 간다(3.4). `wl-cli` 의 안내 줄은 사이드카가 뜨기를 기다리거나 다시 띄울 때와 동시 상한을 지키려고 다른 사이드카를 내릴 때 나오고, 하루 청소 줄은 응답을 다 흘려보낸 뒤에 나온다(3.3, 3.5). 문구는 부록 C.17이다.

진단 줄은 엔진이 결과와 함께 stderr로 내는 줄이다. 성공(종료 코드 0)에도 나온다. 조용히 버리면 사용자가 그 파일을 고칠 수 없고, stdout에 실으면 옛 구현과 모양이 갈리기 때문에 이 자리에 둔다.

| 명령 | 진단 줄 |
|---|---|
| `list_trash`, `list_reports`, `list_templates` 와 명령 짝 | 못 읽은 항목이 있을 때. `<무엇> <n>건을 못 읽어 목록에서 뺐다.` 다음에 항목마다 `<자리> — <이유>` |
| `plan_day`, `plan-day` | 저장하다 같은 제목 노트를 만났을 때. 같은 제목 경고 글 1줄 |
| `shard-notes` | 이동을 중간에 세웠을 때 3줄. `apply=true` 로 옮긴 뒤 색인을 못 맞췄을 때 1줄 |
| `verify-shard` | 기준값과 다를 때 3줄 |

글자는 부록 C.16이다. `<무엇>` 은 휴지통 항목, 회고, 템플릿 가운데 1가지다. 진단 줄의 `<자리>` 와 `<이유>` 는 파일 자리와 이유 글을 바꾸지 않고 적어서, vault 안 파일 이름이 그대로 실린다.

WL 줄은 실패를 알리는 줄이고 `WL-<번호> <문구>` 꼴이다. 진단 줄 뒤에 붙고 LF로 끝난다. 문구가 여러 줄일 수 있다. `WL-412` 의 문구는 늘 3줄이고, 받은 값을 문구에 그대로 적는 실패는 그 값에 든 줄바꿈까지 싣는다.

묶음 실행기는 stderr에서 처음 맞는 `/\bWL-\d{3}\b/` 를 WL 번호로 읽는다. 플래그 없는 JavaScript 정규식이라 `\b` 와 `\d` 가 ASCII만 본다(묶음이 정한 규칙, 지금은 `expect.wl` 칸이 0건). serve 모드의 응답 프레임은 같은 번호를 오류 코드 칸에 따로 싣는다(4.2). 다시 짓는 엔진은 자기가 짓는 로그 문구와 진단 문구에 이 꼴의 글자를 쓰지 않는다. 받은 글자와 파일 이름은 지금 엔진처럼 바꾸지 않고 적는데, 그 글자에 `WL-123` 같은 꼴이 들면 처음 맞는 번호가 WL 줄의 번호가 아니게 된다. 지금 엔진도 같고 6.7의 11번에 둔다.

WL 번호 뒤의 문구는 계약이 아니다(0.2). 다만 선결 조건 거절 문구(7.2)는 부르는 쪽이 할 일을 글로 알려 주는 유일한 자리라, 고칠 때 그 뜻을 지킨다.

WL 줄이 없는 실패가 3가지 있다. 엔진이 뜨기 전에 vault가 없어 끝나면 stderr는 2줄이고 번호가 없다. 이름을 못 찾으면 안내 문구만 있다(부록 C.2). 예상 밖 실패는 6.6이다. `wl-cli` 가 자기 자리에서 vault 환경변수를 못 찾으면 `WL-400 WITHLOG_VAULT 환경변수가 없다. vault 폴더의 절대 경로를 넣고 다시 실행한다.` 1줄을 내고 종료 코드 2로 끝난다. 엔진의 2줄 안내와 문구가 다르다.

인코딩은 stdout과 같다. serve 모드는 UTF-8 바이트를 프레임에 싣고, 단발 모드는 위처럼 로그 줄만 UTF-8로 못박혀 있다.

## 6.5 종료 코드와 WL 코드

종료 코드는 부르는 쪽이 다음에 할 일을 고르는 값이다. 엔진은 0, 2, 3, 5를 내고, `wl-cli` 가 4를 더한다.

| 코드 | 뜻 | 내는 쪽 | 언제 | 부르는 쪽이 할 일 |
|---|---|---|---|---|
| 0 | 성공 | 엔진 | 명령이 끝까지 돌았다. 일부만 해낸 명령도 0이다(`shard-notes` 의 `stoppedAt`, `verify-shard` 의 `ok: false`, `empty-trash` 의 `failed`) | 응답을 읽는다. 일부 실패는 응답 값으로 가린다 |
| 2 | 부르는 법이 틀렸다 | 엔진, `wl-cli` | 이름을 못 찾음, vault가 없음. `wl-cli`는 모르는 이름, vault 환경변수 없음, 소켓 경로가 너무 김, 사이드카 jar 자리를 못 찾음(3.3) | 부르는 법을 고친다 |
| 3 | 명령은 맞는데 실행이 실패했다 | 엔진 | `WL-400`, `WL-404`, `WL-409`, `WL-500`, serve 모드의 예상 밖 실패 | WL 번호로 갈래를 가린다 |
| 4 | 사이드카에 못 붙었다 | `wl-cli`만 | 소켓이 없음, 사이드카를 못 띄움, 준비를 못 기다림, 프레임이 어긋남 | 사람을 부른다. 노트가 없다는 뜻이 아니다 |
| 5 | 선결 조건이 어긋나 아무것도 안 썼다 | 엔진 | `WL-412` | 다시 읽고 다시 얹은 뒤 부른다 |

3, 4, 5를 가르는 이유는 대응이 정반대이기 때문이다. 4를 3과 섞으면 래퍼가 「노트가 없다」와 「백엔드가 죽었다」를 못 가리는데, 앞의 것은 넘어갈 일이고 뒤의 것은 사람을 부를 일이다. 5를 3과 섞으면 「다시 읽고 다시 얹으면 되는 실패」를 문장에서 찾아야 한다.

엔진과 `wl-cli` 가 정한 종료 코드에 1은 없다. 1은 잡지 않은 예외로 프로세스가 끝날 때 JVM 실행기가 내는 값이다. 엔진에서는 단발 모드의 예상 밖 실패와 시작 실패가 그렇다(6.6). `wl-cli` 에서도 요청이 프레임 상한을 넘을 때(인자 64개 초과, 인자 1개가 1 MiB 초과, 4.1) 잡지 않은 예외로 1이 된다(코드 읽기로 확인, 실행 안 함). 세션 표식이 argv에 2칸을 더해서, 사용자 인자 63개도 표식이 붙으면 이 상한에 걸린다. `wl-cli report due` 가 내는 20은 0.1에서 뺀 자동 리포트 잡의 값이라 다루지 않는다.

WL 코드는 실패의 갈래이고, 명령이 아니라 실패의 종류가 번호를 정한다. 그래서 같은 종류의 실패는 어느 명령에서 나도 대체로 같은 번호다. 응답 프레임의 오류 코드 칸에는 같은 숫자가 실리고(4.2), 코드가 없으면 0이다. 아래 표의 갈래는 설계 의도이고, 실제로 어느 실패가 어느 번호인지의 정본은 부록 C의 번호다. 의도와 어긋나는 실패는 6.7의 1번부터 4번에 모았다.

| WL | 종료 | 갈래 | 대표 자리 | 다시 부르면 |
|---|---|---|---|---|
| `WL-400` | 3 | 값이 규칙을 어겼다 | 인자 문법(5.2, 5.4), 값 읽기(5.3), 식별자 모양(1.4), 워크스페이스 표식 없음(1.1), 빈 제목, 점수 범위, 뒤집힌 날짜 구간 | 같은 답이다. 인자를 고친다 |
| `WL-404` | 3 | 대상이 없다 | 색인에 없는 노트, 하위 노트, 회고, 템플릿, 휴지통 항목, 이름으로 못 찾은 아젠다, 샤드 매핑 파일 | 대상을 다시 찾는다. 이 갈래만 「새로 만들어도 된다」를 뜻한다 |
| `WL-409` | 3 | 지금 상태에서는 못 하는 일이다 | 기록 층(5.5), 못 읽는 코멘트 파일 위의 쓰기, markdown이 아닌 컨테이너의 카드와 마커 걷기, 저장 위치를 모르는 노트, 판 번호 범위 밖, 4부가 없는 판 | 같은 답이다 |
| `WL-412` | 5 | 부르는 쪽이 든 토큰이 지금 파일과 어긋났다 | 7.2 | 다시 읽고 다시 얹으면 된다 |
| `WL-500` | 3 | 파일을 다루다 실패했다 | 읽기, 쓰기, 옮기기, 지우기 실패, 저장 상한 초과, 폴더 이름 접미사 소진, 프론트매터 없는 파일에 쓰기, 옛 모양 노트에 쓰기 | 입출력 오류는 다시 부르면 지날 수 있다. 저장 상한, 옛 모양 노트, 프론트매터 없음은 같은 답이다 |

`WL-404` 만 「없다」를 뜻하는 것이 중요하다. 나머지 번호는 대상이 있는데 못 다룬 경우라, 그 위에 새로 쓰면 사용자 글을 잃는다. `wl-cli` 의 자동화가 이 갈림에 기댄다. 색인 DB(SQLite)를 다루다 난 오류는 `WL-500` 이 아니라 6.6의 예상 밖 실패다. 엔진이 DB 오류를 WL 갈래로 바꾸지 않기 때문이다(코드 읽기로 확인).

`wl-cli` 가 자기 자리에서 낸 실패는 표와 다르다. vault 환경변수가 없을 때, 소켓 경로가 103바이트를 넘을 때, 사이드카를 띄워야 하는데 jar 자리를 못 찾을 때는 `WL-400` 머리를 단 1줄을 쓰고 종료 코드 2로 끝난다(3.3, 부록 C.2).

묶음은 1부 실패 9건을 「종료 코드 3과 빈 stdout」으로 잰다. 번호와 문구는 안 재고, 아래 번호와 문구는 코드 읽기로 확인한 값이다.

| 케이스 | 인자 | WL | 문구 |
|---|---|---|---|
| `get_doc/missing` | `{"id":"nd없는노트"}` | `WL-400` | `노트 id 모양이 아니다: nd없는노트` |
| `get_report/missing` | `{"id":"rv-evening-1999-01-01"}` | `WL-404` | `Review not found: rv-evening-1999-01-01` |
| `get_sub_note/missing-child` | `{"parent":"ndfixture-00000001","id":"nd없는하위"}` | `WL-400` | `하위 노트 id 모양이 아니다: nd없는하위` |

## 6.6 예상 밖 실패

예상 밖 실패는 6.5의 WL 갈래 5개로 분류되지 않은 실패다. 프로그램의 결함이거나 엔진이 예상하지 못한 입력이다. 코드 읽기로 찾은 예는 프론트매터의 `mins: .nan` (1.15), 색인 DB가 내는 SQLite 오류, 아주 깊게 겹친 JSON 배열(5.4)이다. 엔진은 이 실패를 일부러 잡아 분류하지 않는다. 모르는 실패는 결함이라 단서(스택 트레이스)가 남아야 하기 때문이다.

serve 모드는 그 요청 1개만 실패로 답하고 계속 요청을 받는다.

| 칸 | 값 |
|---|---|
| stdout | 0바이트 |
| stderr | `사이드카 안에서 실패했다: <무엇>. 자세한 것은 사이드카 로그에 있다.` 와 LF |
| 상태 칸(종료 코드) | 3 |
| 오류 코드 칸 | 0(코드 없음) |

`<무엇>` 은 예외의 문구이고, 문구가 없거나 공백뿐이면 예외 종류의 짧은 이름(`StackOverflowError` 같은 것), 그것도 없으면 `알 수 없는 실패` 다. 그 요청에서 이미 쌓인 진단 줄은 버려진다. 스택 트레이스는 사이드카 로그 파일에 남는다. 이렇게 답하는 이유는, 연결을 그냥 끊으면 부르는 쪽이 응답도 오류도 못 받은 채 기다리기 때문이다. `wl-cli` 는 받은 상태 3을 그대로 종료 코드로 낸다.

단발 모드는 JSON을 안 내고 비정상 종료한다. stdout은 0바이트이고, stderr에는 Spring Boot의 `Application run failed` 오류 로그와 스택 트레이스가 남는다. 그 요청에서 쌓인 진단 줄은 안 나온다. 종료 코드는 엔진이 정하지 않고, main이 예외로 끝날 때 java 실행기가 내는 1이다(코드 읽기로 확인, 실행 안 함).

다시 짓는 구현은 단발 모드의 예상 밖 실패와 시작 실패를 종료 코드 1로 끝낸다. 지금 엔진과 같은 값이고, 부르는 쪽이 아는 0, 2, 3, 4, 5 어느 것과도 겹치지 않아야 「분류 안 된 실패」로 읽히기 때문이다. stdout은 0바이트이고, stderr에는 WL 줄을 쓰지 않는다. WL 번호로 갈래를 가리는 쪽이 이 실패를 분류된 실패로 오해하지 않게 하려는 규칙이다. 사람이 원인을 찾을 글은 남기되 그 모양은 계약이 아니다.

엔진이 뜨지 못한 실패도 같은 갈래다. vault 값이 비었거나(`--withlog.vault=`) 폴더가 아니거나, 색인 DB 자리를 못 정하거나, 색인 스키마를 못 올리면 엔진이 시작 단계에서 선다. 단발 모드는 위와 같이 끝나고, stderr의 스택 트레이스 안에 `vault 뿌리가 폴더가 아니다: <경로>` 같은 문구가 든다(부록 C.13). serve 모드는 사이드카가 끝내 준비되지 않아서, `wl-cli` 가 기다리다 종료 코드 4로 끝난다(3.3). `WITHLOG_VAULT` 가 없거나 공백뿐이고 `--withlog.vault=` 로 시작하는 칸도 없는 경우만은, 엔진이 뜨기 전에 알아보고 2줄 안내와 종료 코드 2로 끝낸다(1.1).

쓰기 도중에 예상 밖 실패가 나면 그 앞에서 끝난 파일 쓰기는 디스크에 남는다. 파일 1개의 쓰기는 원자적이지만 명령 전체는 아니다(7.4). 응답이 없으니 부르는 쪽은 다시 읽어 상태를 확인해야 한다. 묶음은 이 갈래를 1건도 안 잰다.

## 6.7 얼어 있는 특이점

다시 지을 때 지킬지 고칠지는 부록 D에서 정한다. 번호의 정본은 부록 C이고, 아래는 6.5의 갈래 정의와 어긋나는 자리다.

1. 「지금 상태에서는 못 하는 일」인데 `WL-409` 가 아니라 `WL-400` 인 거절이 있다. 노트가 남은 아젠다 지우기, 아젠다가 남은 프로젝트 지우기, 빌트인 템플릿과 리추얼 템플릿 지우기, 같은 rev 를 든 리추얼 템플릿 저장, 워크스페이스 표식 없음, 보관물이 사라진 휴지통 되살리기, 같은 이름의 아젠다나 프로젝트가 100개까지 차 있음이다. 값 오류용 검사로 거절해서 그렇다.
2. 없는 대상인데 `WL-404` 가 아닌 거절이 있다. 그 코멘트가 없다, 그 커밋은 이 노트의 판 목록에 없다, 그 노트에는 판이 아직 없다, 판 번호 범위 밖은 `WL-409` 이고, 휴지통 보관중 옮길 노트 파일이 없다는 `WL-400` 이다. 「없다」 갈래만 새로 만들어도 된다는 규칙에 기대는 쪽은 이것들을 「있는데 못 다룬다」로 읽는다.
3. 다시 불러도 같은 답인데 `WL-500` 인 거절이 있다. `Lexical JSON 노트의 본문은 고칠 수 없다`, `markdown 이 아닌 하위 노트는 저장하지 않는다`, `폴더로 안 올라간 단일 파일 노트에는 하위 노트를(첨부를) 둘 수 없다`, `노트가 저장 상한을 넘어 저장하지 않았다`, `프론트매터가 없어 … 않았다` 다. 6.5가 `WL-500` 을 「재시도할 수 있다」로만 읽으면 이 실패에서 같은 호출을 되풀이한다.
4. 비슷한 소진이 번호가 다르다. 같은 이름 아젠다 100개 소진은 `WL-400` 이고, 폴더 이름 접미사 99개 소진(옮길 자리를 못 찾았다)은 `WL-500` 이다.
5. `WL-404` 문구의 대상 이름이 대부분 영어(`Note`, `SubNote`, `Review`, `Template`, `TrashEntry`, `Agenda`, `Project`, `shard map`)인데, 목록과 검색에서 이름으로 못 찾은 아젠다만 아젠다다.
6. `wl-cli` 는 자기 실패를 `WL-400` 머리로 적고도 종료 코드 2를 낸다. 같은 머리가 엔진에서는 3이다.
7. 예상 밖 실패에서 그때까지 쌓인 진단 줄이 사라진다.
8. 단발 모드의 stdout과 진단 줄과 WL 줄의 인코딩이 로캘을 타고, 로그 줄만 UTF-8로 못박혀 있다. UTF-8이 아닌 로캘에서 한글이 어떻게 나가는지는 재지 않았다.
9. 짝 없는 서로게이트가 `?` 로 나가서 `JSON.stringify` 와 바이트가 갈린다. 실행해 보지는 않았다.
10. `null` 을 싣는 3곳이 조건부 키를 빼는 규칙의 예외다. 같은 회고가 목록에서는 `hasMemo: false` 로, 1건 읽기에서는 `"memo": null` 로 나간다.
11. 받은 글자를 적는 줄이 WL 줄보다 앞에서 `WL-` 꼴을 낼 수 있다. 단발 모드에서 `update_doc '{"id":"WL-999"}'` 를 토큰 없이 부르면, 선결 조건 셈 로그 줄이 `… 노트=WL-999` 를 먼저 찍고 그 뒤에 `WL-400 노트 id 모양이 아니다: WL-999` 가 온다. 처음 맞는 번호를 읽는 쪽은 `WL-999` 를 읽는다. 진단 줄의 파일 이름에 그 꼴이 든 경우도 같다(코드 읽기로 확인).
12. 실수 값을 문구에 적는 자리는 Kotlin의 실수 글자를 쓴다. `evaluate-doc <id> score=150` 은 `평가 점수는 0 에서 100 사이여야 한다: 150.0` 으로 선다.
13. `check-notes` 의 `lastChangeAt` 과 `lastCommentAt` 만 다른 시각 꼴(초를 빼기도 하는 꼴)을 쓴다(6.2).
14. 단발 모드의 예상 밖 실패와 시작 실패의 종료 코드(1로 읽힌다)와, `wl-cli` 가 잡지 않은 예외로 끝날 때의 1을 재지 않았다. 묶음은 이 갈래를 안 덮는다.
