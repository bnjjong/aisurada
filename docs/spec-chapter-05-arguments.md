# withlog 1부 vault 엔진 설명서 > 5장 인자 문법

이 장은 argv가 엔진에 닿아 명령의 값이 되기까지의 문법을 정한다. 이름을 찾는 차례, 명령 표면의 이름=값 문법, 값을 읽는 읽개, 도구 표면의 JSON 검사, 표면에 따라 갈리는 동작을 다룬다.

- **argv 첫 칸이 이름이다.** 도구 이름 29개를 먼저, 명령 이름 61개를 다음에 대소문자를 가려 맞대고, 어느 목록에도 없으면 WL 코드 없이 종료 코드 2로 끝난다.
- **명령 표면은 `--` 로 시작하는 칸을 버리고**, 첫 `=` 가 맨 앞이 아닌 칸을 이름 인자로, 나머지 칸을 자리 인자로 본다. 모르는 이름과 상한을 넘는 자리 인자는 `WL-400` 이다.
- **도구 표면은 JSON 객체 1개를 받고**, 명령 표면의 문법을 거치지 않고 값을 자리에 바로 놓는다. 모르는 키, 갈래가 틀린 값, JSON `null`, 상한을 넘는 값은 `WL-400` 이다.
- **값은 읽개마다 규칙이 다르고**, 다듬을지는 칸마다 정한다. 대체로 조회 조건과 토큰은 다듬고, 저장할 글과 자리 인자는 받은 그대로 읽는다.
- **근거**: 도구 표면으로 부르는 1부 케이스 448건 가운데 성공 439건이 stdout 바이트를, 실패 9건이 종료 코드 3과 빈 stdout을 잰다. 나머지는 코드 읽기로 확인했다. 숫자와 공백 판정은 Kotlin 표준 라이브러리 1.9.25 소스로, JSON 읽개는 엔진 jar에 든 `kotlinx.serialization-json` 1.6.3의 바이트코드로 확인했고, 이 갈래들은 실행해 보지 않았다.

### 낱말

| 낱말 | 뜻 |
|---|---|
| 칸 | argv의 원소 1개 |
| 이름 인자 | `이름=값` 꼴의 칸. 문구에서는 옵션이라고도 부른다 |
| 자리 인자 | 이름 없이 차례로 받는 칸 |
| 읽개 | 칸의 글자를 값으로 바꾸는 규칙 1개(5.3) |
| 다듬기 | 앞뒤의 공백 글자를 떼는 일(0.3). 글자 집합은 5.3에 다시 적는다 |
| UTF-16 차례 | 글자를 UTF-16 코드 단위의 수 값으로 앞에서부터 맞대 정한 차례. 정렬은 모두 이 차례다 |

## 5.1 이름 찾기

엔진은 argv를 이 차례로 다룬다. 단발 모드(3.1)와 serve 모드(3.2)가 같은 차례를 밟는다(코드 읽기로 확인).

1. argv의 끝에서 2번째 칸이 세션 표식 글자(`\u0000` 뒤에 `wl-session-id`)와 정확히 같으면 끝 2칸을 뗀다(4.4). 마지막 칸이 세션 id이고 모양은 안 본다. 표식이 NUL 글자로 시작해서 운영체제 argv로는 칠 수 없고, `wl-cli` 가 소켓 요청에만 싣는다.
2. 남은 argv의 첫 칸이 이름이다. 이 자리에서는 `--` 로 시작하는 칸도 이름으로 본다. 그래서 단발 모드에서 `--withlog.vault=...` 같은 설정 칸을 이름보다 앞에 두면 그 설정 글자가 모르는 이름이 된다. 단발 실행의 첫 칸이 정확히 `serve` 면 이 차례를 안 밟고 serve 모드로 뜬다(3.2).
3. 그 이름을 도구 이름 29개와 맞댄다. 맞으면 도구 표면이다.
4. 맞는 도구가 없으면 명령 이름 61개와 맞댄다. 맞으면 명령 표면이다.
5. 어느 목록에도 없거나 argv가 비었으면 stdout 없이 종료 코드 2로 끝난다. WL 코드는 없고 stderr는 부록 C.2의 안내 문구다.

맞대기는 글자가 정확히 같아야 맞고, 대소문자를 가리며, 공백을 안 뗀다. `GET_DOC` 과 `get_doc` 은 모르는 이름이다. 도구 이름은 밑줄을 쓰고(`get_doc`) 명령 이름은 하이픈을 쓴다(`get-doc`). 지금은 목록 2개에 겹치는 이름이 없다. 그래도 차례를 못박는 이유는 스킬과 래퍼가 부르는 도구 이름이 계약이고, 이름이 겹치는 날에도 그쪽이 이겨야 하기 때문이다. 밑줄을 하이픈으로 바꾸는 규칙으로 찾지 않고 목록으로 맞대는 이유는, 규칙에서 벗어난 이름 1개가 조용히 안 잡히기 때문이다.

도구 29개는 저마다 명령 1개로 옮겨진다(부록 B). 도구 표면은 5.2의 문법을 안 거치고 값을 자리에 바로 놓고(5.4), 그 뒤로는 명령 표면과 같은 처리를 지난다. 명령 61개 가운데 도구 짝이 있는 것은 29개이고, 나머지 32개는 명령 표면에만 있다(부록 A). 4부 명령 7개는 4부를 뺀 판에서도 이름으로 찾아진다. 그래서 그 판은 5.2의 문법 검사를 지나고, 쓰기 깃발 명령이면 워크스페이스 표식과 색인 맞추기까지 지난 뒤, 칸을 읽기 전에 `WL-409` 로 거절한다(32.2).

serve 모드의 argv는 요청 프레임의 바이트를 UTF-8로 푼 글자이고, UTF-8이 아닌 바이트 자리는 `U+FFFD` 가 된다(4.1, 코드 읽기로 확인). 단발 모드의 argv는 JVM이 운영체제 인자를 푼 글자이고, 그 풀이는 이 설명서가 정하지 않는다.

`wl-cli` 를 거치면 이름 찾기가 1겹 더 앞에 선다(3.3). `wl-cli` 는 첫 칸으로 갈 곳을 정하고, 엔진으로 보내는 이름은 위 목록과 같은 목록에서 고른다. 그래서 `wl-cli` 를 거친 호출은 엔진의 「모르는 명령」 답을 보지 않는다.

| 첫 칸 | 가는 곳 | 종료 코드 |
|---|---|---|
| `doctor`, `sweep`, `report`, `schedule`, `install` | `wl-cli` 가 직접 다룬다(3.3, 3.5, 3.6) | 그 명령이 정한다 |
| 없음, `--list`, `-l`, `--help`, `-h` | `wl-cli` 도움말. stdout에 쓴다 | 0 |
| 도구 이름 29개와 명령 이름 61개 | serve 모드 엔진 | 엔진이 정한다 |
| 그 밖의 글자 | `wl-cli` 의 「알 수 없는 이름」 안내(부록 C.2) | 2 |

`serve` 는 엔진을 띄우는 단어라 이 목록에 없다. 그래서 `wl-cli serve` 는 「알 수 없는 이름」으로 끝난다. 묶음의 1부 케이스 448건은 모두 도구 이름으로 부르고, 명령 이름으로 부르는 묶음 케이스 12건은 4부 케이스다(묶음이 잰다).

## 5.2 명령 표면

명령 이름 뒤의 칸을 앞에서부터 1칸씩 이렇게 다룬다(코드 읽기로 확인).

1. `--` 로 시작하는 칸은 자리와 상관없이 버린다. `-` 가 1개뿐인 칸(`-x`)은 버리지 않는다. 단발 모드에서는 Spring이 이 칸을 설정으로 따로 읽는다(3.1, 33.1, 5.6의 1번). serve 모드에서는 이 칸이 아무 데도 안 간다. 이름 인자에 `--` 를 안 쓰는 이유는, 문법 2가지가 섞이면 오타 난 필터가 설정으로 조용히 흘러가 「필터를 걸었는데 다 나온다」가 되기 때문이다.
2. 칸에서 처음 나오는 `=` 를 찾는다. 그 자리가 2번째 글자 이후면 이름 인자다. 이름은 `=` 앞의 글자를 다듬은 것이라 `type =plan` 의 이름은 `type` 이다. 값은 `=` 뒤의 글자 전부이고 이 단계에서는 안 다듬는다. 첫 `=` 에서만 가르므로 값 안의 `=` 는 그대로 남는다.
3. `=` 가 없거나 맨 앞 글자가 `=` 면 자리 인자다. 빈 칸(`""`)과 `=abc` 도 자리 인자이고, 자리 인자는 안 다듬는다.
4. 이름 인자의 이름을 그 명령의 허용 목록과 글자 그대로 맞댄다. 대소문자를 가려서 `list-docs Type=plan` 은 모르는 이름이다. 없으면 그 칸에서 바로 `WL-400` 으로 선다. 그래서 argv 차례로 처음 걸린 이름 1개만 문구에 적히고, 이 실패가 6번의 자리 인자 수 실패보다 앞선다. 다듬은 이름이 비는 칸(`=x`)도 빈 이름으로 이 검사에 걸려 `모르는 옵션이다: .` 로 선다.
5. 같은 이름이 다시 오면 뒤엣것이 이긴다.
6. 칸을 다 본 뒤 자리 인자 수가 그 명령의 상한을 넘으면 `WL-400` 으로 선다. 상한은 명령마다 0, 1, 2, 무제한 가운데서 정하고(부록 A), 따로 안 정한 명령은 1이다.

```
WL-400 <명령> 이 모르는 옵션이다: <다듬은 이름>. 쓸 수 있는 것은 [<허용 이름을 UTF-16 차례로>] 뿐이다.
WL-400 <명령> 이 받는 자리 인자는 <상한> 개인데 <받은 수> 개를 받았다: <사용법>
```

허용 목록은 UTF-16 차례로 늘어놓고 `[a, b]` 꼴(쉼표와 공백 1칸)로 적는다. 허용 이름이 없는 명령은 `[]` 다. `<사용법>` 은 그 명령의 사용법 글이고(부록 A), 계약이 아니다.

남는 자리 인자를 조용히 버리지 않는 이유는, 버리면 `list-docs 3` 을 친 사람이 100건을 받고도 문법을 틀린 줄 모르기 때문이다. 모르는 이름을 버리지 않는 이유도 같다. `stat=done` 같은 오타가 필터를 안 건 것과 같은 결과를 내면, 사람은 필터가 안 먹는다고 결론을 낸다.

| argv | 결과 |
|---|---|
| `["list-docs", "type=plan", "limit=0"]` | 이름 인자 2개 |
| `["list-docs", "Type=plan"]` | `WL-400 list-docs 이 모르는 옵션이다: Type. 쓸 수 있는 것은 [agenda, bodies, date, favorite, favoriteCategory, from, limit, tag, to, type] 뿐이다.` |
| `["list-docs", "3"]` | `WL-400 list-docs 이 받는 자리 인자는 0 개인데 1 개를 받았다: ...` |
| `["list-docs", ""]` | 위와 같다. 빈 칸도 자리 인자 1개다 |
| `["list-docs", "3", "foo=1"]` | `foo` 가 모르는 이름이라 그 문구로 선다. 자리 인자 수는 그 뒤라 안 본다 |
| `["search-docs", "a=b"]` | `WL-400 search-docs 이 모르는 옵션이다: a. ...` 검색어에 `=` 가 들면 `query=a=b` 로 준다 |
| `["get-doc", "<노트 id>", "--withlog.vault=/x"]` | 3번째 칸은 명령 인자에서 사라진다. 단발 모드에서는 Spring이 그 값을 vault 설정으로 쓰고(33.1), serve 모드에서는 아무 데도 안 가서 serve 모드 엔진이 원래 vault를 쓴다 |
| `["get-doc", "a=b"]` | `WL-400 get-doc 이 모르는 옵션이다: a. 쓸 수 있는 것은 [] 뿐이다.` |

자리 인자는 명령이 꺼낼 때 검사한다. 첫 자리 인자가 없거나 공백뿐이면 `WL-400 인자가 하나 필요하다: <사용법>` 이다. 자리 인자 2개를 요구하는 명령은 2번째가 없거나 공백뿐이면 `WL-400 인자가 둘 필요하다: <사용법>` 이다. `link-docs` 만은 2번째 칸에 문구가 따로 있다(`대상 노트 id 가 필요하다: <사용법>`, 15장). 빈 셸 변수가 `""` 로 넘어올 때 그것을 값으로 받으면 「id 모양이 아니다」라는 엉뚱한 문구가 나와서, 공백뿐인 칸을 없는 칸으로 본다.

꺼낸 자리 인자는 안 다듬고 그대로 식별자 모양 검사(1.4)로 간다. 그래서 `get-doc " ndfixture-00000001"` 은 「노트 id 모양이 아니다」로 선다. 예외는 하위 노트 명령의 부모 참조이고, `/` 로 나눈 조각마다 다듬는다(11.8). 2번째 자리가 선택인 명령(`list-attachments`, `write-attachment`, 코멘트 명령)은 공백뿐인 2번째 칸을 없는 칸으로 접는다(18장, 19장).

## 5.3 값 읽기

이름 인자의 값은 글자이고, 명령은 칸마다 아래 읽개 가운데 1개로 그 글자를 읽는다. 어느 칸을 어느 읽개로 읽는지는 명령 장이 정하고, 이 절은 읽개의 문법만 정한다. 도구 표면도 값을 글자로 바꿔 같은 자리에 놓으므로(5.4), 이 읽개를 똑같이 지난다. 이 절의 규칙은 모두 코드 읽기로 확인했고, 묶음은 이 경계를 안 잰다.

다듬기는 앞뒤에서 아래 글자를 떼는 일이다. Java의 `Character.isWhitespace` 와 `Character.isSpaceChar` 가운데 어느 쪽이라도 참인 글자이고, 0.3에서 정한 다듬기와 같다.

```
U+0009~U+000D, U+001C~U+001F, U+0020, U+00A0, U+1680, U+2000~U+200A,
U+2028, U+2029, U+202F, U+205F, U+3000
```

`U+0085`, `U+200B`, `U+FEFF` 는 이 집합에 없어서 안 떼어진다. 「공백뿐이다」도 모든 글자가 이 집합에 드는 것을 뜻한다.

| 읽개 | 받는 글자 | 문법 | 안 준 것과 빈 값 | 실패 문구 |
|---|---|---|---|---|
| 다듬은 글 | 늘 다듬은 값 | 아무 글자 | 다듬은 뒤 비면 안 준 것 | 없음 |
| 날것 | 늘 받은 글자 | 아무 글자 | 빈 글은 값이다 | 없음 |
| 정수 | 늘 다듬은 값 | 아래 정수 문법. 32비트 부호 있는 범위 | 다듬은 뒤 비면 안 준 것 | `<이름> 은 숫자여야 한다: <다듬은 값>` |
| 실수 | 늘 다듬은 값 | 아래 실수 문법 | 같다 | `<이름> 은 숫자여야 한다: <다듬은 값>` |
| 불리언 | 늘 다듬은 값 | 정확히 `true` 나 `false` | 같다 | `<이름> 은 true 나 false 여야 한다: <다듬은 값>` |
| 쉼표 목록 | 늘 다듬은 값 | `,` 로 나누고 조각을 다듬고 빈 조각을 버린다 | 빈 목록 | 읽개에는 없다. 조각을 쓰는 칸이 검사한다 |
| JSON 배열 | 늘 받은 글자 | 5.4의 JSON 읽개로 읽어 최상위가 배열 | 칸이 정한다. 빈 글은 배열이 아니라 실패다 | `<이름> 은 JSON 배열이어야 한다: <받은 글자>` |
| 날짜 | 칸마다 다르다 | 아래 날짜 문법과 달력 | 칸이 정한다 | `<이름> 은 YYYY-MM-DD 모양이어야 한다: <값>` |
| 시각 | 칸마다 다르다 | `^([01][0-9]\|2[0-3]):[0-5][0-9]$` | 칸이 정한다 | `<이름> 은 HH:MM 모양이어야 한다: <값>` |
| 열거값 | 칸마다 다르다 | 칸마다 정한 낱말 목록 | 칸이 정한다 | `모르는 <무엇> 이다: <값>. 쓸 수 있는 것은 [<목록>] 뿐이다.` |

실패는 모두 `WL-400` 이다. 문구의 `<이름>` 은 이름 인자의 이름이고, 도구 표면으로 들어왔어도 명령 쪽 이름이 적힌다. `list_docs '{"dateFrom":"x"}'` 는 `from 은 YYYY-MM-DD 모양이어야 한다: x` 로 선다. 「받는 글자」가 「칸마다 다르다」인 읽개는 그 칸이 다듬어 넘기면 다듬은 값을, 날것으로 넘기면 받은 글자를 읽고, 문구의 `<값>` 도 그 글자다.

정규식과 모양 검사는 모두 입력 전체와 맞아야 통과한다. 부분만 맞는 찾기로 검사하면 Java 정규식의 `$` 가 끝 줄바꿈 바로 앞에서도 맞아 `09:30` 뒤에 LF가 붙은 값이 통과하는데, 엔진은 전체 맞춤을 써서 그 값을 거절한다. 시각, 날짜, 회고 날짜, 식별자 모양(1.4), 템플릿 id, 휴지통 항목 id가 모두 그렇다. 정규식의 `[0-9]` 와 `\d` 는 ASCII 숫자만이다.

다듬을지를 가르는 기준은 값이 어디에 쓰이는가다. 조회 조건, 선결 조건 토큰(`f1`), 이름 인자로 받는 식별자(`comment_id`)는 다듬어 읽는다. `type= plan` 처럼 공백이 섞인 필터를 그대로 넘기면 어느 유형에도 안 맞아 「맞는 노트가 없다」로 보이기 때문이다. 제목, 본문, 메모, 첨부 내용처럼 저장할 글은 날것으로 읽는다. 끝 줄바꿈을 떼면 같은 글을 다시 저장할 때마다 파일이 바뀌고, 사용자가 쓴 글과 다른 글이 남기 때문이다. 자리 인자로 받는 식별자는 다듬지 않고 그대로 모양 검사로 보낸다(5.2). 이 기준에서 벗어나는 칸이 있어서, 칸마다의 정본은 부록 A, 부록 B, 명령 장의 N.3이다. 날것으로 읽어 놓치기 쉬운 칸은 이렇다.

| 명령 | 날것으로 읽는 칸 | 그래서 생기는 일 |
|---|---|---|
| `create-doc` | `type`, `date`, `time`, `format`, `tier`, `links` 항목의 `to` 와 `kind` | 앞뒤 공백이 붙으면 모양이나 낱말 검사에서 선다 |
| `update-doc` | `date`, `time` | 같다 |
| `create-sub-note` | `type` | 같다 |
| `save-template` | `id`, `type` | `id= x` 는 「템플릿 id 모양이 아니다」로 선다 |
| 모든 명령 | 자리 인자 | 5.2 |

빈 값의 뜻도 이 갈림을 따른다.

| 예 | 읽개 | 뜻 |
|---|---|---|
| `list-docs agenda=` | 다듬은 글 | 아젠다 필터를 안 건 것 |
| `set-favorite <id> f1=` | 다듬은 글 | 토큰을 안 보낸 것(7.2) |
| `set-favorite <id> category=` | 날것 | 라벨을 지우라는 뜻 |
| `update-doc <id> body=` | 날것 | 본문을 비우라는 뜻 |
| `update-doc <id> tags=` | JSON 배열 | 빈 글은 배열이 아니라 `tags 은 JSON 배열이어야 한다: ` 로 선다. 태그를 다 지우려면 `tags=[]` 다 |
| `save-template id=` | 날것 | 빈 id는 새로 만들기(24장) |

정수 읽개의 문법은 이렇다. 맨 앞에 `+` 나 `-` 를 1개까지 두고, 그 뒤에 10진 숫자를 1개 이상 둔다. 앞자리 0을 받아서 `007` 은 7이다. 값이 -2,147,483,648 이상 2,147,483,647 이하여야 하고, `3000000000` 은 실패다. 10진 숫자는 ASCII 숫자만이 아니라, UTF-16 코드 단위 1개로 적히는 글자 가운데 유니코드 범주가 Nd(10진 숫자)인 글자를 모두 받는다. 그래서 `limit=１２` (전각 숫자)는 12다. U+FFFF 위의 숫자(U+1D7CE 같은 수학 숫자)는 코드 단위 2개로 적혀서 받지 않는다. Kotlin `toIntOrNull` 이 코드 단위마다 Java `Character.digit` 을 부르기 때문이다. 어느 글자가 Nd인지는 엔진을 돌리는 JDK의 유니코드 판이 정한다. 엔진은 Java 21을 목표로 지어 기기에 깔린 JDK 21 이상에서 돌고, 그 판을 번들에 못박지 않는다(JDK 21은 Unicode 15.0). 그래서 새 유니코드 판에 들어간 숫자의 성패는 기기마다 갈릴 수 있다. 묶음은 이 갈래를 안 재서, 다시 짓는 구현이 고를 판은 부록 D에서 정한다. 0과 음수가 무엇을 뜻하는지는 칸이 정한다(`list-docs limit=0` 은 전부, 9장).

실수 읽개의 문법은 아래와 같고, 입력 전체가 맞아야 한다. Java `Double.valueOf` 문서의 문법과 같다.

```
실수   = 앞뒤 [U+0000~U+0020]* 사이에 ( 부호? "NaN" | 부호? "Infinity" | 부호? 수 꼬리? )
부호   = "+" | "-"
꼬리   = "f" | "F" | "d" | "D"
수     = 10진수 | 16진수
10진수 = 숫자+ ( "." 숫자* )? 지수? | "." 숫자+ 지수?
지수   = ( "e" | "E" ) 부호? 숫자+
16진수 = ( "0x" | "0X" ) ( 16진숫자+ "."? | 16진숫자* "." 16진숫자+ ) ( "p" | "P" ) 부호? 숫자+
숫자   = ASCII 0~9, 16진숫자 = 0~9, a~f, A~F
```

몇 가지를 덧붙인다. 다듬기를 먼저 해서, 앞뒤의 U+0000~U+0020 가운데 다듬기 집합에 없는 글자(U+0001 같은 것)만 이 문법의 바깥 자리에서 받아지고, 그래도 숫자로 읽힌다. 꼬리 `f`, `F` 는 float로 반올림하지 않고 `d` 처럼 double로 읽는다. `+NaN`, `-NaN`, `NaN` 은 모두 NaN이다. 16진수는 `p` 지수가 꼭 있어야 해서 `0x10` 은 실패이고 `0x1p3` 은 8이다. 범위를 넘으면 무한대(`1e999`)나 0이 되고 실패가 아니다. 이 값들이 범위 검사를 어떻게 지나는지는 칸이 정한다(`evaluate-doc score=NaN` 은 범위 검사에서 선다, 15장).

불리언 읽개는 대소문자를 가린다. 모르는 값을 거짓으로 떨어뜨리지 않는 이유는, `remove=yes` 를 친 사람은 연결이 끊기길 기대하는데 거짓으로 읽으면 연결이 1개 더 생기기 때문이다. 예외는 `list-docs` 와 `search-docs` 의 `favorite` 칸 1개다. 이 칸은 다듬은 값 전체를 로캘 없는 소문자화로 바꾼 뒤 `true`, `false` 와 맞대서 `TRUE` 도 받고, 실패 문구가 `모르는 즐겨찾기 값 이다: <소문자로 바꾼 값>. 쓸 수 있는 것은 [true, false] 뿐이다.` 다.

JSON 배열 읽개는 5.4의 JSON 읽개와 같은 읽개를 쓴다. 그래서 따옴표 없는 글자가 문자열 아닌 리터럴로 읽히고, `tags=[a]` 는 배열 읽기를 지나 항목 검사에서 `tags 항목이 문자열이 아니다: a` 로 선다. 항목 규칙(문자열만, 객체만, 모르는 키 금지)은 칸마다 정한다(13장, 23장, 부록 B.6).

날짜 읽개는 Java `LocalDate.parse` 와 같고, 문법은 아래와 같다. 입력 전체가 맞아야 하고 숫자는 ASCII뿐이다.

```
날짜 = 연도 "-" 월 "-" 일
연도 = 숫자 4자리 | "+" 숫자 5~10자리 | "-" 숫자 4~10자리
월   = 숫자 2자리, 일 = 숫자 2자리
```

연도는 -999,999,999 이상 999,999,999 이하이고 그 밖은 실패다. 부호 없는 5자리 이상(`10000-01-01`)과 4자리에 `+` 를 붙인 꼴(`+2026-06-01`)은 실패다. 음수 연도(`-0001-01-01`, `-2026-06-01`)는 받고, `-0000-01-01` 은 실패이며, `0000-01-01` 은 받는다. 달력에 없는 날(`2026-02-30`)과 자릿수가 모자란 꼴(`2026-6-1`)은 실패다. 달력 검사를 하는 이유는 `2026-02-30` 으로 만든 노트가 저장은 되는데 다음 훑기에서 건너뛰어져, 아무 데서도 안 보이는 노트가 되기 때문이다. 문구에 날짜를 다시 적는 자리는 연도가 4자리를 넘으면 `+10000-01-01`, 음수면 `-0001-01-01` 처럼 적는다.

회고 날짜만은 달력을 안 보고 모양 `^[0-9]{4}-[0-9]{2}-[0-9]{2}$` 만 본다(25장). 회고 날짜는 달력의 칸이 아니라 파일 이름이라서, 옛 목록에 있던 회고가 새 목록에서 빠지면 안 되기 때문이다.

시각 읽개는 정규식을 먼저 보고, 맞으면 그 글자를 시와 분으로 읽는다. 정규식이 시를 23까지, 분을 59까지만 받아서 그 뒤의 읽기는 실패하지 않는다. `09:30:00`, `9:30`, `24:00`, 끝에 LF가 붙은 `09:30` 은 모두 실패다.

열거값 읽개는 칸마다 낱말 목록과 맞대는 법이 다르다.

| 칸 | 낱말 | 맞대는 법 | 문구의 <무엇> |
|---|---|---|---|
| 노트 유형(`type`) | `plan`, `build`, `report`, `research`, `meeting`, `free` | 대소문자 무시 | 유형 |
| 관계 종류(`link-docs` 의 `kind`, `links` 항목의 `kind`) | `direct`, `indirect`, `attach` | 대소문자 무시 | 관계 종류 |
| 노트 층(`create-doc` 의 `tier`) | `reading`, `record` | 대소문자 무시 | 노트 층 |
| 회고 종류(회고 명령의 `kind`) | `morning`, `evening`, `weekly` | 소문자로 바꿔 맞댐 | 회고 종류 |
| 템플릿 갈래(`category`) | `doc`, `ritual` | 소문자로 바꿔 맞댐 | 템플릿 갈래 |
| 템플릿 유형(템플릿 명령의 `type`) | 노트 유형과 같은 6개 | 소문자로 바꿔 맞댐 | 템플릿 유형 |
| 본문 포맷(`create-doc` 의 `format`) | `markdown` | 받은 글자와 정확히 같아야 | 본문 포맷 |
| 색(`hue`) | 12개(20장) | 정확히 같아야 | 문구가 따로 있다: `hue 값이 아니다: <값>` |

「대소문자 무시」는 Java `String.equalsIgnoreCase` 와 같다. UTF-16 길이가 같아야 하고, 앞에서부터 맞대는 글자 2개가 같거나, 2개를 `Character.toUpperCase` 로 바꾼 값이 같거나, 그 대문자를 다시 `Character.toLowerCase` 로 바꾼 값이 같으면 그 자리가 맞는다. 맞대는 단위는 UTF-16 코드 단위이고, 짝을 이룬 서로게이트만 코드 포인트 1개로 맞댄다. 로캘을 안 탄다. 그래서 `type=reſearch`(U+017F), `type=buıld`(U+0131), `type=BUİLD`(U+0130) 는 모두 맞고, 켈빈 기호 U+212A 도 `k` 와 맞는다. 「소문자로 바꿔 맞댐」은 받은 글자 전체를 로캘 없이(Java `Locale.ROOT` 로) 소문자로 바꾼 뒤 낱말과 글자 그대로 맞댄다. 이 방식에서는 위 3개 예가 안 맞고, U+0130 은 `i` 와 결합 점 2글자가 되어 길이부터 달라진다. 터키어 로캘에서 돌아도 `RITUAL` 은 `ritual` 이 된다. 방식 2개가 섞인 까닭은 칸마다 따로 옮겨 왔기 때문이고(5.6의 8번), 같은 정의가 B.3의 아젠다 제목 맞대기(대소문자 무시)와 `favorite` 칸(소문자로 바꿔 맞댐)에도 걸린다. `list_tags` 의 `query` 만은 SQLite LIKE 의 기본 동작이라 ASCII 글자의 대소문자만 무시한다(B.3).

문구의 `[<목록>]` 은 위 낱말을 표의 차례로 적는다. 예를 들어 `모르는 유형 이다: memo. 쓸 수 있는 것은 [plan, build, report, research, meeting, free] 뿐이다.` 다. `<값>` 은 그 칸이 읽은 글자이고 소문자로 바꾸기 전의 글자다. 다듬어 읽는 칸이면 다듬은 값이고, 날것으로 읽는 칸이면 받은 글자다.

## 5.4 도구 표면

도구 표면의 인자는 JSON 객체 1개다. 엔진은 이 차례로 검사하고, 처음 걸린 자리에서 `WL-400` 으로 선다(코드 읽기로 확인).

1. 이름 뒤 칸에서 `--` 로 시작하는 칸을 뺀다(5.2와 같은 규칙). 남은 칸이 2개 이상이면 선다. 따옴표를 빠뜨린 셸이 JSON을 여러 칸으로 쪼갠 경우가 거의 전부라서, 뒤 칸을 조용히 버리면 필터 없는 전체 목록이 아무 말 없이 나간다.
2. 남은 칸이 없거나 그 칸을 다듬은 글이 비면 빈 객체 `{}` 로 본다.
3. 다듬은 글을 JSON으로 읽는다(아래 JSON 읽개). 읽기에 실패하면 선다.
4. 최상위가 객체가 아니면 선다.
5. 스키마에 없는 키를 모두 모아 UTF-16 차례로 적고 선다. 키는 대소문자를 가린다. 버려진 키는 읽기에서는 걸지 않은 필터가 되고 쓰기에서는 저장 안 된 값이 되는데, 그것이 「맞는 노트가 없다」와 구분되지 않기 때문이다.
6. 스키마의 칸을 부록 B의 표 차례로 1개씩 다 본다. 칸마다 아래를 차례로 하고, 다음 칸으로 넘어간다.
   - 키가 없으면 필수 칸에서 선다. 필수가 아니면 그 칸을 건너뛴다.
   - 키가 있으면 JSON `null` 이어도 있는 것으로 보고, 갈래를 검사하고, 배열 항목 수 상한을 보고, 글자 수 상한을 본다.
   - 통과한 값을 글자로 바꿔 그 칸의 자리에 놓는다(아래 「옮기는 자리」). 노트 경로 칸은 이 자리에서 값을 나누고 조각 수를 검사한다.
7. 칸을 다 보면 명령이 그 자리에서 칸을 읽는다(5.3). 5.2의 문법은 거치지 않는다.

6번이 칸마다 끝까지 돈다는 점이 차례를 정한다. 노트 경로의 조각 수 실패는 그 칸의 차례에 나서, 뒤 칸의 갈래 오류보다 앞선다. `write_attachment '{"parent":"a/b/c","name":1}'` 은 `parent` 문구로 선다. 필수 칸이 빠진 실패도 그 칸의 차례에 나서, `get_sub_note '{"id":5}'` 는 `parent 가 필요하다.` 로 선다.

7번 때문에 도구 표면의 값에는 5.2의 규칙이 안 걸린다. `--` 로 시작하는 값도 버리지 않고, 자리 인자 수 상한과 허용 이름 검사도 없다. 그래서 `list_attachments '{"parent":"ndfixture-00000001/--x"}'` 의 2번째 조각 `--x` 는 살아남아 하위 노트 id 모양 검사에 걸리고, `WL-400 하위 노트 id 모양이 아니다: --x` 와 종료 코드 3으로 선다. 같은 값의 `write_attachment` 도 같은 문구로 서고 아무것도 안 쓴다.

```
WL-400 <도구> 이 받는 인자는 JSON 한 덩어리인데 <n> 개를 받았다. 셸에서 따옴표로 감쌌는지 본다: <도구> '{"키":"값"}'
WL-400 인자 JSON 파싱 실패(<도구>): <다듬은 원문>
WL-400 인자 검증 실패(<도구>): 인자는 JSON 객체여야 한다: <다듬은 원문>
WL-400 인자 검증 실패(<도구>): 모르는 키다: [<모르는 키를 UTF-16 차례로>]. 쓸 수 있는 것은 [<스키마 차례의 키>] 뿐이다.
WL-400 인자 검증 실패(<도구>): <키> 가 필요하다.
WL-400 인자 검증 실패(<도구>): <키> 는 <기대> 여야 한다: <값의 JSON 글자>
WL-400 인자 검증 실패(<도구>): <키> 항목이 너무 많다(최대 <상한>개): <n>개
WL-400 인자 검증 실패(<도구>): <키> 가 너무 길다(최대 <상한>자): <n>자
WL-400 인자 검증 실패(<도구>): parent 는 `노트id` 이거나 `노트id/하위노트id` 여야 한다: <값>
```

모르는 키 목록은 키마다 1번씩, 따옴표 없이 적는다. 빈 키(`{"": 1}`)는 빈 글자로 적혀서 `모르는 키다: []` 처럼 보인다.

### JSON 읽개

엔진의 JSON 읽개는 `kotlinx.serialization-json` 1.6.3의 기본 설정이다. 이 판의 바이트코드로 아래 규칙을 확인했고(코드 읽기로 확인, 실행 안 함), 같은 읽개를 5.3의 JSON 배열 읽개도 쓴다. 표준 JSON보다 너그러운 자리와 엄한 자리가 섞여 있다.

- **바깥 공백**: 칸 전체를 5.3의 다듬기로 먼저 다듬는다. 토큰 사이에서 넘기는 공백은 탭, LF, CR, 스페이스 4개뿐이다.
- 객체의 키는 큰따옴표 문자열이어야 한다. `{id: "x"}` 는 읽기 실패다.
- 값 자리의 따옴표 없는 글자 덩어리는 문자열이 아닌 리터럴로 읽는다. 덩어리는 탭, LF, CR, 스페이스, `,`, `:`, `{`, `}`, `[`, `]`, `"`, `\` 에서 끝나고, U+007F와 ASCII 밖 글자는 덩어리에 든다. 덩어리가 U+0000~U+001F 가운데 탭, LF, CR이 아닌 글자를 만나면 거기서 끊기고, 그 글자 때문에 읽기가 실패한다. 따옴표 없는 `null` 만 JSON `null` 이고, `true`, `abc`, `+5`, `5d`, `1.2.3`, `'x'` 같은 나머지는 받은 글자 그대로의 리터럴이다. 숫자 모양은 이 단계에서 안 본다.
- 따옴표 문자열 안의 탈출은 `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, `\u` 와 16진 4자리(대소문자 무시)다. 다른 탈출은 읽기 실패다. `\u` 로 짝 없는 서로게이트도 만들 수 있다.
- 따옴표 문자열 안의 탈출하지 않은 제어 문자(U+0000~U+001F, 실제 LF와 탭 포함)도 그대로 받는다. 표준 JSON은 이것을 거절한다. 그래서 줄바꿈을 그대로 실은 `create_doc` 본문은 성공한다.
- 같은 키가 여러 번 오면 마지막 값이 이긴다.
- 끝 쉼표(`[1,]`, `{"a":1,}`)와 앞 쉼표(`[,1]`)는 읽기 실패다. 주석은 없다.
- 값 뒤에 다른 글자가 남으면 읽기 실패다(`{} x`).
- 중첩 깊이에 정한 상한은 없다. 객체는 깊이 200부터 JVM 스택 대신 힙에 쌓는 재귀로 바꿔 읽어서 스택이 안 넘친다. 배열은 그 장치 없이 JVM 스택 위의 재귀로 읽어서, 배열을 아주 깊게 겹치면 스택이 넘칠 수 있다. 그때는 6.6의 예상 밖 실패가 된다. 2026-10-24에 단발 모드로 재니 배열 4,000겹은 받고 5,000겹에서 종료 코드 1로 섰다. 이 경계는 JVM 스택 크기에 달려서 계약이 아니고, 다시 짠 구현은 4,000겹까지는 받아야 지금 엔진과 같다.
- 최상위가 따옴표 없는 글자 덩어리 1개면(`get_doc ndfixture-00000001`) 읽기는 지나고 4번의 「JSON 객체여야 한다」로 선다.
- BOM(U+FEFF)은 다듬기 집합에도 토큰 사이 공백에도 없어서, 맨 앞에 오면 따옴표 없는 글자 덩어리의 첫 글자가 된다. 그래서 BOM 뒤에 객체가 오면 그 덩어리 뒤에 글자가 남아 읽기 실패이고, BOM만 있으면 4번으로 선다.

이 너그러움은 종료 코드를 바꾼다. 엄격한 JSON 읽개로 지은 구현은 아래 입력을 「인자 JSON 파싱 실패」(종료 코드 3)로 거절하는데, 지금 엔진은 받는다. `search_docs '{"query":"x", "limit":+5}'` 와 `limit` 이 `5d` 인 입력은 양의 정수 갈래를 지나 성공(종료 코드 0)하고, 본문에 실제 LF를 실은 `create_doc` 도 성공한다. `limit` 이 `5.0` 인 입력은 표준 JSON이라 어느 읽개든 읽고, 양의 정수 판정(아래)에서 5로 지난다. 다시 짓는 구현은 지금 엔진처럼 받아야 같은 종료 코드를 내고, 묶음은 이 갈래를 안 잰다. 거절로 바꿀지는 부록 D에서 정한다.

### <값의 JSON 글자>

갈래 오류 문구의 `<값의 JSON 글자>`, 배열 칸이 명령으로 넘기는 글자, 부록 C.4의 `<항목의 JSON 글자>` 는 모두 읽은 값을 공백 없이 다시 찍은 글자다.

| 값 | 다시 찍은 꼴 |
|---|---|
| 문자열 | 큰따옴표로 감싸고, 6.1과 같은 집합만 탈출한다(`\"`, `\\`, `\b`, `\t`, `\n`, `\f`, `\r`, 나머지 U+001F 이하는 소문자 `\u00xx`). `/` 와 ASCII 밖 글자와 짝 없는 서로게이트는 그대로다 |
| 리터럴 | 받은 글자 그대로(`2026`, `+5`, `abc`, `null`) |
| 배열 | `[, 원소를 , 로 이은 것, ]` |
| 객체 | `{, "키":값 을 , 로 이은 것, }`. 키 차례는 처음 나온 차례이고, 같은 키는 1번만 적고 값은 마지막 값이다 |

그래서 `{"id": 2026}` 은 `id 는 문자열 여야 한다: 2026` 이고, `{"favorite": "true"}` 는 `favorite 는 true 나 false 여야 한다: "true"` 이고, `{"id":{"a":1,"b":2,"a":3}}` 은 `id 는 문자열 여야 한다: {"a":3,"b":2}` 다.

### 칸의 갈래

| 갈래 | 받는 값 | 뒤로 넘기는 글자 | <기대> |
|---|---|---|---|
| 문자열 | JSON 문자열. 빈 글도 받는다 | 탈출을 푼 글자 그대로. 안 다듬는다 | 문자열 |
| 불리언 | 따옴표 없는 `true`, `false` | `true`, `false` | `true 나 false` |
| 양의 정수 | 따옴표 없는 리터럴 가운데 아래 판정을 지나는 것 | 아래 판정의 64비트 정수를 10진으로 적은 글자 | `1 이상의 정수` |
| 숫자 | 따옴표 없는 리터럴 가운데 5.3의 실수 문법을 지나는 것 | 그 실수를 Java `Double.toString` 으로 다시 찍은 글자. `72` 는 `72.0`, `1e2` 는 `100.0`, `1e21` 은 `1.0E21`, `1e999` 는 `Infinity` 가 된다 | 숫자 |
| 문자열 배열 | 항목이 모두 JSON 문자열인 배열. 빈 배열도 받는다 | 다시 찍은 JSON 배열(`["a", "b"]`) | 문자열 배열 |
| 객체 배열 | 항목이 모두 객체인 배열. 항목 안의 키는 여기서 안 본다 | 같은 꼴 | 객체 배열 |

양의 정수 판정은 이 차례다. 리터럴을 5.3의 실수 문법으로 읽고, 그 값을 64비트 정수로 바꾼다. 바꿀 때 소수부는 버리고, 64비트 범위를 넘는 값과 무한대는 64비트 최댓값이나 최솟값으로 붙이고, NaN은 0으로 한다. 그 정수를 다시 실수로 바꾼 값이 원래 실수와 같고 정수가 1 이상이면 지난다. 그래서 `1.0` 은 1, `5d` 는 5, `1e18` 은 1000000000000000000 이 된다. `Infinity` 와 `1e19` 는 64비트 최댓값으로 붙은 뒤 원래 값과 달라서 거절된다. `9223372036854775808` 은 실수로 2^63이 되고, 붙은 최댓값을 다시 실수로 바꾸면 같은 2^63이라 지나서 9223372036854775807 로 넘어간다. 실수로 정확히 못 적는 큰 정수는 실수 값의 자릿수로 넘어가서 `12345678901234567` 은 `12345678901234568` 이 된다. 지금 이 갈래인 칸은 `search_docs` 와 `list_tags` 의 `limit` 2개뿐이고, 뒤의 정수 읽개(5.3)가 32비트를 넘는 값을 `limit 은 숫자여야 한다: <넘긴 글자>` 로 거절한다.

문자열 칸에 숫자나 불리언을 받아 주지 않는 이유는, `{"tag": 2026}` 같은 호출이 구현마다 다른 답을 내면 안 되기 때문이다. 배열을 구분자로 이어 붙이지 않고 JSON 글자로 나르는 이유는 태그 안에 쉼표가 들 수 있기 때문이다. 양의 정수 칸이 `1.0` 을 받는 이유는 옛 JavaScript 구현이 정수와 실수를 안 가렸기 때문이다.

상한은 4가지이고 모두 도구 표면에만 있다(5.5). 글자 수는 JSON을 푼 문자열의 UTF-16 코드 단위로 세서, 짝 없는 서로게이트도 1로 센다. 옛 스키마가 JavaScript 문자열 길이를 봤고, 바이트로 세면 한글 본문에서 상한이 3배쯤 빨리 걸리기 때문이다.

### 상한

| 상한 | 값 | 칸 |
|---|---|---|
| 글자 수 | 200,000 | 본문류 칸 8개(부록 B.8) |
| 글자 수 | 200 | `create_doc`, `update_doc` 의 `template` |
| 항목 수 | 50 | `create_doc`, `update_doc` 의 `tags` |
| 항목 수 | 200 | `create_doc` 의 `links` |

### 옮기는 자리

통과한 값은 칸마다 정한 자리로 간다. 정본은 부록 B의 「가는 자리」 열이다.

| 옮기는 자리 | 하는 일 | 쓰는 칸 |
|---|---|---|
| 자리 인자 n | 그 값을 n번째 자리 인자로 놓는다 | `get_doc`, `get_report`, `get_template`, `set_favorite`, `evaluate_doc`, `delete_doc`, `update_doc` 의 `id` (자리 0). `restore_doc`, `purge_doc` 의 `trashId` (자리 0). `link_docs` 의 `from` (자리 0)과 `to` (자리 1). 하위 노트 명령 5개의 `parent` (자리 0). `get_sub_note`, `update_sub_note`, `delete_sub_note` 의 `id` (자리 1) |
| 이름 인자 | 그 값을 정한 이름의 이름 인자로 놓는다. 이름이 다를 수 있다(`dateFrom` 은 `from`, `dateTo` 는 `to`) | 나머지 칸 모두. `save_template` 의 `id` 도 자리 인자가 아니라 이름 인자 `id=` 로 간다 |
| 노트 경로 | 값을 `/` 로 나누고 공백뿐인 조각을 버린 뒤, 남은 1~2조각을 자리 인자 0과 1에 놓는다. 남은 조각은 안 다듬는다 | `list_attachments`, `list_comments`, `write_attachment` 의 `parent` |

노트 경로에서 조각이 0개거나 3개 이상이면 위 `parent 는 ...` 문구로 선다. 손자를 물었는데 앞 2조각만 써서 부모의 첨부가 나오면 안 되기 때문이다. 2번째 조각은 하위 노트 명령의 부모 참조와 달리 직계 자식인지 안 보고, 그 루트 아래 어느 깊이의 하위 노트든 가리킨다. 하위 노트 id가 루트 안에서 유일하기 때문이다. 그래서 손자 하위 노트는 사슬(`노트id/자식id/손자id`)이 아니라 `노트id/손자id` 로 가리키면 닿는다. 묶음의 `list_attachments` 에 3조각 케이스가 있고, 종료 코드 3과 빈 stdout을 잰다. `list_docs` 는 스키마 밖에서 늘 `limit=0` 을 더 놓는다. 옛 도구에는 건수 인자가 없어서 늘 전부를 냈기 때문이다(9장).

값을 `이름=값` 글자로 다시 지어 5.2의 문법에 넣지 않고 자리에 바로 놓는다. 그렇게 해야 값 안의 `=` 가 문법이 되지 않는다. 묶음의 `search_docs/equals-sign` (`{"query":"a=b"}`)이 이 규칙으로 지나가서 6.3의 봉투를 낸다(묶음이 잰다).

자리에 놓인 뒤로는 명령 표면과 같은 코드가 값을 읽는다. 그래서 그 뒤의 실패 문구는 도구 이름이 아니라 명령의 사용법을 적는다. `get_doc '{"id":""}'` 는 `WL-400 인자가 하나 필요하다: get-doc <노트 id>` 로 선다.

### 표면 2개가 만난 뒤의 차례

명령마다 갈래가 더 있지만 앞뒤 차례는 모든 명령이 같다(코드 읽기로 확인).

1. 쓰기 깃발 명령이면 워크스페이스 표식을 본다(1.1). `init-workspace` 는 뺀다.
2. 쓰기 깃발 명령이면 색인을 맞춘다(8.3). 이 단계의 실패(`notes/` 를 못 읽음 같은 것)가 인자 오류보다 앞선다.
3. 쓰기 깃발 명령이면 쓴 쪽이 바뀌었을 때 vault git에 먼저 커밋한다(31.1). 이 커밋은 뒤의 인자 검사가 실패해도 이미 일어난다.
4. 명령이 칸을 읽는다(5.3). 자리 인자 꺼내기, 식별자 모양, 날짜, 열거값이 여기서 걸린다. 4부를 뺀 판의 4부 명령은 이 단계에서 칸을 읽기 전에 `WL-409` 로 선다(32.2).
5. 도메인 검사와 파일 읽기 쓰기가 돈다.

2번과 3번 사이에서 선결 조건 토큰을 받는 명령 5개(7.2)는 토큰이 왔는지를 로그 줄로만 센다. 이 셈은 아무것도 안 막고, 자리 인자를 모양 검사 없이 로그에 적는다(6.7의 11번). 토큰이 없거나 어긋난 쓰기를 거절하는 일은 5번의 파일 쓰기 자리가 한다.

그래서 워크스페이스가 아닌 폴더에서는 쓰기 명령의 인자 값이 틀려도 워크스페이스 문구로 선다. 모르는 키, 갈래 오류, 노트 경로 조각 수, 모르는 이름 인자, 자리 인자 수는 그보다 앞이라 워크스페이스와 상관없이 선다.

## 5.5 표면이 바꾸는 동작

표면 2개는 5.4의 7번 뒤로 같은 처리를 지나고, 어느 표면으로 왔는지만 아래 자리에서 쓴다. 판정 기준은 도구 이름으로 불렀는지 1가지다. 사람이 `wl-cli update-doc` 을 손으로 부르면 사람이어도 명령 표면이고, 표면이 가르는 것은 부른 사람이 아니라 부른 길이다.

| 동작 | 도구 표면 | 명령 표면 | 이유 | 장 |
|---|---|---|---|---|
| 기록 층 노트의 목록과 검색 | 안 보인다 | 보인다 | 기록 노트에 마스킹이 못 가린 자격증명이 섞일 수 있어 AI에게 감춘다 | 9장, 10장 |
| 기록 층 노트 1건 읽기 | `WL-409` | 읽는다 | 없다고 답하면 부르는 쪽이 같은 노트를 다시 만든다 | 11.4 |
| 기록 층 노트의 하위 노트 목록과 1건 | `WL-409` | 읽는다 | 하위 노트는 루트를 지나서만 닿는다 | 11.8, 16장 |
| 태그 빈도 | 읽기 층만 센다 | 읽기 층만 센다 | 층을 고를 칸을 열면 기록 층 태그가 새는 길이 생긴다 | 12장 |
| `get_doc` 의 `agendaFacts` | 싣는다 | 안 싣는다 | 앱은 안 쓰는 글이라 싣는 만큼 낭비다 | 11.6 |
| 응답의 `tier` 키 | 안 나온다 | 층이 `record` 일 때 싣는다 | 앱이 기록 노트를 보통 노트로 다루지 않게 | 11.6 |
| 세션 표식의 값 | 쓴다 | 버린다 | Claude 셸에서 띄운 앱이 그 셸의 세션 변수를 물려받는다 | 1.10, 4.4 |
| 편집 도장의 `editedBy` | `tool` | `app` | 마지막으로 고친 쪽을 남긴다 | 1.10 |
| 원본 요청 절 경고 | 싣는다 | 안 싣는다 | 사용자의 말을 받아 적는 쪽은 Claude뿐이다 | 13장 |
| 본문 200,000자, 템플릿 200자, 태그 50개, 연결 200개 상한 | 검사한다 | 안 한다 | 옛 도구 스키마의 상한을 옮겼다 | 5.4 |
| `list_docs` 의 건수 | 늘 전부 | 기본 100건 | 옛 도구에 건수 인자가 없었다 | 9장 |
| vault git 커밋의 쓴 쪽 | `tool` 과 세션 | `app` | 쓴 쪽이 바뀌면 그 앞 글을 먼저 커밋한다 | 31.1 |
| 선결 조건 토큰 요구 | 같다 | 같다 | 덮어쓰기 감지는 누가 불렀는지와 상관이 없다 | 7.2 |

`tier` 키가 도구 표면에서 안 나오는 까닭은 2가지다. 노트 모양을 싣는 읽기 응답(목록, 검색, 1건 읽기)이 기록 층 노트를 빼거나 거절하고, 쓰기 응답(`update_doc`, `set_favorite`, `evaluate_doc`, `link_docs`, `create_doc`, `delete_doc` 등)에는 노트 모양이 없어 `tier` 키 자체가 없다(코드 읽기로 확인). 그래서 도구 표면이 기록 층 노트에 쓰기를 해도(5.6의 11번) 응답에 `tier` 는 안 나온다.

세션 표식은 `wl-cli` 가 `CLAUDE_CODE_SESSION_ID` 를 다듬어 비지 않을 때 싣는다(3.3, 4.4). 엔진은 표식 뒤 칸을 모양 검사 없이 그대로 쓰고, 명령 표면이면 버린다. 앱이 띄운 `wl-cli` 가 그 변수를 물려받은 경우에도 앱의 쓰기가 무관한 세션을 가리키지 않게 하려고 그렇게 한다.

명령 표면에만 있는 칸이 있다. 도구는 옛 CLI와 인자까지 같아야 했고, 어떤 칸은 AI 손에 일부러 안 쥐여 주기 때문이다. `tier` 가 그 예이고, 기록 층으로 만든 노트를 도구 표면이 못 읽어서 AI가 그 노트를 다시 만드는 고리를 막는다.

| 명령 | 명령 표면에만 있는 칸 | 장 |
|---|---|---|
| `list-docs` | `limit`, `bodies` | 9장 |
| `search-docs` | 자리 인자로 주는 검색어 | 10장 |
| `list-reports` | `bodies` | 25장 |
| `list-templates` | `bodies` | 24장 |
| `list-sub-notes` | `bodies` | 16장 |
| `create-doc` | `mins`, `tier` | 13장 |
| `update-doc` | `date`, `time`, `mins` | 14장 |
| `update-sub-note` | `tags` | 17장 |

도구 짝이 없는 명령 32개는 도구 이름으로는 못 부른다(부록 A). 아젠다와 프로젝트 쓰기, 코멘트 쓰기, `init-workspace`, `empty-trash`, `shard-notes` 가 여기 든다. 그래서 Claude는 도구 표면으로 사용자의 아젠다를 지우거나 휴지통을 비우거나 vault를 재배치하지 못한다. 다만 명령 이름은 누구나 `wl-cli` 로 부를 수 있어서, 이것은 접근 통제가 아니라 도구 계약의 경계다.

## 5.6 얼어 있는 특이점

다시 지을 때 지킬지 고칠지는 부록 D에서 정한다.

1. `--` 로 시작하는 칸은 명령 표면과 도구 표면 모두에서 argv 칸째 사라진다. 그래서 `--` 로 시작하는 검색어를 자리 인자로 주면 검색어가 없는 것이 되고, 도구 표면의 JSON 칸이 `--` 로 시작하면 그 칸이 사라져 `{}` 가 된다. 단발 모드는 이 칸을 Spring 6.2.8의 명령줄 문법으로 따로 읽는다. `--이름=값` 은 설정이고, `--이름` 은 값 없는 설정이고, `--` 1칸 뒤의 칸은 설정으로 안 읽는다(엔진은 그래도 버린다). 이름이 빈 `--=x` 는 Spring이 「Invalid argument syntax」로 거절해서 엔진이 뜨기 전에 6.6의 예상 밖 실패가 된다. Spring은 설정 이름의 대소문자와 하이픈을 너그럽게 맞춰서 `--WITHLOG.VAULT=/x` 도 vault 설정을 덮는데, 1.1의 「vault 없음」 사전 검사는 정확히 `--withlog.vault=` 로 시작하는 칸만 본다(코드 읽기와 저장소의 2026-10-18 실측 기록으로 확인). 묶음의 jar 어댑터는 argv 끝에 `--withlog.vault=<경로>` 와 `--withlog.db.home=<경로>` 2칸을 붙인다(34.5). 어댑터는 계약이 아니라서 다시 짓는 구현은 자기 어댑터를 적어도 되지만, 같은 단발 모드 꼴을 지키려면 이 2칸을 설정으로 받고 명령 인자에서는 뺀다. 나머지 설정 키는 33.1을 따른다. 위 Spring의 갈래들은 계약이 아니고 묶음도 안 잰다.
2. 이름 찾기 실패 문구(부록 C.2)는 도구 이름으로 읽기 도구 12개만 늘어놓는다. 쓰기 도구 15개와 `list_comments`, `plan_day` 는 빠진다.
3. JSON 읽개가 따옴표 없는 값과 따옴표 안의 날 제어 문자를 받는다(5.4). 엄격한 읽개로 지은 구현은 `{"limit": +5}`, `{"limit": 5d}`, 실제 LF가 든 본문을 「인자 JSON 파싱 실패」로 거절해서, 지금 엔진이 종료 코드 0을 내는 입력에 3을 낸다.
4. 같은 키가 2번 오면 조용히 마지막 값이 이긴다. 모르는 키를 시끄럽게 거절하는 원칙과 어긋난다.
5. JSON `null` 은 안 준 것이 아니라 갈래 오류다. `update_doc '{"id":"<노트 id>", "tags":null}'` 은 「`tags 는 문자열 배열 여야 한다: null`」로 선다.
6. 양의 정수 칸이 64비트 범위까지 통과시켜서, `{"limit": 3000000000}` 은 도구 검사를 지난 뒤 정수 읽개에서 `limit 은 숫자여야 한다: 3000000000` 으로 선다. 9223372036854775808 은 9223372036854775807 로 바뀌어 넘어간다.
7. 정수 읽개는 유니코드 10진 숫자를 받고, 실수 읽개와 날짜와 회고 날짜와 시각 정규식은 ASCII 숫자만 받는다. `history` 의 판 번호는 다듬지 않은 2번째 자리 인자를 같은 정수 문법으로 읽어서 ` 3 ` 처럼 공백이 붙으면 실패하고, `commit=` 모양 검사는 유니코드 숫자를 16진 숫자로 받는다(31.4).
8. 대소문자를 다루는 법이 칸마다 다르다. 불리언은 가리는데 `list-docs` 와 `search-docs` 의 `favorite` 만 안 가려서, `list-docs favorite=TRUE` 는 받고 `list-docs bodies=TRUE` 는 실패다. 열거값은 「대소문자 무시」와 「소문자로 바꿔 맞댐」이 섞여서, `type=reſearch` 는 노트 유형에서 맞고 템플릿 유형에서 안 맞는다.
9. `create-doc` 의 `type` 과 `format` 은 날것으로 읽어서 `type= plan` 이 실패하고, `list-docs` 의 `type` 은 다듬어 읽어서 통과한다.
10. 도구 표면의 상한이 명령 표면에는 없다. 명령 표면으로 태그 51개 이상을 주면 파일에는 다 적히고 다음 읽기는 앞 50개만 본다(1.8). 그 노트의 다음 메타 쓰기가 51번째부터를 지울 수 있다. 실행해 보지는 않았다.
11. 기록 층을 막는 자리가 읽기 3곳(목록과 검색, `get_doc`, 하위 노트 읽기)뿐이다. 그래서 도구 표면이 기록 층 노트의 첨부 목록과 코멘트를 읽고, 그 노트에 메타 쓰기, `update_doc`, 첨부 쓰기, 하위 노트 만들기와 고치기와 지우기, 휴지통 보내기를 할 수 있다. `list_trash` 도 층을 안 걸러서 기록 층 노트의 제목과 경로를 싣고, `create_doc` 의 같은 제목 경고도 층을 안 걸러서 같은 아젠다의 기록 층 노트 id와 날짜를 실을 수 있다. 코드 읽기로만 확인했다.
12. `history` 는 공백뿐인 `query=` 를 「찾을 글자가 비었다」로 세우려는 검사를 두었지만, 다듬은 글 읽개가 먼저 빈 값을 없음으로 접어서 그 검사에 닿지 않는다(31.4).
13. 노트 경로 칸의 조각은 안 다듬고, 하위 노트 명령의 `parent` 조각은 다듬는다(11.8). 그래서 `{"parent":"ndfixture-00000001/ snfixture-00000001"}` 은 `list_attachments` 에서 하위 노트 id 모양 오류로 서고, `list_sub_notes` 에서는 통과한다.
14. 빈 칸(`""`)도 자리 인자 수에 든다. `["list-docs", ""]` 은 「자리 인자는 0 개인데 1 개를 받았다」로 선다.
15. 이름 인자의 이름은 다듬고 값은 안 다듬어서, `type =plan` 은 받고 `type= plan` 은 칸마다 다르다(9번). 이름이 공백뿐인 `=x` 는 빈 이름의 「모르는 옵션이다: .」로 선다.
16. 도구 표면의 값은 5.2를 안 거쳐서, 노트 경로 조각 `--x` 처럼 명령 표면이라면 버려질 값이 살아남는다(5.4).
17. 노트 경로 칸(첨부와 코멘트)의 2번째 조각은 직계 관계를 안 봐서 `노트id/손자id` 가 손자에 닿고, 사슬로 준 `노트id/자식id/손자id` 는 거절된다. 하위 노트 명령의 부모 참조는 거꾸로 사슬을 받고 마디마다 직계 관계를 본다(11.8). 같은 하위 노트를 가리키는 문법이 명령마다 갈린다.
