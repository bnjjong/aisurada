01

엔진이 하는 일

질문 1개를 받으면 vault 폴더를 처음부터 읽어서, JSON 답 1개를 쓰고 끝납니다.

읽기만 합니다

vault의 파일을 하나도 고치지 않습니다. create_doc 같은 쓰기 명령은 이름은 알아듣지만 WL-409로 거절합니다. serve 모드만 홈 아래에 실행 상태 파일과 소켓을 둡니다.

단발 모드는 부를 때마다 새로 뜹니다

명령 1개를 처리하면 프로그램이 끝나고, 다음 호출은 앞 호출에서 본 것을 기억하지 않습니다. serve 모드로 띄우면 떠 있는 채 요청을 받습니다(17장).

색인이 없습니다

원래 엔진은 노트 목록을 DB에 저장해 둡니다. 이 엔진은 그런 저장 파일 없이 부를 때마다 vault를 전부 다시 읽습니다(15장).

비유

도서관 사서를 떠올리면 쉽습니다. 「이 번호 책 정보 주세요」라고 하면, 사서는 목록 카드 없이 서가를 처음부터 끝까지 걸으며 책을 찾고, 정해진 양식에 적어 건넨 뒤 퇴근합니다. 다음 질문이 오면 새 사서가 와서 처음부터 다시 걷습니다. 서가에 손을 대지는 않습니다.

02

직접 불러 보기

데모 vault(노트 1개)에서 실제로 돌린 결과 · README.md

명령줄 한 줄이 질문이고, 화면에 찍히는 JSON과 종료 코드가 답입니다.

터미널
$ 1java -jar dist/wl-engine.jar 2get_doc 3'{"id":"nddemo-00000001"}' 4--withlog.vault=/path/to/vault
# 같은 일을 명령 이름으로 부르면
$ java -jar dist/wl-engine.jar get-doc nddemo-00000001 --withlog.vault=/path/to/vault
  1. 1
    엔진 띄우기
    Java로 jar 파일 하나를 실행합니다.
  2. 2
    이름
    무엇을 할지입니다. 밑줄(get_doc)은 도구 이름, 하이픈(get-doc)은 명령 이름입니다.
  3. 3
    인자
    도구 이름에는 JSON 1칸을, 명령 이름에는 맨 값이나 이름=값을 줍니다.
  4. 4
    설정 칸
    --로 시작하는 칸입니다. 여기서는 vault 위치이고, 환경변수 WITHLOG_VAULT로 줘도 됩니다.

id는 모양으로 종류를 압니다

노트

인자 읽기

설명서 5장 · 32.2 · args/ArgsParser · JsonReader

입구는 두 개, 출구는 하나입니다. 어느 모양으로 불러도 같은 ParsedArgs가 됩니다.

JSON 읽개의 규칙 · 표준 JSON과 조금 다릅니다

원래 엔진의 JSON 라이브러리(kotlinx.serialization 1.6.3)는 표준보다 조금 느슨합니다. 설명서가 그 동작을 규칙으로 적어 두어서, 이 엔진은 220줄짜리 JSON 읽개를 직접 짜서 같은 규칙을 따릅니다. 값은 글자, 맨 글자(리터럴), 객체, 배열 4갈래로 나눠 담습니다.

받음{"id":"x","id":"nddemo-00000001"}

같은 키가 두 번 오면 뒤의 값이 이깁니다. 이 호출은 노트를 찾아 성공합니다.

설명서가 토큰을 「머리말과 BOM까지 포함한 파일 전체 바이트의 SHA-256」으로 정했기 때문입니다. 글자로 풀고 BOM을 뗀 뒤에 지으면 같은 노트라도 다른 값이 나옵니다. 그래서 풀기 전에 먼저 짓습니다.

SnakeYAML은 따옴표 없는 2026-06-16을 날짜 객체로 바꿉니다. 그러면 원래 적힌 글자를 잃습니다. 자동 해석 규칙에서 날짜 하나만 빼서, created 같은 값이 적힌 글자 그대로 남게 했습니다.

「BOM 떼기」가 뭔가요

BOM은 파일 맨 앞에 몰래 붙는 보이지 않는 글자 1개입니다(U+FEFF, UTF-8 바이트로는 EF BB BF 3개). 윈도의 메모장 같은 일부 편집기가 UTF-8 파일을 저장할 때 붙입니다. 눈에는 안 보이지만 컴퓨터가 보면 첫 글자가 ---가 아니라 이 투명 글자입니다. 그냥 읽으면 「머리말이 없다」고 잘못 판단하기 때문에, 머리말을 자르기 전에 맨 앞의 투명 글자를 먼저 떼어 냅니다.

유지하는 계약

  • 소켓 프레임 errorCode가 stderr 추출값보다 우선이며 0도 명시적인 코드 없음입니다. CLI의 첫 WL 정규식 일치에는 로그/파일명 오인식 한계가 있습니다.
  • 종료 0이어도 stderr·warning·incomplete가 있을 수 있습니다. 성공 결과와 주의 정보를 함께 보존합니다.
  • 실패 stdout, 손상 JSON, 스키마 불일치는 앱 계약 오류이며 WL-500으로 변환하지 않습니다.
  • 응답 키 precondition과 요청 키 f1은 다릅니다. 앱은 해시를 만들거나 토큰을 trim/정규화하지 않습니다.
  • 파생 쓰기의 before가 보유 토큰과 일치할 때만 after를 이어받을 수 있습니다. 일치해도 본문 캐시는 따로 갱신해야 하므로 오래된 본문에 새 토큰만 붙여 재저장하지 않습니다.
  • WL-412는 보호 대상 본문 쓰기의 거절입니다. 선행 색인·git·쓴 쪽 기록까지 모두 없었다는 뜻은 아닙니다. 초안을 유지하고 최신 본문 위에 재적용합니다.
  • 명령 전체는 트랜잭션이 아닙니다. WL-500이나 응답 유실에서 부분 반영 가능성을 고려하고 상태를 확인해야 합니다.
  • reindex와 reindex-paths는 명령 표면 호출(args 배열)이며 JSON 객체로 호출하지 않습니다. paths는 공백·특수문자·중복·순서를 보존합니다.
  • scanned는 항상 indexed + unchanged의 합이며, removed는 삭제된 노트 수가 아닌 삭제된 색인 행 수입니다.
  • conflicts 항목에는 reason 키가 없어야 하며, reason이 있으면 계약 위반으로 거절합니다. skipped/conflicts가 있어도 프로세스 종료 0이므로 작업 완료와 손상 안내를 분리하여 소비합니다.
  • vault별 재조정은 1개만 실행되며 동일 예약 구간의 요청은 병합합니다. 실행 중 새 변경은 대기열에 보존하여 후속 실행으로 처리하며, full 응답도 새 이벤트를 지우지 않습니다.
  • 실패 시 직전 성공 보고서와 시각을 보존하고 자동 재시도를 돌리지 않으며 다음 명시적 복구 요청에서 full reindex로 재개합니다.
  • reindex-paths는 템플릿/회고/휴지통을 검사하지 않으므로 healthScope.templatesReviewsTrash:false로 기록하며 이전 full 검사 경고를 unverifiedPriorHealth로 보존합니다.

신선도에서 지킬 조건

  • 읽기나 엔진 시작만으로 색인이 맞춰지지 않습니다. 메타는 옛 색인이고 본문·토큰은 현재 파일일 수 있습니다.
  • scanned는 indexed+unchanged이고 removed는 노트 수가 아닌 색인 행 수입니다. skipped/conflicts/unsharded와 원문 경로·이유·순서를 보존합니다.
  • 종료 0이어도 손상·충돌 안내를 유지합니다. 실패한 재조정은 일부 색인 행이 반영됐을 수 있어 캐시를 빈 목록으로 교체하거나 최신으로 확정하지 않습니다.
  • reindex-paths의 mode:full fallback에는 회고·템플릿·휴지통 검사가 없습니다. 갱신 범위와 건강 검사 범위는 별도로 기록합니다.
  • 소켓 argv는 총 64칸입니다. 명령을 빼면 경로 63개, 세션 표식 2칸이 붙으면 61개입니다. 앱 이벤트 묶음은 전송 예산을 넘으면 full reindex로 전환하며, 201개를 그대로 보내 엔진 fallback을 기대하지 않습니다.
  • 앱은 meta.db를 직접 읽지 않습니다. 8-1/8-2에는 DB·파일 감시·VaultKey·UI·엔진 재구현을 추가하지 않습니다.

8-1/8-2 완료 기준: 명세의 full/paths 응답과 항목·건수 관계, 실패 전달, 원문 보존, vault별 세대 격리, 경합 방어, 예약 생명주기 논리적 무효화, 지원 범위 내 깊은 스냅숏 격리를 mock으로 검증하고 16개 파일 275개 테스트와 빌드를 통과시켰습니다. 7-1 미분류 쓰기 실패 정책 보완도 완료했습니다.
