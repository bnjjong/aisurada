# Rust 엔진 이전 3단계 W4a — 코멘트 쓰기(`create_comment`, `update_comment`, `delete_comment`)

## 요약

**결론:** 코멘트를 만들고, 고치고, 지우는 쓰기 3개를 Rust 엔진으로 옮겼다. Java 엔진과 합성 vault에서 **응답과 폴더 전체 바이트가 912건 모두 같다**(앞 묶음 포함, 456단계, 이 가운데 코멘트는 49단계). 쓰기 스위치(`AISURADA_ENGINE_WRITE=rust`)는 기본 꺼짐이라 앱의 동작은 그대로다. 실제 창 확인은 아직 못 했다([손 확인 안내](rust-engine-hand-check.md)).

[W3c 기록](rust-engine-step3-w3c.md)에 이어진다. 남은 W4는 휴지통 4개(`delete_doc`, `restore_doc`, `purge_doc`, `empty_trash`)다.

## 1. 하는 일

코멘트는 노트 폴더의 `comments.json`에, 후속 노트의 코멘트는 그 노트의 바로 위 노트 폴더의 `sub-comments/<후속 노트 id>.json`에 있다. 세 명령이 같은 인자(`id`, `subId`, `body`, `comment_id`, `anchor_quote`)를 받는다.

| 명령 | 하는 일 |
| --- | --- |
| `create_comment` | 코멘트를 더한다. `comment_id`를 안 주면 `cm…` 번호를 발급한다. 주면 모양을 검사하지 않고 그대로 받는다(Java가 그렇다. 단 모양이 틀린 id는 다음에 읽을 때 조용히 빠진다). 앵커 인용문은 공백뿐이면 저장하지 않는다. 본문은 20,000자, 앵커는 2,000자까지 |
| `update_comment` | 본문을 고치고 `editedAt`을 지금으로 찍는다(만든 시각보다 앞서면 만든 시각으로) |
| `delete_comment` | 코멘트를 지우고, **그 노트 본문에서 그 코멘트의 앵커 표시**(`<!--aisc:id-->`, `<!--/aisc:id-->`)도 걷어낸다. 본문이 바뀌면 응답에 `bodyBefore`·`bodyAfter` 확인 값이 들어간다. 마지막 코멘트를 지우면 파일이 사라진다 |

**검사 차례(Java와 같다):** 노트 id → 후속 노트 id 모양 → 고치기·지우기는 `comment_id` → 만들기·고치기는 본문(없음, 공백, 20,000자 초과) → 앵커 길이 → 노트 찾기 → 코멘트 파일 읽기(너무 크거나 JSON이 아니면 **409로 멈춘다**, 쓰면 있던 코멘트가 사라지기 때문) → 식별자 겹침·없음(409).

**지우기가 본문을 다시 쓰는 일**은 W3c의 후속 노트 지우기와 같은 부품(`write/sub_note.rs`)을 쓴다. 메인 노트는 자리를 안 옮기고, 후속 노트는 정식 폴더 이름으로 옮겨질 수 있다. 편집 도장은 새로 찍지 않는다. 본문이 마크다운이 아니면(JSON 노트) 앵커를 걷어낼 수 없어 409다.

| 부품 | 자리 | 하는 일 |
| --- | --- | --- |
| 명령 | `commands/comment_write.rs` | 세 명령과 코멘트 자리 풀기(후속 노트의 파일은 바로 위 노트 폴더 안) |
| 코멘트 파일 | `write/comments_file.rs` | 코멘트를 만든 시각과 id 차례로 놓아 `{"v": 1, "comments": [...]}`로 쓰기, 앵커 표시 걷어내기 |
| JSON 파일 글 | `write/json_out.rs` | 들여쓰기 두 칸, `"키": 값`, 끝 줄바꿈 하나. Java `JsonWriter.toFileBytes`와 같다. 휴지통 목록 파일에도 쓸 것이다 |
| 화면 | `data/commands.ts`의 `write.createComment`, `updateComment`, `deleteComment` | 호출 객체가 됐다. 옛 길로 풀면 노트와 후속 노트 id가 자리 인자로 풀린다 |

## 3. Java와 다르게 둔 것

- 코멘트 파일은 읽을 때 엄격한 JSON 읽개(`serde_json`)를 쓴다. Java는 느슨한 읽개(따옴표 없는 글, 주석 따위를 받는 쪽)를 쓰므로, 그런 모양의 파일은 Java가 읽고 Rust는 「내용이 JSON 이 아니다」로 멈춘다. 앱이 만든 파일은 늘 엄격한 JSON이라 닿지 않는다. 읽기 명령(`list_comments`)도 이미 같은 읽개다.
- 코멘트 시각의 시간대는 W3b처럼 OS 시간대(`TZ`)를 쓴다. 오프셋 글은 늘 `+09:00`이다(Java가 그렇다).
- AI 호출(`caller: ai`)에 대한 별도 규칙은 이 명령들에 없다.
- 스냅숏 쓰기는 안 옮겼다(스냅숏 설정이 켜지면 호스트가 쓰기를 Java로 보낸다).

## 4. 확인하지 못한 것과 남은 일

- **실제 앱 창에서 확인하지 못했다.** 손 확인 점검표에 코멘트 항목을 더했다(이슈 #54, #61).
- 두 프로세스가 같은 코멘트 파일을 동시에 쓰는 경합 시험은 하지 않았다(이슈 #63).
- 다음은 휴지통 4개(`delete_doc`, `restore_doc`, `purge_doc`, `empty_trash`)다.
