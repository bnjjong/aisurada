# 16장 개발 계획 — 직계 하위 노트 목록과 중첩 탐색

작성일: 2026-10-28

후속 검토에서 확인한 화면의 중복 색인 실행 및 공통 계층 네 문제는 [보완 완료](./review-workspace-fixes-2026-10-28.md)했다. 최신 검증은 24개 파일·587개 테스트와 빌드 통과다.

진행 갱신: **16-1~16-3 구현 및 재구현 엔진 대상 16-4 검증 완료**. 실제 엔진 통합을 포함한 22개 파일·558개 테스트와 빌드가 통과했다. [16장 구현 결과](./review-chapter-16-complete.md)에 실행 방법·화면 검증·원본 엔진 미검증 범위를 기록했다. 아래 현황과 작업 설명은 계획 작성 당시 기준이다.

목표는 `list_sub_notes` / `list-sub-notes`의 직계 목록을 손실 없이 받아, 메인 노트부터 하위 노트를 한 단계씩 탐색할 수 있게 하는 것이다. 16장은 읽기 계약이며, 앱이 디스크나 DB를 훑어 직계 관계·정렬·토큰을 재계산하지 않는다.

## 3. 16-1 — 응답 계약과 요청 클라이언트

첫 구현 요청의 범위다. 실제 엔진 호출·파일 접근·UI 없이 완료할 수 있다.

권장 API는 다음과 같다. 이름은 기존 구조에 맞춰 조정할 수 있다.

```typescript
interface ListSubNotesToolOptions {
  readonly parent: string;
}

interface ListSubNotesCommandOptions {
  readonly parent: string;
  readonly bodies?: boolean | string;
}

client.listSubNotesTool({ parent: 'ndfixture-00000001' });
// execute({ command: 'list_sub_notes', args: ['{"parent":"ndfixture-00000001"}'] })

client.listSubNotesCommand({
  parent: 'ndfixture-00000001/snfixture-00000001',

// execute({ command: 'list-sub-notes', args: [parent, 'bodies=true'] })
```

`bodies`는 boolean이면 소문자 문자열로, string이면 원문 그대로 보낸다. `' true '`, `''`, `'TRUE'` 등 엔진 문법 시험도 표현할 수 있으며, 반환 타입은 본문의 존재를 확정하지 않는다. boolean 입력의 편의와 원시 문자열 입력의 차이를 문서화한다.

### 3.2 응답 DTO와 validator

```typescript
interface SubNoteListLink {
  readonly to: string;
  readonly kind: string;
  readonly [extraKey: string]: unknown;
}

interface SubNoteListItem {
  readonly id: string;
  readonly ref: string;
  readonly type: string;
  readonly title: string;
  readonly created: string;
  readonly date: string;
  readonly time: string;
  readonly mins: number;
  readonly editedBy?: string;
  readonly editedAt?: string;
  readonly editedSessionId?: string;
  readonly format: string;
  readonly precondition?: string;
  readonly body?: string;
  readonly links: readonly SubNoteListLink[];
  readonly tags: readonly string[];
  readonly path: string;
  readonly [extraKey: string]: unknown;
}

interface ListSubNotesResponse {
  readonly parent: string;
  readonly subNotes: readonly SubNoteListItem[];
  readonly [extraKey: string]: unknown;
}
```

- `isSubNoteListItem`과 `isListSubNotesResponse`를 `ResponseValidator<T>`로 구현하고 `decodeResponse`에 전달한다. 최상위는 전용 필수 객체 봉투이므로 순수 배열과 불완전 목록을 다루는 `createListResponseValidator`를 재사용하지 않는다.
- 필수 문자열, 정수 `mins`, `tags` 모든 원소의 문자열, `links` 모든 원소의 `to`·`kind` 문자열을 검사한다. 빈 배열은 정상이다. 뒤쪽의 잘못된 원소도 검사하고 누락·null·타입 오류는 `schema_mismatch`로 처리한다. `path`는 색인된 원소에 필수로 취급한다.
- 선택 문자열은 키가 있으면 문자열을 요구하고, 누락을 null이나 빈 문자열로 채우지 않는다. markdown/html도 파일을 읽지 못하면 `precondition`이 없으므로 필수화하지 않는다. 토큰 문자열 형식이나 날짜·시각을 추측해 수정하지 않는다.
- validator는 구조 검증에 집중하며 `format`·`type`·`kind`에 확인되지 않은 열거 제약이나 `mins`에 독자적인 상한을 추가하지 않는다. 링크의 추가 키를 포함해 알려지지 않은 추가 키와 원문·순서를 유지한다.
- 본문 유무, json의 토큰 생략, 도장 쌍, `editedBy === 'app'`의 세션 생략, 코멘트나 메인 노트 전용 필드의 부재 등 생성 조건은 fixture·실제 엔진 검증에서 확인한다. 저수준 공통 응답형의 `body`는 선택적이며 `bodies=true`의 완전한 본문 취득을 타입만으로 보장하지 않는다. 추가 키 보존 정책과 명세의 생성 조건 검증을 구분한다.
- JSON의 키 순서·2칸 들여쓰기·끝 LF는 fixture의 기대 바이트로 비교하고 실제 응답 validator에서 강제하지 않는다. 빈 배열이나 취득 성공만으로 색인 건강 상태를 덧붙이지 않는다.

### 3.3 요청 생성과 런타임 입력 정책

- 도구는 필수 옵션 객체에서 `parent`만 JSON 객체 한 칸으로 보낸다. 명령은 부모 원문 한 칸 뒤에 지정한 `bodies=<값>`만 보낸다. shell 문자열을 만들지 않는다.
- `parent`의 빈 문자열·공백·잘못된 id·중복 `/`·조각 앞뒤 공백은 원문 전달한다. 부모 조각 해석·존재·직계 관계·층·`bodies` 문법과 오류 순서는 엔진이 판단한다. 클라이언트가 잘못된 문자열을 임의 WL 오류로 만들지 않는다.
- 일반 객체 또는 null prototype 객체만 받고, 필수 `parent`는 문자열이어야 한다. 명령의 `bodies`는 undefined면 생략하고 boolean/string만 받는다. null·타입 오류·미지원 키는 전송 전 로컬 `TypeError`로 거절한다. 미지원 키는 값이 undefined여도 거절한다. 특히 도구의 `bodies`, 양 표면의 `id`, `tier`, `limit`, `recursive` 등이 조용히 사라지지 않아야 한다.
- 명령의 부모가 `--`로 시작하거나 첫 `=`가 첫 글자 뒤에 있으면 5.2에서 설정/이름 옵션으로 읽힐 수 있으므로 전송 전 명시적인 로컬 입력 오류로 거절한다. 부모를 trim한 뒤 검사하거나 다른 문자열로 바꾸지 않는다. 첫 글자가 `=`인 값은 자리 인자로 보내 엔진이 판정하게 한다. 로컬 오류에는 엔진 WL 코드나 종료 코드를 붙이지 않는다.
- 잘못된 JSON·누락한 parent·null·모르는 키·자리 인자 초과·반복 옵션·설정 플래그 등 엔진의 원시 문법 검증은 명시적인 `Transport.execute` 호출로 따로 시험한다. NUL·플랫폼 argv 제한은 실제 전송부의 책임이다.
- 반환은 기존 `DecodedResponse<ListSubNotesResponse>`다. 성공 stderr, 원본 바이트, 실패 분류, 계약 위반과 전송 실패를 그대로 보존하며 자동 재조회·재시도·reindex를 추가하지 않는다.

### 3.4 fixture와 완료 기준

명세 예시 세 개를 서로 구분해 기록한다.

| fixture | 출처와 지위 |
|---|---|
| 메인 `0001` → 자식 `snfixture-00000001` | 16.6 명세 예시. 명세에서 수용 묶음이 잰다고 밝힌 값 |
| 자식 `snfixture-00000001` → 손자 `snfixture-00000006` | 16.6 코드 읽기로 계산한 예시. 실측 수용 출력으로 표시하지 않음 |
| 메인 `0002` → 빈 배열 | 16.6 명세 예시. 명세에서 수용 묶음이 잰다고 밝힌 값 |

세 예시의 토큰·path·ref·키 순서·UTF-8·2칸 들여쓰기·끝 LF 1개를 명세의 독립 기대 바이트와 대조한다. fixture 자신을 파싱 후 재직렬화한 값만으로 원본 바이트 정확성을 증명하지 않는다. 이번 저장소에서 수용 묶음을 실행한 결과와 명세가 보고한 측정 결과를 구분한다.

합성 fixture와 클라이언트 경유 테스트는 다음을 덮는다.

- 기본 메타, `bodies=true`의 본문 위치·원문, json, 파일 읽기 실패에 따른 토큰·도장 누락, 빈 tags/links, 옛 `.md` path, 도장·세션의 조건, 추가 키와 중첩 추가 키 보존.
- 형제 여러 개와 created 동률, 오프셋 때문에 글자 순서와 순간 순서가 다른 예시를 받아 응답 순서를 보존하는지 확인. 클라이언트 테스트로 엔진 정렬 구현을 검증했다고 주장하지 않는다.
- DTO의 필수 키 각각 누락·null·타입 오류, 선택 키 null, 비정수 mins, 잘못된 links/tags 및 뒤쪽 원소, 배열/null 최상위, 잘못된 봉투를 거절하는지 확인.
- 양 표면의 정확한 command·argv, 중첩 참조·공백·한글·NFC/NFD·줄바꿈·따옴표 원문, `bodies` 생략/true/false/빈 문자열/공백/대문자/잘못된 문자열 전달, 로컬 타입 오류·미지원 키·위험한 명령 자리 인자에서 전송하지 않는지 확인.
- 성공 stderr, 빈 stdout, 잘못된 JSON, 스키마 위반, 실패인데 stdout이 있는 계약 위반을 클라이언트를 통해 검증한다.
- 종료 3의 WL-400/404/409, 코드 없는 종료 2, 예상 밖 종료 1·미분류 실패, 소켓 WL 코드와 CLI stderr, pre_dispatch/in_flight 전송 실패 및 신호 종료를 주입해 공통 분류와 원본이 유지되는지 확인한다. 한 번 호출이 다른 표면이나 reindex 호출로 이어지지 않는지도 확인한다.

완료 기준은 위 테스트·공개 export·실행 가능한 README 예시, `npm test`와 `npm run build` 통과다. 16-1의 mock 테스트는 부모 검증 순서·층 검사·디스크 읽기·실제 정렬·수용 묶음의 실행을 증명하지 않는다.

## 4. 16-2 — 부모별 읽기 상태와 중첩 탐색

조회 함수를 주입받는 상태 모듈로 시작한다. 권장 위치는 `src/engine/reading/` 또는 기존 상태 구조에 맞춘 별도 모듈이다. 16-1의 저수준 클라이언트와 분리한다.

1. vault, 전체 부모 참조, 호출 표면, 본문 요청 설정과 요청 세대를 구분한다. 초기·로딩·성공 빈 목록·성공 목록·실패·이전 성공 보유 상태를 표현하고, 실패를 `[]`로 바꾸지 않는다. UI에서 허용할 본문 옵션은 boolean으로 제한해도 저수준 문자열 계약은 유지한다.
2. 자식으로 들어갈 때 응답 원소의 `ref`를 그대로 다음 `parent`로 보낸다. 하위 id만 전역 키로 사용하거나 디스크 path로 참조를 조립하지 않는다. 요청 원문과 정규화된 응답 `parent`는 구분해 저장하며 JavaScript trim으로 엔진 정규화를 흉내 내지 않는다.
3. 되돌아가기·breadcrumb는 실제로 방문한 부모 참조와 표시용 제목을 보관한다. 제목은 식별자로 사용하지 않는다. 자식이 있는지 표시하는 별도 필드가 없으므로 항목 존재만으로 자손 유무를 확정하거나 전체 트리를 선제 재귀 조회하지 않는다.
4. vault·부모·표면·본문 모드 전환, 같은 부모의 재조회에서 이전 요청의 늦은 성공·실패가 현재 결과를 덮지 못하게 한다. 구독자나 화면에서 받은 값의 변경이 다른 부모의 캐시에 전파되지 않도록 상태 소유권을 정한다.
5. 목록의 본문·토큰은 메타와 같은 판임을 보장하지 않는다. 메타 전용 결과에 토큰이 있어도 이전 본문과 자동 결합해 저장 기준 판을 만들지 않는다. 토큰 없는 빈 본문도 실제 빈 파일로 확정하지 않는다.
6. 외부 갱신 신호로 목록을 무효화하거나 다시 읽는 정책을 별도로 둔다. 신호 없이 목록이 완전한 최신값이라고 표시하지 않는다. 조상 이동·하위 노트 추가/삭제·부모 관계 변경 시 관련 부모 캐시의 재조회 범위를 정한다.

완료 기준: deferred mock으로 같은 부모 요청 역전, 부모·vault·표면·본문 모드 전환, 뒤로 가기, 빈 목록과 실패 구분, 이전 성공 보존, 결과 참조 격리 및 폐기된 요청 무효화를 검증한다. 실제 UI나 엔진 실행은 이 단위의 완료 조건이 아니다.

## 5. 16-3 — 앱 목록과 상세 연결

선행 조건은 16-2, 실제 앱 Transport, 안정적인 vault·메인 노트 선택 경로다. 기존 `DocRoute.tsx`에 목록 영역을 붙이되 실제 조회 경로와 함께 구현한다. 별도 mock 화면은 실제 연결 완료로 표시하지 않는다.

- 앱 조회는 기록 층도 읽을 수 있는 명령 표면을 기본으로 선택하고, 기본값은 메타만 요청한다. 읽기 전용 목록에 `bodies=true`를 자동으로 붙이지 않는다. 도구용 호출 경로가 필요하면 별도 유지하며 WL-409 때 명령으로 자동 우회하지 않는다.
- 현재 컨테이너의 직계 목록, 로딩·빈 상태·실패·이전 데이터의 상태를 표시하고, 받은 순서와 title·tags·links를 보존한다. 손자를 메인 노트의 직계로 평탄화하지 않는다. 존재하지 않는 부모와 자식이 없는 부모를 구별한다.
- 항목에서 하위 목록으로 들어가는 동작과 노트 상세를 여는 동작을 구분한다. 상세는 11.8 `get_sub_note`를 별도 구현한 뒤 현재 응답 `parent`와 항목 `id`를 전달한다. 전체 `ref`를 id 자리에 보내지 않는다. 코멘트는 상세에서 읽으며, 목록에 빈 comments를 만들어 붙이지 않는다.
- 중첩 경로를 라우트나 탭에 보관할 경우 현재 `/doc/:id`에 원시 `/` 참조를 끼워 넣지 않는다. vault·부모 참조를 보존하는 경로 또는 query 인코딩과 새로고침 복원을 설계한다. 엔진에 보내는 원문에는 URL 인코딩을 남기지 않는다.
- 8장 갱신 완료 뒤 관련 목록을 다시 읽는다. reindex 성공과 목록 읽기가 원자적 스냅숏은 아니며, 실패/보류 중에는 이전 결과를 최신으로 표시하지 않는다. 감시 미구현 단계에도 명시적인 다시 읽기 경로는 제공할 수 있지만 색인 갱신과 목록 재호출의 의미를 구별한다.
- 편집·저장은 하위 노트 쓰기 명세와 초안 상태가 준비된 별도 단계다. 목록 토큰을 메인 노트 `update_doc`의 f1로 연결하지 않는다.

완료 기준: 실제 화면에서 메인→자식→손자→되돌아가기, 기록 층, 빈 목록·오류·진단, vault 전환과 요청 역전을 확인한다. 상세 기능을 포함할 경우 11.8 전체 읽기 계약의 검증 결과도 별도로 남긴다.

## 6. 16-4 — 격리 환경의 실제 엔진 계약 검증

임시 vault·HOME·DB/state·작업 디렉터리를 분리하고, 사용한 엔진 빌드·플랫폼·전송 방식·fixture와 실제 측정 범위를 기록한다. 원본 엔진과 재구현 엔진의 결과는 구분한다. 재구현이 디스크를 바로 읽는 경우 16.9의 허용 차이와 원본의 색인 신선도 차이를 명시한다.

| 축 | 필수 검증 |
|---|---|
| 참조와 직계 | 메인→자식→손자, 빈 부모, `/`만 있는 값, 연속·끝 `/`, 조각 공백, 형제·손자를 잘못 둔 참조. 존재하는 메인의 빈 목록과 없는 메인의 WL-404 구분 |
| 검증 우선순위 | 없는 앞 조각 뒤에 잘못된 조각을 붙이면 앞의 WL-404가 먼저. 기록 층의 존재하는 하위 참조는 도구 WL-409, 없는 참조는 WL-404. 잘못된 `bodies`와 선행 목록 읽기 실패의 우선순위 |
| 표면과 문법 | 도구의 parent 필수·문자열·알 수 없는 키·인자 수, 명령의 옵션·자리 인자 수·반복 bodies, bodies 생략/빈 값/true/false/TRUE 및 5.3 공백 집합. WL 코드·문구·종료·빈 stdout을 16.4와 대조 |
| 순서 | 형제 2개 이상, created 동률의 id 차례, 서로 다른 오프셋으로 순간 순서와 글자 순서가 다른 데이터 |
| 저장 모양 | 자식 없는 메인, 옛 md/html 단일 파일 메인, json 메인 아래 markdown 자식, json 자식, 옛 단일 md 자식, 수동 변경 path, 중복 메인 id 승자의 자식, 색인에서 제외된 부모와 자손 |
| 본문과 도장 | 메타/본문 모드의 필드 차이와 키 순서, 항상 있는 빈 tags/links, 코멘트 미포함, 도장 쌍·app/App 세션 차이, json의 빈 body·토큰 없음 |
| 읽기 실패 | 파일 누락, 1,000,000바이트 경계, UTF-8 오류, 재현 가능한 I/O 오류에서 메타 보존·토큰/도장 생략·빈 body. `bodies=false`여도 토큰용 본문 읽기가 일어나는 점 확인 |
| 색인 낡음 | 색인 뒤 자식 추가·삭제·본문 변경·같은 path 다른 파일 교체 후 재조정 전후 비교. 메타/본문/토큰 혼합을 원자적 판으로 오인하지 않는지 확인 |
| 전체 실패 | 원소·참조 경로·컨테이너의 잡히지 않는 YAML 표기, 메인 HTML 첨부 읽기 실패가 명령 전체에 미치는 영향. 도구와 명령의 메인/하위 컨테이너 조합별 차이 확인 |

권한·OS 차이 때문에 I/O 실패를 재현하지 못하면 미검증으로 남기며, 합성 오류 응답을 실제 파일 실패 재현으로 기록하지 않는다. 이 명령의 코멘트 미포함과 실제 파일을 열지 않는 동작은 관찰 가능한 범위 또는 계측 근거를 구분한다.

공식 수용 묶음은 도구 표면 111건이다. 메인 노트 110개를 부모로 주는 목록과 잘못된 id 한 건이며, 실패는 종료 3과 빈 stdout만 측정한다. 중첩·층·명령 bodies·형제 순서·도장·낡은 색인은 그 묶음 밖이다. 실제 묶음을 확보해 실행한 경우에만 실행 결과를 기록하고, 위 추가 경계 검증과 분리한다.

## 7. 다음 개발 요청의 범위

**16-1의 타입·validator·두 표면 클라이언트·fixture·테스트·공개 export·사용 예시만 구현한다.** 첫 단위에서 부모 탐색 상태, UI, 11장 전체 읽기, 네이티브 전송, 색인·파일 파서 재구현이나 하위 노트 쓰기를 추가하지 않는다.

이 문서는 개발 계획이며, 단계별 구현 결과는 별도 검토 기록을 따른다.
