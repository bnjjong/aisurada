# 8장 기반 개발 계획 — 색인 재조정과 신선도

작성일: 2026-10-27

다음 목표는 **색인 재조정의 결과를 손실 없이 읽고, vault별 갱신 상태를 추적해 낡은 목록을 최신이라고 취급하지 않는 것**이다. 먼저 reindex 응답 validator와 명령 클라이언트를 구현하고, 그 위에 앱의 재조정 정책을 연결한다.

근거: [8장 명세](./spec-chapter-08-index-and-freshness.md), [4장 프레임](./spec-chapter-04-socket-protocol.md), [5장 인자](./spec-chapter-05-arguments.md), [6장 출력](./spec-chapter-06-output-and-errors.md), [7장 계획](./plan-chapter-07-write-pipeline.md).

## 1. 현재 상태와 우선순위

- src/engine에는 공통 Transport·decodeResponse·validator, 봉투 검사, 회고 읽기, 쓰기 토큰/결과 정책이 있다.
- reindex DTO·명령 클라이언트·vault 재조정 상태·실제 파일 감시·네이티브 실행부는 없다.
- 2026-10-27 재실행: `npm test` 10개 파일·146개 통과, `npm run build` 성공.
- 7-1의 미분류 실패를 본문 미변경으로 판단하는 문제, 미정의 종료/WL 조합을 충돌로 확정하는 문제는 여전히 보완 대상이다. 8-1 읽기 계약 준비와 독립적이지만 실제 저장/갱신 연결 전에 고쳐야 한다.
- 세션 목록의 30초 TTL은 Claude 세션 캐시다. 노트 색인 신선도와 같은 상태로 재사용하지 않는다.

요청에 따라 다음 개발은 **8-1**로 진행한다. 6장 회고 UI와 7-2 초안 상태 관리는 별도 후속 작업으로 유지한다. 이번 계획에서 앱에 SQLite나 엔진을 새로 도입하지 않는다.

## 2. 설계에서 구분할 것

| 구분 | 규칙과 앱에 주는 의미 |
|---|---|
| 색인의 소유자 | 엔진이다. 앱/CLI는 meta.db·WAL·스키마 표를 직접 열지 않는다 |
| 원본과 파생물 | vault 파일이 원본이고 색인은 파생물이다. 앱 메모리 캐시는 그 위의 별도 계층이다 |
| 읽기 | 엔진 시작이나 읽기 명령만으로 색인은 갱신되지 않는다 |
| 메타와 본문 | 존재·메타는 마지막 색인, 본문·토큰·도장·코멘트는 호출 시 파일에서 올 수 있다. 한 응답을 같은 시점의 스냅숏이라고 보장하지 않는다 |
| 색인 밖 자료 | 회고·템플릿·휴지통·사실층·4부 파일은 별도 읽기다. 노트 색인 세대만으로 이 캐시를 최신이라고 표시하지 않는다 |
| 재조정 성공 | skipped/conflicts가 있어도 종료 0이다. 작업 완료와 vault 건강 상태를 분리한다 |
| 재조정 실패 | 일부 행은 이미 반영됐을 수 있다. 이전 캐시를 유지하되 상태가 불확실함을 기록한다 |
| removed | 지운 색인 행 수다. 지워진 노트 id 목록이나 노트 개수로 사용하지 않는다 |
| 쓰기 후 읽기 | 성공 쓰기 뒤에도 1건 맞추기가 실패해 옛 메타가 나올 수 있다. 저장 성공 토큰과 재조회 메타가 늘 동기라고 가정하지 않는다 |

skipped에 나온 노트를 목록 캐시에서 임의로 제거하지 않는다. 본문 파일이 남으면 옛 색인 행이 유지되는 8.7의 경우가 있기 때문이다. 반대로 빈 본문이나 토큰 없음만 보고 삭제·빈 노트 덮어쓰기를 실행하지 않는다.

## 3. 8-1 — 재조정 응답과 명령 클라이언트 (바로 다음 개발 단위)

### 3.1 파일과 API

권장 파일:

- `src/engine/indexing/types.ts`: reindex 응답·항목 타입.
- `src/engine/indexing/validators.ts`: 순수 타입 가드.
- `src/engine/commands/reindex.ts`: Transport 주입 클라이언트.
- `src/engine/__fixtures__/chapter08/`: 명세 예시·합성 경계 자료.
- 관련 테스트, 공개 export, README의 타입 검사되는 사용 예시.

API 권장안:

```typescript
createReindexClient(transport).reindex()
// execute({ command: 'reindex', args: [] })
// Promise<DecodedResponse<FullReindexResponse>>

createReindexClient(transport).reindexPaths(paths)
// execute({ command: 'reindex-paths', args: [...paths] })
// Promise<DecodedResponse<ReindexResponse>>
```

두 명령 모두 명령 표면이며 JSON 객체를 인자로 붙이지 않는다. `reindexPaths([])`는 명세상 아젠다만 맞출 수 있는 paths 호출이다. 저수준 클라이언트가 몰래 full reindex로 바꾸지 않는다.

클라이언트는 받은 경로의 순서·공백·중복·문자를 유지하고, `..` 정리·trim·필터링·경로 접기를 엔진 대신 구현하지 않는다. 빈 입력과 특수 문자의 엔진 동작을 재현하는 호출도 가능하게 한다. 감시 이벤트에서 안전한 명령을 고르는 정책은 8-2에 별도로 둔다.

### 3.2 응답 검사

필드 순서는 `mode → elapsedMs → agendas → scanned → indexed → unchanged → removed → skipped → conflicts → unsharded`다. 이 순서는 fixture에 기록하고 실제 값 검사와 구분한다.

| 필드 | validator 규칙 |
|---|---|
| mode | full 또는 paths. reindex() 응답은 full만 허용하고 reindexPaths()는 둘 다 허용 |
| elapsedMs, agendas, scanned, indexed, unchanged, removed | 0 이상의 정수. scanned === indexed + unchanged |
| skipped | 모든 원소의 kind/path/reason 필수. path/reason은 문자열 원문 유지 |
| skipped.kind | agenda, note, docTemplate, ritualTemplate, review, trash |
| conflicts | 모든 원소의 kind/path 필수. kind는 note 또는 review. reason은 이 항목에 없는 키이므로 있으면 계약 위반 |
| unsharded | 모든 원소가 문자열인 배열 |

공통 원칙:

- 기존 ResponseValidator<T> 순수 타입 가드와 decodeResponse를 재사용한다. 잘못된 응답은 schema_mismatch이고 새 WL 코드로 만들지 않는다.
- 배열 여부만 검사하지 말고 모든 항목을 검사한다. 빈 배열은 허용한다.
- kind의 대소문자는 위 계약 그대로다. docTemplate/ritualTemplate을 소문자로 바꾸지 않는다.
- 경로·이유·행 순서를 변환하지 않는다. unsharded도 정렬해 돌려주지 않는다.
- 상세 reason 문구의 열거 목록을 validator에 박지 않는다. 손상 안내는 kind 및 경로로 구조화하고 원문 이유를 표시할 수 있게 한다.
- 알려진 필드의 잘못된 값은 거절하되, 미정의 추가 키는 원본에 보존한다.
- 정확한 건수·elapsedMs 값은 구현별·실행별로 달라질 수 있다. 110이나 특정 경과 시간을 실제 응답에 강제하지 않는다.
- 일괄 표식 확인·색인 재조정·쓴 쪽 기록을 클라이언트에서 중복 수행하지 않는다. 두 명령은 쓰기 깃발이 없다.

### 3.3 fixture와 테스트

8.4의 full 응답을 예시 fixture로 관리한다. elapsedMs는 예시이고, 나머지도 코드 읽기로 구성된 값이며 공식 묶음이 응답 바이트를 검증한 값이 아님을 기록한다. paths·200개 초과 fallback·오류 사례는 합성 fixture로 표시한다.

필수 테스트:

- 명령 이름/argv: reindex 인자 없음, paths의 0/1/여러 경로·순서·문자 원문 보존.
- full/paths 응답, paths 요청의 full fallback, reindex 요청의 paths 응답 거절.
- 빈 배열, skipped 6종, conflicts 2종, unsharded 문자열, 추가 키 보존.
- 음수·소수·문자열 숫자, scanned 불일치, 필수 키 누락, 배열 뒤쪽의 잘못된 항목.
- 잘못된 kind, conflicts의 reason, 손상 안내가 있어도 성공과 stderr 동시 유지.
- WL-400/500, 미분류 엔진 실패, 전송 실패, 스키마 오류를 원본과 함께 반환.
- 키 순서·들여쓰기·끝 LF가 고정된 fixture 바이트와 일치. 실제 엔진 출력 생성 검증으로 확대하지 않는다.

완료 기준: 기존 146개 동작 및 신규 테스트, `npm test`, `npm run build`가 통과한다. mock 주입만으로 응답을 읽고 손상 정보를 소비할 수 있으며 화면·DB·실제 감시 없이 완성한다.

## 4. 8-2 — vault별 재조정 코디네이터

구체적인 공개 API·세대/경합·실패·paths 정책과 검증 기준은 [8-2 상세 계획](./plan-chapter-08-task-02.md)을 따른다. 8-1은 [완료 검토](./review-chapter-08-task-01.md)에서 175개 테스트·빌드 통과를 확인했다.

8-1 뒤에 별도 개발한다. React/Zustand에 직접 결합하지 않는 상태·주입 가능한 클라이언트부터 검증한다.

### 트리거와 기본 정책

- vault 열기, 바깥 파일 변경, 수동 새로고침, 완료 불확실 상태의 복구를 재조정 사유로 구분한다.
- 첫 버전은 명세가 설명하는 현재 앱처럼 full reindex를 기본으로 한다. focus·탭 전환·개별 읽기마다 전체 훑기를 반복하지 않는다.
- 엔진 시작만으로 완료 상태를 만들지 않는다. reindex 성공 전에는 미확인/갱신 필요 상태다.
- 타이머/감시를 직접 만들지 않고 이벤트와 시계·실행 함수를 주입한다. 실제 감시와 debounce 수치는 8-3에서 정한다.

### 상태와 경합

- vault별로 실행 1개, 실행 중 추가 변경 여부, 요청 세대, 마지막 성공 보고서, 마지막 실패를 분리한다.
- 같은 vault의 중복 요청은 합치고 다른 vault와 섞지 않는다. 이벤트가 실행 중 들어오면 다음 실행 필요성을 남긴다.
- full 성공으로 비울 수 있는 대기는 그 요청이 시작할 때 포착한 범위까지다. 실행 중 새 이벤트를 최신 결과라고 처리하거나 대기열에서 지우지 않는다.
- 이전 vault/세대의 늦은 결과는 현재 상태를 덮지 않는다.
- 실패하면 캐시를 빈 목록으로 덮거나 마지막 성공 시각을 갱신하지 않는다. 부분 색인 가능성을 기록하고 이후 명시적 재조정 경로를 제공한다.
- skipped/conflicts/unsharded는 갱신 결과 보고서로 보존한다. 성공 종료와 건강 안내를 독립적으로 표현한다. paths의 빈 unsharded를 vault 전체에 문제가 없다는 뜻으로 해석하지 않는다.

### 선택적 paths 최적화

처음부터 활성화하지 않는다. 도입 시 다음 조건을 충족해야 한다.

- `reindex-paths`에서 첫 글자가 아닌 곳의 `=`는 옵션으로, `--` 시작은 설정으로 처리된다. 감시 경로를 이 문법으로 안전하게 전달할 수 없으면 앱 정책으로 full reindex를 선택한다. 저수준 클라이언트의 계약은 바꾸지 않는다.
- 경로를 넘긴 뒤 실제 삭제/이동 접기·정리는 엔진에 맡긴다. 실패 이유를 문자열로 추측해 보정하지 않는다.
- 프로토콜 상한은 argv 64칸이다. 명령 1칸을 빼면 최대 63개 경로, 세션 표식 2칸이 붙으면 최대 61개다. transport가 허용 예산을 제공하도록 하고 모르면 보수적으로 61개를 사용한다. 인자 1칸의 UTF-8 1MiB 상한과 CLI 전체 argv 제한도 실제 전송부에서 검사한다.
- 따라서 소켓에서 201개를 그대로 보내 엔진의 200개 초과 fallback을 기대하면 안 된다. 이벤트 묶음이 예산을 넘으면 full reindex로 전환한다. 임의 chunk 분할은 후속 최적화로 남긴다.
- 응답 mode:full은 갱신 범위가 전체였다는 뜻이다. reindex-paths fallback에는 템플릿·회고·휴지통 검사가 없으므로 건강 검사 범위는 요청 명령과 함께 기록한다. 필요하면 전체 reindex가 별도로 필요하다.

완료 기준: deferred mock으로 이벤트 병합·실행 중 추가 이벤트·늦은 결과·vault 전환·실패 후 상태·전송 예산·fallback 건강 범위를 검증한다. 데이터 손상 안내를 완료 0으로 숨기지 않는다.

## 5. 8-3 — 실제 감시와 화면 재조회

선행 조건: 실제 네이티브 Transport·파일 감시, 노트 목록/상세 스키마(9~11장), 7장 쓰기 결과 보완과 초안 보존 정책.

1. vault 열기와 외부 변경 이벤트를 코디네이터에 연결한다. 감시하는 저장소와 노트·아젠다·회고·템플릿·휴지통 영역을 구분한다.
2. `.tmp` 같은 무시 대상은 해당 규약에 따라 감시부에서 제외한다. 이벤트가 발생했다는 이유로 에디터 초안을 외부 본문으로 덮지 않는다.
3. reindex 결과의 path/reason·conflicts·unsharded 안내를 표시한다. 숫자는 통계/진단이며 removed만큼 노트를 삭제하는 UI 처리를 하지 않는다.
4. 성공한 뒤 관련 목록·메타를 재조회하고 열린 노트는 필요한 경우만 본문을 읽는다. 회고/템플릿/휴지통은 자체 변경 이벤트와 읽기 경로로 따로 갱신한다.
5. 쓰기 성공 뒤 읽기가 낡거나 토큰이 없으면 새 토큰으로 옛 본문을 덮지 않는다. 쓰기 응답 토큰과 확인된 기준 판을 유지하고 재조정·재읽기를 거친다.
6. 부분 색인 실패 뒤의 WL-404는 파일 부재의 충분한 근거가 아니다. 실패한 갱신 상태를 함께 보고하고 새 노트를 자동 생성하지 않는다.

완료 기준: 격리 vault에서 손편집·이름 변경·삭제·동기화 충돌·전체 재조정 실패를 재현하고, 기존 초안과 손상 안내가 보존되는 것을 확인한다. mock 검증과 실제 파일 감시 검증을 구분한다.

## 6. VaultKey와 엔진 구현의 별도 작업

VaultKey 공식은 소켓·실행 상태 이름에 쓰이므로 계약이다. 그러나 현재 앱은 주입받은 vaultId로 상태를 구분하면 충분하다. 8-1에서 해시/경로 공식이나 SQLite를 불필요하게 추가하지 않는다.

실제 네이티브 연결을 만들 때는 아래를 독립 검증한다.

- 절대 경로화와 .·..의 글자 정리, 끝 / 제거, 심볼릭 링크 미해결, NFC/NFD 미정규화.
- UTF-8 SHA-256 앞 16자리와 Java Locale.ROOT 소문자/UTF-16 이름 조각 규칙. JS 기본 소문자화가 모든 경계에서 같다고 가정하지 않는다.
- 8.2의 6개 기대값과 İ/켈빈 기호·한글·루트·40자 잘림·NFC/NFD 차이.
- 현재 엔진의 DB와 별도 구현의 상태 파일을 공유하지 않음. 구현 상태는 실제 하네스/런타임이 지정한 자리에 두며 vault에 DB를 만들지 않음.

엔진을 직접 구현한다면 다음은 별도 범위다.

| 절 | 필요한 구현·검증 |
|---|---|
| 8.1~8.2 | SQLite 여부 선택, 파생 표·스키마 수명·동시 접근. 앱/CLI의 DB 직접 접근 금지 |
| 8.3 | 아젠다→후보→mtime/size/첨부 관문→열기→해시 관문→정리 순서. 모든 파일이 사라진 경우 정리 보류 |
| 8.4 | full reindex의 템플릿·회고·휴지통 건강 검사, 배열 순서, 중간 실패의 부분 색인 보존 |
| 8.5 | raw 인자 200개 경계, 경로 다듬기·조각 결합·노트 접기·중복 제거·정리 범위·늦은 삭제 보호 |
| 8.6 | 색인 없는 구현 허용 범위와 상태 경로, 병렬 읽기, 읽기 전용 레인의 vault/HOME 무변경 |
| 8.7 | 프로젝트 재구축 부재, 깨진 파일 옛 행 유지, 같은 크기/mtime 편집, 사라진 하위 노트, 같은 id 승자, 부분 색인 읽기 |

색인 없는 aisurada Java 구현과 SQLite 기반 기존 엔진의 낡음 차이를 한쪽 버그로 임의 교정하지 않는다. 부록 D의 결정 전 8.6이 허용하는 차이를 기록한다.
